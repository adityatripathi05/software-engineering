## Concept

### Plain-English Explanation

Everything in this module so far has one shape: a request arrives, a response leaves, the exchange is over in milliseconds. A WebSocket starts as exactly that — one HTTP request — and then refuses to end: server and client upgrade the connection and keep it open, sending each other messages for minutes or hours. Ledgerly's dashboard uses one to watch operations (02.10) progress live instead of polling.

The mental adjustment is bigger than the API. After the upgrade, **HTTP is gone**: no status codes, no error bodies, no per-request retries, no RFC 9457. The entire vocabulary that modules 02 and 03.8 built for talking about failure has to be rebuilt from the only material left — frames, and a two-byte **close code**.

### Technical Explanation

**The handshake is an HTTP request** — a GET with `Upgrade: websocket` — and FastAPI treats it as one: `@app.websocket("/ws/operations")` routes it, and dependencies (03.5) run before your handler. This is the last moment HTTP exists, and the last moment you can reject with an HTTP response. Captured: a dependency raising `HTTPException(403)` produces an HTTP **denial response** — the client's library reports `WebSocketDenialResponse`, a browser sees a failed fetch. A dependency raising `WebSocketException(code=1008, reason=...)` instead rejects at the WebSocket layer:

```text
3.  WebSocketException(1008) from dependency
    client sees close code=1008 reason='invalid credentials'
3b. HTTPException(403) from a websocket dependency
    client raised WebSocketDenialResponse
```

**Browser reality shapes authentication.** The browser `WebSocket` API cannot set an `Authorization` header. The dashboard authenticates the handshake with its session cookie (01.5) — which the browser attaches automatically, cross-site rules permitting. That "automatically" is a threat: ⚠️ **CORS does not apply to WebSockets.** No preflight, no `Access-Control-*` gate — any origin can open a socket and the cookie rides along. The server must check the `Origin` header itself against the 01.9 allow-list, or any page on the internet can hold an authenticated feed (cross-site WebSocket hijacking; 16.x returns to it). Tokens in query strings work for non-browser clients but land in access logs (16.13) — prefer cookies or a first-message credential.

**After `accept()`, the vocabulary is frames and close codes:**

| Code | Meaning | Who sends it |
|---|---|---|
| 1000 | Normal closure | Either side, on purpose |
| 1001 | Going away | Server at shutdown/deploy (04.9) |
| 1008 | Policy violation (auth, limits) | You, explicitly |
| 1011 | Server error | You, explicitly — see below |
| 4000–4999 | Application-defined | You — your error catalogue's WS dialect |
| 1006 | Abnormal closure | ⚠️ **Nobody.** The browser *synthesises* it when the connection died with no close frame |

The last row is the one that runs the incident. Captured over a real socket: when a handler raises an unhandled exception after `accept()`, uvicorn logs `Exception in ASGI application` and the TCP connection simply drops — **no close frame at all**:

```text
/ws/strict: NO close frame — abrupt TCP drop (a browser reports this as 1006)
```

To the client, your bug is *indistinguishable from a network failure* — and network failures are precisely what client reconnect logic is built to retry. An explicit close, by contrast, arrives intact and says what it means:

```text
/ws/tolerant: closed code=4400 reason='unrecognised message; see /docs/ws'
```

**Disconnection is an input, not an error.** `receive_*()` raises `WebSocketDisconnect` when the peer leaves (captured: `code=1000` on a clean close); the canonical loop catches it and runs cleanup. Sending after close raises `RuntimeError: Cannot call "send" once a close message has been sent` — connection state is real state, and your code holds it.

> **Version note** — captured on uvicorn 0.46 using its default WebSocket implementation, the `websockets` library (16.0 here), which sends protocol-level keepalive pings (`ping_interval=20` by default). The `wsproto` fallback does not — and idle proxies (01.10) kill quiet connections at *their* timeout regardless of which side pings. The keepalive/proxy interplay is treated properly in module 12.

### Mental Model

> A WebSocket is an HTTP request that never finishes. Until `accept()`, you still have HTTP — dependencies, 403s, one last chance to refuse politely. After it, you have frames, close codes, and state. Everything HTTP gave your errors for free — identity, blame, retryability — you now provide by hand, and the cost of not providing it is a 1006: *your bug, wearing a network failure's face*.

## How It Works

One connection's life against the operations feed, with every exit labelled:

```text
GET /v1/ws/operations  Upgrade: websocket        ← still HTTP: routing, deps (03.5)
  ├─ dep raises HTTPException      ──▶ HTTP denial response (no socket ever exists)
  ├─ dep raises WebSocketException ──▶ close frame 1008 + reason
  ▼
accept()                                          ← HTTP ends here
  ════ open: minutes-to-hours; a NEW resource class (memory + fd per conn) ════
  │  reader task:  receive_json() ─▶ subscribe / ping / garbage
  │  writer task:  events queue  ─▶ send_json(operation updates)
  ├─ client leaves        ──▶ receive raises WebSocketDisconnect(1000/1001) → cleanup
  ├─ we reject a message  ──▶ close(4400, reason)          client KNOWS: don't resend that
  ├─ we hit our own bug   ──▶ ⚠️ unhandled: NO frame → client sees 1006 → retries as if
  │                            the network blipped → next crash → retry → storm
  └─ deploy (03.9)        ──▶ close(1001) at shutdown; EVERY connection, EVERY deploy
```

Two structural consequences deserve prose. First, the reader and writer are **separate tasks**: a handler blocked in `receive_json()` cannot push events, so a push feed that also listens (pings, subscription changes) needs both directions running concurrently — `asyncio.TaskGroup` with the 03.8 caveat about `ExceptionGroup` wrapping. Second, the bottom line of the diagram: deploys sever every open connection at once. With 03.9's lifecycle in mind, **reconnection is not recovery from the exceptional — it is a scheduled, fleet-wide event several times a week**, and the client logic that handles it (backoff, jitter, resubscribe) is part of the server team's contract, not an afterthought in the JS.

Connections are also a budget in the 03.6 sense: each holds a file descriptor and buffers for its lifetime, per process, and none of it shows up in requests-per-second thinking. The arithmetic before shipping: `expected concurrent dashboards ÷ replicas` versus per-process memory and fd limits — written in the PR, like the other budgets. Fan-out beyond one process (an event must reach sockets on other replicas) is deliberately out of scope here: that is Redis pub/sub (10.15) wired up in module 12.

## Code Example

The handshake dependency — cookie identity plus the Origin check CORS will not do for us:

```python
# ledgerly/deps.py (continued from 03.5)
async def get_ws_tenant(ws: WebSocket) -> TenantId:
    """Auth for WebSocket handshakes. Browser sockets cannot send Authorization
    headers; identity rides on the session cookie (01.5). CORS does NOT gate
    WebSockets, so the Origin check is ours to make (01.9, 16.x)."""
    if ws.headers.get("origin") not in settings.cors_allowed_origins:
        raise WebSocketException(code=1008, reason="origin not allowed")
    session_token = ws.cookies.get(settings.session_cookie_name)
    if session_token is None:
        raise WebSocketException(code=1008, reason="not authenticated")
    return await resolve_session_tenant(ws.app.state.redis, session_token)
```

The feed itself — reader and writer as peer tasks, and every exit an explicit frame:

```python
# ledgerly/routers/operations_ws.py
@router.websocket("/ws/operations")
async def operations_feed(ws: WebSocket, tenant: Annotated[TenantId, Depends(get_ws_tenant)]) -> None:
    await ws.accept()
    events: asyncio.Queue[OperationEvent] = asyncio.Queue(maxsize=256)   # bounded: 12.x
    try:
        async with asyncio.TaskGroup() as tg:                            # 03.8's caveat applies
            tg.create_task(read_client(ws, tenant, events))
            tg.create_task(push_events(ws, tenant, events))
    except* WebSocketDisconnect:
        pass                                          # the client left; an input, not an error
    except* Exception:
        logger.exception("ws_feed_crashed", extra={"tenant": tenant})
        with suppress(RuntimeError):
            await ws.close(code=1011, reason="internal error")   # a FRAME, not a TCP drop
    finally:
        await subscriptions.drop_all(tenant, ws)      # cleanup runs on every exit path
```

The `except* Exception` block is this notebook's 03.8 lesson transposed: there is no `ExceptionMiddleware` to save a socket — an escape here is an abrupt drop, so the handler is its own last handler, converting bugs into an explicit 1011 the client can at least distinguish from wifi.

And the reader's message handling — tolerant where the contract permits, explicit where it doesn't:

```python
async def read_client(ws: WebSocket, tenant: TenantId, events: EventQueue) -> None:
    while True:
        raw = await ws.receive_json()                 # WebSocketDisconnect ends the loop
        match parse_client_message(raw):              # tolerant reader: ignores unknown
            case Subscribe(operation_id=op):          #   extra fields (02.3)
                await subscriptions.add(tenant, op, ws)
            case Ping():
                await ws.send_json({"type": "pong"})
            case Unparseable(reason=reason):
                await ws.close(code=4400, reason=reason)   # deterministic: don't resend
                return
```

`4400` is doing the job the error catalogue (02.9) does over HTTP: a stable, documented identity that tells the client this close is *its payload's fault* — deterministic, not retryable-as-is — as opposed to 1011 (our fault) or 1001 (nobody's fault, reconnect freely). Publish the taxonomy next to the problem types; module 12 grows it.

## Design Patterns / Tradeoffs

### Rejecting work: before vs after `accept()`

Pre-accept you have HTTP: an `HTTPException` becomes a denial response with a real status — visible to proxies, curlable, cheap. Post-accept you have only frames. So the pattern: **everything knowable at handshake time is decided at handshake time** — auth, origin, tenant limits, even "is this feature enabled for you" — via dependencies raising `WebSocketException`/`HTTPException`. Message-level policy (what you may subscribe to) necessarily lives post-accept, in the 4000-range vocabulary. The anti-pattern is accepting first and interrogating later: it spends a connection slot on a client you were always going to reject, and at reconnect-storm rates that difference is the fleet.

### Push-only vs request-reply over the socket

- **Push-only feed** (plus client pings): one obvious writer, trivial reader, the shape above. *Use for:* live status, notifications — Ledgerly's case.
- **Request-reply over WS** (client sends commands, awaits results): now you own correlation ids, per-message timeouts, ordering, and error frames — a private RPC protocol, hand-rolled. *Use when:* genuinely bidirectional interaction (12.x's console). *Do NOT use* to tunnel what is naturally a REST call: `POST /v1/invoices` over a socket forfeits idempotency keys, HTTP retries, caching, and the entire 02-module contract for zero gain.

### Do you need a WebSocket at all?

The owned comparison — WebSocket vs SSE vs long polling — is 12.6's, but the boundary rule belongs here because it is the most common design review comment: **server-to-client-only data does not need a WebSocket.** Operation progress could ride Server-Sent Events (02.10, 12.4) — plain HTTP, proxy-friendly, auto-reconnecting. Ledgerly's dashboard uses the socket because module 12's features (presence, typing, commands) are coming; if yours are not, reach for SSE first and keep HTTP's whole toolbox.

**Recommendation:** decide rejections at the handshake; keep the socket push-only until interaction forces request-reply; and let 12.6 talk you *out* of the socket when one direction suffices.

## Production Scenario

**Ledgerly, Tuesday 22 September, 11:40.** A release tightens the operations feed: incoming messages now validate against a strict Pydantic model (`extra="forbid"`) — hygiene, prompted by 16.3's input-validation review. At **11:41**, Redis latency alerts fire. By **11:43**, API p99 is degrading for *HTTP* endpoints, support reports "dashboards flickering", and the error log is scrolling the same traceback hundreds of times a second.

### Symptoms

- Uvicorn logs, at flood volume: `Exception in ASGI application` → `ValidationError: ... v  Extra inputs are not permitted [type=extra_forbidden]`.
- Browser consoles fleet-wide: connections closing with **1006 (abnormal closure)** immediately after subscribing — then reconnecting, instantly.
- Handshake rate on `/v1/ws/operations`: from ~6/s to **~7,000/s**. Roughly 2,600 dashboards are open; each is cycling connect → subscribe → drop about three times a second.
- Redis (which every handshake consults via `get_ws_tenant`, 03.5): CPU saturated — and since HTTP auth shares it, *all* authenticated traffic slows. The storm's damage arrives through the handshake's dependency cost, not the sockets themselves.

### Diagnosis

1. **Alert → Metrics.** Redis saturation with flat business traffic; the request-rate anomaly isolates to WebSocket handshakes. Something is making every dashboard reconnect continuously.
2. **Logs.** The traceback names the deploy: the strict subscribe model rejects a field `v` — which the dashboard JS has sent in every subscribe message for a year (a client-build version tag; the old server ignored it). The validator raises; nothing catches it on a socket; the connection drops with no frame.
3. **The 1006 is the accelerant.** Because no close frame arrives, the dashboard's reconnect logic — written for flaky wifi — classifies each drop as a network failure and retries *immediately*; its backoff (latent bug, never before exercised at scale) only engaged for failed *handshakes*, and the handshakes all succeed. Deterministic bug + network-failure semantics + no backoff = 2,600 clients in a tight loop.
4. **Eliminated:** Redis as cause (victim of handshake load — it serves fine at normal rates), the network (only WS routes cycling), and capacity (sockets barely register; it is the *per-handshake auth work* that burns).

### Root Cause

A strict validator turned a harmless, long-standing extra field into an unhandled exception on an accepted socket — which uvicorn surfaces as an abrupt TCP drop, not a close frame. Clients saw 1006, applied network-failure retry semantics to a deterministic server rejection, and converted one line of validation into a fleet-wide authenticated-handshake storm whose cost landed on shared Redis.

### Fix

*Mitigation (11:52):* roll back the release — the crash is in the new validator, so this works (unlike 03.9's latent gate). Reconnects succeed, dashboards stabilise within a minute, Redis recovers. A per-tenant handshake rate limit (10/min, 02.12 machinery) goes in at the edge the same hour, so no future loop — whatever its cause — can reach four digits per second.

*Permanent fix:*

1. Message validation becomes a **tolerant reader** (02.3, the Code Example): known fields extracted, unknown fields ignored — the same compatibility posture the HTTP API has held since module 02, now applied to frames. Genuinely unparseable messages get `close(4400, reason)`: a deterministic verdict the client must not blind-retry.
2. The handler catches its own failures and closes with an explicit **1011** — bugs stop wearing the network's face.
3. The dashboard's reconnect gets the reliability ladder (15.14 formalises it): exponential backoff **with jitter** from the first retry, reset only after a stable connection — applied to *all* close paths, not just failed handshakes.

### Prevention

- **The incident closes into a named CI test** — no message may ever produce a frameless drop:

```python
# tests/ws/test_messages_never_crash_the_socket.py
@pytest.mark.parametrize("payload", [
    {"type": "subscribe", "operation_id": "op_7712", "v": 1},   # the field that did it
    {"type": "subscribe"}, {"type": "warp"}, {}, ["not", "an", "object"], "garbage",
])
async def test_bad_messages_get_a_close_frame(ws_client, payload):
    """A validation verdict is a 4400 WITH a frame; an abrupt drop reads as 1006
    = network failure and invites retry storms (03.12)."""
    verdict = await ws_client.send_and_await_outcome("/v1/ws/operations", payload)
    assert verdict.kind in {"reply", "close"}          # never "abrupt"
    if verdict.kind == "close":
        assert 4000 <= verdict.code < 5000, verdict
```

- **Close codes become telemetry**: the server counts every close it sends by code, and the dashboard reports client-observed closes (including synthesised 1006s) to a beacon endpoint — the 1006 rate is now a first-class alert, because the server cannot see its own abrupt drops any other way.
- The handshake-rate limit stays, and the WS message contract (accepted messages, close-code taxonomy) is published in the API docs beside the problem-type catalogue (02.9), so the next client team builds against a contract instead of observed behaviour.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the client closes the tab? | `receive_*` raises `WebSocketDisconnect` — an input. Catch it, drop subscriptions, exit cleanly. |
| ...the handler raises after `accept()`? | No handler above you on a socket: the connection drops **frameless**, the client reports 1006 and retries as if the network failed. Catch and `close(1011)` yourself. |
| ...a message fails validation? | Close 4400 with a reason — a deterministic verdict, published in the taxonomy. Never let the validator's raise escape. |
| ...a deploy rolls? | Every connection on old replicas closes (send 1001 at shutdown, 04.9). Reconnect-and-resubscribe is a scheduled fleet-wide event — design and load-test it. |
| ...2,600 clients reconnect at once? | Each handshake pays full auth (deps, Redis). Jittered client backoff plus a handshake rate limit, or the dependency bill arrives all at once. |
| ...the proxy idles out quiet sockets? | Frameless drop → 1006 at the client. Keepalive pings below the proxy timeout (Version note; module 12). |
| ...an evil page opens a socket to us? | CORS won't stop it and the session cookie comes along. The Origin check in `get_ws_tenant` is the only gate. |
| ...you send after close? | `RuntimeError: Cannot call "send" once a close message has been sent.` Connection state is your state — the writer must stop when the socket does. |

## Common Pitfalls

**Letting exceptions escape on an accepted socket.** The incident's ignition: no `ExceptionMiddleware` catches for you here, and the client sees a fake network failure. *Instead:* the handler is its own last handler — explicit 1011.

**Strict message validation as a breaking change.** `extra="forbid"` against deployed clients is 02.3's compatibility lesson refused. *Instead:* tolerant reader for evolution; 4400 for garbage.

**Relying on CORS.** It never applied. *Instead:* explicit Origin allow-list at the handshake, always.

**Auth after `accept()`.** Spends sockets on clients you'll reject, and at storm rates that is the capacity. *Instead:* decide everything knowable in handshake dependencies.

**One loop for both directions.** Blocked in `receive`, you cannot push; blocked in a slow `send`, you cannot hear the disconnect. *Instead:* reader and writer as peer tasks over a bounded queue.

**Reconnect without jittered backoff.** Every client bug and every deploy becomes a synchronised storm paid in handshake-auth. *Instead:* exponential backoff with jitter on all close paths, reset on stability.

**Tunnelling REST through the socket.** Recreates HTTP badly — no idempotency keys, no retries, no caching, no error catalogue. *Instead:* the socket pushes; commands with HTTP semantics stay HTTP.

- The malformed-message parametrised test above, on the assembled app — every payload earns a frame, never an abrupt drop.
- A handshake test matrix: no cookie → 1008; bad Origin → 1008; `HTTPException` path → HTTP denial; valid → accept (all four captured behaviours pinned).
- A disconnect test asserting subscriptions are dropped and no writer task leaks after the client vanishes mid-push.
- A reconnect-storm smoke test (13.13): N clients in a deliberate crash loop, asserting the handshake rate limit engages and HTTP p99 stays within budget.

## Interview Questions

1. *Explain.* What happens to an unhandled exception in a WebSocket handler, and why is that worse than a 500? — No frame is sent; the client synthesises 1006 and cannot distinguish your bug from a network drop, so it retries — a 500 at least says whose fault it was.
2. *Debug this.* Redis saturates, WS handshakes are up 1000×, browsers show 1006 right after subscribing, started at a deploy. — New strict validation crashing on a long-sent extra field; frameless drops trigger network-style instant retries; roll back, then tolerant reader + explicit close codes + client backoff.
3. *Design.* Authenticate a browser WebSocket. — Cookie on the handshake (headers unavailable), explicit Origin allow-list because CORS doesn't apply, all decided in dependencies before `accept()`; tokens in query strings leak into logs.
4. *Explain.* Why do reader and writer need separate tasks? — Each direction blocks; a handler stuck in `receive` cannot push, and vice versa. TaskGroup both, mind the `ExceptionGroup` wrapping (03.8).
5. *Design.* Define an error vocabulary for a WS API. — Handshake rejections via HTTP/1008; 1011 for our bugs; 1001 at shutdown; documented 4000-range for deterministic client-payload verdicts with retry guidance — the close-code edition of the 02.9 catalogue.
6. *Explain.* What does a deploy do to your WebSocket estate? — Severs all of it; reconnection is a scheduled fleet event whose cost is per-handshake auth × concurrent clients, so backoff/jitter and rate limits are capacity planning, not politeness.
7. *Design.* Live progress for a long-running export — WebSocket? — Not necessarily: one-directional → SSE keeps HTTP semantics (02.10, 12.4); the socket earns its place when interaction arrives (12.6 owns the comparison).

## Key Takeaways

- The handshake is your last HTTP moment: route it, run dependencies, reject with `HTTPException` (denial) or `WebSocketException(1008)`. After `accept()`, only frames and close codes exist.
- **1006 is never sent — it is the client's name for your frameless drop.** An unhandled exception on a socket hands your bug a network failure's retry semantics; catch and close 1011 yourself.
- Rebuild the error contract on close codes: 1011 ours, 4000-range documented verdicts, 1001 at deploys — published like the problem catalogue.
- CORS does not guard sockets; the Origin check and cookie handling are yours (and the reason browser WS auth looks nothing like API-key auth).
- Reader and writer are peer tasks; disconnection is an input; cleanup lives in `finally`.
- Connections are a budget (fd + memory + per-handshake auth), reconnection is a scheduled storm — jittered backoff on clients, rate limits at the edge, close codes in telemetry.
- Push-only? Consider SSE first (12.4/12.6); cross-process fan-out is module 12 + Redis pub/sub (10.15).
