# 03.6 Sync vs Async Endpoints — The Threadpool

> **Prerequisites:** 03.5 (dependencies), 01.1 (event loop and accept queue) · modern-python 12.1 (GIL), 12.5 (asyncio)
> **What you'll learn:**
> - Say exactly what FastAPI does differently for `def` and `async def`, and where the work runs
> - Recognise the **AnyIO threadpool** as a fixed, shared, global resource with a default size
> - Diagnose threadpool exhaustion, which looks nothing like the event-loop blocking of 01.1
> - Choose per endpoint on evidence, including the case where `def` is the correct answer
> **Level:** Intermediate

---

> ⚡ **Thursday 16:20, month-end** — API pods cycle unhealthy → restarted → unhealthy. The cause: forty threads, all parked on one slow outbound call in `def` endpoints.

## Concept

### Plain-English Explanation

FastAPI lets you write a handler either way:

```python
@router.get("/a")
async def handler_a(): ...      # runs ON the event loop

@router.get("/b")
def handler_b(): ...            # runs in a THREAD from a shared pool
```

Both work. Both look identical from outside. The difference is where the work happens, and it decides
what happens when the endpoint is slow.

An `async def` handler runs directly on the event loop, so a blocking call inside it stalls *every*
concurrent request in the process — that was 01.1's incident. A `def` handler is dispatched to a
worker thread, so blocking is fine; the event loop stays free.

The catch, and the reason for this notebook: that thread pool has **forty threads**, it is **shared by
every `def` handler and every `def` dependency in the application**, and it is not per-endpoint or
per-route. Forty is a lot until one endpoint holds a thread for two seconds at twenty-five requests
per second — and then it is exactly zero, for everybody.

### Technical Explanation

**What FastAPI does with each declaration:**

```text
async def handler  ──▶ awaited directly on the event loop
                       ✅ no thread; thousands concurrent
                       ⚠️ any blocking call inside stalls the whole loop (01.1, 04.2)

def handler        ──▶ anyio.to_thread.run_sync(handler)
                       ✅ blocking is safe; the loop stays responsive
                       ⚠️ consumes one of a FIXED, SHARED pool of threads
```

The same rule applies to **dependencies** (03.5). A `def` dependency on an `async def` route is also
dispatched to the threadpool — so an endpoint can be "async" and still consume threadpool capacity
through its dependency graph. That is easy to miss when auditing.

**The pool.** AnyIO's default limiter allows **40** concurrent `run_sync` calls per process. Not per
route, not per router — per process. Requests beyond that queue on a semaphore, waiting for a thread.

```text
capacity = 40 threads  ÷  handler duration  =  sustainable requests per second

  handler takes  50 ms  →  800 rps        comfortable
  handler takes 200 ms  →  200 rps        fine for most services
  handler takes 2000 ms →   20 rps        ⚠️ 25 rps saturates it completely
```

That arithmetic is the whole of the capacity planning, and it is worth doing before shipping any `def`
endpoint that performs network I/O.

**What saturation looks like — and how it differs from 01.1's incident:**

| | Event-loop blocking (01.1) | Threadpool exhaustion (here) |
|---|---|---|
| Caused by | Blocking call in an `async def` handler | Too many concurrent `def` handlers |
| `event_loop_lag_seconds` | **High** (1–2 s) | **Near zero** — the loop is fine |
| CPU | Often high (the blocking work is CPU) | Often **low** — threads are waiting on I/O |
| Which endpoints are affected | *All* of them, including `async def` | Only `def` handlers and `def` dependencies |
| `async def` endpoints during the incident | Slow | **Fast and healthy** |
| The tell | Loop lag | Requests queueing with idle CPU and a healthy loop |

The row that matters diagnostically is the fourth: under threadpool exhaustion your `async def`
endpoints keep working perfectly, so a health check written as `async def` reports a healthy service
while every `def` endpoint queues. That asymmetry is what makes the incident below confusing.

**Raising the limit is not the fix** — threads cost ~8 MB of stack each, they contend for the GIL for
any CPU work (modern-python 12.1), and each one typically holds a database connection, so the real
ceiling is usually your connection pool (05.9), not memory.

### Mental Model

> `async def` puts the work **on the event loop**, where blocking hurts everyone. `def` puts it **in a
> pool of forty threads**, where blocking is safe but *capacity is a fixed, shared, global budget*. A
> `def` endpoint that waits two seconds is spending 1/40th of your entire application's synchronous
> capacity for those two seconds — and it is spending it on behalf of every other `def` endpoint too.

## How It Works

The saturation cascade, which is what turns a slow endpoint into an outage:

```text
  25 rps × 2.0 s per request = 50 concurrent  >  40 threads

  ┌── AnyIO threadpool (40) ─────────────────────────────────┐
  │ [pdf][pdf][pdf][pdf][pdf][pdf][pdf][pdf] … all 40 busy   │
  └───────────────────────────────────────────────────────────┘
        ▲                                    ▲
        │                                    │
  GET /invoices/{id}/pdf              GET /ready   ← a `def` handler too!
  (the slow endpoint)                       │
                                            └─ queues behind 40 PDF renders
                                               → readiness probe times out (15.9)
                                               → orchestrator removes the replica (14.8)
                                               → its traffic moves to the remaining replicas
                                               → they saturate faster
                                               → they are removed too
                                               → ⚠️ cascading removal
```

Note the second arrow. **The health check shares the pool.** A readiness endpoint written as `def` —
even a trivial one — waits behind whatever else is in the queue. That is how a slow endpoint becomes a
replica-cycling outage rather than one slow route.

**Finding what uses the pool** is not obvious from reading route decorators, because dependencies count
too:

```python
@router.get("/invoices/{invoice_id}")
async def get_invoice(                       # ← async: not on the pool
    invoice_id: InvoiceId,
    settings: Annotated[Settings, Depends(load_settings_from_disk)],   # ⚠️ def → POOL
) -> InvoiceOut: ...
```

An `async def` route with one `def` dependency consumes a thread on every request.

## Code Example

Instrumenting the pool, because you cannot manage a resource you cannot see:

```python
# ledgerly/observability/threadpool.py
import anyio.to_thread
from prometheus_client import Gauge

THREADPOOL_CAPACITY = Gauge("anyio_threadpool_capacity", "Total worker threads available")
THREADPOOL_IN_USE = Gauge("anyio_threadpool_borrowed", "Threads currently executing")
THREADPOOL_WAITING = Gauge("anyio_threadpool_waiting", "Tasks queued for a thread")

async def sample_threadpool() -> None:
    """Started from lifespan (03.9). Without this, threadpool exhaustion is
    invisible: CPU is low, the event loop is healthy, and requests just queue."""
    limiter = anyio.to_thread.current_default_thread_limiter()
    while True:
        THREADPOOL_CAPACITY.set(limiter.total_tokens)
        THREADPOOL_IN_USE.set(limiter.borrowed_tokens)
        THREADPOOL_WAITING.set(limiter.statistics().tasks_waiting)
        await anyio.sleep(1)
```

Choosing correctly per endpoint. A fast pure-CPU handler is a legitimate `def`:

```python
# ledgerly/routers/invoices.py (excerpt)
@router.post("/{invoice_id}/preview", response_model=PreviewOut, name="previewInvoice")
def preview_invoice(invoice_id: InvoiceId, body: PreviewRequest) -> PreviewOut:
    """`def` on purpose: pure CPU, no I/O, ~3 ms. Honestly: at 3 ms the GIL means
    the loop barely benefits — a CPU-bound thread holds the GIL, so the loop
    thread progresses little either way. What `def` buys is protection against
    the tail: when one preview is 300 ms (500-line invoice), a thread bounds the
    damage to one pool slot instead of freezing every request (04.7)."""
    return compute_preview(body)          # deterministic formatting and totals
```

> **Version note** — this GIL caveat is the build most production images run in 2026. On
> free-threaded CPython (3.13 experimental, 3.14 supported), CPU-bound threads genuinely run in
> parallel and the `def`-offload argument strengthens; 04.7 and 17.7 take this up properly.

An endpoint doing network I/O must be `async def` with an async client:

```python
# ledgerly/routers/invoices.py (excerpt)
@router.post("/{invoice_id}/send", status_code=202, name="sendInvoice")
async def send_invoice(
    invoice_id: InvoiceId, svc: Service, tenant: Tenant,
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key")],
) -> OperationOut:
    """`async def`: the only work is awaiting the database and the queue. As a
    `def` handler this would hold a thread for the duration of both — turning
    ~40 ms of I/O wait into 1/40th of the application's sync capacity."""
    return await svc.queue_send(tenant, invoice_id, idempotency_key=idempotency_key)
```

Wrapping a genuinely blocking library from an async handler, with the limit made explicit:

```python
# ledgerly/services/pdf.py
import anyio.to_thread

# A dedicated limiter: PDF rendering may use at most 8 threads, so it cannot
# consume the whole shared pool. This is a bulkhead (15.17) — the same idea as
# 02.11's per-destination caps, applied to threads.
_PDF_LIMITER = anyio.CapacityLimiter(8)

async def render_pdf(invoice: Invoice) -> bytes:
    """render_invoice_pdf is a synchronous third-party library. Wrapping it keeps
    the event loop free (01.1); the limiter keeps it from starving every other
    `def` handler in the process."""
    return await anyio.to_thread.run_sync(
        render_invoice_pdf, invoice, limiter=_PDF_LIMITER
    )
```

And the health check, which must never share a contended resource:

```python
# ledgerly/routers/health.py
from sqlalchemy import text

@router.get("/ready", include_in_schema=False)
async def ready(request: Request) -> Response:
    """`async def` deliberately. A `def` readiness probe queues behind every
    other synchronous handler, so the orchestrator removes a replica that is
    merely busy — turning a slow endpoint into a cascading removal (15.9)."""
    async with asyncio.timeout(2):
        # `async with`, or the checked-out connection is never returned and the
        # probe itself drains the pool — a readiness check causing the outage.
        async with request.state.engine.connect() as conn:
            await conn.execute(text("SELECT 1"))
    return Response(status_code=204)
```

## Design Patterns / Tradeoffs

### `async def` with async libraries

- *Advantages:* thousands of concurrent requests per process; no thread overhead; cancellation and
  timeouts propagate (04.8); the natural fit for an I/O-bound API.
- *Disadvantages:* one blocking call stalls everything (01.1); requires async drivers throughout —
  `asyncpg`/`psycopg` async, `httpx`, `redis.asyncio`; every third-party library must be checked.
- *Failure mode:* a synchronous SDK slipped into a handler; `event_loop_lag_seconds` spikes.
- *Use when:* the handler's work is awaiting I/O. The default for an API.

### `def` with synchronous libraries

- *Advantages:* blocking is safe; any library works; simple mental model; genuinely correct for short
  CPU-bound work.
- *Disadvantages:* capacity is capped at 40 concurrent across the whole process; each thread costs
  memory and, for CPU work, contends for the GIL; every `def` handler shares one budget.
- *Failure mode:* pool exhaustion — the incident below.
- *Use when:* short pure-CPU work; a synchronous-only dependency with low request volume; migrating a
  WSGI codebase incrementally.
- *Do NOT use when:* the handler performs network I/O of any meaningful duration.

### The decision, made concrete

```text
Does the handler do I/O?
  ├─ no, and it is fast (< ~10 ms)      → `def`     ✅ bounds the tail (GIL caveat above)
  ├─ no, and it is slow (CPU-heavy)     → a worker (11.1), not an endpoint at all (04.7)
  └─ yes
       ├─ an async client exists         → `async def` ✅
       ├─ only a sync client exists,
       │  low volume                     → `def`, with the capacity arithmetic written down
       └─ only a sync client exists,
          high volume                    → `async def` + to_thread with a dedicated
                                            CapacityLimiter (bulkhead)
```

### Tuning the pool

| Action | Effect | Cost |
|---|---|---|
| Raise the default limiter | More concurrent `def` handlers | ~8 MB stack each; GIL contention; **usually exceeds the DB pool first** (05.9) |
| Dedicated `CapacityLimiter` per workload | One workload cannot starve others | Must choose limits per workload |
| Convert the endpoint to `async def` | Removes it from the pool entirely | Requires an async client |
| Move the work to a worker (11.1) | Removes it from the request path | Async API and polling (02.10) |

**Recommendation:** do not raise the global limit as a first response — it moves the bottleneck to the
database pool and hides the design problem. Add per-workload limiters so heavy work is bulkheaded, and
convert genuinely I/O-bound handlers to `async def`.

## Production Scenario

**Ledgerly, Thursday 16:20, month-end.** Alerts fire for replica cycling: API pods are failing
readiness checks and being restarted by the orchestrator. Latency on most endpoints is climbing. CPU
utilisation across the fleet is **11%**.

### Symptoms

- Readiness probes (`GET /ready`) timing out at 3 seconds; the orchestrator removes replicas, then
  restarts them; they fail again shortly after starting.
- API p99 for `GET /v1/invoices` (an `async def` endpoint): **normal, 45 ms** throughout.
- API p99 for `POST /v1/invoices/{id}/export-csv` (a `def` endpoint): **31 seconds**.
- CPU: 11%. Memory: normal. `event_loop_lag_seconds`: **0.002** — the event loop is completely healthy.
- Database: p99 3 ms, connection pool at 40% utilisation. Not implicated.
- The pattern started when a customer began a bulk export of 900 accounting periods.

### Diagnosis

1. **Alert.** Readiness failures and replica cycling. The obvious hypotheses — CPU saturation, memory
   pressure, a slow database — are all eliminated within two minutes by their metrics.
2. **Metrics, the decisive combination.** Requests are queueing while **CPU is low and the event loop is
   healthy**. That rules out 01.1's failure entirely: nothing is blocking the loop. Something else is
   a bottleneck, and it is not a resource anyone was watching.
3. **The asymmetry names it.** `async def` endpoints are fast; `def` endpoints are slow. That split maps
   onto exactly one shared resource — the AnyIO threadpool — and onto nothing else in the system.
4. **Confirm from inside the process**, via a debug endpoint added during the incident:

```python
>>> limiter = anyio.to_thread.current_default_thread_limiter()
>>> limiter.total_tokens, limiter.borrowed_tokens, limiter.statistics().tasks_waiting
(40, 40, 218)                      # ⚠️ all 40 in use, 218 requests queued for a thread
```

5. **Identify the consumer.** Thread stacks (`faulthandler.dump_traceback()`) show 38 of 40 threads
   inside `export_csv`, in `requests.get()` against the internal reporting service:

```python
# as it was
@router.post("/{invoice_id}/export-csv")
def export_csv(invoice_id: InvoiceId, svc: Service) -> Response:
    rows = requests.get(f"{REPORTING_URL}/rows/{invoice_id}", timeout=30).json()
    return Response(build_csv(rows), media_type="text/csv")
```

6. **Why readiness failed.** `/ready` was also a `def` handler — a trivial one, returning `204` after a
   database ping. It queued behind 218 waiting tasks. The orchestrator concluded the replica was
   unhealthy, removed it, and moved its traffic to the remaining replicas, which saturated faster. The
   cascade was self-reinforcing.

### Root Cause

A `def` endpoint performing a slow network call. Each request held one of the process's 40 threads for
2–3 seconds (longer once the reporting service itself slowed under the load). At the customer's export
rate of ~25 requests per second, demand for threads was ~60 concurrent against a supply of 40.

Three factors turned a slow endpoint into an outage:

- **The pool is global.** Every `def` handler in the application shares it, so one endpoint's demand
  starved all of them.
- **The health check was in the pool.** A `def` readiness probe cannot report health when the pool is
  the thing that is unhealthy — it queues instead of answering.
- **Nothing measured the pool.** CPU, memory, event-loop lag, database pool and queue depth were all
  monitored. The resource that was actually exhausted had no metric at all, which is why diagnosis took
  25 minutes rather than 25 seconds.

The endpoint had been written as `def` because the reporting client library was synchronous, and at its
original volume — a handful of requests a day — that was a perfectly reasonable decision. **Nothing
about the endpoint changed; the traffic did.**

### Fix

*Mitigation (9 minutes):*

1. Change `/ready` to `async def` and redeploy. Replica cycling stops immediately — replicas are busy
   but no longer being killed, which halts the cascade.
2. Rate-limit the export endpoint to 5 concurrent per tenant at the edge (02.12), capping demand on the
   pool.

*Permanent fix:*

1. **The export endpoint converted to `async def` with `httpx`**, removing it from the pool entirely:

```diff
- @router.post("/{invoice_id}/export-csv")
- def export_csv(invoice_id: InvoiceId, svc: Service) -> Response:
-     rows = requests.get(f"{REPORTING_URL}/rows/{invoice_id}", timeout=30).json()
+ @router.post("/{invoice_id}/export-csv")
+ async def export_csv(invoice_id: InvoiceId, svc: Service,
+                      reporting: ReportingClient) -> Response:
+     rows = await reporting.rows_for(invoice_id)       # httpx, one client per process (01.7)
      return Response(build_csv(rows), media_type="text/csv")
```

2. **A dedicated `CapacityLimiter` for the remaining synchronous work** (PDF rendering), so no single
   workload can consume the shared pool.
3. **Threadpool metrics and an alert**, which is the change that makes the class visible in future.
4. **A rule: health and readiness endpoints are always `async def`**, asserted by a test — they must
   report on the system, not queue inside it.
5. **Large exports moved to the operation pattern** (02.10) in the following sprint: a 900-period export
   does not belong in a request at all.

### Prevention

- **Threadpool saturation alert** — the metric nobody had:

```yaml
- alert: ThreadpoolSaturated
  expr: anyio_threadpool_borrowed / anyio_threadpool_capacity > 0.8
  for: 2m
  annotations:
    summary: "AnyIO threadpool {{ $value | humanizePercentage }} used; `def` handlers are queueing"
    runbook: |
      Low CPU + healthy event loop + slow `def` endpoints = threadpool exhaustion (03.6).
      Find the consumer with faulthandler.dump_traceback(); convert it to async def
      or give it a dedicated CapacityLimiter. Do NOT simply raise the global limit.

- alert: ThreadpoolQueueGrowing
  expr: anyio_threadpool_waiting > 20
  for: 1m
```

- **An architecture test asserting that health endpoints are async and that `def` handlers do no
  network I/O:**

```python
# tests/architecture/test_sync_handler_policy.py
import ast, inspect, pytest
from fastapi.routing import APIRoute
from ledgerly.main import app

SYNC_IO = {"requests", "urllib", "urllib3", "httplib", "psycopg2", "smtplib", "boto3"}
ROUTES = [r for r in app.routes if isinstance(r, APIRoute)]

@pytest.mark.parametrize("route", ROUTES, ids=lambda r: r.path)
def test_sync_handlers_do_no_network_io(route) -> None:
    if inspect.iscoroutinefunction(route.endpoint):
        return
    source = inspect.getsource(route.endpoint)
    used = {n.id for n in ast.walk(ast.parse(source)) if isinstance(n, ast.Name)}
    assert not (used & SYNC_IO), (
        f"{route.path} is a `def` handler doing network I/O: it holds one of the "
        "40 shared threads for the duration of the call (03.6)"
    )

@pytest.mark.parametrize("path", ["/health", "/ready"])
def test_health_endpoints_are_async(path) -> None:
    route = next(r for r in ROUTES if r.path == path)
    assert inspect.iscoroutinefunction(route.endpoint), (
        f"{path} must be async def: a sync health check queues behind the threadpool "
        "and reports unhealthy when the app is merely busy (03.6, 15.9)"
    )
```

- **Do the capacity arithmetic before shipping a `def` endpoint that does I/O**: `40 ÷ duration = max
  rps`. Write the number in the pull request. Most of these endpoints ship with an implied capacity of
  20 rps that nobody has stated.
- **Health checks never share a contended resource.** The generalised rule from this incident: a probe
  that queues behind the thing it is meant to report on will always give the wrong answer at the worst
  moment (15.8, 15.9).
- **Load-test alongside existing traffic**, not in isolation (13.13). Tested alone, the export endpoint
  performed acceptably; the failure only exists in the presence of other `def` handlers competing for
  the same pool. This is the same lesson as 01.1, from the opposite direction.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a `def` handler takes 2 seconds? | It holds 1/40th of the application's sync capacity for 2 seconds. 20 rps saturates the pool. |
| ...an `async def` handler blocks? | The whole event loop stalls — every request, including `async` ones (01.1, 04.2). |
| ...a dependency is `def`? | It uses the threadpool too, even on an `async def` route. Audit dependencies, not just handlers. |
| ...the readiness probe is `def`? | It queues behind saturated work and reports unhealthy while the app is merely busy → cascading replica removal. |
| ...you raise the threadpool limit? | You move the bottleneck to the database pool (05.9) and add ~8 MB per thread. Rarely the right first move. |
| ...CPU is low but requests queue? | Threadpool exhaustion or connection-pool exhaustion — not CPU. Check both limiters. |
| ...`event_loop_lag_seconds` is near zero during an incident? | The loop is fine. The bottleneck is a pool: threads, connections or an external semaphore. |
| ...traffic increases 10×? | `async def` scales with the loop; `def` hits a hard wall at 40 concurrent, and the wall is shared. |

## Common Pitfalls

**`def` handlers doing network I/O.** The incident above. *Instead:* `async def` with an async client,
or a dedicated limiter if only a sync client exists.

**A `def` health or readiness endpoint.** Reports the pool's health, not the application's, exactly when
it matters. *Instead:* `async def`, asserted by a test.

**Auditing only route decorators.** `def` dependencies consume the pool on `async def` routes.
*Instead:* audit the whole dependency graph.

**Raising the global limiter as the fix.** Moves the bottleneck and hides the design problem.
*Instead:* per-workload limiters and converting I/O-bound handlers.

**`async def` with a synchronous client inside.** The worst of both: no thread protection and a blocked
loop. *Instead:* `await anyio.to_thread.run_sync(..., limiter=...)`.

**No threadpool metrics.** The exhausted resource is invisible; CPU, memory and loop lag all look fine.
*Instead:* export capacity, borrowed and waiting.

**Assuming `async def` is always faster.** For short pure-CPU work, `def` is *better* — it keeps the
loop free. Async is about I/O concurrency, not speed (04.10).

## How to Test This

- The architecture tests above: no network I/O in `def` handlers; health endpoints are `async def`.
- A load test that saturates the pool and asserts `/ready` still responds within its probe timeout —
  the property the incident violated.
- A metrics test asserting the threadpool gauges are exported and non-zero at startup.
- A concurrency test on a wrapped sync workload asserting its dedicated limiter caps concurrency at the
  configured value.

## Key Takeaways

- `async def` runs **on the event loop**; `def` runs in a **shared pool of 40 threads**. Both are valid;
  the choice is about where the work waits.
- The threadpool is a **fixed, global, shared budget**. `40 ÷ handler duration = your maximum rps` for
  *all* `def` handlers combined.
- `def` dependencies consume the pool too, even on `async def` routes.
- Threadpool exhaustion looks nothing like event-loop blocking: **low CPU, healthy loop lag, and only
  `def` endpoints affected**. That asymmetry is the diagnosis.
- **Health and readiness endpoints must be `async def`.** A probe that queues behind the resource it
  reports on will always be wrong when it matters.
- Export threadpool metrics. It is the one major resource in a FastAPI process with no default
  visibility.
- Do not raise the global limit reflexively — bulkhead heavy workloads with dedicated limiters and
  convert I/O-bound handlers to `async def`.
