## Concept

### Plain-English Explanation

Everything before this notebook made the application correct; this notebook is about the machinery that runs it. In production your process has three relationships it did not have on your laptop: something **starts and stops it** (an orchestrator, systemd, a platform), something **multiplies it** (workers, replicas), and something **stands in front of it** (a proxy). Each relationship is operated through a narrow channel — signals downward, sockets sideways, headers forward — and each channel can silently fail while the application itself remains perfectly healthy.

The one that fails most quietly is the first. Every graceful behaviour this module built — drain in-flight requests (03.9's diagram deferred it here), close WebSockets with 1001 (03.12), run teardown after `yield` (03.9) — executes only *after the process receives a shutdown signal*. If the signal never arrives, all of it is dead code, and nothing tells you: the deploy still "works", the old container still disappears — by SIGKILL, after a grace period nobody watched expire.

### Technical Explanation

**The signal path.** A rolling deploy stops a replica by sending **SIGTERM** to the container's **PID 1** and, after a **grace period** (`stop_grace_period`, default 10 s in Docker/Swarm), SIGKILL. Three facts govern everything downstream. First, only PID 1 gets the signal — if PID 1 is a shell (`CMD uvicorn ...` shell form runs `sh -c`), the signal stops there: `sh` neither forwards SIGTERM nor, as PID 1, dies to it by default. Second, PID 1 also inherits the kernel's orphan-reaping duty, which a Python process does not perform — the standard fix for both problems is a tiny init (`tini`) as PID 1 with your server `exec`'d under it. Third, ⚠️ **SIGKILL is not a signal you handle** — it is the deadline after which none of your code runs, which is why 03.9's rule stands: correctness rests on idempotent work and reconciliation, never on teardown.

**What uvicorn does when the signal arrives** (SIGTERM/SIGINT; SIGBREAK on Windows — same path). Captured, with a 4-second request in flight and the signal sent 1 second in:

```text
t= 2.38s  INFO:  Shutting down                                   ← signal received; stop accepting
t= 2.50s  INFO:  Waiting for connections to close. (CTRL+C to force quit)
t= 5.57s  INFO:  127.0.0.1:64474 - "GET /v1/slow HTTP/1.1" 200 OK   ← in-flight request COMPLETES
t= 5.66s  INFO:  Waiting for application shutdown.
t= 5.66s  [lifespan] shutdown in pid=25956                       ← code after yield (03.9)
t= 5.66s  INFO:  Application shutdown complete.
client outcome: HTTP 200 {'status': 'rendered', 'invoice': 'inv_9f2c41'} after 4.2s
```

The order is the contract: **stop accepting → drain in-flight → lifespan shutdown → exit**. The client saw a normal 200; the engine was disposed only after the last response left. Everything 03.9 taught about teardown presumes this sequence — and this sequence presumes the signal.

**The drain deadline.** Drain cannot be unbounded: a 03.11 trickle-download or an open WebSocket would hold the old replica forever. `--timeout-graceful-shutdown` caps it — captured with a 30-second request and a 2-second cap:

```text
t= 2.38s  INFO:   Shutting down
t= 2.48s  INFO:   Waiting for connections to close. (CTRL+C to force quit)
t= 4.49s  ERROR:  Cancel 1 running task(s), timeout graceful shutdown exceeded
t= 4.84s  asyncio.exceptions.CancelledError: Task cancelled, timeout graceful shutdown exceeded
t= 4.84s  INFO:   "GET /v1/very-slow HTTP/1.1" 500 Internal Server Error
client outcome: HTTP 500 after 3.5s
```

Expiry cancels the remaining request tasks; the handler dies by `CancelledError` and the client at least receives a response (a 500 — through a mid-deploy LB, often a 502) rather than a frameless reset. The invariant that makes the whole ladder coherent: **slowest legitimate request < graceful timeout < orchestrator grace period.** Ledgerly: 20 s (03.11's spooled downloads are client-paced but bounded) < 25 s < 30 s. Every gap is deliberate — the difference between each pair is where lifespan teardown and process exit must fit.

**Workers.** `uvicorn --workers N` runs a **parent supervisor** that binds the socket once, starts N server processes that share it, and monitors them. Captured on the pinned stack — including an unplanned demonstration of the monitoring:

```text
INFO:  Started parent process [8388]
INFO:  Started server process [20708]
[lifespan] startup in pid=20708          ← lifespan runs PER WORKER (03.1, 03.9)
INFO:  Started server process [13044]
[lifespan] startup in pid=13044
INFO:  Child process [20708] died        ← a worker crashed...
INFO:  Started server process [14188]    ← ...and the supervisor replaced it
six GET /v1/ping → pid 13044 ×5, pid 14188 ×1     ← accept is contested, NOT round-robin
^SIGBREAK
INFO:  Shutting down                     (both workers, fanned out by the parent)
[lifespan] shutdown in pid=14188
[lifespan] shutdown in pid=13044
INFO:  Application shutdown complete.    ×2
INFO:  Stopping parent process [8388]    exit code 0
```

Three lessons are in that transcript. Lifespan runs once *per worker* — N workers = N engines = N × `pool_size` database connections, the multiplication 03.6's budget arithmetic must include. The supervisor restarts dead workers (the crash here is a Windows socket-sharing artifact — see the Version note — but the restart behaviour is exactly its job everywhere). And requests are not balanced: workers race to `accept()` on the shared socket, and whoever wins, wins — five of six pings landed on one worker.

**gunicorn** is the older answer: a pre-fork master managing workers, with FastAPI run via `uvicorn.workers.UvicornWorker`. It brings a richer signal vocabulary — `SIGHUP` graceful reload, `TTIN`/`TTOU` to grow/shrink the worker pool live, `USR2` binary upgrades — and one famous trap: ⚠️ **`--timeout` is not a request timeout.** It is a *liveness watchdog*: a worker that fails to heartbeat for that long is killed with prejudice. For async workers the heartbeat runs on the event loop — so what actually trips it is a **blocked loop** (03.6's sync-call-in-async), executing your CPU-bound bug as a worker SIGKILL plus dropped in-flight requests. (Behaviour stated from gunicorn's documented model, not captured — it does not run on Windows.)

**The proxy seam.** Termination in front (01.10) means the app must be *told* what the edge saw: `--proxy-headers` with `--forwarded-allow-ips=<your proxies' CIDR>` (never `"*"` — 01.10's incident) restores scheme/client; and when the proxy strips a path prefix, `root_path` tells the app the prefix it can no longer see. Captured: with `FastAPI(root_path="/api")`, handlers still match `/v1/ping`, `request.scope["root_path"]` is `"/api"`, and the OpenAPI document gains `servers: [{"url": "/api"}]` so `/docs` fetches the schema through the proxy correctly. Finally the 01.7 inequality — proxy idle timeout below server keep-alive — is deployment configuration too, set in the same files as everything above.

### Mental Model

> A deploy is a conversation held entirely in signals, and your application only speaks *after* it hears its name. Every graceful feature you built — drain, 1001 closes, teardown — is the *second half* of that conversation. The infrastructure between the orchestrator and PID 1 is a chain of parties who may simply not pass the message on, and a dropped message doesn't error: it just means the conversation ends with a bullet instead of a goodbye, invisibly, every single deploy.

## How It Works

One replica's death during a rolling deploy, done correctly — every arrow a real mechanism:

```text
orchestrator decides replica must go
  │ 1. deregister from LB / stop routing     ← BEFORE the signal, or the proxy keeps
  │                                            sending requests to a draining process
  │ 2. SIGTERM ──▶ PID 1 (tini) ──▶ uvicorn
  │                  │ shell-form CMD: signal stops at sh; steps 3-6 never happen ⚠️
  ▼ 3. stop accepting (socket closed; LB health checks now fail too — belt & braces)
  │ 4. drain: in-flight HTTP completes; WebSockets closed 1001 (03.12)
  │      └─ deadline: --timeout-graceful-shutdown → cancel stragglers (500)
  │ 5. lifespan shutdown: cancel supervised tasks, close clients, dispose engine (03.9)
  │ 6. exit 0 ──▶ orchestrator starts/promotes replacement (start-first: already up, 14.9)
  ▼
  grace period expires with the process still alive? ──▶ SIGKILL: steps 4-6 abandoned,
                                                         no 1001s, no teardown, no evidence
```

Two orderings in that timeline carry most of the operational pain. **Deregistration before signal**: if the LB learns about the death only from failing health checks, there is a window where it routes new requests into a process that is refusing them — visible as a 502/503 blip on *every* deploy, usually misattributed to "deploys are just bumpy". **Drain before teardown**: lifespan shutdown disposes the engine; run it while requests are still in flight and they die on a closed pool — which is why uvicorn's sequence (captured above) does the draining first, and why writing your own "cleanup on SIGTERM" handler that races it is an anti-pattern.

The worker topology decides who receives and fans out the signal:

```text
                     ┌────────────── one machine ──────────────┐
  uvicorn --workers 3:   parent [binds socket, supervises]      signal → parent → children
                           ├─ worker (lifespan, engine, pool)
                           ├─ worker (lifespan, engine, pool)   RAM, DB conns ×3 (03.6)
                           └─ worker (lifespan, engine, pool)
  orchestrator replicas:   container ─ single uvicorn worker    signal → tini → uvicorn
                     (×N containers; the ORCHESTRATOR is the supervisor)
```

## Code Example

The incident's cause and its fix are four lines of Dockerfile apart:

```dockerfile
# ❌ shell form: PID 1 is sh -c. SIGTERM lands on the shell and stops there —
#    uvicorn never hears it; every stop is SIGKILL after the grace period.
CMD uvicorn ledgerly.main:app --host 0.0.0.0 --port 8000

# ✅ exec form under a real init: tini is PID 1 (forwards signals, reaps orphans),
#    uvicorn receives the actual SIGTERM. Flags per 01.10 / this notebook:
ENTRYPOINT ["tini", "--"]
CMD ["uvicorn", "ledgerly.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--proxy-headers", "--forwarded-allow-ips", "10.0.0.0/24", \
     "--timeout-graceful-shutdown", "25"]
```

And the deployment stanza that completes the deadline ladder — the numbers must be read together, never tuned separately:

```yaml
# compose/swarm — the deadline ladder: request 20s < graceful 25s < grace 30s
services:
  api:
    stop_grace_period: 30s        # SIGTERM → (30s) → SIGKILL
    deploy:
      update_config:
        order: start-first        # 03.9's incident: prove startup BEFORE removing capacity
        parallelism: 1
```

The CI test that turns "graceful" from a flag name into a verified property — the incident's named closure:

```python
# tests/deploy/test_sigterm_actually_drains.py
async def test_sigterm_drains_in_flight_and_exits(api_container):
    """Sends the real signal at the real PID 1 and asserts the 03.9 sequence ran.
    Catches shell-form CMDs, missing tini, and graceful-timeout > grace-period
    regressions — none of which any unit test can see (03.14)."""
    slow = asyncio.create_task(api_container.get("/v1/slow"))      # 4s in flight
    await asyncio.sleep(1)
    t0 = time.monotonic()
    api_container.signal("SIGTERM")                                # what the deploy sends
    assert (await slow).status_code == 200                         # drained, not reset
    assert await api_container.wait_exit(timeout=30) == 0          # before the grace period
    logs = api_container.logs()
    assert "Application shutdown complete" in logs                 # lifespan teardown ran
    assert "Cancel" not in logs                                    # nothing was guillotined
```

The middle assertion is the load-bearing one: a shell-form CMD passes every other test in the suite — the app is *correct* — and fails only here, because only here does anyone send the production signal at the production PID 1 and time the death.

> **Version note** — captured on uvicorn 0.46, whose built-in multiprocess supervisor (rewritten in 0.30) monitors and restarts workers — the historical reason to front uvicorn with gunicorn. gunicorn (23.x) remains maintained but slow-moving, and does not run on Windows. These transcripts were captured on Windows: SIGBREAK stands in for SIGTERM (uvicorn handles both on the same path), the exit code 3 seen after console-break shutdowns is a Windows console convention — *unrelated* to 03.9's exit-3-on-startup-failure — and the mid-run worker death in the workers transcript (`WinError 10022`) is a Windows socket-inheritance artifact; on Linux, shared-socket workers are the reliable default. The supervisor's restart response is identical on all platforms.

## Design Patterns / Tradeoffs

### Who supervises: uvicorn workers vs gunicorn vs the orchestrator

- **`uvicorn --workers N`** — one container/VM, N processes, uvicorn's parent supervises (binds once, restarts dead workers, fans out signals — all captured above). *Advantages:* no extra dependency; one deployment unit saturates a multi-core box. *Disadvantages:* the unit of scheduling is the whole group — resource limits, OOM kills and metrics apply to N workers collectively; no per-worker CPU pinning; reload/scale vocabulary is minimal. *Failure mode:* one worker leaking memory takes the shared cgroup limit down with all N. *Use when:* systemd/VM deployments; a container platform that charges per container.
- **gunicorn + `UvicornWorker`** — pre-fork master, rich signal vocabulary (`HUP` reload, `TTIN`/`TTOU` live resize), battle-aged. *Disadvantages:* second dependency and second config surface; the `--timeout` liveness trap above; ⚠️ `--preload` re-creates 03.1's import-before-fork incident deliberately (app imported once, then forked — any engine created at import is shared across workers). *Use when:* you specifically need its hooks/reload semantics on a VM. *Not* the default it once was.
- **One worker per container, orchestrator replicas** — the supervisor is Swarm/Kubernetes: restart policies replace the parent process, scaling is `replicas: N`, resource limits and metrics are per-process, and the signal path is the short one (`tini → uvicorn`). *Disadvantages:* per-container overhead; container count grows with cores. *Failure mode:* forgetting that *the orchestrator* is now the restart mechanism and adding `--workers 4` inside the container too — two supervisors, doubled pools, and signals that fan out twice. **Ledgerly's choice**, and why this notebook's canonical CMD runs a single worker.

**Recommendation:** containers → one worker per container and let the orchestrator do every job it already has; VMs → uvicorn's own workers; gunicorn where its specific signal vocabulary is the requirement. Change the answer when the platform changes, not per service.

### The drain deadline: generous vs guillotine

A **long graceful timeout** (minutes) honours slow work — and makes every deploy take minutes per batch, holds two versions live longer (schema and contract skew windows, 02.3), and lets one stuck connection stall the fleet's rollout. A **short timeout** (seconds) makes deploys crisp — and executes 03.11-style legitimate long downloads as 500s on every release. The resolution is not a cleverer number: it is **removing long-lived work from the drain path** — spool-then-stream keeps downloads fast (03.11), WebSockets are closed proactively with 1001 *at the start* of drain because reconnection is a designed path (03.12), and genuinely long jobs live in workers (03.10), not requests. Then the timeout protects against the pathological only, and 25 s is comfortable. If a route's legitimate duration exceeds your ceiling, that route — not the fleet's deploy speed — is what needs redesigning.

## Production Scenario

**Ledgerly, Tuesday 6 October, 11:20.** First monthly review of the close-code telemetry shipped after the 03.12 incident. The dashboard has a counter for every close the server sends. One panel stops the meeting: `ws_closes_sent_total{code="1001"}` — the "going away" frame every deploy should broadcast — reads **zero**. Not low. Zero, across 41 deploys since the counter existed. The same dashboard shows client-reported **1006** spikes at 14:0x on every deploy day — deploys happen at 14:00.

### Symptoms

- The zero 1001 counter and the deploy-aligned 1006 spikes (client beacons, 03.12's prevention).
- Retro-correlation, once someone looks: a ~4-second blip of LB 502/504s at every deploy, long normalised as "deploys are bumpy"; and 03.10's audit of BackgroundTasks losses — 41 deploys' worth of hard kills — whose investigation had stopped at "deploys kill processes" without asking why the kills were hard.
- Nothing else. No alert ever fired for this; the discovery is a human reading a number against its own denominator (41 deploys × ~2,600 sockets and not one goodbye).

### Diagnosis

1. **Metrics → the missing negative.** A graceful shutdown *produces* evidence: 1001 closes, drain logs, teardown logs. Grep the aggregated logs for `Shutting down` and `Application shutdown complete` on api replicas: **absent for every deploy**, present only in local dev logs. The graceful path has never executed in production.
2. **Eliminated:** the app (dev shows the full captured sequence on Ctrl+C); uvicorn's config (`--timeout-graceful-shutdown` is set); the orchestrator (Swarm logs show `SIGTERM` dispatched, then `SIGKILL` at `stop_grace_period` +30 s — it kept its side of the contract, every time).
3. **The gap is between the two.** `docker inspect` on the running container: `"Cmd": ["/bin/sh", "-c", "uvicorn ledgerly.main:app ..."]` — shell form, from the very first Dockerfile. PID 1 is `sh`. SIGTERM is delivered to `sh`, which as PID 1 has no default death and forwards nothing. uvicorn — one PID over — never hears it. Thirty seconds later, SIGKILL takes the process tree whole: no drain, no 1001, no teardown, and *no error anywhere*, because dying to SIGKILL is not an error any process gets to log.
4. **Blast radius, finally attributed:** every deploy's 502 blip (in-flight requests severed), every deploy's 1006 storm-let (frameless WS drops — the 03.12 taxonomy's "our fault" case at fleet scale), and a meaningful share of 03.10's metering losses (BackgroundTasks annihilated mid-flight 41 times).

### Root Cause

The Dockerfile's shell-form `CMD` made `sh` PID 1; `sh` neither dies to nor forwards SIGTERM, so the fleet's only shutdown has always been the grace period expiring into SIGKILL — silently converting every "graceful" behaviour built in 03.9–03.12 into dead code, on every deploy, since the service existed.

### Fix

*Mitigation (same day):* exec-form `CMD` under `tini` (the Dockerfile block above), deployed at 15:40. The 15:40 deploy itself — running the *old* image's last minutes — still hard-kills; the 16:10 canary deploy after it shows the first `Shutting down` lines and nonzero 1001s in production history. The 502 blip vanishes from the LB graphs.

*Permanent fix:* the deadline ladder made explicit and asserted (request 20 s < graceful 25 s < grace 30 s, the compose stanza above); LB deregistration ordered before signal delivery in the deploy job; and the `test_sigterm_actually_drains` container test wired into CI — the only test in the suite that would ever have caught this class, because it is the only one that sends the production signal at the production PID 1.

### Prevention

- The drain test above, in CI, against the built image — not the app object.
- **The 1001/1006 deploy ratio becomes an alert**, not a monthly reading: a deploy that produces client-side 1006s without server-side 1001s is a hard kill by definition, whatever the flags claim.
- A one-line image lint: fail the build if `CMD`/`ENTRYPOINT` is shell-form (14.x owns the fuller Dockerfile review). The meta-lesson stands with 03.10's: *silence is not success* — a graceful path that leaves no evidence of running must be treated as not running.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the process dies by SIGKILL? | No code runs — not drain, not teardown. Correctness rests on idempotency and reconciliation (03.9, 03.10), and the *evidence* is only what didn't happen (no shutdown logs, no 1001s). |
| ...SIGTERM never reaches uvicorn? | The incident. Shell-form CMD, missing tini, a wrapper script without `exec` — verify with the drain test and the 1001 counter, not by reading flags. |
| ...a worker crashes mid-flight? | Its in-flight requests die; the supervisor (uvicorn parent or orchestrator) restarts it — captured. Clients retry per 01.3/02.8 semantics; a restart *loop* is 03.9's crash-loop lore. |
| ...drain exceeds the graceful timeout? | Remaining tasks are cancelled; clients get 500/502 — captured. If legitimate requests hit this, fix the route (03.10/03.11), not the timeout. |
| ...the graceful timeout exceeds the grace period? | The guillotine beats the drain: SIGKILL mid-teardown. The ladder invariant exists precisely for this; assert it in CI. |
| ...the LB routes to a draining replica? | Connection refused → 502 blip every deploy. Deregister before signalling; health checks are the backstop, not the mechanism. |
| ...WebSockets are open at deploy time? | Closed 1001 at drain start — reconnection is scheduled, fleet-wide, by design (03.12). Frameless drops instead = you're being SIGKILLed. |
| ...`--forwarded-allow-ips="*"` sneaks in? | Any client spoofs scheme and IP (01.10). The CIDR is deployment config with a CI assertion, same file as everything else here. |
| ...someone runs `--reload` in production? | The reloader is a dev supervisor: extra process, file-watching overhead, restart-on-write. One captured `docker inspect` away from an embarrassing retro. |

## Common Pitfalls

**Shell-form CMD / wrapper scripts without `exec`.** The incident: PID 1 that eats signals. *Instead:* exec form under `tini`; any entry script ends in `exec uvicorn ...`; lint the image.

**Two supervisors.** `--workers 4` inside a container the orchestrator already replicates: doubled pools (03.6 arithmetic), group-fate OOM kills, twice-fanned signals. *Instead:* one supervisor — orchestrator in containers, uvicorn's parent on VMs.

**gunicorn `--timeout` as a request timeout.** It is a liveness watchdog; with async workers it fires on a blocked *loop* and answers your 03.6 bug with SIGKILL. *Instead:* request deadlines live in the app (04.8); the watchdog stays a watchdog.

**`--preload` (gunicorn) with import-time resources.** Deliberately imports once and forks — resurrecting 03.1's shared-engine incident by design. *Instead:* lifespan-created resources (03.9), and no preload without proving imports are pure.

**Tuning the timeouts separately.** Graceful timeout raised above the grace period "to be safe" = teardown guillotined. *Instead:* the ladder is one decision — request < graceful < grace — asserted together.

**Trusting the word "graceful".** Flags don't prove behaviour; the fleet ran 41 hard-kill deploys with every graceful flag set correctly *in the app*. *Instead:* the drain test and the 1001/1006 ratio — evidence over configuration.

## How to Test This

- The container-level drain test (above): real image, real SIGTERM at PID 1, assert the drained 200, the exit-before-grace, the teardown log line, and the absence of cancellations.
- A ladder assertion in CI: parse deployment config and fail if `timeout-graceful-shutdown ≥ stop_grace_period`, or if `forwarded-allow-ips` is `"*"`.
- A deploy smoke check in staging (13.13): run traffic through a rolling update and assert zero non-1001 socket closes and zero LB 5xx — the 03.12 telemetry doing double duty as a deploy gate.

## Interview Questions

1. *Explain.* Walk a SIGTERM from `docker stop` to your `finally` block, naming every place it can be lost. — Orchestrator → container PID 1 (shell-form CMD stops here; tini forwards) → uvicorn handler → stop accepting → drain (graceful timeout) → lifespan shutdown → exit; SIGKILL after the grace period ends the walk unconditionally.
2. *Debug this.* Every deploy produces a ~4 s blip of LB 502s and a spike of client-reported WebSocket 1006s, but the app has graceful shutdown "configured". — The signal isn't arriving: check PID 1 (`docker inspect` for shell-form CMD), then whether shutdown logs/1001s exist at all; the fix is exec-form + tini, verified by a drain test.
3. *Design.* Set the three timeouts for a service whose slowest legitimate request is 20 s, on a platform with SIGKILL 30 s after SIGTERM. — Graceful timeout between them (≈25 s): above the slowest request so drains finish, below the grace period so teardown runs; then remove anything longer-lived than 20 s from the request path rather than widening the ladder.
4. *Explain.* uvicorn `--workers 4` vs four orchestrator replicas — what actually differs? — Supervisor identity (parent process vs platform), blast-radius of limits/OOM (group vs per-process), metrics granularity, signal fan-out; resource math is identical (4 lifespans, 4 pools). Never both at once.
5. *Explain.* Why is gunicorn's `--timeout` dangerous with async workers, and what is it actually for? — It's a heartbeat-liveness kill, not a request deadline; an event loop blocked by sync work misses heartbeats and the master SIGKILLs the worker, dropping all its in-flight requests. Request deadlines belong in the app.
6. *Design.* Zero-downtime rolling deploy, end to end. — start-first ordering (03.9), deregister from LB before SIGTERM, drain with a ladder-consistent timeout, 1001s to sockets, lifespan teardown, exit before grace; gate the rollout on the staging smoke check and the 1001/1006 ratio.
7. *Debug this.* After moving behind a new gateway that serves the API under `/api`, the app works but `/docs` is blank and generated links are wrong. — The proxy strips the prefix the app never sees: set `root_path="/api"` (captured: schema gains `servers:[{"url":"/api"}]`), and confirm forwarded headers are trusted from the gateway's CIDR only.
8. *Explain.* What does "the process was SIGKILLed" mean for correctness, and how do you even know it happened? — No cleanup ran; correctness must already rest on idempotent work + reconciliation (03.10's outbox). You know only by absent evidence: missing shutdown logs, zero 1001s, losses surfacing in reconciliation.

## Key Takeaways

- Graceful shutdown is the *second half* of a conversation: SIGTERM must actually reach uvicorn (exec-form CMD, tini as PID 1) or drain, 1001s and teardown are dead code — silently, on every deploy.
- The captured sequence is the contract: stop accepting → drain in-flight → lifespan shutdown → exit; the deadline ladder (slowest request < graceful timeout < grace period) is one decision asserted in CI, not three flags.
- Workers multiply lifespans — engines, pools, memory — and share a socket by contest, not rotation; pick exactly one supervisor: the orchestrator in containers, uvicorn's parent on VMs, gunicorn only for its signal vocabulary.
- gunicorn's `--timeout` is a liveness watchdog that answers a blocked event loop with SIGKILL; `--preload` re-creates 03.1's import-before-fork incident on purpose.
- The proxy seam is one trust boundary: forwarded headers from an explicit CIDR (never `"*"`), `root_path` when a prefix is stripped, keep-alive per 01.7 — all deployment config, all CI-assertable.
- Long-lived work has no place on the drain path: spool downloads (03.11), close sockets 1001 early (03.12), move jobs to workers (03.10) — then the guillotine only ever cuts pathology.
- SIGKILL runs nothing and logs nothing: build correctness on idempotency and reconciliation, and treat *missing* graceful-path evidence (a zero 1001 counter) as an alert, because silence is not success.
