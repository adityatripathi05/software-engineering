## Concept

### Plain-English Explanation

Pydantic's headline feature is that it turns untrusted input into typed Python objects. Its most
important behaviour, and the one that causes production incidents, is **how hard it tries** to do
that.

By default Pydantic is *lax*: given a field declared `int` and a value `"42"`, it will happily give
you `42`. That is usually what you want from an HTTP API, where everything arrives as a string. But
"try hard to make it fit" and "refuse anything that is not exactly right" are different contracts, and
the gap between them is where money loses cents, booleans acquire surprising values, and a field you
thought was validated turns out to have been converted.

The other half of the notebook is the mirror image: **serialisation**. A Pydantic model can produce
several different JSON representations of itself depending on which arguments you pass, and the
difference between `model_dump()` and `model_dump(mode="json")` is the difference between a `Decimal`
object your JSON encoder cannot handle and the string it needs.

### Technical Explanation

**Lax vs strict.** In lax mode (the default), Pydantic coerces across types when the conversion is
considered lossless-ish. The full table is long; these are the rows that matter:

| Declared | Input | Lax result | Strict result | Danger |
|---|---|---|---|---|
| `int` | `"42"` | `42` | error | Usually desirable for HTTP |
| `int` | `42.0` | `42` | error | Fine |
| `int` | `42.7` | **error** | error | Pydantic v2 refuses lossy float→int ✅ |
| `float` | `"49.90"` | `49.9` | error | ⚠️ **the money trap** |
| `Decimal` | `"49.90"` | `Decimal("49.90")` | `Decimal("49.90")` | ✅ exact |
| `Decimal` | `49.90` (float) | `Decimal("49.9")` — via `str()` | error | ⚠️ looks clean; trailing-zero scale lost, upstream float error preserved in disguise |
| `bool` | `"yes"`, `"on"`, `"1"`, `"t"` | `True` | error | Surprising in query params |
| `str` | `42` | **error** | error | v2 does not stringify numbers ✅ |
| `datetime` | `"2026-08-24T09:41:02Z"` | aware datetime | same | ✅ |
| `datetime` | `1756032422` | aware datetime (epoch) | error | An id mistaken for a timestamp |
| `list[int]` | `"1,2,3"` | error | error | ✅ |

Two rows deserve emphasis. **`float` accepts any numeric string**, which is exactly how money enters a
system as a binary floating-point value. And the **`Decimal`-from-float row is deceptive**: Pydantic
v2 converts a float to `Decimal` through `str()`, so `49.90` becomes a clean-looking `Decimal("49.9")`
— not the raw constructor's `Decimal(49.90)` = `49.89999999999999857891…`. The conversion hides two
real losses: the scale is gone (`"49.90"` carries two decimal places; the float round-trips as one),
and if the float is the *result of upstream float arithmetic*, its error is faithfully preserved
inside a value that now looks exact. You cannot tell a clean float from a dirty one after the fact —
which is why the correct policy is to reject floats at the boundary rather than convert them.

**Money has exactly two correct representations:**

```python
amount_cents: int          # integer minor units — ✅ preferred for APIs
amount: Decimal            # with explicit precision, and NEVER constructed from a float
```

`float` is never correct for money. Not "usually fine", not "fine below a threshold" — the error is
unbounded under summation, and financial reconciliation is precisely the operation that surfaces it.

**Validators**, and when each runs:

```text
raw input
   │
   ├─ model_validator(mode="before")   dict-level, BEFORE any field parsing
   │                                    use for: renaming legacy keys, restructuring payloads
   ▼
   ├─ field_validator(..., mode="before")   per field, raw value
   │                                         use for: normalising strings, stripping formatting
   ▼
   ├─ CORE VALIDATION (types, constraints)
   ▼
   ├─ field_validator(..., mode="after")    per field, typed value
   │                                         use for: rules about one field
   ▼
   └─ model_validator(mode="after")     whole model, typed
                                         use for: cross-field rules ✅ most common
```

`mode="wrap"` wraps core validation, letting you catch and transform errors — rarely needed, and worth
knowing exists for the "accept a legacy format, fall back to the new one" case.

⚠️ Validators must be **pure and synchronous**. No database calls, no HTTP, no I/O. Pydantic runs them
during parsing, before your handler exists; an `async` rule cannot run there and a blocking one stalls
the event loop (04.2). Data-dependent rules belong in the service layer (07.3).

**Serialisation** is symmetric to validation and just as configurable:

| Call | Produces | Use for |
|---|---|---|
| `model_dump()` | Python objects — `Decimal`, `datetime`, `UUID` stay as they are | Passing to other Python code |
| `model_dump(mode="json")` | JSON-compatible primitives | Anything crossing a JSON boundary — queues, Redis, logs |
| `model_dump_json()` | A JSON `str` | Direct serialisation |
| `model_dump(by_alias=True)` | Field aliases as keys | Wire formats that differ from your Python names |
| `model_dump(exclude_unset=True)` | Only explicitly-set fields | Patch semantics (02.7) |
| `model_dump(exclude_none=True)` | Drops `None` values | ⚠️ Almost never what you want at an update boundary |

**`computed_field`** exposes a derived value in the output schema and in the OpenAPI document:

```python
@computed_field
@property
def amount_outstanding_cents(self) -> int:
    return self.amount_cents - self.amount_paid_cents
```

**`TypeAdapter`** validates types that are not models — `list[InvoiceOut]`, `dict[str, int]`, a union.
It is the right tool for validating a message payload from a queue (11.7) or a Redis value (10.2),
where there is no route to attach a model to.

### Mental Model

> Pydantic is **a translator with a configurable amount of goodwill**. Lax mode says "do your best to
> make this fit", which is what you want for HTTP strings and disastrous for money. Decide, per field,
> whether you want a translator or a gatekeeper — and remember that once a value has passed through
> `float`, no amount of later care can recover what it lost.

## How It Works

The money trap, at the precision where it becomes visible. Every transcript below is real output
from Python 3.14 / Pydantic 2.13 — run them yourself:

```python
>>> from pydantic import BaseModel
>>> class LineFloat(BaseModel):
...     unit_price: float
...     quantity: int
>>> LineFloat(unit_price="49.90", quantity=3).unit_price
49.9                                     # lax: string → float, accepted
>>> 49.9 * 3
149.7                                    # this one HAPPENS to look right...
>>> 41.65 * 3
124.94999999999999                       # ⚠️ ...and its neighbour does not
>>> 53.50 * 0.21
11.235                                   # ⚠️ prints like a clean tie — it is not one.
>>> f"{53.50 * 0.21:.20f}"               #    A 21% VAT line; remember it for the scenario.
'11.23499999999999943157'
>>> total = 0.0
>>> for _ in range(1000): total += 0.10
>>> total
99.9999999999986                         # ⚠️ 1000 × 0.10, accumulated the way services do it
```

That first pair is what makes float money *insidious* rather than merely wrong: most individual
results survive the round-trip, so spot checks pass, and the error appears only for particular value
combinations — *some* invoices wrong, not all of them.

> **Version note** — Python 3.12+ gave the builtin `sum()` compensated (Neumaier) summation, so
> `sum([0.10] * 1000)` returns exactly `100.0` while the `+=` loop above still drifts. Do not read
> that as absolution: `+=` accumulators, per-line multiplication, `round()` on near-half values and
> float aggregation in the database all remain lossy.

The two correct alternatives:

```python
>>> from decimal import Decimal
>>> class LineDecimal(BaseModel):
...     unit_price: Decimal
>>> LineDecimal(unit_price="49.90").unit_price * 3
Decimal('149.70')                        # ✅ exact, scale preserved
>>> LineDecimal(unit_price=49.90).unit_price
Decimal('49.9')                          # ⚠️ from a FLOAT: clean-looking (str conversion),
>>>                                      #    but the scale is gone — "49.90" became "49.9"
>>> Decimal(49.90)                       # the raw constructor shows what the float really is
Decimal('49.89999999999999857891452847979962825775146484375')

>>> 4990 * 3                                              # ✅ integer minor units
14970
```

The `Decimal('49.9')` line is the subtlety worth internalising: **declaring `Decimal` does not make a
float input trustworthy**. Pydantic converts float→`Decimal` through `str()`, which produces a
clean-looking value whether the float was pristine or the end product of lossy upstream arithmetic —
the raw constructor's long expansion shows what is really being papered over. Since you cannot tell a
clean float from a dirty one after the fact, the safe policy is to refuse floats on the wire and
require strings or integer minor units.

## Code Example

Money handled correctly, with the guard against float input made explicit:

```python
# ledgerly/schemas/money.py
from decimal import Decimal
from typing import Annotated, Any

from pydantic import BeforeValidator, Field, PlainSerializer

def _reject_float(value: Any) -> Any:
    """A float has ALREADY lost precision by the time Pydantic sees it, so
    accepting one and converting to Decimal preserves a wrong number. Require a
    string or an int on the wire."""
    if isinstance(value, float):
        raise ValueError(
            "monetary values must be sent as a string or integer minor units, "
            "not a JSON number with a decimal point (float precision is lossy)"
        )
    return value

Money = Annotated[
    Decimal,
    BeforeValidator(_reject_float),
    Field(max_digits=14, decimal_places=2, ge=0),
    PlainSerializer(lambda d: f"{d:.2f}", return_type=str, when_used="json"),
]

# Ledgerly's public API uses integer minor units — no decimal point crosses the
# wire at all. `Money` exists for internal computation and for the CSV importer,
# where values genuinely arrive as decimal strings.
Cents = Annotated[int, Field(ge=0, le=10**12)]
```

Validators at the right level, with the ordering that matters:

```python
# ledgerly/schemas/invoice.py (excerpt)
from datetime import date
from pydantic import BaseModel, ConfigDict, field_validator, model_validator

class InvoiceCreate(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    customer_id: CustomerId
    currency: Currency
    issue_date: date
    due_date: date
    lines: Annotated[list[InvoiceLineIn], Field(min_length=1, max_length=500)]
    po_number: str | None = None

    @field_validator("po_number", mode="before")
    @classmethod
    def normalise_po_number(cls, value: object) -> object:
        """BEFORE: the raw value, so we can clean formatting the client applied.
        Pure and synchronous — no I/O in a validator (see Concept)."""
        if isinstance(value, str):
            cleaned = value.strip().upper().replace(" ", "")
            return cleaned or None
        return value

    @model_validator(mode="after")
    def dates_must_be_ordered(self) -> "InvoiceCreate":
        """AFTER: fields are parsed and typed, so cross-field rules are simple.
        This is the most common validator you will write."""
        if self.due_date < self.issue_date:
            raise ValueError("due_date must not precede issue_date")
        return self
```

Output with a derived field, and the serialisation call that matters when a model leaves Python:

```python

class InvoiceOut(BaseModel):
```

```python
# ledgerly/services/invoices.py (excerpt)
```

Settings, validated once at import so misconfiguration fails before the process serves traffic
(03.1, 07.9):

```python
# ledgerly/config.py
from functools import lru_cache
from typing import Annotated, Literal

from pydantic import Field, PostgresDsn, RedisDsn, SecretStr, model_validator
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="LEDGERLY_", env_file=".env",
                                      extra="forbid")   # an unknown var is a typo, not a feature

    environment: Literal["local", "staging", "production"]
    database_url: PostgresDsn
    redis_url: RedisDsn
    db_pool_size: Annotated[int, Field(ge=1, le=50)] = 10
    cursor_signing_key: SecretStr        # never rendered by repr() or logging (16.10)

    @model_validator(mode="after")
    def production_requires_tls(self) -> "Settings":
        # ⚠️ Cross-field rule, so mode="after" — a field_validator on `environment`
        # would see info.data == {} here, because fields validate in declaration
        # order and environment is declared first. The bug ships silently: the
        # check never fires locally and rejects every valid production config.
        if (self.environment == "production"
                and "sslmode=require" not in str(self.database_url)):
            raise ValueError("production database_url must require TLS (01.8)")
        return self

@lru_cache
def get_settings() -> Settings:
    return Settings()          # pure computation; safe at import (03.1)
```

## Design Patterns / Tradeoffs

### Money representation

| | `int` minor units (✅ API) | `Decimal` (✅ internal) | `float` (❌) |
|---|---|---|---|
| Exactness | Exact | Exact | Lossy, unbounded under summation |
| JSON representation | A number, no ambiguity | Must be a string on the wire | A number that lies |
| Arithmetic | Trivial and fast | Correct; slower; needs an explicit context | Fast and wrong |
| Sub-cent values | Impossible without a smaller unit | Native | Native |
| Database column | `bigint` | `numeric(14,2)` | ⚠️ `double precision` — never |
| Use when | Public API fields, storage | Tax rates, FX, anything sub-cent | Never for money |

**Recommendation:** integer minor units at the API and in the database; `Decimal` for intermediate
computation where sub-cent precision matters (tax and FX), rounded to minor units at the boundary with
an explicit rounding mode. Never `float`, anywhere in the path.

### Strict vs lax mode

- **Lax (default)** — appropriate for HTTP, where every value arrives as a string. Costs you the
  coercions in the table above.
- **Strict per field** (`Field(strict=True)`) — appropriate for fields where a coercion would be a
  silent data change: money, identifiers, enumerations.
- **Strict per model** (`ConfigDict(strict=True)`) — appropriate for **internal** boundaries: a message
  consumed from a queue (11.7), a value read from Redis (10.2), a row mapped from the database. There
  the producer is you, so a coercion signals a bug rather than a forgiving client.
- **Recommendation:** lax at the HTTP edge, strict on internal boundaries, and per-field strictness
  wherever a coercion would be a correctness change.

### Where a rule belongs

| Rule | Home | Why |
|---|---|---|
| Format, range, length | `Field(...)` constraint | Cheapest; documented in OpenAPI (02.4) |
| Normalisation (trim, upcase) | `field_validator(mode="before")` | Operates on the raw value |
| Cross-field consistency | `model_validator(mode="after")` | Needs typed fields, no I/O |
| "Does this customer exist" | Service layer | Needs the database |
| "Is this transition legal" | Domain | Needs current state (07.3) |

The boundary is I/O. A validator that wants to query the database is telling you the rule is not a
schema rule.

### Discriminated unions

When a payload can be one of several shapes, a discriminated union gives precise errors and a clean
OpenAPI schema:

```python
class BankTransfer(BaseModel):
    method: Literal["bank_transfer"]
    iban: str

class CardPayment(BaseModel):
    method: Literal["card"]
    last_four: Annotated[str, Field(pattern=r"^\d{4}$")]

Payment = Annotated[BankTransfer | CardPayment, Field(discriminator="method")]
```

Without the discriminator, Pydantic tries each member and reports every failure, producing an error
body that is confusing to a client and unhelpful in support. With it, the `method` value selects one
branch and the error names only that branch's problems.

## Production Scenario

**Ledgerly, quarterly VAT filing.** Three customers report that their VAT submissions were rejected by
the tax authority for arithmetic inconsistency: the sum of line-item VAT does not equal the declared
total VAT. Each discrepancy is one or two cents. The submissions are legally required and now late.

### Symptoms

- Roughly **3.2%** of imported invoices carry a per-line VAT that differs by exactly one cent from
  the tax authority's own recomputation of `rate × net` for that line; on multi-line invoices the
  differences sum to ±0.01–0.03 against the declared total.
- The discrepancy is invisible from the API's own output — Ledgerly's stored line VATs and totals are
  *internally consistent with each other*, which is what sent support down the "the authority's
  validator must be wrong" path for two days.
- All affected invoices came through the **CSV importer**, which accepts decimal strings; invoices
  created through the JSON API (integer minor units) are unaffected.
- No errors anywhere. Every import returned `201`. Every total was stored successfully.
- The problem has existed since the importer shipped fourteen months ago, and grew with import volume.

### Diagnosis

1. **Alert.** None. Arithmetic that is wrong by a cent is not an error condition; it is a successful
   computation of a wrong value.
2. **Metrics.** Nothing. This is the fourth incident in this curriculum whose only symptom is *incorrect
   data*, and the pattern is now familiar enough to name: correctness failures need business-invariant
   checks, because operational metrics are structurally blind to them.
3. **Reproduce from the raw import file.** Take one rejected invoice and recompute its worst line —
   net 53.50, VAT 21% — the way the importer does (float) and the way the tax authority does (exact
   decimal). The decisive experiment, in the REPL:

```python
>>> from ledgerly.schemas.legacy_import import ImportedLine
>>> line = ImportedLine(unit_price="53.50", quantity=1)   # CSV string, accepted
>>> type(line.unit_price)
<class 'float'>                          # ⚠️ first surprise: lax coercion to float
>>> vat = line.unit_price * 0.21
>>> vat, round(vat, 2)
(11.235, 11.23)                          # the importer's per-line VAT: 11.23
>>> f"{vat:.20f}"
'11.23499999999999943157'                # ⚠️ the "11.235" above is below the half-cent
>>> from decimal import Decimal, ROUND_HALF_UP
>>> (Decimal("53.50") * Decimal("0.21")).quantize(Decimal("0.01"), ROUND_HALF_UP)
Decimal('11.24')                         # the authority's arithmetic: one cent more
```

4. **Read the schema.** The importer's line model declares `unit_price: float`. Pydantic's lax mode
   accepted the decimal strings from the CSV and converted them to binary floats — doing exactly what it
   was asked to do:

```python
# as it was
class ImportedLine(BaseModel):
    description: str
    quantity: int
    unit_price: float          # ⚠️ money as float
```

5. **Trace the rounding.** The importer computed each line's VAT as `round(net * rate, 2)` on floats.
   Two distinct mechanisms bite, both only near half-cent boundaries: (a) the float product sits *just
   below* the true tie — `53.50 × 0.21` is really `11.234999…`, so it rounds to `11.23` where exact
   arithmetic gives `11.24`; and (b) when the product IS exactly representable — `16.25 × 0.10` is
   exactly `1.625` — Python's `round()` uses banker's rounding (half-to-even) and produces `1.62`,
   while the authority's rule is half-up: `1.63`. Most lines are nowhere near a boundary and round
   identically — hence 3.2% of invoices rather than all of them.
6. **Why the API output looked right.** `InvoiceOut` returns the already-rounded per-line VAT and the
   stored totals, which are internally consistent with each other. The discrepancy is only visible
   against an *independent exact recomputation* — which is precisely what the tax authority does on
   submission, and what nothing inside Ledgerly ever did.

### Root Cause

`float` for money. Pydantic's lax coercion accepted the CSV's decimal strings and produced binary
approximations, and per-line VAT was then rounded with `round()` — so lines near a half-cent boundary
rounded differently from the tax authority's exact half-up arithmetic, in either of two ways: the
float product landing just below the true tie, or a genuine tie resolved half-to-even instead of
half-up.

Nothing malfunctioned. The importer validated its input, the arithmetic executed correctly, the values
were stored successfully. The type declaration was wrong, and every layer downstream faithfully
propagated the consequence.

The JSON API was unaffected only because 03.3's models happen to use integer minor units — a decision
made for API-design reasons that incidentally prevented this. The importer was written by a different
team six months later and reached for the obvious type.

### Fix

*Mitigation (same day):* recompute totals for all affected invoices from their stored line values using
`Decimal`, and issue corrected VAT summaries to the three affected customers so they could refile.

*Permanent fix:*

1. **The `Money` type** shown above: `Decimal` with an explicit `BeforeValidator` that **rejects
   floats**. A CSV value arrives as a string and stays exact; a JSON number with a decimal point is a
   `422` telling the client to send a string or minor units.
2. **`Decimal` arithmetic with an explicit rounding step**, quantised once at the boundary:

```python
# ledgerly/services/totals.py
from decimal import Decimal, ROUND_HALF_UP

def total_cents(lines: Sequence[ImportedLine]) -> int:
    """Exact accumulation, one explicit rounding at the end, with a named mode.
    ROUND_HALF_UP matches the tax authority's stated rule — the choice is a
    domain decision and is documented, not a default."""
    total = sum((l.unit_price * l.quantity for l in lines), start=Decimal("0"))
    return int((total * 100).quantize(Decimal("1"), rounding=ROUND_HALF_UP))
```

3. **The database column changed** from `double precision` to `numeric(14,2)` for imported line prices
   (`bigint` cents for totals), via a zero-downtime migration (06.13).
4. **A repository-wide audit** for `float` in any monetary context, which found two more: a currency
   conversion helper and a reporting aggregate.

### Prevention

- **A schema test banning `float` in monetary fields** — the direct control:

```python
# tests/schemas/test_no_float_money.py
import inspect, pytest
from pydantic import BaseModel
import ledgerly.schemas as schemas

MONEY_HINTS = ("price", "amount", "total", "cost", "fee", "tax", "balance", "cents")

MODELS = [obj for _, obj in inspect.getmembers(schemas, inspect.isclass)
          if issubclass(obj, BaseModel)]

@pytest.mark.parametrize("model", MODELS, ids=lambda m: m.__name__)
def test_monetary_fields_are_never_float(model) -> None:
    for name, field in model.model_fields.items():
        if any(hint in name.lower() for hint in MONEY_HINTS):
            assert field.annotation is not float, (
                f"{model.__name__}.{name} is a float: monetary values must be int "
                "minor units or Decimal — float precision loss is unbounded (03.4)"
            )
```

- **A CI check for `double precision` columns** whose names match the same hints, so the database and
  the schema cannot disagree.
- **A property-based test** on the totalling function (modern-python 15.6 covers `hypothesis`): for any
  list of line prices, `total_cents(lines)` equals the exact `Decimal` computation. Property tests are
  particularly effective here because the failure depends on *specific value combinations* that
  example-based tests will not stumble upon.
- **A business-invariant check on a schedule**: `sum(line totals) == invoice total` for every invoice,
  run nightly, alerting on any mismatch. This is the third such invariant in this curriculum (01.6's
  duplicate counter, 03.3's paid-with-no-payment), and the pattern is now explicit: **when the failure
  is "the data is wrong", the only detector is a query that asserts what must be true.**
- **A written rule in the schema guide:** monetary values are `int` minor units at the API and in
  storage; `Decimal` for intermediate computation; `float` never. New engineers reach for `float`
  because it is the obvious type — the rule has to be written down somewhere they will read it.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a client sends `"49.90"` for a `float` field? | Accepted and silently converted to a binary approximation. Unbounded error under summation. |
| ...a client sends `49.90` for a `Decimal` field? | Pydantic converts it via `str()` into a clean-looking value — scale lost, upstream float error hidden. Reject floats explicitly. |
| ...a validator needs a database call? | It cannot — validators are synchronous and run before your handler. Move the rule to the service (07.3). |
| ...you `model_dump()` into a queue payload? | `Decimal` and `datetime` objects break the JSON encoder. Use `mode="json"`. |
| ...you use `exclude_none=True` at an update boundary? | Explicit nulls are dropped, so "clear this field" is silently ignored (02.7). |
| ...a union member matches partially? | Without a discriminator you get every branch's errors. Use `Field(discriminator=...)`. |
| ...an environment variable is misspelled? | With `extra="forbid"` on settings, startup fails. Otherwise it is silently ignored and the default applies. |
| ...a `SecretStr` is logged? | It renders as `**********`. A plain `str` would appear in tracebacks and logs (16.10). |

## Common Pitfalls

**`float` for money.** The incident above. *Instead:* integer minor units, or `Decimal` that never
touches a float.

**`Decimal` constructed from a float.** The raw constructor exposes the float's true expansion;
Pydantic's `str()` path hides it behind a clean-looking value. Either way the number's provenance
cannot be trusted. *Instead:* reject
floats at the boundary; require strings or minor units.

**I/O in a validator.** Synchronous, pre-handler, and it will block the event loop (04.2). *Instead:*
schema rules in the model, data rules in the service.

**`model_dump()` where `mode="json"` is needed.** Leaves `Decimal`, `datetime` and `UUID` objects that
JSON encoders reject — and the failure appears at the queue or cache boundary, far from the cause.

**`exclude_none=True` at an update boundary.** 02.7's wrong fix, in another form.

**Reusing one model across the HTTP edge and internal boundaries.** The edge wants lax coercion; an
internal boundary wants strict, because you are the producer and a coercion means a bug.

**Unions without a discriminator.** Error bodies list every branch's failures and clients cannot tell
which shape was intended.

**Settings without `extra="forbid"`.** `LEDGERLY_DB_POOL_SIZE=30` when the field is `db_pool_size` is
silently ignored and the default is used — a configuration change that appears to work.

## How to Test This

- The float-money schema test and the `double precision` column check.
- A property test asserting the totalling function matches exact `Decimal` arithmetic over generated
  inputs.
- A round-trip test per output model: `model_validate(model_dump(mode="json"))` reproduces the object,
  proving the JSON representation is lossless.
- A coercion test for every field where strictness matters: assert that `"49.90"` for a cents field is
  a `422` rather than a silently truncated integer.
- A settings test asserting an unknown `LEDGERLY_*` variable raises at construction.

## Interview Questions

1. *Explain.* What is lax mode and give a coercion that is dangerous. — Best-effort conversion; `float`
   accepting numeric strings is how money becomes imprecise.
2. *Explain.* Why is `Decimal("49.90")` fine but `Decimal(49.90)` not? — The float already lost
   precision before `Decimal` saw it.
3. *Debug this.* 3% of invoices have totals off by a cent, only from the CSV importer, with no errors.
   — `float` money; reproduce by summing the parsed values.
4. *Explain.* When do you use `model_validator(mode="before")` versus `mode="after"`? — Before for raw
   restructuring; after for cross-field rules on typed values.
5. *Explain.* Why must validators not perform I/O? — They are synchronous and run during parsing; a
   blocking call stalls the event loop.
6. *Explain.* What does `mode="json"` change and when does it matter? — Converts to JSON primitives;
   required whenever the payload leaves Python.
7. *Design.* Where would you use strict mode, and why not everywhere? — Internal boundaries where you
   are the producer; the HTTP edge legitimately receives strings.

## Key Takeaways

- Pydantic's default is **lax**: it coerces aggressively. That is right for HTTP and wrong for money.
- **`float` is never a monetary type.** Use integer minor units at the API and in storage, `Decimal`
  for intermediate computation, and reject floats at the boundary — a float input to a `Decimal`
  field cannot be trusted, however clean it looks after conversion.
- Validators are **synchronous and pure**. Schema rules in the model; anything needing data in the
  service layer.
- `model_dump()` returns Python objects; `model_dump(mode="json")` returns JSON primitives. Use the
  latter whenever the value leaves Python.
- Lax at the HTTP edge, **strict on internal boundaries** — a coercion on data you produced is a bug
  signal, not a convenience.
- Use discriminated unions so error messages name one branch instead of all of them.
- Validate settings at import with `extra="forbid"`, so a misspelled environment variable stops the
  process instead of silently applying a default.
- Data-correctness failures have no operational signal. **Assert business invariants on a schedule** —
  this is now the third instance of that lesson.
