## Concept

### Plain-English Explanation

Middleware is a layer wrapped around your entire application. A request passes inward through every layer before it reaches routing; the response passes back out in reverse. The onion analogy is exact, not approximate: each layer literally holds the next as `self.app`, and "the application", from any layer's point of view, is everything inside it.

Two properties follow immediately. First, middleware runs on **every** request — including requests that match no route, CORS preflights, and requests your handlers will reject. Second, the layers are assembled once at startup, so the stack's behaviour is a property of the **assembled application** (03.2): each layer can be correct in isolation while the bugs live in the ordering.

### Technical Explanation

From 03.1: an ASGI application is a callable taking `(scope, receive, send)`. **Middleware** is an ASGI application that is constructed holding another ASGI application, does something before or after delegating, and passes the same three arguments — possibly wrapped — down the chain. That is the entire mechanism. Everything in this notebook is a consequence of it.

What crosses a layer boundary is exactly three things: the **scope** dict (method, path, raw headers — mutable, shared by all layers), the **receive** callable (yields `http.request` messages carrying the request body), and the **send** callable (accepts `http.response.start`, then `http.response.body` messages). A middleware that wants to act on the response does not "get a response object" — it substitutes its own `send` and inspects messages as the inner application emits them. Holding messages instead of forwarding them is how streaming breaks, which the Code Example returns to.

FastAPI (via Starlette) assembles the stack **once**, at startup, and freezes it — `add_middleware` afterwards raises `RuntimeError: Cannot add middleware after an application has started`. The assembled stack is your registered middleware plus layers you did not register:

- **`ServerErrorMiddleware`** — always outermost. Catches anything that escapes everything else and produces a bare 500. If you registered a handler for `Exception` itself, FastAPI wires it in here.
- **`ExceptionMiddleware`** — always *innermost*, directly outside the router. This is where `HTTPException` handling and every type-specific handler from 03.8 live.
- **`AsyncExitStackMiddleware`** — a FastAPI internal supporting `yield` dependencies (03.5).

The geography has a sharp consequence: ⚠️ **an exception raised in your middleware bypasses your exception handlers.** Handlers live in `ExceptionMiddleware`, *inside* the user stack; an error thrown above it can only fall outward, to `ServerErrorMiddleware`, and becomes a `text/plain` 500 that ignores your error contract (02.9). The Production Scenario is built on this.

Registration order is the detail everyone gets wrong at least once — this repo included, until this notebook was checked against the running framework. **Each `add_middleware` call wraps outside the ones already added, so the last one added is the outermost.** The constructor form, `FastAPI(middleware=[...])`, reads top-down from outermost to innermost — the order you review is the order that executes, which is why Tradeoffs recommends it.

Cost, for completeness: a pure-ASGI layer adds roughly a function call and a closure per message — sub-microsecond, irrelevant next to one database query. The expensive middleware mistakes are semantic (ordering, buffering, blocking I/O paid on every request), never the stack's call overhead.

### Mental Model

> The stack is an onion assembled once at startup. `add_middleware` pushes a new **outermost** skin, so the last line of assembly is the first code to touch every request. Requests travel outside-in, responses inside-out — and routing, dependencies and your exception handlers all live at the core, below every layer you add.

## How It Works

Ledgerly's stack after this notebook's incident, with what actually crosses each boundary:

```text
            ──▶ scope + receive ──▶                      ◀── send(start), send(body) ◀──

  uvicorn  (bytes ⇄ ASGI messages; --proxy-headers rewrites client addr — 01.10)
  └─ ServerErrorMiddleware          [automatic] last-resort 500; runs the Exception handler
     └─ RequestContextMiddleware    request id into a contextvar; id header onto every response
        └─ CORSMiddleware           ⚠️ answers OPTIONS preflight HERE — inner layers never see it
           └─ CachePolicyMiddleware stamps Cache-Control on responses passing outward (01.4)
              └─ TenantAuditMiddleware  records route + key prefix; assumes nothing about headers

                    └─ AsyncExitStackMiddleware [automatic] scope for yield-dependencies (03.5)
                       └─ router ──▶ dependencies (03.5) ──▶ handler (or threadpool, 03.6)
```

The reverse-registration rule, demonstrated rather than asserted — two trivial middlewares that print on entry and exit:

```python
app.add_middleware(First)      # registered first
app.add_middleware(Second)     # registered second
```

```text
enter Second (registered second)      ← added LAST, runs FIRST
enter First (registered first)
      handler
exit  First
exit  Second
```

And the exception geography. A handler registered for a specific type catches that exception from a *handler*, because `ExceptionMiddleware` sits between router and user stack — but the identical exception raised in *middleware* falls past it:

```python
@app.exception_handler(LookupError)
async def lookup_handler(request, exc): ...   # returns a mapped 422
```

```text
raised in handler    -> 422 {"title":"mapped by the LookupError handler"}
raised in middleware -> 500 'Internal Server Error'        ← text/plain, contract bypassed
```

The second line is the one to remember: middleware failures do not speak your API's error language unless you give `ServerErrorMiddleware` an `Exception` handler as a backstop — and even then, as the incident shows, the response may be missing more than its body shape.

## Code Example

The request-context middleware referenced since 01.1, in full — it demonstrates the two techniques nearly all pure-ASGI middleware is made of: reading the scope on the way in, wrapping `send` on the way out.

```python
# ledgerly/middleware/request_context.py
import uuid
from contextvars import ContextVar

from starlette.types import ASGIApp, Message, Receive, Scope, Send

# Readable anywhere downstream — services, repositories, log filters (04.4, 15.2) —
# without threading a parameter through every call signature.
request_id_var: ContextVar[str] = ContextVar("request_id", default="-")

class RequestContextMiddleware:
    """Outermost layer: every request gets an id; every response returns it."""

    def __init__(self, app: ASGIApp) -> None:
        self.app = app

    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        if scope["type"] != "http":                 # lifespan, websocket: pass through
            await self.app(scope, receive, send)
            return

        # Trust the edge's id if the proxy set one (01.10); mint one otherwise.
        incoming = dict(scope["headers"]).get(b"x-request-id")
        request_id = incoming.decode("latin-1") if incoming else f"req_{uuid.uuid4().hex[:12]}"
        token = request_id_var.set(request_id)

        async def send_with_id(message: Message) -> None:
            if message["type"] == "http.response.start":
                message.setdefault("headers", []).append(
                    (b"x-request-id", request_id.encode("latin-1"))
                )
            await send(message)                      # forward immediately — never hold

        try:
            await self.app(scope, receive, send_with_id)
        finally:
            request_id_var.reset(token)              # or the id leaks to the next request
```

Three things to look at. The `scope["type"]` guard — lifespan and WebSocket scopes flow through the same stack, and header code that assumes HTTP crashes startup. `send_with_id` forwards every message the moment it sees it, editing `http.response.start` in flight and accumulating nothing. And the `finally` reset: the contextvar is request-scoped only because we scope it (04.4).

Because middleware runs before routing, this works for requests no handler ever sees. Captured from the assembled app:

```text
GET /v1/nope -> 404, x-request-id: req_c2022d554bec        ← no route matched; id anyway
preflight    -> 200, x-request-id: req_bb52a460c3dc        ← answered by CORS, id anyway
with edge id -> x-request-id: req_edge_7bd41c              ← propagated, not replaced
```

Now the trap. Starlette also offers `BaseHTTPMiddleware` (and its decorator sugar `@app.middleware("http")`), which hides `receive`/`send` behind a `request → response` interface. That interface invites reading the response — and there is only one way to "read" a streamed one:

```python
# ledgerly/middleware/audit_dispatch.py — ⚠️ runs fine, wrong under load
class AuditDispatchMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        response = await call_next(request)
        # "Just log the response size" — this joins EVERY chunk into ONE bytes object:
        body = b"".join([chunk async for chunk in response.body_iterator])
        audit_log.info("response", path=request.url.path, bytes=len(body))
        return StreamingResponse(iter([body]), status_code=response.status_code,
                                 headers=dict(response.headers))
```

Measured through an outermost probe that counts `http.response.body` messages, against an 8 MiB streamed CSV export:

```text
plain streaming:            8388608 bytes total, 129 body messages, largest message   65536 bytes
through body-joining audit: 8388608 bytes total,   2 body messages, largest message 8388608 bytes
```

The client sees identical bytes, every test passes, and the streaming that 03.11 will build is silently gone: the full response materialises in memory per concurrent request, and time-to-first-byte becomes time-to-last-byte. A 300 MB export through this layer is a 300 MB allocation. The pure-ASGI equivalent observes without holding — the same `send`-wrapper shape as above, summing `len(message.get("body", b""))` per message and logging on the last. Body *rewriting* (compression, say) belongs at the proxy (01.10), not here.

## Design Patterns / Tradeoffs

### Pure-ASGI class vs `BaseHTTPMiddleware`

**Pure ASGI** — a class with `__init__(self, app)` and `__call__(scope, receive, send)`, the repo convention (03.1). *Advantages:* sees the protocol as it is — messages, not materialised objects — so streaming, WebSockets and lifespan pass through untouched; no hidden machinery; cheapest possible layer. *Disadvantages:* the raw interface is easy to get subtly wrong (forgetting the scope-type guard or to forward a message); headers are byte-pair lists, not a mapping. *Failure modes:* a swallowed message hangs the response; a mutated scope surprises inner layers.

**`BaseHTTPMiddleware`** — subclass with `dispatch(request, call_next)`. *Advantages:* the familiar `Request`/`Response` vocabulary; fine for header-only logic on non-streaming routes. *Disadvantages:* it inserts real machinery — the downstream app runs in a separate task, the response re-wrapped as a stream — and its convenience invites exactly the body-buffering shown above. *Failure modes:* buffered streams; and its task boundary has historically interacted poorly with downstream contextvars and disconnect cancellation, behaviour that has shifted across Starlette versions — which is itself the argument: it couples you to machinery you don't control. *When to use:* quick internal tooling. *When NOT:* anything that streams, or that other middleware must compose with predictably.

### Middleware vs dependency vs the proxy

The real decision is rarely "how do I write middleware" — it is whether the concern belongs here at all. The three homes see different worlds:

| | Middleware | Dependency (03.5) | Edge proxy (01.10) |
|---|---|---|---|
| Sees | Every request: 404s, preflights, unauthenticated | Only requests matched to its route | Everything, before your process |
| Has | Raw scope: method, path, header bytes | Path params, validated input, DI, other deps | Its own config language |
| Errors become | ⚠️ bare 500s past your handlers | Properly mapped responses (401/403/422, 03.8) | Proxy error pages |
| In OpenAPI | Invisible | Declared (headers, security) | Invisible |
| Right for | Request ids, CORS, cache policy, body-size caps, metrics | Auth, tenant resolution, authorisation, per-route policy | TLS, compression, buffering, static, coarse rate limits |

The rule that falls out: **if the concern needs to know *who* or *which route*, it is a dependency; if it must touch every byte in or out regardless of routing, it is middleware; if it is transport plumbing every service needs, it is the proxy.** Authentication in middleware is the classic misplacement, and module 08 builds it as dependencies for exactly these reasons.

### Assembling the stack

Sequential `add_middleware` calls read backwards, and worse, they *scatter* — a second module can add a layer no reviewer sees next to the others. Prefer the constructor list: the whole stack in one block, ordered as it executes:

```python
# ledgerly/main.py (excerpt) — order here IS execution order, outermost first
app = FastAPI(
    title="Ledgerly Invoicing API",
    lifespan=lifespan,
    middleware=[
        Middleware(RequestContextMiddleware),        # ids for everything below, incl. CORS rejections
        Middleware(CORSMiddleware, **cors_kwargs(settings)),   # 01.9; answers preflights here
        Middleware(CachePolicyMiddleware),           # 01.4; stamps responses passing outward
        Middleware(TenantAuditMiddleware),           # innermost: routed traffic only
    ],
)
```

**Recommendation:** pure-ASGI classes, assembled in the constructor list, snapshot-tested (below). Keep the stack short — each layer taxes every request, and most candidates for "new middleware" are really dependencies or proxy config.

## Production Scenario

**Ledgerly, Tuesday 09:58.** Deploy `2026-08-25.2` ships `TenantAuditMiddleware` — a compliance requirement (16.13): record route, tenant and API-key prefix for every API call. The review comment on the pull request reads "added last so nothing escapes it": one `app.add_middleware(TenantAuditMiddleware)` appended below the existing middleware block. By 10:04, support has 12 tickets — the dashboard at `app.ledgerly.com` will not load. By 10:15, forty.

### Symptoms

- Every browser user sees a dead dashboard. The console shows the browser's CORS complaint: the preflight response has no `Access-Control-Allow-Origin` header, so the actual request was never sent.
- Server-to-server integrations — the majority of traffic, `key_live_7ac…` among them — are **completely unaffected**.
- The 5xx alert fires, but weakly: errors are only 3% of requests. `http_server_errors_total` by method: **100% of the 5xxs are `OPTIONS`.** Their route label is unmatched — no route ever saw them.
- The error responses are `text/plain` — the `Api5xxOutsideErrorContract` alert (every 5xx body must be RFC 9457 `application/problem+json`, 02.9) fires for the first time since it was written.
- The error log lines carry `request_id=-`. Repeating, from uvicorn:

```text
ERROR:    Exception in ASGI application
Traceback (most recent call last):
  ...
  File ".../starlette/middleware/errors.py", line 164, in __call__
    await self.app(scope, receive, _send)
  File "/app/ledgerly/middleware/tenant_audit.py", line 14, in __call__
    scheme, credential = headers[b"authorization"].split(b" ", 1)
                         ~~~~~~~^^^^^^^^^^^^^^^^^^
KeyError: b'authorization'
```

### Diagnosis

1. **Alert → Metrics.** Support noise says "browsers only"; metrics agree — the 5xxs are exclusively `OPTIONS` with no matched route. Only one thing sends routeless `OPTIONS` at volume: **CORS preflights** (01.9). That eliminates handlers, the database and every dependency in two minutes — no routed request is failing.
2. **The misdirection.** The browser says "CORS policy", so the first fifteen minutes go to CORS configuration. A config diff eliminates that hypothesis — nothing in `cors_allowed_origins` changed. The CORS *config* is fine; something is preventing the CORS *middleware* from answering.
3. **Logs.** The traceback names `tenant_audit.py` and `KeyError: b'authorization'`. Two details in the same log lines carry the ordering story: `request_id=-` — the error happened **outside** `RequestContextMiddleware` — and `errors.py` directly above the audit frame — the exception fell straight from the new middleware into `ServerErrorMiddleware`, past every handler.
4. **Reproduce.** A preflight is just an `OPTIONS` request you can send yourself (01.9):

```bash
$ curl -s -i -X OPTIONS https://api.ledgerly.com/v1/invoices \
    -H 'Origin: https://app.ledgerly.com' \
    -H 'Access-Control-Request-Method: GET' \
    -H 'Access-Control-Request-Headers: authorization'
HTTP/1.1 500 Internal Server Error
content-type: text/plain; charset=utf-8

Internal Server Error
```

   The same request *with* an `Authorization` header returns 200. The asymmetry names the bug: preflights carry no credentials, **by specification** — the whole point of a preflight is to ask permission before sending them.

### Root Cause

The audit middleware, registered last and therefore outermost, sat above `CORSMiddleware` — so it received CORS preflights, which previously never penetrated below the CORS layer. Preflights carry no `Authorization` header, so its unguarded parse raised on every one; raised above both `ExceptionMiddleware` and `CORSMiddleware`, each error left as a bare 500 with no CORS headers, which browsers report as a CORS failure rather than a server error.

The post-mortem repro made the ordering point brutally concrete — the identical middleware, registered one position earlier (inside CORS):

```text
--- audit OUTSIDE cors (the deploy)  --- preflight OPTIONS -> 500, allow-origin: None
--- audit INSIDE  cors (one line moved) preflight OPTIONS -> 200, allow-origin: https://app.ledgerly.com
```

One line lower and there is no incident — and no bug report either, because preflights would never reach the broken parse. The defect was real in both orderings; only the assembly decided whether it detonated. This is 03.2's route-shadowing lesson wearing a different coat: **the unit was correct, the assembled application was not.** The assembled-app suite existed, but no test sent a preflight — the one request a browser constructs and a test author forgets.

### Fix

*Mitigation (10:22, six minutes):* roll back to the previous image (14.17). Browser traffic recovers immediately. No flag existed to disable the middleware without a deploy — noted for 14.16.

*Permanent fix, in review the same week:*

1. **Attribution moved to where identity exists.** Recording *which tenant, which key* requires resolved identity — `get_tenant`'s job (03.5) — so the audit event moves to a router-level dependency, where a malformed credential becomes a mapped 401 (03.8), not a 500. The middleware keeps only the raw access record and **parses nothing**.
2. **The stack rewritten in constructor-list form** (Tradeoffs above), audit layer inside CORS, with the walkable-stack transcript pasted into the pull request.
3. **An `Exception` backstop handler** returning `application/problem+json`, wired by FastAPI into `ServerErrorMiddleware` — so even a middleware failure speaks the error contract (02.9). With honesty about its limit: that response is emitted *outside* `CORSMiddleware` and will still trigger browser CORS complaints. The backstop fixes the contract for API clients; only middleware that does not raise fixes browsers.

### Prevention

The incident closes into two named tests on the assembled app and one alert that already proved itself:

```python
# tests/architecture/test_middleware_stack.py
def test_preflight_requires_no_credentials() -> None:
    """Browsers send preflights with NO Authorization header — so do we, to every route."""
    client = TestClient(app)
    for route in api_routes(app):
        response = client.options(example_path(route), headers={
            "Origin": "https://app.ledgerly.com",
            "Access-Control-Request-Method": next(iter(route.methods)),
            "Access-Control-Request-Headers": "authorization,content-type",
        })
        assert response.status_code == 200, route.path
        assert "access-control-allow-origin" in response.headers, route.path

def test_middleware_stack_order() -> None:
    """The stack is assembly, not code review folklore. Reordering must show in a diff."""
    layer, names = app.build_middleware_stack(), []
    while not isinstance(layer, APIRouter):
        names.append(type(layer).__name__); layer = layer.app
    assert names == ["ServerErrorMiddleware", "RequestContextMiddleware", "CORSMiddleware",
                     "CachePolicyMiddleware", "TenantAuditMiddleware",
                     "ExceptionMiddleware", "AsyncExitStackMiddleware"]
```

- The `Api5xxOutsideErrorContract` alert stays: any `text/plain` 5xx means an error escaped the handlers — which now specifically implies *middleware*, making it a locator, not just a detector.
- Review rule, added to the middleware directory's README: middleware runs before routing, authentication and validation, so it may assume **nothing** about the request. The requests your handlers never see are precisely the ones middleware must survive.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...middleware raises? | The error skips your exception handlers (they live innermost) → bare `text/plain` 500 from `ServerErrorMiddleware`; register an `Exception` backstop for the contract, and expect CORS-less errors in browsers. |
| ...middleware neither calls downstream nor sends? | No response is ever produced; the server logs that the app returned without completing the response and the client gets a connection-level failure. |
| ...middleware does I/O and that dependency is down? | Every request pays, including `/ready` — a Redis-dependent outermost layer puts Redis in front of your readiness probe (03.6's rule: probes never share a contended resource). Timeouts are mandatory (04.8). |
| ...a request matches no route? | Middleware still ran, all of it. 404s traverse the full stack; metrics and logging middleware must label them safely. |
| ...a browser sends a preflight? | `OPTIONS`, no credentials, answered by `CORSMiddleware` — layers outside CORS see it, layers inside never do. Placement decides exposure. |
| ...someone reorders the stack in a refactor? | Behaviour changes with zero code changes to any middleware. The snapshot test turns that into a visible diff. |
| ...middleware reads the request body from `receive`? | Downstream sees an already-consumed stream unless every message is replayed — buffer-and-replay is a deliberate pattern (16.9 uses it for size caps), not a side effect. |
| ...a streamed response passes a body-joining layer? | It materialises fully in memory per request; time-to-first-byte becomes time-to-last-byte (03.11). |
| ...`add_middleware` runs after startup? | `RuntimeError: Cannot add middleware after an application has started` — the stack is frozen at assembly. |

## Common Pitfalls

**Assuming route-level invariants in middleware.** "Every request has an `Authorization` header" is true at the handler — auth ran — and false in middleware, where preflights, probes and garbage traffic all appear. *Instead:* parse nothing; move identity-dependent work into dependencies.

**Authentication in middleware.** It runs fine, and forfeits DI, OpenAPI visibility and error mapping — a bad credential becomes a 500 instead of a 401. *Instead:* dependencies (03.5); module 08 builds the real thing.

**Reading the body in `BaseHTTPMiddleware`'s dispatch.** One innocuous audit line buffers every streamed response. *Instead:* pure ASGI; observe messages in the `send` wrapper, never hold them.

**Expecting exception handlers to catch middleware errors.** They live innermost; middleware errors fall outward. *Instead:* middleware that cannot raise, plus an `Exception` backstop.

**Ordering by accretion.** Each new `add_middleware` line lands outermost — the newest, least-reviewed code touches every request first. *Instead:* one constructor list, snapshot-tested.

**Blocking or unbounded I/O in a layer.** A 50 ms lookup in middleware is 50 ms on every endpoint, including health probes. *Instead:* keep layers CPU-trivial; anything slower needs a timeout and a reason it isn't a dependency.

**Treating `@app.middleware("http")` as a third kind.** It is `BaseHTTPMiddleware` in disguise, same semantics. *Instead:* choose between the two real options on their tradeoffs.

## How to Test This

- The two named tests from Prevention, on the assembled app: the preflight sweep and the stack-order snapshot.
- A streaming test with an outermost probe counting `http.response.body` messages — many small messages, not one big one — pinning the no-buffering property.
- A contextvar-scoping test: two sequential requests through `RequestContextMiddleware` observe different ids, and a request *without* the middleware observes the default (`-`).
- A contract test that a forced handler exception yields `application/problem+json` with the correct status — through the full stack, not a partial app (03.2).

## Interview Questions

1. *Explain.* Walk a request through a FastAPI middleware stack — what did you register, what did the framework add? — ServerErrorMiddleware outermost, user middleware in reverse registration order, ExceptionMiddleware innermost, then routing.
2. *Explain.* Why does `add_middleware` order "read backwards", and how do you make ordering reviewable? — Each call wraps outside the previous; the constructor list reads outer→inner in one diffable block.
3. *Debug this.* After a deploy, browsers report CORS errors; curl with credentials works; 5xxs are all `OPTIONS`. — New middleware outside CORSMiddleware crashed on credential-less preflights; its 500s lack CORS headers, so browsers misreport the failure.
4. *Explain.* Where do exceptions raised in middleware go? — Past every type-specific handler to ServerErrorMiddleware: bare `text/plain` 500 unless an `Exception` backstop is registered.
5. *Design.* Request-id propagation behind a proxy: which layer, what rules? — Outermost middleware; accept the edge's id, mint otherwise, contextvar for logs (15.2), echo on every response including errors and 404s.
6. *Design.* Compliance wants every call attributed to tenant and key — middleware or dependency? — Attribution needs resolved identity → dependency; raw coverage of unrouted traffic → a parse-nothing middleware; the split is the answer.
7. *Explain.* What breaks when response-logging middleware iterates `body_iterator`? — Streaming: the full body materialises per request; memory and time-to-first-byte degrade with response size.

## Key Takeaways

- Middleware is an ASGI app holding an ASGI app; scope, `receive` and `send` are all that cross a boundary, and wrapping `send` — forwarding every message immediately — is the core technique.
- The stack is assembled **once at startup**; behaviour lives in the assembly, not the classes. **Last `add_middleware` = outermost**; prefer the constructor list, where review order is execution order, and snapshot-test it.
- Middleware runs **before routing**: it sees 404s, preflights and unauthenticated traffic, so it may assume nothing a handler can assume.
- Exceptions in middleware bypass your handlers and break the error contract; browser-facing errors emitted outside `CORSMiddleware` additionally masquerade as CORS failures.
- Concern placement: needs identity or route → dependency; must see every byte regardless of routing → middleware; transport plumbing → proxy.
- Pure-ASGI over `BaseHTTPMiddleware` for anything that streams or must compose predictably; body-joining audit code is the canonical silent killer.
- Middleware cost is paid by every request in the process — including your health probes (03.6).
