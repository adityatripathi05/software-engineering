# 03.2 Routing and Parameters

> **Prerequisites:** 03.1 (application structure), 02.1 (URI design), 02.6 (filter parameters)
> **What you'll learn:**
> - Predict which route FastAPI will match, and why declaration order decides it
> - Use `Annotated` for path, query, header and cookie parameters, with validation in the signature
> - Type path parameters so that a mistyped URL fails usefully rather than confusingly
> - Recognise route shadowing, the most common routing defect and the hardest to see in review
> **Level:** Beginner

---

## Concept

### Plain-English Explanation

Routing is the step where a URL becomes a Python function call. FastAPI does it by walking a list of
routes in the order you registered them and taking the **first one that matches**.

"First one that matches" is a simple rule with a sharp edge. `/v1/invoices/{invoice_id}` matches
`/v1/invoices/overdue` perfectly well — `overdue` is a plausible value for a string path parameter. So
if you register the parameterised route first and add a literal `/v1/invoices/overdue` route later,
the literal route is unreachable. It is registered, it appears in the OpenAPI document, it shows in
the docs page, and it never runs.

Nothing errors. The application starts cleanly. The new endpoint simply returns whatever the *other*
handler decides to do with an invoice id of `"overdue"` — usually a `404`, sometimes a `422`, and
occasionally something worse.

### Technical Explanation

**Matching is ordered and first-wins.** Starlette holds routes in a list; each is tried in turn
against the request path and method. There is no specificity ranking, no "literal beats parameter"
rule, no warning about overlap. Registration order *is* precedence.

```text
routes = [
  APIRoute("/v1/invoices",              methods={"GET","POST"}),
  APIRoute("/v1/invoices/{invoice_id}", methods={"GET","PUT","DELETE"}),   ← matches "overdue"
  APIRoute("/v1/invoices/overdue",      methods={"GET"}),                  ← unreachable
]

GET /v1/invoices/overdue
   ├─ "/v1/invoices"              → no match (extra segment)
   ├─ "/v1/invoices/{invoice_id}" → MATCH, invoice_id="overdue"  ← stops here
   └─ "/v1/invoices/overdue"      → never evaluated
```

**The rule that follows: literal paths must be registered before parameterised ones at the same
depth.** Within a router that is declaration order in the file; across routers it is `include_router`
order (03.1).

**Parameter sources**, all declared in the function signature and all validated by Pydantic:

| Source | Declaration | Notes |
|---|---|---|
| Path | `invoice_id: InvoiceId` | Inferred from the path template; always required |
| Query | `limit: Annotated[int, Query(ge=1, le=200)] = 50` | Defaults make it optional |
| Header | `idempotency_key: Annotated[str, Header(alias="Idempotency-Key")]` | Hyphen/underscore conversion is automatic; `alias` is clearer |
| Cookie | `session: Annotated[str \| None, Cookie(alias=SESSION_COOKIE)] = None` | 01.5 |
| Body | `body: InvoiceCreate` | A Pydantic model is a body by default (03.3) |
| Dependency | `svc: Annotated[Service, Depends(get_service)]` | 03.5 |

**Prefer `Annotated`.** The older style — `limit: int = Query(50, ge=1)` — puts a `Query` object in the
default slot, which means the annotation lies to type checkers and the function cannot be called
directly from a test or a worker. `Annotated[int, Query(ge=1)] = 50` keeps the type honest and the
default a real default.

**Path converters** constrain what a segment may contain, which is how you disambiguate without
relying on order:

```text
/v1/invoices/{invoice_id}                  matches any single segment
/v1/invoices/{invoice_id:int}              digits only — "overdue" no longer matches
/v1/files/{path:path}                      matches across "/" — the only converter that does
```

⚠️ A `:path` converter swallows the rest of the URL, so anything registered after it at that prefix is
unreachable. It is also a directory-traversal surface if the value ever reaches a filesystem call
(16.3).

**Validation errors carry a location.** A failure produces `422` with `loc` telling the client exactly
where the bad value was — `["query", "limit"]`, `["path", "invoice_id"]`, `["body", "amount_cents"]`.
That is worth preserving when you reshape the error body (02.9).

### Mental Model

> Routing is **a list scanned top to bottom, first match wins**. A parameterised segment matches any
> literal you might add later, so *specific before general* is not a style preference — it is the only
> ordering that works. And because a shadowed route still appears in your documentation, the defect is
> invisible everywhere except in production traffic.

## How It Works

The full ordering picture, including the router-level dimension that is easy to miss:

```text
app.include_router(invoices.router)          ← registered first: its routes come first
app.include_router(reports.router)           ← registered second

  invoices.router                              reports.router
    GET  /v1/invoices                            GET /v1/invoices/summary   ⚠️ UNREACHABLE
    POST /v1/invoices                                (shadowed by {invoice_id} above)
    GET  /v1/invoices/{invoice_id}   ←────────────────┘
    GET  /v1/invoices/{invoice_id}/lines

  ⚠️ Ordering is a property of the WHOLE app, not of one file. Two routers can be
     individually correct and collide when combined — which is why the guard is a
     test over app.routes, not a review convention.
```

**What the shadowing handler does with the value** decides how confusing the symptom is:

```text
invoice_id: str        →  service looks up "summary" → 404 "No invoice summary"
                          (a plausible-looking 404 that sends the client hunting for a typo)

invoice_id: int        →  422 {"loc": ["path","invoice_id"], "msg": "not a valid integer"}
                          (confusing, but at least it names the parameter)

invoice_id: InvoiceId  →  a validated pattern (^inv_[0-9a-z]{14}$) rejects it at the edge:
                          422 "string does not match pattern" — unambiguous, and it makes
                          the shadowing visible immediately
```

The third row is the argument for typed identifiers beyond documentation value: **a constrained path
parameter turns silent shadowing into a loud, specific error**.

## Code Example

Route registration with the ordering made explicit and enforced:

```python
# ledgerly/routers/invoices.py
from typing import Annotated
from fastapi import APIRouter, Depends, Header, Path, Query, Response, status

from ledgerly.ids import InvoiceId
from ledgerly.schemas.invoice import InvoiceOut, InvoiceCreate, Page

router = APIRouter(prefix="/invoices", tags=["invoices"], redirect_slashes=False)  # 02.1

# ─── literal paths FIRST ──────────────────────────────────────────────────────
# Anything below the parameterised route would be shadowed by {invoice_id}.

@router.get("/summary", response_model=InvoiceSummary, name="getInvoiceSummary")
async def get_summary(svc: Service, tenant: Tenant) -> InvoiceSummary:
    return await svc.summary(tenant)

@router.get("/overdue", response_model=Page[InvoiceOut], name="listOverdueInvoices")
async def list_overdue(svc: Service, tenant: Tenant) -> Page[InvoiceOut]:
    return await svc.list_invoices(tenant, status="overdue")

# ─── collection ───────────────────────────────────────────────────────────────

@router.get("", response_model=Page[InvoiceOut], name="listInvoices")
async def list_invoices(
    svc: Service,
    tenant: Tenant,
    limit: Annotated[int, Query(ge=1, le=200, description="Page size.")] = 50,
    cursor: Annotated[str | None, Query(description="Opaque; echo `next_cursor`.")] = None,
) -> Page[InvoiceOut]:
    return await svc.list_invoices(tenant, limit=limit, cursor=cursor)      # 02.5

# ─── parameterised paths LAST ─────────────────────────────────────────────────

@router.get("/{invoice_id}", response_model=InvoiceOut, name="getInvoice")
async def get_invoice(
    # A constrained pattern rejects "summary" and "overdue" loudly rather than
    # letting them look like real ids — see How It Works.
    invoice_id: Annotated[InvoiceId, Path(pattern=r"^inv_[0-9a-z]{14}$")],
    svc: Service, tenant: Tenant,
) -> InvoiceOut:
    return await svc.get_invoice(tenant, invoice_id)
```

Header and cookie parameters, with aliases rather than relying on name conversion:

```python
# ledgerly/routers/invoices.py (continued)
@router.post("", status_code=status.HTTP_201_CREATED, response_model=InvoiceOut,
             name="createInvoice")
async def create_invoice(
    body: InvoiceCreate,
    response: Response,
    svc: Service,
    tenant: Tenant,
    # alias= is explicit and survives renaming the Python parameter. Required
    # (no default) because 02.8 makes it mandatory on unsafe endpoints.
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key",
                                           min_length=8, max_length=255)],
    if_match: Annotated[str | None, Header(alias="If-Match")] = None,
) -> InvoiceOut:
    invoice = await svc.create_invoice(tenant, body, idempotency_key=idempotency_key)
    response.headers["Location"] = f"/v1/invoices/{invoice.id}"      # 01.3
    return invoice
```

And the guard that makes ordering a property the application asserts about itself:

```python
# ledgerly/routing/guards.py
import re
from fastapi import FastAPI
from fastapi.routing import APIRoute

PARAM = re.compile(r"\{[^}]+\}")

def assert_no_shadowed_routes(app: FastAPI) -> None:
    """Fails at startup if a literal path is registered after a parameterised
    path that would match it. Registration order is precedence, and a shadowed
    route still appears in the docs — so nothing else will tell you (03.2)."""
    seen_parameterised: list[str] = []
    for route in app.routes:
        if not isinstance(route, APIRoute):
            continue
        if PARAM.search(route.path):
            seen_parameterised.append(route.path)
            continue
        for earlier in seen_parameterised:
            if re.fullmatch(PARAM.sub(r"[^/]+", earlier), route.path):
                raise RuntimeError(
                    f"Route {route.path!r} is shadowed by {earlier!r} registered earlier. "
                    "Declare literal paths before parameterised ones (03.2)."
                )
```

Called from `main.py` after `include_router`, this turns a silent production defect into a process
that refuses to start — the same principle as 01.9's wildcard-CORS validator.

## Design Patterns / Tradeoffs

### Disambiguating overlapping paths

**A. Ordering — literals before parameters** (✅ the baseline)

- *Advantages:* no extra syntax; works for every case; costs nothing.
- *Disadvantages:* invisible in review, and fragile across routers — two individually-correct files can
  collide when combined.
- *Failure mode:* a shadowed route that appears in the docs and never runs.
- *Use when:* always, backed by the startup assertion above.

**B. Constrained path parameters** (`pattern=`, `:int`)

- *Advantages:* makes shadowing impossible rather than merely avoided; produces a specific `422`;
  documents the id format in OpenAPI.
- *Disadvantages:* a format change becomes a routing change; a wrong pattern rejects valid ids.
- *Use when:* your identifiers have a stable, documented shape — which they should (02.1).

**C. A distinct path prefix for non-id sub-resources**

`/v1/invoices/{invoice_id}` and `/v1/invoice-reports/summary` cannot collide at all. It costs a less
tidy URI space and removes the problem structurally. Reasonable when a "view" is really a different
resource (02.1).

**Recommendation:** all three together — constrained parameters as the primary defence, literals-first
as the convention, and the startup guard so neither can be forgotten.

### `Annotated` vs the default-value style

| | `Annotated[int, Query(ge=1)] = 50` | `int = Query(50, ge=1)` |
|---|---|---|
| Type checkers | Correct — the type is `int` | Confused — the default is a `Query` object |
| Calling the function directly | Works; the default is `50` | Broken; you get a `Query` instance |
| Reusable parameter definitions | ✅ `Limit = Annotated[int, Query(ge=1, le=200)]` | ❌ |
| FastAPI support | Current and recommended | Legacy, still supported |

Use `Annotated`, and hoist repeated declarations into named aliases so the same parameter is defined
once for the whole API.

### Where validation belongs

Signature-level constraints (`ge`, `le`, `pattern`, `max_length`) are **cheap and early**: they reject
bad input before any handler code, any dependency resolution, and any database access. Push as much as
possible there. Reserve service-layer validation for rules that need data — "this invoice belongs to
this tenant", "this state transition is legal" — which cannot be expressed in a type (07.3).

## Production Scenario

**Ledgerly, Tuesday 11:40.** The reporting team ships a new endpoint, `GET /v1/invoices/summary`,
which the dashboard's new landing page depends on. It works perfectly in local development and passes
its unit tests. In production, the landing page shows "Failed to load summary" for every user.

### Symptoms

- `GET /v1/invoices/summary` returns `422`:

```json
{"type":"https://api.ledgerly.com/problems/validation-failed","title":"Validation failed",
 "status":422,"detail":"The request has 1 invalid field(s)",
 "errors":[{"field":"invoice_id","code":"string_pattern_mismatch",
            "message":"String should match pattern '^inv_[0-9a-z]{14}$'"}]}
```

- The error names **`invoice_id`** — a parameter the summary endpoint does not have and the client
  never sent.
- The endpoint is present in `/docs`, present in `openapi.json`, and its handler has full test
  coverage.
- The developer's local branch works. So does the test suite. So does a `TestClient` call in the
  reporting module's own tests.
- `http_requests_total{route="/v1/invoices/{invoice_id}"}` shows the traffic — attributed to the
  *wrong route*, which is the clue nobody looked at for forty minutes.

### Diagnosis

1. **Alert.** None. A `422` is a client error; the `4xx` dashboards show a small rise attributed to a
   route that legitimately receives bad ids sometimes.
2. **Reproduce.** Immediate and consistent in production, never locally. That combination usually
   means environment — but the code is identical, so it must be *assembly*.
3. **The error message is the diagnosis, if you read it literally.** The response mentions
   `invoice_id`. A request that reaches a handler which validates `invoice_id` **is being handled by
   the invoice-detail route**. The summary handler never ran.
4. **Confirm by dumping the route table** in the running application:

```python
>>> [(r.path, r.name) for r in app.routes if r.path.startswith("/v1/invoices")]
[('/v1/invoices',              'listInvoices'),
 ('/v1/invoices/{invoice_id}', 'getInvoice'),        # ← matches "summary"
 ('/v1/invoices/{invoice_id}/lines', 'listInvoiceLines'),
 ('/v1/invoices/summary',      'getInvoiceSummary')] # ← registered last, unreachable
```

5. **Why it worked locally.** The developer had been running the reporting router alone
   (`uvicorn ledgerly.routers.reports:router`) for iteration speed, and their tests built a
   `TestClient` from a minimal app containing only that router. In both cases no `{invoice_id}` route
   existed to shadow it. **The defect exists only in the assembled application**, which nothing in
   their workflow constructed.
6. **Find the cause of the ordering.** The summary endpoint was added to `reports.router`, and
   `include_router(reports.router)` came *after* `include_router(invoices.router)` in `main.py` — a
   line nobody looked at, in a file the reporting change did not touch.

### Root Cause

Route matching is first-wins over registration order. `/v1/invoices/{invoice_id}` was registered before
`/v1/invoices/summary`, so the literal path was unreachable. The path parameter's `pattern` constraint
then rejected `"summary"`, producing a `422` about a parameter the client never sent.

Three properties made this hard:

- **The shadowed route appears in the OpenAPI document and the docs page**, because the document is
  generated from the route table rather than from reachability. Everything *looked* correct.
- **The collision is a property of the assembled app**, not of either router. Both files are correct in
  isolation, and the pull request touched neither `main.py` nor `invoices.py`.
- **The tests constructed a partial application.** Fast, focused tests that build a minimal app are
  good practice and cannot see this class of bug at all.

The constrained `pattern` on `invoice_id`, added in 02.1, made the symptom *specific* rather than a
plausible-looking `404` — which shortened the investigation considerably once someone read the error
literally.

### Fix

*Mitigation (3 minutes):* move the summary route above the parameterised route. Because it lived in a
different router, this meant reordering `include_router` calls:

```diff
- app.include_router(invoices.router, prefix="/v1")
  app.include_router(reports.router, prefix="/v1")
+ app.include_router(invoices.router, prefix="/v1")   # parameterised routes last
```

⚠️ That fix is correct and fragile: it depends on a reviewer noticing next time. The permanent fix is
to stop depending on ordering.

*Permanent fix:*

1. **`assert_no_shadowed_routes(app)` called at startup**, so a shadowed route stops the process
   instead of returning a confusing `422` in production.
2. **The literal views moved into the invoices router**, above the parameterised routes, with a comment
   marking the boundary. Related paths belonging to one resource live in one file (02.1, 03.1).
3. **Contract tests run against the assembled application**, not a partial one — see below.

### Prevention

- **The startup guard is the control.** Everything else is convention; this refuses to boot.
- **Test against the real app.** The generalised lesson from this incident:

```python
# tests/conftest.py
from ledgerly.main import app as real_app     # the ASSEMBLED application

@pytest.fixture
async def client():
    """Every API test uses the real app. Building a minimal app per test module is
    faster and cannot see route shadowing, middleware ordering (03.7) or handler
    registration — all of which are properties of assembly (03.2)."""
    transport = ASGITransport(app=real_app)
    async with AsyncClient(transport=transport, base_url="http://test") as c:
        yield c
```

- **A smoke test per route**, asserting that each registered route is actually reachable and dispatches
  to the handler it names:

```python
# tests/routing/test_every_route_is_reachable.py
@pytest.mark.parametrize("route", ROUTES, ids=lambda r: r.name)
@pytest.mark.anyio
async def test_literal_route_dispatches_to_its_own_handler(client, auth, route):
    if "{" in route.path or "GET" not in route.methods:
        pytest.skip("parameterised or non-GET")
    response = await client.get(route.path, headers=auth)
    assert response.status_code != 422 or "invoice_id" not in response.text, (
        f"{route.path} appears to be shadowed by a parameterised route (03.2)"
    )
```

- **Constrain every path parameter with a pattern.** It converts silent shadowing into a specific,
  greppable error and documents the identifier format (02.1, 02.4).
- **Treat "works locally, fails in production, identical code" as an assembly problem.** Route order,
  middleware order (03.7) and handler registration are all properties of the whole application, and all
  three are invisible to tests that build a subset of it.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a literal path is added after a parameterised one? | It is unreachable, still documented, and silently mis-dispatched. The startup guard is the only reliable detection. |
| ...two routers define overlapping paths? | Whichever is included first wins. Ordering is an application-level property, not a file-level one. |
| ...a path parameter is unconstrained? | Any literal you later add is swallowed, and the symptom is a plausible `404`. |
| ...a `:path` converter is used? | It matches across `/`, so everything registered after it at that prefix is unreachable — and it is a traversal surface (16.3). |
| ...a client sends a header with underscores? | HTTP headers use hyphens; rely on `alias=` rather than implicit conversion. |
| ...a query parameter is unknown? | Ignored by default — the silent-filter problem (02.6). Use a model with `extra="forbid"`. |
| ...validation fails? | `422` with `loc` naming the source and field. Preserve that structure when reshaping errors (02.9). |
| ...a test builds a partial app? | It cannot see shadowing, middleware order or registration defects. Test the assembled app. |

## Common Pitfalls

**Parameterised routes before literal ones.** The incident above. *Instead:* literals first, patterns on
parameters, and a startup assertion.

**Assuming the docs page proves reachability.** OpenAPI is generated from the route table, not from what
can actually be dispatched. *Instead:* a reachability smoke test.

**`int = Query(50, ge=1)` instead of `Annotated`.** Breaks type checking and direct calls. *Instead:*
`Annotated[int, Query(ge=1)] = 50`.

**Unconstrained path parameters.** Makes shadowing silent and lets malformed ids reach the service
layer. *Instead:* `pattern=` matching your documented id format.

**Testing routers in isolation only.** Fast, useful, and blind to assembly defects. *Instead:* at least
one suite against the assembled app.

**Putting the version prefix on each decorator.** `@router.get("/v1/invoices/...")` in every file makes
a new version a mass edit. *Instead:* `include_router(prefix="/v1")` (02.3).

**Relying on trailing-slash redirects to fix a near-miss path.** 02.1's incident. *Instead:*
`redirect_slashes=False` and one canonical form.

## How to Test This

- The startup guard, exercised by a test that registers a deliberately shadowed route and asserts the
  application refuses to start.
- The reachability smoke test over the assembled route table.
- A parameter-validation test per constrained path parameter: a valid id `200`s, a malformed one `422`s
  with `loc == ["path", ...]`.
- A test that the assembled app's route list matches a committed snapshot, so an ordering change shows
  up as a reviewable diff (the same idea as committing `openapi.json` — 02.4).

## Interview Questions

1. *Explain.* How does FastAPI choose which route handles a request? — First match in registration
   order; no specificity ranking.
2. *Debug this.* A new endpoint returns `422` naming a parameter it does not declare, works locally, and
   appears in the docs. — Route shadowing; dump the assembled route table.
3. *Explain.* Why does `Annotated` matter for parameter declarations? — It keeps the annotation honest
   for type checkers and direct calls, and makes declarations reusable.
4. *Design.* How do you make route shadowing impossible rather than merely avoided? — Constrained path
   parameters plus a startup assertion over the route table.
5. *Explain.* Why can a route be in the OpenAPI document and still be unreachable? — The document is
   generated from the route table, not from dispatch reachability.
6. *Explain.* What is special about a `:path` converter? — It matches across `/`, shadowing everything
   after it, and it is a traversal risk.
7. *Design.* Two teams own two routers with overlapping prefixes. How do you prevent collisions? —
   Ownership by resource, a startup guard, and reachability tests in the shared CI pipeline.

## Key Takeaways

- Routing is **first-match-wins over registration order**. Specific before general is a correctness
  rule, not a convention.
- A shadowed route still appears in your documentation and your OpenAPI document. **Nothing tells you**
  — so assert it at startup.
- Constrain path parameters with patterns. It turns silent shadowing into a specific error and
  documents the id format.
- Use `Annotated` for every parameter so the type stays honest and declarations are reusable.
- Route order, middleware order and handler registration are properties of the **assembled
  application**. Tests that build a partial app cannot see any of them.
- "Works locally, fails in production, identical code" almost always means an assembly difference.
- Push validation into the signature where it is cheap and early; keep data-dependent rules in the
  service layer.
