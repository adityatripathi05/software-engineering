## Concept

### Plain-English Explanation

A worker process has a life: it is born, it serves requests for hours or weeks, and it dies — at a deploy, a scale-down, or a crash. **Lifespan** is the one place where code runs exactly once at each end of that life. It is literally a context manager around the serving period: everything before the `yield` runs with zero traffic, the process serves while the generator is suspended at the `yield`, and everything after runs with zero traffic again on the way down.

03.1 established *why* resources live here — created per worker, after the fork, never at import. This notebook is about the lifecycle itself: what the protocol guarantees, what startup should and should not gate on, and how the things you start here stay alive and get put away.

### Technical Explanation

**The protocol.** Lifespan is an ASGI scope like `http` (03.7's guard clause exists because of it). On boot, the server sends `lifespan.startup`; Starlette runs your generator up to the `yield`; the app answers `lifespan.startup.complete` — and only then does uvicorn start accepting connections. If the code before `yield` raises, the app answers `lifespan.startup.failed`, and uvicorn prints the traceback, logs `Application startup failed. Exiting.` and exits with **code 3** (captured below). On shutdown — SIGTERM from the orchestrator, Ctrl-C locally — the server stops accepting, lets in-flight requests finish (the draining details are 04.9 and 03.14), then sends `lifespan.shutdown`, which resumes your generator after the `yield`.

**Where the yielded state goes.** The mapping you yield becomes per-request `request.state`: Starlette copies it into each request's scope, so `request.state.engine` is the same engine object for every request (that is the point — one pool per process), while attribute *assignments* on one request's state do not leak into the next. This is the hand-off that 03.5's `get_session` and 03.6's `/ready` rely on.

**Per worker, not per app.** `uvicorn --workers 4` forks four processes; lifespan runs in each. Four engines, four Redis clients, four of every background task. Whatever you size in lifespan multiplies by the worker count — the arithmetic that decides whether Postgres runs out of connections lives in 06.8, but the multiplication happens *here*.

**The failure asymmetry that shapes the design.** An exception before `yield` doesn't degrade the process — it prevents it from *existing*. The orchestrator restarts it, the same exception fires, and the process crash-loops for as long as the cause persists. That is exactly right for a bad configuration: the deploy fails loudly at rollout, no traffic ever meets the broken build. It is exactly wrong for a dependency that can blip: gate startup on a network call and every blip becomes a window in which **no new capacity can come into existence** — no deploys, no scale-ups, no self-healing restarts. The incident below is that window with a rolling deploy inside it.

> **Version note** — behaviour captured on uvicorn 0.46. The default `--lifespan auto` runs the protocol whenever the app supports it; `--lifespan off` skips it entirely, and the app then serves with `request.state` empty — every route that touches state 500s. Never "fix" a lifespan error by turning lifespan off.

⚠️ The older `@app.on_event("startup")` / `("shutdown")` API is deprecated and banned in this repo (§4.3): two disconnected callbacks cannot share locals, and nothing pairs each acquisition with its release. Lifespan is one function where `finally` sits directly under the resources it must undo.

### Mental Model

> Lifespan is a context manager around a worker's serving lifetime. Before `yield`: **construct what you own** — fail fast on your own config, never on someone else's uptime. After `yield`: undo it in reverse. The `yield` line is the boundary between *booting* and *serving*, and the protocol guarantees traffic exists only on the serving side of it.

## How It Works

The whole life of one worker, with the two failure exits:

```text
process start
  │ import ledgerly.main          pure, no sockets (03.1)
  │ lifespan.startup ──▶ code before yield:
  │     get_settings()            ✅ fail fast HERE — config is owned, deterministic
  │     create_async_engine(...)  no I/O: pools connect lazily, on first checkout
  │     Redis.from_url(...)       no I/O
  │     start supervised tasks    sampler (03.6), metrics loops
  │         │
  │         ├─ raises ──▶ lifespan.startup.failed ──▶ exit code 3
  │         │             orchestrator restarts ──▶ ⚠️ crash loop while the cause persists
  │         ▼
  │ startup.complete ──▶ uvicorn binds and accepts   ← traffic can exist only from here
  │ ════════ serving; generator suspended at `yield` ════════
  │ SIGTERM ──▶ stop accepting ──▶ drain in-flight (04.9, 03.14)
  │ lifespan.shutdown ──▶ code after yield: cancel tasks, close clients, dispose engine
  ▼ exit 0                (SIGKILL skips ALL of this — cleanup must tolerate never running)
```

The startup-failure exit, captured by pointing the Redis client at a closed port and running the "fail fast" ping the incident is about:

```text
INFO:     Started server process [12276]
INFO:     Waiting for application startup.
ERROR:    Traceback (most recent call last):
  ...
  File "/app/ledgerly/lifespan.py", line 13, in lifespan
    await redis.ping()          # "fail fast" hardening — the bug
  ...
redis.exceptions.TimeoutError: Timeout connecting to server
ERROR:    Application startup failed. Exiting.
$ echo $?
3
```

Note what is *absent*: the process never bound the port, never answered a probe, never appeared in any request metric. From the orchestrator's side there is only a task that keeps exiting; from the load balancer's side, nothing ever existed. Startup failures are invisible to every observability signal except process logs and restart counts — worth knowing before you decide what is allowed to cause one.

## Code Example

Ledgerly's `lifespan.py`, grown from 03.1's version: the same construct-only resource block, plus the background tasks 03.6 promised, supervised and put away properly.

```python
# ledgerly/lifespan.py
@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[State]:
    settings = get_settings()                     # validated config; raising here is CORRECT
    engine = create_async_engine(settings.database_url, pool_size=settings.db_pool_size)
    redis = Redis.from_url(settings.redis_url, socket_timeout=2, socket_connect_timeout=2)
    tax_client = build_tax_client()               # one client per process (01.7)
    # ⚠️ no ping, no SELECT 1, no warmup call. Startup gates on nothing we don't own;
    # readiness (03.6, 15.9) is what gates TRAFFIC on dependency health.

    tasks = [
        asyncio.create_task(supervise(sample_threadpool), name="threadpool-sampler"),  # 03.6
        asyncio.create_task(supervise(sample_pools), name="pool-sampler"),
    ]
    try:
        yield {"engine": engine, "redis": redis, "tax_client": tax_client}
    finally:
        for task in tasks:                        # reverse of startup: tasks first —
            task.cancel()                         # they USE the clients closed below
        await asyncio.gather(*tasks, return_exceptions=True)
        await tax_client.aclose()
        await redis.aclose()
        await engine.dispose()
```

Two orderings carry the correctness. Tasks are cancelled *before* the clients they use are closed — the reverse of construction, as with any nested resource. And the list of task references is not housekeeping: it is the difference between a background task and a leak, for a reason the next listing exists to show.

⚠️ **A crashed background task is silent.** `asyncio.create_task` returns a task nobody awaits; if it raises, the exception sits unretrieved until the task object is garbage-collected — which for a task held in a list is *never* while the process lives. Captured:

```text
C. app keeps serving; is the sampler alive?
  task.done()=True  exception retrieved by anyone? no
Task exception was never retrieved
future: <Task finished name='Task-8' coro=<sample_threadpool() ...
        exception=RuntimeError('redis connection lost')>
```

The sampler died on its first iteration; the app served happily; asyncio's complaint appeared only when the last reference was dropped. In production that means the metrics from 03.6 quietly stop, and the threadpool alert that closed that incident is blind again. Hence the supervisor:

```python
# ledgerly/observability/tasks.py
async def supervise(factory: Callable[[], Coroutine[None, None, None]]) -> None:
    """Run a lifespan loop forever: log crashes, count them, restart with backoff.
    Exits only via cancellation at shutdown."""
    while True:
        try:
            await factory()
        except asyncio.CancelledError:
            raise                                  # shutdown — propagate, never swallow
        except Exception:
            logger.exception("background_task_crashed", extra={"task": factory.__name__})
            BACKGROUND_TASK_RESTARTS.labels(task=factory.__name__).inc()
            await asyncio.sleep(5)                 # backoff before restart
```

`BACKGROUND_TASK_RESTARTS` rising is a real alert — a sampler restarting every 5 seconds means its dependency is down, and *something* now says so. The bare `raise` on `CancelledError` is load-bearing: swallow it and shutdown hangs waiting for a task that refuses to die (04.8 treats cancellation properly).

Finally, lifespan in tests — the trap first, because it looks like an app bug:

```text
A. TestClient WITHOUT `with` — lifespan never runs
  -> 500 'Internal Server Error'                  ← request.state.engine doesn't exist
B. TestClient inside `with` — lifespan runs, state present
  lifespan: startup
  -> 200 {"engine":"ENGINE-SENTINEL"}
  lifespan: shutdown
```

`TestClient(app)` alone never starts the lifespan; the `with` block is what sends `lifespan.startup` and `.shutdown`. The 03.2 thread again: the assembled application includes its lifecycle, and a fixture that skips it is testing a process state that cannot exist in production. The project's conftest runs the client as a context manager for exactly this reason (13.3).

## Design Patterns / Tradeoffs

### What startup is allowed to gate on

**A. Verify everything at startup** ("fail fast on all of it" — ping Redis, `SELECT 1`, call the tax API)

- *How it works:* lifespan probes each dependency and raises if any is unreachable.
- *Advantages:* a wrong URL or dead dependency surfaces at deploy time, in the deploy log.
- *Disadvantages:* startup now fails whenever anything blips — and a process that cannot start cannot hold capacity, answer probes, or serve the endpoints that *don't* need the dead dependency. Rollback does not help, because the gate is in every image.
- *Failure mode:* the incident below — a dependency blip becomes a no-new-capacity window.
- *Use when:* never for network dependencies. The legitimate fail-fast — malformed config — is already covered by validated settings, with no I/O.

**B. Construct-only startup, readiness gates traffic** (✅ this repo)

- *How it works:* lifespan builds clients (no I/O — engines and pools connect lazily), starts tasks, yields. `/ready` (03.6) reports whether the process can serve; features with soft dependencies degrade (10.x, 15.16).
- *Advantages:* processes always come into existence and hold their slot; a dependency blip degrades exactly the features that need it, for exactly its duration; deploys and scale-ups proceed during blips.
- *Disadvantages:* a genuinely broken dependency URL is discovered at first use, not at boot — which is why readiness must actually check what serving requires, and why config validation must catch the *shape* errors early.
- *Use when:* the default.

**C. Lazy everything** (no lifespan; create resources on first request)

- *Advantages:* nothing to design.
- *Disadvantages:* first requests pay connection setup; under concurrency, many requests race to create the "singleton" (the 03.1 anti-pattern in async form); nothing distinguishes booting from serving.
- *Use when:* scripts and prototypes, not services.

**Recommendation:** B. The rule that keeps it honest: **fail fast on what you own (config, code, wiring); report on what you don't (dependency health, via readiness); never make someone else's uptime a precondition for your process existing.** And keep readiness itself minimal — it gates on what makes serving *impossible*, not on everything the app ever uses, or a cache blip removes your whole fleet (15.9).

### What runs in-process vs elsewhere

Lifespan tasks are per-process by construction, which is precisely right for observation loops (each process samples *its own* threadpool and pools) and precisely wrong for business work: N workers means N copies, and a deploy kills them mid-job. Migrations are the sharpest case — run Alembic in lifespan and every worker races to migrate on every boot, serialised on Postgres locks, coupling schema changes to process restarts. Migrations run once, in the pipeline, before the new image rolls (14.12); recurring business jobs belong to workers with queues and retries (03.10, 11.8).

## Production Scenario

**Ledgerly, Wednesday 11:03.** The managed-Redis provider begins an announced 15-minute maintenance failover. Nobody worries: the API's Redis usage degrades gracefully, and the last provider failover was a non-event. At **11:05**, a routine deploy starts rolling — six replicas, Swarm defaults: `stop-first`, parallelism 2 (14.9).

By 11:09 the deploy is stalled, four replicas are gone, and p99 on the survivors has tripled.

### Symptoms

- The pipeline reports the rolling update **paused: task failures exceed retry limit**.
- Orchestrator logs for every new task: the captured traceback — `redis.exceptions.TimeoutError` inside `lifespan`, then `Application startup failed. Exiting.`, exit code 3, restart, repeat.
- The four running replicas: **healthy**. Latency is up from absorbed load (each now carries 1.5×), and the edge starts returning 429s under 02.12's limits — but errors from Redis itself: none worth paging. Their clients reconnected after the failover on next use, exactly as designed.
- 11:12, the on-call attempts rollback. **The rollback tasks crash with the identical traceback.**

### Diagnosis

1. **Alert.** Deploy-stalled plus latency. The exit-code-3 pattern in task logs says these processes never *started* — so every request-path metric is silent about them; the evidence lives in process logs and restart counts only.
2. **Logs.** The traceback names the line: `await redis.ping()` in `lifespan`. Not a request, not a handler — the boot gate itself.
3. **Dependency health.** The Redis dashboard shows the maintenance window, 11:03–11:18, announced two weeks ago. Correlation is exact: every task that attempted to start inside the window died; every process started before it kept serving.
4. **The rollback failure is the tell.** Rolling back swaps images, and the ping is not in this deploy — `git log` finds it added **three weeks earlier**, as hardening after a staging incident where a wrong `REDIS_URL` produced confusing first-request errors. Every image since carries the gate. The defect is not in what is rolling out; it is in what both versions share — which is why the mitigation cannot be a version change at all.
5. **Eliminated on the way:** the new application code (identical failure on old image), Redis capacity (running replicas fine), and the deploy tooling (it did exactly what `stop-first` promises: removed capacity, then asked for replacements that could not exist).

### Root Cause

A `redis.ping()` added to lifespan as fail-fast hardening made a third-party dependency's uptime a precondition for the process existing. During the failover window no new process could start anywhere — deploy, rollback, restart, or scale-up — while `stop-first` ordering kept removing healthy capacity ahead of replacements that were doomed. A Redis blip that running processes absorbed by design became a fleet-shrinking event purely through the startup path.

### Fix

*Mitigation (11:13):* stop trying to change versions — protect what exists. The update stays paused, edge rate limits are tightened to shed load fairly (02.12), and the team waits out the window. At 11:18 Redis returns, crash-looping tasks start on their next retry, the update resumes and completes by 11:21. Total: 12 minutes degraded, zero data lost, one uncomfortable truth: **there was no faster path** — when startup is gated on a dependency, mitigation is reduced to protecting survivors until the dependency returns.

*Permanent fix:*

1. The ping is deleted; lifespan is construct-only (the Code Example). The staging problem it was solving is re-solved correctly: URL shape validation in settings (07.9) catches typos at deploy, and `/ready`'s diagnostics surface "redis: unreachable" in seconds at first use.
2. `order: start-first` for the API service (14.9): replacements must prove they start before old tasks stop. Capacity can now only grow during a rollout.
3. The team writes down the rule from the retro, because it generalises past Redis: *rollback mitigates bad changes, not latent conditions — anything three weeks old is in every image you can roll to.*

### Prevention

- **The incident closes into a named CI test** — startup must succeed with the entire world unreachable:

```python
# tests/architecture/test_startup_needs_no_dependencies.py
async def test_lifespan_completes_with_everything_down(monkeypatch) -> None:
    """Startup may construct, never connect. If this hangs or raises, someone
    added a network call to lifespan — that is a no-new-capacity window (03.9)."""
    monkeypatch.setenv("LEDGERLY_DATABASE_URL", "postgresql+asyncpg://ledgerly@127.0.0.1:1/x")
    monkeypatch.setenv("LEDGERLY_REDIS_URL", "redis://127.0.0.1:1/0")     # closed port
    get_settings.cache_clear()
    async with asyncio.timeout(1.0):                  # construction is instant; I/O is not
        async with lifespan(app) as state:
            assert {"engine", "redis", "tax_client"} <= state.keys()
```

- **Alert on task restart counts** (exit-code-3 loops), because startup failures are invisible to every request-path signal — the restart counter is their only voice.
- **Runbook entry** keyed to the log pattern: `Application startup failed` + a dependency timeout in lifespan → do not roll back; protect running capacity and fix or wait out the dependency.
- The `BACKGROUND_TASK_RESTARTS` alert from the Code Example ships in the same change — the other way this notebook's machinery fails silently.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...code before `yield` raises? | `startup.failed`, exit 3, no port bound; the orchestrator restarts it into a crash loop until the cause is gone. Only config should be able to do this. |
| ...Redis is down when a replica starts? | Construct-only startup: the replica starts, serves, and Redis-backed features degrade. Ping-gated: no replica can start anywhere. |
| ...a lifespan background task crashes? | Silently dead — the exception is unretrieved while you hold the reference. Supervise: log, count, restart with backoff. |
| ...teardown raises halfway? | Later closes are skipped unless each is guarded; process exit reclaims sockets anyway, but drain-sensitive work is lost (04.9). |
| ...the process gets SIGKILL? | Nothing after `yield` runs. Anything that *requires* cleanup to run is a design bug — crash-safety comes from idempotency and reconciliation (11.x, 19.8). |
| ...`--workers` doubles? | Everything lifespan makes doubles: pools, clients, samplers. Check the connection arithmetic (06.8) before the flag. |
| ...a test builds `TestClient` without `with`? | Lifespan never runs; `request.state` is empty; every state-touching route 500s. The failure is in the fixture, not the app. |
| ...migrations run in lifespan? | Every worker races Alembic on every boot, serialised on locks, and a schema problem becomes a crash loop. Pipeline, once, before rollout (14.12). |

## Common Pitfalls

**Probing dependencies at startup.** The incident. It feels like rigour; it converts every blip into a no-new-capacity window shared by deploy, rollback and self-healing. *Instead:* construct only; validate config shapes; let readiness and degradation do their jobs.

**Fire-and-forget `create_task`.** No reference, no supervision — the task can be dead for weeks, and the first symptom is whatever its output was supposed to prevent. *Instead:* hold references, supervise, count restarts, cancel at shutdown.

**Cleanup outside `finally`, or in registration order.** A startup that half-succeeds, or a teardown where one close raises, leaks the rest. *Instead:* `try/finally` around the `yield`, undo in reverse, guard each close.

**Swallowing `CancelledError` in loops.** The shutdown path cancels your tasks; a loop that catches everything and continues never dies, and shutdown hangs until the orchestrator loses patience. *Instead:* re-raise cancellation, always (04.8).

**Warmups and cache preloads before `yield`.** Each one is another dependency your process cannot exist without, paid on every restart. *Instead:* warm lazily or from a job; keep boot O(construction).

**`on_event` pairs.** Deprecated, and structurally worse: acquisition and release in separate functions drift apart under maintenance. *Instead:* lifespan; the `finally` sits under what it undoes.

## How to Test This

- The closed-ports startup test above — the architecture guarantee that boot needs nobody.
- All API fixtures use `with TestClient(app)` (or the `ASGITransport` equivalent with explicit lifespan), so tests exercise the process state production runs in (13.3).
- A supervisor test: inject a factory that raises twice then blocks; assert two restart-counter increments and that cancellation exits promptly.
- A shutdown test: run the lifespan context over spy resources, exit it, assert every close ran exactly once, in reverse order, even when one raises.

## Interview Questions

1. *Explain.* Walk through what happens between `uvicorn` starting and the first request being accepted. — Import (pure), `lifespan.startup`, your pre-`yield` code, `startup.complete`, then bind/accept; failure before `yield` exits code 3 with no port bound.
2. *Debug this.* During a deploy, new replicas crash-loop with exit 3 while old ones serve fine; rollback crash-loops too. — Startup gates on a blipping dependency; the gate predates the deploy, so no image change helps; protect survivors and remove the gate.
3. *Design.* Which dependency checks belong at startup, readiness, and request time? — Startup: config validation only. Readiness: what makes serving impossible. Request time: everything else, behind timeouts and degradation.
4. *Explain.* Why must you keep references to lifespan background tasks? — An unreferenced task can be GC'd, and a crashed one holds its exception unretrieved; either way the loop is dead with no signal. Supervise and count restarts.
5. *Explain.* Why do migrations not belong in lifespan? — N workers race per boot, schema changes couple to restarts, and failures become crash loops; run once in the pipeline before rollout.
6. *Debug this.* Every test in a new suite gets 500s from routes that work in production. — `TestClient` without `with`: lifespan never ran, `request.state` is empty.
7. *Design.* What must still be correct if the process dies with SIGKILL? — Everything: shutdown code may never run, so correctness rests on idempotent work and reconciliation, not cleanup.

## Key Takeaways

- Lifespan is a context manager around one worker's serving lifetime; traffic exists only between `startup.complete` and `lifespan.shutdown`, and the yielded mapping becomes every request's `request.state`.
- **Fail fast on what you own; never gate startup on what can blip.** A startup probe converts dependency blips into windows where no capacity can be created — and rollback lives inside the window too.
- Startup failures are invisible to request-path telemetry: exit code 3, process logs and restart counters are the only evidence.
- Background tasks started here need references, supervision, restart counting, and cancellation that is re-raised — a dead sampler is a blind alert.
- Teardown mirrors startup in reverse, inside `finally`, each step guarded; and SIGKILL means it may not run at all.
- Everything in lifespan is per worker: multiply by `--workers` before sizing anything.
- Lifespan runs in tests only inside `with TestClient(...)` — fixtures that skip it test an impossible process.
