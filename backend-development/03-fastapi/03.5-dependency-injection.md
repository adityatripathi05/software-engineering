## Concept

### Plain-English Explanation

Dependency injection in FastAPI is a way of saying *"this handler needs a database session, an
authenticated tenant, and a service object — work out how to produce them."* You declare the need in
the signature; FastAPI builds the object graph before your function runs.

It is genuinely excellent for wiring, and it has one behaviour that surprises people badly enough to
cause outages: **a `yield` dependency's cleanup code runs after the response has already been sent.**

That is a sensible design — it means cleanup cannot delay the client — but it has a consequence that
is easy to miss. Anything that can *fail* must not live after the `yield`, because by then it is too
late to tell anyone. A failure there cannot become a `500`, cannot reach your exception handlers, and
cannot stop the `201` the client already has. The client is told the work succeeded; the work did not.

### Technical Explanation

**What `Depends` does.** FastAPI inspects the signature, resolves each dependency (recursively,
because dependencies may have dependencies), and passes the results in. Resolution happens *before*
the handler body.

```text
GET /v1/invoices/inv_9f2c41
   │
   ├─ resolve get_settings()            ─┐
   ├─ resolve get_session(request)       │  built once per request,
   ├─ resolve get_tenant(credentials)    │  in dependency order
   └─ resolve get_invoice_service(       │
           session, tenant)             ─┘
        │
        ▼
   handler runs
        │
        ▼
   response generated and SENT
        │
        ▼
   yield-dependency teardown, in REVERSE order   ⚠️ AFTER the response
```

**Per-request caching.** By default a dependency called from several places in one request is resolved
**once** and reused. `get_settings` invoked by four sub-dependencies produces one call. Disable with
`Depends(fn, use_cache=False)` when you genuinely need a fresh object per call site — rare, and worth
a comment when you do.

⚠️ The cache key includes the *arguments*, so two call sites that pass different values to a
parameterised dependency get two objects. That is correct behaviour and occasionally surprising: a
dependency you believed ran once may run many times because a sub-dependency differs.

**`yield` dependencies** are context managers written as generators:

```python
async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
    async with maker() as session:
        yield session          # ← the handler runs here
    # ← everything after the yield runs AFTER the response is sent
```

Three properties that matter:

1. **Teardown runs after the response.** Raising there cannot change the status or body.
2. **Teardown runs in reverse dependency order** — the last dependency created is the first torn down,
   like nested context managers.
3. **An exception in the handler propagates into the generator** at the `yield`, so `try/finally` and
   `except` work as they would in a context manager. This is how a session can be rolled back on
   failure.

**The rule this produces:**

> Everything after `yield` must be **cleanup that cannot meaningfully fail**: closing a session,
> releasing a lock, returning a connection to a pool. Anything that can fail in a way the client needs
> to know about — above all, `commit()` — belongs inside the handler, where its exception can still
> become a response.

**`dependency_overrides`** is the test seam: `app.dependency_overrides[get_tax_client] = fake_client`
replaces a dependency for the whole application without patching imports. It is the reason to inject
collaborators rather than import them (13.8).

### Mental Model

> A dependency is **a promise to have something ready before the handler runs, and to tidy up after
> the response has gone**. The word *after* is load-bearing: teardown happens in a world where the
> client already believes it knows what happened. Put nothing there that could make that belief false.

## How It Works

The timing that causes the incident, drawn against the response:

```text
❌ COMMIT IN TEARDOWN                          ✅ COMMIT IN THE HANDLER

  resolve get_session                            resolve get_session
     └─ session opened                              └─ session opened
  handler: repo.insert(invoice)                  handler: repo.insert(invoice)
  handler: return invoice                        handler: await session.commit()
     │                                              │  └─ IntegrityError raised HERE
  201 Created SENT TO CLIENT ────────▶ 😀           │
     │                                           exception propagates to the
  teardown: await session.commit()               handler's caller
     └─ IntegrityError ⚠️                           │
        · response already sent — cannot           error handler maps it (03.8)
          be changed                                  │
        · exception handlers do NOT run           409 Conflict SENT TO CLIENT ──▶ 🙂
        · logged as an unhandled task error          │
        · TRANSACTION ROLLED BACK                 teardown: session.close()  (cannot fail
                                                             meaningfully)
  Client holds a 201 and an invoice id
  for a row that does not exist.
```

**Where the session, the transaction and the service sit** in a correct arrangement:

```text
get_session          opens a session; rolls back on exception; CLOSES it in teardown
     │                (teardown does no work that can fail)
     ▼
get_repository       wraps the session; no transaction control
     │
     ▼
get_invoice_service  owns the transaction: `async with session.begin(): …`  (07.5)
     │
     ▼
handler              calls the service; maps domain errors to HTTP (07.3)
```

The service owning the transaction is the Unit of Work pattern arriving early (06.10, 07.5). The point
here is narrower: **transaction boundaries must be inside the request, not in teardown**, because only
there can a failure become a response.

## Code Example

The session dependency, doing only what cannot fail:

```python
# ledgerly/deps.py
from typing import Annotated, AsyncIterator
from fastapi import Depends, Request
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker

async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
    """Owns the session's LIFETIME, not its transaction.

    ⚠️ No commit here. Code after `yield` runs once the response has been sent,
    so a failing commit cannot become an error response — the client would hold a
    201 for a row that was rolled back (03.5).
    """
    maker = async_sessionmaker(request.state.engine, expire_on_commit=False)
    session = maker()
    try:
        yield session
    except Exception:
        # The handler raised. Roll back before the connection returns to the pool,
        # so the next request does not inherit an aborted transaction (06.3).
        await session.rollback()
        raise
    finally:
        await session.close()      # cannot meaningfully fail

Session = Annotated[AsyncSession, Depends(get_session)]
```

The service, which owns the transaction inside the request:

```python
# ledgerly/services/invoices.py (excerpt)
class InvoiceService:
    def __init__(self, session: AsyncSession, repo: InvoiceRepository,
                 clock: Clock) -> None:
        self._session, self._repo, self._clock = session, repo, clock

    async def create_invoice(self, tenant: TenantId, body: InvoiceCreate, *,
                             idempotency_key: str) -> Invoice:
        # The transaction opens and closes INSIDE the request. An IntegrityError
        # here propagates to the handler, is mapped by the error handlers (03.8),
        # and the client receives 409 instead of a false 201.
        async with self._session.begin():
            invoice = self._build(tenant, body)
            await self._repo.insert(invoice, idempotency_key=idempotency_key)
            await self._outbox.enqueue(self._session, "invoice.created", invoice.id)
        return invoice
```

Wiring, with each dependency doing one thing:

```python
# ledgerly/deps.py (continued)
from fastapi import Header, HTTPException, Request

async def get_tenant(request: Request,
                     authorization: Annotated[str | None, Header()] = None) -> TenantId:
    """Identity from the credential — never from the request body (03.3)."""
    if authorization is None:
        raise HTTPException(401, "Missing credentials",
                            headers={"WWW-Authenticate": "Bearer"})     # 01.3
    return await resolve_tenant(request.state.redis, authorization)

def get_invoice_repository(session: Session) -> InvoiceRepository:
    return InvoiceRepository(session)

def get_invoice_service(
    session: Session,
    repo: Annotated[InvoiceRepository, Depends(get_invoice_repository)],
) -> InvoiceService:
    return InvoiceService(session, repo, clock=SystemClock())

# Named aliases keep handler signatures short and the wiring in one place (03.2).
Service = Annotated[InvoiceService, Depends(get_invoice_service)]
Tenant = Annotated[TenantId, Depends(get_tenant)]
```

Router-level dependencies for cross-cutting requirements that are not values:

```python
# ledgerly/routers/invoices.py
router = APIRouter(
    prefix="/invoices",
    tags=["invoices"],
    # Runs for every route in this router. `dependencies=` is for side-effecting
    # checks whose return value nobody needs — authorisation, rate limiting.
    dependencies=[Depends(require_scope("invoices:read"))],      # 08.12
)
```

And the test seam that dependency injection exists for:

```python
# tests/conftest.py
from ledgerly.main import app
from ledgerly.deps import get_tenant, get_tax_client

@pytest.fixture
def override_dependencies(fake_tax_client):
    """Replaces collaborators without patching imports — no knowledge of where
    the module imports what (modern-python 15.5's 'inject, don't patch')."""
    app.dependency_overrides[get_tenant] = lambda: TenantId("t_test")
    app.dependency_overrides[get_tax_client] = lambda: fake_tax_client
    yield
    app.dependency_overrides.clear()        # ⚠️ or state leaks into the next test (13.6)
```

## Design Patterns / Tradeoffs

### Where the transaction boundary lives

**A. In the `yield` dependency (commit after `yield`)**

- *How it works:* the session dependency commits during teardown.
- *Advantages:* handlers never write `commit()`; one place controls it; superficially DRY.
- *Disadvantages:* **the commit happens after the response has been sent**, so a failure cannot be
  reported; error handlers do not run; the client receives success for work that was rolled back.
- *Failure mode:* the incident below.
- *Use when:* never.

**B. In the service, inside the request** (✅ recommended)

- *Advantages:* failures become responses; the transaction boundary matches the business operation, so
  two writes that must be atomic are visibly in one block (02.8, 02.10); the service is reusable by
  workers with the same semantics (11.1).
- *Disadvantages:* the service must be given a session; the boundary must be chosen deliberately.
- *Use when:* always.

**C. In the handler**

- *Advantages:* explicit at the call site.
- *Disadvantages:* transaction control leaks into the HTTP layer, so a worker calling the same logic
  gets different semantics (07.3).
- *Use when:* trivial single-write endpoints where a service would be ceremony — and accept that it
  will move when the endpoint grows.

### Function, class and parameterised dependencies

| | Function | Class with `__call__` | Parameterised factory |
|---|---|---|---|
| Example | `get_session` | `RequireScope("invoices:write")` | `require_scope("invoices:write")` |
| Configuration | Closure or settings | Constructor arguments | Factory arguments |
| Caching | Per request | Per request, per instance | Per request, per returned function |
| OpenAPI visibility | Parameters appear in the schema | Same | Same |
| Use when | Most things | Reusable policies with state | Reusable policies without state |

Prefer functions. Reach for a class when a dependency has meaningful configuration and is used in many
places — an authorisation policy is the canonical case (08.12).

### What belongs in a dependency

| Belongs | Does not belong |
|---|---|
| Producing a resource (session, client, service) | Business logic |
| Authenticating and resolving identity | Writing to the database |
| Authorisation checks (`dependencies=[...]`) | Anything whose failure needs a domain-specific response body |
| Extracting and validating request context | Slow I/O that could be lazy |

A dependency runs on **every** request to its routes, before the handler. An expensive dependency is an
expensive endpoint, and a dependency that writes is a write you cannot see from the handler.

## Production Scenario

**Ledgerly, Wednesday 15:30.** A customer reports that their integration receives `201 Created` with an
invoice id, and a subsequent `GET` of that id returns `404`. They assume a replication delay (02.10) and
retry after five seconds. Still `404`. The invoice does not exist.

### Symptoms

- Roughly **0.4%** of `POST /v1/invoices` calls return `201` with an id that never becomes readable.
- The `Location` header points at a resource that has never existed.
- `http_requests_total{route="/v1/invoices",status="201"}` and the number of rows in `invoices` diverge
  by exactly that 0.4% over any window.
- **No `5xx` responses.** The API's error rate is flat and correct.
- Application logs contain unhandled-exception tracebacks with **no request context** — no request id,
  no route, no tenant:

```text
ERROR: Exception in ASGI application
Traceback (most recent call last):
  ...
  File "ledgerly/deps.py", line 21, in get_session
    await session.commit()
sqlalchemy.exc.IntegrityError: (psycopg.errors.UniqueViolation)
  duplicate key value violates unique constraint "ix_invoices_tenant_number"
```

- Those tracebacks never produce a Problem Details body (02.9) — the error handlers are not running for
  them.

### Diagnosis

1. **Alert.** None. `201` is a success, and the exception is logged but produces no `5xx`, so neither
   the error-rate alert nor the SLO alert fires. This is 02.10's lesson recurring: *the client is told
   about something that is not durably readable*, but this time the cause is inside FastAPI's
   lifecycle rather than in replication.
2. **Metrics.** The `201`-count versus row-count divergence is the anchor. Two counters that must be
   equal and are not — another instance of the **ratio between two things that should track each
   other** being the only usable signal (02's recap).
3. **Logs.** The traceback names `deps.py`, line 21 — `await session.commit()` *inside the session
   dependency, after the `yield`*. And the absence of request context is itself diagnostic: the
   `RequestContextMiddleware` (15.2) has already completed, because the response has already been sent.
4. **Reproduce deterministically** by forcing a constraint violation:

```python
@pytest.mark.anyio
async def test_constraint_violation_at_commit(client, auth):
    body = {**INVOICE, "number": "INV-2026-0417"}          # duplicate invoice number
    first = await client.post("/v1/invoices", json=body, headers=auth)
    second = await client.post("/v1/invoices", json=body, headers=auth)
    assert second.status_code == 409                        # expected
    # actual: 201, and the row does not exist
```

   The test fails with `assert 201 == 409`. The mechanism is confirmed in one run.

5. **Read the dependency:**

```python
# as it was
async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
    async with async_sessionmaker(request.state.engine)() as session:
        yield session
        await session.commit()        # ⚠️ after the yield → after the response
```

6. **Why 0.4%.** Only requests whose commit *fails* are affected — deferred constraint violations,
   concurrent duplicate invoice numbers (05.3), and serialisation failures under load (05.11). The
   successful 99.6% commit fine, so the pattern looked like an intermittent, unexplained data-loss bug
   rather than a systematic defect.

### Root Cause

The transaction was committed in the dependency's teardown. FastAPI runs code after `yield` **once the
response has been sent to the client**, so:

- the `201` and its `Location` header had already gone;
- the `IntegrityError` could not be converted into a `409` (02.9), because there was no response left
  to write;
- registered exception handlers never ran, because the request had already completed;
- the session's context manager rolled the transaction back, discarding the insert;
- the client kept an invoice id for a row that never existed.

Every part of that is FastAPI behaving as documented. The defect is placing a fallible operation in a
phase reserved for cleanup.

The pattern came from a widely-copied tutorial snippet, and it works perfectly whenever nothing fails —
which is why it survived code review, a full test suite, and eight months of production.

### Fix

*Mitigation (18 minutes):* move the commit into the service's transaction block, as shown in the Code
Example. The dependency retains only rollback-on-error and close:

```diff
  async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
-     async with async_sessionmaker(request.state.engine)() as session:
-         yield session
-         await session.commit()
+     session = async_sessionmaker(request.state.engine, expire_on_commit=False)()
+     try:
+         yield session
+     except Exception:
+         await session.rollback()
+         raise
+     finally:
+         await session.close()
```

Duplicate-number requests immediately began returning `409` with a Problem Details body, and the
`201`/row-count divergence went to zero.

*Permanent fix:*

1. **Transaction ownership documented and enforced**: services open transactions with
   `async with session.begin()`. A CI check greps for `session.commit()` outside `services/`.
2. **The unique constraint mapped to a domain error** so `409` is deliberate rather than a generic
   `500` (02.9, 05.3).
3. **A rule written into the code-review guide**: *nothing after `yield` in a dependency may fail in a
   way the client needs to know about.* Cleanup only.

### Prevention

- **A test asserting a commit failure becomes an error response** — the direct control, and the test
  that reproduces the incident:

```python
# tests/api/test_commit_failures_are_reported.py
@pytest.mark.anyio
async def test_constraint_violation_returns_409_not_201(client, auth, seeded_invoice):
    """A failure at commit MUST reach the client. If the transaction is committed
    in dependency teardown, this test sees 201 and no row (03.5)."""
    duplicate = {**INVOICE, "number": seeded_invoice.number}
    response = await client.post("/v1/invoices", json=duplicate, headers=auth)

    assert response.status_code == 409
    assert response.headers["content-type"].startswith("application/problem+json")
    assert await count_invoices_with_number(seeded_invoice.number) == 1
```

- **An architecture test banning transaction control outside the service layer:**

```python
@pytest.mark.parametrize("path", sorted(pathlib.Path("ledgerly").rglob("*.py")))
def test_commit_only_happens_in_services(path) -> None:
    if "services/" in str(path).replace("\\", "/"):
        return
    source = path.read_text(encoding="utf-8")
    assert ".commit()" not in source, (
        f"{path} commits outside the service layer. In a dependency's teardown this "
        "runs AFTER the response is sent and cannot be reported to the client (03.5)"
    )
```

- **Alert on the created-versus-persisted divergence.** `rate(http_requests_total{status="201",
  route="/v1/invoices"}) - rate(invoices_inserted_total)` sustained above zero. Two counters that must
  agree are a far better detector than either alone — the recurring lesson of module 02.
- **Alert on unhandled ASGI exceptions**, separately from `5xx`. An exception that produces no `5xx` is
  *more* alarming than one that does, because it means the failure was invisible to the client-facing
  error path. Nobody had a monitor for that log pattern.
- **Review rule for `yield` dependencies:** everything after the `yield` must be justifiable as
  "cleanup that cannot fail". Commits, network calls, and event publishing all fail this test.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a dependency's teardown raises? | The response is already sent. It is logged as an unhandled error and the client is never told. |
| ...the handler raises? | The exception propagates into the generator at the `yield`, so `except`/`finally` run — this is how rollback works. |
| ...you commit after `yield`? | A failing commit rolls back silently while the client holds a success. The incident above. |
| ...two dependencies both need a session? | Per-request caching gives them the same one — which is what makes a single transaction possible. |
| ...a dependency is slow? | Every request to those routes pays it, before the handler. Push laziness into the object it returns. |
| ...a test forgets to clear `dependency_overrides`? | The override leaks into every later test in the process (13.6). Clear it in the fixture's teardown. |
| ...a dependency writes to the database? | The write is invisible from the handler and outside the service's transaction. Dependencies produce; services write. |
| ...a `finally` block itself raises? | It masks the original exception. Keep teardown trivial. |

## Common Pitfalls

**Committing after `yield`.** The incident above; it is in a great many tutorials. *Instead:* commit in
the service, inside the request.

**Business logic in dependencies.** Runs on every request, invisible to the handler, and untestable
without HTTP. *Instead:* dependencies produce collaborators; services act.

**Forgetting to roll back on exception.** The connection returns to the pool inside an aborted
transaction, and the next request using it fails with `InFailedSqlTransaction` (06.3). *Instead:*
`except: rollback(); raise`.

**Not clearing `dependency_overrides`.** Cross-test contamination that produces failures in unrelated
tests. *Instead:* clear in a fixture teardown.

**Expensive work in a dependency.** A dependency that fetches configuration on every request makes
every endpoint slower. *Instead:* create it in lifespan (03.1) and inject the ready object.

**`use_cache=False` by habit.** Rebuilds objects unnecessarily, and if one of them is a session you now
have two transactions in one request. *Instead:* leave caching on; disable only with a comment
explaining why.

**Importing collaborators instead of injecting them.** Removes the override seam, so tests must patch
module paths (modern-python 15.5). *Instead:* inject.

## How to Test This

- The commit-failure test above — the one that catches the entire class.
- The architecture test banning `.commit()` outside `services/`.
- A rollback test: force an exception mid-handler, then assert the next request on the same pooled
  connection succeeds (proving the session was rolled back, not just closed).
- A teardown-order test asserting nested `yield` dependencies tear down in reverse creation order.
- An override-leak test: run a test that sets an override, then assert `app.dependency_overrides` is
  empty in a later test.

## Interview Questions

1. *Explain.* When does the code after `yield` in a FastAPI dependency run? — After the response has
   been sent to the client.
2. *Explain.* Why must a transaction not be committed there? — A failure cannot become a response;
   the client keeps a success for work that rolled back.
3. *Debug this.* Clients receive `201` with ids that `404`, there are no `5xx`, and the logs show
   `IntegrityError` tracebacks without request context. — Commit in dependency teardown.
4. *Explain.* What does per-request dependency caching guarantee, and why does it matter for sessions?
   — One instance per request, so every collaborator shares one session and one transaction.
5. *Design.* Where does the transaction boundary belong, and why not in the handler? — In the service,
   so workers and CLIs get identical semantics.
6. *Explain.* How does a `yield` dependency roll back on failure? — The exception is thrown into the
   generator at the `yield`.
7. *Design.* How would you replace a third-party client in tests without patching imports? —
   `dependency_overrides`, cleared in teardown.

## Key Takeaways

- `Depends` resolves before the handler and tears down **after the response is sent**, in reverse
  order.
- **Nothing after `yield` may fail in a way the client needs to know about.** Cleanup only: close,
  release, return to pool.
- Commit inside the service, inside the request. A commit in teardown turns a `409` into a false `201`
  and a silently discarded write.
- Roll back on exception before closing, or the pooled connection carries an aborted transaction into
  the next request.
- Per-request caching means all collaborators share one session — which is what makes a single
  transaction per request possible.
- Dependencies **produce**; services **act**. Business logic in a dependency is invisible from the
  handler and runs on every request.
- An exception that produces **no** `5xx` deserves its own alert. Invisible failures are worse than
  visible ones.
- Inject collaborators so `dependency_overrides` can replace them — and clear the overrides.
