> **Level:** Intermediate

## Concept

### Plain-English Explanation

Uploads and downloads are the endpoints where the body stops being "a JSON object" and becomes *bytes that may not fit* — in memory, in a timeout, in patience. Both directions have the same two enemies. The first is accidental buffering: code that quietly materialises the whole body (a `bytes` parameter, a list of rows, 03.7's body-joining middleware) and turns a 300 MB file into a 300 MB allocation per request. The second is subtler and the heart of this notebook: streaming works by **backpressure**, which means your generator runs at the *client's* network speed — and so does everything the generator is holding.

### Technical Explanation

**Uploads.** A multipart form field declared as `UploadFile` is parsed incrementally into a **`SpooledTemporaryFile`**: bytes stay in memory up to Starlette's 1 MiB spool threshold, then roll to disk. Captured on the pinned stack:

```text
64 KiB upload : {'rolled_to_disk': False, 'backing': 'BytesIO'}
8 MiB upload  : {'rolled_to_disk': True,  'backing': '_TemporaryFileWrapper'}
```

So `UploadFile` is memory-safe by default — until someone calls `await file.read()` with no size guard and re-materialises the whole thing anyway. Its file operations hop through the threadpool (03.6), which is fine for a few awaits and worth knowing before you loop over thousands. ⚠️ Declaring the parameter as `bytes = File(...)` skips the spool entirely: the full body lands in memory, per concurrent request.

For raw (non-multipart) bodies, `request.stream()` yields chunks as the server reads the socket. Chunk sizes are a **transport property, not a contract** — the same 8 MiB body arrived as one chunk under `TestClient` and as 65 chunks (max 128 KiB) under real uvicorn. Code must be correct for any chunking, which also means: enforce size limits *while reading*, incrementally. `Content-Length` is a client claim (absent entirely on chunked uploads), and ⚠️ neither uvicorn nor FastAPI imposes any body-size limit — the caps live at the proxy (01.10) and in a `receive`-wrapping guard (03.7's legitimate buffer-and-replay case, built properly in 16.9).

**Downloads.** `StreamingResponse` iterates your generator and `send`s each chunk (03.7's `http.response.body` messages). The `send` awaits real socket capacity, so once the OS buffers fill, **the producer runs at the consumer's pace**. Captured — an 8 MiB stream to a client throttled at 2 MB/s:

```text
t= 1.54s producer yielding chunk 0
t= 2.12s producer yielding chunk 32       ← 2 MiB/s: the generator is being PACED
t= 3.15s producer yielding chunk 64
t= 4.17s producer yielding chunk 96
t= 5.11s producer done (chunk 127)
```

Note the corollary from the same experiment: a *small* response (512 KiB) showed no pacing at all — it vanished into kernel buffers and the generator finished instantly. Backpressure is invisible below buffer sizes and absolute above them, which is exactly why streaming endpoints pass load tests with small fixtures and fail with real exports.

Two failure edges, both captured. A generator that **raises mid-stream** cannot change the status — the 200 left in the first message (03.8):

```text
HTTP 200, received 196608 bytes
curl: (18) transfer closed with outstanding read data remaining
```

The client got a *valid-looking prefix of a file* on a success status; only the transport-level truncation signal distinguishes it from a complete one. And a client that **disconnects** cancels the response task — cancellation reaches the generator, and a `try/finally` around the loop ran ~0.3 s after the abort in the captured run. Cleanup does happen; the design question is what was *held* until it did.

### Mental Model

> A streamed response is a **loan of whatever the generator holds, at the client's pace**. Memory, a temp file, a pool thread, a database connection — each is on loan until the last byte drains. Decide per resource whether client-paced is affordable; if not, finish the server-paced work first, park the bytes in a spool, and lend only the spool.

## How It Works

The three phases of a streamed download, with the ownership that matters:

```text
phase 1: server-paced      handler runs, generator starts, chunks fill OS buffers
                           (fast; ends when ~MBs of socket buffer are full)
phase 2: client-paced      each `yield` awaits the client draining the socket
                           ⚠️ EVERYTHING the generator holds is held at THIS pace
phase 3: settlement        last chunk drains → normal close
                           │ generator raises → 200 stands, stream truncated (curl 18)
                           │ client vanishes  → cancellation → finally runs (~0.3s)
```

Phase 2 is where designs are honest or not. A generator over an in-memory list is lending memory you already spent — harmless. A generator over a **database cursor is lending a pooled connection** (03.6's budget logic, applied to 05.9's pool): a 4-minute download is a 4-minute connection hold, and the pool arithmetic is `pool_size ÷ concurrent slow downloads`, not requests per second. The exhaustion, when it comes, announces itself with this exact message — provoked deliberately here on a 2-slot pool:

```text
sqlalchemy.exc.TimeoutError:
  QueuePool limit of size 2 overflow 0 reached, connection timed out, timeout 1.00
```

Every *other* endpoint that needs a connection gets that error, while the downloads proceed happily. The resource leak is inside successful requests — which is what makes the incident below slippery.

## Code Example

An upload endpoint that enforces its limit while reading — the guard is incremental, so the answer arrives before the response starts and can still be a clean 413 problem (03.8):

```python
# ledgerly/routers/attachments.py
MAX_ATTACHMENT_BYTES: Final = 25 * 1024 * 1024      # contract, documented in OpenAPI (02.4)

@router.post("/{invoice_id}/attachments", status_code=201, name="attachInvoiceFile")
async def attach_file(
    invoice_id: InvoiceId, tenant: Tenant, file: Annotated[UploadFile, File()],
) -> AttachmentOut:
    # ⚠️ filename and content_type are CLIENT CLAIMS. The name may contain
    # ../, NUL, or 300 unicode tricks; the type may say pdf over an .exe.
    safe_name = sanitize_filename(file.filename)     # allowlist chars, cap length
    size = 0
    async with attachment_store.writer(tenant, invoice_id, safe_name) as out:
        while chunk := await file.read(64 * 1024):
            size += len(chunk)
            if size > MAX_ATTACHMENT_BYTES:
                raise AttachmentTooLarge(              # DomainError → 413 problem (03.8)
                    f"Attachments are limited to {MAX_ATTACHMENT_BYTES} bytes.")
            await out.write(chunk)
    detected = sniff_content_type(await peek_magic_bytes(out))   # 16.3, not the header
    return AttachmentOut(id=out.id, bytes=size, content_type=detected)
```

The loop shape is the point: fixed-size reads, a running total, and failure while the status line is still ours to choose. Storage itself is deliberately behind `attachment_store` — proxying versus presigned object-store uploads, and resumability for the 2 GB case, are module 09's decisions (09.2, 09.3, 09.5), not a router's.

Now the download side — first the shape that causes the incident, byte-for-byte plausible:

```python
# ⚠️ runs fine, wrong under load: the session lives INSIDE the generator,
# so the connection is on loan for the entire client-paced download.
@router.get("/statements/{period}/lines.csv")
async def statement_lines(period: Period, tenant: Tenant, session: Session) -> StreamingResponse:
    async def rows() -> AsyncIterator[bytes]:
        result = await session.stream(lines_query(tenant, period))   # server-side cursor
        async for row in result:
            yield encode_csv_row(row)
    return StreamingResponse(rows(), media_type="text/csv")
```

And the fix — split the phases. Server-paced work completes against a spool; the connection goes back before the first byte is lent out:

```python
@router.get("/statements/{period}/lines.csv")
async def statement_lines(period: Period, tenant: Tenant, session: Session) -> Response:
    spool = SpooledTemporaryFile(max_size=1024 * 1024)        # memory → disk, like uploads
    total = 0
    result = await session.stream(lines_query(tenant, period))
    async for row in result:                                   # server-paced: seconds
        total += spool.write(encode_csv_row(row))
        if total > MAX_EXPORT_BYTES:
            raise ExportTooLarge("Use the async export operation (02.10).")
    spool.seek(0)                                              # session closes with the
    return StreamingResponse(                                  # request scope (03.5) —
        iter_file(spool), media_type="text/csv",               # BEFORE the slow lend-out
        headers={"Content-Length": str(total),                 # truncation now detectable
                 "Content-Disposition": content_disposition("statement.csv")},
    )
```

Two dividends beyond the pool. `Content-Length` is now known, so a truncated download stops being a valid-looking prefix — every competent client can detect the mismatch. And the size guard has a number to check *before* promising success, with the overflow answer already designed: 02.10's operation pattern, rendering to object storage (09.2) by a worker. The spool costs disk and a delay of the first byte by the query duration — the Tradeoffs section prices that.

## Design Patterns / Tradeoffs

### Moving a large body: three shapes

**A. Buffer** (build `bytes`, return `Response`) — *advantages:* simplest; `Content-Length` free; works with any middleware. *Disadvantages:* peak memory = body size × concurrency; time-to-first-byte = total time. *Use when:* bodies are provably small (the PDF invoices of 03.6, single-digit MB, already bounded by the renderer).

**B. Stream end-to-end** (generator over the live source) — *advantages:* O(chunk) memory; first byte immediately; the only option when the source is itself unbounded or real-time (12.4's SSE). *Disadvantages:* everything the generator holds is client-paced (the incident); mid-stream failure truncates a 200; usually no `Content-Length`. *Use when:* the held resources are cheap — a file handle, an object-store read (09.3) — or the stream is genuinely endless.

**C. Spool-then-stream** — *advantages:* expensive resources held server-paced only; length known; failures happen before the status line. *Disadvantages:* disk I/O and space per concurrent export; first byte waits for the full query; needs its own size ceiling. *Use when:* the source holds a pooled or contended resource and the body is bounded — the default for DB-backed exports.

**Recommendation:** A for small-and-bounded, C for database-backed downloads, B only when what you hold is cheap. And a size ceiling on *every* path, because each shape degrades differently past it: A runs out of memory, B runs out of pool, C runs out of disk — pick the failure you can see coming, then route past-ceiling work to 02.10's operation pattern.

### Upload parameter shapes

| | `UploadFile` | `bytes = File(...)` | `request.stream()` |
|---|---|---|---|
| Memory | Spooled: ≤1 MiB then disk | ⚠️ whole body, always | O(chunk), your loop |
| Size enforcement | While reading (`read(n)` loop) | Too late — already in RAM | While reading |
| Multipart fields | Parsed for you | Parsed for you | ⚠️ raw body only |
| Use | Default for form uploads | Never past toy size | Raw PUT bodies, protocol endpoints |

Whatever the shape, the proxy's `client_max_body_size` (01.10) is the outer wall, and the in-app cap (16.9) exists because the proxy's number is coarse and shared. Two limits, both tested.

## Production Scenario

**Ledgerly, Monday 14 September, 14:05.** A large accounting-firm tenant switches its new document-archival tool to "full sync": every statement export for every client, in parallel — through their office egress proxy, which throttles aggregate bandwidth. **~120 concurrent downloads of `/v1/statements/{period}/lines.csv`, each trickling at DSL speed.**

By 14:11, `POST /v1/invoices` — and every other database-touching endpoint, for every tenant — is failing.

### Symptoms

- 500-problem responses across the API; logs show the QueuePool timeout from How It Works — `QueuePool limit of size 15 overflow 5 reached, connection timed out` (`# illustrative - not captured output`; production's pool numbers, same message shape as the captured one).
- The 03.6 dashboards do their job in one glance: event-loop lag near zero, threadpool 4/40 — **both prior incident classes eliminated in seconds.** This is something else holding something else.
- Postgres itself: nearly idle. CPU 6%, no slow queries. But `pg_stat_activity` shows all 80 connections (4 replicas × 20) occupied — state `idle in transaction`, ages **3–9 minutes**, all running the statement-lines cursor, all from one tenant's API key (`# illustrative - not captured output`).
- The downloads themselves: succeeding. Slowly, happily, 200s all the way. **The incident's only errors are on the endpoints *not* involved.**

### Diagnosis

1. **Alert → Metrics.** 500s fleet-wide, DB healthy, loop and threadpool healthy. Pool-wait metrics (06.8) say requests die waiting for connections that never come back.
2. **Who holds them.** `pg_stat_activity` answers precisely: idle-in-transaction connections aged like downloads, tied to the statement export, tied to one tenant. In-flight request telemetry agrees: ~120 active `lines.csv` requests, average age 5 minutes.
3. **Why a download holds a connection for 5 minutes.** The route streams from a server-side cursor: correct against buffering (the 03.7 lesson, applied), but the session lives inside the generator — and the backpressure trace from How It Works says the generator advances at the client's pace. Connection hold time = client download time. The tenant's throttled proxy made that minutes.
4. **The arithmetic that was never written down** (03.6's discipline, unlearned for this resource): `20 connections/replica ÷ 5-minute holds` = 4 concurrent slow downloads per replica saturate it. The tool opened 30 per replica.
5. **Eliminated en route:** a database problem (idle, no locks), a leak (connections return the moment a download completes or is killed), and the export query itself (1.8 s server-paced — the other 298 s are the loan).

### Root Cause

The statement export streamed directly from a pooled database connection, so backpressure converted each connection into a client-paced loan. One tenant's slow, parallel client borrowed the entire fleet's pool for minutes at a time; every other endpoint starved waiting. The successful requests were the outage; the failing ones were bystanders.

### Fix

*Mitigation (14:19):* a per-tenant concurrency cap on export routes at the edge — 4 in flight per tenant (02.12 machinery, new limit). The archival tool's requests queue politely; the pool refills within two minutes; bystander endpoints recover. The tenant is asked to drop to their tool's default concurrency.

*Permanent fix:* the spool-then-stream rewrite from the Code Example — connection hold drops from client-minutes to the 1.8-second query. Exports over the size ceiling move to 02.10's operation pattern rendering into object storage (09.2), which also removes the re-render on the tool's inevitable retry sweeps. `db_connection_hold_seconds` becomes a per-route histogram, because the number that mattered was measurable all along.

### Prevention

- **The incident closes into a named test** — the property, not the bug:

```python
# tests/api/test_exports_do_not_lend_the_pool.py
async def test_connection_returns_before_client_finishes_download(app_client, pool_status):
    """Streaming a statement must hold a DB connection for the QUERY, not the
    DOWNLOAD (03.11). Start a stream, consume one chunk, stall — the pool must
    already be back to baseline while the response is still in flight."""
    async with app_client.stream("GET", "/v1/statements/2026-08/lines.csv") as response:
        await anext(response.aiter_bytes())          # first chunk arrived, stream open
        assert pool_status.checked_out() == 0        # ...and the loan is already repaid
```

- **Alert on `idle in transaction` age** (threshold: 60 s) — the Postgres-side signature of any client-paced hold, whatever causes the next one (05.11 hardens this properly).
- **The capacity arithmetic rule from 03.6, generalised in the runbook:** every streaming route ships with `pool ÷ hold-time` written in the PR, where hold time assumes the *slowest plausible client*, not the test client.
- Per-tenant concurrency caps on all download routes become standing config, not incident response (16.9 revisits as DoS hygiene).

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the client downloads at modem speed? | Backpressure paces your generator to match. Whatever it holds is held for the duration — budget pools accordingly, or spool. |
| ...the client disconnects mid-stream? | The response task is cancelled; `finally` in the generator runs (captured ~0.3 s). Resources not in a `finally` are leaked until GC. |
| ...the generator raises mid-stream? | The 200 already left; the client gets a truncated body and only a transport-level signal (curl 18). Do failable work before the first byte; send `Content-Length` when known. |
| ...an upload has no `Content-Length`? | Chunked encoding — legal and common. Limits must be enforced while reading, never by trusting the header. |
| ...someone declares `bytes = File(...)`? | Whole body in memory per request; 30 concurrent 100 MB uploads is 3 GB. `UploadFile` spools at 1 MiB. |
| ...a `BaseHTTPMiddleware` layer reads the body? | Streaming silently dies (03.7's captured 129-messages-to-2). The pass-through property needs its own test. |
| ...traffic on downloads ×10? | Shape A dies of memory, B of pool, C of disk. You chose which; the ceiling routes overflow to 02.10. |
| ...the uploaded file claims to be a PDF? | A claim. Sniff magic bytes, sanitise the filename, and treat both as attacker input (09.4, 16.3). |

## Common Pitfalls

**Streaming from a pooled connection.** The incident. Correct against buffering, wrong against backpressure. *Instead:* spool-then-stream; lend only cheap resources client-paced.

**`await file.read()` with no bound.** Undoes the spool's protection in one call. *Instead:* fixed-size `read(n)` loop with a running guard.

**Trusting client metadata.** Filename, content type, `Content-Length` — all claims, all attacker-controlled. *Instead:* sanitise, sniff, count.

**Testing streams with small fixtures.** Below buffer sizes backpressure is invisible; the 512 KiB test passes while the 300 MB reality pins resources. *Instead:* test past buffer size, with a stalled consumer (the named test above).

**CPU-heavy work between yields.** Each `await send` parks the coroutine, but the encoding between yields runs on the loop (03.6, 04.7). *Instead:* keep per-chunk work trivial; heavy transformation belongs in the worker that 02.10 hands the job to.

**Ignoring truncation on the client side.** A curl-18 body imported as a complete CSV is silent wrong data. *Instead:* emit `Content-Length` (spool makes it free) and make your own SDKs verify it.

**Building resumable/ranged/2 GB handling here.** The router is the wrong layer to fight physics. *Instead:* module 09 — presigned transfers (09.2/09.3), resumability (09.5).

## How to Test This

- The stalled-consumer pool test above — the connection-loan property, on the assembled app.
- An upload-cap test posting a body 1 byte over the limit as *chunked* encoding, asserting a 413 problem and that the partial spool is gone.
- A truncation test: force the generator to raise after N chunks, assert the client observes a transport error (not a short-but-valid file) and, with the spool path, a `Content-Length` mismatch.
- A disconnect test: cancel mid-download, assert the generator's cleanup ran and pool/temp-file baselines are restored.

## Interview Questions

1. *Explain.* What is backpressure in an ASGI streaming response, and what does it couple? — `send` awaits socket drain; the generator runs at client pace, so every resource it holds is held for the download duration.
2. *Debug this.* All write endpoints return 500s; Postgres is idle but all connections are `idle in transaction` for minutes; downloads are fine. — Streaming exports holding sessions across client-paced transfers; cap concurrency, then spool-then-stream.
3. *Explain.* Why can't an error mid-stream produce a 500? — The status line went with the first message; only truncation remains. Hence: failable work before byte one, and `Content-Length` so truncation is detectable.
4. *Design.* Uploads up to 25 MB from browsers — walk the limits. — Proxy cap (01.10), app-level incremental guard returning 413 problems, `UploadFile` spooling, magic-byte sniffing; beyond that size, presigned upload (09.2).
5. *Explain.* Why did the 512 KiB load test miss what the 300 MB export hit? — Small bodies vanish into kernel buffers; backpressure only manifests past them. Test bigger than the buffers, slower than the fixtures.
6. *Explain.* `UploadFile` vs `bytes` vs `request.stream()` — what does each hold in memory? — Spool-bounded / everything / one chunk; and only the first two parse multipart.
7. *Design.* A tenant's tool opens 120 parallel slow downloads. What protects the fleet? — Per-tenant concurrency caps at the edge (02.12/16.9), spooled exports so the pool isn't lendable, and the operation pattern for bulk sync.

## Key Takeaways

- Streaming's contract is backpressure: the generator — and everything it holds — runs at the client's pace. A streamed response is a client-paced **loan**; decide per resource whether you can afford it.
- Database-backed downloads default to **spool-then-stream**: connection held for the query, spool lent for the transfer, `Content-Length` for free.
- Uploads: `UploadFile` spools at 1 MiB; enforce size *while reading*; filename, type and length are attacker claims.
- Mid-stream failure truncates a 200 — put failable work before the first byte, and make truncation detectable.
- Disconnects cancel the generator and run `finally`; put every held resource behind one.
- Backpressure is invisible under buffer-sized tests — test past the buffers with a stalled consumer.
- Every streaming route ships with its arithmetic: `pool ÷ slowest-client hold time`, written down (03.6's rule, new resource).
