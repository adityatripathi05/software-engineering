## Concept

### Plain-English Explanation

`app = FastAPI()` looks like it starts a web server. It does not. It builds an object — a router, a
middleware stack, a set of exception handlers and an OpenAPI generator — and then does nothing. The
object sits there, inert, until something calls it.

That something is uvicorn (01.1). It imports your module, finds the object, opens a socket, and from
then on calls `await app(scope, receive, send)` once per request. Your application is a *function
uvicorn calls*, not a process that runs.

That distinction has a practical consequence that catches people out constantly: **everything at
module level runs at import time**, before any server exists, before configuration is necessarily
valid, and — critically — potentially *before the process forks into workers*. Code that opens a
database connection at import is not "initialising the app". It is creating a socket that several
processes are about to inherit and use simultaneously.

### Technical Explanation

**What `FastAPI()` builds:**

```text
FastAPI(...)
 ├─ router            APIRoute objects; path → handler, with types for validation and OpenAPI
 ├─ middleware stack  wraps the router; built ONCE, at startup, in reverse registration order (03.7)
 ├─ exception handlers  status/exception-class → response builder (03.8)
 ├─ dependency overrides  the test seam (13.8)
 └─ openapi()         derives the contract from the route table on first call (02.4, 03.13)
```

None of that touches the network. `FastAPI` is an ASGI application: a callable with the signature
`async def __call__(scope, receive, send)`, exactly as in 01.1.

**What uvicorn does with it:**

```text
uvicorn ledgerly.main:app
   1. import ledgerly.main            ← ALL module-level code runs HERE
   2. locate the attribute `app`
   3. (multi-worker) fork N children  ← children INHERIT everything created in step 1
   4. bind and listen on the socket
   5. await app({"type": "lifespan"}, ...)   ← startup hook (03.9)
   6. per connection: parse HTTP → build scope → await app(scope, receive, send)
   7. on shutdown: lifespan shutdown, drain connections (04.9)
```

⚠️ Steps 1 and 3 are the whole of this notebook's danger. Anything created in step 1 exists **once**
and is then **shared by every forked child**. For pure Python objects (a compiled regex, a parsed
config) that is a benefit — copy-on-write memory. For anything holding an operating-system resource —
a socket, a file descriptor, a connection pool — it is a correctness bug, because two processes will
read and write the same file descriptor with no coordination.

**Three kinds of module-level code**, and only one is safe:

| At import time | Safe? | Why |
|---|---|---|
| Constants, enums, compiled regexes, Pydantic model classes | ✅ | Immutable; identical in every child |
| Reading environment variables into a settings object | ✅ | Pure computation, and it fails fast (07.9) |
| Creating routers and registering routes | ✅ | Pure object construction |
| **Opening a database engine, Redis client, HTTP client** | ❌ | Holds sockets; forked children share them |
| **Network calls** (fetching config, warming a cache) | ❌ | Slows import; fails at import; untestable |
| **Mutable module-level state** | ❌ | Per-process, so wrong across replicas (01.6) |

The rule that follows: **resources are created in `lifespan`** (03.9), which runs *after* the fork, once
per worker process.

### Mental Model

> `app` is **an object, not a server**. Importing it must be free of side effects: no sockets, no
> network, no mutable state. Everything that holds an OS resource is created in `lifespan`, which runs
> once per worker, after any fork. If importing your application does something, that something will
> happen at the worst possible time.

## How It Works

**Fork safety**, which is the mechanism behind the incident below:

```text
❌ Engine created at import                     ✅ Engine created in lifespan

  import ledgerly.main                            import ledgerly.main
    └─ engine = create_async_engine(...)            └─ (nothing opened)
         └─ TCP socket fd=7 to PostgreSQL
                                                   fork → child A, child B, child C
  fork → child A (inherits fd=7)                     each runs lifespan:
         child B (inherits fd=7)                       child A: engine → fd=7  (its own)
         child C (inherits fd=7)                       child B: engine → fd=8  (its own)
                                                       child C: engine → fd=9  (its own)
  ⚠️ THREE processes write to ONE socket
     PostgreSQL sees interleaved protocol         ✅ Three independent connections
     bytes from three senders → protocol
     desynchronisation, decryption failures,
     results delivered to the wrong process
```

The failure is *probabilistic* — it needs two workers to use the shared connection at overlapping
moments — which is why it never reproduces locally with one worker and appears as a small percentage
of mysterious errors in production.

**Project layout** that keeps import-time work out and makes the URI space navigable:

```text
ledgerly/
├── main.py                app assembly ONLY: create FastAPI, include routers, add middleware
├── config.py              pydantic-settings; validated at import (pure, and fails fast — 07.9)
├── lifespan.py            engine, Redis, HTTP clients — created and disposed here (03.9)
├── deps.py                shared Depends providers (03.5)
├── ids.py                 typed public identifiers (02.1)
├── routers/               one module per resource; mirrors the URI space (02.1)
│   ├── invoices.py            /v1/invoices
│   ├── invoice_lines.py       /v1/invoices/{invoice_id}/lines
│   ├── customers.py           /v1/customers
│   └── operations.py          /v1/operations                      (02.10)
├── schemas/               request/response models, split by direction (02.4, 03.3)
├── services/              business logic; no FastAPI imports       (07.3)
├── repositories/          data access; no FastAPI imports          (07.4)
├── models/                SQLAlchemy models                        (06.1)
├── middleware/            pure-ASGI middleware                     (01.1, 03.7)
└── errors/                catalogue + handlers                     (02.9, 03.8)
```

The load-bearing rule is the one about `services/` and `repositories/`: **they must not import
FastAPI**. That is what lets a worker (11.1) or a CLI reuse them, and it is what stops HTTP concerns
leaking into business logic (07.3). It is also mechanically checkable, which is why the architecture
test below exists.

## Code Example

`main.py` — assembly only, and importable with no side effects:

```python
# ledgerly/main.py
from fastapi import FastAPI

from ledgerly.config import get_settings
from ledgerly.errors.handlers import register_error_handlers
from ledgerly.lifespan import lifespan
from ledgerly.middleware.cache_policy import CachePolicyMiddleware      # 01.4
from ledgerly.middleware.request_context import RequestContextMiddleware # 15.2
from ledgerly.openapi import use_stable_operation_ids                   # 02.4
from ledgerly.routers import customers, invoice_lines, invoices, operations

settings = get_settings()          # pure: reads env, validates, raises on bad config

app = FastAPI(
    title="Ledgerly Invoicing API",
    version="2.0.0",
    lifespan=lifespan,             # ⚠️ resources are created HERE, not at import (03.9)
    docs_url="/docs" if settings.expose_docs else None,
)

# Registration order matters: the FIRST added is the OUTERMOST (03.7).
app.add_middleware(RequestContextMiddleware)   # outermost: every log line gets a request id
app.add_middleware(CachePolicyMiddleware)      # innermost of the two

register_error_handlers(app)

for router in (invoices.router, invoice_lines.router, customers.router, operations.router):
    app.include_router(router, prefix="/v1")

use_stable_operation_ids(app)      # pure: rewrites operation ids on the route table
```

Nothing in that module opens a socket, makes a request, or mutates shared state. Importing it in a
test is instant and free — which is what makes `TestClient(app)` viable (13.3).

Contrast the two versions of resource creation:

```python
# ❌ ledgerly/db.py — the shape that causes the incident below.
from sqlalchemy.ext.asyncio import create_async_engine

# Runs at IMPORT. Opens sockets before the process forks into workers.
engine = create_async_engine(settings.database_url, pool_size=20)
```

```python
# ✅ ledgerly/lifespan.py — created per worker, after the fork, and disposed cleanly.
from contextlib import asynccontextmanager
from typing import AsyncIterator, TypedDict

import httpx
from fastapi import FastAPI
from redis.asyncio import Redis
from sqlalchemy.ext.asyncio import AsyncEngine, create_async_engine

class State(TypedDict):
    engine: AsyncEngine
    redis: Redis
    tax_client: httpx.AsyncClient

@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[State]:
    settings = get_settings()
    engine = create_async_engine(settings.database_url, pool_size=settings.db_pool_size)
    redis = Redis.from_url(settings.redis_url, decode_responses=False)
    tax_client = build_tax_client()          # one client per process (01.7)

    try:
        yield {"engine": engine, "redis": redis, "tax_client": tax_client}
    finally:
        # Ordered teardown; each must run even if an earlier one fails (04.9).
        await tax_client.aclose()
        await redis.aclose()
        await engine.dispose()
```

Handlers reach those resources through `request.state`, which uvicorn populates from the lifespan
yield — so nothing is a module-level global:

```python
# ledgerly/deps.py
from typing import Annotated, AsyncIterator
from fastapi import Depends, Request
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker

async def get_session(request: Request) -> AsyncIterator[AsyncSession]:
    """The engine comes from lifespan state, so it is this worker's engine.
    Session lifecycle and transaction ownership are 03.5 and 06.3."""
    maker = async_sessionmaker(request.state.engine, expire_on_commit=False)
    async with maker() as session:
        yield session

Session = Annotated[AsyncSession, Depends(get_session)]
```

## Design Patterns / Tradeoffs

### Where resources are created

**A. Module-level globals**

- *Advantages:* trivial to write; importable from anywhere without plumbing.
- *Disadvantages:* runs at import, so it breaks tests, breaks `--preload`, and holds sockets across a
  fork; impossible to have two configurations in one process; cleanup never happens.
- *Failure mode:* shared file descriptors across workers — the incident below.
- *Use when:* never for anything holding an OS resource.

**B. `lifespan` + `request.state`** (✅ recommended)

- *Advantages:* created after fork, once per worker; disposed deterministically; startup failure stops
  the process before it serves traffic; tests construct their own state.
- *Disadvantages:* resources reach handlers through `request`, which feels indirect at first.
- *Use when:* always.

**C. A lazily-initialised singleton (`@lru_cache` on a factory)**

- *Advantages:* no import-time work; created on first use, therefore after fork.
- *Disadvantages:* first request pays the cost; no clean shutdown hook; per-process still, so it hides
  the multi-worker question rather than answering it.
- *Use when:* pure computed values (a parsed rate table); not for sockets.

### Application factory vs module-level `app`

| | Module-level `app` | `def create_app() -> FastAPI` |
|---|---|---|
| uvicorn target | `ledgerly.main:app` | `ledgerly.main:create_app` (with `--factory`) |
| Multiple configurations in one process | ❌ | ✅ (tests, plugins) |
| Import-time work | Whatever is at module level | Deferred to the call |
| Familiarity | The FastAPI default | The Flask convention |

**Recommendation:** module-level `app` with an *empty* module scope. The factory pattern is mostly a
workaround for import-time side effects; if there are none, you do not need it. Adopt a factory when
you genuinely need several differently-configured apps in one process.

### Router organisation

Organise by **resource**, mirroring the URI space (02.1) — `routers/invoices.py` owns `/v1/invoices`.
The alternative, organising by technical layer (`routers/get.py`, `routers/post.py`), makes it
impossible to find the code for a URL and guarantees merge conflicts. Set the version prefix once, at
`include_router`, so a new version is a routing change rather than an edit to every route (02.3).

## Production Scenario

**Ledgerly, Monday 10:20.** Roughly 2% of requests fail with database errors. The errors are varied
and strange, and they started when the team moved from one uvicorn process per container to four
gunicorn workers per container as part of a cost-reduction exercise.

### Symptoms

- ~2% of requests return `500`. The underlying exceptions vary:

```text
psycopg.OperationalError: consuming input failed: SSL error: decryption failed or bad record mac
psycopg.OperationalError: server closed the connection unexpectedly
psycopg.ProgrammingError: the last operation didn't produce a result
sqlalchemy.exc.InterfaceError: connection already closed
```

- The errors are **not** correlated with load, endpoint, tenant or query. They appear on trivial reads
  and on complex writes alike.
- PostgreSQL logs show `incomplete startup packet` and occasional
  `invalid message format` from the API's connection pool.
- **Zero occurrences in local development or in CI**, both of which run a single process.
- Staging, which runs two workers, shows the same errors at roughly 1%.

### Diagnosis

1. **Alert.** The `5xx` SLO alert. First hypothesis — a database problem — is eliminated quickly:
   PostgreSQL's own metrics are healthy, other services connecting to the same instance are fine, and
   `pg_stat_database` shows no unusual load.
2. **Metrics.** The error rate scales with **worker count**, not with request rate. One worker: zero.
   Two workers: ~1%. Four workers: ~2%. That relationship is the entire diagnosis in one graph, and it
   points at something being shared between processes.
3. **Logs.** The variety of exceptions is itself the clue. A genuine database fault produces a
   consistent error; *protocol desynchronisation* produces whatever garbage happens to be read next —
   decryption failures, malformed messages, results arriving for a query the process never sent.
4. **The decisive check** — count backends per connection from PostgreSQL's side:

```sql
SELECT client_addr, client_port, count(*) AS backends
FROM pg_stat_activity WHERE datname = 'ledgerly'
GROUP BY 1, 2 HAVING count(*) > 1;

 client_addr | client_port | backends
-------------+-------------+----------
 10.0.2.31   |       54118 |        4      ← four backends on ONE client port
```

   Four processes are using a single TCP connection. That is impossible unless they inherited it.

5. **Read the startup path.** `ledgerly/db.py` creates the engine at module scope, and the gunicorn
   command uses `--preload`:

```bash
gunicorn ledgerly.main:app -k uvicorn.workers.UvicornWorker --workers 4 --preload
```

   `--preload` imports the application **once in the parent**, then forks. Every child inherits the
   engine object, its pool, and the open sockets inside it.

### Root Cause

The SQLAlchemy engine was created at import time. With `--preload`, the import happens in the parent
process, so the connection pool's TCP sockets are created before `fork()`. Each child inherits the
same file descriptors.

PostgreSQL's wire protocol is a stateful, ordered byte stream. When two processes write queries onto
the same socket, their messages interleave; when they read, each may consume bytes belonging to the
other. Under TLS it manifests as decryption failures, because the cipher state advances per message
and each process has its own copy of a state that is being mutated by another.

The rate scales with the probability that two workers use the same pooled connection at overlapping
moments — hence 1% at two workers and 2% at four, and zero in any single-process environment.

The same defect existed before the gunicorn change; it was simply unreachable with one process. **The
migration did not introduce the bug; it made an existing one observable.**

### Fix

*Mitigation (4 minutes):* drop `--preload`. Each worker then imports the application independently and
creates its own engine, so no descriptor is shared. Errors go to zero immediately.

*Permanent fix — move resource creation into `lifespan`*, as shown earlier, so the code is correct
regardless of preloading:

```diff
- # ledgerly/db.py
- engine = create_async_engine(settings.database_url, pool_size=20)
+ # ledgerly/lifespan.py — created per worker, AFTER any fork, disposed on shutdown.
+ engine = create_async_engine(settings.database_url, pool_size=settings.db_pool_size)
```

⚠️ Removing `--preload` costs memory (each worker imports separately, losing copy-on-write sharing).
Ledgerly kept it off deliberately: the memory saving is small for a Python API, and preloading is a
standing invitation for exactly this class of bug. If you do want it, add a `post_fork` hook that
disposes and recreates every pool in the child — but the lifespan approach makes the hook unnecessary.

*Related fix found in the same review:* the Redis client and the `httpx.AsyncClient` were also
module-level. Neither had caused visible errors yet — Redis tolerates interleaving better and the
HTTP client's pool happened not to be exercised concurrently — but both were latent instances of the
identical defect. All three moved to `lifespan` together.

### Prevention

- **An architecture test forbidding I/O at import time**, which is the control that generalises:

```python
# tests/architecture/test_no_io_at_import.py
"""Importing the application must open no sockets. This catches engines, Redis
clients, HTTP clients and config fetches created at module scope — all of which
are inherited across a fork and shared between workers (03.1)."""
import socket, importlib, pytest

@pytest.fixture
def forbid_sockets(monkeypatch):
    def _blocked(*args, **kwargs):
        raise AssertionError(
            "socket created during import — move it into lifespan (03.1)"
        )
    monkeypatch.setattr(socket.socket, "connect", _blocked)
    monkeypatch.setattr(socket.socket, "connect_ex", _blocked)

def test_importing_the_app_opens_no_connections(forbid_sockets) -> None:
    for module in ("ledgerly.main", "ledgerly.deps", "ledgerly.config"):
        importlib.reload(importlib.import_module(module))
```

- **A layering test** asserting that `services/` and `repositories/` never import `fastapi`, so the
  business logic stays reusable by workers and the CLI (07.1):

```python
@pytest.mark.parametrize("path", sorted(pathlib.Path("ledgerly/services").rglob("*.py")))
def test_services_do_not_import_fastapi(path) -> None:
    source = path.read_text(encoding="utf-8")
    assert "import fastapi" not in source and "from fastapi" not in source, (
        f"{path} imports FastAPI: business logic must be callable from workers too (07.3)"
    )
```

- **Run CI with more than one worker.** For the second time in this curriculum (01.6 was the first), a
  whole class of defect was invisible under a single process. One integration job with
  `--workers 2` would have caught this before the migration.
- **Alert on error-rate correlation with worker count** — or more practically, treat *"errors that
  vary in kind and do not correlate with load or endpoint"* as a signature of shared-state corruption
  rather than of a failing dependency.
- **A deployment rule:** `--preload` is disallowed unless a `post_fork` hook explicitly reinitialises
  every pooled resource, and that hook is tested.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a resource is created at import? | It is shared across forked workers. Sockets desynchronise; pools double-count. |
| ...you run one worker in dev and four in production? | An entire class of bug exists only in production. Run multi-worker in CI. |
| ...configuration is invalid? | Settings validation at import fails the process immediately — the one import-time side effect you *want* (07.9). |
| ...lifespan startup raises? | uvicorn aborts; the process never serves traffic. Correct: better to fail to start than to serve without a database (03.9). |
| ...a test imports the app? | With a clean module scope this is instant and offline. With import-time I/O, tests need a live database. |
| ...you need two app configurations in one process? | Use a factory. With module-level state you cannot. |
| ...a worker is killed and replaced? | Its own lifespan runs; nothing is inherited. That is the property you are protecting. |
| ...you add a second replica? | Per-process resources multiply — pool size × workers × replicas (05.9, 03.14). |

## Common Pitfalls

**Creating engines, clients or pools at module scope.** The incident above. *Instead:* `lifespan`,
asserted by an import-time I/O test.

**`--preload` with inherited resources.** Turns a latent defect into a live one. *Instead:* avoid it,
or reinitialise pools in `post_fork`.

**Business logic importing FastAPI.** Ties services to HTTP so workers and CLIs cannot reuse them, and
encourages raising `HTTPException` deep in the domain (02.9, 07.3). *Instead:* domain errors, mapped
at the router.

**Module-level mutable state.** Per-process, therefore wrong across replicas — 01.6's incident.
*Instead:* Redis or the database.

**Routers organised by HTTP method or layer.** You cannot find the code for a URL. *Instead:* one
module per resource, mirroring the URI space.

**Network calls at import to fetch configuration.** Import becomes slow and can fail; tests need a
network. *Instead:* environment variables validated at import; remote configuration fetched in
lifespan with a local fallback.

**Putting the version prefix on every route decorator.** A new version becomes an edit to every file.
*Instead:* set it once at `include_router` (02.3).

## How to Test This

- The import-time socket test above — it generalises to every resource type.
- The layering test asserting `services/` and `repositories/` are FastAPI-free.
- A multi-worker integration job in CI (`--workers 2`), which is the only way this class of bug is
  visible at all.
- A lifespan test asserting that `engine.dispose()` and `redis.aclose()` are called on shutdown
  (13.9), so a leak is caught before it reaches a rolling deploy.

2. *Explain.* Why must a connection pool not be created at import time? — Forked workers inherit the

   per worker, with deterministic teardown.
6. *Explain.* Why should `services/` not import FastAPI? — So workers, CLIs and tests can reuse the
   logic without an HTTP context.
7. *Design.* How would you prove your application performs no I/O at import? — Patch `socket.connect`

## Key Takeaways

- `app` is an **object, not a server**. uvicorn imports it and calls it; nothing runs until it does.
- **Import time is the wrong time for everything except pure computation.** Constants, models, routers
  and validated settings — nothing else.
- Anything holding an OS resource belongs in `lifespan`, which runs **once per worker, after any
  fork**. Inherited sockets corrupt stateful protocols in ways that look like random database faults.
- Errors that vary in kind and do not correlate with load or endpoint are a signature of **shared
  state**, not of a failing dependency.
- Run multi-worker in CI. Single-process test environments hide an entire class of defect — this is
  the second time in this curriculum, after 01.6.
- Mirror the URI space in the file tree, and keep `services/` and `repositories/` free of FastAPI so
  the logic is reusable by workers and testable without HTTP.
