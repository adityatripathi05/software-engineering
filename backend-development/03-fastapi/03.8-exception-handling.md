## Concept

### Plain-English Explanation

02.9 designed what an error response looks like; this notebook is about how an exception becomes one. Somewhere between `raise InvoiceAlreadyPaid()` deep in a service and the `409` with a problem body on the wire, something has to catch the exception, decide what it means in HTTP terms, and build the response. That something is an **exception handler**, and the interesting engineering is not writing one — it is deciding *where the meaning lives*.

An error response is an assertion to the client: "this happened, and here is what to do about it." The mapping layer is where those assertions are made. Map too coarsely and your API starts asserting things that are not true — which, as the incident below shows, is worse than failing, because clients *act* on assertions.

### Technical Explanation

**Dispatch.** Handlers are registered per exception class via `@app.exception_handler(SomeError)` (or the `exception_handlers=` constructor argument — assembly, like 03.7's middleware list). When an exception escapes a route handler or a dependency, `ExceptionMiddleware` — innermost in the stack (03.7) — walks the exception's **MRO**, `type(exc).__mro__`, and calls the first registered handler it finds. Two consequences, both verified on the pinned stack:

- A handler registered for a **base class catches every subclass** — one handler for a `DomainError` root covers the whole hierarchy.
- An **exact registration wins over a base** registration, because the exact class appears earlier in the MRO. Specialise only where the response genuinely differs.

**The two `HTTPException`s.** ⚠️ `fastapi.HTTPException` *subclasses* `starlette.exceptions.HTTPException` — and the framework's own errors (the 404 for an unmatched path, the 405 for a wrong method) raise the **Starlette** parent. MRO walks upward, never down: a handler registered on the FastAPI subclass misses the router's own errors. Captured:

```text
handler registered on fastapi.HTTPException:
  handler-raised 404 -> application/problem+json: {"shape":"problem+json","status":404}
  router's own   404 -> application/json: {"detail":"Not Found"}          ⚠️ default shape
handler registered on starlette HTTPException (the base):
  handler-raised 404 -> application/problem+json
  router's own   404 -> application/problem+json                          ✅ one shape
```

Register on the Starlette class, or your API speaks two error dialects — exactly the inconsistency 02.9 exists to prevent, and it appears only on the assembled app's unrouted paths, where partial-app tests never look (03.2).

**What the handler receives and returns.** `(request, exc) → Response`. Handlers may be sync or async, and they run inside the request — after `yield`-dependency cleanup has *not* yet happened (the session dependency's rollback in 03.5 runs as the exception propagates through it, before the handler builds the response). A handler that itself raises has nowhere to go but `ServerErrorMiddleware`: handlers must be boring, allocation-only code.

**The validation pair.** `RequestValidationError` (client sent a bad request → 422, override per 02.9) has a server-side sibling: **`ResponseValidationError`**, raised when a handler returns something its `response_model` cannot validate. That one is *your* bug, and FastAPI correctly turns it into a 500 rather than shipping a malformed body — the contract is protected in both directions (03.3).

### Mental Model

> Dispatch is `isinstance` in disguise: the first registered class on the exception's MRO wins. Design for it — one exception **hierarchy** owned by the domain, one **handler** owned by the HTTP layer, and a mapping between them that only asserts what it can prove.

## How It Works

Where an exception is raised decides who can catch it. The full geography, with 03.7's rows included for contrast:

| Raised in... | Caught by... | Client sees |
|---|---|---|
| Route handler or service below it | `ExceptionMiddleware` → your handler | Mapped problem response |
| A dependency (03.5) | Same — dependencies run inside routing | Mapped problem response |
| A `yield` dependency's cleanup | Nothing before it — response already sent (03.5) | The original (successful) response |
| Middleware (03.7) | `ServerErrorMiddleware` only | Bare 500 unless the `Exception` backstop is registered |
| An exception handler itself | `ServerErrorMiddleware` | Bare 500 |
| Mid-stream, after `http.response.start` | Nobody can change the status | A truncated body on a 200 (03.11) |
| A background task (03.10) | Runs after the response | Their 2xx already arrived; logs are the only witness |

The first two rows are the happy path this notebook builds. Every other row is a way for an error to *escape the mapping* — and each has its own notebook because each needs its own defence.

One escape route is new in the era of structured concurrency, and it lives inside the happy path. `asyncio.TaskGroup` (modern-python 12.5) wraps failures in an `ExceptionGroup` — whose MRO contains *neither* your domain classes nor `HTTPException`:

```python
@app.get("/quote")
async def quote() -> QuoteOut:
    async with asyncio.TaskGroup() as tg:       # tax rate + FX rate, concurrently
        tax = tg.create_task(tax_client.rate_for(address))
        fx = tg.create_task(fx_client.rate_for(currency))
    ...
```

```text
GET /quote -> 500 'Internal Server Error'      ⚠️ TaxProviderUnavailable handler never ran
```

The `TaxProviderUnavailable` raised inside the group came out as `ExceptionGroup[TaxProviderUnavailable]`, matched no handler, and became a 500 — the client lost the `502`, the `retryable` flag, and the `Retry-After` it would have acted on. The fix belongs at the concurrency boundary, not in the handler table: unwrap deliberately (`except* TaxProviderUnavailable` and re-raise the leaf, 04.8), because a handler registered for `ExceptionGroup` cannot know which member matters.

## Code Example

The architecture in three files. Domain exceptions first — importable by services and workers, so no FastAPI anywhere near them (03.1's layering rule):

```python
# ledgerly/errors/domain.py
from typing import ClassVar

from ledgerly.errors.catalogue import (          # 02.9 — the published vocabulary
    EXTERNAL_REF_CONFLICT, IDEMPOTENCY_KEY_REUSED, INVOICE_ALREADY_PAID,
    INVOICE_NOT_FOUND, ProblemType,
)

class DomainError(Exception):
    """Root of every business error. Carries its own problem identity, so the
    HTTP layer never guesses: the raiser decides the meaning, once."""
    problem: ClassVar[ProblemType]

    def __init__(self, detail: str, **extensions: object) -> None:
        super().__init__(detail)
        self.detail = detail
        self.extensions = extensions             # e.g. conflicting_ref="INV-0042"

class InvoiceNotFound(DomainError):     problem = INVOICE_NOT_FOUND
class InvoiceAlreadyPaid(DomainError):  problem = INVOICE_ALREADY_PAID
class IdempotencyKeyReused(DomainError): problem = IDEMPOTENCY_KEY_REUSED
class ExternalRefConflict(DomainError): problem = EXTERNAL_REF_CONFLICT
```

One handler for the whole hierarchy — MRO dispatch does the routing, the exception carries the payload:

```python
# ledgerly/errors/handlers.py (excerpt; problem_response and the validation
# and Exception handlers are 02.9's — register() wires all of them in main.py)
@app.exception_handler(DomainError)
async def _domain(request: Request, exc: DomainError) -> JSONResponse:
    return problem_response(exc.problem, exc.detail, request, **exc.extensions)

@app.exception_handler(StarletteHTTPException)   # ⚠️ the Starlette base — see Concept
async def _http(request: Request, exc: StarletteHTTPException) -> JSONResponse:
    problem = catalogue.for_status(exc.status_code)      # 404 → not-found, 405 → ...
    return problem_response(problem, str(exc.detail), request,
                            headers=exc.headers)          # keeps WWW-Authenticate (01.3)
```

And the part that decides what an `IntegrityError` *means* — in the repository, where the schema knowledge lives. 03.5 promised that a duplicate insert "is mapped by the error handlers and the client receives 409 instead of a false 201"; here is the mapping, done at the right granularity:

```python
# ledgerly/repositories/invoices.py (excerpt)
# The meaning of an IntegrityError lives in WHICH constraint fired, not in the
# exception type. Every unique constraint gets an explicit decision here; the
# CI test in 03.8's Prevention fails any migration that adds one without.
CONSTRAINT_TO_ERROR: Final[dict[str, type[DomainError]]] = {
    "uq_idempotency_key_per_tenant": IdempotencyKeyReused,
    "uq_invoices_tenant_external_ref": ExternalRefConflict,
}

async def insert(self, invoice: Invoice, *, idempotency_key: str) -> None:
    try:
        self._session.add(invoice)
        await self._session.flush()
    except IntegrityError as exc:
        name = constraint_name(exc)     # driver-specific extraction — 06.7
        if error_cls := CONSTRAINT_TO_ERROR.get(name):
            raise error_cls(f"Conflict on {invoice.external_ref!r}.",
                            conflicting_ref=invoice.external_ref) from exc
        raise   # ⚠️ unknown constraint → 500 ON PURPOSE. A wrong 4xx is an
                # instruction clients will follow; a 500 is a page we will fix.
```

The `from exc` matters: the original `IntegrityError` — constraint name, SQL — stays chained for the server-side log keyed by `request_id`, while the client sees only the catalogue entry (02.9's leak rule). And the bare `raise` on the last line is the load-bearing decision of the whole listing: the absence of a mapping is information, and the honest translation of "I don't know what this means" is a 500, never a guess.

Verified end to end — the base handler catching a subclass, and the exact registration winning where one exists:

```text
subclass, base registered  -> {'handler': 'DomainError(base)', 'slug': 'invoice-already-paid'}
subclass, exact registered -> {'handler': 'InvoiceNotFound(exact)', 'slug': 'invoice-not-found'}
```

## Design Patterns / Tradeoffs

### Where the exception-to-HTTP mapping lives

**A. `raise HTTPException(...)` everywhere, including services**

- *How it works:* any layer that detects a problem raises the HTTP answer directly.
- *Advantages:* zero machinery; the status is visible at the raise site.
- *Disadvantages:* services now import FastAPI, so the worker (11.1) and CLI reusing them either crash on an HTTP concept or grow `except HTTPException` translation shims; the same business condition gets different statuses at different raise sites; nothing links errors to the catalogue.
- *Failure mode:* grep for `HTTPException(409` returns eleven files and three different `detail` strings for one condition.
- *Use when:* never below the router layer. At the router itself, for purely-HTTP conditions (a malformed header a dependency rejects — 03.5's `get_tenant` 401), it is the right tool.

**B. Domain exceptions + one registration per concrete type**

- *Advantages:* explicit; each mapping visible in one decorator.
- *Disadvantages:* every new error class needs a handler nobody forgets; twenty near-identical functions; the mapping knowledge scatters.
- *Failure mode:* the forgotten registration — the new exception falls through to the 500 backstop and ships as `internal-error` until someone notices.
- *Use when:* a handful of error types, or responses that genuinely differ structurally.

**C. One hierarchy, one handler, identity on the exception** (✅ the Code Example)

- *Advantages:* adding an error class is one declaration; MRO dispatch guarantees coverage — a `DomainError` subclass *cannot* miss the handler; the catalogue link is enforced by the `problem` attribute; services stay HTTP-free.
- *Disadvantages:* the exception classes carry presentation-adjacent data (`detail`, extensions), a coupling you must police — the `problem` attribute is the only HTTP-flavoured thing allowed on them.
- *Failure mode:* someone puts response-building logic on the exception; the hierarchy becomes a shadow HTTP layer.
- *Use when:* the default. This is 07.3's service-layer contract seen from the FastAPI side.

**Recommendation:** C, with A retained strictly at the router/dependency layer for transport-level rejections. Revisit toward B only for the rare error whose response shape differs from the standard problem body.

### Mapping database errors: type-level vs constraint-level

Type-level (`IntegrityError → 409`) is one line and correct exactly as long as the write path contains one unique constraint — it is asserting "the only thing that can conflict is X". Constraint-level costs a dict and a helper, and stays correct as the schema grows, because each constraint gets a deliberate decision — including the decision *not to map* (internal invariants like an outbox uniqueness should surface as 500s, not client errors). The incident below is the type-level assertion expiring. Choose constraint-level the moment a second unique constraint enters any mapped path — and pin the completeness in CI, because "the moment" arrives in a migration nobody connects to error handling.

## Production Scenario

**Ledgerly, Tuesday 1 September, 08:40.** Support escalates three enterprise tickets with the same shape: "your API rejects invoice creation with `idempotency-key-reused`, but the key is freshly generated — and our integration is now marking those invoices as already-synced." One customer attaches their reconciliation report: 312 September invoices their ERP believes exist in Ledgerly do not.

The previous Thursday's release included a long-requested migration: `uq_invoices_tenant_external_ref`, a unique constraint on the customer-supplied ERP reference, per tenant.

### Symptoms

- 5xx rate: flat. Latency: flat. No alert fired at any point — every response the API sent was well-formed, fast, and wrong.
- `http_requests_total{route="/v1/invoices",status="422"}` stepped up **40×** at 00:07 on 1 September — the moment several customers' ERPs, whose reference sequences reset monthly, began reusing August's `external_ref` values.
- The 422 bodies are valid problems from the catalogue (02.9): `type: .../idempotency-key-reused`, whose documented client action is *"the create already succeeded — fetch the existing resource and continue."* The SDKs did exactly that.
- Server logs for those request ids, `ERROR` level, contain the truth the client never saw: `IntegrityError … duplicate key value violates unique constraint "uq_invoices_tenant_external_ref"`.

### Diagnosis

1. **Alert → Metrics.** Nothing server-side fired; the signal is customers reporting **wrong data**, days of it. The 422 step-change at 00:07 on the 1st, confined to tenants with monthly reference sequences, dates the trigger precisely — but a 4xx step is what a misbehaving client also looks like, which is why nobody paged on it.
2. **Logs, joined on `request_id`** (the bridge 02.9 built): the customer quotes `req_01J9…`; the server log for that request shows the `IntegrityError` naming `uq_invoices_tenant_external_ref`. The response claimed an idempotency conflict; the database says external-ref conflict. **The error response asserted a state the database disproves** — for these keys, `idempotency_keys` has no prior row at all.
3. **Read the mapping.** `except IntegrityError: raise IdempotencyKeyReused(...)` in the repository — written when the idempotency index was the *only* unique constraint the insert could hit, and correct for two years.
4. **Why the blast radius is data, not errors.** The mapped type's documented client action is "treat as already-done" (02.9's `retryable`/action discipline working *against* us — the better your error contract, the more faithfully clients obey a wrong error). Integrations skipped 1,940 creations across 7 tenants believing them duplicates.

### Root Cause

The repository mapped the exception *type* `IntegrityError` to the business meaning "idempotency key reused". That equivalence was a property of the schema, not of the exception — true only while exactly one unique constraint existed on the path. Thursday's migration added a second; every violation of it was then reported as, and acted on as, a different error that had not occurred. Nothing about the mapping changed; the schema did — 03.6's incident theme ("nothing about the endpoint changed; the traffic did"), one layer down.

### Fix

*Mitigation (09:35):* hotfix the mapping to translate **only** the idempotency constraint and re-raise everything else. Real collisions now surface as `500 internal-error` — marked `retryable: true` in the catalogue, so obedient SDKs queue and retry instead of skipping. Uglier, honest, recoverable.

*Data repair — the expensive part:* the 1,940 wrongly-skipped creations are extracted from logs by request id, per tenant, and each affected customer gets the list plus replay guidance. As in 01.4, the remediation is only *possible* because every error response carried `request_id`.

*Permanent fix:* the constraint-keyed `CONSTRAINT_TO_ERROR` map from the Code Example; a new catalogue entry `external-ref-conflict` (409, not retryable, extension `conflicting_ref`) published with docs and typed SDK exceptions per 02.9's machinery; the September collisions now return an error that names the actual conflict and the actual ref.

### Prevention

- **The map is complete by construction.** The incident closes into a named CI test — a migration adding a unique constraint now fails until someone makes a mapping decision:

```python
# tests/contract/test_integrity_error_mapping_is_exhaustive.py
def test_every_unique_constraint_has_a_mapping_decision() -> None:
    unique = {c.name for t in Base.metadata.tables.values()
              for c in [*t.constraints, *t.indexes]
              if getattr(c, "unique", False) or isinstance(c, UniqueConstraint)}
    decided = CONSTRAINT_TO_ERROR.keys() | INTERNAL_ONLY_CONSTRAINTS   # explicit 500 list
    assert unique <= decided, (
        f"unique constraints with no error-mapping decision: {unique - decided}. "
        "Map each to a DomainError, or add to INTERNAL_ONLY_CONSTRAINTS (03.8)."
    )
```

- **A nightly invariant check on the error traffic itself:** every `idempotency-key-reused` response emitted yesterday must join to a row in `idempotency_keys`. An API that asserts state can be audited against that state — and for wrong-*data* failures like this one, where every dashboard stays green, a business-invariant check is the **only** detector class that fires. It would have caught this at 06:00 on day one instead of day five.
- **Step-change alerting on 4xx by problem `type`** (not just rate): a 40× shift in the mix is a signal even when the total stays modest. Route it to the API owners, not the pager.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...no handler matches the exception? | It falls to `ServerErrorMiddleware`: the `Exception` backstop (02.9) returns a problem-shaped 500; without one, a bare `text/plain` 500. |
| ...the exception handler itself raises? | Only `ServerErrorMiddleware` is left. Handlers must be allocation-only code — no I/O, no lookups that can fail. |
| ...a domain error is raised inside `TaskGroup`? | It surfaces as `ExceptionGroup` and misses your handler → 500. Unwrap with `except*` at the concurrency boundary (04.8). |
| ...an exception escapes after streaming starts? | The status line is already sent; the client gets a truncated 200. Validate before the first byte (03.11). |
| ...a new unique constraint is added? | Without a mapping decision it must fail CI (the exhaustiveness test) — otherwise the blanket map lies. |
| ...the handler returns a wrong status for the type? | Clients branch on `(type, status)` (02.9); the pair is pinned by the catalogue-stability test. |
| ...an `HTTPException` is raised in a service? | It works, and couples the service to HTTP — the worker running the same code now emits transport errors (07.3). Raise domain errors below the router. |
| ...the framework 404s an unmatched path? | It raises the *Starlette* `HTTPException`. If your handler is registered on FastAPI's subclass, that 404 ships in the default shape. |

## Common Pitfalls

**Registering on `fastapi.HTTPException`.** Router-raised 404/405s keep the default `{"detail": ...}` shape; your API has two dialects, visible only on the assembled app. *Instead:* register on the Starlette base.

**Type-level `IntegrityError` mapping.** An assertion about the schema that expires with the next migration — the incident above. *Instead:* constraint-keyed mapping with a CI exhaustiveness test.

**Guessing on unknown errors.** Mapping the unmapped to a plausible 4xx tells clients to act on fiction. *Instead:* re-raise; a 500 pages you, a wrong 409 silently corrupts the integration.

**Handlers that do work.** A handler that queries the DB or calls a service can raise, and its failures have no net below but the bare 500. *Instead:* everything the response needs travels on the exception.

**Catching `Exception` in the route to "map errors locally".** It swallows `HTTPException` from dependencies and hides real bugs behind one status (guide §8: catching Exception and continuing). *Instead:* let exceptions propagate to the registered handlers; that is what they are for.

**Wrapping without `from`.** Re-raising a translated error without `from exc` severs the chain; the log for the 500 no longer contains the constraint name or SQL that explains it. *Instead:* always chain; the server log gets everything, the client gets the catalogue entry (02.9, 16.2).

**Forgetting the response side.** `ResponseValidationError` 500s in production are your serialisation bugs reaching customers as outages. *Instead:* the contract tests of 03.3, and treat any occurrence as a defect, never as noise.

## How to Test This

- The two contract tests from Prevention: constraint-mapping exhaustiveness, and the nightly invariant reconciling `idempotency-key-reused` responses against `idempotency_keys` rows.
- A parametrised assembled-app test provoking each `DomainError` subclass through a real route and asserting `(type, status)` matches the catalogue — plus one unrouted-path request asserting the 404 is problem-shaped (the Starlette-registration trap).
- A test that raises `RuntimeError` inside a repository double and asserts the response is the problem-shaped 500 with **no fragment** of the exception message in the body (02.9's leak test, wired to this module's handlers).
- A test that a `TaskGroup`-wrapped domain error still maps correctly — pinning the `except*` unwrapping at the concurrency boundary.

2. *Explain.* Why register the HTTP-exception handler on Starlette's class rather than FastAPI's? — The router's own 404/405 raise the Starlette parent; MRO walks upward only, so the subclass registration misses them.
3. *Debug this.* Customers receive `idempotency-key-reused` for keys they never used, starting the day after a migration. — A type-level `IntegrityError` mapping asserting the wrong constraint; join client `request_id` to server logs, read the constraint name, map per constraint.
4. *Design.* Error architecture for an API whose services are shared with queue workers. — Domain exception hierarchy carrying catalogue identity, one handler at the HTTP edge, workers translate the same hierarchy to retry/DLQ decisions; `HTTPException` only at the router.
5. *Explain.* Why must an unmapped `IntegrityError` become a 500 rather than a 409? — A 4xx is an instruction clients follow; asserting a meaning you cannot prove converts a server bug into silent client-side data corruption.
6. *Debug this.* A route using `TaskGroup` returns 500 while the handler for the raised domain error demonstrably works elsewhere. — `ExceptionGroup` wrapping; the group's MRO matches no handler; unwrap with `except*` and re-raise the leaf.
7. *Explain.* An exception is raised after a streaming response has started — what can a handler do? — Nothing: the status line is gone; the client sees a truncated 200. Prevention moves validation before the first byte.

## Key Takeaways

- Dispatch is an MRO walk in innermost `ExceptionMiddleware`: base-class handlers cover hierarchies, exact registrations win, and anything unmatched falls to the 500 backstop.
- One domain hierarchy, one handler, identity carried on the exception — services never import FastAPI, and `HTTPException` lives only at the router/dependency layer.
- Register the HTTP handler on **Starlette's** `HTTPException`, or unrouted 404s speak the default dialect.
- Map `IntegrityError` by **constraint name**, keep the map exhaustive in CI, and let unknown constraints be 500s: a wrong 4xx is worse than a failure, because clients obey it.
- The better your error contract, the more damage a wrong error does — audit the assertions your errors make with invariant checks, because wrong-data failures fire no other alarm.
- Know the escape routes: middleware (03.7), `ExceptionGroup`, mid-stream (03.11), background tasks (03.10), handler-raised — each bypasses the mapping and each has a defence.
- Always chain (`raise X from exc`): the client gets the catalogue entry, the log keyed by `request_id` gets the truth.
