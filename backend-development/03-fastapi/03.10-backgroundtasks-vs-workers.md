# 03.10 BackgroundTasks vs Real Workers

> **Prerequisites:** 03.9 (the process lifecycle and what SIGKILL skips) · 03.8 (failures after the response) · 03.6 (the shared threadpool) · 02.8 (idempotency keys) · 02.10 (the operation pattern)
> **What you'll learn:**
> - State the actual contract of `BackgroundTasks`: in-process, after the response, no record, no retry
> - Classify a side effect by the guarantees it needs — and pick BackgroundTasks, the outbox, or a queue worker accordingly
> - Spot the two silent failure modes: exceptions after the 2xx is gone, and work deleted by deploys and kills
> - Recognise revenue- and data-bearing work hiding inside "fire and forget"
> **Level:** Intermediate

---

> ⚡ **Thursday 3 September, 10:30** — the August close finds invoices the metering service never saw, and nothing ever errored. The cause: revenue events riding an at-most-once, in-process mechanism.

## Concept

### Plain-English Explanation

"Do it in the background" means two profoundly different things, and FastAPI's `BackgroundTasks` is only the small one. It moves work until *after the response is sent* — the client stops waiting, which is genuinely valuable — but the work still runs **in the same process**, with no queue in front of it and no record behind it. A **real worker** is the big meaning: a separate process consuming a persistent queue, with retries, failure visibility, and a life independent of the web process's deploys and restarts.

The choice between them is not about size or speed. It is about a single question: **if this work silently never happens, is that acceptable?** If yes, `BackgroundTasks` is a fine latency optimisation. If no, the work needs to be *recorded* somewhere durable before you promise the client anything — and 03.5's service has been quietly demonstrating that answer all module, writing `invoice.created` to an outbox inside the same transaction as the invoice itself.

### Technical Explanation

**Mechanics.** A handler declares `background_tasks: BackgroundTasks` and calls `add_task(fn, *args)`. Starlette attaches the tasks to the response; after `http.response.body` is sent, they run in order, inside the same ASGI call. Verified on the pinned stack:

- The response leaves first; the client's 200 is on the wire before the first task line executes.
- A **sync** task function is dispatched to the AnyIO threadpool — one of 03.6's forty shared threads, invisible to any audit that only reads route decorators.
- An exception in a task cannot touch the response — the client keeps the 2xx, and the traceback lands in the server log as an ASGI-application error. There is no retry, no counter unless you add one, and no record that the work was ever intended.

> **Version note** — the ordering of background tasks versus `yield`-dependency teardown has changed across FastAPI releases (0.106 notably moved teardown to run "after the response is sent" and its docs warned that tasks could no longer use request resources). On the pinned FastAPI 0.136, the captured order is task **first**, teardown second — the request's session is still open inside the task. Treat this ordering as unspecified: code that borrows request-scoped resources in a task is correct or broken depending on a framework minor. Pass IDs; acquire resources inside the task.

**The failure domain is unchanged.** `BackgroundTasks` runs after the response but *inside* the worker process, so everything from 03.9 applies: a deploy's SIGTERM drains in-flight calls only within the stop-grace window, a SIGKILL deletes whatever was running, and none of it leaves evidence. Contrast the guarantees:

```text
                     BackgroundTasks      outbox + relay (11.15)    queue worker (11.x)
survives crash/kill  ❌ lost, no trace    ✅ row is committed        ✅ message is persisted
retries              ❌ none              ✅ relay retries           ✅ policy + backoff + DLQ
atomic with DB write ❌ can diverge       ✅ same transaction        ❌ needs outbox anyway
observability        ❌ logs, if you log  ✅ unrelayed rows count    ✅ queue depth, job status
latency cost         none                 one INSERT                 one enqueue
```

**Delivery guarantee vocabulary** (proper treatment in 11.9): `BackgroundTasks` is **at-most-once** — zero or one execution, silently. The outbox and queues give **at-least-once** — one or more — which is why every consumer of them must be idempotent (02.8's `idempotency_key` discipline is not optional there).

### Mental Model

> `BackgroundTasks` moves work **later**, not **out**. The process remains the failure domain, and the work has the durability of a local variable: any deploy, kill, or unhandled exception deletes it, and the deletion looks exactly like success. Use it only where you could also, in principle, have done nothing.

## How It Works

The life of one request with a background task, and everywhere the task can silently die:

```text
t=0     handler runs          (session open, transaction commits inside — 03.5)
t=40ms  http.response.start / body ──▶ client has its 201        ← promise made
t=41ms  background tasks run, in order, same process
        ├─ raises?            traceback in server log; client keeps the 201   ⚠️
        ├─ sync function?     occupies 1 of the 40 shared threads (03.6)      ⚠️
        ├─ SIGTERM now?       runs only if it finishes inside stop-grace      ⚠️
        └─ SIGKILL / OOM now? gone. no log, no counter, no row                ⚠️
t=?     yield-dependency teardown, ASGI call completes
```

The captured mechanics, in order — the promise-then-work inversion first:

```text
1. ordering
      handler returns
      background task runs
   client got 200 {'ok': True}
2. failing task — what does the client see?
   client got 200 {'ok': True}          ← ConnectionError happened; nobody was told
```

Then the version-sensitive teardown order (see the Version note — do not build on this):

```text
3. task using the request's yield-dependency session
      background task: insert ok        ← session still open on FastAPI 0.136...
      teardown: session closed          ← ...but this pair has swapped before
4. sync vs async task placement
      sync task thread: AnyIO worker thread     ← 03.6's shared pool
      async task thread: (the event loop)
```

Line 2 is the entire risk model in one transcript. The client's 200 said "done"; the metering call failed a millisecond later; the system's total memory of that divergence is one log line — and in the incident below, not even that.

## Code Example

A legitimate `BackgroundTasks` use — loss-tolerant by construction, IDs not resources, failure counted:

```python
# ledgerly/routers/invoices.py (excerpt)
@router.post("/{invoice_id}/mark-viewed", status_code=204, name="markInvoiceViewed")
async def mark_viewed(
    invoice_id: InvoiceId, tenant: Tenant, background_tasks: BackgroundTasks,
) -> None:
    """Recipient-opened tracking. Losing one event skews an analytics counter
    by one — acceptable on every deploy, which is the admission test (03.10)."""
    background_tasks.add_task(record_view, tenant_id=tenant, invoice_id=invoice_id)

async def record_view(*, tenant_id: TenantId, invoice_id: InvoiceId) -> None:
    try:
        async with analytics_client() as client:      # own resources, own timeout (04.3)
            await client.emit("invoice.viewed", tenant=tenant_id, invoice=invoice_id)
    except Exception:
        logger.warning("view_event_dropped", extra={"invoice": invoice_id})
        DROPPED_SIDE_EFFECTS.labels(kind="invoice.viewed").inc()   # loss is MEASURED
```

The counter is the discipline: even permitted losses are counted, so "loss-tolerant" remains a number someone can check rather than an assumption nobody revisits. Note also what the task takes — two IDs — and what it builds for itself: its client, its timeout. Nothing borrowed from the request.

For work that must happen, the pattern is already in the codebase. 03.5's service commits the fact and the obligation together:

```python
# ledgerly/services/invoices.py (excerpt — unchanged since 03.5)
async with self._session.begin():
    invoice = self._build(tenant, body)
    await self._repo.insert(invoice, idempotency_key=idempotency_key)
    await self._outbox.enqueue(self._session, "invoice.created", invoice.id)
    # ⚠️ same transaction: either the invoice AND the obligation to announce it
    # exist, or neither does. There is no third state to lose.
```

The relay that turns outbox rows into webhook deliveries and queue jobs is 11.15's subject; the consumer-side idempotency it forces is 02.8's. What matters here is the shape: **durability first, execution second** — the exact inverse of `add_task`, which executes without ever recording. And for work that is merely *long* rather than obligatory — the 900-period export from 03.6 — neither of these applies: that is 02.10's operation pattern, a resource the client polls, processed by a real worker (11.16).

## Design Patterns / Tradeoffs

### Choosing the mechanism, by required guarantee

| Side effect needs... | Mechanism | Why |
|---|---|---|
| Nothing — losing it is fine, always | `BackgroundTasks` + drop counter | Zero infrastructure; latency shaved; loss measured |
| To happen iff a DB write happened | Outbox row in the same transaction (03.5, 11.15) | Atomicity is only available inside the transaction |
| To happen, retrying through failures | Queue worker with idempotent jobs (11.1, 02.8) | Retries need persistence and a consumer that survives deploys |
| Minutes of compute, progress, a result | Operation pattern (02.10) + worker (11.16) | The request must end; the work must not |
| To run per process, forever | Supervised lifespan task (03.9) | It is observation, not work — samplers, not jobs |

**A. `BackgroundTasks`** — *advantages:* nothing to deploy; task shares the code and config of the app; perfect for shaving 50–200 ms of non-essential I/O off a response. *Disadvantages:* at-most-once with silent loss; sync tasks spend the shared threadpool; the after-response context is a versioning minefield for borrowed resources. *Failure mode:* revenue-bearing work drifts in because "it's just one call" — the incident. *Do NOT use when:* anyone would ever reconcile, audit, or miss the result.

**B. "Just add retries inside the background task."** The tempting middle that solves nothing: retrying in-process extends the task's lifetime, which *increases* its exposure to the deploy window while it keeps occupying the loop or a pool thread — and the terminal failure is exactly as silent as before. Retry policy belongs where the attempt is recorded (worker, relay), not where it is hoped.

**C. Outbox + relay** — *advantages:* the only mechanism that ties the side effect atomically to the state change; backlog is a queryable table (`SELECT count(*) WHERE relayed_at IS NULL` is a dashboard for free). *Disadvantages:* delivery latency is relay-poll latency; the relay is one more moving part (11.15 builds it properly). *Use when:* the side effect announces or depends on a committed write — webhooks, metering, projections.

**D. Queue worker** — *advantages:* full retry/DLQ/visibility machinery; horizontal scaling decoupled from web capacity. *Disadvantages:* enqueue-then-commit and commit-then-enqueue are both wrong in different ways (the dual-write problem — which is why C feeds D in 11.15, rather than competing with it). *Use when:* the work itself is substantial, regardless of how it is triggered.

**Recommendation:** default side effects into the outbox when they relate to a write, and a queue when they are standalone jobs; admit something into `BackgroundTasks` only by passing the test in the Mental Model — *could we have done nothing?* — and instrument the loss anyway. ARQ vs Celery and the queue-technology decisions are deliberately deferred (11.4, 11.10).

## Production Scenario

**Ledgerly, Thursday 3 September, 10:30.** Finance runs the August close. Ledgerly bills tenants monthly on invoice volume, and the billing input comes from the metering service, which aggregates `usage` events emitted by the API. The close includes a reconciliation step — count invoices created in August in the primary database, compare with metering's total.

It fails. The database says **311,209**. Metering says **309,067**. The gap — 2,142 invoices, 0.69% — is real money about to be *under*-billed, across dozens of tenants.

### Symptoms

- Every August dashboard was green. API error rate, latency, database health: nothing to see. The gap produced **zero operational signal for 33 days**; the reconciliation check is the first and only detector.
- Grepping August's logs for `metering_emit_failed` (a WARN — never alerted) returns **1,894** lines. Two clusters: ~1,655 during a 40-minute metering-service degradation on 12 August, and a daily dribble of timeouts.
- 1,894 accounted losses against a 2,142 gap leaves **248 events with no trace at all** — no log line, nothing. Their timestamps cannot even be plotted, because they do not have timestamps.

### Diagnosis

1. **Alert.** None — by construction. The failing writes were fire-and-forget; a wrong-*data* outcome with healthy servers is precisely the class only a business-invariant check can catch, and this one caught it at its monthly cadence: a 33-day detection window.
2. **Logs → code.** The WARN lines lead to the emission site: `background_tasks.add_task(emit_usage, ...)` after invoice creation, with a try/except that logs and moves on. At-most-once, acknowledged nowhere.
3. **Accounting for the unaccounted.** The 248 traceless losses correlate with nothing observable — which is itself the finding. Cross-referencing deploy timestamps shows August had 41 rollouts; tasks in flight when a worker was killed past its stop-grace died between the 2xx and the emit, before the except clause existed. The number 248 is only known because the *database* can be counted. **The mechanism cannot account for its own losses; only an external source of truth can.**
4. **Eliminated:** metering-service data loss (its ingest log matches what it was sent), double-counting in the DB (idempotency keys, 02.8), and August's code changes (the emission site is fourteen months old — it predates the metering service being load-bearing for billing; the *contract* changed around an unchanged line, 03.6's recurring theme).

### Root Cause

Revenue-bearing events were emitted through a mechanism whose contract is at-most-once, in-process, and unrecorded. Every metering blip and every hard kill during 41 deploys deleted billable events, and each deletion was indistinguishable from success — the strongest signal it left was a WARN nobody paged on, and 248 of the losses left nothing at all.

### Fix

*Mitigation — recover August:* the source of truth contains the answer. Usage *is* invoice creation, so August's true usage is recomputed per tenant from the invoices table and imported into metering as a correction batch before the 5 September billing run. Billing goes out correct and two days late. The retro is blunt about the luck involved: **this was recoverable only because the lost events were derivable from owned data.** Had the events carried anything not persisted elsewhere, the money would simply be gone.

*Permanent fix:* metering stops being a separate emission. The `invoice.created` outbox event — written in the same transaction since 03.5 — gains metering as a second consumer via the relay (11.15), delivered at-least-once with the invoice id as the idempotency key; metering dedupes on it (02.8). The `add_task` emission site is deleted. Nothing new is written on the hot path; the obligation was already durable, and the emission had simply never been moved onto it.

### Prevention

- **The reconciliation check goes from monthly to daily**, and becomes an alert rather than a close-time step. The check itself was already the only working detector — the fix is its *frequency*: a 33-day detection window becomes one day, and a future gap is a page with yesterday's deploys still in scroll-back.
- **The incident closes into a named CI test** — `BackgroundTasks` call sites become an allowlisted, reviewed set:

```python
# tests/architecture/test_backgroundtasks_is_loss_tolerant_only.py
LOSS_TOLERANT_SITES: Final = {           # reviewed: losing these is acceptable + counted
    "ledgerly/routers/invoices.py::mark_viewed",
}

def test_no_unreviewed_backgroundtasks_sites() -> None:
    """add_task is at-most-once with silent loss (03.10). Every use is a claim
    that the work may silently never happen — make the claim in review."""
    found = {f"{path}::{fn}" for path, fn in scan_add_task_call_sites("ledgerly/")}
    assert found <= LOSS_TOLERANT_SITES, (
        f"unreviewed BackgroundTasks sites: {found - LOSS_TOLERANT_SITES}. "
        "If losing this work is unacceptable, use the outbox (03.5, 11.15) or a worker."
    )
```

- **`DROPPED_SIDE_EFFECTS` is emitted at every allowlisted site** and dashboarded — permitted loss stays a measured number, not a belief. Seven of the metrics that lied in August were green; the one that would not have lied did not exist.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the background task raises? | Client keeps its 2xx; the traceback is a server-log entry; nothing retries. Count drops or lose silently. |
| ...the process is killed mid-task? | The work vanishes without a log line. Only an external source of truth can even establish the count. |
| ...a deploy rolls during heavy traffic? | Tasks in flight past stop-grace die. 41 deploys/month × in-flight windows = the incident's 248. |
| ...the task is a sync function? | It occupies one of the 40 shared threads (03.6) for its duration — capacity spent after responses, invisible to route audits. |
| ...the task borrows the request's session? | Works or breaks depending on FastAPI minor (see Version note). Pass IDs; open resources inside the task. |
| ...the dependency the task calls has a 40-minute outage? | At-most-once turns the outage into permanent loss for every event in it. At-least-once turns it into backlog. |
| ...the same outbox event is delivered twice? | By design (at-least-once). The consumer dedupes on the idempotency key (02.8) — that is the price of durability. |
| ...tasks are added but the response fails to send? | Starlette runs tasks only after a successful response start; a pre-response failure means no task — one more reason not to hide obligations here. |

## Common Pitfalls

**Must-happen work in `add_task`.** Webhooks, emails, metering, projections — anything someone reconciles later. The incident. *Instead:* outbox when tied to a write; queue when standalone.

**Judging the mechanism by the demo.** In a tutorial, `BackgroundTasks` and a worker look identical — the difference is invisible until a deploy or a blip, which demos don't have. *Instead:* choose by guarantee, not by appearance.

**Borrowing request-scoped resources in tasks.** Correctness by framework minor. *Instead:* IDs in, own session/client inside the task.

**In-task retry loops.** They lengthen exposure to the kill window, hold the loop or a pool thread, and fail exactly as silently at the end. *Instead:* retries live where attempts are recorded.

**Uncounted "acceptable" loss.** Loss-tolerance decided once, in someone's head, in 2024. *Instead:* a drop counter per site and a dashboard — keep the claim checkable.

**Heavy CPU in a task.** After-response or not, it is the same process: a sync render blocks a pool thread, an async-wrapped one blocks the loop (03.6, 04.7). *Instead:* real workers for real work.

**Announcing before committing.** `add_task(notify)` placed before the transaction closes can announce a write that rolls back — the 03.5 false-201 bug wearing a new hat. *Instead:* the outbox makes the ordering impossible to get wrong.

## How to Test This

- The allowlist architecture test above — every `add_task` site is a reviewed loss-tolerance claim.
- A test per allowlisted site asserting the drop counter increments when the downstream call fails (inject a failing client; the response must still be 2xx).
- An outbox test: force a rollback after `enqueue` and assert no event row survives; commit and assert exactly one (atomicity in both directions).
- The reconciliation query itself runs in CI against a seeded database — the invariant check is code, with a test proving it detects a planted gap.

## Interview Questions

1. *Explain.* What exactly does FastAPI's `BackgroundTasks` guarantee? — Execution after the response, in-process, in order; at-most-once; failures land in logs after the client has its 2xx.
2. *Debug this.* Monthly reconciliation shows 0.7% of usage events missing; API dashboards were green all month. — Fire-and-forget emission: dependency blips and deploy kills deleted events silently; move emission onto the transactional outbox and dedupe downstream.
3. *Design.* Invoice creation must trigger a customer webhook. Walk the mechanism choice. — Must-happen and tied to a write → outbox row in the invoice's transaction, relay delivers at-least-once with signatures and retries (02.11), consumer idempotent on event id.
4. *Explain.* Why is "add retries to the background task" not a fix? — Longer in-process lifetime, more kill-window exposure, same silent terminal failure; retries need a recorded attempt to be meaningful.
5. *Explain.* Why must a task not use the request's database session? — Teardown ordering relative to tasks is version-dependent; on some releases the session is closed. Pass IDs, acquire inside.
6. *Debug this.* After adding several sync background tasks, unrelated `def` endpoints slow down. — The tasks spend the shared AnyIO threadpool after each response (03.6); convert to async tasks or move to workers.
7. *Design.* When is `BackgroundTasks` the right answer? — Loss-tolerant, small, non-obligatory side effects where the alternative is doing nothing; with the loss counted.

## Key Takeaways

- `BackgroundTasks` = later, not elsewhere: same process, same failure domain, at-most-once, no record. Its admission test is *"could we acceptably have done nothing?"*
- The client's 2xx is a promise made **before** the task runs; every task failure is a broken promise only the logs know about — and kill-time failures not even the logs.
- Sync tasks spend 03.6's shared threadpool; task/teardown ordering is version-dependent — pass IDs, own your resources.
- Must-happen side effects tied to writes go through the **outbox in the same transaction** (already canon since 03.5); standalone jobs go to workers; long work is 02.10's operation pattern.
- At-least-once is the durable world's price: consumers dedupe on idempotency keys (02.8), always.
- Wrong-data loss with green dashboards is detected by business-invariant reconciliation or not at all — and the detection window equals the check's cadence.
- Even permitted loss gets a counter. Loss-tolerance is a measurement, not a memory.
