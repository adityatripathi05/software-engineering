# 03.3 Request and Response Models

> **Prerequisites:** 03.2 (parameters), 02.4 (`response_model` as a security boundary), 02.7 (update semantics) · modern-python 18.4 (pydantic)
> **What you'll learn:**
> - Separate the three models every mutable resource needs — create, update, output — and why one model cannot serve all three
> - Identify **server-controlled fields** and keep them out of every input model
> - Use `extra="forbid"` so a client typo is an error rather than a silent no-op
> - Recognise mass assignment: the vulnerability that looks exactly like ordinary schema reuse
> **Level:** Beginner

---

## Concept

### Plain-English Explanation

A Pydantic model at an API boundary is not a description of your data. It is a **statement of what a
client is allowed to say**, and separately, of what a client is allowed to see.

Those two lists are different, and neither matches your database table. A client may set an invoice's
amount but not its id. It may read the invoice's status but never set it — status is a consequence of
payments, not an input. Your table has both columns; a single model that mirrors the table gets both
directions wrong at once.

The temptation to reuse one model is strong, because at the moment you write it the lists happen to
coincide. They diverge the first time you add a computed field, a server-assigned timestamp, or a
state machine — and when an input model quietly accepts a field it should not, a client can set state
it was never supposed to control. That is **mass assignment**, and it is number three on the OWASP API
Security Top 10 for good reason: it does not look like a vulnerability, it looks like tidy code.

### Technical Explanation

**Three models per mutable resource:**

| Model | Direction | Contains | Excludes |
|---|---|---|---|
| `InvoiceCreate` | in | Everything a client may supply at creation | id, status, timestamps, computed totals, tenant |
| `InvoiceUpdate` | in | Fields a client may change afterwards, all optional | Everything in the create-only set, plus create-only fields |
| `InvoiceOut` | out | Everything a client may see | Internal columns, other tenants' data, secrets (02.4) |

They are not the same set with different optionality. `currency` may be settable at creation and
immutable afterwards, so it is in `Create` and not in `Update`. `status` is in neither input model but
is in `Out`. `amount_paid_cents` is derived, so it appears only in `Out`.

**Server-controlled fields** — the category that matters:

```text
A field is server-controlled if its value is a CONSEQUENCE, not a CHOICE.

  id              assigned by us (02.1)
  tenant_id       derived from the credential, never from the body   ← critical
  status          a consequence of payments and actions
  paid_at         a consequence of a payment
  amount_paid     a sum of payment rows
  created_at      a fact about time
  version         a concurrency token (01.4, 05.13)

  Rule: if a client could set it to a value that contradicts reality,
  it must not be in an input model.
```

`tenant_id` is the sharpest case. It must come from the authenticated principal (08.14). A `tenant_id`
field in a request model is a cross-tenant write primitive, and it is one line of "convenience" away
from existing in most codebases.

**`extra` behaviour** decides what happens to fields you did not declare:

| `extra` | Unknown field in the body | When |
|---|---|---|
| `"ignore"` (Pydantic default) | Silently dropped | ⚠️ Never for input models — a typo becomes a silent no-op |
| `"forbid"` | `422` naming the field | ✅ Input models |
| `"allow"` | Kept as an attribute | Only for pass-through payloads you deliberately do not model |

The default is the dangerous one. A client sending `{"amount_cent": 4990}` — one character wrong —
gets `201 Created` with an invoice for zero, and nothing anywhere says why.

⚠️ **`extra="forbid"` does not save you from mass assignment.** It rejects *undeclared* fields. Mass
assignment is a *declared* field that should not have been there. The two controls are complementary
and neither substitutes for the other.

### Mental Model

> An input model is **the client's vocabulary** — the exact set of things it is permitted to assert. An
> output model is **the client's view**. Neither is your table. Every field in an input model is a
> permission you are granting; ask of each one, *"what happens if a client sets this to the worst
> possible value?"*

## How It Works

The three-model pattern, and where the values that are *not* in the input model come from:

```text
  POST /v1/invoices
  {"customer_id": "cus_8f21", "currency": "EUR", "lines": [...]}
          │
          ▼
  InvoiceCreate  (extra="forbid")           ← the ONLY things the client may say
          │
          ├── tenant_id      ← from the credential (08.14), never the body
          ├── id             ← generated (02.1)
          ├── status         ← "draft", a domain rule, not an input
          ├── amount_cents   ← computed from lines
          ├── created_at     ← now()
          └── version        ← 1
          │
          ▼
  Invoice (domain object) ──▶ persisted ──▶ InvoiceOut  ← the client's view
                                              excludes internal_risk_score,
                                              crm_notes, stripe_customer_id (02.4)
```

**The same resource, three vocabularies:**

```text
                       Create   Update   Out
  id                     ✗        ✗       ✓      assigned by us
  tenant_id              ✗        ✗       ✗      never leaves, never enters
  customer_id            ✓        ✗       ✓      set once; changing it is a different operation
  currency               ✓        ✗       ✓      immutable after creation
  due_date               ✓        ✓       ✓      client-controlled throughout
  notes                  ✓        ✓       ✓
  status                 ✗        ✗       ✓      ⚠️ a consequence — the incident below
  amount_cents           ✗        ✗       ✓      computed from lines
  amount_paid_cents      ✗        ✗       ✓      computed from payments
  version                ✗        ✗       ✓      concurrency token (01.4)
  created_at             ✗        ✗       ✓
```

Reading that table row by row is the design exercise. Every `✓` in an input column is a permission,
and the ones that should be `✗` are almost always there because a model was reused.

## Code Example

Input models — narrow, explicit, and closed:

```python
# ledgerly/schemas/invoice.py
from datetime import date, datetime
from decimal import Decimal
from typing import Annotated, Literal

from pydantic import BaseModel, ConfigDict, Field, model_validator

from ledgerly.ids import CustomerId, InvoiceId

Currency = Literal["EUR", "GBP", "USD"]

class InvoiceLineIn(BaseModel):
    model_config = ConfigDict(extra="forbid")

    description: Annotated[str, Field(min_length=1, max_length=500)]
    quantity: Annotated[int, Field(gt=0, le=10_000)]
    unit_price_cents: Annotated[int, Field(ge=0)]     # integer minor units, never float (03.4)
    tax_code: Literal["standard", "reduced", "zero", "exempt"]


class InvoiceCreate(BaseModel):
    """What a client may say when creating an invoice.

    Deliberately absent: id, tenant_id, status, amount_cents, version,
    created_at — all consequences rather than choices. A client that could set
    `status` could create an invoice that is already paid (see below)."""
    model_config = ConfigDict(extra="forbid")

    customer_id: CustomerId
    currency: Currency
    due_date: date
    lines: Annotated[list[InvoiceLineIn], Field(min_length=1, max_length=500)]
    notes: Annotated[str | None, Field(default=None, max_length=2000)]
    po_number: Annotated[str | None, Field(default=None, max_length=64)]

    @model_validator(mode="after")
    def due_date_must_be_future(self) -> "InvoiceCreate":
        if self.due_date < date.today():
            raise ValueError("due_date must not be in the past")
        return self


class InvoiceUpdate(BaseModel):
    """What a client may change afterwards. Note `customer_id` and `currency`
    are absent: they are settable at creation and immutable after it. Merge-patch
    semantics — absent means unchanged (02.7)."""
    model_config = ConfigDict(extra="forbid")

    due_date: date | None = None
    notes: Annotated[str | None, Field(default=None, max_length=2000)]
    po_number: Annotated[str | None, Field(default=None, max_length=64)]

    def changes(self) -> dict[str, object]:
        return self.model_dump(exclude_unset=True)        # 02.7
```

The output model — a separate class, not a superset:

```python
# ledgerly/schemas/invoice.py (continued)
class InvoiceOut(BaseModel):
    """What a client may see. Built from the domain object explicitly, so adding
    a database column can never widen the API (02.4)."""
    model_config = ConfigDict(from_attributes=True, extra="forbid")

    id: InvoiceId
    number: str
    customer_id: CustomerId
    status: str = Field(description="Extensible; treat unknown values as 'open'.")   # 02.3
    currency: Currency
    amount_cents: int
    amount_paid_cents: int
    due_date: date
    notes: str | None
    po_number: str | None
    version: int = Field(description="Use as the If-Match value on updates.")        # 01.4
    created_at: datetime
```

The router, where the input model's narrowness becomes concrete — the tenant comes from the
credential and never from the body:

```python
# ledgerly/routers/invoices.py (excerpt)
@router.post("", status_code=201, response_model=InvoiceOut, name="createInvoice")
async def create_invoice(
    body: InvoiceCreate,
    response: Response,
    svc: Service,
    tenant: Tenant,          # ← from the credential (08.14). NOT a field on InvoiceCreate.
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key")],
) -> InvoiceOut:
    invoice = await svc.create_invoice(tenant, body, idempotency_key=idempotency_key)
    response.headers["Location"] = f"/v1/invoices/{invoice.id}"
    response.headers["ETag"] = f'"{invoice.version}"'
    return InvoiceOut.model_validate(invoice)
```

And the service, which sets every server-controlled field itself:

```python
# ledgerly/services/invoices.py (excerpt)
async def create_invoice(self, tenant: TenantId, body: InvoiceCreate, *,
                         idempotency_key: str) -> Invoice:
    # Every field here is OURS. None of them could be influenced by the request
    # body, because none of them exists on InvoiceCreate.
    invoice = Invoice(
        id=new_invoice_id(),
        tenant_id=tenant,
        number=await self._numbering.next_for(tenant),
        status=InvoiceStatus.DRAFT,                       # always draft; never from input
        amount_cents=sum(l.quantity * l.unit_price_cents for l in body.lines),
        amount_paid_cents=0,
        version=1,
        created_at=datetime.now(UTC),
        customer_id=body.customer_id,
        currency=body.currency,
        due_date=body.due_date,
        notes=body.notes,
        po_number=body.po_number,
    )
    return await self._repo.insert(tenant, invoice, idempotency_key=idempotency_key)
```

## Design Patterns / Tradeoffs

### Model organisation

**A. Three separate classes** (✅ recommended)

- *Advantages:* each direction states exactly what it permits; adding a field is a deliberate decision
  per direction; the OpenAPI document shows three accurate schemas (02.4); impossible to leak or accept
  by accident.
- *Disadvantages:* apparent duplication; three places to touch when a genuinely client-controlled field
  is added.
- *Use when:* always for resources with any server-controlled state.

**B. One base plus inheritance** (`InvoiceBase` → `Create`, `Update`, `Out`)

- *Advantages:* shared fields declared once; less repetition.
- *Disadvantages:* **inheritance widens by default** — a field added to the base appears in all three,
  including inputs. That is precisely the failure mode you are trying to prevent, arriving through a
  refactor nobody reviews as an API change.
- *Use when:* the shared set is stable and small, and you have the CI check below.
- *Do NOT use when:* the resource has server-controlled state that could accidentally be inherited into
  an input model.

**C. One model with `response_model_exclude` / `exclude` sets**

- *Advantages:* one class; exclusions declared at the route.
- *Disadvantages:* the exclusion lives at the call site rather than in the type, so a new route forgets
  it; the OpenAPI schema and the actual response can disagree; input direction is unprotected.
- *Use when:* never as the primary mechanism.

**Recommendation:** A, with the duplication accepted deliberately. The "duplication" is not
duplication — the three lists are genuinely different, and forcing them to look the same is what
creates the vulnerability.

### `extra` policy per direction

| | Input models | Output models |
|---|---|---|
| Setting | `extra="forbid"` | `extra="forbid"` |
| Effect | A typo or an injected field is a `422` naming it | An unexpected attribute raises server-side rather than serialising |
| Cost | Clients must be exact; adding a field is a client-visible change (02.3) | None in practice |

Both directions closed. On input it prevents silent no-ops; on output it turns "somebody returned the
wrong object" into a `500` your error handler logs (03.8), rather than a leak nobody notices for seven
months (02.4).

### Where validation belongs

| Rule | Where | Why |
|---|---|---|
| `quantity > 0`, `max_length`, format | Pydantic field constraint | Cheap, early, self-documenting in OpenAPI |
| "due date after issue date" | `model_validator(mode="after")` | Needs several fields, no I/O |
| "customer belongs to this tenant" | Service layer | Needs data |
| "invoice may be voided in this state" | Service layer / domain | Needs current state (07.3) |

The dividing line is **I/O**. If the rule can be checked from the payload alone, it belongs in the
model, where it produces a precise `422` before any handler code runs.

## Production Scenario

**Ledgerly, Thursday, month-end close.** The finance team reports a reconciliation failure: 1,847
invoices across 23 tenants are marked `paid` in Ledgerly with **no corresponding payment records**.
Total face value: €2.1 M. Revenue reporting for the quarter is wrong, and nobody knows in which
direction.

### Symptoms

- 1,847 invoices with `status = 'paid'` and `amount_paid_cents = 0`, and no rows in the `payments`
  table referencing them.
- The affected invoices were **created** in that state — their audit trail shows a single
  `invoice.created` event and no `invoice.paid` transition.
- **Every request that created them returned `201 Created`.** No errors, no anomalies, normal latency.
- All 1,847 came through the API, from 23 different tenants, over roughly five weeks.
- The payment webhook handler, the payment service and the state machine are all functioning correctly
  and have full test coverage.

### Diagnosis

1. **Alert.** None. Creating an invoice is the most ordinary thing this API does. The discrepancy was
   found by the finance team's month-end reconciliation, five weeks after it started.
2. **Metrics.** Nothing anomalous. Invoice creation volume, status distribution and latency are all
   within normal ranges — 1,847 out of ~400,000 invoices is 0.5%.
3. **Logs.** The audit log (02.7) records the created state, and it is unambiguous:

```json
{"event":"invoice.created","invoice_id":"inv_9f2c41","tenant":"t_44f1",
 "status":"paid","amount_cents":128400,"amount_paid_cents":0,
 "api_key":"key_live_2b8e…","request_id":"req_01J8Z9K2M4"}
```

   An invoice created directly as `paid`. The service is supposed to set `status=DRAFT`
   unconditionally.

4. **Read the request body**, retained for `POST` requests for 30 days:

```json
{"customer_id":"cus_8f21","currency":"EUR","due_date":"2026-09-30",
 "lines":[…],"status":"paid"}
```

   The client sent `status`. The API accepted it.

5. **Read the schema.** The create endpoint's model is not `InvoiceCreate` — it is `InvoiceIn`, a
   single model used for both create and update, and it contains `status` because the *update* path
   needed to expose state transitions to the admin tool:

```python
# as it was
class InvoiceIn(BaseModel):
    customer_id: CustomerId
    currency: Currency
    due_date: date
    lines: list[InvoiceLineIn]
    notes: str | None = None
    status: InvoiceStatus | None = None        # ⚠️ added for the admin update endpoint
    paid_at: datetime | None = None            # ⚠️ same commit
```

6. **Find how clients discovered it.** They read the OpenAPI document (02.4). `status` was a documented,
   optional field on the create request schema, so generated SDKs exposed it as a constructor
   argument. Several integrators, migrating historical invoices from a previous system, set it
   deliberately and reasonably — the API told them they could.

### Root Cause

One model served both create and update. Six weeks earlier, an internal admin tool needed to correct
an invoice's status manually, so `status` and `paid_at` were added to `InvoiceIn`. The update endpoint
needed them; the **create** endpoint shared the model and inherited them.

The service then trusted the parsed model:

```python
# as it was
invoice = Invoice(**body.model_dump(exclude_none=True), id=new_invoice_id(),
                  tenant_id=tenant, version=1)
```

`**body.model_dump()` is the mass-assignment idiom: it takes whatever the client sent and applies it
to the domain object. A field added for one endpoint became a writable field on another, and the
spread operator ensured nobody had to notice.

**This is mass assignment (OWASP API3).** It required no exploit, no unusual client and no malice —
the API documented the field as settable, and clients used it as documented. The 0.5% incidence is
simply how many clients happened to have a reason to set it.

The `extra="forbid"` setting would not have helped: `status` was *declared*. Only the separation of
create from update would have.

### Fix

*Mitigation (30 minutes):* deploy a create-specific model, and reject `status` and `paid_at` on the
create path with a `422`:

```diff
- async def create_invoice(body: InvoiceIn, ...):
+ async def create_invoice(body: InvoiceCreate, ...):   # no status, no paid_at, extra="forbid"
```

Four integrators immediately received `422`s, were contacted the same day, and were given the correct
migration endpoint (`POST /v1/invoices/{id}/payments`) for recording historical payments.

*Permanent fix:*

1. **Three models per resource**, as shown above. `status` appears in `InvoiceOut` only; state changes
   go through explicit action endpoints (01.2).
2. **The service constructs the domain object field by field.** No `**body.model_dump()` anywhere:

```diff
- invoice = Invoice(**body.model_dump(exclude_none=True), id=..., tenant_id=tenant)
+ invoice = Invoice(id=new_invoice_id(), tenant_id=tenant, status=InvoiceStatus.DRAFT,
+                   customer_id=body.customer_id, currency=body.currency,
+                   due_date=body.due_date, notes=body.notes, ...)
```

   Explicit construction is more typing and it is the control: a new field on the input model cannot
   reach the domain object unless someone writes a line to put it there.

3. **`extra="forbid"` on every input model**, closing the adjacent silent-typo failure.
4. **Data remediation:** the 1,847 invoices were reverted to their correct computed status, and the
   finance team was given a reconciliation report per tenant. Four tenants had already issued dunning
   letters based on the wrong state, which required customer-facing apologies.

### Prevention

- **A test asserting that no input model contains a server-controlled field** — the control that
  encodes the lesson directly:

```python
# tests/security/test_no_server_controlled_fields_in_input_models.py
import inspect, pytest
from pydantic import BaseModel
import ledgerly.schemas as schemas

SERVER_CONTROLLED = {
    "id", "tenant_id", "status", "version", "created_at", "updated_at",
    "paid_at", "amount_paid_cents", "number", "internal_risk_score",
}
INPUT_SUFFIXES = ("Create", "Update", "In")

INPUT_MODELS = [
    obj for _, obj in inspect.getmembers(schemas, inspect.isclass)
    if issubclass(obj, BaseModel) and obj.__name__.endswith(INPUT_SUFFIXES)
]

@pytest.mark.parametrize("model", INPUT_MODELS, ids=lambda m: m.__name__)
def test_input_model_has_no_server_controlled_fields(model) -> None:
    offending = SERVER_CONTROLLED & set(model.model_fields)
    assert not offending, (
        f"{model.__name__} accepts server-controlled field(s) {sorted(offending)}: "
        "a client could set state it does not own (mass assignment, 03.3 / 16.3)"
    )

@pytest.mark.parametrize("model", INPUT_MODELS, ids=lambda m: m.__name__)
def test_input_model_forbids_unknown_fields(model) -> None:
    assert model.model_config.get("extra") == "forbid", (
        f"{model.__name__} silently ignores unknown fields; a client typo becomes a no-op"
    )
```

- **A lint rule banning `**model.model_dump()` into a domain or ORM constructor.** The spread operator
  is the mechanism that turns a schema mistake into a data-integrity incident; explicit construction
  makes the mistake visible in review.
- **Review input-model changes as API permission changes.** Adding a field to a request model grants a
  client the right to set it. Ledgerly's CODEOWNERS now routes `schemas/` changes to an API owner, and
  the pull-request template asks: *which endpoints does this field become settable on?*
- **Alert on business invariants**, not just errors: `invoices where status='paid' and
  amount_paid_cents = 0` should be zero, checked hourly. That query would have fired on day one instead
  of at month-end. This is the same lesson as 01.6's `duplicate_invoice_total` — when the technical
  metrics cannot see a problem, the business invariant can.
- **Compare the OpenAPI request schema against expectations in CI.** The committed contract (02.4)
  would have shown `status` appearing on the create request in the pull-request diff.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a client sends a field you did not declare? | `extra="forbid"` → `422` naming it. The default silently ignores it. |
| ...a client sends a field you *did* declare but should not have? | Mass assignment. Only model separation prevents it. |
| ...a field is added to a shared base model? | It appears in every input model that inherits it. Prefer separate classes. |
| ...`tenant_id` is in a request model? | A cross-tenant write primitive. It must come from the credential (08.14). |
| ...the service does `Model(**body.model_dump())`? | Every current and future input field is applied blindly. Construct explicitly. |
| ...a client typos a field name? | With `forbid`, `422`. Without, a successful request that did nothing. |
| ...an output model is missing on a route? | Every attribute of the returned object is serialised (02.4). |
| ...a database column is added? | Nothing changes, if outputs are explicit models. Everything changes, if you return ORM objects. |

## Common Pitfalls

**One model for create, update and output.** The incident above. *Instead:* three classes; the
duplication is the design.

**`Model(**body.model_dump())`.** Applies whatever the client sent. *Instead:* explicit field-by-field
construction in the service.

**Relying on `extra="forbid"` to stop mass assignment.** It rejects *undeclared* fields; mass
assignment uses declared ones. *Instead:* both controls.

**`tenant_id` (or `user_id`, or `role`) in an input model.** Turns a request body into an authorisation
decision. *Instead:* derive from the credential.

**A shared base model for inputs.** Inheritance widens by default, so a field added for one endpoint
appears on all of them. *Instead:* separate classes, or the CI check above.

**Leaving `extra` at the default on inputs.** A client typo becomes a `201` that did nothing.
*Instead:* `forbid`.

**Validating business rules in the model.** A validator that needs a database call cannot run in
Pydantic and will drag I/O into your schema layer. *Instead:* payload-only rules in the model,
data-dependent rules in the service (07.3).

## How to Test This

- The two schema tests above (no server-controlled fields; `extra="forbid"`) — parametrised over every
  input model so a new one is covered automatically.
- A per-endpoint test asserting that sending a server-controlled field returns `422`:
  `test_create_invoice_rejects_status_field`.
- A test asserting `create` ignores nothing: send an unknown field and assert `422` with the field name
  in `loc` (02.9).
- A business-invariant test in the integration suite: after creating an invoice by any documented
  route, `status == "draft"` and `amount_paid_cents == 0`.

## Interview Questions

1. *Explain.* Why do you need separate request and response models? — They express different
   permissions; neither matches the table.
2. *Explain.* What is mass assignment, and why does `extra="forbid"` not prevent it? — Accepting a
   declared field a client should not control; `forbid` only rejects undeclared fields.
3. *Debug this.* Invoices exist as `paid` with no payment records, all created through the API with
   `201`. — A shared input model exposing `status`; check the request bodies and the schema.
4. *Design.* Which fields belong in `InvoiceCreate` but not `InvoiceUpdate`, and why? — Set-once fields
   like `currency` and `customer_id`; immutability is expressed by absence.
5. *Explain.* Why is `Model(**body.model_dump())` dangerous? — It applies every current and future input
   field to the domain object without review.
6. *Explain.* Where should `tenant_id` come from? — The authenticated credential, never the body.
7. *Design.* How would you prove no input model accepts a server-controlled field? — A parametrised test
   over every model, comparing field names against a maintained set.

## Key Takeaways

- An input model is **the client's vocabulary**; an output model is **the client's view**. Neither is
  your table, and they are not each other.
- Three models per mutable resource. The apparent duplication is three genuinely different lists.
- **Every field in an input model is a permission.** Ask what happens if a client sets it to the worst
  possible value.
- Server-controlled fields are those whose value is a *consequence* rather than a *choice*. `status`,
  `tenant_id`, `version`, computed totals and timestamps are never inputs.
- `extra="forbid"` on inputs turns a client typo into an error. It does **not** prevent mass assignment.
- Never spread a request model into a domain constructor. Explicit construction is the control that
  makes a schema mistake visible in review.
- When technical metrics cannot see a problem, a **business invariant** can. Check the ones that must
  always hold, on a schedule.
