## Concept

### Plain-English Explanation

02.4 made the argument: the OpenAPI document is a release artefact — generated, committed, diffed in review, and fed to the SDK generators that produce the `client.createInvoice(...)` your customers call. This notebook is the other half of that deal: the FastAPI mechanics. Every decorator you have written since 03.2 — `response_model`, `name=`, `status_code`, `tags` — was quietly writing that document while it configured the route.

The defaults are *fine for a demo and wrong for a contract*: FastAPI will happily generate operation ids from your function names, advertise a 422 body you never send, and expose your schema on an endpoint you thought you had turned off. None of these is a bug; all are decisions the framework made because you didn't.

### Technical Explanation

The document is **derived from the route table**. `app.openapi()` walks `app.routes` on first call, builds the JSON, and caches it on `app.openapi_schema`; `/openapi.json` serves that cached object, and `/docs` is nothing but a static Swagger UI page whose JavaScript fetches it. So the document describes only what the table holds — why a shadowed route still appears in it (03.2), and why 03.1's `use_stable_operation_ids(app)` runs *after* all `include_router` calls: it rewrites the assembled table. And ⚠️ **the cache is real state**: any `app.openapi()` call before assembly finishes freezes the document there. Captured — after a first call, rewriting operation ids changed nothing until the cache was busted:

```text
after use_stable_operation_ids, spec is same object as before: True
getInvoice id in cached spec: getInvoice_v1_invoices__invoice_id__get
after cache bust (app.openapi_schema = None):
GET    /v1/invoices/{invoice_id}      operationId=getInvoice
```

The knobs map one-to-one onto the document. **`operationId`** comes from `route.operation_id` if set, else FastAPI synthesises it from the route *name* plus path and method — `create_invoice_v1_invoices_post` — where the name itself defaults to the handler's function name. **`response_model`** (or the return annotation, 03.3) becomes the 200 schema, registered under `components/schemas`. **`responses={...}`** adds per-status declarations — where 02.9's problem catalogue reaches the SDKs. **`tags`** group operations in the UI and in generated client namespaces; `FastAPI(openapi_tags=[...])` describes them. **`summary`** is the one-line label; **`description`** defaults to the docstring. **`deprecated=True`** marks the operation (02.13 starts here). **`include_in_schema=False`** removes a route from the document but not from the app — captured: the route serves traffic yet is absent from `paths`. And **`docs_url` / `redoc_url` / `openapi_url`** control exposure — a trap we return to below.

One default *contradicts* your app's behaviour. FastAPI documents a **422 with `HTTPValidationError`** on every route with a body or parameters — but Ledgerly overrides `RequestValidationError` to return a catalogue problem body (03.8, 02.9), so the document advertises a shape the API never sends. Exception handlers are invisible to the generator: declarations describe, they never enforce, and behaviour never flows back into declarations.

### Mental Model

> The OpenAPI document is **compiled output**, and the decorator kwargs are the source language. Whatever you do not write, the compiler fills in from your Python internals — function names, auto-422s — exactly the material a public contract must not depend on. Customising OpenAPI is severing the accidental link between your refactors and your customers' code.

## How It Works

The full pipeline, from decorator to customer, with the two consumption paths from 02.4:

```text
@router.get(..., response_model=, name=, responses=, tags=)
        │  (registration: builds APIRoute objects — 03.2)
        ▼
   app.routes ──── use_stable_operation_ids(app)   ← rewrites the table (main.py, 03.1)
        │
        ▼  first call only
   app.openapi() ──▶ app.openapi_schema  (cached dict; ⚠️ mutations after this are invisible)
        │
        ├──▶ GET /openapi.json ──▶ /docs (Swagger UI fetches it in the browser)
        │                              — the LIVE path: this process, this build
        └──▶ scripts/export_openapi.py ──▶ openapi.json committed (02.4)
                                       ──▶ CI diff gate ──▶ SDK generation, portal docs
                                               — the ARTEFACT path: reviewed, versioned
```

The live document answers "what does *this running process* serve" — useful in dev, dangerous as a generation source: it reflects whatever build answered, feature flags and all. Releases hang off the artefact path: regenerated in CI, drift fails the build (02.4's export script), SDKs generated from the file review approved.

Exposure is the second mechanism with a half-measure trap. Captured:

```text
docs_url=None:              GET /docs          -> 404
docs_url=None:              GET /redoc         -> 404
docs_url=None:              GET /openapi.json  -> 200   ⚠️
openapi_url=None:           GET /docs          -> 404
openapi_url=None:           GET /redoc         -> 404
openapi_url=None:           GET /openapi.json  -> 404
```

`docs_url=None` removes the UI page and nothing else — the machine-readable map of your API is still one GET away. `openapi_url=None` removes the schema *and* both UIs, which are just its clients. 03.1's `main.py` gated only `docs_url` on `settings.expose_docs`; the Tradeoffs section completes the gate.

## Code Example

Start with what the generator does when told nothing — three invoices routes, one without an explicit `name=`, real output:

```text
--- operationIds as FastAPI generates them ---
GET    /v1/invoices/{invoice_id}      operationId=getInvoice_v1_invoices__invoice_id__get
POST   /v1/invoices                   operationId=create_invoice_v1_invoices_post
GET    /v1/invoices/{invoice_id}/pdf  operationId=getInvoicePdf_v1_invoices__invoice_id__pdf_get
```

Every one becomes an SDK method name — path noise, double underscores and all. The middle one is dangerous: with no `name=`, it is built from the *function* name, so a refactor renaming `create_invoice` renames a public SDK method. That is why 02.4's `use_stable_operation_ids` (recap: copies each route's `name` into `operation_id`, raises on duplicates) runs in `main.py` — after it, the ids are exactly the 03.2 names: `getInvoice`, `createInvoice`, `getInvoicePdf`.

Next, the error side of the contract — a route declaring what it can actually return, with the 02.9 catalogue models:

```python
# ledgerly/routers/invoices.py
@router.get(
    "/{invoice_id}",
    response_model=InvoiceOut,
    name="getInvoice",
    summary="Retrieve an invoice",
    responses={
        404: {"model": ProblemDetails, "description": "No such invoice in this tenant"},
        429: {"model": ProblemDetails, "description": "Rate limit exceeded"},
    },
)
async def get_invoice(invoice_id: InvoiceId, svc: Service, tenant: Tenant) -> InvoiceOut:
    return await svc.get_invoice(tenant, invoice_id)
```

What the generator produced for it — declared statuses merged with the defaults:

```text
"responses": {
  "200": {..., "$ref": "#/components/schemas/InvoiceOut"},
  "404": {"description": "No such invoice in this tenant",
          ..., "$ref": "#/components/schemas/ProblemDetails"},
  "429": {"description": "Rate limit exceeded",
          ..., "$ref": "#/components/schemas/ProblemDetails"},
  "422": {"description": "Validation Error",
          ..., "$ref": "#/components/schemas/HTTPValidationError"}    ⚠️
}
```

Look at the 422. We never declared it, and — because 03.8 overrides `RequestValidationError` into a problem body — Ledgerly never sends that shape; it flows into every SDK as a typed response the client will fail to parse the day it matters. Both fixes are verified: **declaring 422 yourself replaces the default**, and **router-level `responses=` merges onto every route**, so the correction is one line per router:

```python
# ledgerly/main.py — every v1 route documents the catalogue's ambient errors
PROBLEM = {"model": ProblemDetails}
for router in (invoices.router, invoice_lines.router, customers.router, operations.router):
    app.include_router(router, prefix="/v1", responses={
        401: PROBLEM | {"description": "Missing or invalid API key"},
        422: PROBLEM | {"description": "Validation problem (see the problem catalogue)"},
        429: PROBLEM | {"description": "Rate limit exceeded"},
    })
```

Captured proof of both behaviours — one route declaring 422 explicitly, one relying on the router-level merge:

```text
/v1/one -> {"429": ".../ProblemDetails", "422": ".../ProblemDetails"}   # both overridden
/v1/two -> {"429": ".../ProblemDetails", "422": ".../HTTPValidationError"}  # merge alone
                                              # doesn't touch the auto-422 — declare it
```

The asymmetry: router-level `responses` *adds* statuses but only displaces the auto-422 when 422 itself is declared — hence its entry in the router-level dict, which does propagate. ⚠️ And none of this changes behaviour: declaring a 404 does not make the handler return one; 03.8's handlers do that. The route-table test below keeps the two in agreement.

Finally, visibility and lifecycle metadata, all captured working: `include_in_schema=False` kept `/v1/internal/cache-stats` serving but out of `paths` (auth still guards it; absence from the document guards nothing); `deprecated=True` marked the legacy PDF route for 02.13's sunset process; `openapi_tags` gave the `invoices` tag its portal description.

> **Version note** — FastAPI ≥ 0.101 with Pydantic v2 generates *separate input and output schemas* when they differ. Captured on 0.136.1: a model with a defaulted field used in both directions appears as `Adjustment-Input`/`Adjustment-Output` in `components/schemas` — merely *adding a default* to a shared model renames schemas and churns the committed snapshot. `FastAPI(separate_input_output_schemas=False)` restores single-schema behaviour (verified); Ledgerly keeps the split and uses distinct `*In`/`*Out` models on public routes anyway (03.3), which sidesteps the renaming.

## Design Patterns / Tradeoffs

### What to expose where: docs and schema in production

- **Everything public** (`/docs` + `/openapi.json` on api.ledgerly.com). *How:* defaults. *Advantages:* zero infrastructure; always matches the running build. *Disadvantages:* the live schema becomes an unversioned generation source; "Try it out" fires real requests at production; the full surface is advertised to scanners first. *Failure mode:* a partner generates their SDK from the live URL during a canary and ships against a build you rolled back. *Use when:* internal services behind the perimeter, dev, staging.
- **All off** (`openapi_url=None` in prod), docs published from the committed artefact on a portal (docs.ledgerly.com renders `openapi.json` from the release tag). *Advantages:* the only obtainable schema is the reviewed one, versioned with releases; prod serves no metadata. *Disadvantages:* a portal to run; docs lag unreleased work (the point). *Failure mode:* the portal build silently stops updating — pin it to the release pipeline, not a cron. *Use when:* the API is a product with external consumers. **Ledgerly's choice** — `expose_docs` now gates `openapi_url` too, completing 03.1's half-gate.
- **Half measures** — `docs_url=None` alone: as captured, hides the furniture, leaves the map. Not a security control (routes answer regardless; only auth, 03.5, is) *and* it fails the convenience goal — the schema people wanted hidden is the part still served. *Use when:* never on a public edge; internally when only the UI should go.

**Recommendation:** live docs everywhere private, artefact-only in production. If a self-serve audience needs an interactive sandbox, point it at a non-prod environment, never `api.ledgerly.com`.

### Where the documentation prose lives

Two real options. **Decorator kwargs and docstrings** (`summary=`, docstring-as-description, `Field(description=..., examples=[...])` — 03.3/03.4): prose lives beside the code and shows up in the snapshot diff; the cost is chunky decorators. **A custom `app.openapi()` override** (FastAPI's escape hatch: replace the method, post-process the dict): total control, at the cost of a shadow layer where the document diverges from the route table — precisely the disease 02.4 exists to prevent. Ledgerly uses kwargs everywhere; `use_stable_operation_ids` deliberately edits the *route table*, not the generated dict, so there is one source of truth. Reach for the override only for what routes cannot express (custom `x-` extensions for a gateway) — and keep it a pure function you can test.

## Production Scenario

**Ledgerly, Wednesday 30 September, 10:15.** The business-invariant alert fires: `ledgerly_invoices_created_hourly` is 40% below the same-weekday baseline (the check built after 03.5's silent-outbox incident). Nothing else is alarming — 5xx flat, p99 normal. The API is healthy; the invoices are missing.

### Symptoms

- The invariant alert, and its segmentation: the drop is entirely **API-key traffic** (integrations); dashboard-originated creates are normal.
- Server logs: nothing. No errors, no 4xx spike — the missing requests *never arrive*. Access logs show several high-volume tenants' keys going quiet from 09:00.
- 10:31, two support tickets, same shape: nightly-built integration pipelines failing with `TypeError: client.getOperationStatus is not a function` — thrown by Ledgerly's own TypeScript SDK, in the 02.10 loop that polls `op_7712`-style operations after submitting invoices.

### Diagnosis

1. **Alert → Metrics.** Business invariant only — no server-side signal *can* exist; the failure is an absence. The API-key segmentation says "integrations broke", not "we broke".
2. **Logs.** Confirm absence, not failure: the quiet tenants' last successful calls were yesterday evening — whatever broke, broke *their* side overnight.
3. **Dependency health — ours is their SDK.** The ticket names it: a method vanished. Timeline: API deploy Tuesday 18:40; SDK v2.7.3 auto-published from the committed `openapi.json` at 19:05; nightly builds picked it up via caret ranges and died on the first operations-poll — taking invoice creation with them.
4. **Diff the artefact.** `git diff v2.7.2 v2.7.3 -- openapi.json`: six operationIds on the operations router changed — `get_operation_status` → `read_operation_status` and friends. The Tuesday PR was a house-style refactor renaming handler functions, and the operations router had **no explicit `name=` on its routes**: `use_stable_operation_ids` faithfully copied `route.name` into the ids, and `route.name` was silently the function name. CI's freshness gate (02.4) passed — the file *was* regenerated and committed; the rename sat in plain sight in a 400-line diff, and nobody read six changed ids as six deleted SDK methods.

### Root Cause

The operations routes' operationIds were derived from function names because no explicit `name=` was ever set; a rename refactor therefore renamed public SDK methods, and the pipeline — working as designed — published the break as a patch release that customers' builds absorbed overnight.

### Fix

*Mitigation (10:52):* deprecate SDK v2.7.3 on the registry and publish v2.7.4 from a corrected document: explicit `name="get_operation_status"` (and the other five) restoring the *old* ids. ⚠️ The snake_case ids are ugly against the 03.2 house style — and they are **the published contract**: renaming them to `getOperationStatus` now would be a second break dressed as a fix; pretty names, if wanted, arrive through 02.13's deprecation process. Pipelines recover on their next build; throughput is back on baseline by 12:10.

*Permanent fix:* the route-table test below, plus a CI **schema-diff gate**: the job that regenerates `openapi.json` also classifies the diff (removed path, changed operationId, narrowed type ⇒ *breaking*; additions ⇒ *additive*) and fails a breaking diff unless the PR carries a `contract-break` label and a changelog entry. The reviewer no longer has to spot six renamed strings in 400 lines; the pipeline names the break.

### Prevention

The incident closes into a named CI test. Explicit names can't be mechanically told apart from defaulted ones (the default *is* `route.name`) — but house style can: handlers are snake_case, route names camelCase, so a snake_case id is one nobody chose:

```python
# tests/contract/test_operation_ids_are_explicit.py
import re
from fastapi.routing import APIRoute
from ledgerly.main import app

CAMEL = re.compile(r"^[a-z]+(?:[A-Z][a-z0-9]+)+$")   # getInvoice, listOverdueInvoices
GRANDFATHERED = {"get_operation_status", ...}         # 30 Sep incident: frozen, see 02.13

@pytest.mark.parametrize("route", [r for r in app.routes
                                   if isinstance(r, APIRoute) and r.include_in_schema])
def test_operation_id_is_deliberate(route: APIRoute) -> None:
    """A snake_case id is a Python function name leaking into SDKs (03.13)."""
    assert CAMEL.match(route.name) or route.name in GRANDFATHERED, (
        f"{route.path}: operationId {route.name!r} looks like a function name — "
        "set name= explicitly on the route")
```

And the business-invariant alert keeps its place as this failure class's only detector: when the break is in the customer's build, your telemetry sees absence, and only a number with a baseline notices absence.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a route is added without `name=`? | Its operationId is the function name; the CI camelCase test fails the PR before an SDK inherits it. |
| ...a handler function is renamed? | Nothing — explicit `name=` decouples the contract from the refactor. That decoupling is the whole point. |
| ...two routes get the same name? | `use_stable_operation_ids` raises at import (02.4) — fail fast at assembly, 03.9's principle, not a silently dropped SDK method. |
| ...the committed `openapi.json` goes stale? | CI's freshness gate regenerates and fails (02.4); the diff gate then classifies what changed. |
| ...something calls `app.openapi()` mid-assembly? | The cache freezes there; later table edits are invisible. Keep generation out of import paths; bust with `app.openapi_schema = None` in tooling that must re-generate. |
| ...you set `docs_url=None` and call the API hidden? | `/openapi.json` still serves the full map (captured). Exposure is `openapi_url`'s job; *security* is auth's job (03.5), never the document's. |
| ...a shared model gains a default field? | Schema splits into `-Input`/`-Output` names and the snapshot churns (Version note) — a rename in the eyes of every generator, caught by the diff gate. |
| ...a declared error is never actually sent? | The document lies until the route-table test cross-checks declarations against the catalogue — declarations describe, handlers (03.8) behave. |

## Common Pitfalls

**Shipping generated operationIds.** `create_invoice_v1_invoices_post` becomes a customer-facing method name, and every refactor is a potential break. *Instead:* explicit `name=` on every schema-visible route, enforced by test, welded to `operation_id` at assembly (02.4).

**Treating hidden docs as security.** `docs_url=None`, `include_in_schema=False` — the routes still answer for anyone who guesses. *Instead:* auth on every route (03.5); exposure settings are contract hygiene, not access control.

**Letting the auto-422 speak for you.** The default advertises `HTTPValidationError` while your 03.8 handlers send problem bodies — typed SDK clients parse the documented shape and fail on the real one. *Instead:* declare 422 with the catalogue model.

**Aspirational `responses={}`.** Declaring 404/429 on a route that can't produce them, or forgetting ones it can — fiction in both directions. *Instead:* declarations mirror the 02.9 catalogue for that route, checked by a route-table test; handlers stay the only place behaviour lives.

**Post-processing the generated dict as a lifestyle.** A custom `app.openapi()` that "fixes up" the document is a second source of truth the route table knows nothing about. *Instead:* express it on the routes; reserve the override for what routes cannot express, as a pure, tested function.

**Generating SDKs from a live `/openapi.json`.** You get whatever build answered — canary, feature-flagged, rolled back. *Instead:* generate from the committed artefact at a release tag (02.4).

## How to Test This

- Route-table tests over the assembled `app.routes`: every schema-visible route has a deliberate (camelCase) name; every route declares a filtered response model (02.4's test); `responses` cover the route's catalogue errors — cheap, no I/O, import-and-assert.
- The freshness + diff gate in CI: regenerate `openapi.json`, fail on drift, classify breaking vs additive.
- An exposure test: build the app with the prod settings profile and assert `/docs`, `/redoc` *and* `/openapi.json` all 404 — pinning the captured half-gate trap.

## Interview Questions

1. *Explain.* Where does FastAPI's OpenAPI document come from, and when? — Derived from the route table on the first `app.openapi()` call, cached on `app.openapi_schema`; `/docs` is a static UI that fetches `/openapi.json`. Handlers contribute nothing.
2. *Debug this.* Customers report a generated SDK method vanished after a patch release; the API had "no changes", only a refactor. — OperationIds were defaulting to function names; a rename flowed through generation into the SDK. Restore the old ids explicitly, then gate id changes in CI.
3. *Explain.* Why is `docs_url=None` not enough to take an API dark? — It removes only the UI; the schema still serves at `/openapi.json`. `openapi_url=None` removes both — and neither is a security boundary; auth is.
4. *Design.* Documentation exposure for a B2B API. — Live docs in dev/staging; production serves neither UI nor schema; a portal renders the committed artefact per release tag; SDKs generate from that artefact, never from a live endpoint.
5. *Explain.* Your API returns RFC 9457 problems for validation errors, but SDK users see parse failures on 422s. Why? — FastAPI auto-documents `HTTPValidationError`; the exception-handler override never reaches the document. Declare 422 with the problem model.
6. *Design.* A schema-stability gate for CI. — Commit the generated document; regenerate and fail on drift; classify the diff and require an explicit label for breaking changes; publish SDKs only from tagged artefacts.
7. *Debug this.* A route added yesterday serves fine but is missing from `/openapi.json`. — Either `include_in_schema=False`, or something cached `app.openapi()` before the router was included — look for imports that generate the schema at module load.

## Key Takeaways

- The document is compiled from the route table; decorator kwargs are the source. Everything you don't write, defaults write for you — out of your Python internals.
- Operation ids are public API: explicit `name=` on every route, welded to `operation_id` at assembly, enforced by a route-table test — so refactors can never rename a customer's method.
- `responses={}` is how the 02.9 catalogue reaches SDKs — declare ambient errors once at `include_router`, and 422 explicitly to displace the auto-generated lie.
- Declarations describe; handlers behave. Only tests over the assembled app keep them honest.
- `docs_url=None` hides the furniture, not the map; `openapi_url=None` hides both; auth is the only security either way. Production serves the artefact story: committed snapshot → portal + SDKs.
- `app.openapi()` caches on first call — keep generation out of import-time code.
- This topic's failure mode is *absence*: broken customers stop calling. Only a business-invariant baseline notices silence.
