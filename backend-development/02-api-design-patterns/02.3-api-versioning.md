# 02.3 API Versioning

> **Prerequisites:** 02.1 (URIs are permanent), 02.2 (contracts and schemas) · 01.4 (media-type negotiation)
> **What you'll learn:**
> - Define "breaking change" from the client's side, which is the only side that counts
> - Recognise the additive changes that break clients anyway — new enum values chief among them
> - Choose between URI, header and media-type versioning on operational grounds
> - Keep the number of live versions small enough that you can still ship features
> **Level:** Intermediate

> ⚡ **Tuesday 11:30** — partial payments ship, and customers' integrations crash on invoices nobody partially paid. The cause: one new enum value.

## Concept

### Plain-English Explanation

Versioning is not about numbers. It is about making a promise you can keep.

A version says: *"code written against this today will still work in a year."* Every version you
publish is a promise you must honour until every client has moved off it — which, for a B2B product,
means until a company that integrated three years ago and has since lost the engineer who wrote it
decides to look at it again. That may be never.

So the real skill is not picking `/v1/` versus `Accept: application/vnd.ledgerly.v1+json`. It is
**knowing what actually breaks a client**, so you can make most changes without a new version at all.
Teams that version well ship almost everything additively and cut a new version once every few years.
Teams that version badly either break clients constantly or end up maintaining six versions and
unable to change anything.

### Technical Explanation

**A change is breaking if a correctly-written existing client stops working.** Not "if the schema
changed" — clients do not consume schemas, they consume responses.

Clearly breaking:

- Removing or renaming a field, endpoint or parameter
- Changing a field's type (`amount: 4990` → `amount: "49.90"`)
- Making an optional request field required
- Adding a new validation rule that rejects previously-accepted input
- Changing the meaning of a value while keeping its name
- Changing a status code for an existing condition (`200` → `202`)

Usually safe:

- Adding a new optional request field
- Adding a new endpoint
- Adding a new *response* field (see the caveat below)
- Relaxing validation

**And the ones that surprise people — additive changes that break real clients:**

| Change | Why it breaks | Who it breaks |
|---|---|---|
| **New enum value** | Generated SDKs model enums as closed sets; an unknown value is a deserialisation error | Java, Go, Rust, C#, Swift, TypeScript strict clients |
| New response field | Strict schema validation (`additionalProperties: false`), or code doing an exhaustive `match` | Clients validating against a stored schema |
| Field becomes nullable | `str` → `str \| None` breaks any client that did not expect null | Typed clients; Python clients at runtime |
| New error code | Client's error handling has no branch for it and falls into a default that retries wrongly (01.3) | Any client with exhaustive error mapping |
| Ordering change on a list | A client that assumed insertion order now shows wrong data | Anything paging without a stable sort (02.5) |
| Tightened rate limit | Working integrations begin failing (02.12) | High-volume clients |
| New required header | Same as a required field | All clients |

**Enum extension is the sharpest of these**, because it feels obviously additive and is documented as
safe almost nowhere. In Python and JavaScript, an unknown string is just a string, so nothing breaks —
which means your own client library and your own tests will not detect it. In a generated Java or Go
SDK, `InvoiceStatus.valueOf("partially_paid")` throws. This is the scenario below.

**Versioning strategies:**

```text
URI path         GET /v2/invoices/inv_9f2c41
                 visible, greppable, cache-friendly, easy to route at the proxy
                 ⚠️ implies the whole API versions together

Header           GET /invoices/inv_9f2c41
                 Ledgerly-Version: 2026-08-24
                 invisible in logs and browsers unless you log it; needs Vary (01.4)

Media type       Accept: application/vnd.ledgerly.v2+json
                 protocol-correct; same caveats as headers; awkward in curl

Query parameter  GET /invoices/inv_9f2c41?version=2
                 easy to test in a browser; pollutes the cache key; easy to forget

Date-based       Ledgerly-Version: 2026-08-24   (Stripe's model)
                 pinned per account at signup; each change is a small, named migration
```

### Mental Model

> A version is **a promise about what will not change**, and every live version is a promise you are
> still paying for. Your goal is not good version numbers — it is to make most changes *additively*
> so that you rarely need one. Ask of every change: *would a competent client written last year still
> work?* The client's language matters to that answer, which is why "additive" must be judged against
> the strictest consumer you have, not the most forgiving.

## How It Works

Ledgerly versions the **URI path** for structural changes and treats everything else as additive,
governed by a published compatibility policy. The key insight is that the policy is part of the API:

```text
PUBLISHED COMPATIBILITY POLICY (in the API reference, and in the OpenAPI description)

  We may, without a new version:
    · add new fields to responses          → clients MUST ignore unknown fields
    · add new values to enumerated fields  → clients MUST tolerate unknown values
    · add new optional request parameters
    · add new endpoints and new error `type` URIs

  We will not, without a new version:
    · remove or rename anything
    · change a field's type or nullability
    · change the meaning of an existing value
    · tighten validation on an existing field

  Clients that cannot tolerate the first list must pin a version (02.13).
```

That policy is doing real work. Without it, "we added an enum value and it broke you" is Ledgerly's
fault. With it published *before* the change, it is a documented contract — and, more usefully, it
tells you what to put in your SDKs and your OpenAPI so clients are generated correctly in the first
place.

**The lifecycle of a version:**

```text
v1 ────────────────────────────────────────────────────────────────▶ (still serving)
                    │
          v2 introduced (breaking change batched here)
                    │────────────────────────────────────▶
                    │           │
                    │      v1 marked deprecated: Deprecation + Sunset headers (02.13)
                    │           │
                    │           │        usage telemetry per API key drives outreach
                    │           │                    │
                    │           │              brownouts (short scheduled 410s)
                    │           │                    │
                    └───────────┴────────────────────┴──── v1 removed when usage is zero
```

⚠️ **Batch breaking changes.** A version is expensive to introduce and expensive to retire, so the
changes that need one should queue up and ship together. An API that cuts a version per breaking
change ends up at v7 with six live promises; an API that batches ships v2 once every three years.

## Code Example

Version routing in FastAPI, where the two versions share everything except the boundary schemas:

```python
# ledgerly/main.py
from fastapi import FastAPI
from ledgerly.routers import v1, v2

app = FastAPI(title="Ledgerly Invoicing API")
app.include_router(v1.api)    # prefix="/v1"
app.include_router(v2.api)    # prefix="/v2"
```

The important discipline is that **only the schema layer is duplicated**. The service layer (07.3)
has one implementation; each version's schemas adapt the same domain object to a different promise:

```python
# ledgerly/schemas/v1/invoice.py
from enum import StrEnum
from pydantic import BaseModel, ConfigDict, Field

class InvoiceStatusV1(StrEnum):
    """v1's CLOSED status set. This exact list was promised to clients in 2024
    and can never grow — a v1 client's generated SDK models it as an enum."""
    DRAFT = "draft"
    OPEN = "open"
    PAID = "paid"
    VOID = "void"

class InvoiceOutV1(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: str
    number: str
    status: InvoiceStatusV1
    amount_cents: int = Field(ge=0)
    currency: str

    @classmethod
    def from_domain(cls, invoice: Invoice) -> "InvoiceOutV1":
        # The v1 COMPATIBILITY SHIM. New domain states must be projected onto
        # the four values v1 promised. `partially_paid` is a kind of `open` to a
        # client that has never heard of partial payment — which is exactly what
        # a v1 client is. Losing detail here is the point: v1 promised four values.
        status = invoice.status
        if status in {"partially_paid", "overdue"}:
            status = "open"
        return cls(id=invoice.id, number=invoice.number, status=InvoiceStatusV1(status),
                   amount_cents=invoice.amount_cents, currency=invoice.currency)
```

A word on `amount_cents`, which this module uses throughout: money travels as **integer minor
units** (Stripe's convention) — no float rounding drift, and JSON-safe without string-encoding a
decimal. `Decimal` mapped to `NUMERIC` is the right alternative when amounts are not whole minor
units — multi-currency with fractional minor units, rates and percentages — and 05.3 picks that
choice up on the storage side.

v2 carries the richer state *and* declares its enum open, so the same mistake cannot recur:

```python
# ledgerly/schemas/v2/invoice.py
class InvoiceOutV2(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: str
    number: str
    # ⚠️ Deliberately `str`, not StrEnum, with the permitted values documented as
    # examples rather than as a closed schema. Generated SDKs then produce a
    # string, and a new state is genuinely additive. The cost is that clients
    # lose compile-time exhaustiveness — which is the trade v1 got wrong.
    status: str = Field(examples=["draft", "open", "partially_paid", "overdue", "paid", "void"],
                        description="Extensible. New values may be added at any time; "
                                    "treat unrecognised values as 'open'.")
    amount_cents: int = Field(ge=0)
    amount_paid_cents: int = Field(ge=0)          # new in v2
    currency: str
```

Requests are tagged with the version they used, so usage telemetry per version and per client exists
from day one — the data that makes deprecation possible later (02.13):

```python
# ledgerly/middleware/version_telemetry.py
from prometheus_client import Counter

API_VERSION_USAGE = Counter(
    "api_version_requests_total", "Requests per API version and client",
    ["version", "api_key_id", "route"],
)

async def record_version(request: Request, call_next):
    version = request.url.path.split("/")[1]           # "v1" | "v2"
    response = await call_next(request)
    API_VERSION_USAGE.labels(version=version,
                             api_key_id=getattr(request.state, "api_key_id", "anonymous"),
                             route=request.scope.get("route").path if request.scope.get("route") else "unknown",
                             ).inc()
    return response
```

⚠️ `api_key_id` as a metric label is a cardinality risk (15.3). Ledgerly bounds it by labelling only
keys on the deprecation list and bucketing the rest as `other` — the alternative, discovering at
sunset time that you cannot say who is still on v1, is worse.

## Design Patterns / Tradeoffs

### URI path versioning

- *How it works:* `/v1/...`, `/v2/...`; the version is part of every URI.
- *Advantages:* visible in logs, dashboards, browser bars and support tickets; routable at the proxy,
  so you can send versions to different deployments; caches key on it naturally (01.4); trivial for
  clients to pin; the easiest to reason about at 3 a.m.
- *Disadvantages:* violates the idea that a URI names a resource, since `/v1/invoices/x` and
  `/v2/invoices/x` are the same invoice; implies whole-API versioning; clients must rewrite every URL
  to upgrade.
- *Failure mode:* v1 and v2 code drift apart because they are separate route trees, and a bug fixed
  in one is missed in the other.
- *Use when:* public APIs with third-party integrators. Default choice, and Ledgerly's.
- *Do NOT use when:* you need per-resource version granularity.

### Header or media-type versioning

- *Advantages:* URIs stay canonical; per-resource granularity; upgrading is a header change; the
  media-type form is what HTTP intends (01.4).
- *Disadvantages:* invisible unless you deliberately log it; must be in `Vary` or caches will mix
  versions (01.4 — the same leak mechanism); harder to test from a browser; easy for a client to omit
  and silently get a default.
- *Failure mode:* a client omits the header, receives the *latest* version, and breaks on your next
  release. Mitigate by defaulting to the **oldest supported** version, never the newest.
- *Use when:* fine-grained evolution, or a mature consumer base comfortable with headers.

### Date-based versions pinned per account

- *How it works:* each account is pinned to the date it signed up; every change is a small named
  migration applied in reverse for older pins.
- *Advantages:* many tiny changes rather than rare huge ones; clients upgrade deliberately; no `/v7/`.
- *Disadvantages:* requires a migration framework and per-version transformation chains; every
  response passes through N transformers; substantial engineering investment.
- *Use when:* a large public API with many integrators and frequent evolution.
- *Do NOT use when:* you have neither the volume nor the tooling to justify it.

### No versioning, additive-only

- *Advantages:* one code path, no duplication, no deprecation programme; forces genuinely
  backward-compatible design.
- *Disadvantages:* you can never remove or fix anything structurally wrong; the schema accretes
  deprecated fields forever; requires clients to be tolerant, which you cannot enforce.
- *Use when:* internal APIs where you control every client and can change them all at once.
- *Do NOT use when:* third parties consume it.

**Recommendation:** URI versioning with a **published compatibility policy** that makes additive
changes explicitly allowed, so v2 is needed once every few years. The policy matters more than the
mechanism — most teams get the mechanism right and never write down what "additive" means.

## Production Scenario

**Ledgerly, Tuesday 11:30.** The partial-payments feature ships — customers can now record a payment
smaller than the invoice total, and the invoice enters a new `partially_paid` state. It was reviewed
as a purely additive change: a new enum value and a new response field, no removals. Ninety minutes
later, three enterprise customers open P1 tickets.

### Symptoms

- Three customers report that their invoice-sync integration is crashing. All three are large
  accounts; two run overnight reconciliation that will fail tonight if not fixed.
- Their error messages, quoted in the tickets, are all deserialisation failures:

```text
com.fasterxml.jackson.databind.exc.InvalidFormatException: Cannot deserialize value of type
  `com.ledgerly.model.InvoiceStatus` from String "partially_paid": not one of the values
  accepted for Enum class: [DRAFT, OPEN, PAID, VOID]
```

- **The API is completely healthy.** `2xx` rate normal, latency normal, error rate flat. The failures
  are entirely on the client side; Ledgerly's servers returned `200 OK` with valid JSON every time.
- The other ~197 integration customers report nothing.
- Ledgerly's own dashboard, mobile apps, Python SDK and JavaScript SDK all work perfectly.

### Diagnosis

1. **Alert.** None. Ledgerly's metrics cannot see a client-side parse failure — every request
   succeeded. This is a general property worth internalising: **breaking a contract produces no
   server-side signal at all.**
2. **Metrics.** The only visible trace is indirect: `api_version_requests_total{version="v1"}` for
   those three keys drops to near-zero after 11:32, because their sync processes are crash-looping
   rather than polling. A traffic *drop* for one client is the detectable symptom.
3. **Logs.** Nothing. The requests are `200`s.
4. **Correlate the affected customers.** The decisive step. All three use SDKs generated from
   Ledgerly's OpenAPI document with `openapi-generator` targeting **Java** or **Go**. The 197
   unaffected customers use Python, JavaScript, or hand-written HTTP calls.
5. **Reproduce in thirty seconds** by generating a Java client from the published OpenAPI and feeding
   it a `partially_paid` invoice. The generated enum is closed; the parse throws.
6. **Root cause confirmed by reading the OpenAPI document**, which was doing exactly what it was told:

```yaml
InvoiceStatus:
  type: string
  enum: [draft, open, paid, void]     # ← published as a CLOSED set since 2024
```

### Root Cause

Adding a value to an enumerated field is a **breaking change for any client whose language models
enums as closed sets** — which is every strongly-typed generated SDK. Ledgerly's OpenAPI had declared
`status` as a four-value enum, and generators had faithfully produced closed types in Java, Go, Rust
and C#.

The change passed review as additive because it was judged against the languages the team uses.
Python and JavaScript treat an unknown string as a string; nothing in Ledgerly's own test suite,
SDKs, or dogfooding could have detected the problem. **The compatibility of a change depends on the
strictest consumer, and Ledgerly had no test representing one.**

Compounding it: no compatibility policy had ever been published, so clients had no basis on which to
build tolerant parsers, and Ledgerly had no basis on which to call the change permitted.

### Fix

*Mitigation (18 minutes):* revert the v1 projection so v1 clients never see the new value. The feature
stays live — the *data* is correct, and only the v1 representation is clamped:

```python
# ledgerly/schemas/v1/invoice.py — the shim shown earlier, deployed as the hotfix.
if status in {"partially_paid", "overdue"}:
    status = "open"     # v1 promised four values; project new states onto them.
```

All three integrations recovered on their next poll with no change on their side. `amount_paid_cents`
was left in the v1 response — a new *field* is tolerated by these generators, which ignore unknown
properties by default, and this was verified against a generated Java client before deploying rather
than assumed.

*Permanent fix:*

1. **v2 ships the real model**: `status` as an open string, `amount_paid_cents`, and the full state
   set. v1 keeps its four-value promise forever.
2. **A published compatibility policy** (the block in *How It Works*), in the API reference and in the
   OpenAPI `info.description`, stating that v2 enums are extensible and clients must tolerate unknown
   values.
3. **v2's OpenAPI does not declare closed enums** for extensible fields — the values appear as
   `examples` and prose, so generators produce `string`. Losing compile-time exhaustiveness is the
   deliberate price of being able to add states.
4. **A generated-SDK compatibility suite in CI**, described below, so "additive" is verified rather
   than assumed.

### Prevention

- **Test against the strictest client you have, not the friendliest.** CI now generates a Java and a
  Go client from the current OpenAPI and replays a fixture corpus through them:

```yaml
# .github/workflows/sdk-compat.yml (excerpt)
- name: Generate strict SDKs from the current OpenAPI
  run: |
    openapi-generator generate -i openapi.json -g java   -o /tmp/sdk-java
    openapi-generator generate -i openapi.json -g go     -o /tmp/sdk-go
- name: Replay response fixtures through the generated clients
  run: ./scripts/sdk_compat_check.sh   # fails on any deserialisation error
```

- **An OpenAPI diff gate** that classifies every schema change and fails the build on a breaking one
  without an explicit override:

```bash
# CI: compare the PR's contract against the last released contract.
$ oasdiff breaking https://api.ledgerly.com/v1/openapi.json ./openapi.json
ERROR  [response-property-enum-value-added] /v1/invoices/{invoice_id} GET response 200:
       added enum value 'partially_paid' to property 'status'
```

  ⚠️ Note that `oasdiff` classifies *adding* a response enum value as breaking. That is the tool
  encoding exactly the lesson this incident taught, and the team had never run it.

- **Design enums as open from the first release.** Deciding on day one whether a field is a closed set
  (`currency` — genuinely closed) or an open set (`status` — will grow) costs nothing then and cannot
  be changed later.
- **Alert on a per-client traffic drop.** For the third time in this curriculum (01.4, 01.8), the only
  server-side signal of a serious problem was traffic quietly going away. An alert on
  `api_version_requests_total` falling >80% for any single key over 15 minutes would have paged before
  the first ticket.
- **A published compatibility policy is a technical control**, not documentation. It defines what your
  CI gate enforces and what your SDK generators emit.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...you add an enum value? | Breaking for generated typed SDKs. Either version it or have declared the enum open from the start. |
| ...you add a response field? | Usually safe; breaks clients validating with `additionalProperties: false`. Verify against a generated client. |
| ...you make a field nullable? | Breaking for typed clients. Treat as a version change. |
| ...you add a new error `type`? | Clients without a branch for it fall through to a default — which may retry a permanent failure (01.3). Publish the taxonomy as open. |
| ...a client omits the version header? | With header versioning, default to the **oldest** supported version. Defaulting to newest breaks them on your next release. |
| ...you need to retire a version? | You need per-client usage telemetry, gathered from day one. Without it, retirement is guesswork (02.13). |
| ...a bug is fixed in v2 but not v1? | Duplicated route trees drift. Keep one service layer; version only the boundary schemas. |
| ...a client is on a version you removed? | `410 Gone` with a `Link` to migration docs — never a silent `404`. |

## Common Pitfalls

**Judging "additive" against your own language.** The entire scenario. Python and JavaScript hide the
problem your Java customers will hit. *Instead:* test against a generated strict client in CI.

**Declaring enums closed in OpenAPI by default.** Pydantic `StrEnum` → closed schema → closed
generated types → the field can never grow. *Instead:* decide open vs closed per field, deliberately,
before the first release.

**Versioning per change.** Reaching v6 in two years means six live promises and no capacity for
anything else. *Instead:* batch breaking changes; make everything else additive.

**Duplicating the service layer per version.** Two implementations drift, and a bug fixed in one
survives in the other. *Instead:* one domain and service layer, version-specific schemas at the edge.

**Defaulting an omitted version to "latest".** Every client that forgot the header breaks on your next
release, and they will be the least sophisticated ones. *Instead:* default to the oldest supported.

**Removing a version on schedule rather than on evidence.** Dates do not migrate clients; telemetry
and outreach do (02.13). *Instead:* remove when usage reaches zero, using brownouts to flush out
clients you cannot identify.

**Never publishing a compatibility policy.** Without it, every additive change is arguably a breach of
contract, and clients have no basis to write tolerant code. *Instead:* publish it before you need it.

## How to Test This

- The generated-SDK compatibility job (Java + Go at minimum) replaying a response-fixture corpus.
- An `oasdiff breaking` gate against the last released OpenAPI, failing the build without an explicit,
  reviewed override label.
- A test per legacy version asserting the shim: `test_v1_projects_partially_paid_to_open`.
- A test that every v1 response validates against the *stored 2024* v1 schema file, not against the
  current code's schema — otherwise the test moves whenever the code does.

## Interview Questions

1. *Explain.* Define a breaking change without referring to your schema. — A correctly-written existing
   client stops working.
2. *Explain.* Why is adding an enum value breaking, and for whom? — Generated SDKs in typed languages
   model enums as closed sets and fail to deserialise unknown values.
3. *Debug this.* Three of two hundred customers report crashes; your API returns `200` for every
   request and all metrics are green. — A contract break; correlate affected customers by SDK
   language; reproduce with a generated client.
4. *Design.* URI or header versioning for a public API with 200 integrators? Defend it. — URI for
   visibility, routability and pinning; note the caching and default-version pitfalls of headers.
5. *Explain.* What must exist before you can retire v1? — Per-client usage telemetry, outreach,
   `Deprecation`/`Sunset` headers, and brownouts.
6. *Design.* You must add a new invoice state. How do you ship it without breaking anyone? — Project
   it onto existing states for old versions; expose it fully in the new version; publish the policy.
7. *Explain.* Why default an omitted version header to the oldest supported version? — Clients that
   forgot to pin should not be upgraded silently.

## Key Takeaways

- A version is a promise you keep paying for. Minimise the number of live promises by making most
  changes additive.
- **"Additive" must be judged against your strictest consumer.** New enum values, new nullability and
  new error codes all break generated typed SDKs while your Python tests stay green.
- Publish a compatibility policy stating what may change without a version. It is a technical control
  that drives your CI gate and your SDK generation, not documentation.
- Decide open vs closed for every enumerated field before the first release. It cannot be changed
  afterwards.
- URI versioning is the pragmatic default for public APIs: visible, routable, pinnable, debuggable.
- Version the **boundary schemas**, not the service layer. Duplicated implementations drift.
- Breaking a contract produces **no server-side error signal**. Detect it with strict-client CI checks
  and with alerts on per-client traffic disappearing.
