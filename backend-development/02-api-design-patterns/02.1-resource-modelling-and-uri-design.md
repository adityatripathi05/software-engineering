# 02.1 Resource Modelling and URI Design

> **Prerequisites:** 01.2 (methods and safety), 01.3 (status codes), 01.10 (proxies and forwarded headers) · modern-python 18.1 (REST as a client)
> **What you'll learn:**
> - Turn a domain into resources — including the parts of a domain that are not obviously nouns

> - Treat the URI as the one part of your API you can never refactor
> **Level:** Beginner

## Concept

### Plain-English Explanation

Designing an API starts with naming things. Not endpoints — *things*. An invoice is a thing. A
customer is a thing. "Send the invoice" is not a thing; it is something that happens to one.

The reason this ordering matters is not aesthetics. Once a URI is published, it exists forever. Some
customer has it hardcoded in a script that nobody at their company maintains any more. You can
rewrite your database schema, swap your framework, rename every class, and split your monolith — and
none of that is visible to a client. Change `/v1/invoices/{id}` to `/v1/billing/invoices/{id}` and
you have broken everyone.

> **Your internal code is refactorable. Your URIs are not.** Spend the extra hour before the first
> release, not the six weeks after the hundredth customer.

### Technical Explanation

**A resource is anything worth naming and addressing independently.** The test: would a client ever
want to fetch, link to, cache, or set permissions on this thing by itself? If yes, it is a resource
and it gets a URI.

The shapes you will use:

| Shape | Example | When |
|---|---|---|
| **Collection** | `/v1/invoices` | A set of things; supports `GET` (list) and `POST` (create) |
| **Item** | `/v1/invoices/inv_9f2c41` | One thing; `GET`, `PUT`, `PATCH`, `DELETE` |
| **Sub-collection** | `/v1/invoices/inv_9f2c41/lines` | Things that exist only within a parent |
| **Singleton sub-resource** | `/v1/invoices/inv_9f2c41/pdf` | Exactly one of a thing per parent; no id |
| **Action sub-resource** | `/v1/invoices/inv_9f2c41/send` | An operation modelled as a thing you `POST` (01.2) |
| **Filtered view** | `/v1/invoices?status=overdue` | A subset; **not** a new path (02.6) |

**Conventions that are not worth debating** — pick these and move on: plural collection names
(`/invoices`, not `/invoice`), lowercase with hyphens for multi-word segments
(`/credit-notes`), no file extensions (use `Accept` — 01.4), no verbs in paths except deliberate
action sub-resources, and **one canonical form with no trailing slash**.

**What goes in the path versus the query string:**

- **Path** — identity. It answers *which thing*. `/v1/invoices/inv_9f2c41`.
- **Query** — everything else: filtering, sorting, pagination, field selection, expansion.
  `?status=overdue&sort=-due_date&limit=50`.

The practical consequence: two URIs differing only in query string may be the *same resource* viewed
differently, so they can share cache validators and permissions. Two URIs differing in path are
different things. Getting this backwards — `/v1/invoices/overdue` as a path — creates a resource that
is really a query, and you will end up with `/v1/invoices/overdue/unpaid/eur` before long.

**Identifiers.** Three choices, and the difference is externally visible forever:

```text
/v1/invoices/40218          sequential integer  — leaks volume and invites enumeration
/v1/invoices/8f3c1a2b-…     bare UUID           — safe, but unreadable and untyped
/v1/invoices/inv_9f2c41     prefixed opaque id  — safe, self-describing, greppable in logs
```

A sequential id tells anyone who can create two records how many you created in between — sign up in
January and again in February, subtract, and you know Ledgerly's monthly invoice volume. It also
makes enumeration trivial, which turns any authorisation gap into a bulk data extraction (16.8).
A **prefixed opaque identifier** costs nothing and removes both problems; the storage-side choice
(serial vs UUIDv4 vs UUIDv7) is a separate decision made in 05.1.

### Mental Model

> A URI **names a thing, permanently, in public**. Ask of every path segment: *is this a thing a
> client would want to address on its own?* If it is a filter, it belongs in the query string. If it
> is a verb, it belongs in the method (01.2) or in a deliberate action sub-resource. If it is an
> internal implementation detail, it should not be in the URI at all.

## How It Works

Ledgerly's resource map, with the reasoning for each decision:

```text
/v1/customers                          collection
/v1/customers/{customer_id}            item
/v1/customers/{customer_id}/contacts   sub-collection — a contact has no life outside a customer

/v1/invoices                           collection  ← NOT nested under customers (see below)
/v1/invoices/{invoice_id}              item
/v1/invoices/{invoice_id}/lines        sub-collection — a line item is meaningless alone
/v1/invoices/{invoice_id}/pdf          singleton sub-resource — exactly one per invoice, no id
/v1/invoices/{invoice_id}/send         action sub-resource — POST only (01.2)
/v1/invoices/{invoice_id}/payments     sub-collection … but payments are ALSO
/v1/payments/{payment_id}              a top-level resource, because a payment can be
                                       queried, refunded and reported on independently

/v1/invoices?customer_id=cus_8f21      the "customer's invoices" view — a QUERY, not a path
```

Two decisions in that map are the ones worth understanding.

**Invoices are not nested under customers**, even though every invoice has exactly one customer. The
reason is not style; it is that a nested URI *asserts an ownership that can change*. Ledgerly later
had to support customer merges — and if invoice URIs had been `/v1/customers/{cid}/invoices/{iid}`,
then every merge would have changed the URI of every invoice, breaking every stored link, every
cached entry (01.4), and every customer's hardcoded path. A flat `/v1/invoices/{id}` with
`customer_id` as an attribute survives the merge untouched.

> **Rule of thumb:** nest only when the child genuinely cannot exist without that exact parent and
> the relationship can never be reassigned. Invoice lines qualify. Invoices do not.

**Payments appear in two places.** `/v1/invoices/{id}/payments` is the natural way to ask "what has
been paid against this invoice", and `/v1/payments/{id}` is the natural way to address one payment.
That is not duplication — the first is a *sub-collection view*, the second is the canonical item URI.
Return the canonical URI in `Location` and in the resource body so clients converge on one form.

**Nesting depth.** Each level adds a segment every client must construct correctly, and a parent id
that must be validated (and that *can disagree* with the child — see the pitfall below). Two levels
is comfortable, three is a smell, four means you are modelling your database, not your API.

## Code Example

The router layout follows the resource map, so the file tree and the URI space match — which is what
makes an unfamiliar engineer able to find the code for a URI in one guess.

```python
# ledgerly/routers/__init__.py
from fastapi import APIRouter
from ledgerly.routers import customers, invoices, invoice_lines, payments

# ⚠️ redirect_slashes=False: FastAPI's default issues a 307 from /v1/invoices/ to
# /v1/invoices. That redirect is a liability behind a proxy (see the scenario below).
# One canonical form; anything else is a 404 the client can see and fix.
api = APIRouter(prefix="/v1", redirect_slashes=False)

api.include_router(customers.router)        # /v1/customers
api.include_router(invoices.router)         # /v1/invoices
api.include_router(invoice_lines.router)    # /v1/invoices/{invoice_id}/lines
api.include_router(payments.router)         # /v1/payments
```

Identifiers are generated in one place, typed, and prefixed — so a `customer_id` can never be passed
where an `invoice_id` is expected without a type checker complaining:

```python
# ledgerly/ids.py
import secrets
from typing import NewType

InvoiceId = NewType("InvoiceId", str)
CustomerId = NewType("CustomerId", str)
PaymentId = NewType("PaymentId", str)

_ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyz"

def _generate(prefix: str, length: int = 14) -> str:
    """Prefixed, opaque, URL-safe. The prefix makes IDs self-describing in logs,
    support tickets and error reports; the random body prevents enumeration and
    stops anyone deriving our volume from consecutive values."""
    body = "".join(secrets.choice(_ALPHABET) for _ in range(length))
    return f"{prefix}_{body}"

def new_invoice_id() -> InvoiceId:
    return InvoiceId(_generate("inv"))

def new_customer_id() -> CustomerId:
    return CustomerId(_generate("cus"))
```

⚠️ The public identifier is deliberately **not** the primary key. Internally, invoices use a
`bigint` surrogate key for join performance and a UUIDv7 for ordering (05.1); `inv_9f2c41` is a
separate indexed column. Coupling the URI to the storage key means a storage decision becomes a
public API decision, and those have very different change costs.

The nested route shows the validation that nesting obliges you to do:

```python
# ledgerly/routers/invoice_lines.py
router = APIRouter(prefix="/invoices/{invoice_id}/lines", tags=["invoice-lines"])

@router.get("/{line_id}", response_model=InvoiceLineOut)
async def get_line(invoice_id: InvoiceId, line_id: str,
                   svc: Service, tenant: Tenant) -> InvoiceLineOut:
    """⚠️ The parent id in the path MUST be verified against the child's actual
    parent. Loading the line by line_id alone and ignoring invoice_id means
    /v1/invoices/inv_AAA/lines/line_belonging_to_BBB returns BBB's data — a
    broken-object-level-authorisation bug hiding in a URI design decision (16.8)."""
    return await svc.get_line(tenant, invoice_id=invoice_id, line_id=line_id)
```

Verifying the canonical form from the shell:

```bash
$ curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://api.ledgerly.com/v1/invoices/
404
$ curl -s -o /dev/null -w '%{http_code}\n' https://api.ledgerly.com/v1/invoices
200
```

A `404` for the non-canonical form is a *feature*: the client sees the mistake during integration
rather than depending on a redirect that behaves differently in every HTTP library.

## Design Patterns / Tradeoffs

### Flat vs nested resource URIs

**A. Flat, with relationships as attributes and query filters** (`/v1/invoices?customer_id=…`)

- *How it works:* every resource has one canonical top-level URI; relationships are fields.
- *Advantages:* URIs survive reparenting (merges, transfers, corrections); one place to implement
  permissions and caching per resource; shallow paths are easy for clients to construct; filters
  compose (`?customer_id=…&status=overdue`).
- *Disadvantages:* the parent–child relationship is less discoverable; clients must know which query
  parameter to use; no natural place to enforce "this child belongs to this parent".
- *Failure mode:* a client omits `customer_id` and pulls the whole tenant's invoices — so your
  pagination and limits must be sound (02.5).
- *Use when:* the child is independently meaningful, or the relationship can ever change. Default.
- *Do NOT use when:* the child has no identity outside its parent.

**B. Nested** (`/v1/invoices/{invoice_id}/lines/{line_id}`)

- *Advantages:* the hierarchy is self-documenting; the parent scopes authorisation naturally; ids can
  be unique per parent rather than globally.
- *Disadvantages:* URIs break if the relationship is ever reassigned; every request must validate
  parent–child consistency; deep paths are error-prone to build; caching keys multiply.
- *Failure mode:* the parent id in the path is not checked against the child's real parent — a BOLA
  bug that reads as a URI-design detail (16.8).
- *Use when:* the child cannot exist alone and cannot be reassigned. Invoice lines, order items,
  comment threads.
- *Do NOT use when:* you are expressing a filter. `/v1/customers/{id}/invoices` as the *only* way to
  list invoices forces every consumer through a hierarchy they may not care about.

**Recommendation:** flat by default, one level of nesting for genuinely dependent children, and query
parameters for every relationship that is really a filter.

### Identifier strategy

| | Sequential integer | Bare UUID | Prefixed opaque (✅) |
|---|---|---|---|
| Leaks volume | Yes — subtract two ids | No | No |
| Enumerable | Trivially | No | No |
| Readable in logs / tickets | Yes | Poorly | Yes — `inv_9f2c41` is unmistakable |
| Type-confusable | Yes: id `40218` could be anything | Yes | No — prefix disambiguates |
| URL length | Shortest | 36 chars | ~18 chars |
| Use when | Internal-only ids, never public | Public ids where readability does not matter | Public API identifiers |

The prefix is worth more than it looks. When a support ticket says "invoice 40218 is wrong", someone
has to work out whether that is an invoice id, a customer id or an invoice *number*. When it says
`inv_9f2c41`, there is nothing to work out — and a log search finds it immediately (15.1).

⚠️ **Invoice number ≠ invoice id.** The number (`INV-2026-0417`) is a business identifier: sequential
by legal requirement, per-tenant, and visible to the end customer. The id is a system identifier.
Conflating them puts a legally-mandated sequential counter in your URIs and gives you the enumeration
problem by another route. Keep both; expose both; use the id in URIs.

## Production Scenario

**Ledgerly, Thursday 13:20.** Three integration customers report intermittent `401 Unauthorized`
from the API within an hour of each other. Their credentials are valid, and most of their requests
work fine. One customer says it started after they upgraded their HTTP client library.

### Symptoms

- Sporadic `401`s from three of ~200 integration customers. Others are unaffected.
- `http_requests_total{status="401"}` up 4× — but the absolute number is small.
- The application logs show the `401`s arriving with **no `Authorization` header at all**, from
  clients that demonstrably send one on their successful requests:

```json
{"route":"/v1/invoices","status":401,"has_auth_header":false,"api_key":null,
 "user_agent":"python-httpx/0.27.0","referer":null,"tenant":null}
```

- Immediately preceding each `401`, the same client has a `307` on a near-identical path:

```json
{"route":"/v1/invoices/","status":307,"location":"http://api-internal:8000/v1/invoices",
 "user_agent":"python-httpx/0.27.0"}
```

### Diagnosis

1. **Alert.** The `4xx`-ratio alert fired at low severity. Authentication failures are normally a
   customer problem, which is why this sat for two hours before anyone looked closely.
2. **Metrics.** Segmenting `401`s by API key shows only three keys affected — so it is not a
   platform-wide auth change. Segmenting by user agent shows all three run recently-updated clients.
3. **Logs.** The `307`-then-`401` pair is the whole story once you see it, and it is visible only
   because the request log records the `location` header on redirects. The trailing slash on
   `/v1/invoices/` is the trigger.
4. **The decisive detail** is in that `Location` value: `http://api-internal:8000/v1/invoices`.
   The scheme is `http`, and the host is an internal service name. That URL is not reachable from the
   internet and is not the host the client authenticated to.
5. **Reproduce:**

```bash
$ curl -s -o /dev/null -D- -H "Authorization: Bearer $TOKEN" \
       https://api.ledgerly.com/v1/invoices/ | grep -i '^location'
location: http://api-internal:8000/v1/invoices
```

6. **Root cause confirmed** by reading the two interacting behaviours: FastAPI generated the redirect,
   and the proxy configuration decided what host it named.

### Root Cause

Two independently harmless things combined:

1. **FastAPI's `redirect_slashes=True` default.** A request to `/v1/invoices/` produces a `307` to
   the canonical `/v1/invoices`. Starlette builds that `Location` from the request's URL as the
   *application* sees it — which, behind a reverse proxy, is `http://api-internal:8000/...` unless
   the app is told the original scheme and host (01.10).
2. **A recent nginx change** dropped `proxy_set_header X-Forwarded-Host $host;` during a config
   tidy-up. Nothing broke, because nothing else used it — until a redirect needed to name the
   external host.

Clients that append a trailing slash then followed the redirect to an internal hostname. Well-behaved
HTTP libraries **strip the `Authorization` header when a redirect changes host or downgrades scheme**
— exactly as they should, since sending a bearer token to a different host would leak it. So the
request either failed to connect at all, or (where a client had its own resolution for that name in a
peered network) arrived with no credentials. Hence `401`, with no `Authorization` header, from
customers who were definitely sending one.

The three affected customers were the three whose newly-updated client libraries had begun following
`307`s automatically for `GET`. It looked like an authentication incident; it was a URI design
decision interacting with a proxy header.

### Fix

*Mitigation (12 minutes):* restore the proxy header, which makes the redirect at least point at the
right place:

```diff
  proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
+ proxy_set_header X-Forwarded-Host  $host;
  proxy_set_header Host              $host;
```

*Permanent fix — remove the redirect entirely:*

```diff
- api = APIRouter(prefix="/v1")
+ # One canonical URI form. A trailing slash is a 404, not a redirect: redirects
+ # behind a proxy depend on X-Forwarded-* being correct, and clients handle
+ # redirect+credentials inconsistently. See 02.1.
+ api = APIRouter(prefix="/v1", redirect_slashes=False)
```

This is the deeper fix because it removes a *class* of problem rather than one instance. A redirect
is a second request with different security properties, issued on the client's behalf, whose target
your application computes from headers it may not control. Not emitting one is strictly simpler.

*Customer communication:* the three customers were told to drop the trailing slash — a one-character
change — and the canonical form was documented explicitly in the API reference and the OpenAPI
`servers` block (02.4).

### Prevention

- **A canonical-URI contract test** that asserts no route redirects:

```python
# tests/contract/test_canonical_uris.py
import pytest
from ledgerly.main import app

PATHS = [r.path for r in app.routes if r.path.startswith("/v1")]

@pytest.mark.anyio
@pytest.mark.parametrize("path", PATHS)
async def test_trailing_slash_does_not_redirect(client, auth, path: str) -> None:
    response = await client.get(path.rstrip("/") + "/", headers=auth,
                                follow_redirects=False)
    assert response.status_code != 307, (
        f"{path} redirects on a trailing slash; behind a proxy the Location can name "
        "an internal host and clients will drop the Authorization header (02.1)"
    )

@pytest.mark.anyio
@pytest.mark.parametrize("path", PATHS)
def test_paths_are_lowercase_hyphenated_and_plural(path: str) -> None:
    assert path == path.lower(), f"{path} is not lowercase"
    assert "_" not in path.split("{")[0], f"{path} uses underscores; use hyphens"
```

- **Log the `Location` header on every `3xx`.** It cost nothing and it turned a two-hour puzzle into a
  ten-second diagnosis. Redirects are requests you issue on a client's behalf; you should be able to
  see where you sent them.
- **A URI review gate.** Because URIs are permanent, adding a public path is one of the few changes
  worth a mandatory second reviewer. The checklist: is it a noun; is it plural; is nesting justified
  by an unchangeable relationship; is the identifier opaque and prefixed; is there exactly one
  canonical form.
- **Assert the proxy header set as an invariant** (01.10) rather than relying on nobody tidying it
  away. Config that silently degrades a *different* subsystem is exactly what integration tests
  against the real proxy are for.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a client appends a trailing slash? | With `redirect_slashes=False`, an immediate `404` they can fix. With a redirect, a second request whose target depends on proxy headers. |
| ...a resource's parent changes? | Flat URIs survive; nested URIs break every stored link. This is the argument against nesting. |
| ...a client enumerates ids? | Opaque prefixed ids make it infeasible. Sequential ids turn any authorisation gap into bulk extraction (16.8). |
| ...the parent id in a nested path does not match the child? | You must return `404` — validating only the child id is a BOLA vulnerability. |
| ...you need to rename a resource? | You cannot, for existing clients. You add the new URI, serve both, and deprecate the old one over months (02.13). |
| ...two resources are genuinely the same thing? | Pick one canonical URI, return it in `Location` and in the body, and treat the other as a view. |
| ...a URI is cached by a CDN? | Path shape decides cache granularity. A filter in the path fragments the cache; a filter in the query keeps one resource with variants (01.4). |
| ...the URI contains a business identifier? | Invoice numbers are legally sequential; putting them in URIs reintroduces enumeration and volume leakage. |

## Common Pitfalls

**Verbs in paths.** `/v1/getInvoices`, `/v1/invoices/create`. The method already says what is
happening (01.2), and now you have two ways to express one operation. *Instead:* nouns plus methods;
action sub-resources only for genuine non-CRUD operations.

**Filters as path segments.** `/v1/invoices/overdue` looks tidy until you need overdue *and* in EUR
*and* for one customer. *Instead:* `/v1/invoices?status=overdue&currency=EUR` (02.6).

**Nesting to express ownership that can change.** The most expensive mistake in this notebook,
because it is invisible until the day someone asks for a merge or transfer feature. *Instead:* nest
only for genuinely dependent children.

**Sequential public ids.** Leaks volume, invites enumeration, and makes every authorisation bug
scalable. *Instead:* prefixed opaque ids; keep sequential keys internal.

**Trusting the parent id in a nested path.** Loading the child by its own id and ignoring the parent
segment is a cross-object authorisation bug. *Instead:* filter by both, always.

**Leaving `redirect_slashes` on.** A redirect behind a proxy names whatever host your app believes it
is on, and clients drop credentials across host changes. *Instead:* one canonical form, `404` for the
rest.

**Exposing the storage key in the URI.** Your primary-key strategy becomes a public API decision, and
changing it later (05.1) becomes a breaking change. *Instead:* a separate public identifier column.

**Modelling your database tables as resources.** A join table is not a resource; a resource is
whatever a *client* wants to address. *Instead:* design the URI space from the consumer's vocabulary,
then map it onto storage.

## How to Test This

- The canonical-URI and naming-convention tests above, parametrised over the whole route table.
- A nested-resource test asserting `/v1/invoices/{A}/lines/{line_of_B}` returns `404`.
- A test that the public identifier format matches `^(inv|cus|pay)_[0-9a-z]{14}$` for created
  resources, so an accidental switch to the storage key is caught immediately.
- A test that `Location` on `201` is the canonical item URI and that fetching it returns `200` (01.3).

## Interview Questions

1. *Explain.* Why is a URI harder to change than a database schema or a class name? — It is a public
   contract held by clients you cannot see or coordinate with.
2. *Design.* Invoices belong to customers. Would you use `/v1/customers/{id}/invoices/{id}` or
   `/v1/invoices/{id}`? — Flat, because ownership can change (merges) and nesting bakes it into the
   URI.
3. *Explain.* What does a sequential public id leak? — Volume between two observations, plus trivial
   enumeration.
4. *Debug this.* Three customers get `401`s with no `Authorization` header, and the requests are
   preceded by a `307`. — Redirect changed host/scheme; clients strip credentials. Check `Location`
   and the proxy's forwarded headers.
5. *Design.* Where do filtering and sorting go, and why not in the path? — Query string; path segments
   multiply resources and fragment caches.
6. *Explain.* When is nesting the right choice? — When the child cannot exist without that exact
   parent and can never be reassigned.
7. *Design.* You must rename `/v1/credit-notes` to `/v1/adjustments`. What is the plan? — Add the new
   URI, serve both, measure usage per client, deprecate with `Sunset` headers (02.13); never a
   cutover.

## Key Takeaways

- Model **things, not operations**. The method carries the verb; the URI carries the noun.
- URIs are the one part of your API you cannot refactor. Treat adding a public path as a decision
  requiring a second reviewer.
- **Nest only when the relationship can never change.** Invoice lines yes; invoices under customers
  no. A nested URI encodes an ownership claim you may later need to move.
- Path = identity, query = everything else. A filter in a path is a resource you did not mean to
  create.
- Use **prefixed opaque identifiers** in public URIs, separate from your storage key and separate
  from business numbers like invoice numbers.
- Have exactly one canonical URI form. Turn off slash redirects: a redirect is a second request whose
  target your app computes from proxy headers, and clients drop credentials across host changes.
- Validate the whole path, not just the last segment. An unchecked parent id is an authorisation bug.
