## Concept

### Plain-English Explanation

A client sends `POST /v1/invoices`. Three seconds later its socket times out. What happened?

It might be that the request never arrived. It might be that the invoice was created and the response
was lost on the way back. It might be that the invoice was created, the response was sent, and the
client's own network dropped it. From the client's side these are **indistinguishable** — and they
demand opposite actions. Retry, and you may create a duplicate invoice. Do not retry, and you may
have silently lost the customer's data.

There is no way to remove this ambiguity. Networks lose packets; processes die between a database
commit and a response write. What you *can* do is make the retry safe: let the client attach a label
to its request, and promise that a request bearing a label you have already processed will return the
original outcome rather than doing the work again.

That label is an idempotency key. It converts an unanswerable question — *did it happen?* — into one
the server can answer authoritatively.

### Technical Explanation

**The ambiguity, precisely:**

```text
client                          network                          server
  │  POST /v1/invoices  ─────────────────────────────▶  invoice created, COMMITTED
  │                                                      │
  │  ◀────────────────  201 Created  ──────X lost        │
  │                                                      │
  │  [3s timeout]                                        │
  │                                                      │
  │  ??? did it happen ???        ← the client cannot distinguish this from
  │                                 "the request never arrived"
```

**An idempotency key** is a client-generated unique token (a UUID, per logical operation) sent in a
header. The server records the key together with the outcome, and a repeat of the same key returns the
recorded outcome without re-executing.

**Four things the naive implementation gets wrong**, each of which is a real production failure:

1. **Scope.** A key stored globally collides across tenants and API keys. Keys must be scoped to
   `(tenant, api_key, key)` at minimum — the incident below.
2. **Request fingerprinting.** If the same key arrives with a *different* body, the client has made a
   mistake (reused a key, or a bug regenerated the body). Replaying the old response hides the bug and
   may silently drop a real operation. The correct answer is `422`.
3. **Atomicity.** The key's *completion* — the recorded outcome — and the work must commit in
   **one transaction**. Separate transactions mean a crash can leave a key marked done with nothing
   created, so every retry returns "already processed" for an invoice that does not exist — silent
   data loss. (The *claim* is different: it must commit **before** the work, on its own — see below.)
4. **The in-flight state.** Claiming a key, then crashing, leaves a record that is neither complete nor
   available. Without an expiry, that key is poisoned forever and the client can never succeed.

**The state machine:**

```text
                     request with key K arrives
                                │
                  INSERT (tenant, api_key, K, fingerprint, 'in_flight')
                                │ ON CONFLICT DO NOTHING
                ┌───────────────┴───────────────┐
         inserted (we own it)            not inserted (someone has it)
                │                                │
                │                        SELECT the existing row
                │                                │
                │              ┌─────────────────┼──────────────────┐
                │       fingerprint          state =            state = 'in_flight'
                │        mismatch           'completed'          and fresh
                │              │                 │                    │
                │            422              replay the           409 + Retry-After
                │      "key reused with     stored response       "still processing"
                │       a different body"    (status + body)           │
                │                                                      │
       do the work AND write the                        state = 'in_flight' but claimed_at
       response into the SAME transaction               older than the lease → RE-CLAIM
                │                                       (the previous holder crashed)
         state = 'completed'
```

The two branches on the right are the ones that separate a working implementation from a
demonstration.

### Mental Model

> An idempotency key is **a name the client gives to an intention**, not to a request. "The invoice
> for purchase order 88213" is one intention; the client may attempt it five times over a flaky
> network, and all five attempts carry the same name. Your job is to guarantee that one name produces
> at most one effect — and to return the *same answer* every time, so the client can stop asking.

## How It Works

**Storage: two layers with different jobs.**

```text
Redis  ── fast path ──▶  most repeats are answered in <1 ms, no database round trip
                         ⚠️ NOT the guarantee — Redis can lose data (10.16), and a
                            cache miss must be safe

PostgreSQL ── the guarantee ──▶  UNIQUE (tenant_id, api_key_id, key)
                                 the constraint is what actually prevents duplicates,
                                 and it holds even if Redis is empty, down, or lying
```

This split matters. A common mistake is treating Redis as the guarantee, which makes duplicate
prevention only as durable as a cache (01.6's lesson: a cache is an optimisation, the constraint is
the guarantee).

**The table:**

```sql
CREATE TABLE idempotency_keys (
    tenant_id     uuid        NOT NULL,
    api_key_id    text        NOT NULL,
    key           text        NOT NULL,
    fingerprint   text        NOT NULL,     -- hash of method + path + body
    state         text        NOT NULL,     -- 'in_flight' | 'completed'
    claimed_at    timestamptz NOT NULL DEFAULT now(),
    response_status  integer,
    response_body    jsonb,
    resource_id      text,
    expires_at    timestamptz NOT NULL,
    PRIMARY KEY (tenant_id, api_key_id, key)   -- ← the scope, and the guarantee
);
CREATE INDEX ix_idempotency_expires ON idempotency_keys (expires_at);
```

The primary key **is** the design. `(tenant_id, api_key_id, key)` means one tenant's `invoice-001`
cannot collide with another's, and one customer's key cannot be guessed or reused by another.

**Key lifetime.** 24 hours is the common choice (Stripe uses this); Ledgerly uses 72 hours because
customer batch jobs sometimes retry the next business day. Too short and a legitimate retry duplicates;
too long and the table grows and clients accumulate stale expectations. The number should exceed your
longest plausible client retry window, and it belongs in the documentation.

## Code Example

The core, with all four failure modes handled:

```python
# ledgerly/idempotency/store.py
import hashlib, json
from dataclasses import dataclass
from datetime import datetime, timedelta, UTC

from sqlalchemy import select, text
from sqlalchemy.dialects.postgresql import insert
from sqlalchemy.ext.asyncio import AsyncSession

from ledgerly.models import IdempotencyKey

KEY_TTL = timedelta(hours=72)
CLAIM_LEASE = timedelta(seconds=90)     # > the longest request; a crashed holder is re-claimable

class KeyReusedWithDifferentPayload(Exception): ...
class RequestInFlight(Exception): ...

@dataclass(frozen=True, slots=True)
class Replay:
    status: int
    body: dict

def fingerprint(method: str, path: str, body: dict) -> str:
    """Same key + same request = replay. Same key + DIFFERENT request = client bug,
    and replaying the old response would silently swallow a real operation."""
    canonical = json.dumps({"m": method, "p": path, "b": body},
                           sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode()).hexdigest()
```

Claiming the key — one statement, no check-then-act race:

```python
# ledgerly/idempotency/store.py (continued)
async def claim(
    session: AsyncSession, *, tenant_id: str, api_key_id: str, key: str, fp: str,
) -> Replay | None:
    """Returns None if we own the key and must do the work; a Replay if the
    operation already completed. Raises if the key is busy or misused.

    ⚠️ INSERT ... ON CONFLICT is atomic. A SELECT-then-INSERT would let two
    concurrent replicas both believe they own the key (01.6, 04.5)."""
    now = datetime.now(UTC)
    statement = (
        insert(IdempotencyKey)
        .values(tenant_id=tenant_id, api_key_id=api_key_id, key=key, fingerprint=fp,
                state="in_flight", claimed_at=now, expires_at=now + KEY_TTL)
        .on_conflict_do_update(
            index_elements=["tenant_id", "api_key_id", "key"],
            # Re-claim only if the previous holder's lease has expired (it crashed).
            set_={"claimed_at": now, "fingerprint": fp},
            where=(IdempotencyKey.state == "in_flight")
                  & (IdempotencyKey.claimed_at < now - CLAIM_LEASE),
        )
        .returning(IdempotencyKey.state, IdempotencyKey.claimed_at)
    )
    if (await session.execute(statement)).first() is not None:
        return None                                  # we own it — proceed with the work

    existing = (await session.execute(
        select(IdempotencyKey).where(
            IdempotencyKey.tenant_id == tenant_id,
            IdempotencyKey.api_key_id == api_key_id,
            IdempotencyKey.key == key,
        )
    )).scalar_one()

    if existing.fingerprint != fp:
        raise KeyReusedWithDifferentPayload(key)      # → 422
    if existing.state == "completed":
        return Replay(existing.response_status, existing.response_body)
    raise RequestInFlight(key)                        # → 409 + Retry-After (01.3)
```

The service, where the two-phase shape lives. The claim commits **first, on its own** — that is
what makes the in-flight state visible to concurrent duplicates and durable across a crash:

```python
# ledgerly/services/invoices.py (excerpt)
async def create_invoice_idempotent(
    self, tenant: TenantId, api_key_id: str, key: str, body: InvoiceCreate,
) -> tuple[int, dict, bool]:                 # (status, body, was_replay)
    fp = fingerprint("POST", "/v1/invoices", body.model_dump(mode="json"))

    # Phase 1 — claim, committed on its own BEFORE the work starts. A concurrent
    # duplicate must be able to SEE the in_flight row; inside the work's open
    # transaction it is invisible, and the duplicate blocks on the row lock
    # instead of getting its fast 409.
    async with self._session.begin():
        replay = await claim(self._session, tenant_id=tenant, api_key_id=api_key_id,
                             key=key, fp=fp)
    if replay is not None:
        return replay.status, replay.body, True

    # Phase 2 — the work, plus the claim row's completion, in ONE transaction.
    async with self._session.begin():
        invoice = await self._repo.insert(tenant, body)
        payload = InvoiceOut.model_validate(invoice).model_dump(mode="json")

        # ⚠️ Same transaction as the invoice INSERT. In a separate transaction, a
        # crash between the two commits either fabricates a result (key completed,
        # no invoice) or loses one (invoice committed, key still in_flight).
        await mark_completed(self._session, tenant_id=tenant, api_key_id=api_key_id,
                             key=key, status=201, body=payload, resource_id=invoice.id)
    return 201, payload, False
```

Two commits, each load-bearing. The first makes the claim *visible and durable*: until it commits,
a concurrent duplicate cannot see the `in_flight` state (it blocks on the uncommitted row's lock
rather than getting `409` + `Retry-After`), and a crash rolls the claim back entirely — which
silently turns the lease/re-claim branch into dead code. A crash *between* the two transactions
leaves a committed `in_flight` row, exactly what the lease exists for: retries get `409` until
`CLAIM_LEASE` passes, then re-claim and re-run work that never committed. The second transaction is
the atomicity requirement from the concept section — and note the edge it closes: because the
completion update rides **in** the work's transaction, there is no instant at which the invoice
exists but the stored response does not, so a crash cannot strand a committed invoice behind a key
that still says `in_flight`.

And the route, which turns the exceptions into the statuses from 01.3:

```python
# ledgerly/routers/invoices.py (excerpt)
@router.post("", status_code=201, response_model=InvoiceOut, name="createInvoice")
async def create_invoice(
    body: InvoiceCreate, response: Response, svc: Service, tenant: Tenant,
    api_key: ApiKeyId,
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key",
                                           min_length=8, max_length=255)],
) -> InvoiceOut:
    """The header is REQUIRED — no default. Making it optional means the common
    path is the unsafe one, and clients only discover this after a duplicate."""
    try:
        status_code, payload, replayed = await svc.create_invoice_idempotent(
            tenant, api_key, idempotency_key, body)
    except KeyReusedWithDifferentPayload:
        raise HTTPException(422, "This Idempotency-Key was used with a different request body.")
    except RequestInFlight:
        # Headers for an error response travel ON the exception, not on `response`.
        raise HTTPException(409, "A request with this Idempotency-Key is still processing.",
                            headers={"Retry-After": "2"})
    response.status_code = status_code
    # Tells the client this was a replay, which is invaluable when debugging their retries.
    response.headers["Idempotent-Replay"] = "true" if replayed else "false"
    return InvoiceOut.model_validate(payload)
```

⚠️ Note where `Retry-After` travels: `HTTPException(..., headers={...})`. FastAPI builds the error
response from the exception alone — anything set on the injected `Response` before a `raise` is
silently dropped, a trap that recurs in real codebases because the success path teaches the
`response.headers[...]` habit.

## Design Patterns / Tradeoffs

### Natural uniqueness constraint vs an idempotency key

**A. Natural uniqueness** — a unique index on domain data (`(tenant_id, invoice_number)`)

- *How it works:* the domain already forbids duplicates; a retry violates the constraint and you
  translate the violation into "return the existing row".
- *Advantages:* no extra table, no TTL, no client cooperation, correct forever rather than for 72
  hours; enforced by the database under any concurrency.
- *Disadvantages:* only works when the domain genuinely has a unique key; the client must supply it.
- *Use when:* the operation has a natural identity — an invoice number, a payment reference, an
  external system's order id.
- *Do NOT use when:* two legitimately identical requests can both be valid (two identical £50 payments
  in one day are two payments).

**B. Client-supplied idempotency key**

- *Advantages:* works for any operation, including those with no natural key; the client controls the
  boundary of "one intention"; standard practice, so integrators already understand it.
- *Disadvantages:* a table to store and expire; the guarantee lasts only as long as the TTL; depends on
  clients generating keys correctly.
- *Use when:* creates and actions with external side effects — payments, sends, refunds.

**C. Both** (✅ recommended)

Ledgerly uses natural uniqueness where it exists *and* idempotency keys on every unsafe endpoint. They
protect against different failures: the constraint protects against your own bugs and concurrent
replicas; the key protects against client retries and gives the client back a coherent response
rather than a `409`.

### Where the guarantee lives

| | Redis only | PostgreSQL only | Redis + PostgreSQL (✅) |
|---|---|---|---|
| Speed | Sub-millisecond | ~1–3 ms | Fast path in Redis |
| Durability | ❌ eviction and failover lose keys (10.16) | ✅ | ✅ constraint is authoritative |
| Atomic with the work | ❌ different system | ✅ same transaction | ✅ |
| Failure mode | A Redis restart permits duplicates | Extra load on the primary | Redis miss falls through — safe |
| Use when | Never for financial effects | Small scale, simple | Default |

The rule this table encodes: **the cache may be wrong; the constraint may not.** A Redis miss must fall
through to the database and still be correct.

### Server-generated vs client-generated keys

Client-generated is standard, and it must be. Only the client knows which of its attempts are the same
intention — the server sees two TCP connections and cannot tell whether they represent one logical
operation or two. A server-generated key would have to be derived from the request content, which
turns two legitimately identical operations into one.

⚠️ Document that keys must be **unique per intention and random** (UUIDv4). Human-readable keys like
`invoice-001` are how the incident below happened.

## Production Scenario

**Ledgerly, Tuesday 16:40.** A support ticket from a mid-size customer, marked urgent:

> *"We created an invoice through your API and got back an invoice for a company we've never heard of.
> The response has a different customer name, a different amount, and an invoice number that isn't in
> our sequence. Whose invoice is this?"*

### Symptoms

- A `POST /v1/invoices` from tenant B returned `201` with an invoice belonging to **tenant A**,
  including tenant A's customer name and amount.
- The invoice tenant B intended to create **was never created**. They have a `201` and no invoice.
- Nine such reports arrive within two hours, all from customers whose integrations were built by the
  same consultancy.
- **Every metric is healthy.** `201` responses, normal latency, no errors. The API returned success for
  every request.
- Reviewing logs shows the same `Idempotency-Key` values recurring across *different* tenants:
  `invoice-001`, `batch-1`, `test`, `2026-08-24-1`.

### Diagnosis

1. **Alert.** None. Every request succeeded quickly. As with 01.4's cache leak, a cross-tenant data
   exposure looks exactly like normal successful traffic.
2. **Reproduce**, and it is immediate:

```bash
$ curl -s -X POST /v1/invoices -H "$TENANT_A_AUTH" -H 'Idempotency-Key: invoice-001' \
       -d '{"customer_id":"cus_A","amount_cents":49900}' | jq -r '.id, .customer_id'
inv_9f2c41
cus_A

$ curl -s -X POST /v1/invoices -H "$TENANT_B_AUTH" -H 'Idempotency-Key: invoice-001' \
       -d '{"customer_id":"cus_B","amount_cents":120000}' | jq -r '.id, .customer_id'
inv_9f2c41          # ⚠️ tenant A's invoice
cus_A               # ⚠️ tenant A's customer
```

   Two commands, and the root cause is established.

3. **Read the schema.** The idempotency table's primary key is `(key)`. Not `(tenant_id, key)`. Not
   `(tenant_id, api_key_id, key)`. Just the client-supplied string:

```sql
\d idempotency_keys
       Column      |  Type   | Nullable
-------------------+---------+----------
 key               | text    | not null      ← PRIMARY KEY
 response_status   | integer |
 response_body     | jsonb   |
```

4. **Understand why it took eighteen months to surface.** The keys most clients generate are UUIDv4s,
   which never collide. The nine affected customers all used the same integration consultancy, whose
   template code generated sequential keys of the form `invoice-{n}`. Collisions required two tenants
   to independently choose the same human-readable string — rare, until several customers shared a
   code template.
5. **Bound the exposure.** Because `response_body` is stored, the table *is* the evidence: a query for
   keys whose stored `resource_id` belongs to a different tenant than the requester enumerates every
   affected pair exactly.

### Root Cause

The idempotency key was treated as globally unique because clients were assumed to send UUIDs. The
table's primary key was the raw client string, so the first tenant to use `invoice-001` owned it for 24
hours, and every other tenant sending that key received tenant A's stored response — including tenant
A's invoice data.

Two failures compounded:

1. **Missing scope.** A client-supplied identifier was used as a global key. Any value that arrives from
   a client is in the client's namespace, never yours — and there are as many namespaces as there are
   tenants.
2. **No fingerprint check.** The stored fingerprint field did not exist, so a completely different
   request body replayed a completely unrelated response. Fingerprinting would have turned a data leak
   into a `422`, which is a bad day for one integration rather than a breach.

The stored response also meant tenant B's genuine invoice was **never created**: the code saw a
completed key and returned early. Tenant B had a `201`, no invoice, and no way to know.

### Fix

*Mitigation (25 minutes):*

1. Truncate `idempotency_keys`. Every entry was at most 24 hours old, and losing them makes duplicates
   *possible* for one retry window — a far smaller harm than continuing to serve cross-tenant data.
2. Deploy the scoped primary key:

```python
# alembic/versions/2026_08_25_scope_idempotency_keys.py
def upgrade() -> None:
    op.execute("TRUNCATE TABLE idempotency_keys")          # entries are ≤24h old
    op.drop_constraint("idempotency_keys_pkey", "idempotency_keys", type_="primary")
    op.add_column("idempotency_keys", sa.Column("tenant_id", postgresql.UUID(), nullable=False))
    op.add_column("idempotency_keys", sa.Column("api_key_id", sa.Text(), nullable=False))
    op.add_column("idempotency_keys", sa.Column("fingerprint", sa.Text(), nullable=False))
    op.create_primary_key("idempotency_keys_pkey", "idempotency_keys",
                          ["tenant_id", "api_key_id", "key"])
```

*Permanent fix:*

1. **Scope** to `(tenant_id, api_key_id, key)` — a key is meaningful only within the credential that
   issued it.
2. **Fingerprinting**, so the same key with a different body is `422` rather than a wrong replay. This
   is the defence-in-depth layer: even with correct scoping, a client reusing a key within its own
   tenant now gets an error instead of a stale invoice.
3. **Documentation and SDK change**: keys must be UUIDv4. Ledgerly's SDKs now generate one
   automatically per call, so the correct behaviour is the default and a client has to work to get it
   wrong.
4. **The in-flight lease** described earlier, added at the same time — the review that produced the fix
   found that a crash mid-request left a key permanently unusable.

*Customer remediation:* the nine affected tenants were given the list of invoices they believed they
had created but had not, and told which of their data had been visible to whom. The consultancy was
contacted directly so their template could be fixed for every client they had built for.

### Prevention

- **A cross-tenant idempotency test**, which is one of the highest-value ten lines in the suite:

```python
# tests/security/test_idempotency_is_tenant_scoped.py
@pytest.mark.anyio
async def test_same_key_in_two_tenants_creates_two_invoices(client, tenant_a, tenant_b):
    key = {"Idempotency-Key": "invoice-001"}     # deliberately collision-prone
    a = await client.post("/v1/invoices", json=INVOICE_A, headers={**tenant_a, **key})
    b = await client.post("/v1/invoices", json=INVOICE_B, headers={**tenant_b, **key})

    assert a.status_code == b.status_code == 201
    assert a.json()["id"] != b.json()["id"], "idempotency key leaked across tenants"
    assert b.json()["customer_id"] == INVOICE_B["customer_id"]

@pytest.mark.anyio
async def test_same_key_different_body_is_rejected(client, tenant_a):
    key = {"Idempotency-Key": str(uuid4())}
    assert (await client.post("/v1/invoices", json=INVOICE_A,
                              headers={**tenant_a, **key})).status_code == 201
    assert (await client.post("/v1/invoices", json=INVOICE_B,
                              headers={**tenant_a, **key})).status_code == 422
```

- **A schema review rule: every table holding client-supplied identifiers must include `tenant_id` in
  its key.** This generalises well beyond idempotency — it is the same rule that prevents the
  cross-tenant bugs in 05.4, and it is checkable by a migration-linting test.
- **A crash test**, since the in-flight branch is untested in most implementations: kill the process
  between claim and commit, then retry with the same key, and assert the retry eventually succeeds
  rather than being locked out.
- **Alert on key collisions.** A counter incremented when `claim` finds an existing key with a
  *different* fingerprint. In a healthy system this is near-zero; a rise means a client is generating
  keys badly, which is worth telling them before it becomes a ticket.
- **Ship key generation in the SDK.** The most reliable way to make clients use UUIDs is to never ask
  them to.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the client times out and retries? | The key replays the stored response. This is the entire purpose. |
| ...two replicas process the same key simultaneously? | `INSERT … ON CONFLICT` means one wins; the other gets `409` + `Retry-After`. A `SELECT`-then-`INSERT` would let both proceed (04.5). |
| ...the process crashes after claiming the key? | The lease expires and the key becomes re-claimable. Without a lease, the client is locked out permanently. |
| ...the process crashes after committing but before responding? | The key is `completed`; the retry replays the stored response. This is the case the design exists for. |
| ...the completion record and the work are in different transactions? | A crash between them creates a key marked done with no resource — every retry then reports success for something that does not exist. |
| ...the same key arrives with a different body? | `422`. Replaying would silently discard a genuine operation. |
| ...Redis is down? | Fall through to PostgreSQL. Slower, still correct — the constraint is the guarantee, not the cache. |
| ...two tenants use the same key string? | Nothing, if the key is scoped. A cross-tenant leak, if it is not. |
| ...a key is reused after its TTL? | It is a new operation and will execute. Document the window; make it longer than any plausible client retry. |
| ...a client never sends a key? | Make the header required on unsafe endpoints. Optional means the default path is the unsafe one. |

## Common Pitfalls

**Global key scope.** The incident above. Client-supplied strings live in the client's namespace.
*Instead:* `(tenant_id, api_key_id, key)`.

**No request fingerprint.** Replays an unrelated response and swallows a real operation. *Instead:*
hash method, path and body; `422` on mismatch.

**Separate transactions for the completion and the work.** A crash between them produces silent data
loss that retries cannot repair. *Instead:* one transaction for work + completion — the *claim* alone
commits first, so concurrent duplicates can see it.

**`SELECT` then `INSERT`.** Two concurrent replicas both find no row and both proceed (01.6, 04.5).
*Instead:* `INSERT … ON CONFLICT DO NOTHING` and branch on whether you inserted.

**No in-flight lease.** A crashed request poisons the key forever. *Instead:* `claimed_at` plus a lease
longer than your slowest request.

**Redis as the guarantee.** Eviction, restart or failover permits duplicates (10.16). *Instead:* Redis
as a fast path over a database constraint.

**Optional idempotency headers on unsafe endpoints.** The default path becomes the unsafe one and
clients discover it via a duplicate charge. *Instead:* required, with SDKs generating keys.

**Storing responses forever.** The table grows without bound. *Instead:* `expires_at` with a reaper job
(11.8), and an index to make the sweep cheap.

**Storing the response body without thinking about PII.** You have created a second copy of customer
data with a different retention rule. *Instead:* store the minimum needed to reconstruct the response,
and apply the same deletion policy (16.14).

## How to Test This

- The cross-tenant and fingerprint tests above.
- A concurrency test: fire 20 simultaneous requests with the same key and assert exactly one `201`,
  nineteen `409`/replays, and one row created (this must run against a real database — 13.12).
- A crash test that kills the worker between claim and commit, then retries and asserts eventual
  success.
- A TTL test: expire a key, resubmit, assert a second resource is created (proving the documented
  window is real).

## Interview Questions

1. *Explain.* Why can a client not tell whether a timed-out `POST` succeeded? — The failure can occur
   before or after the commit; both look identical from the client.
2. *Design.* Implement idempotency for `POST /v1/payments`. Walk through the states. — Scoped key,
   fingerprint, `INSERT … ON CONFLICT`, in-flight lease, same-transaction completion, replay.
3. *Explain.* Why must the completion record and the work share a transaction — and why must the
   claim *not*? — A crash between completion and work leaves a completed key with no resource; an
   uncommitted claim is invisible to concurrent duplicates and vanishes on a crash.
4. *Debug this.* A customer receives another customer's invoice from an endpoint that returns `201`.
   — Idempotency key not scoped to tenant; reproduce with two tenants and the same key.
5. *Explain.* Same key, different body — what do you return and why? — `422`; replaying would silently
   drop a genuine operation.
6. *Explain.* Why is Redis alone insufficient? — It can evict or lose keys; the guarantee must be a
   durable constraint.
7. *Design.* When would you prefer a natural uniqueness constraint? — When the domain has a real unique
   key; it is permanent and needs no client cooperation.

## Key Takeaways

- The ambiguity is unavoidable: a timed-out client **cannot** know whether its write happened. Keys
  make the retry safe rather than removing the ambiguity.
- A key names an **intention**, not a request. Only the client can decide which attempts are the same
  intention, so keys must be client-generated.
- **Scope keys to `(tenant, api_key, key)`.** A client-supplied string is in the client's namespace;
  treating it as global is a cross-tenant data leak.
- **Fingerprint the request.** Same key with a different body is a client bug and must be `422`, never
  a replay.
- Commit the **claim first, on its own**; the completion record and the work then **commit in one
  transaction**, or a crash produces silent data loss.
- Handle the in-flight state with a lease, or a crashed request locks the client out permanently.
- Redis is the fast path; a **database constraint is the guarantee**. A cache miss must still be
  correct.
- Require the header on unsafe endpoints and generate keys in your SDKs, so the safe path is the
  default one.
