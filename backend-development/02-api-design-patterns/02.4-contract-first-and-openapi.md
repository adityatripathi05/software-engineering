# 02.4 Contract-First Design and OpenAPI

> **Prerequisites:** 02.1 (resource modelling), 02.3 (what breaks a client) · modern-python 18.4 (pydantic validation)
> **What you'll learn:**
> - Treat the OpenAPI document as a released artefact rather than a by-product of running the app
> - Use `response_model` as a **security boundary**, not as documentation
> - Keep `operationId` stable, because it becomes the method name in every generated SDK
> - Choose between contract-first and code-first on team structure, not preference
> **Level:** Intermediate

---

## Concept

### Plain-English Explanation

Your API's contract is what clients build against. If it says an invoice has six fields, a client
generates a class with six fields and writes code that assumes them. The contract is the product;
the implementation is how you honour it.

FastAPI is unusually good here — it derives an OpenAPI document from your type hints automatically,
so the documentation is generated from the same code that runs. That is a genuine advantage over
hand-written docs, which drift within weeks.

But "generated from the code" has a hidden condition: **it documents what you declared, not what you
return.** If a route has no declared response type, FastAPI documents nothing and serialises
whatever object your function produced. The document says one thing; the wire says another; and the
gap is where internal fields escape. Getting this right is one line per route, and forgetting it is
the incident below.

### Technical Explanation

**OpenAPI** is a JSON/YAML description of an HTTP API: paths, operations, parameters, request and
response schemas, security schemes, and examples. Its value is that machines consume it —
documentation sites, SDK generators, mock servers, contract-test tooling, API gateways, and
compatibility checkers (02.3) all read the same document.

**Two ways to get one:**

```text
CODE-FIRST (FastAPI's default)          CONTRACT-FIRST
  Python types                            openapi.yaml  ← hand-written, reviewed
      │ FastAPI derives                       │ generator
      ▼                                       ▼
  openapi.json ──▶ SDKs, docs, mocks      server stubs + client SDKs + docs
                                              │
  ✓ never drifts from the code            ✓ the contract is designed, not emitted
  ✗ the contract is whatever              ✓ frontend and backend start in parallel
    the code happened to do               ✗ can drift from the implementation
  ✗ easy to ship an undeclared route      ✗ heavier tooling, more ceremony
```

**`response_model` does two distinct jobs**, and conflating them is the root of this notebook's
incident:

1. **Documentation** — it is what appears in the OpenAPI schema.
2. **Serialisation filtering** — FastAPI validates your return value against the model and emits
   **only the model's fields**. Anything else is dropped.

Job 2 is a security control. Without a declared response type, FastAPI serialises the object you
returned — every attribute of it — and documents nothing. A handler that returns an ORM row therefore
returns the whole row.

⚠️ In modern FastAPI, a **return type annotation** serves the same purpose:
`async def get_customer(...) -> CustomerOut:` filters exactly as `response_model=CustomerOut` does.
Either is fine. What is not fine is neither — and `-> dict`, `-> Any`, or no annotation at all are
all "neither".

**`operationId`** deserves attention disproportionate to its size. SDK generators turn it into the
method name: `operationId: "getInvoice"` becomes `client.getInvoice(...)` in every generated client.
FastAPI's default derives it from the function name plus the path plus the method
(`get_invoice_v1_invoices__invoice_id__get`), which is both ugly and **unstable** — renaming a Python
function silently renames a public SDK method, which is a breaking change (02.3) introduced by a
refactor.

**Other contract elements that carry real weight:** `security` schemes (so generated clients know how
to authenticate), `examples` (which become the tests people copy), `deprecated: true` (which drives
IDE warnings — 02.13), and `servers` (which pins the canonical base URL — 02.1).

### Mental Model

> The OpenAPI document is a **release artefact with the same status as a package version**: pinned,
> diffed, reviewed, and published. If your code can return something the document does not describe,
> the document is fiction — and the difference is not a documentation bug, it is whatever leaked.

## How It Works

Ledgerly is code-first with contract-first *discipline* bolted on. The pipeline:

```text
  Pydantic models + route annotations
             │
             │  app.openapi()
             ▼
      openapi.json  ──────────┬──────────────────────────────────────────┐
             │                │                                          │
             │ committed      │ oasdiff breaking vs last release (02.3)  │
             │ to the repo    │ ──▶ FAILS CI on a breaking change        │
             ▼                │                                          ▼
   reviewed in the PR         │                              SDK generation (Python,
   like any other artefact    │                              TS, Java, Go) on release
                              ▼
                    contract tests: every response
                    validated against the schema (13.4)
```

The committed `openapi.json` is what makes this work. Because it is in the repository, a change to
the public contract shows up **as a diff in the pull request**, next to the code that caused it. A
reviewer sees `- "status": {"enum": [...]}` in the same review as the Python change. Without the
committed artefact, contract changes are invisible until a customer finds them.

**Where the filtering happens** is worth seeing precisely, because it explains the incident:

```text
handler returns  ──▶  FastAPI validates against    ──▶  serialised response
                      the declared response type

  Customer ORM row          CustomerOut                  {"id", "name", "email",
  ├─ id                     ├─ id                         "country", "created_at"}
  ├─ name                   ├─ name
  ├─ email                  ├─ email                     ✅ 5 fields
  ├─ country                ├─ country
  ├─ created_at             └─ created_at
  ├─ internal_risk_score  ─────────────────────────X     dropped
  ├─ acquisition_channel  ─────────────────────────X     dropped
  ├─ crm_notes            ─────────────────────────X     dropped
  └─ stripe_customer_id   ─────────────────────────X     dropped

  ...with NO declared response type, every one of those nine fields is serialised
  and none of them appear in the OpenAPI document.
```

## Code Example

Stable operation ids, generated from route metadata rather than function names, so refactoring
Python cannot rename a public SDK method:

```python
# ledgerly/openapi.py
from fastapi import FastAPI
from fastapi.routing import APIRoute

def use_stable_operation_ids(app: FastAPI) -> None:
    """operationId becomes the method name in every generated SDK, so it is part
    of the public contract. Deriving it from the route NAME (which we set
    explicitly) rather than the function name means a Python refactor cannot
    rename `client.getInvoice()` for every customer (02.3)."""
    seen: set[str] = set()
    for route in app.routes:
        if isinstance(route, APIRoute):
            if route.name in seen:
                raise RuntimeError(f"Duplicate operationId {route.name!r}: "
                                   "SDK generation would silently drop a method.")
            seen.add(route.name)
            route.operation_id = route.name
```

```python
# ledgerly/routers/customers.py
@router.get(
    "/{customer_id}",
    response_model=CustomerOut,     # ← contract AND serialisation filter
    name="getCustomer",             # ← the stable operationId
    summary="Retrieve a customer",
    responses={
        404: {"model": ProblemDetails, "description": "No such customer in this tenant"},
        429: {"model": ProblemDetails, "description": "Rate limit exceeded"},
    },
)
async def get_customer(customer_id: CustomerId, svc: Service,
                       tenant: Tenant) -> CustomerOut:
    return await svc.get_customer(tenant, customer_id)
```

The schema itself declares what leaves the building. On the output path the protection is the
declared field list itself: with `from_attributes=True`, validation reads *only* the declared
fields, so an undeclared ORM attribute is never touched. (`extra="forbid"` does its real work on
*input* models, where an unknown field must be rejected — 02.7):

```python
# ledgerly/schemas/customer.py
from datetime import datetime
from pydantic import BaseModel, ConfigDict, EmailStr, Field

class CustomerOut(BaseModel):
    """The PUBLIC representation. Deliberately not the ORM model (07.6): the set
    of fields a client may see is a decision, not a consequence of the schema."""
    model_config = ConfigDict(from_attributes=True, extra="forbid")

    id: CustomerId = Field(examples=["cus_8f21ac4d1e77b3"])
    name: str = Field(examples=["Nordwind Logistik GmbH"])
    email: EmailStr
    country: str = Field(min_length=2, max_length=2, examples=["DE"])
    created_at: datetime
```

Pinning the document as an artefact, so a contract change is a reviewable diff:

```python
# scripts/export_openapi.py — run in CI; the job fails if the file is not up to date.
import json, pathlib
from ledgerly.main import app

target = pathlib.Path("openapi.json")
current = json.dumps(app.openapi(), indent=2, sort_keys=True) + "\n"
if target.read_text(encoding="utf-8") != current:
    target.write_text(current, encoding="utf-8")
    raise SystemExit(
        "openapi.json was stale and has been regenerated. Commit it: a change to the "
        "public contract must be visible in the pull request that causes it."
    )
```

And the test that would have prevented the incident — one assertion over the whole route table:

```python
# tests/contract/test_every_route_declares_a_response.py
import pytest
from fastapi.routing import APIRoute
from ledgerly.main import app

ROUTES = [r for r in app.routes if isinstance(r, APIRoute) and r.include_in_schema]

@pytest.mark.parametrize("route", ROUTES, ids=lambda r: f"{list(r.methods)[0]} {r.path}")
def test_route_declares_a_filtered_response_type(route: APIRoute) -> None:
    declared = route.response_model
    assert declared is not None, (
        f"{route.path} has no response_model or return annotation: FastAPI will "
        "serialise whatever object the handler returns, including internal fields, "
        "and will document none of them (02.4)"
    )
    assert declared not in (dict, list, object), (
        f"{route.path} declares {declared!r}, which filters nothing"
    )
```

## Design Patterns / Tradeoffs

### Code-first (FastAPI default)

- *How it works:* Python types are the source of truth; OpenAPI is derived.
- *Advantages:* documentation cannot describe a route that does not exist; no duplication between
  schema and code; fast to iterate; excellent editor support; the generated document is always
  syntactically valid.
- *Disadvantages:* the contract is *emitted* rather than designed, so it inherits whatever the code
  does — including omissions; consumers cannot start until the server exists; easy to ship a contract
  change without noticing.
- *Failure mode:* an undeclared response type produces a document that quietly disagrees with reality.
- *Use when:* one team owns the API and its main consumers; a small number of integrators.
- *Do NOT use when:* multiple teams must build against the contract before the server exists.

### Contract-first

- *How it works:* `openapi.yaml` is written and reviewed first; server stubs and client SDKs are
  generated from it.
- *Advantages:* the contract is a designed artefact with its own review; frontend, mobile and backend
  work in parallel from day one; mock servers exist immediately; naturally forces you to think about
  the consumer.
- *Disadvantages:* the implementation can drift unless you test against the contract; YAML by hand is
  tedious; generated stubs fit awkwardly into idiomatic Python.
- *Failure mode:* the document says one thing and the server does another, with nothing detecting it.
- *Use when:* several teams or vendors integrate against one API; the contract must be agreed before
  implementation.

### Hybrid — code-first with the contract as a released artefact (✅ recommended)

- *How it works:* generate from code, **commit** the document, diff it in CI against the last release,
  gate on breaking changes (02.3), and validate live responses against it (13.4).
- *Advantages:* no drift (it is generated) *and* the contract is reviewable (it is committed) *and*
  breaking changes are caught mechanically.
- *Disadvantages:* one more CI step and a file that must be regenerated; consumers still cannot start
  before the server exists.
- *Use when:* almost always, for a Python API with third-party consumers. Ledgerly's choice.

### `response_model` versus a return annotation

Functionally equivalent for filtering. Prefer the **return annotation** for readability and type
checking, and use `response_model=` when the annotation cannot express it — a `Response` subclass, a
union resolved at runtime, or when you need `response_model_exclude_none`. What matters is that one
of them is always present, enforced by the test above.

## Production Scenario

**Ledgerly, Friday 15:50.** An email from a customer's lead engineer, cc'ing their account manager:

> *"While debugging our sync I noticed your customer endpoint returns a field called
> `internal_risk_score`, and something called `crm_notes` that appears to contain your sales team's
> comments about us. Is that intentional?"*

It is not intentional. The notes for that account read, in part, *"price-sensitive, churn risk,
do not offer the enterprise tier until Q4"*.

### Symptoms

- `GET /v1/customers/{id}` returns nine fields. The documentation, the OpenAPI document and the
  generated SDKs all describe five.
- The undocumented four are `internal_risk_score` (a churn model output), `acquisition_channel`,
  `crm_notes` (free text written by the sales team), and `stripe_customer_id` (a payment-processor
  identifier belonging to Ledgerly's own account).
- **No errors, no alerts, no anomalous metrics.** The endpoint has returned `200 OK` for its whole
  life; it simply returns more than anyone intended.
- The behaviour has existed since the endpoint shipped **seven months ago**.

### Diagnosis

1. **Alert.** None, and none was possible. A response with extra fields is a valid `200`. The report
   came from a customer reading a JSON body — which is the only detection mechanism that existed.
2. **Reproduce**, in one command:

```bash
$ curl -s -H "$AUTH" https://api.ledgerly.com/v1/customers/cus_8f21ac4d1e77b3 | jq 'keys'
["acquisition_channel","country","created_at","crm_notes","email","id",
 "internal_risk_score","name","stripe_customer_id"]

$ jq -r '.paths."/v1/customers/{customer_id}".get.responses."200".content
         ."application/json".schema."$ref"' openapi.json
#/components/schemas/CustomerOut          → five properties
```

   The contract and the wire disagree. That single comparison is the diagnosis.

3. **Read the route.** Fourteen lines of code, and the defect is the absence of something:

```python
# ledgerly/routers/customers.py — as it was.
@router.get("/{customer_id}")                       # ⚠️ no response_model
async def get_customer(customer_id: str, svc: Service, tenant: Tenant):
    return await svc.get_customer(tenant, customer_id)    # ⚠️ no return annotation
```

   The service returns a SQLAlchemy `Customer` ORM instance. FastAPI, given nothing to filter
   against, serialises every mapped attribute.

4. **Find the scope.** The same check across the whole route table finds **six** routes with no
   declared response type, three of which return ORM objects.
5. **Bound the exposure.** Access logs identify which API keys called those routes and how often —
   which is how the incident report was able to state, accurately, which customers had received which
   fields.
6. **Find the origin.** `git log` shows the route was added during a release crunch, copied from a
   route that also lacked a response model. Nothing in review or CI could have flagged it, because
   nothing was checking.

### Root Cause

FastAPI serialises the returned object when no response type is declared. Returning an ORM model
directly therefore publishes every column, including columns added *later* — which is why this got
worse over time: `crm_notes` and `internal_risk_score` were added to the `customers` table four
months **after** the endpoint shipped, and were exposed by a migration, not by an API change.

That is the property that makes this class of bug so dangerous. The API surface was not defined by
the API code at all; it was defined by the database schema, and it grew every time anyone added a
column. **A missing `response_model` converts every future migration into an unreviewed API change.**

### Fix

*Mitigation (22 minutes):* declare response models on all six routes and deploy. Because the schemas
already existed for documentation purposes, the change was mechanical:

```diff
- @router.get("/{customer_id}")
- async def get_customer(customer_id: str, svc: Service, tenant: Tenant):
+ @router.get("/{customer_id}", response_model=CustomerOut, name="getCustomer")
+ async def get_customer(customer_id: CustomerId, svc: Service,
+                        tenant: Tenant) -> CustomerOut:
      return await svc.get_customer(tenant, customer_id)
```

⚠️ Removing fields is a **breaking change** (02.3) — a client could be reading `stripe_customer_id`.
Ledgerly accepted the break deliberately: continuing to expose sales notes and a churn score is not a
defensible position, and log analysis showed no client had ever parsed those fields. That judgement
was recorded in the incident report, because "we knowingly broke the contract" needs to be a decision
someone made, not something that happened.

*Permanent fix:*

1. The route-table test above, failing the build on any route without a filtered response type.
2. Response models on every route as the output-path protection: validation against `CustomerOut`
   reads only its declared fields, so undeclared ORM attributes are never serialised. (`extra="forbid"`
   does not add to that — under `from_attributes=True` validation, undeclared attributes are simply
   ignored; keep `forbid` for the *input* models, where it rejects unknown fields.)
3. **`openapi.json` committed to the repository**, so any change to the public contract appears as a
   diff in the pull request that causes it. This is the structural fix — it makes contract changes
   visible to reviewers who are looking at Python.
4. **A hard rule: routers never return ORM objects.** The service layer returns domain objects and the
   router maps to a schema (07.6). This removes the coupling between the database schema and the API
   surface entirely, so a migration can never again change what the API returns.

*Customer remediation:* the affected customers were told what had been exposed and for how long,
which required the access-log analysis in step 5. Ledgerly's sales team was told that CRM notes had
been visible to the customers they described — the conversation nobody wanted to have, and the reason
this incident is remembered.

### Prevention

- **The route-table test** is the direct control and takes ten lines.
- **Commit the contract.** Ledgerly's CI regenerates `openapi.json` and fails if it differs from the
  committed file, so the artefact cannot go stale. Reviewing a contract diff catches what reviewing
  Python does not.
- **A field-level allow-list review** for anything derived from a table with internal columns. Adding
  a column should never widen an API; the response-model rule guarantees it cannot.
- **Contract tests that validate live responses against the schema** (13.4), so drift in either
  direction fails:

```python
# tests/contract/test_responses_match_schema.py
import jsonschema, pytest
from ledgerly.main import app

@pytest.mark.anyio
async def test_customer_response_matches_published_schema(client, auth, seeded_customer):
    spec = app.openapi()
    schema = spec["components"]["schemas"]["CustomerOut"]
    schema["components"] = spec["components"]          # resolve internal $refs
    body = (await client.get(f"/v1/customers/{seeded_customer.id}", headers=auth)).json()
    jsonschema.validate(body, schema)                   # fails on extra or missing fields
    assert set(body) == set(schema["properties"]), "response and contract disagree"
```

- **Treat "the API returned an undocumented field" as a security finding**, not a documentation
  ticket. It is the same class as mass assignment on the input side (16.3), and it should route to the
  same people.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a route has no declared response type? | Every attribute of the returned object is serialised, and none is documented. Fail the build on it. |
| ...someone adds a database column? | With a response model, nothing changes. Without one, your public API just grew. |
| ...the handler returns an ORM object? | Lazy-loaded relationships may also serialise, triggering N+1 during response rendering (06.5) — a performance bug on top of the leak. |
| ...`openapi.json` is not committed? | Contract changes are invisible in review and undetectable by diff tooling (02.3). |
| ...someone renames a Python function? | With derived operation ids, every generated SDK method is renamed — a breaking change from a refactor. |
| ...two routes produce the same `operationId`? | Generators silently drop one. Assert uniqueness at startup. |
| ...the schema and the response disagree? | The schema is fiction. Generated clients break in ways your tests cannot see (02.3). |
| ...an error response is undocumented? | Clients have no branch for it; generated SDKs may not even model it. Declare `responses={...}` for every status you emit. |

## Common Pitfalls

**Omitting `response_model` / the return annotation.** The incident above. *Instead:* enforce it with
a route-table test; there is no case where "whatever the handler returned" is the right contract.

**Returning ORM models from routes.** Couples the API surface to the database schema, so migrations
become API changes, and risks lazy-load N+1 during serialisation. *Instead:* explicit output schemas
(07.6).

**Reusing one model for input and output.** The input model then carries read-only fields (mass
assignment — 16.3), and the output model carries write-only ones. *Instead:* `CustomerCreate`,
`CustomerUpdate`, `CustomerOut` — three models, deliberately.

**Treating OpenAPI as documentation.** It is a machine-consumed contract that generates SDKs, mocks
and compatibility gates. *Instead:* pin it, diff it, review it.

**Unstable `operationId`s.** Public SDK method names derived from Python function names change under
refactoring. *Instead:* set them explicitly from route names and assert uniqueness.

**Undocumented error responses.** Clients cannot handle what they do not know exists. *Instead:*
declare every status you can emit, with a `ProblemDetails` model (02.9).

**Examples that do not work.** Copy-pasted examples are the first thing an integrator runs; a broken
one costs you a support ticket per integrator. *Instead:* generate examples from the same fixtures
your tests use.

## How to Test This

- The route-table test asserting a filtered response type on every route (the highest-value test here).
- The `openapi.json` freshness check in CI.
- Schema validation of live responses, asserting set equality of keys rather than a subset.
- An `operationId` uniqueness and stability test: compare against the committed contract and fail if
  an id changed without a version bump (02.3).

## Interview Questions

1. *Explain.* What does `response_model` do beyond documentation? — It filters the serialised output;
   it is a security boundary.
2. *Debug this.* Your API returns four fields that the OpenAPI document does not mention, and has done
   for months. — Missing response model; the handler returns an ORM object; every column is published.
3. *Explain.* Why does a database migration become an API change without response models? — The
   response is whatever the object has; new columns are new fields.
4. *Design.* Contract-first or code-first for an API three teams will build against before it exists?
   — Contract-first, so consumers can generate clients and mocks immediately.
5. *Explain.* Why commit the generated `openapi.json`? — So contract changes are a reviewable diff and
   can be gated by breaking-change tooling.
6. *Explain.* What is the risk of deriving `operationId` from function names? — Refactoring renames
   public SDK methods.
7. *Design.* How would you prove which customers saw an accidentally exposed field, six months later?
   — Access logs by API key and route, retained long enough to answer it (16.13).

## Key Takeaways

- The OpenAPI document is a **release artefact**: generated, committed, diffed, reviewed, published.
- **`response_model` is a security control.** Without it, FastAPI serialises every attribute of
  whatever you returned and documents none of it.
- Never return ORM objects from routes. It makes the database schema your public API surface, so every
  migration silently changes the contract.
- Separate input and output schemas. One shared model produces mass assignment on one side and leaks
  on the other.
- Keep `operationId` stable and explicit — it is the method name in every generated SDK, and a Python
  refactor should not be able to change it.
- Document every status you can return, with the error model. Undocumented errors become unhandled
  branches in client code.
- "Undocumented field in a response" is a **security finding**. Route it accordingly.
