# 02.9 Standardised Error Responses — RFC 9457 Problem Details

> **Prerequisites:** 01.3 (status codes and headers), 02.3 (what breaks a client), 02.4 (declaring responses in the contract)
> **What you'll learn:**
> - Structure an error body so clients branch on something stable rather than on prose
> - Apply RFC 9457 (which obsoletes RFC 7807), including where extensions belong
> - Replace FastAPI's default `{"detail": …}` shape consistently, including validation errors
> - Write error text that helps a human without telling an attacker how your system is built
> **Level:** Beginner

---

> ⚡ **Thursday 07:10** — a customer's overnight sync half-completes, and their retry script makes it worse. The cause: errors only a human reading prose could tell apart.

## Concept

### Plain-English Explanation

An error response has two audiences with incompatible needs.

A **human** — an engineer integrating against your API at 2 a.m. — wants a sentence explaining what
went wrong and what to do about it. That sentence should improve over time as you learn which
mistakes people make. It should be rewritten when it is unclear.

A **program** needs something that will never change, because it has to decide: retry, give up, alert
someone, or take a different path. If the only thing distinguishing "invoice already paid" from
"invoice not found" is the wording of a sentence, then programs will match on that wording — and the
day you improve it, you break them.

So an error body needs both: a **stable machine identifier** and a **mutable human explanation**,
clearly labelled as such. Almost every error-handling disaster comes from providing only one of them.

### Technical Explanation

**RFC 9457** (2023, obsoleting RFC 7807) defines a small, standard JSON shape served as
`application/problem+json`:

```json
{
  "type":     "https://api.ledgerly.com/problems/invoice-already-paid",
  "title":    "Invoice already paid",
  "status":   409,
  "detail":   "Invoice inv_9f2c41 was paid on 2026-08-19 and cannot be voided.",
  "instance": "/v1/invoices/inv_9f2c41/void"
}
```

| Member | Stability | Purpose |
|---|---|---|
| `type` | **Permanent.** Part of the contract | A URI identifying the *problem class*. This is what clients branch on. |
| `title` | Stable-ish; human-readable summary of the `type` | Short label for logs and dashboards |
| `status` | Permanent | Duplicates the HTTP status, so the body is self-contained when logged (01.3) |
| `detail` | **Explicitly mutable** | This occurrence, in prose. May be reworded, translated, or made more specific at any time |
| `instance` | Per occurrence | Which request/resource this happened to |

Plus **extension members** — any additional top-level fields you need. This is where machine-actionable
specifics belong:

```json
{
  "type": "https://api.ledgerly.com/problems/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "detail": "The request body has 2 invalid fields.",
  "instance": "/v1/invoices",
  "errors": [
    {"field": "amount_cents", "code": "greater_than_equal", "message": "must be at least 0"},
    {"field": "currency", "code": "enum", "message": "must be one of EUR, GBP, USD"}
  ],
  "request_id": "req_01J8Z9K2M4"
}
```

⚠️ `type` is a **URI, not a URL you must serve** — though serving it as documentation is excellent
practice, and turns every error into a link an engineer can follow. What matters is that it is a
stable, unique, opaque-to-parsing identifier. Never renumber or reword it.

**FastAPI's default is not this.** `HTTPException(404, "Not found")` produces `{"detail": "Not found"}`
with content type `application/json`, and validation errors produce a differently-shaped
`{"detail": [{"loc": …, "msg": …, "type": …}]}`. So a client sees `detail` as a string sometimes and
as an array other times — the worst of both worlds. Standardising means overriding both handlers.

**The `request_id` extension** is worth adding to every error. It lets a customer paste one token into
a support ticket, and lets you find the exact request in your logs and traces (15.2). It converts
"something failed yesterday" into a two-second lookup.

### Mental Model

> An error body carries **one thing that must never change and one thing that must be free to
> change**. `type` is the API; `detail` is the documentation. If a client is parsing `detail`, you have
> not given them a `type` they could use — and their breakage is your design's fault, not their
> carelessness.

## How It Works

The error catalogue is a real artefact — a registry, versioned with the code, published with the docs:

```text
ledgerly/errors/catalogue.py                docs site
┌─────────────────────────────────────┐    ┌──────────────────────────────────┐
│ INVOICE_NOT_FOUND                   │    │ /problems/invoice-not-found      │
│   type   .../invoice-not-found      │───▶│  What it means · Why it happens  │
│   title  "Invoice not found"        │    │  How to fix it · Retryable? No   │
│   status 404                        │    └──────────────────────────────────┘
│   retryable False                   │
├─────────────────────────────────────┤    OpenAPI (02.4)
│ INVOICE_ALREADY_PAID                │    responses:
│   type   .../invoice-already-paid   │───▶  409: {model: ProblemDetails,
│   status 409                        │           description: "…"}
│   retryable False                   │
├─────────────────────────────────────┤    generated SDKs
│ TAX_PROVIDER_UNAVAILABLE            │    class InvoiceAlreadyPaid(LedgerlyError)
│   status 502   retryable True       │───▶ raised when type matches
└─────────────────────────────────────┘
```

The `retryable` flag is the part teams usually omit and then wish they had. It lets an SDK make the
retry decision correctly without every integrator re-deriving it from status codes, and it forces the
API author to answer the question deliberately for each error class.

**Two rules about `detail` that must be published**, because clients will otherwise assume the
opposite:

1. `detail` is human-readable and **may change without notice**, including translation.
2. Never parse it. Branch on `type`; if you need a machine-readable specific, it is an extension
   member, and if the one you need is missing, ask for it.

## Code Example

The catalogue — one place where every error class is declared:

```python
# ledgerly/errors/catalogue.py
from dataclasses import dataclass
from typing import Final

BASE = "https://api.ledgerly.com/problems"

@dataclass(frozen=True, slots=True)
class ProblemType:
    slug: str
    title: str
    status: int
    retryable: bool

    @property
    def uri(self) -> str:
        return f"{BASE}/{self.slug}"

# The public, permanent error vocabulary. Adding an entry is additive (02.3);
# changing a slug or a status is a BREAKING change.
INVOICE_NOT_FOUND: Final = ProblemType("invoice-not-found", "Invoice not found", 404, False)
INVOICE_ALREADY_PAID: Final = ProblemType("invoice-already-paid", "Invoice already paid", 409, False)
VALIDATION_FAILED: Final = ProblemType("validation-failed", "Validation failed", 422, False)
IDEMPOTENCY_KEY_REUSED: Final = ProblemType("idempotency-key-reused",
                                            "Idempotency key reused", 422, False)
RATE_LIMITED: Final = ProblemType("rate-limited", "Too many requests", 429, True)
TAX_PROVIDER_UNAVAILABLE: Final = ProblemType("tax-provider-unavailable",
                                              "Tax provider unavailable", 502, True)
INTERNAL_ERROR: Final = ProblemType("internal-error", "Internal server error", 500, True)
```

The response model, so the shape appears in OpenAPI and in every generated SDK (02.4):

```python
# ledgerly/errors/schema.py
from pydantic import BaseModel, ConfigDict, Field

class FieldError(BaseModel):
    field: str = Field(examples=["amount_cents"])
    code: str = Field(examples=["greater_than_equal"], description="Stable; safe to branch on.")
    message: str = Field(description="Human-readable. May change without notice.")

class ProblemDetails(BaseModel):
    """RFC 9457. `type` is the stable contract; `detail` is prose and may change."""
    model_config = ConfigDict(extra="allow")      # extension members are permitted by the RFC

    type: str = Field(examples=["https://api.ledgerly.com/problems/invoice-already-paid"])
    title: str
    status: int
    detail: str | None = None
    instance: str | None = None
    request_id: str | None = None
    errors: list[FieldError] | None = None
```

The handlers — including the validation override, which is the one most APIs forget:

```python
# ledgerly/errors/handlers.py
from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

from ledgerly.errors import catalogue as problems
from ledgerly.observability.context import current_request_id   # contextvars (04.4)

def problem_response(problem: problems.ProblemType, detail: str, request: Request,
                     **extensions: object) -> JSONResponse:
    return JSONResponse(
        status_code=problem.status,
        media_type="application/problem+json",     # ⚠️ not application/json
        content={"type": problem.uri, "title": problem.title, "status": problem.status,
                 "detail": detail, "instance": request.url.path,
                 "request_id": current_request_id(), **extensions},
    )

def register(app: FastAPI) -> None:

    @app.exception_handler(RequestValidationError)
    async def _validation(request: Request, exc: RequestValidationError) -> JSONResponse:
        """FastAPI's default emits {"detail": [ ... ]} — a different shape from
        every other error. Overriding it is what makes the contract uniform."""
        errors = [
            {"field": ".".join(str(p) for p in err["loc"] if p != "body"),
             "code": err["type"],                 # stable pydantic code — safe to branch on
             "message": err["msg"]}               # prose — may change with pydantic versions
            for err in exc.errors()
        ]
        return problem_response(problems.VALIDATION_FAILED,
                                f"The request has {len(errors)} invalid field(s).",
                                request, errors=errors)

    @app.exception_handler(Exception)
    async def _unhandled(request: Request, exc: Exception) -> JSONResponse:
        """⚠️ Never let an exception message reach the client. It leaks table
        names, constraint names, file paths and library versions (16.2). The
        request_id is the bridge: the client quotes it, we find the traceback."""
        logger.exception("unhandled_error", extra={"request_id": current_request_id()})
        return problem_response(problems.INTERNAL_ERROR,
                                "An unexpected error occurred. Quote the request_id to support.",
                                request)
```

Seen from the wire — the client has everything it needs, and nothing it should not have:

```bash
$ curl -s -i -X POST https://api.ledgerly.com/v1/invoices/inv_9f2c41/void -H "$AUTH"
HTTP/1.1 409 Conflict
content-type: application/problem+json

{"type":"https://api.ledgerly.com/problems/invoice-already-paid",
 "title":"Invoice already paid","status":409,
 "detail":"Invoice inv_9f2c41 was paid on 2026-08-19 and cannot be voided.",
 "instance":"/v1/invoices/inv_9f2c41/void","request_id":"req_01J8Z9K2M4"}
```

## Design Patterns / Tradeoffs

### Error identity

**A. Status code only**

- *Advantages:* nothing to build; universally understood.
- *Disadvantages:* one status covers many causes — `409` might be "already paid", "already voided",
  "duplicate number" or "version conflict"; a client cannot distinguish them.
- *Use when:* a tiny internal API with one consumer.

**B. Status + a stable `type` URI** (✅ RFC 9457)

- *Advantages:* precise machine identity; self-documenting when the URI resolves; standard shape means
  generic tooling works; extension members carry specifics.
- *Disadvantages:* a catalogue to maintain; URIs are permanent, so slugs must be chosen carefully.
- *Use when:* any public API.

**C. Status + a numeric or short error code (`"code": "E1042"`)**

- *Advantages:* compact; familiar to enterprise integrators; easy to index in support tooling.
- *Disadvantages:* opaque without a lookup table; codes get reused or renumbered; no natural place to
  put documentation.
- *Use when:* an existing organisational convention requires it — then also emit `type` so standard
  tooling works.

**Recommendation:** B, with the `type` URI resolving to a documentation page. If your organisation
needs short codes, add them as an extension member rather than replacing `type`.

### How much detail to expose

| Audience | Safe to include | Never include |
|---|---|---|
| Any client | The failing field, the constraint that was violated, the resource id they supplied, what to do next | Stack traces, SQL, constraint names, table or column names, library versions, internal hostnames, other tenants' identifiers |
| Same-tenant authenticated | Business-specific reasons ("paid on 2026-08-19") | Anything about other tenants |
| Internal logs | Everything, keyed by `request_id` | — |

The bridge between the two columns is `request_id`. The client gets a token; you get the traceback.
That pairing is what makes it possible to be both helpful and safe (15.2, 16.2).

⚠️ Error messages are also an **enumeration surface**. "No user with that email" versus "Wrong
password" tells an attacker which emails are registered. On authentication endpoints, deliberately
collapse distinct causes into one message and one status (16.7) — the one place where being less
helpful is correct.

### Localisation

If `detail` may be translated, it is even more clearly not parseable — which is a useful argument for
the discipline. Negotiate with `Accept-Language`, add `Vary: Accept-Language` (01.4), and keep `type`,
`title` and the field `code`s untranslated.

## Production Scenario

**Ledgerly, Thursday 07:10.** A customer's operations manager calls the account team: their overnight
"void and reissue" job did not run. 4,100 invoices that should have been reissued with corrected VAT
are sitting untouched, and their VAT filing deadline is Friday.

### Symptoms

- The customer's job stopped at 02:14 after processing 63 of 4,163 invoices.
- Their error log shows the job treating a routine, expected condition as a fatal error:

```text
02:14:07 WARN  void_failed invoice=inv_7c1a payload={"type":"...","title":"Invoice already paid",
               "status":409,"detail":"This invoice has been paid; voiding is not permitted."}
02:14:07 ERROR unrecognised API error — aborting run to avoid data corruption
```

- **Ledgerly returned exactly what it should have**: `409`, with the correct `type`, on invoices that
  were already paid. Roughly 1.5% of any night's batch hits this condition, and it always has.
- Ledgerly's metrics: entirely normal. `409` rate unchanged from the previous week.
- The only change on Ledgerly's side in the preceding 24 hours was a documentation and copy pull
  request titled *"Improve error message clarity"*.

### Diagnosis

1. **Alert.** None, and none was appropriate — the API behaved correctly throughout. The signal came
   through the account team. This is the fifth incident in this module with no server-side signal, and
   the pattern is now familiar: **contract breakage is invisible from the server.**
2. **Metrics.** `409` counts are flat week over week, which rules out a behaviour change and points at
   a *representation* change.
3. **Correlate with deploys.** One deploy in the window, touching only strings:

```diff
- detail = f"Invoice {invoice_id} is already paid and cannot be voided."
+ detail = "This invoice has been paid; voiding is not permitted."
```

4. **Read the customer's integration**, which they supply in the ticket:

```python
# the customer's code
if response.status_code == 409:
    body = response.json()
    if "already paid" in body.get("detail", ""):      # ⚠️ matching on prose
        skip_and_continue(invoice)
    else:
        abort_run("unrecognised API error")           # ⚠️ fail-closed on anything else
```

   The reworded sentence no longer contains "already paid". Every subsequent `409` fell into the
   `else` branch, and the job aborted by design.

5. **Root cause confirmed.** The customer's code is fragile — but the question that matters is *why*
   they wrote it that way.
6. **Read Ledgerly's own docs**, and the answer is uncomfortable: the error reference documented the
   status codes and the human messages. It never stated that `type` was the stable identifier, never
   listed the `type` values, and never said `detail` could change. A `type` field was present in
   responses, but it was undocumented — so no integrator had any reason to use it.

### Root Cause

Ledgerly published no stable machine-readable error identity. `type` existed in the payload but was
absent from the documentation, the OpenAPI `responses` declarations (02.4) and the SDKs. The only
thing distinguishing one `409` from another, as far as any integrator could tell, was the sentence in
`detail`.

Given that, matching on `detail` was the **only available strategy**. The customer's code was a
rational response to the contract they were given, and rewording `detail` was a breaking change
disguised as a copy edit — one that no reviewer could have recognised, because nothing marked those
strings as contract.

### Fix

*Mitigation (20 minutes):* revert the copy change. The customer's job succeeded on its next run and
their VAT filing was made. Reverting a documentation improvement to fix a production incident is
uncomfortable and correct — the customer's deadline outranked the prose.

*Permanent fix:*

1. **Publish the error catalogue.** Every `type` URI listed in the API reference with its meaning,
   whether it is retryable, and the recommended client action. Each URI resolves to a documentation
   page.
2. **Declare error responses in OpenAPI** (02.4), so `type` values appear in generated SDKs:

```python
@router.post("/{invoice_id}/void", responses={
    404: {"model": ProblemDetails, "description": "invoice-not-found"},
    409: {"model": ProblemDetails, "description": "invoice-already-paid · invoice-already-void"},
    422: {"model": ProblemDetails, "description": "validation-failed"},
})
```

3. **Publish the stability policy** alongside the compatibility policy from 02.3: *`type`, `title`,
   `status` and field `code`s are stable; `detail` is prose and may change without notice; do not
   parse it.*
4. **Typed exceptions in the SDKs**, so integrators branch on a class rather than a string:

```python
# ledgerly-python SDK
try:
    client.void_invoice(invoice_id)
except ledgerly.InvoiceAlreadyPaid:      # dispatched on `type`, not on `detail`
    continue
except ledgerly.RateLimited as exc:
    time.sleep(exc.retry_after); retry()
```

5. **Proactive outreach.** Log analysis found four other customers whose retry behaviour correlated
   with `detail` wording. Each was contacted with migration guidance before the copy change was
   re-landed a month later.

### Prevention

- **A CI test pinning the error catalogue**, so changing a `type` is as visible as changing a URI:

```python
# tests/contract/test_error_catalogue_is_stable.py
import json, pathlib, pytest
from ledgerly.errors import catalogue

PUBLISHED = json.loads(pathlib.Path("contracts/error-catalogue.json").read_text())

def test_no_published_problem_type_was_removed_or_changed() -> None:
    current = {p.slug: p.status for p in vars(catalogue).values()
               if isinstance(p, catalogue.ProblemType)}
    for slug, status in PUBLISHED.items():
        assert slug in current, f"problem type {slug!r} was removed — breaking (02.3)"
        assert current[slug] == status, (
            f"problem type {slug!r} changed status {status} → {current[slug]}: "
            "clients branch on the (type, status) pair"
        )
```

- **A test that every error response is `application/problem+json` with a `type`**, parametrised over
  the provokable error conditions — which also catches FastAPI's default handlers slipping back in.
- **Treat error strings as code, not copy.** They live in the catalogue module, not scattered through
  handlers, and a change to one is reviewed by an API owner. The copy PR would have been routed to a
  reviewer who knew the risk.
- **Alert on a customer's error-handling behaviour changing.** A client that suddenly stops issuing
  requests after receiving a `4xx` (as this job did) is a detectable pattern: `requests_after_4xx`
  dropping to zero for one API key. For the fifth time in this module, the observable symptom was
  **traffic quietly stopping**.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...you reword an error message? | Safe **only** if clients have a stable `type` to branch on and know they must use it. |
| ...you add a new error `type`? | Additive, but clients without a branch for it hit their default path — which may retry a permanent failure. Publish the taxonomy as open (02.3). |
| ...a client parses `detail`? | You did not give them a usable alternative. Publish the catalogue and add typed SDK exceptions. |
| ...an unhandled exception escapes? | The generic handler must return a `500` problem with no internal detail, and log the traceback against `request_id`. |
| ...a validation error occurs? | It must have the same shape as every other error. Override FastAPI's default, or clients see two shapes. |
| ...an error message reveals which emails are registered? | An enumeration vulnerability. Collapse authentication failures into one message and status (16.7). |
| ...a constraint name appears in `detail`? | You have published your schema. Map database exceptions to catalogue entries; never pass the message through (16.2). |
| ...a customer reports "an error yesterday"? | With `request_id` in every error body, it is a log lookup. Without it, it is guesswork. |

## Common Pitfalls

**No stable machine identifier.** Clients are forced to parse prose, and your next copy edit is a
breaking change. The incident above. *Instead:* a published `type` catalogue.

**Leaving FastAPI's default error shapes.** `{"detail": "..."}` for `HTTPException` and
`{"detail": [...]}` for validation means `detail` is sometimes a string and sometimes an array.
*Instead:* override both handlers.

**Leaking exception text.** `duplicate key value violates unique constraint
"ix_invoices_tenant_number"` tells an attacker your schema. *Instead:* map to a catalogue entry; log
the original.

**Errors documented only in prose.** If `type` is not in the OpenAPI document, it is not in the SDKs,
so integrators cannot use it. *Instead:* declare `responses={...}` on every route.

**Reusing one `type` for different causes.** A single `invalid-request` for everything gives clients no
more information than the status code. *Instead:* one `type` per distinct client action.

**Changing a `type` URI or its status.** Both are breaking. *Instead:* add a new one and deprecate the
old (02.13).

**Omitting `request_id`.** Every support conversation becomes an archaeology exercise. *Instead:*
include it in every error body, and log it on every request (15.2).

**`Content-Type: application/json` for problems.** Some clients and gateways route on the content type.
*Instead:* `application/problem+json`.

## How to Test This

- The catalogue-stability test above, comparing against a committed `contracts/error-catalogue.json`.
- A parametrised test that provokes each error condition and asserts the media type, the presence of
  `type`, `title`, `status` and `request_id`, and that the `type` is in the catalogue.
- A test asserting that a deliberately raised `ZeroDivisionError` in a route produces a `500` problem
  whose `detail` contains no substring of the exception message.
- A test that a database constraint violation surfaces as a catalogue entry, not as raw SQL text.

## Interview Questions

1. *Explain.* Which parts of an error body are contract and which are not? — `type`, `title`, `status`
   and field `code`s are stable; `detail` is prose.
2. *Debug this.* A customer's job aborted after you shipped a copy change to error messages. — They
   matched on `detail` because no stable `type` was published; revert, then publish the catalogue.
3. *Explain.* Why is `application/problem+json` worth using instead of `application/json`? — Standard
   shape; tooling and gateways can recognise problems generically.
4. *Design.* Design the error contract for a payments API. What is in the body? — `type`, `title`,
   `status`, `detail`, `instance`, `request_id`, plus extensions like `errors` and `retryable`.
5. *Explain.* What must never appear in an error `detail`, and how do you stay helpful anyway? — Stack
   traces, SQL, schema names; use `request_id` as the bridge to internal logs.
6. *Explain.* Why should authentication errors be deliberately vague? — Distinct messages let an
   attacker enumerate registered accounts.
7. *Design.* You must change an error's status from `400` to `422`. Is that safe? — No; clients branch
   on `(type, status)`. Add a new `type` and deprecate.

## Key Takeaways

- An error body serves a program and a human. Give each what it needs: a **permanent `type`** and a
  **mutable `detail`**, and publish which is which.
- If clients parse `detail`, that is a design failure on your side — they had no alternative.
- RFC 9457 (not 7807) is the current standard: `type`, `title`, `status`, `detail`, `instance`, plus
  extension members for machine-actionable specifics.
- Override FastAPI's default handlers, **including validation errors**, or your API has two error
  shapes.
- Maintain the error catalogue as a versioned artefact, declare it in OpenAPI, and pin it in CI.
  Changing a `type` or its status is a breaking change.
- Never leak exception text. `request_id` lets you be safe to clients and complete in your logs.
- Mark each error class **retryable or not**, so SDKs and integrators do not have to guess (15.14).
