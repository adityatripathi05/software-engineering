# 02.7 Bulk Operations and Partial Updates

> **Prerequisites:** 02.1 (resources), 02.4 (request and response schemas) · modern-python 18.4 (pydantic)
> **What you'll learn:**
> - Represent the three distinct states a `PATCH` field can be in — absent, null, and valued — and why two is not enough
> - Use Pydantic v2's `model_fields_set` and `exclude_unset` correctly at an update boundary
> - Choose between all-or-nothing, per-item and asynchronous semantics for bulk endpoints
> - Design a bulk endpoint whose retry does not duplicate the work that already succeeded
> **Level:** Intermediate

---

## Concept

### Plain-English Explanation

Two features that look small and are not.

**Partial update.** A client wants to change one field on an invoice without sending the other
fifteen. Simple — except that "I did not mention `notes`" and "I want `notes` cleared" arrive as
almost the same thing, and if your code cannot tell them apart it will delete data the client never
asked it to touch. The client sees `200 OK`. Nobody finds out until someone looks for a note that is
no longer there.

**Bulk operation.** A client wants to create five hundred invoices in one request instead of five
hundred requests. Simple — except that a request either succeeds or fails, and five hundred items can
half-succeed. What status do you return when 497 worked? What does the client do next? If they retry,
do they get 497 duplicates?

Both features are places where the *edges* carry all the difficulty and the happy path teaches you
nothing.

### Technical Explanation

**A `PATCH` field has three states, not two:**

```text
request body                    what the client means
{}                              leave `notes` exactly as it is       ← ABSENT
{"notes": null}                 clear `notes`                        ← NULL
{"notes": "Paid by cheque"}     set `notes` to this value            ← VALUE
```

In Python, a plain `str | None = None` model field collapses ABSENT and NULL into the same value —
`None` — and once collapsed you cannot recover the distinction. That is the defect at the centre of
this notebook.

Pydantic v2 gives you two tools for it:

- **`model_fields_set`** — the set of field names that were *explicitly present in the input*,
  regardless of value. This is the only way to distinguish absent from null.
- **`model_dump(exclude_unset=True)`** — a dict of just those fields, with their values (including
  explicit `None`).

⚠️ `exclude_none=True` is **not** the same and is the trap: it drops explicit nulls too, so
`{"notes": null}` silently becomes "do nothing" and the client's clear operation is ignored. Use
`exclude_unset`, never `exclude_none`, at an update boundary.

**Two standard patch formats:**

| | JSON Merge Patch (RFC 7386) | JSON Patch (RFC 6902) |
|---|---|---|
| Content type | `application/merge-patch+json` | `application/json-patch+json` |
| Body | `{"notes": null, "due_date": "2026-09-30"}` | `[{"op":"replace","path":"/notes","value":null}]` |
| `null` means | **delete the field** | nothing special — it is a value |
| Array handling | Whole-array replacement only | Index-level add/remove/move |
| Preconditions | External (`If-Match` — 01.4) | `{"op":"test",...}` built in |
| Readability | High | Low |
| Use when | Flat resources, most APIs | Deep documents, collaborative editing |

Ledgerly uses merge-patch semantics — `null` clears — which is what most clients expect, and it
documents that explicitly, because the alternative reading ("null is just a value") is equally
defensible and the client cannot guess.

**Bulk operations** have three coherent designs, and the failure is picking none of them:

```text
A. All-or-nothing        one transaction; any failure rolls back everything
                         → 201 or 4xx; retry is safe because nothing partial exists

B. Per-item             each item independent; response reports each outcome
                         → 207 Multi-Status; retry must be per-item idempotent (02.8)

C. Asynchronous job     accept, enqueue, return a job handle
                         → 202 + Location; poll for per-item results (02.10)
```

The unforgivable design is "one transaction per item, `200` at the end, no per-item results" — the
client cannot tell what happened and cannot safely retry.

### Mental Model

> For partial updates: **absent, null and valued are three different instructions**, and a model that
> represents them with two values will destroy data. For bulk: **a request is atomic, a batch is
> not** — so you must decide, and document, what "partially succeeded" means before a client
> discovers it by retrying.

## How It Works

The three-state problem, drawn through the layers where it is usually lost:

```text
  PATCH /v1/invoices/inv_9f2c41
  {"due_date": "2026-09-30"}          ← client mentions ONE field

          │  Pydantic parses into InvoiceUpdate
          ▼
  InvoiceUpdate(due_date=date(2026,9,30), notes=None, po_number=None, terms=None)
                                        └────────── defaults, NOT client intent ──────────┘

          │  ❌ model_dump()                        │  ✅ model_dump(exclude_unset=True)
          ▼                                         ▼
  {"due_date": ..., "notes": None,          {"due_date": date(2026, 9, 30)}
   "po_number": None, "terms": None}                │
          │                                         │
          ▼                                         ▼
  UPDATE invoices SET due_date=…,           UPDATE invoices SET due_date=…
    notes=NULL, po_number=NULL,               WHERE id=…
    terms=NULL WHERE id=…                    ✅ one column touched
  ⚠️ THREE FIELDS SILENTLY ERASED
```

`model_fields_set` is what preserves the distinction — it holds `{"due_date"}` regardless of what the
defaults are, so "the client did not mention `notes`" survives all the way to the SQL.

## Code Example

The update schema, with the tri-state made explicit at the boundary:

```python
# ledgerly/schemas/invoice_update.py
from datetime import date
from pydantic import BaseModel, ConfigDict, Field

class InvoiceUpdate(BaseModel):
    """Merge-patch semantics: an ABSENT field is unchanged, an explicit `null`
    clears the field. `model_fields_set` is the only thing that distinguishes
    the two, so it must survive into the service layer (07.3)."""
    model_config = ConfigDict(extra="forbid")     # unknown field → 422, not ignored

    due_date: date | None = None
    notes: str | None = Field(default=None, max_length=2000)
    po_number: str | None = Field(default=None, max_length=64)
    payment_terms: str | None = None

    def changes(self) -> dict[str, object]:
        """Only the fields the client actually sent, with their values —
        including explicit None, which means 'clear this'.

        ⚠️ exclude_unset, NOT exclude_none. exclude_none would drop explicit
        nulls and silently ignore the client's request to clear a field."""
        return self.model_dump(exclude_unset=True)
```

The service applies exactly those fields, and nothing else:

```python
# ledgerly/services/invoices.py (excerpt)
async def patch_invoice(
    self, tenant: TenantId, invoice_id: InvoiceId, patch: InvoiceUpdate,
    *, expected_version: int,
) -> Invoice:
    changes = patch.changes()
    if not changes:
        raise NoChangesRequested()          # → 400: an empty patch is a client bug

    invoice = await self._repo.get_for_update(tenant, invoice_id)   # 05.14
    if invoice.status in TERMINAL_STATUSES:
        raise InvoiceNotEditable(invoice_id, invoice.status)        # → 409 (01.3)

    # Optimistic concurrency: the ETag the client read must still be current,
    # or two concurrent patches silently overwrite each other (01.4, 05.13).
    updated = await self._repo.apply_changes(
        tenant, invoice_id, changes, expected_version=expected_version
    )
    await self._audit.record(tenant, "invoice.patched", invoice_id,
                             fields=sorted(changes))    # WHICH fields, not their values (16.13)
    return updated
```

The bulk endpoint, using per-item semantics with per-item idempotency so a retry is safe:

```python
# ledgerly/routers/invoices.py (excerpt)
from fastapi import status

MAX_BATCH = 500

@router.post("/batch", response_model=BatchResult, name="createInvoicesBatch")
async def create_invoices_batch(
    body: BatchCreate, response: Response, svc: Service, tenant: Tenant,
) -> BatchResult:
    """Per-item semantics. Each item carries its own idempotency key, so a client
    that retries the whole batch after a timeout re-creates nothing (02.8).

    The status is computed from the outcome: 201 when every item succeeded, 207
    only when the outcomes are mixed — so a client that checks only the status
    is not silently wrong (the ⚠️ under Bulk semantics below)."""
    if len(body.items) > MAX_BATCH:
        raise HTTPException(422, f"Batch exceeds {MAX_BATCH} items.")

    results = await svc.create_many(tenant, body.items)
    failed = sum(r.status >= 400 for r in results)
    response.status_code = (status.HTTP_201_CREATED if failed == 0
                            else status.HTTP_207_MULTI_STATUS)
    return BatchResult(results=results, succeeded=len(results) - failed, failed=failed)
```

The response envelope is the contract that makes partial success usable:

```python
# ledgerly/schemas/batch.py
class BatchItemResult(BaseModel):
    index: int                       # position in the request — the client's correlation key
    idempotency_key: str
    status: int                      # per-item HTTP-style status: 201, 409, 422 …
    id: InvoiceId | None = None      # present on success
    error: ProblemDetails | None = None   # present on failure (02.9)

class BatchResult(BaseModel):
    results: list[BatchItemResult]
    succeeded: int
    failed: int
```

Seen from the wire — the client can act on this without guessing:

```bash
$ curl -s -X POST https://api.ledgerly.com/v1/invoices/batch -H "$AUTH" -d @batch.json | jq
{
  "results": [
    {"index": 0, "idempotency_key": "po-88213-1", "status": 201, "id": "inv_9f2c41"},
    {"index": 1, "idempotency_key": "po-88213-2", "status": 201, "id": "inv_9f2c58"},
    {"index": 2, "idempotency_key": "po-88213-3", "status": 422,
     "error": {"type": "https://api.ledgerly.com/problems/validation-failed",
               "title": "Validation failed", "status": 422,
               "detail": "currency 'XYZ' is not supported"}}

}
```

## Design Patterns / Tradeoffs

### Update semantics

**`PUT` — full replacement**

- *Advantages:* idempotent by method, so infrastructure may retry it (01.2); unambiguous — the body is
  the new state; no null/absent question exists.
- *Disadvantages:* the client must read-modify-write, which is a lost-update race unless paired with
  `If-Match` (01.4, 05.13); large payloads; a client on an old schema version silently clears fields it
  does not know about.
- *Use when:* small resources, configuration objects, or when retry-safety by method matters most.

**`PATCH` with merge semantics** (✅ Ledgerly's choice)

- *Advantages:* small payloads; no read-modify-write; a client that does not know about a field cannot
  clear it; natural for mobile clients on poor connections.
- *Disadvantages:* not idempotent by method, so nothing retries it for you; the three-state problem;
  `null` semantics must be documented because they are genuinely ambiguous.
- *Failure mode:* absent treated as null — the incident below.
- *Use when:* resources with many fields and partial-permission editing.

**`PATCH` with JSON Patch operations**

- *Advantages:* explicit and unambiguous; array element operations; built-in `test` op gives
  preconditions without `If-Match`.
- *Disadvantages:* verbose; hard to read in logs; awkward to validate with Pydantic; poor SDK
  ergonomics.
- *Use when:* deep nested documents, collaborative editing, or when array-index operations are needed.
- *Do NOT use when:* the resource is flat — the complexity buys nothing.

### Bulk semantics

| | A. All-or-nothing | B. Per-item (`207`) | C. Async job (`202`) |
|---|---|---|---|
| Transaction | One | One per item | Per item, in a worker |
| Status | `201`/`4xx` | `207 Multi-Status` | `202` + `Location` |
| Retry safety | Safe — nothing partial exists | Needs per-item idempotency | Needs job idempotency |
| Partial success | Impossible | Reported per item | Reported per item on poll |
| Practical size | ~100s (one transaction, one timeout) | ~100s | Unbounded |
| Client complexity | Lowest | Moderate — must read results | Highest — must poll (02.10) |
| Failure mode | One bad row rejects 499 good ones | Client ignores `results` and assumes success | Client never polls; results expire |
| Use when | Items are genuinely one unit (a journal entry's lines) | Independent items, moderate size | Thousands of items, or slow per-item work |

**Recommendation:** B for independent items, with per-item idempotency keys and a documented result
envelope; A when the items form a single business fact that must not half-apply; C above a few hundred
items or when each item does external I/O.

⚠️ The most common mistake is B's failure mode: clients receive `207`, treat it as success because it
is `2xx`, and never inspect `results`. Mitigate by returning `207` *only* when there is at least one
failure, `201` when all succeeded — so a plain status check is not silently wrong.

## Production Scenario

**Ledgerly, Wednesday 09:15.** A customer's operations lead writes: *"We ran our usual due-date
extension across 1,200 open invoices last night. This morning every one of them has lost its PO
number, its payment terms and its internal notes. Our AP team cannot match them to purchase orders."*

### Symptoms

- 1,200 invoices have `po_number`, `payment_terms` and `notes` set to `NULL`. `due_date` is correctly
  updated on all of them.
- Every request returned `200 OK`. The client logged 1,200 successes.
- No errors, no alerts, no latency anomaly. `http_requests_total{route="/v1/invoices/{id}",method="PATCH"}`
  shows 1,200 requests and 1,200 `200`s.
- The customer's request bodies, which they supply in the ticket, contain exactly one field:

```json
{"due_date": "2026-09-30"}
```

- Ledgerly's own dashboard does not exhibit the problem — editing an invoice there preserves
  everything.

### Diagnosis

1. **Alert.** None. This is the fourth incident in this module with no operational signal: the API did
   exactly what its code said, quickly and successfully. Data destruction is not an error condition.
2. **Metrics.** Nothing anomalous. 1,200 `PATCH`es is a normal night for that customer.
3. **Logs.** The audit log is what breaks it open, because it records *which fields* each patch
   changed:

```json
{"event":"invoice.patched","invoice_id":"inv_9f2c41","tenant":"t_44f1",
 "fields":["due_date","notes","payment_terms","po_number"],"actor":"key_live_2b8e…"}
```

   The client sent one field. The service recorded four. The gap between the request body and the
   applied change set is the entire bug, and it is visible in one log line — because someone had
   thought to log field *names* (not values) months earlier.

4. **Reproduce**, immediately and deterministically:

```python
>>> patch = InvoiceUpdate.model_validate({"due_date": "2026-09-30"})
>>> patch.model_dump()
{'due_date': datetime.date(2026, 9, 30), 'notes': None,
 'po_number': None, 'payment_terms': None}          # ⚠️ three unintended NULLs
>>> patch.model_fields_set
{'due_date'}                                         # ✅ the truth was available
```

5. **Why the dashboard was unaffected:** it is a form that submits *every* field, so the values it
   sends for `notes` and `po_number` are the current ones. The bug required a client that sent a
   genuinely partial body — which is to say, a client using `PATCH` as intended.

### Root Cause

The handler applied `patch.model_dump()`, which materialises **every** field including those the
client never sent, filling them with the model's defaults — `None`. The repository then wrote all four
columns.

```python
# as it was
changes = patch.model_dump()                    # ⚠️ all fields, defaults included
await repo.apply_changes(tenant, invoice_id, changes)
```

The type annotation `notes: str | None = None` is doing two incompatible jobs: expressing that the
field is *nullable*, and expressing that it is *optional in the request*. Those are different
properties, and Python's default value mechanism cannot distinguish them. `model_fields_set` exists
precisely to recover the distinction, and the code never consulted it.

The endpoint had shipped nine months earlier. Every test used a full-body patch — because the tests
were written from the dashboard's usage — so the defect was invisible to the entire test suite.

### Fix

*Mitigation (35 minutes):* the audit log records which fields changed, and point-in-time recovery
(05.18) provides the values. A one-off restore job read the pre-patch values from a PITR snapshot and
restored `notes`, `po_number` and `payment_terms` for the 1,200 affected invoices, leaving the
correctly-updated `due_date` alone.

⚠️ That recovery was possible only because of two decisions made long before: audit logging of changed
field names, and a PITR window longer than the detection time. Without either, the data was gone.

*Permanent fix:*

```diff
- changes = patch.model_dump()
+ # Only fields the client actually sent. exclude_unset preserves explicit nulls
+ # (which mean "clear this") while omitting fields that were never mentioned.
+ changes = patch.model_dump(exclude_unset=True)
+ if not changes:
+     raise NoChangesRequested()
```

Plus three structural changes so the class cannot recur:

1. **`changes()` as a method on every update schema**, so no handler ever calls `model_dump()` directly
   on a patch model. The safe call is the only convenient one.
2. **A lint rule** forbidding `model_dump()` without `exclude_unset` in any module under
   `ledgerly/schemas/*update*` or in service update paths.
3. **`extra="forbid"`** on update models, so `{"due_dat": …}` is a `422` rather than a patch that
   changes nothing while reporting success.

### Prevention

- **The test that encodes the lesson** — assert the *untouched* fields, which is what nobody thought
  to do:

```python
# tests/api/test_partial_update_semantics.py
@pytest.mark.anyio
async def test_absent_fields_are_left_unchanged(client, auth, seeded_invoice):
    before = seeded_invoice        # has notes, po_number and payment_terms set
    response = await client.patch(f"/v1/invoices/{before.id}",
                                  json={"due_date": "2026-09-30"},
                                  headers={**auth, "If-Match": f'"{before.version}"'})
    after = response.json()
    assert after["due_date"] == "2026-09-30"
    # The assertions that were missing for nine months:
    assert after["notes"] == before.notes
    assert after["po_number"] == before.po_number
    assert after["payment_terms"] == before.payment_terms

@pytest.mark.anyio
async def test_explicit_null_clears_the_field(client, auth, seeded_invoice):
    """The other half: an explicit null MUST still clear. A fix that made the
    first test pass by dropping all Nones would break this one."""
    response = await client.patch(f"/v1/invoices/{seeded_invoice.id}",
                                  json={"notes": None},
                                  headers={**auth, "If-Match": f'"{seeded_invoice.version}"'})
    assert response.json()["notes"] is None
```

  The pairing matters: the obvious fix (`exclude_none=True`) passes the first test and fails the
  second. A single test would have driven the wrong fix.

- **Audit which fields changed, on every mutation.** Field names, never values (16.13). It is what made
  both diagnosis and recovery possible here, and it costs one line in the service layer.
- **Write API tests from the API's perspective, not the UI's.** Every test used full-body patches
  because they were modelled on the dashboard. A test-writing rule — *at least one single-field patch
  test per patchable resource* — would have caught it on day one.
- **Alert on bulk field nulling.** A daily job flags any tenant where more than N rows had a non-null
  field set to null within an hour. Data destruction has no natural error signal, so it needs a
  deliberate one.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a client omits a field in `PATCH`? | It must be unchanged. `model_dump(exclude_unset=True)` is the mechanism; `model_fields_set` is the truth. |
| ...a client sends explicit `null`? | Under merge-patch semantics it clears the field. Document that; `exclude_none` would silently ignore it. |
| ...a client sends an empty patch `{}`? | `400` — nothing to do, and it is almost certainly a client bug. |
| ...two clients patch the same invoice concurrently? | Last writer wins unless you require `If-Match` → `412` (01.4, 05.13). |
| ...a bulk request half-succeeds? | You must report per item. `207` with a results array; never a bare `200`. |
| ...a client retries a bulk request after a timeout? | Without per-item idempotency keys, everything that succeeded is duplicated (02.8). |
| ...a bulk request contains 100,000 items? | Cap it in the schema. Above a few hundred, switch to an async job (02.10). |
| ...a client ignores the `results` array? | Return `207` only on partial failure and `201` on full success, so a naive status check is not wrong. |
| ...an item fails validation in an all-or-nothing batch? | 499 valid items are rejected. That is the trade — make sure it is the one you intended. |

## Common Pitfalls

**`model_dump()` on a patch model.** Materialises every field with its default and erases whatever the
client did not mention. The incident above. *Instead:* `model_dump(exclude_unset=True)`, wrapped in a
`changes()` method so it is the path of least resistance.

**`exclude_none=True` as the fix.** Passes the "don't wipe" test and breaks the "explicit null clears"
behaviour. *Instead:* `exclude_unset`, with tests for both halves.

**Undocumented `null` semantics.** Clients cannot guess whether `null` clears or is ignored. *Instead:*
state it in the OpenAPI description of every nullable patchable field (02.4).

**`PATCH` without `If-Match`.** Concurrent patches silently overwrite each other, and the field-level
granularity makes it *more* likely, not less (04.6). *Instead:* require the precondition on
contended resources.

**Bulk endpoints returning a bare `200`.** The client cannot tell what happened and cannot retry
safely. *Instead:* `207` with per-item results, or all-or-nothing with a single status.

**Bulk without per-item idempotency.** One timeout turns 497 successes into 497 duplicates on retry.
*Instead:* an idempotency key per item (02.8).

**Unbounded batch size.** A 100,000-item request is a memory and timeout hazard, and its transaction
holds locks for minutes (05.12). *Instead:* cap it in the schema so the limit is in the contract.

**Testing patches only with full bodies.** The test suite then cannot see the entire bug class.
*Instead:* mandate single-field patch tests.

## How to Test This

- The paired tests above: absent fields unchanged, **and** explicit null clears. Neither alone is
  sufficient, and the pair prevents the wrong fix.
- A property test: for any subset of patchable fields, patching that subset changes exactly those
  columns (`hypothesis` is already covered in modern-python 15.6).
- A bulk test with a deliberate mid-batch failure, asserting `207`, per-item statuses, and that
  succeeded items persisted.
- A bulk retry test: submit, kill the connection mid-response, resubmit the identical batch, assert
  the total row count is unchanged.

2. *Explain.* Difference between `exclude_unset` and `exclude_none` in Pydantic v2, and why it matters
   here. — The first respects explicit nulls; the second discards them, ignoring a clear request.
3. *Debug this.* Customers report that a single-field `PATCH` wiped three other fields, and every

4. *Design.* A client wants to create 500 invoices in one call. Design the endpoint. — Per-item
   semantics, per-item idempotency keys, `207` with a results array, capped size.
5. *Explain.* Why is `207` risky as a success status? — It is `2xx`, so naive clients treat it as
   success and never read the per-item results.
6. *Design.* When would you make a bulk endpoint all-or-nothing instead? — When the items constitute a
   single business fact that must not half-apply.
7. *Explain.* How do you make a bulk retry safe after a timeout? — Per-item idempotency keys, with a
   durable uniqueness guarantee behind them.

## Key Takeaways

- A patchable field has **three** states. A model that represents two will destroy data, silently,
  with a `200`.
- `model_dump(exclude_unset=True)` is the correct call at an update boundary. `exclude_none=True` is
  the plausible-looking wrong fix, and only a paired test catches the difference.
- Document your `null` semantics. Merge-patch says null clears; that is a choice a client cannot infer.
- Require `If-Match` on contended `PATCH` resources, or field-level updates race each other.
- Bulk endpoints must choose: all-or-nothing, per-item with `207`, or an async job. "One transaction
  per item and a bare `200`" is not a design.
- Per-item **idempotency keys** are what make a bulk retry safe. Without them, one timeout duplicates
  everything that already worked.
- Audit *which fields* changed on every mutation. It is what makes silent data destruction diagnosable
  and, with PITR, recoverable.
