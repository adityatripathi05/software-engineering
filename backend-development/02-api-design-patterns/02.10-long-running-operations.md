# 02.10 Long-Running Operations — 202 + Polling vs Webhooks vs SSE

> **Prerequisites:** 01.3 (status codes, `Location`, `Retry-After`), 02.1 (resources), 02.8 (idempotency)
> **What you'll learn:**
> - Recognise when work does not belong inside a request/response cycle, using a timeout budget rather than intuition
> - Model an operation as a **resource** with an explicit lifecycle and terminal states
> - Choose between polling, webhooks and SSE for delivering completion, and combine them correctly
> - Avoid the visibility race that makes a freshly-issued job handle return `404`
> **Level:** Intermediate

---

## Concept

### Plain-English Explanation

Some work cannot finish while a client waits. Rendering 40,000 invoices into a PDF archive, importing
a 200 MB ledger file, recalculating VAT across a year — these take minutes, and there is no timeout
you can set that makes them fit in an HTTP request. Load balancers give up at 60 seconds. Mobile
networks drop connections. A user closes a laptop lid.

So you change the shape of the answer. Instead of *"here is your result"*, you say *"I have accepted
your request; here is where to find out how it is going."* The work moves to a background worker
(module 11) and the client gets a handle.

That handle is the design. Done well, it is a resource with a clear lifecycle that a client can poll,
resume after a crash, and reason about. Done badly, it is a job id that sometimes does not exist yet,
a status that never reaches a terminal state, and clients that poll forever or resubmit work that is
already running.

### Technical Explanation

**The timeout budget** tells you when to move work out of the request, without guessing:

```text
client timeout            30 s     the shortest link in the chain governs everything
  └─ load balancer idle   60 s
      └─ proxy read       30 s
          └─ app request  25 s     ← your real budget
              └─ handler  ~20 s    leaving margin for queueing (01.1) and serialisation

  Any operation whose p99 approaches ~20 s belongs in a worker.
  Any operation whose p99 exceeds it is ALREADY failing, intermittently, for someone.
```

⚠️ Judge by **p99, not the average**. An import that averages 4 seconds and takes 45 for the largest
tenant is already timing out for that tenant every night.

**The `202` pattern:**

```text
POST /v1/invoice-exports                     ← create an operation
  {"period": "2026-07", "format": "csv"}
        │
        ▼
HTTP/1.1 202 Accepted
Location: /v1/operations/op_7c1a3e            ← WHERE to find out how it is going
Retry-After: 5                                ← HOW SOON to ask again
{"id": "op_7c1a3e", "status": "pending", ...}

        │  … worker processes it (module 11) …
        ▼
GET /v1/operations/op_7c1a3e
HTTP/1.1 200 OK
Retry-After: 3                                ← still working; ask again in 3 s
{"id": "op_7c1a3e", "status": "running", "progress": 0.42}

        ▼  … later …
HTTP/1.1 200 OK
{"id": "op_7c1a3e", "status": "succeeded",
 "result": {"download_url": "https://...", "expires_at": "..."},   ← 09.6
 "completed_at": "2026-08-24T09:47:11Z"}
```

**The operation is a resource** (02.1), with the states any client must be able to handle:

```text
   pending ──▶ running ──┬──▶ succeeded   ← TERMINAL
      │           │      ├──▶ failed      ← TERMINAL, with an error body (02.9)
      │           │      └──▶ cancelled   ← TERMINAL
      └───────────┴──▶ expired            ← TERMINAL: worker never claimed it, or
                                             the result TTL passed
```

Every non-terminal state must be able to reach a terminal one. **A worker that crashes must not leave
an operation `running` forever** — that is the single most common defect in this pattern, and it makes
clients poll indefinitely. A lease with a heartbeat (11.5) or a reaper job (11.8) transitions stale
operations to `failed`.

**Two `202` variants** that are worth distinguishing:

- **The operation is the resource.** `POST /v1/invoice-exports` → `202` + `Location:
  /v1/operations/op_…`. The result is a *new* thing that did not exist before.
- **The operation mutates an existing resource.** `POST /v1/invoices/{id}/send` → `202`, and the
  invoice's own state eventually becomes `sent`. The client may poll the invoice rather than an
  operation, if the state change is observable there.

### Mental Model

> A long-running operation is **a resource representing an intention in progress**. It has a URI, a
> lifecycle, terminal states, and a retention period. The client's contract is: *poll until terminal,
> then read the result*. Everything that goes wrong with this pattern is a violation of one of those
> four words — a handle with no URI yet, a state that never terminates, or a result that vanished.

## How It Works

**The visibility race** — the failure mode that makes this pattern subtly unreliable, and the subject
of the scenario below:

```text
❌ Operation row and job enqueue in DIFFERENT transactions

  t=0   INSERT operation (op_7c1a) ─── transaction A ───▶ COMMIT
  t=1   enqueue job to Redis        ─── separate call ───▶ ok
  t=2   return 202 + Location
  t=3   client GETs /v1/operations/op_7c1a
        └─▶ reads from a REPLICA that has not caught up  ──▶ 404 ⚠️
        └─▶ or: enqueue succeeded, INSERT rolled back    ──▶ 404 forever ⚠️
        └─▶ or: INSERT committed, enqueue failed         ──▶ pending forever ⚠️

✅ Operation row and job enqueue in ONE transaction (the outbox idea — 11.15)

  t=0   BEGIN
          INSERT operation (op_7c1a, status='pending')
          INSERT outbox_message (job payload)        ← same transaction
        COMMIT                                        ← both or neither
  t=1   return 202 + Location
  t=2   relay publishes the outbox message to the queue
  t=3   client GETs /v1/operations/op_7c1a ──▶ 200 {"status": "pending"} ✅
```

The rule: **the client can only be told about something that is already durably visible.** Returning a
handle before the thing it names is readable is a promise you have not yet kept.

⚠️ Read replicas make this worse and are easy to overlook. If the status endpoint reads from a replica
(17.12) while the write went to the primary, a `404` is possible even with correct transactions. Route
reads-after-write for operations to the primary, or make the status endpoint tolerate the gap
explicitly.

## Code Example

The operation resource, with a lifecycle the client can rely on:

```python
# ledgerly/schemas/operation.py
from datetime import datetime
from enum import StrEnum
from typing import Literal
from pydantic import BaseModel, Field

class OperationStatus(StrEnum):
    PENDING = "pending"
    RUNNING = "running"
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    CANCELLED = "cancelled"
    EXPIRED = "expired"

TERMINAL = {OperationStatus.SUCCEEDED, OperationStatus.FAILED,
            OperationStatus.CANCELLED, OperationStatus.EXPIRED}

class OperationOut(BaseModel):
    id: str = Field(examples=["op_7c1a3e9b2d4f"])
    kind: Literal["invoice_export", "ledger_import", "vat_recalculation"]
    status: OperationStatus
    progress: float | None = Field(default=None, ge=0.0, le=1.0)
    created_at: datetime
    completed_at: datetime | None = None
    result: dict | None = None              # present iff status == succeeded
    error: ProblemDetails | None = None     # present iff status == failed (02.9)
    expires_at: datetime                    # when this record and its result are removed
```

Creating one — idempotent, and durable before the client is told about it:

```python
# ledgerly/routers/exports.py
@router.post("", status_code=status.HTTP_202_ACCEPTED, response_model=OperationOut,
             name="createInvoiceExport")
async def create_invoice_export(
    body: ExportRequest, response: Response, svc: ExportService, tenant: Tenant,
    api_key: ApiKeyId,
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key")],
) -> OperationOut:
    """202 because the work has been accepted, not done.

    The idempotency key matters more here than for a synchronous create: a
    client that times out waiting for the 202 and retries would otherwise start
    a second 40-minute export (02.8)."""
    operation = await svc.start_export(tenant, api_key, idempotency_key, body)

    response.headers["Location"] = f"/v1/operations/{operation.id}"
    response.headers["Retry-After"] = "5"       # tells the client HOW SOON to poll
    return OperationOut.model_validate(operation)
```

The service, where the atomicity requirement is honoured:

```python
# ledgerly/services/exports.py (excerpt)
async def start_export(self, tenant, api_key, idem_key, body) -> Operation:
    async with self._session.begin():                       # ONE transaction
        if replay := await claim_idempotency(self._session, tenant, api_key, idem_key, body):
            return replay                                    # same handle, no second export

        operation = await self._repo.create_operation(
            tenant, kind="invoice_export", status=OperationStatus.PENDING,
            expires_at=datetime.now(UTC) + RESULT_TTL,
        )
        # Enqueued via the outbox in the SAME transaction, so the job cannot exist
        # without the operation row, nor the row without the job (11.15).
        await self._outbox.enqueue(self._session, "export.requested",
                                   {"operation_id": operation.id, **body.model_dump()})
    return operation
```

The status endpoint, which guides the client's polling rather than leaving it to guess:

```python
# ledgerly/routers/operations.py
@router.get("/{operation_id}", response_model=OperationOut, name="getOperation")
async def get_operation(operation_id: str, response: Response,
                        svc: OperationService, tenant: Tenant) -> OperationOut:
    operation = await svc.get(tenant, operation_id)     # 404 if unknown in this tenant (01.3)

    if operation.status not in TERMINAL:
        # Server-directed polling: backs clients off as the job runs longer, so a
        # 40-minute export is not polled 2,400 times.
        elapsed = (datetime.now(UTC) - operation.created_at).total_seconds()
        response.headers["Retry-After"] = str(min(30, max(2, int(elapsed / 10))))
        response.headers["Cache-Control"] = "no-store"
    else:
        # Terminal states never change, so they are safely cacheable by the client.
        response.headers["Cache-Control"] = "private, max-age=300"   # 01.4
    return OperationOut.model_validate(operation)
```

## Design Patterns / Tradeoffs

### Delivering completion

**A. Client polls (`202` + status resource)**

- *How it works:* the client repeatedly `GET`s the operation until it is terminal.
- *Advantages:* works everywhere, including behind firewalls and NAT; no inbound connectivity needed;
  the client controls its own cadence; trivially resumable after a client crash — the URI is durable.
- *Disadvantages:* polling load scales with clients × frequency; latency to discovery is up to one poll
  interval; clients often poll far too aggressively.
- *Failure mode:* a non-terminal state that never terminates produces infinite polling — and a client
  that resubmits on `404` duplicates the work.
- *Use when:* the default. Always support it, even alongside webhooks.
- *Do NOT use when:* completion latency must be sub-second for a large client population.

**B. Webhook on completion**

- *Advantages:* no polling load; near-immediate notification; scales to many operations.
- *Disadvantages:* the client must run a public HTTPS endpoint; delivery is at-least-once, so the
  receiver needs idempotency; failed deliveries need retries and a dead-letter path; hard to develop
  against locally (02.11).
- *Failure mode:* the webhook is lost or the receiver is down, and a client with no polling fallback
  waits forever.
- *Use when:* many operations, server-side clients, and you have built the delivery machinery.
- *Do NOT use when:* it is the *only* mechanism. Always pair with polling as the source of truth.

**C. Server-Sent Events**

- *Advantages:* real-time progress, not just completion; one long-lived HTTP connection; native browser
  support; automatic reconnection with `Last-Event-ID` (12.4).
- *Disadvantages:* holds a connection per watching client, which competes with request capacity
  (12.11); reconnection and cross-replica fan-out need design (12.7); no value for a server-side client
  that just wants the result.
- *Use when:* a browser UI showing live progress on an operation a user is watching.
- *Do NOT use when:* the consumer is a batch integration.

**D. WebSocket** — overkill for this. WebSockets earn their cost when the client also needs to *send*
(12.6). For "tell me when this finishes", SSE or polling is simpler and more robust.

**Recommendation:** polling as the durable, always-available source of truth; webhooks as an optional
optimisation for server-side clients; SSE for browser progress. The combination — *webhook fires,
client fetches the operation to confirm* — is the mature pattern, because it makes the webhook a hint
rather than a fact you must not lose.

### Where the result lives

| | Inline in the operation body | A `download_url` (09.2) | A new resource URI |
|---|---|---|---|
| Size limit | Small (< ~100 KB) | Unbounded | Any |
| Expiry | With the operation record | Signed URL TTL (09.6) | Normal resource lifecycle |
| Use when | Summary, counts, small JSON | Exports, archives, reports | The operation created something addressable |

Ledgerly returns a signed, expiring `download_url` for exports and a resource URI for imports (which
create invoices). Whichever you choose, **document the retention period** — a client that polls a week
later must get `expired`, not `404`, so the distinction between "never existed" and "no longer kept"
is preserved.

## Production Scenario

**Ledgerly, month-end, 23:50.** Alerts fire for worker saturation: the export queue depth climbs from
a normal 3 to 1,400 in twenty minutes. Database CPU rises to 85%. Exports that normally take four
minutes are taking fifty.

### Symptoms

- `export_queue_depth`: 1,400 and climbing. Normal peak is ~20.
- `operations_created_total{kind="invoice_export"}`: **9,100 in 20 minutes**, against a month-end
  normal of ~400.
- The operations table shows the same tenants requesting near-identical exports repeatedly — one tenant
  has 214 pending exports for the same period.
- API logs show a very high rate of `404`s on `GET /v1/operations/{id}` — **11% of all status polls**.
- No deploy. The month-end traffic pattern is expected; the multiplication is not.

### Diagnosis

1. **Alert.** Queue depth. The first useful question — *are we slower, or is there more work?* — is
   answered by `operations_created_total`: there is 22× more work.
2. **Metrics.** 9,100 exports for ~400 genuine requests means clients are creating the same export many
   times. Something is causing resubmission.
3. **Logs.** The `404` rate on the status endpoint is the anomaly that explains it. Correlating one
   client's requests shows a clean, damning sequence:

```json
{"t":"23:51:02.140","route":"POST /v1/invoice-exports","status":202,"op":"op_7c1a3e"}
{"t":"23:51:02.190","route":"GET /v1/operations/op_7c1a3e","status":404}
{"t":"23:51:02.240","route":"POST /v1/invoice-exports","status":202,"op":"op_91b4d2"}
{"t":"23:51:02.290","route":"GET /v1/operations/op_91b4d2","status":404}
{"t":"23:51:02.341","route":"POST /v1/invoice-exports","status":202,"op":"op_c48e11"}
```

   Create, poll 50 ms later, get `404`, assume failure, create again. A tight loop, ~20 exports per
   second per client.

4. **Trace.** A trace of the `POST` shows the operation row committed at t+18 ms and the `202` returned
   at t+21 ms. The `GET` at t+50 ms should have found it — so the row exists but is not *visible* to
   the reader.
5. **The decisive detail:** the status endpoint reads from a **read replica** (17.12), added six weeks
   earlier to offload list queries. Replica lag at month-end peaks at **900 ms**. A client polling
   50 ms after creation reads a replica that has not yet received the row.
6. **Root cause confirmed** by pinning the status endpoint to the primary in a canary and watching the
   `404` rate for that instance drop to zero.

### Root Cause

Two decisions combined into an amplifying loop:

1. **The status endpoint read from a replica.** Under month-end lag, a freshly created operation was
   not yet visible, so its first poll returned `404`.
2. **`404` was the wrong status for "not yet visible", and the client's interpretation of it was
   reasonable.** `404` means "this does not exist". The client's SDK treated it as a failed submission
   and retried the submission — which is exactly what a well-written client should do with a `404`
   (01.3).

Each retry created another 40-minute export job, which deepened the queue, which slowed the workers,
which increased replica lag, which produced more `404`s. A textbook amplification loop: the failure
response caused more load, which caused more failures (15.14's retry-storm shape, arriving through a
different door).

The idempotency key would have prevented the duplication — but the SDK generated a **new key per
attempt**, because it treated each retry as a new operation rather than a retry of the same intention
(02.8's "a key names an intention" lesson, violated).

### Fix

*Mitigation (11 minutes):*

1. Route `GET /v1/operations/{id}` to the primary. `404` rate falls to 0.02% immediately and the
   resubmission loop stops.
2. Pause the export workers, deduplicate the queued jobs by `(tenant, period, format)`, and requeue the
   ~400 genuine ones.

*Permanent fix:*

1. **Read-after-write consistency for operations.** Status reads go to the primary. Operations are
   low-volume and latency-sensitive at creation; list endpoints keep using the replica.
2. **Idempotency key derived from the intention, in the SDK**: `hash(tenant, kind, parameters)` by
   default, so a retry of the same export is the same key and returns the same handle (02.8).
3. **A grace window on the status endpoint.** If the operation id is well-formed, unknown, and *recent*
   by its embedded timestamp, return `202 Accepted` with `Retry-After: 1` rather than `404` — "not yet,
   ask again" instead of "does not exist". This closes the race for any future replication gap:

```python
@router.get("/{operation_id}", response_model=OperationOut)
async def get_operation(operation_id: str, svc, tenant):
    operation = await svc.get(tenant, operation_id)
    if operation is None:
        if svc.is_recently_issued_id(operation_id, within=timedelta(seconds=10)):
            # Well-formed and recent: it exists, we just cannot see it yet.
            return JSONResponse(
                status_code=202,
                content={"id": operation_id, "status": "pending"},
                headers={"Retry-After": "1"},
            )
        raise HTTPException(404, "No such operation.")
```

   The `202` is *returned* as a `JSONResponse` with `Retry-After` set on it directly, not raised:
   a 2xx via `HTTPException` would produce FastAPI's `{"detail": …}` body instead of the operation
   shape, and any header set on an injected `Response` is dropped when an exception is raised
   (the same trap called out in 02.8's router).

4. **Documented client contract**: never resubmit on a `404` from the status endpoint within the first
   30 seconds; always reuse the idempotency key when retrying a submission.

### Prevention

- **A replication-lag test in CI** that creates an operation and immediately polls it against a stack
  with an artificially lagged replica, asserting no `404`:

```python
@pytest.mark.anyio
async def test_operation_is_visible_immediately_despite_replica_lag(client, auth, lagged_replica):
    created = await client.post("/v1/invoice-exports", json=EXPORT, headers=auth)
    assert created.status_code == 202
    location = created.headers["Location"]
    # Poll immediately, with the replica deliberately 2s behind.
    async with lagged_replica(seconds=2):
        first_poll = await client.get(location, headers=auth)
    assert first_poll.status_code != 404, (
        "a freshly issued operation handle must never 404 — clients resubmit on 404 (02.10)"
    )
```

- **Alert on the `404` ratio of the status endpoint.** For an endpoint whose ids you issue yourself, a
  `404` rate above ~0.1% means your own handles are not resolving. That single metric detects the
  entire class.
- **Alert on the ratio of operations created to distinct idempotency keys.** Above 1.2 means clients are
  duplicating work, which is a leading indicator of exactly this loop.
- **Design rule: never return a handle to something that is not yet durably readable.** Applies to
  operations, uploads (09.2), and any resource whose id you hand back before commit.
- **Design rule: a `4xx` must not make a client do more work.** `404` invited a resubmission. The
  correct response for "not yet" is `202` or `409` with `Retry-After` — a status that means *wait*,
  not *start again* (01.3).

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the client polls before the operation is visible? | It must not `404`. Read from the primary, or return `202` + `Retry-After` for recent well-formed ids. |
| ...the worker crashes mid-operation? | A lease and reaper must transition it to `failed` (11.5, 11.8). A permanently `running` operation makes clients poll forever. |
| ...the client crashes and restarts? | It refetches the operation by URI. This is polling's main advantage — the handle is durable. |
| ...a webhook delivery is lost? | Without a polling fallback the client waits forever. Webhooks are a hint; the operation resource is the truth. |
| ...the client polls every 100 ms for 40 minutes? | 24,000 requests. Send `Retry-After` and rate-limit the status endpoint (02.12). |
| ...the client retries the submission? | Without an idempotency key it starts a second job. With one, it gets the same handle (02.8). |
| ...the result is requested after its TTL? | `expired`, not `404` — preserve the difference between "never existed" and "no longer kept". |
| ...the queue backs up? | Operations sit in `pending` longer. Expose queue position or an ETA, and shed new submissions before the queue becomes unbounded (11.14). |
| ...the client cancels? | Support `DELETE /v1/operations/{id}` → `cancelled`, and make the worker check for cancellation between units of work (04.8). |

## Common Pitfalls

**Returning a handle before the record is durably visible.** The incident above. *Instead:* commit the
operation and the job enqueue in one transaction, and read status from the primary.

**`404` for "not yet".** It means "does not exist", so clients resubmit. *Instead:* `202` with
`Retry-After` for recent, well-formed ids.

**Non-terminal states that never terminate.** A crashed worker leaves `running` forever. *Instead:* a
lease with a reaper that fails stale operations.

**No `Retry-After`.** Clients invent a poll interval, usually far too short. *Instead:* direct the
cadence from the server, and back it off as the job runs longer.

**Webhooks as the only delivery mechanism.** One lost delivery means a client waits indefinitely.
*Instead:* webhook as a hint, polling as the source of truth.

**No idempotency on the submission.** A timeout on the `202` starts a second expensive job.
*Instead:* require a key, and derive it from the intention in your SDK.

**Results with no expiry, or expiry with no state.** Either the table grows forever, or clients see
`404` and cannot tell whether they mistyped an id. *Instead:* an `expired` state with a documented TTL.

**Polling the wrong thing.** If the operation mutates an existing resource, let clients poll *that*
resource's state rather than inventing an operation record they must also learn about.

## How to Test This

- The replication-lag test above — the one that encodes the incident.
- A worker-crash test: start an operation, kill the worker, assert the operation reaches `failed`
  within the lease window rather than sitting `running`.
- An idempotency test: submit the same export twice with one key, assert one operation and one job.
- A cancellation test: cancel a running operation and assert the worker stops within one work unit.
- A TTL test: age an operation past `expires_at` and assert `expired`, not `404`.

## Interview Questions

1. *Explain.* How do you decide an operation should be asynchronous? — Compare its p99 against the
   request timeout budget, not its average.
2. *Design.* Design an API for a 40-minute export. What does the client see at each step? — `202` +
   `Location` + `Retry-After`, an operation resource with terminal states, a signed result URL.
3. *Debug this.* Queue depth is 22× normal, clients are resubmitting, and 11% of status polls `404`.
   — A visibility race; the status read is served by a lagging replica and `404` invites resubmission.
4. *Explain.* Why must the operation row and the job enqueue share a transaction? — Otherwise one can
   exist without the other: a handle that never resolves, or a job with no record.
5. *Explain.* Why is a webhook insufficient on its own? — At-least-once delivery can still be lost;
   without a pollable source of truth the client has no recovery.
6. *Design.* How do you stop a client polling every 100 ms? — `Retry-After` with server-directed
   backoff, plus a rate limit on the status endpoint.
7. *Explain.* What must happen if a worker dies mid-operation? — A lease expires and a reaper moves it
   to a terminal state, or clients poll forever.

## Key Takeaways

- Move work out of the request when its **p99** approaches your timeout budget — averages hide the
  tenant that is already failing.
- Model the operation as a **resource** with a URI, an explicit lifecycle, terminal states and a
  documented retention period.
- **Never hand back a handle to something that is not yet durably readable.** Commit the record and the
  job together, and serve status reads from the primary.
- `404` means "does not exist" and therefore invites resubmission. For "not yet", use `202` with
  `Retry-After`. A `4xx` must never make a client do more work.
- Every non-terminal state needs a path to a terminal one, driven by a lease and a reaper — not by hope.
- Send `Retry-After` and back it off. Polling cadence is your decision, not the client's guess.
- Webhooks are a **hint**; the operation resource is the truth. Support polling always.
- Require an idempotency key on submission, and derive it from the intention so retries do not start
  second jobs.
