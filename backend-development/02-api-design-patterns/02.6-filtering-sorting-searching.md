# 02.6 Filtering, Sorting and Searching

> **Prerequisites:** 02.5 (pagination and sort keys), 02.1 (query string vs path)
> **What you'll learn:**
> - Design a filter vocabulary that stays consistent as the API grows
> - Treat every sortable and filterable field as an **index commitment**, not a free feature
> - Recognise why passing a user-supplied column name to the ORM is both a performance and a security defect
> - Know when `ILIKE '%term%'` stops being acceptable and what replaces it
> **Level:** Beginner

---

## Concept

### Plain-English Explanation

Listing endpoints attract features. A client asks to filter by status, then by date range, then to
sort by amount, then to search customer names. Each request is small and reasonable, and the easy way
to grant them all at once is to accept a field name from the client and pass it to the database.

That shortcut is where two different problems begin. The performance one: a field the client can sort
by is a field the database must be able to sort *efficiently*, which means an index — and an index is
a permanent cost on every write. The security one: a column name that arrives from the internet and
reaches your SQL is an injection surface if you build the query as a string.

The discipline is short: **decide which fields are filterable and sortable, write them down, and
reject everything else.** A closed list is not a limitation; it is the only version of this feature
you can operate.

### Technical Explanation

**Filter styles.** Three conventions are common, and the only wrong answer is using more than one:

```text
A. Flat, explicit names          ?status=open&created_after=2026-08-01&amount_min=10000
   readable, self-documenting, trivially typed in OpenAPI (02.4)
   verbose as operators multiply

B. Bracketed operators           ?created_at[gte]=2026-08-01&amount_cents[lt]=10000
   uniform and compact; awkward in generated SDKs; needs custom parsing

C. Filter expression language    ?filter=status eq 'open' and amount_cents gt 10000
   powerful (OData, RSQL); a parser you own; unbounded cost (02.2's lesson)
```

Ledgerly uses **A**. It costs a few extra parameter names and buys typed OpenAPI parameters, generated
SDK arguments, per-parameter validation, and a cost model you can reason about — every filter maps to
a query you have seen and indexed.

**Sorting.** A sort parameter names a field and a direction: `?sort=-created_at` (leading `-` for
descending) or `?sort=created_at:desc`. Two rules make it safe:

1. **The field must be on an allow-list.** Anything else is `400`.
2. **The sort must be total** — append the primary key as a tiebreaker, or pagination breaks (02.5).

**The index commitment.** Sorting a column with no matching index means PostgreSQL reads every
matching row and sorts them:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM invoices WHERE tenant_id='t_44f1' ORDER BY notes DESC LIMIT 50;

Limit  (actual time=8241.117..8241.140 rows=50 loops=1)
  ->  Sort  (actual time=8241.115..8241.130 rows=50 loops=1)
        Sort Key: notes DESC
        Sort Method: external merge  Disk: 2304112kB     ← 2.3 GB spilled to disk
        Buffers: shared hit=12 read=1841204, temp read=288014 written=288014
        ->  Seq Scan on invoices (actual time=0.019..3980.442 rows=4102338 loops=1)
Execution Time: 8319.884 ms
```

Two details are worth reading closely. `Sort Method: external merge Disk: 2304112kB` means the sort
did not fit in `work_mem` and spilled to temporary files — disk I/O that competes with everything
else on the instance. And `shared hit=12 read=1841204` means almost nothing came from cache, so this
one query evicted much of the buffer pool and left *other* queries slow after it finished. That is how
one client's sort degrades an entire database (05.6, 05.7).

**Searching** is a different problem from filtering. `WHERE name ILIKE '%nordwind%'` cannot use a
B-tree index — a leading wildcard means the index's ordering is useless — so it is a sequential scan
every time. It is fine at ten thousand rows and unusable at ten million. The replacements, in
increasing order of capability: a trigram index (`pg_trgm`) for fuzzy substring matching, PostgreSQL
full-text search for word-based relevance (05.8), or a dedicated search engine when you need scoring
and faceting.

### Mental Model

> Every filterable and sortable field is a **standing promise to answer a query efficiently**, and a
> promise costs an index, which costs write throughput and storage. Publish a closed list of fields
> you have made that promise for, and reject the rest with a clear `400`. A field the client can name
> but you have not indexed is an outage that has not happened yet.

## How It Works

The safe pattern in one picture — the client never names a database column:

```text
  ?sort=-amount_cents&status=open&created_after=2026-08-01
              │
              ▼
   parse and validate against a CLOSED registry
              │
   ┌──────────┴────────────────────────────────────────────┐
   │ SORTABLE = {                                          │
   │   "created_at":   Invoice.created_at,   ← ix_tenant_created_id
   │   "amount_cents": Invoice.amount_cents, ← ix_tenant_amount_id
   │   "due_date":     Invoice.due_date,     ← ix_tenant_due_id
   │ }   every entry has a matching index, verified in CI  │
   └──────────┬────────────────────────────────────────────┘
              │  unknown field → 400 with the permitted list
              ▼
   SQLAlchemy column object (never a string) → ORDER BY amount_cents DESC, id DESC
```

The registry does three jobs at once: it is the allow-list, it is the mapping from public name to
internal column (so renaming a column is not a breaking change — 02.3), and it is the list that a CI
test walks to assert an index exists for each entry.

**Filter semantics that need deciding once, explicitly:**

| Question | Ledgerly's answer |
|---|---|
| Multiple values for one filter | `?status=open&status=overdue` → `IN (…)`, capped at 20 values |
| Combining different filters | `AND`. `OR` is not expressible; that is deliberate (it is where cost models die) |
| Ranges | Explicit pairs: `created_after` / `created_before`, half-open `[after, before)` |
| Unknown filter parameter | **`400`**, not ignored — see the pitfall below |
| Null / unset | `?due_date=null` is ambiguous; use `?has_due_date=false` |
| Case sensitivity | Documented per field: `status` exact, `email` case-insensitive via a functional index |

The "unknown parameter" decision is the one that matters most and is most often got wrong. Ignoring
`?statuss=open` returns every invoice — the client sees data, assumes the filter worked, and acts on
a wrong result set. A `400` naming the unknown parameter turns a silent wrong answer into a
five-second fix.

## Code Example

The registry, which is the whole design:

```python
# ledgerly/query/sorting.py
from dataclasses import dataclass
from sqlalchemy import UnaryExpression
from sqlalchemy.orm import InstrumentedAttribute

from ledgerly.models import Invoice

@dataclass(frozen=True, slots=True)
class SortableField:
    column: InstrumentedAttribute
    index_name: str          # asserted to exist by a CI test — see How to Test This

# CLOSED registry. Adding an entry REQUIRES adding an index in the same pull request.
INVOICE_SORTABLE: dict[str, SortableField] = {
    "created_at":   SortableField(Invoice.created_at,   "ix_invoices_tenant_created_id"),
    "amount_cents": SortableField(Invoice.amount_cents, "ix_invoices_tenant_amount_id"),
    "due_date":     SortableField(Invoice.due_date,     "ix_invoices_tenant_due_id"),
    "number":       SortableField(Invoice.number,       "ix_invoices_tenant_number"),
}

class InvalidSort(ValueError): ...

def parse_sort(raw: str, registry: dict[str, SortableField]) -> list[UnaryExpression]:
    """'-created_at' → [created_at DESC, id DESC]. The tiebreaker keeps the order
    total so cursor pagination stays correct (02.5)."""
    descending = raw.startswith("-")
    field = raw.lstrip("-+")
    if field not in registry:
        raise InvalidSort(
            f"Cannot sort by {field!r}. Sortable fields: {', '.join(sorted(registry))}."
        )
    column = registry[field].column
    primary = column.desc() if descending else column.asc()
    return [primary, Invoice.id.desc() if descending else Invoice.id.asc()]
```

The filter parameters are declared as typed query parameters, so validation and documentation come
from the same declaration (02.4):

```python
# ledgerly/query/invoice_filters.py
from datetime import datetime
from typing import Annotated, Literal
from fastapi import Query
from pydantic import BaseModel, Field, model_validator

InvoiceStatus = Literal["draft", "open", "partially_paid", "overdue", "paid", "void"]

class InvoiceFilters(BaseModel):
    # extra="forbid": an unknown query parameter is a 422, not a silently ignored
    # filter that returns the whole collection. See the pitfall below.
    model_config = {"extra": "forbid"}

    status: Annotated[list[InvoiceStatus] | None, Query(max_length=20)] = None
    customer_id: str | None = None
    created_after: datetime | None = None
    created_before: datetime | None = None
    amount_min_cents: Annotated[int | None, Field(ge=0)] = None
    amount_max_cents: Annotated[int | None, Field(ge=0)] = None

    @model_validator(mode="after")
    def ranges_must_be_ordered(self) -> "InvoiceFilters":
        if (self.created_after and self.created_before
                and self.created_after >= self.created_before):
            raise ValueError("created_after must be earlier than created_before")
        if (self.amount_min_cents is not None and self.amount_max_cents is not None
                and self.amount_min_cents > self.amount_max_cents):
            raise ValueError("amount_min_cents must not exceed amount_max_cents")
        return self
```

Applying them — note that no user-supplied string ever reaches the SQL:

```python
# ledgerly/repositories/invoices.py (excerpt)
def apply_filters(statement, filters: InvoiceFilters):
    if filters.status:
        statement = statement.where(Invoice.status.in_(filters.status))
    if filters.customer_id:
        statement = statement.where(Invoice.customer_id == filters.customer_id)
    if filters.created_after:
        statement = statement.where(Invoice.created_at >= filters.created_after)
    if filters.created_before:
        statement = statement.where(Invoice.created_at < filters.created_before)  # half-open
    if filters.amount_min_cents is not None:
        statement = statement.where(Invoice.amount_cents >= filters.amount_min_cents)
    if filters.amount_max_cents is not None:
        statement = statement.where(Invoice.amount_cents <= filters.amount_max_cents)
    return statement
```

⚠️ Contrast with the version that caused the incident below:

```python
# ❌ NEVER. Two defects in one line.
statement = statement.order_by(text(f"{sort_field} {direction}"))
#   1. Any column can be sorted — including unindexed ones (a full scan and disk sort).
#   2. `text()` with an f-string is SQL injection: ?sort=id;DROP TABLE invoices--
#      SQLAlchemy does not sanitise text(); it passes it through (16.2).
```

## Design Patterns / Tradeoffs

### Closed allow-list (✅ recommended)

- *How it works:* a registry maps public field names to columns; anything unlisted is `400`.
- *Advantages:* every permitted query has a known plan and a known index; no injection surface; public
  names are decoupled from column names, so refactoring storage is not a breaking change (02.3); the
  permitted set appears in OpenAPI and generated SDKs.
- *Disadvantages:* every new filter is a code change and a pull request; clients occasionally want a
  field you have not enabled.
- *Failure mode:* the registry drifts from the indexes — someone adds an entry and forgets the index.
  Prevent it with the CI test below.
- *Use when:* always, for public APIs.

### Pass-through field names

- *Advantages:* no work; every field is instantly filterable and sortable.
- *Disadvantages:* injection surface if strings reach SQL; unindexed sorts scan and spill; the public
  API becomes your column names, so a rename is a breaking change; unbounded cost.
- *Use when:* never on a public API. An internal admin tool behind strong authentication is the only
  defensible case, and even then the performance problem remains.

### Filter expression languages (OData, RSQL, custom DSL)

- *Advantages:* very expressive; one parameter serves every combination; familiar to enterprise
  integrators.
- *Disadvantages:* you own a parser and its bugs; arbitrary `OR`/`NOT` combinations defeat index
  planning; cost is client-controlled — the same structural problem as GraphQL (02.2); hard to
  document, hard to generate SDKs for, hard to rate-limit.
- *Use when:* an enterprise product where flexible querying is the feature, and you are prepared to
  build a cost model, a complexity limit and a query-plan guard.
- *Do NOT use when:* you would be shipping it without those three things.

### Substring search: `ILIKE` vs trigram vs full-text

| | `ILIKE '%term%'` | `pg_trgm` GIN index | Full-text search (05.8) |
|---|---|---|---|
| How it works | Sequential scan, per-row comparison | Trigram index on substrings | Lexemes, stemming, ranking |
| Cost at 10M rows | Seconds; scales linearly | Milliseconds | Milliseconds |
| Typo tolerance | None | Similarity scoring | Stemming, not typos |
| Ranking | None | Similarity score | Relevance ranking |
| Index cost | None | Large index, slower writes | Moderate; needs a `tsvector` column |
| Use when | < ~100k rows, admin tools | Fuzzy substring on names, codes | Word search over prose |

**Recommendation:** start with `ILIKE` and a hard row-count ceiling; move to `pg_trgm` when the table
outgrows it. Reach for a dedicated search engine only when you need relevance tuning and faceting,
because it adds a system that can be down and data that can be stale (19.7).

## Production Scenario

**Ledgerly, Tuesday 14:05.** Database CPU jumps to 100% and stays there. API p99 across every endpoint
goes from 90 ms to 6 s. Disk read throughput on the primary goes from 40 MB/s to 900 MB/s. No deploy
in four days.

### Symptoms

- All tenants affected, not just one. Every endpoint slow, including endpoints that do trivial work —
  the classic signature of a *shared resource* being saturated (15.17).
- `pg_stat_database.temp_files` for the invoices database: **412 files in ten minutes**, against a
  normal rate of near-zero.
- Request rate is flat. Nothing is retrying. No traffic anomaly at all.
- The dashboard graph that finally isolates it is `temp_bytes`, which nobody normally looks at.

### Diagnosis

1. **Alert.** Database CPU and API latency SLO. First hypothesis — a traffic spike — is dead within a
   minute because request rate is flat. **Load up, requests flat** means cost-per-request changed
   (the same reasoning as 02.2).
2. **Metrics.** `temp_files` and `temp_bytes` spiking is a specific signal: queries are sorting or
   hashing more data than `work_mem` allows and spilling to disk. That narrows it to a sort or a
   large join, immediately.
3. **Logs → `pg_stat_statements`**, ordered by total time, names the query in one row:

```sql
SELECT queryid, calls, mean_exec_time::int AS mean_ms, temp_blks_written, query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 3;

 calls | mean_ms | temp_blks_written | query
-------+---------+-------------------+-------------------------------------------------
    47 |    8319 |          13500456 | SELECT ... FROM invoices WHERE tenant_id = $1
       |         |                   |   ORDER BY notes DESC LIMIT $2 OFFSET $3
  3812 |       4 |                 0 | SELECT ... FROM invoices WHERE tenant_id = $1
       |         |                   |   ORDER BY created_at DESC, id DESC LIMIT $2
```

   47 calls consuming more total time than 3,812 calls of the normal query. And the sort key is
   `notes` — a free-text column with no index and no business reason to sort by.

4. **`EXPLAIN (ANALYZE, BUFFERS)`** produces the plan shown earlier in this notebook: sequential scan
   over 4.1 M rows, external merge sort spilling 2.3 GB to disk, buffer pool evicted.
5. **Trace back to the caller.** Access logs show one API key, a customer's new "advanced reporting"
   integration, issuing `?sort=notes` while paging with `offset` (02.5) — so each of the 47 calls was
   re-scanning and re-sorting the entire table.
6. **Read the route** to find why an arbitrary column was accepted:

```python
# as it was
sort = request.query_params.get("sort", "created_at")
direction = "DESC" if sort.startswith("-") else "ASC"
statement = statement.order_by(text(f"{sort.lstrip('-')} {direction}"))
```

### Root Cause

The list endpoint passed the client's `sort` parameter straight into `text()`. Any column could be
named, including unindexed ones, and each such request became a full table scan plus a disk-spilling
sort. Combined with offset pagination, one integration paging through its results re-ran that scan for
every page.

There was also a latent **SQL injection**: `text()` performs no sanitisation, so `?sort=id;--` and
worse were syntactically reachable. The customer had not exploited it; a security review had not found
it; it had shipped fourteen months earlier in a pull request titled *"make list endpoints sortable"*.

One line of code carried both a performance defect and a critical vulnerability, and it looked
entirely ordinary.

### Fix

*Mitigation (6 minutes):* block `sort` values outside the known-good set at the proxy (01.10), which
restores database health immediately without a deploy. Then, at minute 20, ship the allow-list.

*Permanent fix:*

1. **The registry and `parse_sort`** shown above. Unknown fields return `400` with the permitted list,
   so the customer's integration got an actionable error instead of a slow answer.
2. **Indexes for every registry entry**, added in the same change:

```sql
CREATE INDEX CONCURRENTLY ix_invoices_tenant_amount_id
    ON invoices (tenant_id, amount_cents DESC, id DESC);
CREATE INDEX CONCURRENTLY ix_invoices_tenant_due_id
    ON invoices (tenant_id, due_date DESC, id DESC);
```

3. **`extra="forbid"` on the filter model**, so unknown query parameters are rejected rather than
   ignored — closing the related failure where `?statuss=open` silently returns everything.
4. **A `statement_timeout` for API requests** (05.7), set to 5 s. A single query can no longer run for
   8 seconds regardless of what future defect allows it. This is the defence-in-depth layer: it does
   not prevent the bug, it bounds the blast radius.

*Customer follow-up:* the reporting integration genuinely wanted to search notes. Ledgerly added a
`?query=` parameter backed by a trigram index — the right feature, delivered deliberately, with an
index behind it.

### Prevention

- **A CI test asserting every sortable field has its index**, which is what keeps the registry honest:

```python
# tests/query/test_sortable_fields_are_indexed.py
import pytest
from sqlalchemy import inspect
from ledgerly.query.sorting import INVOICE_SORTABLE

@pytest.mark.parametrize("name,field", sorted(INVOICE_SORTABLE.items()))
def test_sortable_field_has_a_supporting_index(sync_engine, name, field) -> None:
    existing = {ix["name"] for ix in inspect(sync_engine).get_indexes("invoices")}
    assert field.index_name in existing, (
        f"sortable field {name!r} declares index {field.index_name!r}, which does not "
        "exist: sorting by it will sequentially scan and spill to disk (02.6)"
    )
```

- **A lint rule banning `text()` with an f-string or `%` formatting** anywhere in the codebase. This is
  the generic control for the injection half (16.2), and it is a one-line `ruff` custom rule or a
  grep-based CI check.
- **Alert on `temp_files` and `temp_bytes`.** Disk-spilling sorts are almost always a missing index or
  a query that should not have been permitted. This metric detects the whole class before it becomes
  an outage, and nobody had it on a dashboard.
- **`statement_timeout` on the API's database role.** Any single query that runs longer than a request
  should live is a bug; failing it fast turns a database-wide outage into one client's `500`.
- **A design rule with teeth:** a pull request that adds a sortable or filterable field must add the
  index in the same commit. The CI test enforces it, so it is not a matter of remembering.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a client sorts by an unindexed column? | Sequential scan plus a disk-spilling sort that evicts the buffer pool for everyone. Allow-list prevents it. |
| ...a client sends an unknown filter parameter? | With `extra="forbid"`, `422`. Without it, the filter is ignored and the client acts on the whole collection. |
| ...a client passes `?sort=id;DROP TABLE…`? | Harmless with a registry lookup; catastrophic with `text()` and string formatting (16.2). |
| ...a filter matches millions of rows? | Pagination bounds the response, but not the sort. Indexes and `statement_timeout` bound the work. |
| ...a client sends 5,000 values to an `IN` filter? | Plan time explodes. Cap list lengths in the schema (`max_length=20`). |
| ...`ILIKE '%term%'` runs on a 40 M-row table? | Sequential scan every time. Move to trigram or full-text (05.8). |
| ...you rename a database column? | With a registry, change one mapping. With pass-through names, it is a breaking API change (02.3). |
| ...traffic increases 10×? | Allow-listed queries scale with their indexes. One unindexed sort does not scale at all. |

## Common Pitfalls

**Passing a client-supplied field name to the ORM or to `text()`.** Both an injection vector and an
unbounded performance risk. *Instead:* a closed registry mapping public names to column objects.

**Ignoring unknown query parameters.** `?statuss=open` returns everything and the client believes it
filtered. Silent wrong answers are worse than errors. *Instead:* `extra="forbid"` → `422`.

**Adding a sortable field without an index.** The feature works in staging with 500 rows and takes the
database down at 4 million. *Instead:* index in the same pull request, asserted by CI.

**Sorting without a tiebreaker.** Non-unique sort keys break cursor pagination at page boundaries
(02.5). *Instead:* always append the primary key.

**Inclusive date ranges.** `created_before=2026-08-31` — does it include the 31st? Half the clients
assume one, half the other. *Instead:* half-open `[after, before)`, documented explicitly.

**`OR` across arbitrary filters.** Defeats index selection and makes cost unpredictable. *Instead:*
`AND` only; if a client needs `OR`, add a specific named filter for that case.

**Exposing column names as public parameter names.** Your storage schema becomes your API contract
(02.4's lesson in another form). *Instead:* map public names to columns in the registry.

## How to Test This

- The sortable-field/index test above — the control that keeps the registry and the schema in step.
- A test that an unknown `sort` value returns `400` and names the permitted fields.
- A test that an unknown query parameter returns `422`.
- A plan assertion for each sortable field: run `EXPLAIN` and assert the plan contains an index scan
  and no `Sort` node (13.5 covers wiring `EXPLAIN` into tests).
- A grep-based CI check for `text(f"` and `text("... %s"` anywhere in the repository.

## Interview Questions

1. *Explain.* Why is every sortable field an index commitment? — Without an index the database scans
   and sorts, spilling to disk and evicting the buffer pool for every other query.
2. *Debug this.* Database CPU at 100%, request rate flat, `temp_files` spiking. — A disk-spilling sort
   or hash; find it in `pg_stat_statements`, then `EXPLAIN (ANALYZE, BUFFERS)`.
3. *Explain.* What is wrong with `order_by(text(f"{field} {direction}"))`? — SQL injection, plus an
   unbounded set of unindexed sorts.
4. *Design.* A client asks to filter invoices by any field. What do you offer? — A closed allow-list
   with indexes; add fields on request; explain the cost model.
5. *Explain.* Why reject unknown query parameters instead of ignoring them? — Ignoring returns the
   whole collection while the client believes it filtered.
6. *Explain.* When does `ILIKE '%x%'` stop working, and what replaces it? — When the table outgrows a
   sequential scan; trigram index, then full-text search.
7. *Design.* Should date range filters be inclusive or exclusive? — Half-open `[after, before)`,
   documented, so ranges compose without overlap.

## Key Takeaways

- Filtering and sorting look like free features and are actually **standing performance commitments**.
  Each one costs an index; each index costs write throughput.
- Use a **closed registry** mapping public field names to column objects. It is simultaneously the
  allow-list, the injection defence, and the decoupling from your storage schema.
- Never let a client-supplied string reach SQL. `text()` does not sanitise anything.
- **Reject unknown parameters.** A silently ignored filter returns the whole collection and the client
  cannot tell.
- Sorts must be total — append the primary key, or pagination breaks.
- Watch `temp_files` and `temp_bytes`. A disk-spilling sort is a missing index announcing itself, and
  it degrades every other query on the instance.
- Set `statement_timeout` on the API's database role, so one bad query bounds its own blast radius.
