## Concept

### Plain-English Explanation

Pagination exists because "give me all the invoices" is not a question your server can safely answer.
Ten million rows would exhaust memory, saturate the network, and take longer than any timeout. So you
hand back a slice at a time.

The obvious way to do that is to count: *skip the first 200, give me the next 50.* It works
immediately, it is what every tutorial shows, and it has two problems that do not appear until you
have real data and real users.

The first is that skipping is not free — the database must walk past all 200 rows to find row 201,
so page 10,000 costs ten thousand times what page 1 costs. The second is subtler and much worse:
**a position defined by counting is only meaningful if nothing changes while you are reading.** Rows
are being inserted and deleted the whole time you are paging, so the window slides underneath you and
you silently skip records. Not an error — just missing data, discovered weeks later by an accountant.

### Technical Explanation

**Offset pagination.** `LIMIT 50 OFFSET 200`. The database finds matching rows in sort order,
discards the first 200, and returns the next 50. The discarding is real work — it reads and throws
away every skipped row.

```sql
EXPLAIN ANALYZE
SELECT * FROM invoices WHERE tenant_id = 't_44f1'
ORDER BY created_at DESC LIMIT 50 OFFSET 500000;

Limit  (cost=612840.11..612901.42 rows=50) (actual time=4127.883..4127.902 rows=50 loops=1)
  ->  Index Scan Backward using ix_invoices_tenant_created on invoices
        (actual time=0.041..4085.223 rows=500050 loops=1)   ← read 500,050 rows to return 50
Execution Time: 4128.114 ms
```

That `rows=500050` is the whole problem in one number: 4.1 seconds of work to produce 50 rows, and
the cost grows linearly with page depth no matter how good your index is.

**Keyset (seek) pagination.** Instead of counting rows, *name the last row you saw* and ask for
everything after it:

```sql
SELECT * FROM invoices
WHERE tenant_id = 't_44f1'
  AND (created_at, id) < ('2026-08-24 09:41:02+00', 'inv_9f2c41')   -- row-value comparison
ORDER BY created_at DESC, id DESC LIMIT 50;

Limit  (actual time=0.038..0.271 rows=50 loops=1)
  ->  Index Scan Backward using ix_invoices_tenant_created_id on invoices
        (actual time=0.036..0.254 rows=50 loops=1)          ← read 50 rows to return 50
Execution Time: 0.318 ms
```

Same page, **13,000× faster**, and the cost is constant regardless of depth. The database seeks
directly into the index to the named position.

⚠️ The comparison must be a **row-value comparison** over the full sort key, not
`created_at < :ts AND id < :id`. The latter is wrong — it excludes rows with the same timestamp and a
larger id. PostgreSQL supports `(a, b) < (:a, :b)` natively and can use a composite index for it.

**Cursor pagination** is keyset pagination with the position encoded as an opaque token. The client
gets `cursor=eyJ2IjoxLCJjIjoiMjAyNi0wOC0yNC4uLg`, which it echoes back. The opacity is the point: the
client cannot construct or modify a position, so you can change the sort key, add a tiebreaker, or
switch storage without breaking anyone.

**The stability problem**, which is the real reason to care:

```text
Offset pagination while rows are being inserted at the head of the list:

 t=0  page 1: OFFSET 0  LIMIT 3   ──▶ [ I9  I8  I7 ]
                                        list: I9 I8 I7 I6 I5 I4 …

 t=1  two new invoices arrive       ──▶ list: I11 I10 I9 I8 I7 I6 I5 I4 …
                                                       └──────┘
 t=2  page 2: OFFSET 3  LIMIT 3   ──▶ [ I8  I7  I6 ]
                                        ⚠️ I8 and I7 are RETURNED TWICE,
                                        and nothing is missing yet …

 …but paging a list where rows are DELETED (or when sorting ascending while
 inserts happen at the head) shifts the window the other way and rows are SKIPPED
 ENTIRELY. No error. No duplicate. Just absent.

Keyset pagination over the same mutating list:

 t=0  page 1: (no cursor)          ──▶ [ I9  I8  I7 ]   cursor = after I7
 t=2  page 2: after=I7             ──▶ [ I6  I5  I4 ]   ✅ exact, regardless of
                                                            what happened at the head
```

**Total counts.** `SELECT count(*)` over a filtered set is a full scan of the matching rows and often
costs more than the page itself. A UI that shows "Page 3 of 4,912" is paying that on every request.
Alternatives: omit it, return an estimate from `pg_class.reltuples`, cap it (`"999+"`), or compute it
only when explicitly requested.

### Mental Model

> A page is **a position in a list that is still changing**. Offset names that position by *counting
> from the start*, which is only correct if the start never moves. Keyset names it by *the value of
> the last row you saw*, which stays correct no matter what happens elsewhere in the list. Counting
> is why offset pagination is both slow and lossy — one cause, two symptoms.

## How It Works

Keyset pagination has exactly one hard requirement: **a total order**. The sort key must be unique,
or two rows compare equal and the seek is ambiguous — you will skip or repeat rows at page
boundaries.

`created_at` alone is not unique: two invoices created in the same millisecond tie. The fix is to
append a unique tiebreaker, always:

```text
sort key = (created_at DESC, id DESC)        ← id makes the order total
index    = (tenant_id, created_at DESC, id DESC)
             └── the tenant filter must LEAD the index, or the seek scans other
                 tenants' rows before finding yours (05.4, 05.5)
```

The cursor carries the whole sort key, plus enough context to detect misuse:

```text
cursor payload (before encoding)
{
  "v": 1,                                   schema version — lets you change the shape later
  "s": "created_at:desc",                   the sort it was issued for
  "f": "a3f9…",                             hash of the filter set it was issued for
  "k": ["2026-08-24T09:41:02.481Z", "inv_9f2c41"]    the position
}
        │ JSON → base64url → append HMAC-SHA256 signature
        ▼
"eyJ2IjoxLCJzIjoi…Lmc9.9f2c41ab"
```

The `s` and `f` fields matter more than they look: a client that pages forward and then changes the
`status` filter while reusing the cursor would otherwise get an incoherent result set. Rejecting the
mismatch with a `400` is far better than silently returning nonsense.

The HMAC makes the cursor tamper-evident. Without it, a client can decode the base64, edit the
timestamp, and use the cursor as an undocumented query parameter — which is a filter you never
designed, never indexed and never authorised.

## Code Example

The cursor codec — opaque, versioned and signed:

```python
# ledgerly/pagination/cursor.py
import base64, hashlib, hmac, json
from dataclasses import dataclass
from datetime import datetime

from ledgerly.config import get_settings

@dataclass(frozen=True, slots=True)
class Cursor:
    created_at: datetime
    id: str
    sort: str
    filter_hash: str

class InvalidCursor(Exception): ...

def _sign(payload: bytes) -> str:
    key = get_settings().cursor_signing_key.get_secret_value().encode()
    return hmac.new(key, payload, hashlib.sha256).hexdigest()[:16]

def encode(cursor: Cursor) -> str:
    payload = json.dumps({"v": 1, "s": cursor.sort, "f": cursor.filter_hash,
                          "k": [cursor.created_at.isoformat(), cursor.id]},
                         separators=(",", ":")).encode()
    body = base64.urlsafe_b64encode(payload).rstrip(b"=").decode()
    return f"{body}.{_sign(payload)}"

def decode(token: str, *, expected_sort: str, expected_filter_hash: str) -> Cursor:
    try:
        body, signature = token.rsplit(".", 1)
        payload = base64.urlsafe_b64decode(body + "=" * (-len(body) % 4))
    except (ValueError, TypeError) as exc:
        raise InvalidCursor("malformed cursor") from exc

    # compare_digest, not ==, so the check is not a timing oracle (16.7).
    if not hmac.compare_digest(signature, _sign(payload)):
        raise InvalidCursor("cursor signature mismatch")

    data = json.loads(payload)
    if data.get("v") != 1:
        raise InvalidCursor("unsupported cursor version")
    if data["s"] != expected_sort or data["f"] != expected_filter_hash:
        # A cursor is only valid for the query that produced it.
        raise InvalidCursor("cursor does not match the current sort or filters")
    return Cursor(created_at=datetime.fromisoformat(data["k"][0]), id=data["k"][1],
                  sort=data["s"], filter_hash=data["f"])
```

The repository query, using a row-value comparison so the composite index does the seek:

```python
# ledgerly/repositories/invoices.py
from sqlalchemy import select, tuple_
from sqlalchemy.ext.asyncio import AsyncSession

from ledgerly.models import Invoice
from ledgerly.pagination.cursor import Cursor

MAX_PAGE_SIZE = 200

async def list_invoices(
    session: AsyncSession, *, tenant_id: str, limit: int,
    after: Cursor | None = None, status: str | None = None,
) -> tuple[list[Invoice], bool]:
    """Returns (rows, has_more). Fetches limit+1 to determine has_more without
    a second query and without a count(*)."""
    statement = select(Invoice).where(Invoice.tenant_id == tenant_id)
    if status is not None:
        statement = statement.where(Invoice.status == status)
    if after is not None:
        # (created_at, id) < (:created_at, :id) — a single index seek.
        # ⚠️ NOT `created_at < x AND id < y`, which drops rows sharing a timestamp.
        statement = statement.where(
            tuple_(Invoice.created_at, Invoice.id) < (after.created_at, after.id)
        )
    statement = statement.order_by(
        Invoice.created_at.desc(), Invoice.id.desc()      # total order — id is the tiebreaker
    ).limit(min(limit, MAX_PAGE_SIZE) + 1)

    rows = list((await session.execute(statement)).scalars())
    has_more = len(rows) > limit
    return rows[:limit], has_more
```

The route, with the page envelope that clients actually consume:

```python
# ledgerly/routers/invoices.py (excerpt)
@router.get("", response_model=Page[InvoiceOut], name="listInvoices")
async def list_invoices(
    svc: Service, tenant: Tenant,
    limit: Annotated[int, Query(ge=1, le=MAX_PAGE_SIZE)] = 50,
    cursor: Annotated[str | None, Query(description="Opaque; echo `next_cursor`.")] = None,
    status: Annotated[str | None, Query()] = None,
) -> Page[InvoiceOut]:
    filter_hash = hash_filters(status=status)
    try:
        after = decode(cursor, expected_sort="created_at:desc",
                       expected_filter_hash=filter_hash) if cursor else None
    except InvalidCursor as exc:
        raise HTTPException(400, f"Invalid cursor: {exc}")   # 400, never a silent reset

    rows, has_more = await svc.list_invoices(tenant, limit=limit, after=after, status=status)
    next_cursor = encode(Cursor(rows[-1].created_at, rows[-1].id,
                                "created_at:desc", filter_hash)) if has_more and rows else None
    return Page(data=[InvoiceOut.model_validate(r) for r in rows], next_cursor=next_cursor,
                has_more=has_more)
```

⚠️ `InvalidCursor` returns `400`, not "start from page 1". Silently resetting to the first page is how
an export loop becomes infinite: the client pages, hits a bad cursor, restarts, and re-processes the
same records forever.

## Design Patterns / Tradeoffs

### Offset / limit

- *How it works:* `LIMIT n OFFSET m`, with `page` and `per_page` as the client-facing form.
- *Advantages:* jump to any page; show "page 7 of 214"; trivial to implement; sort by anything without
  a matching index requirement; clients understand it without documentation.
- *Disadvantages:* cost grows linearly with depth; **unstable under concurrent writes** — rows are
  skipped or duplicated; deep pages can time out.
- *Failure mode:* silent data loss during an export — the scenario below.
- *Use when:* small bounded collections (under ~10,000 rows), admin screens with page numbers,
  human browsing where a duplicate row is cosmetic.
- *Do NOT use when:* exporting, syncing, or reconciling anything; or when the collection is large or
  actively written.

### Keyset / seek with an opaque cursor

- *Advantages:* constant-time regardless of depth; **stable** — no skips or duplicates from
  concurrent inserts and deletes; the opaque token lets you change sort keys and storage later.
- *Disadvantages:* no random access ("page 500" is impossible); the sort key must be totally ordered
  and indexed; a total count needs a separate query; changing sort mid-stream invalidates cursors.
- *Failure mode:* a non-unique sort key silently skips or repeats rows at page boundaries — the bug
  that looks exactly like the one keyset was adopted to fix.
- *Use when:* API list endpoints, exports, syncs, infinite scroll — the default for anything a machine
  consumes.
- *Do NOT use when:* the UI genuinely requires numbered page jumps.

### Comparison

| | Offset | Keyset / cursor |
|---|---|---|
| Page 10,000 cost | O(offset) — seconds | O(page size) — sub-millisecond |
| Stable under writes | ❌ skips and duplicates | ✅ |
| Random page access | ✅ | ❌ forward (and backward) only |
| Total count | Usually shown, always expensive | Usually omitted |
| Index requirement | Any sort works | Composite index on the full sort key |
| Client complexity | Trivial | Echo a token |
| Changing sort later | Free | Invalidates cursors (versioned payload handles it) |

**Recommendation:** cursor pagination as the default for every list endpoint; offset only for
human-facing admin screens with a hard depth cap. If you must offer both, make cursor the documented
path and offset the exception.

### Total counts

| Approach | Cost | When |
|---|---|---|
| Omit entirely | Free | API list endpoints; `has_more` is what a machine needs |
| `count(*)` on request only (`?include_total=true`) | Full scan when asked | Admin UIs where the user opted in |
| Estimate from `reltuples` / `EXPLAIN` | Free, ±few % | "About 40,000 results" |
| Capped count (`LIMIT 1000` then "999+") | Bounded | Search results |

Returning an exact total on every list request is one of the most common avoidable costs in an API.
Clients almost always need "is there more?", which `has_more` answers for free.

## Production Scenario

**Ledgerly, month-end.** A customer's finance controller emails: their reconciliation shows **340
invoices missing** from the export Ledgerly's API produced for July. Their auditors have flagged the
discrepancy. This is a billing product; the customer is asking whether they can trust the data.

### Symptoms

- The customer's nightly export pulled 41,660 invoices for July. Ledgerly's database holds 42,000.
- The 340 missing invoices are **not** a contiguous block — they are scattered across the month.
- The export ran without a single error. Every request returned `200`; the client logged no failures.
- `http_requests_total` for the export's API key: normal. Latency: elevated on later pages (some over
  8 s) but within the client's timeout.
- Re-running the export now returns a *different* count: 41,884. Still not 42,000, and not the same
  number as last time.

### Diagnosis

1. **Alert.** None. Every request succeeded. As with 02.3 and 02.4, a correctness failure produced no
   operational signal whatsoever — the third instance of that pattern in this module.
2. **Metrics.** The one anomaly is latency by page depth: p99 for `GET /v1/invoices` climbs from 30 ms
   at `page=1` to 8.2 s at `page=800`. That points at offset scanning and confirms the endpoint is
   offset-paginated, but slowness alone does not lose data.
3. **Logs.** The export's request sequence is exactly what you would expect — `page=1` through
   `page=840`, `per_page=50`, sequential, no gaps, no retries:

```json
{"route":"/v1/invoices","query":"status=paid&page=417&per_page=50","status":200,
 "rows_returned":50,"duration_ms":3980,"api_key":"key_live_2b8e…"}
```

4. **Reproduce deterministically.** The decisive experiment: page through a test tenant with 1,000
   invoices while inserting new ones concurrently, and compare the union of pages against the table.

```python
# scripts/repro_pagination_drift.py
seen: set[str] = set()
for page in range(1, 21):
    rows = await client.get(f"/v1/invoices?page={page}&per_page=50")
    seen.update(r["id"] for r in rows.json()["data"])
    await insert_invoices(2)          # simulate normal write traffic between pages

missing = await all_invoice_ids() - seen
print(f"{len(missing)} invoices never appeared on any page")
# → 38 invoices never appeared on any page
```

5. **Root cause established** — and the mechanism explains every symptom, including why re-running
   gives a different number each time.

### Root Cause

The export endpoint used offset pagination over a collection sorted `created_at DESC` while invoices
were being created continuously.

Each new invoice inserts at the **head** of a descending list, pushing every existing row one position
later. When the exporter had read pages 1–10 and asked for page 11 (`OFFSET 500`), rows that had been
at positions 495–500 were now at 497–502 — so positions 500–502 were skipped entirely. Over 840 pages
and a month of write traffic, 340 invoices fell through the gaps.

Nothing malfunctioned. The API answered every question correctly. The question itself — *"give me
rows 500 to 550 of a list that is changing"* — has no stable answer.

The 8-second page loads were a second symptom of the same cause (offset scanning), and they made it
worse by widening the window during which the list could shift between requests.

### Fix

*Mitigation (same day):* a one-off reconciliation export using keyset pagination against a snapshot,
delivered to the customer with the 340 missing invoices, plus a written explanation. For a finance
product, the explanation matters as much as the data.

*Permanent fix:*

1. **Cursor pagination on all list endpoints**, as shown above, with `(created_at, id)` as the total
   order and a composite index to match:

```sql
-- alembic: CONCURRENTLY because the table is live (06.13)
CREATE INDEX CONCURRENTLY ix_invoices_tenant_created_id
    ON invoices (tenant_id, created_at DESC, id DESC);
```

2. **Offset kept for the admin UI only, capped at depth 10,000**, returning `400` beyond it with a
   message pointing at cursor pagination. A cap is honest: it converts a slow, wrong answer into a
   clear refusal.
3. **`Deprecation` and `Sunset` headers on the `page` parameter** (02.13), with per-client usage
   telemetry to drive migration outreach.
4. **A documented export path**: `GET /v1/invoices?created_after=…&created_before=…` with cursor
   paging, which is *stable by construction* because a closed time window cannot gain new rows once it
   has passed.

### Prevention

- **A drift test in CI** that pages while writing and asserts completeness. This is the test that
  encodes the lesson, and it is cheap:

```python
# tests/pagination/test_no_drift_under_concurrent_writes.py
@pytest.mark.anyio
async def test_cursor_pagination_returns_every_row_while_inserting(client, auth, seed):
    expected = {i.id for i in await seed.invoices(500)}
    seen, cursor = set(), None
    while True:
        params = {"limit": 50, **({"cursor": cursor} if cursor else {})}
        body = (await client.get("/v1/invoices", params=params, headers=auth)).json()
        seen.update(row["id"] for row in body["data"])
        await seed.invoices(3)              # concurrent writes at the head of the list
        cursor = body["next_cursor"]
        if not cursor:
            break
    assert expected <= seen, f"{len(expected - seen)} pre-existing rows were skipped"
```

- **Alert on page depth.** `max(offset)` per API key rising above a few thousand means a client is
  using offset for bulk extraction — the exact misuse that loses data. It is a leading indicator you
  can act on before the customer's auditor does.
- **Cap page size and offset depth in the contract**, not just in the implementation, so the limits are
  visible in the OpenAPI document (02.4) and in generated SDKs.
- **Make the stable path the documented one.** Every code sample, SDK example and quickstart uses
  cursors; offset appears only in the admin UI section with a warning. Documentation is a control:
  clients do what the first example shows.
- **Treat "silently wrong data" as a severity-1 class.** Ledgerly added a monthly automated
  reconciliation — export via the public API, compare counts against the database — which turns this
  entire category from *"a customer's auditor finds it"* into *"a job fails on the 1st"*.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...rows are inserted while a client pages? | Offset skips or duplicates rows. Keyset is unaffected. |
| ...rows are deleted while a client pages? | Offset shifts the window forward and skips rows. Keyset is unaffected. |
| ...the sort key is not unique? | Keyset skips or repeats at page boundaries. Always append a unique tiebreaker. |
| ...a client requests page 100,000? | Offset: seconds of scanning, possibly a timeout. Cap it and return `400`. |
| ...a client tampers with the cursor? | Signed cursors reject it. Unsigned ones become an unindexed, unauthorised filter. |
| ...a client changes filters mid-pagination? | The cursor's filter hash mismatches → `400`. Without that check, the result set is incoherent. |
| ...a cursor is invalid or expired? | `400`. Never silently restart — that turns an export into an infinite loop. |
| ...the client needs a total count? | Make it opt-in. `count(*)` over a filtered set is often costlier than the page. |
| ...the collection is 100× larger next year? | Keyset cost is unchanged; offset cost scales with depth. |

## Common Pitfalls

**Offset pagination for exports and syncs.** The incident above: silent, scattered data loss.
*Instead:* cursor pagination, or a closed time window that cannot change.

**A non-unique sort key.** `ORDER BY created_at DESC` alone ties on identical timestamps and breaks
keyset at page boundaries. *Instead:* always append the primary key.

**`created_at < :ts AND id < :id` instead of a row comparison.** Drops every row sharing the boundary
timestamp. *Instead:* `tuple_(created_at, id) < (:ts, :id)`.

**Unsigned, transparent cursors.** Clients decode and edit them, creating a filter you never designed
or indexed. *Instead:* HMAC-sign, and validate sort and filters on decode.

**Resetting to page 1 on an invalid cursor.** Turns a transient error into an infinite export loop.
*Instead:* `400`.

**Returning an exact total on every request.** Frequently the most expensive part of the response.
*Instead:* `has_more`, with an opt-in total.

**No maximum page size.** `?per_page=100000` is a denial-of-service vector and an unbounded response
(16.9). *Instead:* cap it in the schema so it appears in the contract.

**Sorting by a column with no index.** Every page becomes a sort of the whole table (02.6, 05.5).
*Instead:* an allow-list of sortable fields, each backed by an index.

## How to Test This

- The drift test above — page while writing, assert no pre-existing row is skipped. Run it for both
  ascending and descending sorts.
- A boundary test with many rows sharing one `created_at`, asserting the tiebreaker prevents skips.
- A tampered-cursor test asserting `400`, and a filter-change test asserting `400`.
- A performance assertion: fetch a deep page via cursor and assert the query plan shows `rows` read
  ≈ page size (13.5 covers wiring `EXPLAIN` into tests).

## Interview Questions

1. *Explain.* Why is `OFFSET 500000` slow even with a perfect index? — The database reads and discards
   every skipped row; cost is linear in offset.
2. *Explain.* How does offset pagination lose data? — Position is defined by counting; concurrent
   inserts and deletes shift rows across the window boundary.
3. *Design.* Implement stable pagination for an invoice list. What is the sort key and the index? —
   `(created_at DESC, id DESC)` with `(tenant_id, created_at DESC, id DESC)`.
4. *Debug this.* A customer's export is missing 340 of 42,000 records, scattered, with no errors and a
   different count on every run. — Offset pagination over a mutating collection; reproduce by paging
   while inserting.
5. *Explain.* Why sign the cursor? — It is opaque only if it cannot be forged; otherwise clients use it
   as an unindexed filter.
6. *Explain.* Why is a total count often more expensive than the page? — `count(*)` over the filter
   scans all matching rows; the page reads only its own.
7. *Design.* A UI needs "page 7 of 214" and an API needs stable exports. How do you serve both? —
   Offset with a depth cap for the UI; cursors for the API; document cursors as the supported path.

## Key Takeaways

- Offset pagination has **two** problems from one cause: it defines position by counting. That makes
  it O(offset) slow *and* unstable under concurrent writes.
- The instability is the dangerous half. It produces **silently missing rows**, no errors, and a
  different answer each run — discovered by an auditor, not by a dashboard.
- Keyset pagination needs a **totally ordered** sort key. Always append the primary key as a
  tiebreaker, and use a row-value comparison over the whole key.
- The index must lead with the tenant/filter column and then match the sort key exactly.
- Make cursors **opaque and signed**, carrying a version, the sort, and a filter hash. Reject
  mismatches with `400`; never silently restart.
- Return `has_more`, not a total, unless the client explicitly asks and you have costed it.
- Cap page size and offset depth **in the contract**, so the limits are visible to every generated SDK.
