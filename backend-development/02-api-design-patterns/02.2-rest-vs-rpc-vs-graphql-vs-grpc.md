# 02.2 REST vs RPC vs GraphQL vs gRPC

> **Prerequisites:** 02.1 (resource modelling) · 01.4 (HTTP caching), 01.7 (HTTP/2 and multiplexing)
> **What you'll learn:**
> - Place the four styles on the axis that actually distinguishes them: **who decides the shape of the response**
> - Predict what each style does to your caching, rate limiting, timeouts and observability
> - Choose per *hop* — public API, internal service call, browser client — rather than adopting one style everywhere
> - Recognise why a single expensive request defeats every per-request defence you have
> **Level:** Intermediate

---

> ⚡ **Monday 10:05** — one mobile screen takes down the API, and the query that did it was perfectly legal. The cause: a schema that permits cycles, with no cost controls.

## Concept

### Plain-English Explanation

All four styles solve the same problem: a client wants something a server has. They differ in who is
in charge of the conversation.

With **REST**, the server publishes a set of things and the client fetches them. The server decides
what an invoice looks like. With **RPC**, the client calls a named procedure — the server publishes
verbs rather than nouns. With **GraphQL**, the client sends a description of exactly the data shape
it wants and the server assembles it. With **gRPC**, the client calls a strongly-typed method defined
in a shared contract file, over a binary protocol.

The interesting consequence is not syntax. It is that **every defence you have is built around
"a request"** — rate limits, timeouts, caches, metrics, circuit breakers, audit logs. The moment a
client can make one request that does an unbounded amount of work, all of those defences count it as
one. That is the axis this notebook actually turns on.

### Technical Explanation

**REST.** Resources identified by URIs, manipulated with a uniform set of methods, with
representations negotiated by content type (01.4, 02.1). The characteristic property is that HTTP's
own machinery applies: `GET` is cacheable and idempotent, so proxies, CDNs and browsers can help you
without knowing anything about your domain.

**RPC over HTTP.** The endpoint names an operation — `POST /rpc` with `{"method": "sendInvoice"}`, or
`POST /v1/sendInvoice`. JSON-RPC is the formalised version. Everything is a `POST`, so nothing is
cacheable and nothing is safe to retry automatically (01.2). In exchange, operations that do not map
onto CRUD stop being awkward.

**GraphQL.** A single endpoint (`POST /graphql`) accepting a query describing the desired graph:

```graphql
query {
  invoice(id: "inv_9f2c41") {
    number
    amountCents
    customer { name contacts { email } }
    lines { description amountCents }
  }
}
```

The server resolves each field, often with one function per field. The client gets exactly what it
asked for — no over-fetching, no under-fetching, no round trips for related data. The costs are
structural: **the request is opaque to HTTP**, so `GET` caching, per-endpoint rate limits and
per-route metrics all stop working, and the *cost* of a query is not knowable from its URL.

**gRPC.** Contract-first: a `.proto` file defines messages and service methods; code generators
produce typed client and server stubs. Transport is Protocol Buffers over HTTP/2, giving binary
framing, multiplexed streams, and first-class streaming in both directions (01.7).

```protobuf
service Invoices {
  rpc GetInvoice(GetInvoiceRequest) returns (Invoice);
  rpc StreamInvoiceEvents(StreamRequest) returns (stream InvoiceEvent);
}
```

The trade is that browsers cannot speak it natively (they need gRPC-web plus a proxy), the payloads
are not human-readable, and every L7 component in your path must understand HTTP/2.

**The distinguishing axis:**

```text
        Who decides the response shape?          What is the unit of cost?
REST    server                                   one resource per request  — bounded, cacheable
RPC     server (per method)                      one operation per request — bounded, not cacheable
gRPC    server (per method, typed)               one method per request    — bounded, not HTTP-cacheable
GraphQL CLIENT                                   ⚠️ UNBOUNDED per request  — cost is not knowable
                                                    from the URL or the method
```

That last row is the whole risk profile of GraphQL in one line, and it is why the production scenario
below is a GraphQL scenario.

### Mental Model

> Ask two questions of any style: **who decides the shape of the response**, and **can I tell how
> expensive a request is before I run it?** REST, RPC and gRPC answer the second question with "yes,
> from the route". GraphQL answers "no, only by analysing the query" — which means you must build the
> analysis, because your rate limiter, timeout and cache cannot do it for you.

## How It Works

The same task — *show an invoice with its customer and line items* — in each style:

```text
REST                                     3 round trips, or 1 with explicit expansion
  GET /v1/invoices/inv_9f2c41
  GET /v1/customers/cus_8f21             ← the "under-fetching" complaint
  GET /v1/invoices/inv_9f2c41/lines
  ── or ──
  GET /v1/invoices/inv_9f2c41?expand=customer,lines   ← server-controlled, bounded

RPC
  POST /v1/getInvoiceWithDetails   {"invoice_id": "inv_9f2c41"}
  └─ one call, but a new method for every new combination the UI needs

gRPC
  Invoices.GetInvoice(GetInvoiceRequest{id: "inv_9f2c41", view: FULL})
  └─ typed, ~5× smaller on the wire, streaming available

GraphQL
  POST /graphql   { invoice(id:"inv_9f2c41"){ number customer{name} lines{amountCents} } }
  └─ exactly the fields needed, one round trip, and the server did not choose the shape
```

**What each style costs you operationally** is the part rarely discussed:

| | REST | RPC | gRPC | GraphQL |
|---|---|---|---|---|
| HTTP caching (01.4) | ✅ full | ❌ (all `POST`) | ❌ | ❌ (single `POST` endpoint) |
| Per-route metrics (15.3) | ✅ by path | ✅ by method | ✅ by method | ⚠️ one route; needs operation-name instrumentation |
| Per-endpoint rate limits (02.12) | ✅ | ✅ | ✅ | ❌ must be cost-based |
| Cost predictable before execution | ✅ | ✅ | ✅ | ❌ requires query analysis |
| Retry-safety from the method | ✅ | ❌ | ❌ (idempotency is per-method convention) | ❌ |
| Browser support | ✅ native | ✅ native | ⚠️ gRPC-web + proxy | ✅ native |
| Payload size | JSON | JSON | ~3–10× smaller | JSON, but no over-fetch |
| Schema/type enforcement | via OpenAPI (02.4) | ad hoc | ✅ generated, compile-time | ✅ strong, introspectable |
| Debuggable with `curl` | ✅ | ✅ | ❌ needs `grpcurl` | ⚠️ possible, verbose |

Notice that REST's advantages are almost all *infrastructure* advantages — things other software does
for you because it understands the protocol. GraphQL's advantages are almost all *client* advantages.
That is the real trade, and it explains why the common mature answer is REST at the public edge and
something else inside.

## Code Example

Ledgerly's public API is REST. The interesting engineering is at the seams — where a REST resource
offers bounded expansion so clients do not need GraphQL, and where an internal call uses gRPC.

**Bounded expansion**: gives clients the one-round-trip benefit without giving them an unbounded
query language.

```python
# ledgerly/routers/invoices.py (excerpt)
from enum import StrEnum
from typing import Annotated
from fastapi import APIRouter, Query

class Expandable(StrEnum):
    CUSTOMER = "customer"
    LINES = "lines"
    PAYMENTS = "payments"

@router.get("/{invoice_id}", response_model=InvoiceOut)
async def get_invoice(
    invoice_id: InvoiceId,
    svc: Service,
    tenant: Tenant,
    # A CLOSED set. The client picks from options we have indexed and costed;
    # it cannot ask for customer.contacts.invoices.customer.contacts (see below).
    expand: Annotated[set[Expandable], Query()] = frozenset(),
) -> InvoiceOut:
    return await svc.get_invoice(tenant, invoice_id, expand=expand)
```

Every value of `expand` maps to a known query with a known index (05.5), so the cost of any request
to this route is bounded and knowable — which is exactly what a rate limiter and a timeout need.

**gRPC for an internal hop**, where the client is another service you own:

```protobuf
// contracts/tax/v1/tax.proto — the single source of truth, generating both sides.
syntax = "proto3";
package ledgerly.tax.v1;

service TaxRates {
  // Unary: one request, one response.
  rpc GetRate(GetRateRequest) returns (Rate);
  // Server streaming: the rate service pushes updates as they publish.
  rpc WatchRates(WatchRequest) returns (stream Rate);
}

message GetRateRequest {
  string country_code = 1;   // ISO 3166-1 alpha-2
  string postal_code = 2;
  string tax_category = 3;
}
message Rate {
  int32 basis_points = 1;    // integer, never float — money and rates (05.1)
  string jurisdiction = 2;
  int64 effective_from_unix = 3;
}
```

Field numbers are the contract, not field names: renaming `postal_code` is safe, reusing number `2`
for a different meaning is a silent, catastrophic break. That property — a compiler-enforced
compatibility rule — is the main reason to accept gRPC's operational costs on an internal hop.

Calling it from the FastAPI service, with the same discipline applied to timeouts as any HTTP client
(01.7, 04.3):

```python
# ledgerly/clients/tax_grpc.py
import grpc
from ledgerly.contracts.tax.v1 import tax_pb2, tax_pb2_grpc

class TaxClient:
    def __init__(self, target: str) -> None:
        # One channel per process, like an httpx.AsyncClient (01.7). A channel
        # multiplexes many concurrent RPCs over one HTTP/2 connection.
        self._channel = grpc.aio.insecure_channel(
            target,
            options=[("grpc.keepalive_time_ms", 30_000),
                     ("grpc.max_receive_message_length", 4 * 1024 * 1024)],
        )
        self._stub = tax_pb2_grpc.TaxRatesStub(self._channel)

    async def rate_for(self, country: str, postal: str, category: str) -> int:
        request = tax_pb2.GetRateRequest(
            country_code=country, postal_code=postal, tax_category=category
        )
        try:
            # ⚠️ gRPC has no default deadline. Without this, a hung server holds
            # the caller forever — the most common gRPC production mistake.
            rate = await self._stub.GetRate(request, timeout=2.0)
        except grpc.aio.AioRpcError as exc:
            if exc.code() is grpc.StatusCode.DEADLINE_EXCEEDED:
                raise TaxProviderUnavailable from exc   # → 502 + Retry-After (01.3)
            raise
        return rate.basis_points
```

## Design Patterns / Tradeoffs

### REST

- *How it works:* resources, uniform interface, HTTP semantics as the API's own semantics.
- *Advantages:* every intermediary understands it — caches, proxies, CDNs, retry libraries; trivially
  debuggable; per-route metrics and limits come free; the largest pool of engineers can consume it.
- *Disadvantages:* over- and under-fetching for rich UIs; awkward for operations that are not CRUD;
  chatty on high-latency links; no built-in type contract without OpenAPI discipline (02.4).
- *Failure mode:* URL sprawl as clients ask for combinations (`?expand=`, `?fields=`,
  `/invoices-with-lines`), gradually reinventing a query language without the safeguards.
- *Use when:* public APIs, third-party integrations, anything a browser or a stranger will consume.
- *Do NOT use when:* the interface is genuinely a set of typed operations between services you own on
  both sides and latency matters.

### RPC (JSON over HTTP)

- *Advantages:* operations that are not CRUD are expressed directly; no arguments about which method
  or status to use; simple to implement.
- *Disadvantages:* nothing is cacheable or retry-safe by the protocol; tight coupling between client
  and method signatures; the API surface grows one method at a time and never shrinks.
- *Failure mode:* method proliferation — `getInvoice`, `getInvoiceWithLines`,
  `getInvoiceWithLinesAndCustomer` — each a permanent public commitment (02.13).
- *Use when:* genuinely action-shaped internal APIs, or when the domain resists resource modelling.
- *Do NOT use when:* clients would benefit from caching or from generic retry logic.

### GraphQL

- *Advantages:* clients fetch exactly what they need in one round trip; frontend teams iterate without
  backend changes; strong introspectable schema; excellent for many divergent clients (web, iOS,
  Android) over one backend.
- *Disadvantages:* **cost is client-controlled**; HTTP caching is unavailable; per-endpoint rate
  limiting is meaningless; N+1 resolution is the default behaviour rather than a bug you introduce
  (06.5); observability needs custom instrumentation to be per-operation; authorisation must be
  enforced per *field*, not per route (16.8).
- *Failure mode:* one query, deeply nested or highly aliased, that costs thousands of database
  queries — the scenario below.
- *Use when:* multiple client platforms with diverging data needs, consumed by teams you can support;
  a BFF layer (18.6).
- *Do NOT use when:* the API is public and untrusted, unless you have implemented depth limits,
  complexity scoring and persisted queries. Those are not optional extras; they are the price of entry.

### gRPC

- *Advantages:* generated, type-safe clients in every language; compact and fast; native bidirectional
  streaming; deadlines and cancellation propagate through the stack (04.8); `.proto` files make
  compatibility rules explicit and machine-checkable.
- *Disadvantages:* no browser support without gRPC-web and a translating proxy; opaque on the wire, so
  debugging needs `grpcurl` and tracing; every L7 hop must speak HTTP/2 (01.7); load balancing needs
  to be request-aware, since one long-lived connection otherwise pins to one backend.
- *Failure mode:* no default deadline — a hung server holds callers indefinitely, which propagates
  into a cascading failure (15.15).
- *Use when:* service-to-service calls you own on both ends, especially high-volume or streaming ones.
- *Do NOT use when:* browsers or third parties are the consumers, or when your infrastructure is
  HTTP/1.1-only.

**Recommendation:** choose per hop, not per company. Ledgerly's shape — REST at the public edge
(cacheable, debuggable, universally consumable), gRPC between internal services (typed, fast,
streaming), and no GraphQL until a second and third client platform genuinely diverge — is the
default that most teams arrive at after trying the alternatives.

## Production Scenario

**Ledgerly, Monday 10:05.** The mobile team shipped a GraphQL endpoint eight weeks ago to serve the
new iOS and Android apps. This morning, the database goes to 100% CPU and stays there. API p99 across
*every* endpoint — REST included — climbs from 90 ms to 14 s. The status page goes yellow.

### Symptoms

- PostgreSQL CPU pinned at 100%; `pg_stat_activity` shows ~180 active queries against a pool sized
  for 20 per replica (05.9).
- Every endpoint is slow, not just GraphQL — the database is a shared resource, so one consumer
  saturating it degrades everyone (15.17).
- `http_requests_total{route="/graphql"}`: **11 requests per minute.** Not a traffic spike.
- Rate limiter: **zero rejections**. The configured limit is 600 requests/minute per tenant, and 11
  is comfortably under it.
- No deploy in five days. No change in REST traffic. No infrastructure change.

### Diagnosis

1. **Alert.** Database CPU and API latency SLO both fired. The on-call's first hypothesis — a traffic
   surge — is eliminated in thirty seconds by the request-rate graph, which is flat.
2. **Metrics.** The contradiction is the signal: *maximum database load, minimum request count*. When
   load and request rate diverge, the cost per request has changed. Something is doing far more work
   per call than it used to.
3. **Logs.** Slow-query logs are full of near-identical `SELECT` statements against `contacts` and
   `invoice_lines`, thousands per minute, each individually fast (1–3 ms). That signature — many
   cheap identical queries rather than one slow one — is N+1 (06.5).
4. **Trace.** The decisive artefact. One trace of a single `POST /graphql` request:

```text
POST /graphql                                    38,204 ms
├── resolve invoices (limit: 100)                     14 ms   1 query
├── resolve invoice.customer × 100                 1,180 ms   100 queries
├── resolve customer.contacts × 100                1,240 ms   100 queries
├── resolve contact.customer × 400                 4,900 ms   400 queries   ← cycles back
├── resolve customer.invoices × 400               18,100 ms   400 queries   ← and again
└── resolve invoice.lines × 4,000                 12,700 ms  4,000 queries
                                            ────────────────────────────
                                              5,001 SQL queries, ONE HTTP request
```

5. **Dependency health.** Postgres is the victim, not the cause. Redis is idle. The tax service is fine.
6. **Root cause identified from the query text**, retrieved from the GraphQL operation log.

### Root Cause

A new "account overview" screen in the mobile app issues a query that walks the schema in a cycle:
invoice → customer → contacts → customer → invoices → lines. Each hop is legitimate on its own; the
schema permits traversing back up a relationship, so a five-level query fans out multiplicatively.

Two independent defects made it catastrophic rather than merely slow:

1. **No query cost controls.** No depth limit, no complexity budget, no result-size cap. The schema
   allowed a query whose cost is a product of page sizes, and nothing evaluated that cost before
   executing it.
2. **No batching in the resolvers.** Each field resolver issued its own query — the N+1 problem
   (06.5), which in GraphQL is the *default* behaviour rather than an accident, because resolvers are
   per-field by design.

And the reason nobody caught it: **every per-request defence was blind.** The rate limiter counts
requests and saw 11. The route-level metrics count requests and saw 11. The p99 latency for
`/graphql` was terrible, but at 11 requests/minute it barely registered against overall traffic. A
single HTTP request had become an unbounded unit of work, and the entire defensive apparatus is
denominated in requests.

### Fix

*Mitigation (9 minutes):* disable the GraphQL route at the proxy (01.10). REST latency returns to
normal within two minutes as the database drains. The mobile app's overview screen shows an error;
every other function of the product works.

*Permanent fix, in the order deployed:*

1. **Depth and complexity limits, rejecting before execution** — the control that makes cost knowable:

```python
# ledgerly/graphql/cost.py
from graphql import GraphQLError, ValidationContext, ValidationRule

MAX_DEPTH = 6
MAX_COMPLEXITY = 1_000          # tuned from the p99 of legitimate queries, then doubled

class ComplexityLimitRule(ValidationRule):
    """Rejects an over-budget query during VALIDATION — before a single resolver
    runs, and therefore before a single database query is issued.

    Cost model: each field costs 1, multiplied by the page size of every list
    ancestor. That mirrors the multiplicative fan-out seen in the trace above."""

    def __init__(self, context: ValidationContext) -> None:
        super().__init__(context)
        self._multipliers: list[int] = [1]

    def enter_field(self, node, *_args) -> None:
        page_size = _declared_page_size(node) or 1
        self._multipliers.append(self._multipliers[-1] * page_size)
        if len(self._multipliers) > MAX_DEPTH:
            self.report_error(GraphQLError(
                f"Query exceeds maximum depth of {MAX_DEPTH}.", node))
        if self._multipliers[-1] > MAX_COMPLEXITY:
            self.report_error(GraphQLError(
                f"Query complexity {self._multipliers[-1]} exceeds {MAX_COMPLEXITY}. "
                "Request fewer nested fields or a smaller page size.", node))

    def leave_field(self, *_args) -> None:
        self._multipliers.pop()
```

2. **Batched resolvers** (a DataLoader per request, keyed by parent id) so a legitimate 100-invoice
   query issues 4 queries rather than 5,001. This is 06.5's `selectinload` idea expressed at the
   resolver layer.
3. **Persisted queries.** The mobile clients now send a query *hash*; the server executes only queries
   from an allow-list generated at app build time. An unbounded ad-hoc query becomes impossible for
   first-party clients, and the cost of every permitted query is known in advance.
4. **A separate connection pool for GraphQL** (05.9), capped at 5 connections per replica. Whatever
   GraphQL does in future, it cannot consume more than a fixed slice of the database — a bulkhead
   (15.17). This is the change that converts "GraphQL took the product down" into "GraphQL is slow".

### Prevention

- **Rate-limit on cost, not on requests.** Ledgerly's GraphQL limiter now deducts the computed
  complexity score from a per-tenant budget, so 11 expensive queries can be refused while 600 cheap
  ones are allowed (02.12, 10.13).
- **A CI test that runs the app's own queries against the cost rule**, so a query that would be
  rejected in production fails the mobile build instead:

```python
# tests/graphql/test_query_cost.py
import pathlib, pytest
from graphql import parse, validate
from ledgerly.graphql.schema import schema
from ledgerly.graphql.cost import ComplexityLimitRule

QUERIES = sorted(pathlib.Path("clients/mobile/queries").glob("*.graphql"))

@pytest.mark.parametrize("path", QUERIES, ids=lambda p: p.name)
def test_shipped_queries_are_within_budget(path: pathlib.Path) -> None:
    errors = validate(schema, parse(path.read_text()), rules=[ComplexityLimitRule])
    assert not errors, f"{path.name}: {[e.message for e in errors]}"
```

- **Alert on queries-per-request, not just queries-per-second.** `sql_queries_total /
  http_requests_total` rising is the generic detector for this entire class — it catches GraphQL
  fan-out, ORM N+1 (06.5) and accidental loops in REST handlers with one expression.
- **Give every new API style its own resource pool before its first release.** The bulkhead was the
  cheapest of the four fixes and would alone have prevented the outage.
- **A design-review rule:** any interface where the client controls the amount of work must ship with
  a cost model on day one. That includes GraphQL, bulk endpoints (02.7), unbounded `expand`, and
  arbitrary filter DSLs (02.6).

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a client sends one enormous request? | REST/RPC/gRPC: bounded by the route. GraphQL: unbounded unless you built depth, complexity and result-size limits. |
| ...you need to rate-limit? | Per-route works for REST/RPC/gRPC. GraphQL needs cost-based budgets — request counting is meaningless. |
| ...a CDN sits in front? | Only REST `GET`s benefit. A single `POST /graphql` endpoint is uncacheable by construction (01.4). |
| ...a gRPC server hangs? | Without an explicit deadline the caller waits forever. Always set one; propagate it (04.8, 15.13). |
| ...a browser must call it? | gRPC needs gRPC-web plus a proxy. REST and GraphQL are native. |
| ...you must debug at 3 a.m.? | `curl` works for REST/RPC; GraphQL is verbose but possible; gRPC needs `grpcurl` and good tracing. |
| ...one client is abusive? | Per-route metrics identify it for REST. For GraphQL you need per-operation-name instrumentation, which does not exist by default. |
| ...traffic increases 10×? | REST scales with replicas and caching. GraphQL scales only if the per-query cost is bounded — otherwise 10× traffic can be 1000× load. |

## Common Pitfalls

**Adopting one style everywhere.** The public edge and an internal hop have different consumers,
different trust levels and different latency budgets. *Instead:* choose per hop.

**Shipping GraphQL without cost controls.** Depth limits, complexity scoring, result caps and
batching are the *minimum viable* GraphQL deployment, not a hardening phase for later. *Instead:*
ship them with the first query.

**Assuming GraphQL removes N+1.** It institutionalises it — one resolver per field is the
architecture. *Instead:* DataLoader batching from day one (06.5).

**gRPC without deadlines.** There is no default. A hung server holds every caller until they are
killed. *Instead:* an explicit timeout on every call, derived from a request budget (11.2).

**Reusing a `.proto` field number.** Renaming a field is safe; reusing its number silently
reinterprets old data as a new meaning. *Instead:* `reserved` the number, never recycle it.

**Reinventing GraphQL inside REST.** `?fields=`, `?expand=`, `?include=` with arbitrary depth gives
you GraphQL's unbounded-cost problem with none of its tooling. *Instead:* a closed set of documented
expansions, each with a known cost.

**Choosing a style for the resume rather than the constraint.** The question is never "is GraphQL
good" — it is "do we have multiple clients with divergent needs, and can we afford the cost model,
the field-level authorisation and the custom observability?"

## How to Test This

- The query-cost test above, run against the queries your own clients actually ship.
- A test asserting every gRPC call site passes a `timeout` (an AST check over the client module, in
  the spirit of 01.6's architecture test).
- A `queries_per_request` assertion in integration tests: wrap the session with an event counter and
  assert that fetching 100 invoices issues a bounded number of SQL statements (06.5, 13.5).
- Backward-compatibility tests on `.proto` files using `buf breaking` in CI.

## Interview Questions

1. *Explain.* What distinguishes GraphQL from REST operationally, ignoring syntax? — Who controls
   response shape, and therefore whether request cost is knowable in advance.
2. *Explain.* Why does GraphQL break HTTP caching and per-endpoint rate limiting? — One `POST`
   endpoint; the URL carries no information about what is being asked.
3. *Debug this.* Database at 100% CPU, 11 requests per minute to one endpoint, rate limiter rejecting
   nothing. — Unbounded per-request cost; get a trace and count SQL queries per request.
4. *Design.* You own the mobile app, a web dashboard and a partner API. Which style for each? — REST
   for partners; GraphQL or a BFF for the first-party clients if their needs genuinely diverge.
5. *Explain.* What must ship alongside a GraphQL endpoint before it is production-ready? — Depth and
   complexity limits, batching, field-level authorisation, per-operation metrics, resource bulkhead.
6. *Explain.* Why does gRPC struggle with browsers and with layer-4 load balancers? — No native
   browser support (needs gRPC-web); HTTP/2 multiplexing pins one connection to one backend.
7. *Design.* An internal service call is on your hot path at 50k rps. What would move you from REST to
   gRPC, and what would you have to check first? — Payload size and latency; check that every hop
   speaks HTTP/2 and that deadlines propagate.

## Key Takeaways

- The distinguishing axis is **who decides the response shape**, and the consequence is whether you
  can know a request's cost before executing it.
- Your rate limits, timeouts, caches, metrics and circuit breakers are all denominated in *requests*.
  Any style that lets one request do unbounded work defeats all of them at once.
- REST's real advantage is that infrastructure understands it: caching, retry-safety and per-route
  observability arrive free.
- GraphQL is a strong answer for divergent first-party clients, and it obliges you to build cost
  limits, batched resolvers, field-level authorisation and per-operation metrics. Those are entry
  requirements, not enhancements.
- gRPC is excellent between services you own — typed, compact, streaming — and needs explicit
  deadlines and HTTP/2 all the way through.
- Choose **per hop**. REST at the edge and gRPC inside is a coherent architecture; "we are a GraphQL
  company" is not.
- Give any new interface style its own connection pool before its first release. A bulkhead is the
  cheapest insurance against a cost model you have not yet validated.
