# 01.2 HTTP Methods, Safety and Idempotency

> **Prerequisites:** 01.1 (request lifecycle) · modern-python 18.1 (REST semantics as a client), 18.3 (retries, idempotency keys)
> **What you'll learn:**
> - Distinguish **safe**, **idempotent** and **cacheable** — three independent properties that are constantly conflated
> - Choose the correct method for an operation that does not map to CRUD

> **Level:** Beginner

## Concept

### Plain-English Explanation

HTTP methods are not labels. They are **promises to strangers**.

Your API is used by software you did not write and cannot see: browsers, corporate link scanners,
CDN prefetchers, load-balancer retry logic, HTTP client libraries with automatic retries, and the
customer's own integration code. All of that software makes decisions based on the method — whether
it is safe to send the request again, whether it is safe to send it *speculatively*, whether the
answer can be cached and served to someone else.

When you write `GET /v1/invoices/{id}/send` and that endpoint emails the customer, you have not just
chosen an unusual URL. You have told every piece of infrastructure on the internet, "sending this
request has no consequences — feel free to do it whenever you like, as many times as you like."
Some of them will take you up on it.

### Technical Explanation

Three properties, defined by RFC 9110 §9.2, that are **independent of one another**:

**Safe** — the request is read-only in intent. The client is not requesting a state change. `GET`,
`HEAD`, `OPTIONS` and `TRACE` are safe. Safety is about *intent*, not implementation: logging a page
view during a `GET` does not make it unsafe, because the client did not ask for it and is not
responsible for it.

**Idempotent** — sending the request N times has the same effect on server state as sending it once.
`GET`, `HEAD`, `OPTIONS`, `TRACE`, `PUT` and `DELETE` are idempotent. `POST` and `PATCH` are not.
Note that idempotency constrains **server state**, not the response: `DELETE /v1/invoices/inv_9` may
return `204` the first time and `404` the second; it is still idempotent because the resulting state
is identical.

**Cacheable** — the response may be stored and reused for a later equivalent request. `GET` and
`HEAD` are cacheable by default; `POST` responses are cacheable only with explicit freshness headers
(and almost no cache implements it). Covered fully in 01.4.

| Method | Safe | Idempotent | Cacheable | Has request body | Typical use in Ledgerly |
|---|---|---|---|---|---|
| `GET` | ✅ | ✅ | ✅ | No (ignored if present) | `GET /v1/invoices?status=open` |
| `HEAD` | ✅ | ✅ | ✅ | No | Existence and `Content-Length` checks |
| `OPTIONS` | ✅ | ✅ | ❌ | No | CORS preflight (01.9) |
| `POST` | ❌ | ❌ | Rarely | Yes | `POST /v1/invoices` — create |
| `PUT` | ❌ | ✅ | ❌ | Yes | `PUT /v1/customers/cus_8f21` — full replace |
| `PATCH` | ❌ | ❌ | ❌ | Yes | `PATCH /v1/invoices/inv_77` — partial update (02.7) |
| `DELETE` | ❌ | ✅ | ❌ | Discouraged | `DELETE /v1/invoices/inv_77` — void a draft |

⚠️ **`PATCH` is not idempotent** and this surprises people. `PATCH {"amount_cents": 500}` is
idempotent in practice; `PATCH {"op": "increment", "field": "reminder_count"}` is not. Because the
*method* makes no guarantee, no intermediary may retry it for you — which is why 02.8's idempotency
keys exist.

### Mental Model

> The method is a **contract with infrastructure you will never meet**. Safety says "you may send
> this without being asked." Idempotency says "you may send this again after a timeout." Every
> retry layer, prefetcher and cache in the world reads that contract and acts on it. Break the
> contract and you do not get an error — you get someone else's software doing your state changes
> for you.

## How It Works

The properties matter because of **who replays requests, and when**:

```text
                         ┌─ retries on timeout? ─┐   ┌─ prefetches speculatively? ─┐
Browser                  │  GET/HEAD only        │   │  yes: <link rel=prefetch>,  │
                         │                       │   │  address-bar prediction     │
Corporate link scanner   │  n/a                  │   │  yes: every URL in every    │
(Outlook SafeLinks,      │                       │   │  email, unannounced         │
 Slack/Teams unfurl)     │                       │   │                             │
CDN / caching proxy      │  idempotent methods   │   │  yes: cache warming         │
Load balancer            │  configurable; often  │   │  no                          │
(nginx, HAProxy, Envoy)  │  GET/HEAD by default  │   │                             │
HTTP client libraries    │  urllib3.Retry:       │   │  no                          │
                         │  DEFAULT_ALLOWED_     │   │                             │
                         │  METHODS = GET, HEAD, │   │                             │
                         │  PUT, DELETE, OPTIONS,│   │                             │
                         │  TRACE  (not POST)    │   │                             │
Your own worker retries  │  whatever you allow   │   │  no                          │
(11.6)                   │  — this is on you     │   │                             │
```

Read the fourth row carefully. `urllib3.Retry`, which backs `requests` and therefore most Python
integrations calling your API, retries `PUT` and `DELETE` automatically on connection errors and
`5xx` — because the spec says it may. If your `DELETE /v1/invoices/{id}` is implemented as
"decrement the customer's remaining quota", the client library will happily decrement it three
times on a flaky network, and neither side has done anything wrong except you.

**Non-CRUD operations** are where method choice gets genuinely hard. "Send this invoice", "void this
invoice", "retry this payment" are not creates, replaces or deletes. Two defensible approaches:

1. **Sub-resource with `POST`** — `POST /v1/invoices/inv_77/send`. The operation is a resource that
   you *create an instance of*. Not idempotent by method, so pair it with an idempotency key (02.8).
2. **State transition with `PATCH`/`PUT` on a status field** — `PATCH /v1/invoices/inv_77
   {"status": "sent"}`. Models the invoice as a state machine; the server decides what "sent" means.

Both are correct. What is never correct is `GET /v1/invoices/inv_77/send`.

## Code Example

FastAPI makes the method explicit at the decorator, which is exactly where a reviewer will see it.
The realistic difficulty is in the non-CRUD operations, so that is what this shows.

```python
# ledgerly/routers/invoices.py
from typing import Annotated, Literal
from uuid import UUID

from fastapi import APIRouter, Depends, Header, HTTPException, Response, status

from ledgerly.schemas import InvoiceOut, InvoiceCreate, InvoiceReplace
from ledgerly.services.invoices import InvoiceService
from ledgerly.deps import get_invoice_service, get_tenant

router = APIRouter(prefix="/v1/invoices", tags=["invoices"])
Service = Annotated[InvoiceService, Depends(get_invoice_service)]
Tenant = Annotated[UUID, Depends(get_tenant)]


@router.get("/{invoice_id}", response_model=InvoiceOut)
async def get_invoice(invoice_id: str, svc: Service, tenant: Tenant) -> InvoiceOut:
    """Safe, idempotent, cacheable. No side effects the caller is responsible for."""
    return await svc.get(tenant, invoice_id)


@router.post("", response_model=InvoiceOut, status_code=status.HTTP_201_CREATED)
async def create_invoice(
    body: InvoiceCreate,
    svc: Service,
    tenant: Tenant,
    idempotency_key: Annotated[str | None, Header(alias="Idempotency-Key")] = None,
) -> InvoiceOut:
    """NOT idempotent by method — so the API offers a key to make it so (02.8)."""
    return await svc.create(tenant, body, idempotency_key=idempotency_key)


@router.put("/{invoice_id}", response_model=InvoiceOut)
async def replace_invoice(
    invoice_id: str, body: InvoiceReplace, svc: Service, tenant: Tenant
) -> InvoiceOut:
    """Idempotent: the body is the complete desired state. Sending it twice
    leaves the same row. Note it is a *replace* — omitted fields are cleared,
    which is precisely why PATCH exists (02.7)."""
    return await svc.replace(tenant, invoice_id, body)
```

Those three are the easy cases: they map cleanly onto read, create and replace. The next two are
where method choice actually requires a decision — a delete that must tolerate being repeated, and
an action that is not CRUD at all.

```python
# ledgerly/routers/invoices.py (continued)
@router.delete("/{invoice_id}", status_code=status.HTTP_204_NO_CONTENT)
async def void_invoice(invoice_id: str, svc: Service, tenant: Tenant) -> Response:
    """Idempotent: voiding an already-voided invoice is a no-op that still
    returns 204. ⚠️ Do NOT return 404 on the second call if a retry layer might
    send it — a client that saw a timeout would report a false failure."""
    await svc.void(tenant, invoice_id)              # no-op if already void
    return Response(status_code=status.HTTP_204_NO_CONTENT)


@router.post("/{invoice_id}/send", status_code=status.HTTP_202_ACCEPTED)
async def send_invoice(
    invoice_id: str,
    svc: Service,
    tenant: Tenant,
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key")],
) -> dict[str, str]:
    """A non-CRUD operation modelled as creating a 'send' event.

    POST, never GET: this emails a human being and cannot be un-sent.
    The idempotency key is REQUIRED (no default) so a retry cannot double-send.
    202 because the email is queued, not delivered (02.10, 11.1)."""
    job_id = await svc.queue_send(tenant, invoice_id, idempotency_key=idempotency_key)
    return {"job_id": job_id, "status": "queued"}
```

Three things in that listing are the actual lesson:

- `send_invoice` is a `POST` on a sub-resource with a **mandatory** `Idempotency-Key`. Making the
  header non-optional means the type system enforces the safety property the method cannot.
- `void_invoice` returns `204` even when the invoice is already void. That deliberate choice is what
  makes `DELETE` genuinely idempotent from the caller's perspective — see the pitfall below.
- `replace_invoice` uses `PUT` and is documented as destructive to omitted fields. If that surprises
  a client, the fix is `PATCH` (02.7), not a `PUT` that silently merges.

Verify the contract from the shell — a violated method contract is visible in one command:

```bash
$ curl -i -X GET https://api.ledgerly.com/v1/invoices/inv_77/send
HTTP/1.1 405 Method Not Allowed
allow: POST
content-type: application/problem+json

{"type": "https://api.ledgerly.com/problems/method-not-allowed",
 "title": "Method Not Allowed", "status": 405, "detail": "Use POST to send an invoice."}
```

`405` with an `Allow` header is the correct, self-documenting refusal (01.3, 02.9).

## Design Patterns / Tradeoffs

### Modelling a non-CRUD action

**A. `POST` to an action sub-resource** — `POST /v1/invoices/{id}/send`

- *How it works:* the action is a resource; posting creates an occurrence of it.
- *Advantages:* obvious in logs and metrics (one route per action); each action can have its own
  authorisation rule (08.12), rate limit (02.12) and audit entry; easy to return `202` and a job id.
- *Disadvantages:* not idempotent by method, so every action needs its own key handling; URL space
  grows with verbs, which purists dislike.
- *Failure mode:* client retries after a timeout and sends the invoice twice — unless a key is required.
- *Use when:* the action has side effects outside the database (email, payment, webhook), or needs
  its own permissions or rate limit.
- *Do NOT use when:* the "action" is really just setting a field, in which case you have invented a
  verb for no reason.

**B. `PATCH` a status field** — `PATCH /v1/invoices/{id} {"status": "sent"}`

- *How it works:* the resource is a state machine; the client requests a target state, the server
  validates the transition.
- *Advantages:* small URL space; transitions are validated in one place; naturally expresses illegal
  transitions as `409 Conflict`.
- *Disadvantages:* one route hides many operations, so metrics and rate limits are coarse; hard to
  authorise "may send but may not void" without inspecting the body.
- *Failure mode:* a client sends `{"status": "sent"}` twice; the second must be a benign no-op or
  you have a double-send.
- *Use when:* transitions are internal and cheap, and the set of states is small and closed.
- *Do NOT use when:* different transitions need different permissions or rate limits.

**C. `PUT` an idempotent sub-resource** — `PUT /v1/invoices/{id}/delivery`

- *How it works:* the *result* of the action is a resource you declare should exist.
- *Advantages:* genuinely idempotent by method — retry layers may safely replay it; no key needed.
- *Disadvantages:* awkward for actions that can legitimately happen twice (a second reminder email);
  clients find it unintuitive.
- *Use when:* the action should happen exactly once ever, and "has it happened" is a queryable fact.
- *Do NOT use when:* repetition is meaningful.

**Recommendation:** A for anything with external side effects (Ledgerly uses it for `send`, `void`
in the payment sense, and `retry_payment`); B for pure internal state changes. Reach for C when you
want infrastructure-level retry safety without implementing key storage.

### `PUT` vs `PATCH` for updates

| | `PUT` (replace) | `PATCH` (merge) |
|---|---|---|
| Semantics | Body is the complete new state | Body describes a change |
| Idempotent | Yes, by definition | Not guaranteed |
| Omitted field | Cleared / reset to default | Left unchanged |
| Concurrent edits | Last writer wins, silently clobbering | Only touched fields collide (still a lost update — 04.6) |
| Advantage | Retry-safe; simple to reason about | Small payloads; no need to read-modify-write |
| Disadvantage | Client must fetch, modify, send everything — a lost-update race (05.13) | Ambiguous semantics unless you specify a format (02.7) |
| Use when | Small resources, config objects, or you want retry safety | Large resources, mobile clients, partial permissions |

Pair either with `If-Match` and `ETag` (01.4) to turn "last writer wins" into a `412 Precondition
Failed` — that is optimistic concurrency at the HTTP layer, and it is the same idea as 05.13's
version column.

## Production Scenario

**Ledgerly, Thursday 14:20.** A support ticket: *"Our customers received the same invoice email 47
times."* Twenty minutes later there are nine such tickets, and the email provider's dashboard shows
14,000 sends in an hour against a normal baseline of 300.

### Symptoms

- Duplicate invoice emails to end customers — the most damaging class of bug in a billing product.
- SendGrid spend for the day already 40× budget; the account is approaching its rate cap.
- `http_requests_total{route="/v1/invoices/{id}/send"}` shows 14k requests, up from ~300.
- All of them are **`GET`**, all `200`, p99 latency normal. No errors anywhere. Every dashboard
  except the volume graph is perfectly healthy.
- The requests originate from a handful of IP ranges, with user agents like
  `Mozilla/5.0 ... SkypeUriPreview Preview/0.5` and `Slackbot-LinkExpanding 1.0`.

### Diagnosis

1. **Alert.** No alert fired — nothing was failing. The signal arrived through support, which is
   itself a finding (the prevention section fixes it).
2. **Metrics.** Request volume on one route is 45× normal while every other route is flat. That
   rules out a general traffic event and points at one endpoint.
3. **Logs.** A structured log query grouping by user agent is decisive:

```text
$ logcli query '{app="ledgerly-api"} |= "/send" | json | line_format "{{.user_agent}}"' | sort | uniq -c
   9,412 SkypeUriPreview Preview/0.5 (MSIE 9.0; Windows NT 6.1)
   3,180 Slackbot-LinkExpanding 1.0 (+https://api.slack.com/robots)
   1,255 Mozilla/5.0 (compatible; Microsoft-SafeLinks)
     188 python-httpx/0.27.0
```

   Almost none of the traffic is from a real client. It is from **link scanners**.
4. **Trace.** A trace of one such request is unremarkable: authenticate, load invoice, enqueue email,
   `200`. The code is doing exactly what it was written to do.
5. **Dependency health.** The email provider is fine; it is faithfully sending everything asked.
6. **Root cause found by reading the route table**, not the infrastructure.

### Root Cause

Six weeks earlier, an internal admin tool needed a one-click "resend invoice" link that could be
pasted into a chat channel. Because it had to work as a plain link, it was implemented as
`GET /v1/invoices/{id}/send`.

Last Thursday, a customer-success manager pasted one such link into a Teams channel and emailed
another to a customer. Teams, Slack and Outlook SafeLinks all fetched the URL to generate a preview
— repeatedly, from multiple regions, and again for every person who viewed the message. Each fetch
sent a real invoice email. The scanners carry no user cookies; the link worked for them anyway
because it embedded a **signed action token in the URL** (the "magic link" pattern) — and the token
was not single-use, so every fetch authorised a fresh send. An action-authorising token in a `GET`
URL compounds the unsafe-`GET` mistake.

**Nothing malfunctioned.** Those systems are entitled to fetch a `GET` URL speculatively; that is
what "safe" means. The bug is that a state-changing operation claimed to be safe.

### Fix

*Mitigation (4 minutes):* a route-level kill switch — return `405` for `GET` on the send route and
allow only `POST`. Emails stop immediately. A feature flag (14.16) already existed for the admin
tool, so it was flipped off in the same deploy.

```python
# Deployed as a hotfix; the GET route was deleted entirely in the follow-up PR.
@router.api_route("/{invoice_id}/send", methods=["GET", "HEAD"], include_in_schema=False)
async def send_invoice_wrong_method() -> Response:
    return Response(
        status_code=405,
        headers={"Allow": "POST"},
        content=b'{"title":"Method Not Allowed","detail":"Use POST to send an invoice."}',
        media_type="application/problem+json",
    )
```

*Permanent fix:*

1. The admin tool posts a form (`POST` with a CSRF token — 16.5) instead of following a link.
2. `POST /v1/invoices/{id}/send` requires an `Idempotency-Key`, so even a legitimate client retry
   cannot double-send (02.8).
3. A **send-suppression** record: `(tenant_id, invoice_id, recipient, date)` unique index, so the
   same invoice cannot be emailed twice to the same recipient in a day regardless of what calls the
   endpoint. Defence in depth — the HTTP layer is not the only guard (11.7).

*Customer remediation:* an apology email, and the suppression table backfilled to prevent a
duplicate follow-up.

### Prevention

- **A contract test in CI** asserts that every route with a side effect is non-safe. Ledgerly's
  version walks the route table and fails the build on any `GET`/`HEAD` route whose path contains a
  verb from a hand-maintained "mutating verbs" list (the OpenAPI-document equivalent arrives in 02.4):

```python
# tests/contract/test_method_safety.py
import pytest
from ledgerly.main import app

MUTATING_VERBS = ("send", "void", "retry", "cancel", "refund", "sync", "reset", "delete")

def test_no_state_changing_get_routes() -> None:
    offenders = [
        (route.path, method)
        for route in app.routes
        for method in getattr(route, "methods", set())
        if method in {"GET", "HEAD"}
        and any(verb in route.path.lower() for verb in MUTATING_VERBS)
    ]
    assert not offenders, f"State-changing operations behind a safe method: {offenders}"
```

- **An alert on outbound side-effect volume**, not just on errors: `emails_sent_total` rate,
  `webhooks_delivered_total` rate, `payments_initiated_total` rate. Any of these rising 10× is a
  page even when nothing is failing. This incident was found by customers because we only alerted
  on failure, and nothing failed.
- **A review checklist item**: "does this endpoint change state, and does its method say so?"
- **Rate-limit side-effect endpoints per resource**, not just per client (02.12): no invoice may be
  sent more than 5 times per hour by anyone.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the request is retried by a client library? | `GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS` are retried by default in `urllib3`. Your handler must tolerate it. `POST`/`PATCH` are not — but your *own* retry code (11.6) may do it anyway, so require idempotency keys. |
| ...the same message arrives twice? | For idempotent methods the second is a no-op by design. For `POST` you need a key (02.8) or a natural unique constraint (05.3). |
| ...a crawler finds the URL? | It will issue `GET` and `HEAD` without authentication. Safe methods must therefore be genuinely safe *and* authorised (16.8). |
| ...a proxy caches the response? | Only `GET`/`HEAD` by default. A `GET` that returns tenant-specific data without `Cache-Control: private` can be served to another tenant (01.4 — this is a real breach class). |
| ...the client times out mid-`POST`? | It does not know whether the invoice was created. This ambiguity is unavoidable at the HTTP layer and is exactly what 02.8 solves. |
| ...a load balancer retries on a 502? | Check your LB config. nginx's `proxy_next_upstream` includes non-idempotent methods only with `non_idempotent` set — verify, do not assume. |
| ...`DELETE` is called twice? | Must be `204` both times (or `204` then `404` if no retry layer exists). Never a `500`. |

## Common Pitfalls

**A state change behind `GET`.** The scenario above. Not a style issue — a correctness and cost
issue, because the internet is full of software entitled to fetch your URLs. *Instead:* `POST` to an
action sub-resource, with an idempotency key.

**`POST` for reads because "the query is too long for a URL".** This breaks caching (01.4), breaks
`GET`-only retry logic, and makes the endpoint invisible to CDN and proxy tooling. *Instead:* keep
`GET` with a bounded query language, or use `POST /v1/invoices/search` and *document explicitly*
that it is a non-cacheable read — a conscious, narrow exception (02.6).

**`DELETE` that returns `404` on the second call, behind a retry layer.** The client retried because
of a network timeout, got `404`, and reported "delete failed" to a human. *Instead:* `204` for
"it is not there", reserving `404` for "this ID never existed in your tenant."

**Assuming `PATCH` is idempotent.** It is not, and no intermediary will treat it as such. *Instead:*
design patch bodies to be absolute (`{"status": "sent"}`) rather than relative
(`{"increment_attempts": 1}`), and still require a key for anything expensive.

**Using `POST` for everything ("we're RPC-ish").** Legitimate for gRPC-style APIs (02.2), but then
you inherit *no* cacheability and *no* infrastructure-level retry safety, and you must build both
yourself. Choose it deliberately, not by drift.

**Bodies on `GET` and `DELETE`.** Permitted-but-undefined by the spec; proxies, CDNs and some client
libraries strip them silently. *Instead:* query parameters for `GET`; for `DELETE` that needs
parameters, reconsider whether it is really a `POST` action.

## How to Test This

- A contract test over the route table asserting no safe method is mutating (shown above) — this is
  the test that would have prevented the incident.
- For each idempotent route, a test that calls it **twice** and asserts identical final state and an
  acceptable status pair: `test_void_twice_returns_204_and_leaves_one_void_event`.
- A test that `GET` on an action route returns `405` with an `Allow` header.
- Fuller treatment in 13.3 (API testing) and 13.4 (contract testing).

## Interview Questions

1. *Explain.* What is the difference between safe and idempotent? Give a method that is one but not
   the other. — `DELETE`: idempotent, not safe.
2. *Explain.* Is `PATCH` idempotent? Why does the answer matter operationally? — No; therefore no
   intermediary will retry it, and your own retries need keys.
3. *Design.* Model "send this invoice by email" as an HTTP endpoint. Defend the method. — `POST` on a
   sub-resource, mandatory idempotency key, `202` with a job id.
4. *Debug this.* Volume on one endpoint is 45× normal, all `200`, no errors, and customers report
   duplicate side effects. — Safe-method violation; group logs by user agent; expect link scanners.
5. *Explain.* Why might `DELETE` returning `404` on a second call be a bug? — Retry layers turn an
   idempotent success into a reported failure.
6. *Design.* A client says your `PUT` wiped fields they did not send. What are your options and their
   tradeoffs? — `PATCH` with a defined merge format; or keep `PUT` and add `If-Match`.
7. *Explain.* Which HTTP methods does `urllib3.Retry` retry by default, and why does that list end
   where it does? — The idempotent set; `POST` is excluded because the spec gives no guarantee.

## Key Takeaways

- Safe, idempotent and cacheable are **three separate properties**. Learn the three-column table, not
  a single "read vs write" split.
- The method is a promise to infrastructure you do not control. Browsers, link scanners, CDNs and
  client libraries all act on it, and they are not wrong to.
- **Never put a state change behind `GET` or `HEAD`.** This is the one rule in this notebook with no
  exceptions.
- `PATCH` is not idempotent; `PUT` and `DELETE` are, and your implementation must honour that —
  including returning `204` for a repeated `DELETE`.
- For non-CRUD actions, `POST` to a sub-resource with a required idempotency key is the default
  choice; state-transition `PATCH` is the alternative when transitions are internal and uniform.
- Alert on **side-effect volume**, not only on errors. The worst incidents produce no errors at all.
