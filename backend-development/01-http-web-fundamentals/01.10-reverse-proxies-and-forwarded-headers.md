# 01.10 Reverse Proxies and Load Balancers — `X-Forwarded-*` and Trusting Proxy Headers

> **What you'll learn:**

> **Level:** Intermediate

> ⚡ **Sunday 03:40** — a fraud rule fires: 11 customers logging in from the same IP. Or did they? The cause: uvicorn told to trust `X-Forwarded-*` from anyone.

## Concept

### Plain-English Explanation

In production, your Python process is almost never the first thing a client touches. In front of it
sits at least one intermediary — a load balancer, a CDN, an nginx container — that terminates TLS,
spreads traffic across replicas, and shields the app from clients on bad networks.

That intermediary solves real problems, and it creates one specific new one: **your application no
longer knows who is calling.** Every request now arrives from the proxy's IP address. The original
client's address, the original scheme (`https`), and the original hostname survive only as
`X-Forwarded-*` headers — headers that are *just headers*, which anyone can send.

So the application faces a question with no default right answer: do I believe these? Answer "always"
and an attacker rewrites their own IP address at will. Answer "never" and every client looks like
`10.0.0.7`. The correct answer is "only from proxies I trust, and only the parts they added" — and
getting that wrong silently disables your rate limiting, your IP allow-lists, and your audit trail.

### Technical Explanation

**What a reverse proxy is for:**

| Responsibility | Why it belongs at the proxy |
|---|---|
| TLS termination | C implementations, hardware offload, certificate rotation independent of app deploys (01.8) |
| Load balancing | Health checks, connection draining, replica-aware routing (17.11) |
| Slow-client buffering | A client trickling a request body ties up the proxy, not your event loop (01.1, 16.9) |
| Request size limits | Reject a 5 GB body before Python allocates anything |
| Static files | Serving bytes from disk should never touch an event loop |
| Compression | Pure CPU work, done outside the GIL (01.4) |
| Path routing | Serving the SPA and API on one origin removes CORS entirely (01.9) |
| Basic DoS hygiene | Connection limits, slowloris timeouts (16.9) |

**The headers**, and who adds them:

```text
client 203.0.113.9  ──▶  CDN 198.51.100.4  ──▶  ALB 10.0.1.20  ──▶  uvicorn 10.0.2.31

Arriving at uvicorn:
  X-Forwarded-For:   203.0.113.9, 198.51.100.4, 10.0.1.20
                     └─────┬────┘  └──────┬────────────────┘
                    client-supplied   appended by each proxy it passed through
                    ⚠️ ATTACKER-CONTROLLED      ✅ trustworthy if the proxies are
  X-Forwarded-Proto: https        ← the ORIGINAL scheme; the app sees plain http
  X-Forwarded-Host:  api.ledgerly.com
  Forwarded: for=203.0.113.9;proto=https;host=api.ledgerly.com   ← RFC 7239, the standard form
```

**The rule that everything else follows from:** `X-Forwarded-For` is built by *appending*. Each proxy
appends the address of the peer it received the connection from. So the **rightmost** entries were
added by infrastructure you control, and the **leftmost** entry is whatever the original client sent
— including a value it invented.

> **The client IP is not `xff.split(",")[0]`. It is the rightmost entry that was not added by a proxy
> you trust.** With one trusted proxy in front of you, that is `xff[-1]`. With a CDN plus an ALB, it
> is `xff[-2]`. The number of hops is a configuration fact you must know and assert.

**Fail modes on both sides:**

- **Trusting too much** (`--forwarded-allow-ips="*"`, or taking `xff[0]`): a client sends
  `X-Forwarded-For: 1.2.3.4` and becomes `1.2.3.4` for every purpose — rate limits, allow-lists,
  audit logs, fraud rules. The scenario below.
- **Trusting too little** (no proxy header handling at all): every client is the proxy's IP. One
  rate-limit bucket for the entire internet; `request.url` is `http://` behind an HTTPS edge, so
  redirects and generated links break; audit logs are useless.

### Mental Model

> A reverse proxy **rewrites the truth about who is calling** and hands you the original as
> untrusted text. Trust is not a property of the header — it is a property of **the connection the
> header arrived on**. Believe `X-Forwarded-*` only when the TCP peer is a proxy you operate, and
> count the hops.

## How It Works

```text
Two identical requests. Only the trust configuration differs.

                              ┌──────────────────────────────────────────────┐
attacker sends:               │  --forwarded-allow-ips="*"   (trust anyone)  │
  X-Forwarded-For: 1.2.3.4    │                                              │
        │                     │  uvicorn overwrites request.client with the  │
        ▼                     │  LEFTMOST value → app sees 1.2.3.4           │
   [ ALB 10.0.1.20 ]          │  → attacker picks a new IP per request       │
        │  appends 203.0.113.9│  → rate limiter sees 1 request per "client"  │
        ▼                     │  → IP allow-list can be spoofed              │
   X-Forwarded-For:           └──────────────────────────────────────────────┘
     1.2.3.4, 203.0.113.9
        │                     ┌──────────────────────────────────────────────┐
        ▼                     │  --forwarded-allow-ips="10.0.0.0/8"          │
   [ uvicorn 10.0.2.31 ]      │  + take the rightmost 1 entry (one proxy)    │
                              │                                              │
                              │  peer 10.0.1.20 is trusted → read XFF        │
                              │  client = xff[-1] = 203.0.113.9  ✅ real     │
                              │  the injected 1.2.3.4 is ignored as noise    │
                              └──────────────────────────────────────────────┘
```

The attacker's header is present in both cases. The difference is entirely in which entry the
application chooses to believe, and that choice is worth exactly as much as your rate limiting.

## Code Example

Three pieces have to agree: the proxy must set the headers, uvicorn must be told which peers to
trust, and the application must extract the client IP with the correct hop count.

```nginx
# infra/nginx/ledgerly.conf
upstream ledgerly_api {
    server api:8000;
    keepalive 64;
    keepalive_timeout 60s;             # < uvicorn's 75s — the 01.7 invariant
}

server {
    listen 443 ssl;
    server_name api.ledgerly.com;

    client_max_body_size 10m;          # reject oversized bodies before Python sees them
    client_body_timeout 10s;           # slowloris defence (16.9)
    proxy_read_timeout 30s;            # must exceed your slowest endpoint (15.13)

    location /v1/ {
        proxy_pass http://ledgerly_api;
        proxy_http_version 1.1;                 # required for upstream keep-alive (01.7)
        proxy_set_header Connection "";

        # ⚠️ $proxy_add_x_forwarded_for APPENDS $remote_addr to any client-supplied
        # value. That is correct — the app must count hops from the right. If you
        # instead want to DISCARD what the client sent (safest when nginx is the
        # only edge), use:  proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-For  $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header Host              $host;
    }

    # Same-origin API for the dashboard — this is what removes CORS entirely (01.9).
    location / { proxy_pass http://ledgerly_spa; }
}
```

nginx now *sets* the headers. That is only a third of the job: uvicorn must be told whose headers to
believe, and the application must know how deep the chain is. All three have to agree, and each one
alone is useless.

```dockerfile
# ledgerly/Dockerfile (excerpt)
# --proxy-headers makes uvicorn honour X-Forwarded-Proto/Host so request.url is https://
# --forwarded-allow-ips restricts that trust to our private network.
# ⚠️ NEVER "*" — that trusts any peer, including a client reaching the app directly.
CMD ["uvicorn", "ledgerly.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--timeout-keep-alive", "75", \
     "--proxy-headers", "--forwarded-allow-ips", "10.0.0.0/8"]
```

```python
# ledgerly/http/client_ip.py
"""Client IP extraction that an attacker cannot influence.

TRUSTED_HOP_COUNT is the number of proxies between the internet and this process.
Today: CDN → ALB → nginx → app  ⇒  3. If the topology changes, this constant MUST
change with it, or the client IP silently becomes wrong (in the safe direction if
too high, in the exploitable direction if too low).
"""
from ipaddress import ip_address, IPv4Address, IPv6Address
from fastapi import Request

TRUSTED_HOP_COUNT = 3

def client_ip(request: Request) -> IPv4Address | IPv6Address | None:
    forwarded = request.headers.get("x-forwarded-for")
    if not forwarded:
        # No proxy in front (local dev, direct access). Use the real peer.
        return ip_address(request.client.host) if request.client else None

    chain = [part.strip() for part in forwarded.split(",") if part.strip()]

    # Count from the RIGHT: entries added by our own proxies. The client's real
    # address is the one appended by the outermost proxy we trust.
    # chain = [spoofed…, real_client, cdn_peer, alb_peer]  → index -TRUSTED_HOP_COUNT
    if len(chain) < TRUSTED_HOP_COUNT:
        # Fewer hops than expected: someone reached us bypassing a proxy, or the
        # topology changed. Fail closed — use the direct peer, never chain[0].
        return ip_address(request.client.host) if request.client else None

    try:
        return ip_address(chain[-TRUSTED_HOP_COUNT])
    except ValueError:
        return ip_address(request.client.host) if request.client else None
```

The rate limiter — the component that most depends on this being right — then keys on the verified
address, never on a raw header:

```python
# ledgerly/middleware/rate_limit.py (sketch — the algorithm is 10.13)
from ledgerly.http.client_ip import client_ip

async def rate_limit_key(request: Request) -> str:
    # Prefer a authenticated identity; fall back to a *verified* IP.
    # ⚠️ Never: request.headers["x-forwarded-for"] — that is attacker input.
    if api_key := getattr(request.state, "api_key_id", None):
        return f"rl:key:{api_key}"
    return f"rl:ip:{client_ip(request)}"
```

Verify the whole chain end to end — the spoofing attempt must have no effect:

```bash
# Inject a fake leftmost entry; the app must still see the real client address.
$ curl -s https://api.ledgerly.com/v1/debug/whoami -H 'X-Forwarded-For: 1.2.3.4'
{"client_ip": "203.0.113.9", "scheme": "https", "host": "api.ledgerly.com"}
#              ^^^^^^^^^^^^ real, not 1.2.3.4  ✅
```

## Design Patterns / Tradeoffs

### Where the proxy sits

**A. Cloud load balancer only** (ALB, Cloud Load Balancing) → app

- *Advantages:* managed, no proxy to operate, integrated certificates and health checks; one hop, so
  hop counting is simple.
- *Disadvantages:* limited request manipulation; per-rule cost; less control over buffering and
  timeouts (whose defaults caused 01.7's incident).
- *Use when:* a straightforward API on a managed platform.

**B. Cloud LB → nginx/Traefik sidecar → app**

- *Advantages:* full control of buffering, size limits, path routing, static files and same-origin
  SPA serving; identical behaviour in local compose and production.
- *Disadvantages:* another component to configure, monitor and keep patched; two hops to count.
- *Use when:* you need path routing (the CORS-removing pattern of 01.9), fine-grained limits, or
  local/production parity.

**C. CDN → cloud LB → app**

- *Advantages:* global TLS termination, static caching (01.4), DDoS absorption.
- *Disadvantages:* three hops; **the CDN's cache rules can change your application's semantics**
  without an application deploy — 01.4's breach.
- *Use when:* a global user base or meaningful static/public content.

**D. No proxy — uvicorn exposed directly**

- *Advantages:* one moving part; correct for local development.
- *Disadvantages:* TLS in Python; no slow-client protection; no body-size limit before allocation; no
  independent certificate rotation.
- *Use when:* development, or an internal service on a trusted network behind a mesh.
- *Do NOT use when:* the internet can reach it.

### Trusting the forwarded chain

| Approach | How it works | Risk |
|---|---|---|
| Trust nothing | Use the TCP peer only | Every client is the proxy; rate limits and audit logs are useless |
| `--forwarded-allow-ips="*"` | Trust any peer's headers | **Full spoofing** — the incident below |
| Trust by peer CIDR + hop count (✅) | Believe headers only from private/proxy ranges; index from the right | Requires knowing the topology; must be updated when it changes |
| Proxy overwrites XFF | `proxy_set_header X-Forwarded-For $remote_addr` at the outermost proxy | Simplest and safest **when there is exactly one edge**; loses the real chain if a CDN sits in front |
| Cloud-specific trusted header | ALB's `X-Forwarded-For` semantics, Cloudflare's `CF-Connecting-IP` | Vendor lock-in, but unspoofable if the origin only accepts traffic from the vendor |

**Recommendation:** trust by peer CIDR *plus* a hop count asserted in configuration; additionally
restrict the origin's security group or firewall so **only the proxy can reach it at all**. Network
enforcement is what makes header trust safe — if a client can reach uvicorn directly, no header
policy saves you.

## Production Scenario

**Ledgerly, Sunday 03:40.** An automated fraud rule fires: 11 successful logins to distinct customer
accounts, from accounts that have never shown weekend activity. The security on-call opens the
incident. This is a credential-stuffing attack (08.17) that succeeded — and the question is why the
defences did not slow it down.

### Symptoms

- ~2.1 million `POST /v1/auth/login` requests over 6 hours, against a normal Sunday total of ~4,000.
- **`rate_limit_rejections_total` for the login route: 3.** Essentially zero. The rate limiter is
  running and configured for 5 attempts per IP per minute, and it rejected almost nothing.
- 11 accounts compromised; 2.1 M attempts against ~180,000 distinct email addresses.
- The application dashboard looks *good*: latency normal, error rate normal, no saturation. The API
  cheerfully served two million login attempts.
- Access logs show a startling `client_ip` cardinality: 2.1 M requests, **1.98 M distinct client IP
  values**, from what turns out to be 34 actual source addresses.

### Diagnosis

1. **Alert.** The fraud rule (a business-level detection) fired. No infrastructure alert did —
   another instance of the module's pattern: the system was healthy while doing the wrong thing.
2. **Metrics.** The decisive pair: a 500× increase in login attempts alongside a rate limiter that
   rejected three of them. **The limiter is not broken, it is being evaded** — meaning the key it
   buckets on is under the attacker's control.
3. **Logs.** Cardinality is the tell. Two million distinct client IPs in six hours is not a botnet
   Ledgerly's size would attract; it is a header being generated:

```json
{"ts":"…T03:12:04Z","route":"/v1/auth/login","status":401,"client_ip":"84.117.203.11",
 "xff":"84.117.203.11, 203.0.113.9, 198.51.100.4, 10.0.1.20","peer":"10.0.2.30","email_hash":"a91f…"}
{"ts":"…T03:12:04Z","route":"/v1/auth/login","status":401,"client_ip":"12.44.9.203",
 "xff":"12.44.9.203, 203.0.113.9, 198.51.100.4, 10.0.1.20","peer":"10.0.2.30","email_hash":"6b02…"}
```

   Same second, same TCP peer (the nginx sidecar, `10.0.2.30`), same *second* XFF entry
   (`203.0.113.9` — the real attacker, appended by the CDN), different **leftmost** value. The
   attacker is sending a random `X-Forwarded-For` with every request, and the app is believing it.

   ⚠️ Note the `xff` and `peer` fields exist in the log line at all. Without them this incident is
   unsolvable from logs; with them it takes ninety seconds. That is a logging decision made months
   earlier (15.1).

4. **Trace.** Every request is a legitimate authentication attempt. Nothing is malformed.
5. **Dependency health.** Redis (holding the rate-limit counters) is healthy and holds ~2 M keys with
   a count of 1 each — visible proof that every request created its own bucket.
6. **Configuration** confirms it:

```bash
$ docker inspect ledgerly-api | jq -r '.[0].Config.Cmd | join(" ")'
uvicorn ledgerly.main:app --host 0.0.0.0 --port 8000 --proxy-headers --forwarded-allow-ips *
```

### Root Cause

`--forwarded-allow-ips="*"` tells uvicorn to trust `X-Forwarded-*` from **any** peer, and uvicorn's
proxy-header handling takes the leftmost entry as the client. The rate limiter keyed on
`request.client.host`, which was therefore whatever the attacker wrote.

Every attempt got its own rate-limit bucket, so the limit of 5-per-minute-per-IP was never reached by
anyone. The limiter functioned perfectly and protected nothing.

The `"*"` had been added eight months earlier while debugging why client IPs appeared as `10.0.1.20`
in staging. It worked, it was committed, and nothing about it looked dangerous — the flag reads like
"enable proxy headers", not "let clients choose their own identity".

### Fix

*Mitigation (14 minutes):*

1. Block the 34 real source addresses (`203.0.113.9` and neighbours) at the edge — available only
   because the *second* XFF entry, appended by the CDN, was real and logged.
2. Deploy the corrected trust configuration:

```diff
- "--proxy-headers", "--forwarded-allow-ips", "*"
+ # Trust forwarded headers ONLY from our own load balancer subnet.
+ # "*" lets any client set its own IP and defeats rate limiting entirely. See 01.10.
+ "--proxy-headers", "--forwarded-allow-ips", "10.0.0.0/8"
```

3. Force a password reset for the 11 compromised accounts and notify them (08.16).

*Permanent fix:*

1. `client_ip()` with an explicit `TRUSTED_HOP_COUNT`, as shown above — the application never reads
   `request.client.host` for security decisions again.
2. **Rate limiting moved to a compound key**: `(route, verified_ip, email_hash)` for login, with a
   *separate, stricter* per-account limit. Even a genuinely distributed botnet — where every IP is
   real — cannot make 2 M attempts against 180,000 accounts, because the per-account limit binds
   independently of source (08.17, 10.13).
3. **Network enforcement**: the API's security group now accepts traffic only from the ALB. If the
   header policy is ever wrong again, an attacker still cannot reach the app directly to exploit it.
   Defence in depth — the header policy and the network policy fail independently.

### Prevention

- **A configuration invariant test** in CI:

```python
# tests/security/test_proxy_trust.py
from ipaddress import ip_network
from infra.config import load_uvicorn_args

def test_forwarded_allow_ips_is_not_wildcard() -> None:
    value = load_uvicorn_args()["--forwarded-allow-ips"]
    assert value != "*", (
        "--forwarded-allow-ips='*' lets any client spoof X-Forwarded-For, "
        "defeating rate limiting and IP allow-lists (see 01.10)"
    )
    # ip_network().is_private is the honest check — startswith("172.") would
    # also accept 172.32.0.0, which is public; only 172.16.0.0/12 is private.
    assert all(ip_network(part.strip()).is_private
               for part in value.split(",")), f"non-private trusted range: {value}"
```

- **A spoofing test against a running stack**, asserting an injected leftmost XFF is ignored:

```python
@pytest.mark.anyio
async def test_client_ip_ignores_injected_forwarded_for(proxied_client) -> None:
    response = await proxied_client.get("/v1/debug/whoami",
                                        headers={"X-Forwarded-For": "1.2.3.4"})
    assert response.json()["client_ip"] != "1.2.3.4"
```

- **Alert on rate-limit-key cardinality.** A limiter creating ~1 M keys/hour with a count of 1 each
  is being evaded, not used. This single metric detects the entire class.
- **Alert on the ratio of attempts to rejections**: high traffic on a limited route with near-zero
  rejections is a contradiction that should page.
- **Log `xff`, `peer` and the derived `client_ip` on every request.** They are what made this
  solvable, and they cost nothing.
- **Rate-limit by account as well as by source.** Any IP-based limit is only as good as your ability
  to identify the source; per-account limits do not depend on that at all.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a client sets its own `X-Forwarded-For`? | It must be ignored — trust only headers arriving from proxy peers, and index from the right. |
| ...someone reaches uvicorn directly, bypassing the proxy? | With CIDR-restricted trust, forwarded headers are ignored and the real peer is used. Also block it at the network layer. |
| ...the number of proxy hops changes? | Your hop count is now wrong. Too high → fail closed (safe); too low → spoofable. Assert it in configuration and test it. |
| ...`X-Forwarded-Proto` is missing or wrong? | The app thinks it is on HTTP: redirects to `http://`, `Secure` cookies dropped, generated links wrong. |
| ...the proxy is slow or unhealthy? | Your app is unreachable regardless of its own health. Health checks and connection draining live at the proxy (15.8). |
| ...the proxy buffers request bodies? | Your app sees a fast client even when the real one is slow — usually desirable; it is what protects the event loop (01.1). |
| ...you rate-limit by IP behind a corporate NAT? | Thousands of legitimate users share one address. IP limits need account-level companions. |
| ...traffic increases 10×? | The proxy's connection and worker limits bind before your app's. Size and monitor them too (17.11). |

## Common Pitfalls

**`--forwarded-allow-ips="*"`.** The incident above. It reads like "enable proxy support"; it means
"let clients choose their own identity". *Instead:* the proxy's CIDR, asserted in CI.

**Taking `X-Forwarded-For.split(",")[0]`.** The leftmost value is client-supplied. This one line
appears in countless middleware snippets online. *Instead:* index from the right by trusted hop count.

**Rate limiting on IP alone.** Defeated by any attacker with addresses, and it punishes NAT'd
corporate users. *Instead:* compound keys, plus per-account limits that do not depend on source.

**Forgetting `--proxy-headers` entirely.** Every client is the proxy IP, `request.url` is `http://`,
redirect loops appear behind an HTTPS edge. *Instead:* enable it *and* scope the trust.

**Duplicating responsibilities.** CORS headers, compression or rate limits configured in both proxy
and app produce duplicated headers and double-counted limits. *Instead:* one owner per concern,
written down.

**`proxy_read_timeout` shorter than your slowest endpoint.** The proxy returns `504` while the app is
still working — and the work completes anyway, so a retry duplicates it (01.2). *Instead:* proxy
timeout above the app's own timeout, with the app's timeout being the real budget (15.13).

**Assuming the proxy protects an app that is also directly reachable.** Every proxy-level control —
size limits, rate limits, WAF rules — is bypassed by connecting to the origin. *Instead:* enforce at
the network layer that only the proxy can reach the app.

## How to Test This

- The configuration invariant test (no wildcard trust; private ranges only).
- The spoofing test against a compose stack that includes the real proxy — this must run against
  nginx, not against the ASGI app alone, because the header rewriting is the thing under test.
- A test that `request.url.scheme == "https"` behind a proxy setting `X-Forwarded-Proto: https`, so
  generated links and redirects are correct.
- A rate-limit test asserting that 20 requests with 20 different injected XFF values still consume one
  bucket.

## Interview Questions

1. *Explain.* Why can your application not trust `X-Forwarded-For`? — It is a plain header; anyone can
   send it. Only entries appended by trusted proxies are meaningful.
2. *Explain.* Which entry in the XFF chain is the real client, and how do you know? — The rightmost
   entry not added by a proxy you trust; determined by hop count, not by position from the left.
3. *Debug this.* A rate limiter configured at 5/min/IP rejects almost nothing while the service takes
   2 M login attempts. — IP spoofing via forwarded headers; check trust configuration and key cardinality.
4. *Design.* Which responsibilities would you put in a reverse proxy rather than FastAPI, and why? —
   TLS, buffering, size limits, static files, compression, path routing; all are byte-level or
   tenant-agnostic.
5. *Explain.* What breaks if `X-Forwarded-Proto` is not honoured? — Redirects and generated URLs use
   `http://`; `Secure` cookies are dropped; redirect loops.
6. *Design.* How do you rate-limit an endpoint when many legitimate users share one NAT address? —
   Per-account and per-credential limits alongside IP; never IP alone.
7. *Explain.* Why is restricting the origin's network access part of the fix for a header-trust bug? —
   Header policy and network policy are independent defences; either alone can fail.

## Key Takeaways

- A reverse proxy is where TLS, buffering, size limits, static files, compression and path routing
  belong. Doing them in Python costs event-loop time and gains nothing.
- The proxy takes away your knowledge of the client and hands it back as **untrusted text**.
- **Trust is a property of the connection, not the header.** Believe `X-Forwarded-*` only from proxy
  peers (`--forwarded-allow-ips=<CIDR>`, never `*`) and index the chain **from the right** by a
  known hop count.
- `xff.split(",")[0]` is attacker input. Treating it as the client IP silently disables rate limiting,
  IP allow-lists and audit trails.
- Back header trust with network enforcement: if a client can reach your app directly, every
  proxy-level control is optional for them.
- Rate-limit on compound keys and per-account, so the defence does not rest entirely on identifying
  the source.
- Alert on **rate-limit key cardinality** and on an attempts-to-rejections ratio. A limiter that never
  rejects anything under attack is a limiter being evaded.
