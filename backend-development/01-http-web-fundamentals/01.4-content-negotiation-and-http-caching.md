## Concept

### Plain-English Explanation

The fastest request is the one you never serve, and the second fastest is one where you answer
"nothing has changed" in 200 bytes instead of re-sending 200 KB. HTTP has had this built in since
1999, and most APIs use none of it — then add Redis (module 10) to solve a problem the protocol
would have solved for free.

But HTTP caching also carries the sharpest edge in this module. A cache is a machine that decides
"this stored answer is good enough for that new question". If you describe your responses
carelessly, some machine between you and your users will decide that **one customer's invoices are a
good enough answer for another customer's request**. That is not a hypothetical; it is a recurring
class of breach, and the production scenario below is one instance of it.

Content negotiation is the related question of *which representation* to send — JSON or PDF,
English or German, gzip or Brotli — and it feeds directly into the caching problem, because every
axis you negotiate on is an axis your cache key must include.

### Technical Explanation

**Validators and conditional requests.** A validator is a compact token identifying a specific
version of a resource.

- **`ETag`** — an opaque string chosen by the server: `ETag: "7"` (a version counter),
  `ETag: "a3f9c1…"` (a content hash). A **strong** ETag (`"abc"`) means byte-for-byte identical; a
  **weak** ETag (`W/"abc"`) means semantically equivalent. Weak validators cannot be used for range
  requests, and — importantly — cannot be used with `If-Match` for concurrency control.
- **`Last-Modified`** — a timestamp, with one-second granularity. Adequate for documents, unusable
  for anything that can change twice in a second (which includes most API resources).

Two conditional request headers use validators for two entirely different purposes:

```text
READ path (cheap reads)                    WRITE path (safe concurrent writes)
GET /v1/invoices/inv_9f2                   PUT /v1/invoices/inv_9f2
If-None-Match: "7"                         If-Match: "7"
   │                                          │
   ├─ current ETag == "7" → 304 Not Modified  ├─ current ETag == "7" → apply, return new ETag "8"
   │  (no body — just headers)                │
   └─ changed         → 200 + body + ETag "8" └─ current ETag == "8" → 412 Precondition Failed
```

`If-Match` is **optimistic concurrency control at the HTTP layer** — the same idea as a version
column in 05.13, but enforced by the protocol and understood by any client. It converts a silent
lost update (04.6) into a `412` the client can handle.

**`Cache-Control` — the directives that actually matter:**

| Directive | Meaning | Where it bites |
|---|---|---|
| `max-age=N` | Fresh for N seconds in *any* cache | Combined with `public`, N seconds of stale data for everyone |
| `s-maxage=N` | Fresh for N seconds in *shared* caches only | Lets a CDN cache longer than a browser |
| `public` | Any cache may store it, **including shared ones** | ⚠️ Never on authenticated responses |
| `private` | Only the end user's own cache may store it | The correct default for authenticated API responses |
| `no-cache` | May store, **must revalidate** before reuse | Not "do not cache" — the name is a historic mistake |
| `no-store` | Must not be written to storage at all | The right directive for tokens, PII, payment data |
| `must-revalidate` | May not serve stale on error | Trades availability for correctness |
| `stale-while-revalidate=N` | Serve stale for N s while refreshing in background | Excellent for dashboards; hides origin latency |
| `immutable` | Will never change; do not revalidate | Content-hashed static assets only |

The pair people confuse — `no-cache` **stores and revalidates**; `no-store` **never writes it down**.
If a response contains a bearer token or a customer's bank details, the directive is `no-store`.

**`Vary` is the cache key.** A cache stores a response against the request URL *plus* the headers
listed in `Vary`. `Vary: Accept-Encoding` means gzip and Brotli variants are stored separately.
`Vary: Authorization` means each credential gets its own entry. **A missing `Vary` means the cache
believes every request to that URL deserves the same answer.**

⚠️ `Vary: Authorization` is a correctness backstop, not a design. Shared caches keying on full
credential strings scale terribly, and some CDNs ignore `Vary` on headers they were not configured
for. The real answer for authenticated data is `Cache-Control: private` (or `no-store`), so no shared
cache stores it at all. Use both.

**Content negotiation** happens on four axes: `Accept` (media type), `Accept-Encoding`
(compression), `Accept-Language`, and `Accept-Charset` (obsolete — always UTF-8). Each axis you
honour must appear in `Vary`. Media-type negotiation is also one way to version an API
(`Accept: application/vnd.ledgerly.v2+json`) — tradeoffs in 02.3.

**Compression.** `gzip` is universal; `br` (Brotli) is ~15–20% smaller for text and now near-universal;
`zstd` is faster and increasingly supported. JSON compresses 6–10×, so this is the highest-value
single change for a chatty API. Two cautions: compressing already-compressed bodies (PDF, JPEG,
Parquet) wastes CPU for nothing, and compressing a response that mixes a secret with
attacker-controlled input enables the **BREACH** attack — a compression-ratio side channel
(16.4). Do not compress responses containing CSRF tokens or session identifiers alongside reflected
user input.

### Mental Model

> **`ETag` answers "is my copy still good?" `Cache-Control` answers "who may keep a copy and for how
> long?" `Vary` answers "what makes two requests the same question?"** Get the third one wrong and
> a machine you do not administer will confidently give one customer another customer's data.

## How It Works

The lifecycle of a cached read in Ledgerly's invoice list, with a CDN in front (01.10):

```text
1st request                              2nd request (same client, 30s later)
─────────────                            ────────────────────────────────────
GET /v1/invoices?status=open             GET /v1/invoices?status=open
Authorization: Bearer eyJ…               Authorization: Bearer eyJ…
Accept-Encoding: br, gzip                If-None-Match: W/"lst-t44f1-9013"
        │                                        │
        ▼                                        ▼
   CDN: no entry                           CDN: entry exists but Cache-Control
        │                                       says `private` → not stored here
        ▼                                        ▼  (forwards to origin)
   ORIGIN: query PG (18 ms)                 ORIGIN: SELECT max(updated_at), count(*)
        │  serialise 214 KB                        FROM invoices WHERE tenant=… (1.2 ms)
        │  compress br → 21 KB                     → builds the SAME ETag
        ▼                                        ▼
200 OK                                     304 Not Modified
etag: W/"lst-t44f1-9013"                   etag: W/"lst-t44f1-9013"
cache-control: private, max-age=0,         cache-control: private, max-age=0,
               must-revalidate                            must-revalidate
vary: Accept-Encoding, Authorization       vary: Accept-Encoding, Authorization
content-encoding: br
content-length: 21504                      (no body — 0 bytes)

Cost: 18 ms + 21 KB                        Cost: 1.2 ms + ~200 bytes
```

The second request still reaches your origin — `must-revalidate` with `max-age=0` means "always ask"
— but it costs a cheap aggregate query instead of a full serialisation, and it moves ~21 KB less
data. For a mobile client polling every 30 seconds, that is the difference between a usable and an
unusable integration.

**Generating the ETag matters.** Hashing the serialised body means you did all the work anyway and
only saved bandwidth. A good API ETag is derivable *cheaply*:

- Single resource: a `version` integer column bumped on every update (05.13) → `ETag: "8"`.
- Collection: a composite of tenant, row count and `max(updated_at)` → weak ETag. Cheap with the
  right index (05.5), and correct as long as deletes also bump `updated_at` (they do if you
  soft-delete).

## Code Example

Ledgerly's invoice endpoints, with conditional reads, optimistic writes, and cache directives that
a CDN can be trusted with.

```python
# ledgerly/http/caching.py
from fastapi import Request, Response, status

def etag_matches(request: Request, current_etag: str) -> bool:
    """RFC 9110 §13.1.2: If-None-Match may be a list, or '*'. Compare weakly."""
    header = request.headers.get("if-none-match")
    if not header:
        return False
    if header.strip() == "*":
        return True
    def normalise(tag: str) -> str:
        return tag.strip().removeprefix("W/").strip('"')
    return normalise(current_etag) in {normalise(t) for t in header.split(",")}
```

```python
# ledgerly/routers/invoices.py (excerpt)
from typing import Annotated
from fastapi import APIRouter, Depends, Header, HTTPException, Request, Response, status

from ledgerly.http.caching import etag_matches
from ledgerly.errors import VersionConflict

@router.get("/{invoice_id}", response_model=InvoiceOut)
async def get_invoice(
    invoice_id: str, request: Request, response: Response, svc: Service, tenant: Tenant,
) -> InvoiceOut | Response:
    # Cheap: fetches (id, version) only — no joins, no serialisation.
    version = await svc.get_version(tenant, invoice_id)
    etag = f'"{version}"'

    if etag_matches(request, etag):
        # 304 must repeat the validators and cache directives, and carry no body.
        return Response(
            status_code=status.HTTP_304_NOT_MODIFIED,
            headers={"ETag": etag,
                     "Cache-Control": "private, max-age=0, must-revalidate"},
        )

    invoice = await svc.get(tenant, invoice_id)
    response.headers["ETag"] = etag
    # `private`: no shared cache may store this. This one word is the difference
    # between a fast API and a cross-tenant data leak.
    response.headers["Cache-Control"] = "private, max-age=0, must-revalidate"
    response.headers["Vary"] = "Accept-Encoding, Authorization"
    return invoice
```

The read path saves bandwidth. The write path is where validators earn their keep for *correctness*
— the same `ETag` the client received on its last read becomes the precondition that stops it
overwriting someone else's edit.

```python
# ledgerly/routers/invoices.py (continued)
@router.put("/{invoice_id}", response_model=InvoiceOut)
async def replace_invoice(
    invoice_id: str,
    body: InvoiceReplace,
    svc: Service,
    tenant: Tenant,
    response: Response,
    if_match: Annotated[str | None, Header(alias="If-Match")] = None,
) -> InvoiceOut:
    """Optimistic concurrency at the HTTP layer.

    428 — you must send a precondition (we refuse blind overwrites on this resource).
    412 — you sent one and it no longer holds; re-read and retry.
    """
    if if_match is None:
        raise HTTPException(
            status_code=status.HTTP_428_PRECONDITION_REQUIRED,
            detail="Send If-Match with the ETag from your last read.",
        )
    try:
        expected = int(if_match.strip().removeprefix("W/").strip('"'))
    except ValueError:
        raise HTTPException(status.HTTP_400_BAD_REQUEST, "Malformed If-Match.")

    try:
        invoice = await svc.replace(tenant, invoice_id, body, expected_version=expected)
    except VersionConflict as exc:
        # The write is rejected in the UPDATE ... WHERE version = :expected — 05.13.
        raise HTTPException(
            status_code=status.HTTP_412_PRECONDITION_FAILED,
            detail=f"Invoice was modified (now version {exc.actual}). Re-read and retry.",
        )
    response.headers["ETag"] = f'"{invoice.version}"'
    return invoice
```

The `412` path is the whole reason to bother. Without it, two agents editing the same invoice
produce a silent lost update; with it, the second one is told exactly what happened, in a status its
HTTP library already understands.

Seen from the wire:

```bash
$ curl -i -H "$AUTH" https://api.ledgerly.com/v1/invoices/inv_9f2
HTTP/1.1 200 OK
etag: "7"
cache-control: private, max-age=0, must-revalidate
vary: Accept-Encoding, Authorization

$ curl -i -H "$AUTH" -H 'If-None-Match: "7"' https://api.ledgerly.com/v1/invoices/inv_9f2
HTTP/1.1 304 Not Modified
etag: "7"
cache-control: private, max-age=0, must-revalidate

$ curl -i -X PUT -H "$AUTH" -H 'If-Match: "6"' -d @invoice.json \
       https://api.ledgerly.com/v1/invoices/inv_9f2
HTTP/1.1 412 Precondition Failed
content-type: application/problem+json
{"title":"Precondition Failed","status":412,"detail":"Invoice was modified (now version 7)."}
```

Compression is configured once, at the right layer, and excluded for the wrong content:

```python
# ledgerly/main.py — acceptable in development; in production this belongs in the
# reverse proxy (01.10), which does it in C without touching the event loop.
from fastapi.middleware.gzip import GZipMiddleware
app.add_middleware(GZipMiddleware, minimum_size=1024)   # below ~1 KB it costs more than it saves
```

⚠️ Do not gzip the PDF route: `render_invoice_pdf` output is already compressed, so you pay CPU for a
~0% reduction. Exclude by content type in the proxy, or set `Content-Encoding: identity`.

## Design Patterns / Tradeoffs

### Where to cache

**A. HTTP caching (this notebook)** — `ETag`, `Cache-Control`, `304`

- *How it works:* the client and intermediaries hold the copy; the origin validates cheaply.
- *Advantages:* no infrastructure to run; saves bandwidth *and* serialisation; works for every client
  automatically; invalidation is implicit — a version bump changes the ETag.
- *Disadvantages:* still costs a round trip unless `max-age > 0`; you cannot purge a copy already in
  a client; useless for expensive *writes*.
- *Failure mode:* `public` on authenticated content → cross-tenant leak (below). Stale data if
  `max-age` is set and the resource changes early.
- *Use when:* read-heavy resources fetched repeatedly by the same client — detail views, lists,
  configuration, catalogues.
- *Do NOT use when:* data must be exact to the millisecond, or the response contains secrets
  (`no-store`).

**B. CDN / shared cache** — `s-maxage`, `stale-while-revalidate`

- *Advantages:* offloads the origin entirely; absorbs traffic spikes; terminates near the user.
- *Disadvantages:* only safe for genuinely public data; purging is eventually consistent; config
  lives outside your repo unless you manage it as code.
- *Failure mode:* the leak class in the scenario below; and thundering herd on the origin when a
  popular entry expires (10.9 — the same problem, one layer out).
- *Use when:* public, tenant-agnostic content — docs, marketing, public status pages, invoice PDFs
  fetched via signed URLs (09.6).
- *Do NOT use when:* the response depends on identity, unless every response is `private`.

**C. Application cache (Redis — module 10)**

- *Advantages:* you control invalidation precisely; caches *computations*, not just responses;
  shared across replicas.
- *Disadvantages:* infrastructure to run and fail; invalidation is your problem (10.8); every
  request still pays the network round trip to your origin.
- *Use when:* expensive computations reused across users, or when you need to cache below the HTTP
  layer (a query result used by three endpoints).
- *Do NOT use when:* HTTP caching would have done it — reaching for Redis first is the single most
  common over-engineering in this curriculum.

**Recommendation:** layer them deliberately — HTTP validators on every read endpoint (cheap, always
correct), CDN for public assets only, Redis for expensive shared computation. Most APIs skip
straight to Redis and keep the bandwidth cost forever.

### Strong vs weak ETags

| | Strong `"abc"` | Weak `W/"abc"` |
|---|---|---|
| Guarantees | Byte-identical representation | Semantically equivalent |
| Works with `If-Match` | Yes | No — cannot be used for concurrency control |
| Works with `Range` requests | Yes | No |
| Cost to compute | Usually a body hash | Can be a version or `max(updated_at)` |
| Use when | Single resources with a version column; byte-range downloads (09.5) | Collections, or when serialisation may vary (key order, whitespace) |

Ledgerly uses strong ETags (`"7"`, the version column) for single invoices — because `If-Match` needs
them — and weak ETags for list endpoints.

## Production Scenario

**Ledgerly, Wednesday 11:52.** A support ticket, marked urgent by the agent who read it:
*"I refreshed the invoice list and I'm looking at a different company's invoices. I can see their
customer names and amounts."*

This is a data breach in progress, and the clock on regulatory notification has started.

### Symptoms

- One tenant sees another tenant's `GET /v1/invoices` response. Reproducible intermittently, never
  on the first request after login.
- Application logs show **no anomaly**. Every request was authenticated, authorised, and served the
  correct tenant's data. The tenant-scoping code is correct and has tests.
- `http_requests_total{route="/v1/invoices"}` at the origin dropped **62%** starting Tuesday 16:10.
  Nobody noticed, because "traffic down, latency down" looks like good news.
- The CDN dashboard for the same period shows a cache hit ratio on `/v1/*` rising from 0% to 61%.

### Diagnosis

1. **Alert.** None fired. A cache hit ratio going *up* is not an alert anyone had written. Finding
   number one for the prevention list.
2. **Metrics.** The origin request-rate drop at 16:10 Tuesday is the anchor: something started
   answering requests instead of us. The CDN hit ratio rising at the same minute names the culprit.
3. **Logs.** Origin logs are clean *because the leaked responses never reached the origin*. This is
   the key insight, and it is a general one: **when the application logs show nothing wrong, the
   problem is in a layer that never called the application** (01.1).
4. **Trace.** A reproduction with two accounts and `curl` shows the second request returning
   `age: 47` and `x-cache: HIT` — CDN headers proving a shared cache served a stored copy.
5. **Dependency health.** Postgres, Redis fine. Not implicated.
6. **The response headers are the root cause**, visible in one command:

```bash
$ curl -sI -H "$TENANT_A_AUTH" https://api.ledgerly.com/v1/invoices | grep -iE 'cache|vary|age|x-cache'
cache-control: max-age=60          # ⚠️ no `private`
vary: Accept-Encoding              # ⚠️ no Authorization
age: 47
x-cache: HIT
```

### Root Cause

Two independently reasonable changes combined into a breach:

1. **Six weeks ago**, an engineer added `Cache-Control: max-age=60` to the invoice list to reduce
   load from a customer polling every 5 seconds. Without `private`, this means *any* cache, including
   shared ones. At the time there was no shared cache, so it was harmless — and it stayed harmless
   long enough that nobody connected it to anything.
2. **Tuesday 16:10**, the platform team put a CDN in front of `api.ledgerly.com` to terminate TLS
   closer to users. The default rule cached any response that said it was cacheable. The `/v1/*` path
   was not excluded, because `/v1/*` responses "obviously" would not claim to be cacheable.

The CDN behaved exactly as instructed. It stored a `max-age=60`, non-`private` response under the key
`GET /v1/invoices` + `Accept-Encoding`, and — since `Authorization` was not in `Vary` — served it to
whoever asked next, for 60 seconds.

**No code was wrong. The description of the response was wrong.**

### Fix

*Mitigation (7 minutes, in this order):*

1. Purge the CDN cache for `/v1/*` — stops further leakage immediately.
2. Add a CDN rule: **bypass cache for all `/v1/*`**. Defence at the layer that was misconfigured.
3. Deploy `Cache-Control: private, no-store` on every authenticated route (one middleware, below).

*Permanent fix — a secure default enforced in code, not convention:*

```python
# ledgerly/middleware/cache_policy.py
from starlette.types import ASGIApp, Message, Receive, Scope, Send

# Routes that are genuinely public and safe for shared caches. Explicit allow-list:
# everything not named here is private by default.
PUBLIC_PREFIXES = ("/health", "/ready", "/openapi.json", "/docs", "/v1/status")

class CachePolicyMiddleware:
    """Fail-safe cache directives. An authenticated response can never be stored
    by a shared cache, even if a route forgets to say so."""

    def __init__(self, app: ASGIApp) -> None:
        self.app = app

    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        if scope["type"] != "http":
            await self.app(scope, receive, send)
            return

        is_public = scope["path"].startswith(PUBLIC_PREFIXES)

        async def send_with_policy(message: Message) -> None:
            if message["type"] == "http.response.start" and not is_public:
                headers = message.setdefault("headers", [])
                names = {k.lower() for k, _ in headers}
                if b"cache-control" not in names:
                    headers.append((b"cache-control", b"private, no-store"))
                else:  # a route set its own — make sure it is at least private
                    headers[:] = [
                        (k, v if k.lower() != b"cache-control" or b"private" in v.lower()
                            else b"private, " + v)
                        for k, v in headers
                    ]
                if b"vary" not in names:
                    headers.append((b"vary", b"Accept-Encoding, Authorization"))
            await send(message)

        await self.app(scope, receive, send_with_policy)
```

The invoice-list route then re-adds validators *within* a private policy —
`private, max-age=0, must-revalidate` — recovering the bandwidth saving with none of the risk.

*Remediation:* CDN access logs were used to bound the exposure (which tenant keys received which
cached objects), and the incident was reported per the customer contracts. This is the part nobody
enjoys, and it is decided by whether you can *prove* the blast radius — which is a logging decision
made months earlier (16.13).

### Prevention

- **A contract test that fails the build** if an authenticated route can be shared-cached:

```python
# tests/contract/test_cache_policy.py
import pytest
from ledgerly.main import app
from ledgerly.middleware.cache_policy import PUBLIC_PREFIXES

@pytest.mark.anyio
@pytest.mark.parametrize("path", [r.path for r in app.routes
                                  if not r.path.startswith(PUBLIC_PREFIXES)])
async def test_authenticated_routes_are_never_shared_cacheable(client, auth, path):
    response = await client.get(path, headers=auth)
    cc = response.headers.get("cache-control", "")
    assert "private" in cc or "no-store" in cc, f"{path} may be stored by a shared cache: {cc!r}"
    assert "public" not in cc, f"{path} is marked public"
```

- **CDN configuration as code**, reviewed in the same PR as application changes, with an explicit
  deny-list for `/v1/*`. An infrastructure change that alters application semantics must be visible
  to application reviewers.
- **Alert on origin request-rate dropping** as well as rising. A 62% drop with no deploy is an
  incident signal; it was treated as good news for 19 hours.
- **A synthetic canary**: two test tenants, polling the same endpoint every 30 seconds, asserting
  each sees only its own data. It costs nothing and detects this class in under a minute.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a shared cache is added in front of your API tomorrow? | Every authenticated response must already say `private`/`no-store`. Assume it will happen without your knowledge — it did here. |
| ...the resource changes during `max-age`? | Clients serve stale data for the remainder. Use `max-age=0, must-revalidate` + `ETag` when correctness matters more than the round trip. |
| ...two clients `PUT` the same invoice? | Without `If-Match`, the second silently wins (04.6). With it, the second gets `412`. |
| ...the client sends `If-None-Match` for a deleted resource? | `404`, not `304`. `304` asserts the representation is unchanged, which is untrue. |
| ...the ETag is expensive to compute? | You have saved bandwidth but not CPU. Derive it from a version column or `max(updated_at)`, not a body hash. |
| ...the response is compressed and contains a token? | BREACH-style side channel (16.4). `no-store` and do not compress secret-bearing responses. |
| ...a proxy strips `Vary`? | Some do. This is why `private` is the primary control and `Vary` the backstop. |
| ...traffic increases 10×? | Conditional requests keep the origin cost per client near-constant; without them, serialisation cost scales linearly with polling. |

## Common Pitfalls

**`Cache-Control: max-age=N` without `private` on authenticated responses.** The scenario above. It
is invisible until the day someone adds a CDN. *Instead:* `private` by default, enforced by
middleware, with an explicit public allow-list.

**Believing `no-cache` means "do not cache".** It means "store, but revalidate". *Instead:*
`no-store` for anything you do not want written to disk anywhere.

**Omitting `Vary: Accept-Encoding` while compressing.** A cache may hand a Brotli body to a client
that only accepts gzip, which then fails to decode it. *Instead:* always `Vary` on every header you
negotiate, and let the proxy manage it.

**Hashing the serialised body to build an ETag.** You did all the work and only saved bandwidth. Real
savings come from validators you can compute in a single indexed lookup. *Instead:* a version column
(05.13), or a cheap collection aggregate.

**Returning `304` with a body, or without the `ETag`.** The body is ignored or breaks clients, and a
`304` without validators forces a full re-fetch next time. *Instead:* `304` carries the validators
and cache directives, and nothing else.

**Compressing everything.** Gzipping a 4 MB PDF burns CPU on the event loop (01.1) for no gain.
*Instead:* compress by content type, above a minimum size, in the proxy.

**Reaching for Redis before using HTTP caching.** You take on an availability dependency (10.6) and
an invalidation problem (10.8) to solve something the protocol already solved. *Instead:* add
validators first; measure; then add Redis for what remains.

- The cache-policy contract test above — the highest-value test in this notebook.
- `test_conditional_get_returns_304_and_no_body`, plus a test that a write bumps the ETag so the
  *next* conditional read returns `200`.

- A two-tenant synthetic check runnable in CI and in production as a canary.
- Compression: assert `content-encoding: br` on JSON above 1 KB and absent on PDF.

## Interview Questions

1. *Explain.* What is the difference between `no-cache` and `no-store`? — Store-and-revalidate vs
   never store; the second is for secrets.
2. *Explain.* What does `Vary` do, and what breaks when it is missing? — It defines the cache key;
   missing entries collapse distinct requests into one, which can leak data.
3. *Design.* Two users edit the same invoice concurrently. Design the HTTP contract that prevents a
   lost update. — `ETag` + `If-Match` → `412`; optionally `428` to require the precondition.
4. *Debug this.* A customer sees another customer's data intermittently, application logs are clean,
   and origin traffic dropped 60% yesterday. — A shared cache is serving stored responses; check
   `Cache-Control`/`Vary` and any CDN added recently.
5. *Explain.* Why is hashing the response body a poor ETag strategy for an API? — It requires doing
   the expensive work anyway; only bandwidth is saved.
6. *Design.* Which of your endpoints should be CDN-cacheable and how would you enforce that
   decision? — Public, identity-independent ones only; enforce with a default-private middleware and
   a contract test.
7. *Explain.* When is compressing a response a security risk? — Secret + reflected input in one
   compressed body (BREACH).

---

## Key Takeaways

- `ETag` + `If-None-Match` turns repeat reads into ~200-byte `304`s; `ETag` + `If-Match` turns silent
  lost updates into an explicit `412`. Both are nearly free if your ETag is a version column.
- **`private` is the correct default for every authenticated response.** `public` is a decision that
  requires justification, and `no-store` is required for anything containing secrets.
- `Vary` *is* the cache key. Anything you negotiate on must appear there — and `private` is the
  primary defence, with `Vary` as backstop.
- The most dangerous cache is the one someone else adds to your architecture next Tuesday. Describe
  your responses so that a new cache cannot hurt you.
- Compress text, not already-compressed bytes; do it in the proxy; never compress a secret alongside
  reflected input.
- Use HTTP caching before application caching. Redis (module 10) is for what HTTP cannot do — not a
  substitute for headers you did not set.
