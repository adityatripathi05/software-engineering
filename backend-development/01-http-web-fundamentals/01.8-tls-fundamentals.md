## Concept

### Plain-English Explanation

TLS does three things: it proves you are talking to who you think you are, it stops anyone in the
middle reading the conversation, and it stops anyone in the middle changing it. Authentication,
confidentiality, integrity — in that order of importance, because encryption without authentication
just means you have a private conversation with an attacker.

The part that generates production incidents is almost never the cryptography. It is the
**identity** part: certificates expire, chains are served incompletely, hostnames do not match, and
clocks drift. These failures are absolute — a TLS failure is not a slow request or a degraded
response, it is a connection that does not happen — and they often affect only *some* clients, which
makes them maddening to diagnose.

### Technical Explanation

**What a certificate is.** A signed statement: *"the holder of this public key controls
`api.ledgerly.com`, and I, a Certificate Authority, vouch for that until 2026-11-14."* Your client
trusts it because it trusts the CA — via a **chain**:

```text
Root CA  (ISRG Root X1)              ← in the client's trust store; self-signed; long-lived
   │ signs
Intermediate CA  (Let's Encrypt R11) ← NOT in the trust store; the server must send it
   │ signs
Leaf  (CN=api.ledgerly.com)          ← your certificate; ~90 days
```

The client has the **root** in its trust store. It does not have the intermediate. **The server must
send the leaf *and* every intermediate**, so the client can build a path from what it received to
something it already trusts. Sending only the leaf produces a chain that browsers usually repair
themselves and that Python, Java and Go clients reject outright — the incident below.

**The handshake (TLS 1.3, one round trip):**

```text
CLIENT                                          SERVER
  │  ClientHello ─────────────────────────────────▶
  │    · supported cipher suites
  │    · key share (X25519 public key)
  │    · SNI: api.ledgerly.com   ← which host? (one IP serves many certs)
  │    · ALPN: h2, http/1.1      ← which protocol? (01.7)
  │
  │  ◀───────────────────────────── ServerHello + {EncryptedExtensions,
  │                                  Certificate chain, CertificateVerify, Finished}
  │    everything after ServerHello is already encrypted
  │
  │  ── client validates: signature chain → trusted root
  │                       hostname matches SAN
  │                       not expired, not revoked
  │  Finished ────────────────────────────────────▶
  │  ══════════ application data (your HTTP request) ══════════
```

TLS 1.2 needs two round trips and permits weak cipher suites; **TLS 1.3 removed the weak options
entirely** — no RSA key exchange, no CBC, no renegotiation, forward secrecy mandatory. Configuring
TLS 1.3 correctly is mostly a matter of not configuring it: the bad choices no longer exist.

**Forward secrecy** means the session key is derived from an ephemeral key exchange and discarded.
An attacker who records traffic today and steals your private key next year still cannot decrypt it.
Mandatory in TLS 1.3, optional (and often absent) in older TLS 1.2 configurations.

**SNI** (Server Name Indication) is the hostname sent *in the clear* in the ClientHello, so one IP
can serve many certificates. Two consequences: your load balancer needs it to pick a certificate,
and an observer learns which host you contacted even though the content is encrypted.

**ALPN** negotiates the application protocol during the handshake — this is how HTTP/2 is selected
without an extra round trip (01.7).

**What TLS does not give you:**

- It does not authenticate the *client* (unless you deploy mTLS).
- It does not protect data at rest, in logs, or in your database.
- It does not hide the destination hostname (SNI) or traffic volume and timing.
- It does not make a request authorised — a valid TLS session says nothing about permissions (08).
- It does not protect against a compromised endpoint. Encryption in transit is one control, not a
  security posture.

### Mental Model

> TLS is **an identity check followed by a private channel**. Nearly every production TLS failure is
> in the identity half: expired, incomplete, or wrong-hostname certificates. Treat certificates as
> perishable infrastructure with an expiry date — because that is exactly what they are.

## How It Works

**Where TLS terminates** is an architectural decision with security and operational consequences:

```text
A. Edge termination (most common)
   client ══TLS══▶ [ CDN / ALB ] ──plaintext──▶ [ nginx ] ──plaintext──▶ [ uvicorn ]
                                  └─ inside a private network / VPC

B. Re-encryption (regulated environments)
   client ══TLS══▶ [ ALB ] ══TLS══▶ [ nginx ] ══TLS══▶ [ uvicorn ]
                          └─ internal CA; each hop authenticated

C. Passthrough
   client ══════════════TLS all the way══════════════▶ [ uvicorn ]
           the LB routes on SNI only; cannot read paths, cannot add X-Forwarded-* (01.10)

D. mTLS between services
   service A ══TLS + client cert══▶ service B     both sides prove identity
```

Almost every Python backend uses **A**: terminate at the edge, plaintext (or re-encrypted) inside
the trust boundary, and let uvicorn speak plain HTTP. Terminating TLS in Python is slower, means
certificate rotation requires an application deploy, and gains nothing when the hop is inside a VPC.

⚠️ Under A, "the app only speaks HTTP" makes two things your responsibility: `X-Forwarded-Proto` must
be trusted correctly so your app knows the original scheme (01.10), and cookies must still be marked
`Secure` (01.5) even though the app never sees TLS.

**Certificate lifetime is shrinking and will keep shrinking.** Let's Encrypt issues 90-day
certificates; the CA/Browser Forum has agreed a path toward ~47-day maximum lifetimes by 2029. The
operational conclusion is not "renew more often" — it is **certificate renewal must be fully
automated and monitored, with no human step**. ACME (`certbot`, `cert-manager`, Caddy, Traefik) is
the standard mechanism.

## Code Example

Almost nothing here is Python — which is itself the lesson. What *is* Python is the outbound side
(verifying certificates correctly when Ledgerly calls the tax provider) and the monitoring.

```nginx
# infra/nginx/tls.conf
server {
    listen 443 ssl;
    http2 on;
    server_name api.ledgerly.com;

    # ⚠️ fullchain.pem = leaf + intermediates. Using cert.pem (leaf only) produces a
    # site that works in browsers and fails in Python, Java and Go. See the scenario below.
    ssl_certificate     /etc/letsencrypt/live/api.ledgerly.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.ledgerly.com/privkey.pem;

    ssl_protocols TLSv1.2 TLSv1.3;      # 1.0/1.1 are dead; 1.2 only for legacy clients
    ssl_prefer_server_ciphers off;      # TLS 1.3: let the client choose; all options are safe
    ssl_session_cache shared:SSL:10m;   # resumption — avoids a full handshake (01.7)
    ssl_session_tickets off;            # tickets without rotation weaken forward secrecy

    ssl_stapling on;                    # OCSP stapling: the server proves non-revocation,
    ssl_stapling_verify on;             # so the client needs no extra round trip to the CA

    # HSTS: after the first successful visit, the browser refuses plaintext for 2 years.
    # ⚠️ Do not add `preload` until you are certain every subdomain is HTTPS — it is
    # effectively irreversible for the preload-list lifetime.
    add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
}
```

> **Version note:** Let's Encrypt ended OCSP support in 2025 (revocation moved to CRLs), so for the
> Let's Encrypt certificates in this config `ssl_stapling` is inert as of 2025-26 — nginx has
> nothing to staple. The two directives are harmless to leave in, but stapling is only meaningful
> with a CA that still operates OCSP responders.

The outbound side, where the common mistake is disabling verification to make an error go away:

```python
# ledgerly/clients/tax.py
import httpx, ssl, certifi

def build_tax_client() -> httpx.AsyncClient:
    # httpx verifies by default using certifi's bundle. Explicit is better here
    # because the failure mode of getting it wrong is silent and total.
    ctx = ssl.create_default_context(cafile=certifi.where())
    ctx.minimum_version = ssl.TLSVersion.TLSv1_2
    ctx.check_hostname = True
    ctx.verify_mode = ssl.CERT_REQUIRED
    return httpx.AsyncClient(base_url="https://api.taxprovider.example", verify=ctx)

# ❌ NEVER, in any environment that touches real data:
#     httpx.AsyncClient(verify=False)
# It disables authentication entirely, so the encryption protects a conversation
# with whoever intercepted it. If a self-signed cert must be trusted (a test
# fixture, an internal CA), trust THAT CA explicitly:
#     ssl.create_default_context(cafile="/etc/ledgerly/internal-ca.pem")
```

And the monitoring that turns "certificates expire" from an outage into a ticket:

```python
# ledgerly/observability/cert_expiry.py
"""Exports days-until-expiry for every endpoint we serve or depend on.
Alerts at 21 days (warning) and 7 days (page) — ACME renews at 30, so an alert
means automation has already failed."""
import socket, ssl
from datetime import datetime, UTC
from prometheus_client import Gauge

CERT_EXPIRY = Gauge("tls_certificate_expiry_days", "Days until expiry", ["host"])

def days_until_expiry(host: str, port: int = 443, timeout: float = 5.0) -> float:
    ctx = ssl.create_default_context()
    with socket.create_connection((host, port), timeout=timeout) as sock:
        with ctx.wrap_socket(sock, server_hostname=host) as tls:   # server_hostname = SNI
            not_after = tls.getpeercert()["notAfter"]              # 'Nov 14 08:00:00 2026 GMT'
    expires = datetime.strptime(not_after, "%b %d %H:%M:%S %Y %Z").replace(tzinfo=UTC)
    return (expires - datetime.now(UTC)).total_seconds() / 86400
```

⚠️ This connects with the *system* trust store, so it also validates the chain — a missing
intermediate makes it raise rather than report a number. That is a feature: the check catches both
failure modes.

**Inspecting a chain from the shell** is the single most useful TLS debugging skill:

```bash
$ openssl s_client -connect api.ledgerly.com:443 -servername api.ledgerly.com </dev/null 2>/dev/null \
  | grep -E '^( [0-9] s:| [0-9] i:|Verify return code)'
 0 s:CN = api.ledgerly.com
   i:C = US, O = Let's Encrypt, CN = R11
 1 s:C = US, O = Let's Encrypt, CN = R11        ← the intermediate, correctly served
   i:C = US, O = Internet Security Research Group, CN = ISRG Root X1
Verify return code: 0 (ok)
```

A healthy chain has the leaf at depth 0 and every intermediate above it, ending at a root the client
already trusts. Depth 0 alone is the broken case.

## Design Patterns / Tradeoffs

### Where to terminate

**A. Edge termination, plaintext internally**

- *Advantages:* one place to manage certificates; hardware/C-optimised handshakes; app deploys are
  independent of certificate rotation; the app never handles a private key.
- *Disadvantages:* traffic inside the trust boundary is readable by anything on that network; you
  must trust the network segmentation; the app depends on `X-Forwarded-Proto` for scheme awareness.
- *Failure mode:* an attacker with a foothold inside the VPC reads everything; a misconfigured
  `X-Forwarded-Proto` makes the app generate `http://` URLs and redirect loops.
- *Use when:* the internal hop is inside a private network you control. This is the default.
- *Do NOT use when:* regulatory requirements demand encryption on every hop.

**B. Re-encryption to the origin**

- *Advantages:* encrypted end to end; satisfies PCI/HIPAA-style requirements; protects against
  internal network compromise.
- *Disadvantages:* certificates on every hop (usually an internal CA); more CPU; more to expire;
  harder to debug.
- *Use when:* compliance requires it, or the network between hops is not trusted (cross-datacentre).

**C. TLS passthrough**

- *Advantages:* the LB never sees plaintext; the origin proves its own identity to the client.
- *Disadvantages:* the LB routes on SNI only — no path routing, no header injection, so **no
  `X-Forwarded-For`** (01.10) and no request-level observability at the edge.
- *Use when:* the LB must not be in the trust boundary at all.

**D. mTLS between services**

- *How it works:* both sides present certificates; each verifies the other.
- *Advantages:* strong, transport-level service identity; no bearer token to steal or replay;
  authentication that survives a compromised application layer.
- *Disadvantages:* certificate distribution and rotation for every workload (this is what a service
  mesh exists to automate); debugging is harder; a rotation failure is a total outage between two
  services.
- *Use when:* zero-trust internal networking with automation (mesh or SPIFFE) already in place, or a
  partner integration requiring it.
- *Do NOT use when:* you would be rotating certificates by hand. Hand-managed mTLS fails closed on a
  Sunday.

**Recommendation:** A for the public edge; B when compliance demands it; D only with automation.
Terminating TLS in uvicorn is for local development only.

### Certificate pinning

Pinning a specific certificate or public key in a client defeats a compromised-CA attack, and it
also means **every rotation is a coordinated release**. For mobile apps with a slow update cycle it
has caused more outages than it has prevented attacks. Prefer CAA records, Certificate Transparency
monitoring, and short-lived certificates. Pin only for a small, controlled client population with a
tested backup pin.

## Production Scenario

**Ledgerly, Monday 09:12.** A customer's integration engineer emails: *"Your API started rejecting
our connections over the weekend. `SSLError: certificate verify failed: unable to get local issuer
certificate`."* The on-call engineer opens `https://api.ledgerly.com` in a browser. Padlock. Valid
certificate. Everything looks fine.

Over the next two hours, six more integration customers report the same, and one large customer's
nightly invoice sync has failed twice.

### Symptoms

- Python clients (`requests`, `httpx`), Go clients, and Java clients fail to connect.
- **Browsers work perfectly**, on every machine tried. So does `curl` on the engineer's macOS laptop.
- `curl` on the Ubuntu CI runner fails.
- `https_requests_total` at the edge is down 8%; the missing traffic is entirely server-to-server
  integrations. Interactive dashboard usage is unaffected — which is why nothing paged.
- The application is completely healthy: no errors, normal latency for the requests that arrive.

### Diagnosis

1. **Alert.** None. The failing requests never established a connection, so they appear in no
   application metric. A traffic *drop* is the only signal, and nobody alerts on that (a recurring
   theme in this module — see 01.4).
2. **Metrics.** An 8% drop in request volume with no error increase means clients are failing
   *before* HTTP. That points at DNS, TCP or TLS.
3. **Logs.** nginx `error.log` shows handshake failures from a variety of client IPs, with no
   application-layer entries. Confirms TLS.
4. **The critical observation.** Browsers succeed, Python fails. Browsers and Python differ in
   exactly one relevant way: **browsers repair incomplete chains** by fetching the missing
   intermediate from the URL in the certificate's Authority Information Access extension, and cache
   intermediates they have seen before. Python's `ssl` module does neither. A browser test therefore
   **cannot** validate a chain — the first thing to un-learn from this incident.
5. **Confirmation** in one command:

```bash
$ openssl s_client -connect api.ledgerly.com:443 -servername api.ledgerly.com </dev/null 2>/dev/null \
  | grep -E '^( [0-9] s:|Verify return code)'
 0 s:CN = api.ledgerly.com
Verify return code: 20 (unable to get local issuer certificate)
```

   Depth 0 only. **No intermediate is being served.** Compare with a healthy host, which shows depth
   0 and depth 1.

6. **Dependency health / change correlation.** `certbot`'s log shows a successful renewal at 03:14
   Sunday. The certificate is new and valid — the renewal worked. What changed is *which file nginx
   points at*.

### Root Cause

During a Saturday configuration cleanup, `ssl_certificate` was changed from
`/etc/letsencrypt/live/api.ledgerly.com/fullchain.pem` to `.../cert.pem`. The two files sit side by
side in the same directory, and `cert.pem` reads like the more obvious choice:

```text
cert.pem       leaf only                    ← what was configured
chain.pem      intermediates only
fullchain.pem  leaf + intermediates         ← what nginx must serve
privkey.pem    private key
```

nginx reloaded successfully — the file is a valid certificate, so no error was raised. Browsers kept
working because they fetched the missing intermediate themselves. Every non-browser client, which
is to say every integration customer, broke.

The change passed review, passed the smoke test (a browser check), and broke a class of client
nobody tested.

### Fix

*Mitigation and permanent fix (4 minutes):*

```diff
- ssl_certificate /etc/letsencrypt/live/api.ledgerly.com/cert.pem;
+ # fullchain.pem — leaf + intermediates. cert.pem is leaf-only and breaks every
+ # non-browser client (browsers hide it via AIA fetching). See 01.8.
+ ssl_certificate /etc/letsencrypt/live/api.ledgerly.com/fullchain.pem;
```

`nginx -t && nginx -s reload`, then verify from a clean trust store:

```bash
$ docker run --rm python:3.12-slim python -c \
  "import ssl,socket; ctx=ssl.create_default_context(); \
   s=ctx.wrap_socket(socket.create_connection(('api.ledgerly.com',443)), \
   server_hostname='api.ledgerly.com'); print('OK', s.version())"
OK TLSv1.3
```

*Customer remediation:* affected integrations reconnected on their next retry with no change needed
on their side — worth communicating explicitly, because several had already started implementing
`verify=False` workarounds. **Preventing a customer from disabling verification is part of resolving
this incident**, and is more urgent than the certificate itself.

### Prevention

- **A synthetic TLS check from a clean trust store**, every 5 minutes, from outside the network —
  the Python one-liner above as a monitoring probe. A browser check would have passed throughout.
- **Chain and expiry monitoring together**, since the `days_until_expiry` probe fails on both:

```yaml
# infra/alerts/tls.yaml
- alert: TLSCertificateExpiringSoon
  expr: tls_certificate_expiry_days < 21
  for: 1h
  annotations:
    summary: "{{ $labels.host }} certificate expires in {{ $value | printf \"%.0f\" }} days"
    runbook: "ACME renews at 30 days. An alert here means automation failed — check certbot timers."

- alert: TLSChainIncomplete
  expr: up{job="tls-probe"} == 0
  for: 5m
  annotations:
    summary: "TLS probe cannot validate {{ $labels.host }} from a clean trust store"
```

- **A CI check on the TLS configuration** asserting `ssl_certificate` ends in `fullchain.pem`. A
  one-line grep that would have blocked the change.
- **Alert on request-volume drops**, segmented by client type where possible. Two of this module's
  three silent incidents (01.4, and this one) presented first as traffic quietly going away.
- **Never validate TLS with a browser.** Add `openssl s_client` and a clean-container Python check to
  the deployment runbook.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the certificate expires? | Total outage for all clients, instantly. ACME automation + expiry alerting at 21 days is the only acceptable answer. |
| ...only the leaf is served? | Browsers work; Python/Go/Java fail. Validate from a clean trust store, never a browser. |
| ...the client's clock is wrong? | Validation fails ("not yet valid"). Common on IoT and freshly imaged VMs; ensure NTP. |
| ...the CA is compromised or distrusted? | All its certificates lose trust with a browser update. Mitigate with CT monitoring and CAA records; pinning trades one risk for another. |
| ...TLS terminates at the edge? | Internal traffic is plaintext. `X-Forwarded-Proto` must be trusted (01.10), and cookies must still be `Secure` (01.5). |
| ...an mTLS client certificate expires? | The dependent service is fully unreachable — and this typically fires outside business hours. Automate rotation or do not use mTLS. |
| ...someone sets `verify=False` to fix an error? | You have removed authentication and kept encryption — a private channel to an attacker. Trust the specific CA instead. |
| ...traffic is intercepted by a corporate proxy? | Some enterprise customers MITM with their own CA. Your client-side pinning will break for them; document it. |

## Common Pitfalls

**Serving `cert.pem` instead of `fullchain.pem`.** The incident above. Silent, browser-invisible, and
breaks every machine client. *Instead:* `fullchain.pem`, asserted in CI.

**`verify=False` in a Python client.** Removes authentication entirely; encryption then protects your
conversation with whoever intercepted it. *Instead:* trust the specific CA file. If a vendor tells
you to disable verification, that is a finding to escalate, not an instruction.

**Validating TLS with a browser.** Browsers repair chains and cache intermediates. *Instead:*
`openssl s_client` and a clean-container check.

**Treating certificate expiry as a calendar reminder.** Lifetimes are shrinking toward ~47 days;
manual renewal will not survive it. *Instead:* ACME plus alerting that fires only when automation
has already failed.

**HSTS `preload` added early.** Effectively irreversible for the preload-list lifetime; one HTTP-only
subdomain becomes unreachable for everyone. *Instead:* `max-age` first, `includeSubDomains` once
verified, `preload` last and deliberately.

**Assuming TLS makes the request trusted.** A valid TLS session authenticates the *server* to the
client, not the client to you, and grants no authorisation (08).

**Logging or exporting private keys.** They belong in a secrets manager with restricted read
(16.10), never in an image (14.7) or a repository.

## How to Test This

- A CI grep asserting `fullchain.pem` in every TLS configuration file.
- A clean-container TLS handshake test against staging as a deployment gate (no host trust store, no
  cached intermediates).
- A test that the outbound client rejects a bad certificate: point it at a `badssl.com`-style
  endpoint (or a locally generated self-signed cert) and assert `ssl.SSLCertVerificationError` — this
  is what catches an accidental `verify=False`.
- Assert `Strict-Transport-Security` is present on HTTPS responses (13.4, 16.12).

## Interview Questions

1. *Explain.* What does TLS guarantee, and name three things it does not. — Authentication,
   confidentiality, integrity; not client identity, not data at rest, not authorisation, not the
   destination hostname.
2. *Debug this.* Browsers work; Python clients get `unable to get local issuer certificate`. — Missing
   intermediate; browsers repair chains via AIA, Python does not.
3. *Explain.* Why does the server need to send the intermediate at all? — Clients hold roots, not
   intermediates; they must be able to build a path to something trusted.
4. *Design.* Where would you terminate TLS for a multi-tenant SaaS, and what does the application
   then need to be told? — Edge; `X-Forwarded-Proto`, trusted proxy ranges, `Secure` cookies.
5. *Explain.* What is forward secrecy and why does it matter? — Ephemeral session keys; recorded
   traffic stays safe after a key compromise.
6. *Explain.* What is SNI and what does it leak? — Hostname in the ClientHello, in the clear.
7. *Design.* Would you use mTLS between two internal services? What must exist first? — Only with
   automated certificate distribution and rotation; otherwise expiry becomes an outage.

## Key Takeaways

- TLS incidents are **identity** incidents: expired, incomplete, or mismatched certificates. The
  cryptography is not the risk; the paperwork is.
- **Serve `fullchain.pem`.** A leaf-only chain works in every browser and fails in every machine
  client — the most deceptive TLS failure there is.
- Never validate TLS with a browser. Use `openssl s_client` and a clean trust store.
- Certificate renewal must be automated, and expiry monitored so that an alert means *automation has
  already failed*. Lifetimes are getting shorter, not longer.
- `verify=False` removes the guarantee that matters. Trust a specific CA instead — always.
- Terminate at the edge by default; re-encrypt when compliance requires it; use mTLS only with
  automated rotation.
- TLS 1.3 removed the dangerous options. Enable 1.2 and 1.3, disable everything below, and stop
  tuning cipher suites by hand.
