## Concept

### Plain-English Explanation

Your browser holds credentials for many sites at once. Without a rule, a page on `evil.example.com`
could quietly make a request to `api.ledgerly.com`, your cookies would ride along automatically
(01.5), and the attacker's JavaScript could read your invoices. The **Same-Origin Policy** is the
rule that stops it: script on one origin cannot *read* responses from another origin.

CORS is the mechanism by which a server says *"actually, this specific other origin may read my
responses."* That is the sentence to internalise, because it inverts most people's intuition:

> **CORS does not protect your API. CORS is how you deliberately make your API less protected, for
> origins you name.**

Every CORS error a developer has ever seen is the browser doing its job. The instinct — "make the
error go away" — is what produces the vulnerability in this notebook's scenario.

And the corollary: CORS is enforced **only by browsers**. `curl`, Python, mobile apps and every
attacker's script ignore it entirely. A permissive CORS policy does not make your API vulnerable to
`curl`; it makes it vulnerable to *other people's users' browsers*. Your actual API protection is
authentication and authorisation (08, 16).

### Technical Explanation

**An origin** is the triple `(scheme, host, port)`. `https://app.ledgerly.com` and
`https://api.ledgerly.com` are different origins (different host). `https://app.ledgerly.com` and
`http://app.ledgerly.com` are different origins (different scheme). Note this differs from "site"
for cookies (01.5), where those would be same-*site* — a distinction that trips people up constantly.

**Simple requests vs preflighted requests.** A request avoids preflight only if all of these hold:

- Method is `GET`, `HEAD` or `POST`
- Headers are limited to a CORS-safelisted set (`Accept`, `Accept-Language`, `Content-Language`,
  `Content-Type`, plus a few)
- `Content-Type` is one of `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`

**`Content-Type: application/json` is not on that list**, and `Authorization` is not safelisted.
Therefore *every JSON API call from a browser is preflighted* — which is why preflight behaviour
matters so much for an API like Ledgerly's.

```text
Preflight (an OPTIONS request the browser sends by itself — your JS never sees it)

  OPTIONS /v1/invoices HTTP/1.1
  Origin: https://app.ledgerly.com
  Access-Control-Request-Method: POST
  Access-Control-Request-Headers: content-type, authorization, idempotency-key
        │
        ▼
  HTTP/1.1 204 No Content
  Access-Control-Allow-Origin: https://app.ledgerly.com   ← exact origin, not *
  Access-Control-Allow-Methods: GET, POST, PUT, DELETE
  Access-Control-Allow-Headers: content-type, authorization, idempotency-key
  Access-Control-Allow-Credentials: true
  Access-Control-Max-Age: 600            ← cache this decision for 10 minutes
  Vary: Origin                           ← ⚠️ the response depends on Origin (01.4)

  ... then the real request follows, with its own Access-Control-Allow-Origin header.
```

**The credentials rules**, which exist for one reason:

| `Allow-Origin` | `Allow-Credentials` | Result |
|---|---|---|
| `https://app.ledgerly.com` | `true` | ✅ Works; that one origin may make credentialed requests |
| `*` | absent | ✅ Works for unauthenticated public reads |
| `*` | `true` | ❌ **Browser rejects it** — the spec forbids this combination |
| Reflected `Origin` | `true` | ⚠️ Works, and is equivalent to allowing *every* origin. This is the vulnerability. |

The third row is a deliberate guard rail: `*` plus credentials would mean "any website may read
authenticated responses", so the spec makes it impossible. The fourth row is how developers
accidentally build exactly that, one origin at a time, because reflection satisfies the letter of the
rule while defeating its purpose.

**`Access-Control-Expose-Headers`** is the other side: by default JavaScript can read only a handful
of response headers. If your client needs `ETag` (01.4), `Location` (01.3) or `RateLimit-Remaining`
(02.12), you must expose them explicitly — otherwise they are present on the wire and invisible to
the client, which produces a uniquely confusing bug report.

### Mental Model

> The browser asks: *"May the script at origin X read a response from origin Y?"* CORS headers are
> **Y's answer**, and only browsers listen. Every CORS setting is a decision about **which other
> websites may act as your users**. Write it as an allow-list of named origins, never as a pattern
> that computes an answer from the attacker's input.

## How It Works

Why reflecting the `Origin` header is a vulnerability, drawn as the attack:

```text
Victim is logged in to app.ledgerly.com (session cookie, SameSite=None; Secure) and visits evil.example.com

  evil.example.com serves:
      fetch("https://api.ledgerly.com/v1/invoices", {credentials: "include"})
              │
              ├─ browser sends preflight:  Origin: https://evil.example.com
              │
              ▼
      Ledgerly reflects whatever it was sent:
          Access-Control-Allow-Origin: https://evil.example.com
          Access-Control-Allow-Credentials: true
              │
              ├─ browser: "the server named my origin explicitly and allows
              │            credentials — this is authorised" → sends the real request
              │            WITH the victim's cookies
              ▼
      200 OK  { "invoices": [ … the victim's real data … ] }
              │
              └─ evil.example.com's JavaScript READS the body and exfiltrates it.
```

Note the premise: the session cookie is `SameSite=None; Secure` — realistic for a product with
embedded cross-site widgets, or a cross-site SSO handoff like 01.5's. A `__Host-` cookie with
`SameSite=Lax` (01.5's default) would **not** accompany this request: `Lax` cookies cross sites only
on top-level navigations with safe methods, and a script `fetch()` is a subresource request. So
`SameSite=Lax` *does* block this specific vector — defence in depth, and why origin reflection plus
`Allow-Credentials: true` plus a `SameSite=None` cookie is the truly dangerous combination. CSRF
defences do not save you either — this is not a forged *write*, it is an authorised *read*. The only
control that was supposed to stop this is the Same-Origin Policy, and the server explicitly waived it.

## Code Example

Ledgerly's dashboard (`https://app.ledgerly.com`) calls its API (`https://api.ledgerly.com`), so CORS
is genuinely required. Correct configuration is an explicit list, loaded from settings.

```python
# ledgerly/config.py
from pydantic import AnyHttpUrl, field_validator
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    # Explicit origins only. No regex, no wildcards, no computation from the request.
    cors_allowed_origins: list[AnyHttpUrl] = []

    @field_validator("cors_allowed_origins")
    @classmethod
    def reject_wildcards(cls, value: list[AnyHttpUrl]) -> list[AnyHttpUrl]:
        # A misconfiguration must fail at STARTUP, loudly — never at runtime, silently.
        for origin in value:
            if "*" in str(origin):
                raise ValueError(f"Wildcard CORS origin {origin!r} is not permitted.")
        return value
```

Validating at settings-load time matters more than it looks: a CORS mistake produces no error, no
failing request and no log line — only a quieter security boundary. Refusing to start is the only
feedback loop fast enough to catch it.

```python
# ledgerly/main.py
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from ledgerly.config import get_settings

settings = get_settings()
app = FastAPI(title="Ledgerly Invoicing API")

app.add_middleware(
    CORSMiddleware,
    # ✅ exact origins from configuration, per environment
    allow_origins=[str(o) for o in settings.cors_allowed_origins],
    # ❌ NEVER: allow_origin_regex=r"https://.*\.ledgerly\.com"  — see pitfalls;
    #    a regex without an anchor matches https://ledgerly.com.evil.example.com
    allow_credentials=True,          # the dashboard sends its session cookie
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
    allow_headers=["Authorization", "Content-Type", "Idempotency-Key", "If-Match"],
    # Without this, the dashboard cannot read these headers even though they arrive:
    expose_headers=["ETag", "Location", "RateLimit-Remaining", "RateLimit-Reset", "Retry-After"],
    max_age=600,                     # cache the preflight decision for 10 minutes
)
```

```bash
# .env.production
LEDGERLY_CORS_ALLOWED_ORIGINS=["https://app.ledgerly.com","https://admin.ledgerly.com"]
# .env.local
LEDGERLY_CORS_ALLOWED_ORIGINS=["http://localhost:5173"]
```

Verify the policy from the shell — a preflight is just an `OPTIONS` request you can send yourself:

```bash
# Allowed origin → the browser will proceed
$ curl -s -i -X OPTIONS https://api.ledgerly.com/v1/invoices \
    -H 'Origin: https://app.ledgerly.com' \
    -H 'Access-Control-Request-Method: POST' \
    -H 'Access-Control-Request-Headers: content-type,authorization' | grep -i '^access-control\|^vary'
access-control-allow-origin: https://app.ledgerly.com
access-control-allow-credentials: true
access-control-allow-methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
access-control-allow-headers: Authorization, Content-Type, Idempotency-Key, If-Match
access-control-max-age: 600
vary: Origin

# Attacker origin → NO Access-Control-Allow-Origin header at all. The browser blocks it.
$ curl -s -i -X OPTIONS https://api.ledgerly.com/v1/invoices \
    -H 'Origin: https://evil.example.com' \
    -H 'Access-Control-Request-Method: POST' | grep -ci 'access-control-allow-origin'
0
```

That second command is the entire security test, and it takes one second to run. It is the check
that was missing in the scenario below.

## Design Patterns / Tradeoffs

### Choosing an origin policy

**A. Explicit allow-list** (recommended)

- *How it works:* a configured list of exact origins, per environment.
- *Advantages:* auditable; a new origin is a reviewed change; impossible to accidentally allow an
  attacker; trivially testable.
- *Disadvantages:* every new frontend, preview deployment or partner needs a config change and deploy.
- *Failure mode:* a preview environment cannot call the API, and someone is tempted to "temporarily"
  loosen it — which is precisely how the incident below started.
- *Use when:* always, for authenticated APIs.

**B. `Access-Control-Allow-Origin: *` without credentials**

- *Advantages:* correct and safe for genuinely public data; cacheable by CDNs (01.4); no
  configuration churn.
- *Disadvantages:* cannot be combined with credentials, by design.
- *Use when:* public read-only endpoints — a status page, public exchange rates, published docs.
- *Do NOT use when:* the response depends on who is asking.

**C. Dynamic reflection with an allow-list check**

- *How it works:* read `Origin`, check membership in a list, echo it back if it matches.
- *Advantages:* necessary when you must support many origins with credentials (a multi-tenant product
  with per-customer domains).
- *Disadvantages:* the check is now code you can get wrong — and the common bugs (unanchored regex,
  `startswith`, `in`) all fail *open*.
- *Failure mode:* `origin.endswith(".ledgerly.com")` matches `https://evil-ledgerly.com`;
  `"ledgerly.com" in origin` matches `https://ledgerly.com.evil.example.com`.
- *Use when:* per-tenant custom domains, with **exact set membership** (`origin in ALLOWED_SET`) and
  never a substring or regex test, plus `Vary: Origin`.
- *Do NOT use when:* an explicit static list would do.

**D. No CORS at all — same-origin architecture**

- *How it works:* serve the dashboard and API from the same origin (`https://app.ledgerly.com` and
  `https://app.ledgerly.com/api/...`) via a reverse proxy path rule (01.10).
- *Advantages:* **no CORS whatsoever**; cookies are same-origin; no preflight round trip on every
  call; an entire class of misconfiguration cannot exist.
- *Disadvantages:* couples frontend and API routing; needs a proxy rule; harder if the API is also
  consumed by third parties on other origins.
- *Use when:* a first-party SPA is the main consumer. This is genuinely the best answer more often
  than teams realise, and it is worth considering before configuring CORS at all.

**Recommendation:** prefer D for first-party dashboards; A when origins must differ; B for public
endpoints; C only for per-tenant domains, with exact set membership.

### `Access-Control-Max-Age`

- **Short (0–60 s):** policy changes take effect quickly; costs an extra `OPTIONS` round trip on
  nearly every request — measurable on a chatty dashboard over a high-latency link.
- **Long (600 s+):** removes preflight cost almost entirely; a policy change can take up to that long
  to reach an active browser. Browsers cap it anyway (Chrome at 7200 s, Firefox at 86400 s).
- **Recommendation:** 600 s in production, 0 in development where you are actively changing the
  policy and want to stop debugging a cached preflight.

## Production Scenario

**Ledgerly, Wednesday 16:40.** A bug-bounty report arrives, severity "critical", with a working
proof of concept: an HTML page hosted on the researcher's domain that, when opened by a logged-in
Ledgerly user, reads and displays that user's full invoice list — customer names, amounts, bank
details.

There is no outage. Every metric is healthy. This is the second incident in this module that a
dashboard cannot see.

### Symptoms

- A single static HTML file, opened in any browser by a logged-in user, exfiltrates that user's data.
- The API behaves normally: authenticated request, correct tenant, `200 OK`, correct data. From the
  server's point of view **nothing is wrong** — a legitimate user's browser made a legitimate,
  authenticated request.
- No unusual traffic volume, no errors, no anomalous logs. The requests are indistinguishable from
  the dashboard's own.
- Time-to-exploit for an attacker: sending one link to one employee of one customer.

### Diagnosis

1. **Alert.** None possible. The attack produces valid, authenticated, correctly-scoped requests.
   This is the defining property of this vulnerability class: **it is invisible in application
   telemetry**, which is why the control must be configuration-correct rather than monitored.
2. **Reproduce.** The researcher's PoC works on the first try. Confirmed, not theoretical.
3. **Inspect the response**, which identifies the flaw immediately:

```bash
$ curl -s -i https://api.ledgerly.com/v1/invoices -H 'Origin: https://totally-not-ledgerly.example' \
  | grep -i 'access-control'
access-control-allow-origin: https://totally-not-ledgerly.example    # ⚠️ reflected
access-control-allow-credentials: true                               # ⚠️ with credentials
```

   Any origin is allowed, with credentials. That is the whole bug, visible in one command.
4. **Find the change.** `git log -S allow_origin_regex` locates a commit from four months earlier:

```diff
-    allow_origins=[str(o) for o in settings.cors_allowed_origins],
+    allow_origin_regex=".*",     # TODO: tighten once preview URLs are stable
     allow_credentials=True,
```

5. **Read the commit message**, which explains everything: *"Fix CORS errors on Vercel preview
   deploys."* Preview deployments get a new random subdomain per pull request, so no static list
   could match them. The developer needed the previews to work, `.*` made the error go away, and the
   `TODO` was never revisited.
6. **Assess blast radius.** Web-server logs retain `Origin` and `Referer`. A query over 120 days
   shows only Ledgerly's own origins and localhost — no evidence of exploitation before the
   researcher's PoC. That answer exists only because those fields were logged, which is a decision
   someone made long before it mattered (16.13).

### Root Cause

`allow_origin_regex=".*"` combined with `allow_credentials=True` instructs the browser that **every
website on the internet** may make credentialed requests to Ledgerly's API and read the responses.
The Same-Origin Policy — the single control that stops a malicious page from acting as a logged-in
user — was disabled globally to unblock preview deployments.

The mechanism worked exactly as specified. The configuration described a policy nobody intended.

### Fix

*Mitigation (immediate, 11 minutes):* restore the explicit allow-list and deploy. Preview
deployments broke again, which was accepted for the day.

```diff
-    allow_origin_regex=".*",
+    allow_origins=[str(o) for o in settings.cors_allowed_origins],
```

*Permanent fix — solve the original problem properly, so the shortcut is never needed again:*

1. **Preview deployments proxy the API through their own origin** (option D above): the preview
   frontend serves `/api/*` via a rewrite to a shared staging API. Same origin, therefore no CORS,
   therefore no dynamic origin list. The problem that caused the vulnerability stops existing.
2. **Staging uses a separate API host with its own explicit list**, and staging holds no production
   data — so even a mistake there is not a breach.
3. The `reject_wildcards` validator (shown earlier) makes a wildcard origin **fail at startup**. A
   future engineer cannot reintroduce this without the service refusing to boot.

### Prevention

- **A security contract test in CI** that asserts a hostile origin is refused:

```python
# tests/security/test_cors_policy.py
import pytest

HOSTILE = [
    "https://evil.example.com",
    "https://app.ledgerly.com.evil.example.com",   # substring/suffix bugs
    "https://evil-ledgerly.com",                   # endswith bugs
    "http://app.ledgerly.com",                     # wrong scheme
    "null",                                        # sandboxed iframes / file://
]

@pytest.mark.anyio
@pytest.mark.parametrize("origin", HOSTILE)
async def test_hostile_origins_are_not_allowed(client, origin: str) -> None:
    response = await client.options(
        "/v1/invoices",
        headers={"Origin": origin, "Access-Control-Request-Method": "POST"},
    )
    assert "access-control-allow-origin" not in response.headers, (
        f"CORS allows {origin!r} — any page on that origin can act as a logged-in user"
    )

@pytest.mark.anyio
async def test_allowed_origin_works_and_varies(client) -> None:
    response = await client.options(
        "/v1/invoices",
        headers={"Origin": "https://app.ledgerly.com",
                 "Access-Control-Request-Method": "POST"},
    )
    assert response.headers["access-control-allow-origin"] == "https://app.ledgerly.com"
    assert "origin" in response.headers.get("vary", "").lower()   # cache correctness (01.4)
```

- **A startup validator** that refuses wildcards — configuration that cannot be wrong beats
  configuration that is reviewed.
- **A lint rule / CODEOWNERS gate** on the CORS configuration block, so any change requires a
  security reviewer. `allow_origin_regex` is banned outright in this codebase.
- **Log `Origin` and `Referer` on authenticated requests.** They cost nothing and they are the only
  way to bound the blast radius when this class of report arrives (16.13).
- **A cultural prevention that matters more than the technical ones:** when a developer is blocked by
  a security control, the fix is to solve their problem (a same-origin proxy for previews), not to
  ask them to be careful. A `TODO` next to a disabled security control has a half-life of years.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...an attacker calls your API with `curl`? | CORS is irrelevant — only browsers enforce it. Your defence is authentication and authorisation (08, 16). |
| ...you reflect the `Origin` header with credentials? | Every website can read your users' data. This is a breach, not a misconfiguration. |
| ...you set `Allow-Origin: *` with `Allow-Credentials: true`? | The browser rejects it — the spec prevents this specific mistake, which is why reflection is the dangerous workaround. |
| ...your allow-list check uses a regex? | Unanchored regexes match hostile suffixes. Use exact set membership. |
| ...you allow origins dynamically without `Vary: Origin`? | A cache may serve one origin's allow header to another (01.4). Always `Vary: Origin`. |
| ...a client needs to read `ETag` or `RateLimit-Remaining`? | It cannot, unless listed in `Access-Control-Expose-Headers`. The header is on the wire but invisible to JS. |
| ...the preflight fails? | The real request is never sent. Your server logs show an `OPTIONS` and nothing else — the classic "the request never arrives" report. |
| ...`Origin: null` arrives? | From sandboxed iframes, `file://` and some redirects. Never allow it; it is not an origin you can attribute. |

## Common Pitfalls

**Reflecting `Origin` to "fix" a CORS error.** The vulnerability above. *Instead:* add the specific
origin to the list, or remove the cross-origin requirement with a same-origin proxy.

**`allow_origin_regex` with an unanchored pattern.** `https://.*\.ledgerly\.com` matches
`https://x.ledgerly.com.evil.example.com`. *Instead:* exact set membership; if you must pattern-match,
anchor with `^...$` and test hostile inputs.

**Believing CORS protects your API.** It protects *other people's users*, not your server. A locked-down
CORS policy on an endpoint with broken authorisation is still fully exploitable by `curl` (16.8).

**Forgetting `Vary: Origin` when the allow header is dynamic.** A shared cache can hand one origin's
policy to another — the 01.4 leak class, applied to security headers.

**Forgetting `expose_headers`.** Frontend engineers report "the server isn't sending `ETag`"; it is,
and the browser is hiding it. *Instead:* expose every header the client legitimately needs.

**Preflight blocked by authentication middleware.** Browsers send `OPTIONS` **without credentials**.
Auth middleware that rejects unauthenticated requests will reject the preflight, and every
cross-origin call fails with a confusing CORS error. *Instead:* let `OPTIONS` through before auth —
`CORSMiddleware` handles this when added correctly, but a custom auth middleware added *outside* it
will not.

**Different CORS configuration in the proxy and the app.** Both add headers, browsers see duplicates,
and requests fail. *Instead:* one owner. Ledgerly's is the application.

---

## How to Test This

- The hostile-origin test above — the single highest-value test in this notebook. Include suffix,
  substring, scheme and `null` variants.
- A test that the allowed origin succeeds *and* that `Vary: Origin` is present.
- A test that `OPTIONS` on an authenticated route returns `2xx` without credentials, so preflights are
  never blocked by auth middleware.
- A test asserting the expected `expose_headers` set, so removing one does not silently break the
  dashboard.

   Same-Origin Policy; it makes the API *less* protected, for named origins.

   Non-simple method/headers/content type; `application/json` is not safelisted.

7. *Explain.* Does CORS stop an attacker using `curl` against your API? — No. Only browsers enforce it.

## Key Takeaways

- CORS is a **relaxation** of the Same-Origin Policy, enforced only by browsers. It protects other
  people's users; it is not an API security control.
- Every CORS setting answers the question *"which other websites may act as my users?"* Answer it
  with an explicit list of exact origins.
- **Origin reflection with credentials is equivalent to allowing every website.** It is the most
  common critical CORS finding, and it usually starts as a `TODO`.
- `*` and `Allow-Credentials: true` cannot be combined — that guard rail is why reflection is the
  dangerous path.
- Always `Vary: Origin` when the allow header depends on the request; always `expose_headers` for
  anything the client must read; never let auth middleware reject `OPTIONS`.
- The best CORS configuration is often **no CORS**: serve the SPA and API from one origin behind a
  proxy path rule.
- Make misconfiguration impossible at startup rather than detectable at runtime — this class of bug
  is invisible in telemetry.
