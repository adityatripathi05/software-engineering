# 01.3 Status Codes and Headers

> **Prerequisites:** 01.1 (lifecycle), 01.2 (methods) · modern-python 18.1 (the status-code taxonomy as a client)
> **What you'll learn:**
> - Pick the correct status for the cases that are genuinely ambiguous — `400` vs `422`, `401` vs `403`, `404` vs `403`, `409` vs `422`, `500` vs `502` vs `503`
> - Understand what each class tells a *client's retry logic*, and why that is the real reason the choice matters
> - Use the headers that carry contract information: `Allow`, `Retry-After`, `Location`, `ETag`, `Vary`, `RateLimit-*`
> - Recognise a retry storm caused by an incomplete error response
> **Level:** Beginner

---

> ⚡ **Monday 02:10** — a p99 page for the whole API in the middle of the night. The cause: a refactor that dropped a single response header.

## Concept

### Plain-English Explanation

A status code is not a description for a human reading logs. It is an **instruction to the caller's
error handling**. Three digits tell every client library, proxy and retry loop what to do next:
give up, try again, try again later, fix the request, or follow a pointer somewhere else.

Get it wrong and the failure is not "a slightly misleading log line". Get it wrong and a thousand
clients retry something that will never succeed, or give up on something that would have worked a
second later. The status code is where your API's reliability meets everyone else's.

Headers are the same idea for metadata. They carry the parts of the contract that are not the body:
how to authenticate, how long to wait, what the resource version is, which methods are allowed, what
varies the cache key. A response with the right status and an empty header set is only half an
answer.

### Technical Explanation

**The five classes, read as instructions:**

| Class | Meaning | What a well-behaved client does |
|---|---|---|
| `1xx` | Interim | Keeps waiting (`100 Continue`, `101 Switching Protocols` for WebSockets — 03.12) |
| `2xx` | Success | Proceeds |
| `3xx` | Redirection | Follows the `Location` header (usually automatically) |
| `4xx` | Client error | **Does not retry** — retrying an identical request is pointless. Exceptions: `408`, `425`, `429`. |
| `5xx` | Server error | **May retry** — the request may be fine and the server temporarily is not |

That table is the whole reason status codes matter. A `4xx` says *"you are wrong; do not come back
with the same thing."* A `5xx` says *"I am wrong; come back."* Miscategorising is what produces
either a retry storm or a silently dropped request.

**The genuinely ambiguous choices**, resolved:

- **`400` vs `422`.** `400 Bad Request` — the request is malformed: broken JSON, wrong content type,
  a header the parser rejects. `422 Unprocessable Content` — the syntax is fine but the *semantics*
  are wrong: `amount_cents: -50`, a `due_date` before the issue date. FastAPI returns `422` for
  Pydantic validation failures by default, which fits this split. Both are fine; be consistent, and
  document which you use (02.9).
- **`401` vs `403`.** `401 Unauthorized` — *"I do not know who you are"*: no credentials, expired
  token, bad signature. It **must** carry a `WWW-Authenticate` header. `403 Forbidden` — *"I know who
  you are and you may not do this"*. Sending `401` for an authorised-but-forbidden action makes
  clients refresh their token in a loop; that is a real production bug (08.4).
- **`404` vs `403` for another tenant's resource.** `403` confirms the resource exists — that is an
  information leak (16.8, BOLA). In a multi-tenant API, `GET /v1/invoices/inv_other_tenant` returns
  **`404`**. You are not lying; from that tenant's namespace, it does not exist.
- **`409` vs `422`.** `409 Conflict` — the request is valid but conflicts with current state: voiding
  an already-paid invoice, a duplicate unique key, a failed `If-Match` on a `PUT`. `422` — the
  request could never be valid for any state. Rule: if retrying later *could* succeed, it is `409`.
- **`500` vs `502` vs `503` vs `504`.** `500` — your code raised. `502 Bad Gateway` — a proxy got a
  broken response from upstream. `503 Service Unavailable` — you are up but deliberately refusing
  (overload, shedding, draining during a deploy); **should carry `Retry-After`**. `504 Gateway
  Timeout` — a proxy gave up waiting on upstream. Emitting `503` while shedding load rather than
  `500` is what lets clients back off correctly (15.17).
- **`429 Too Many Requests`.** A `4xx` that *is* retryable — the one every client library treats
  specially. It **must** carry `Retry-After` (02.12); the production scenario below is what happens
  when it does not.

**Headers worth knowing**, grouped by what they do:

```text
Contract / negotiation   Accept, Content-Type, Content-Length, Accept-Encoding, Allow
Caching & concurrency    Cache-Control, ETag, Last-Modified, If-None-Match, If-Match, Vary  (01.4)
Authentication           Authorization, WWW-Authenticate, Set-Cookie, Cookie                (01.5, 08)
Rate limiting            Retry-After, RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset (02.12)
Location & identity      Location, Content-Location
Tracing & correlation    traceparent, X-Request-Id                                          (15.2, 15.6)
Proxy metadata           X-Forwarded-For, X-Forwarded-Proto, Forwarded                      (01.10)
Security                 Strict-Transport-Security, Content-Security-Policy, ...            (16.12)
```

Header mechanics that bite people: names are **case-insensitive**; some headers may appear multiple
times and are combined with commas (`Accept`, `Set-Cookie` is the notorious exception that must not
be combined); your server and proxy each cap header sizes (gunicorn: 8190 bytes per field by
default; nginx-class proxies have their own limits — a fat JWT plus long cookies can exceed the
smallest cap in the chain and produce a `431`/`400` your app never sees); and
`X-`-prefixed custom names have been deprecated since RFC 6648 (use `Ledgerly-Trace-Id`, not
`X-Ledgerly-Trace-Id`, for anything new).

### Mental Model

> The status code is a **branch instruction in the caller's control flow**: `4xx` means "do not
> loop", `5xx` means "loop with backoff", `429`/`503` mean "loop, and here is how long to wait".
> Headers are the arguments to that instruction. Choose the status by asking *what should the
> caller's retry logic do?* — never by asking what reads nicely in a log.

## How It Works

What a typical client actually does with your response, and which header it needs:

```text
                         ┌── 2xx ──▶ proceed
                         │
                         ├── 301/308 ─▶ follow Location, remember it (cached redirect!)
                         ├── 302/307 ─▶ follow Location, do not remember
                         │             (307/308 preserve the method; 301/302 historically
                         │              rewrote POST→GET — never redirect a POST with 302)
   response ──── status ─┤
                         ├── 401 ────▶ read WWW-Authenticate → refresh token → retry ONCE
                         ├── 403 ────▶ surface to user, do not retry
                         ├── 404 ────▶ surface, do not retry
                         ├── 409 ────▶ re-read state, maybe retry with new ETag
                         ├── 422 ────▶ show field errors from the body (02.9)
                         ├── 429 ────▶ sleep(Retry-After) → retry   ⚠️ if the header is
                         │                                            missing, many clients
                         │                                            retry IMMEDIATELY
                         ├── 5xx ────▶ backoff + jitter, bounded attempts (15.14)
                         └── 503 ────▶ sleep(Retry-After) → retry
```

The `429` branch is the dangerous one. `urllib3.Retry`, Java's `resilience4j`, Go's
`hashicorp/go-retryablehttp` and most SDKs all *honour* `Retry-After` when it is present — and most
fall back to their default schedule when it is absent. Some of those defaults are 0 seconds. (`httpx`
is the counter-example: `HTTPTransport(retries=N)` retries connect errors only and never reads
`Retry-After` — an SDK built on it must add that handling itself.)

**`Location` semantics** deserve one note because it is routinely wrong: on `201 Created`, `Location`
holds the URL of the new resource (`/v1/invoices/inv_9f2`). On `202 Accepted`, it holds the URL of
the *status resource* for the async operation (02.10). On `3xx`, it is where to go instead. Same
header, three meanings, decided by the status.

## Code Example

Ledgerly maps domain errors to statuses in exactly one place. Handlers raise domain exceptions;
they never choose status codes. That separation is the point — it is the 07.3 service-layer rule
arriving early.

```python
# ledgerly/errors.py — domain errors know nothing about HTTP.
from dataclasses import dataclass

class LedgerlyError(Exception): ...

@dataclass
class InvoiceNotFound(LedgerlyError):
    invoice_id: str

@dataclass
class InvoiceAlreadyPaid(LedgerlyError):
    """Valid request, wrong current state → retryable in principle → 409."""
    invoice_id: str

@dataclass
class TenantQuotaExceeded(LedgerlyError):
    """Deliberate refusal with a known recovery time → 429 + Retry-After."""
    retry_after_seconds: int

@dataclass
class TaxProviderUnavailable(LedgerlyError):
    """A dependency failed, not the caller → 502/503, never 500."""
```

```python
# ledgerly/http/error_mapping.py — the single place HTTP status is decided.
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

from ledgerly.errors import (
    InvoiceNotFound, InvoiceAlreadyPaid, TenantQuotaExceeded, TaxProviderUnavailable,
)

def problem(status: int, title: str, detail: str, request: Request,
            **extra: object) -> JSONResponse:
    """RFC 9457 Problem Details — the body format is specified fully in 02.9."""
    return JSONResponse(
        status_code=status,
        media_type="application/problem+json",
        content={"type": f"https://api.ledgerly.com/problems/{title.lower().replace(' ', '-')}",
                 "title": title, "status": status, "detail": detail,
                 "instance": str(request.url.path), **extra},
    )

def register_error_handlers(app: FastAPI) -> None:

    @app.exception_handler(InvoiceNotFound)
    async def _(request: Request, exc: InvoiceNotFound) -> JSONResponse:
        # 404, not 403 — never confirm existence across tenants (16.8).
        return problem(404, "Not Found", f"No invoice {exc.invoice_id}.", request)

    @app.exception_handler(InvoiceAlreadyPaid)
    async def _(request: Request, exc: InvoiceAlreadyPaid) -> JSONResponse:
        return problem(409, "Conflict",
                       f"Invoice {exc.invoice_id} is paid and cannot be voided.", request)

    @app.exception_handler(TenantQuotaExceeded)
    async def _(request: Request, exc: TenantQuotaExceeded) -> JSONResponse:
        response = problem(429, "Too Many Requests",
                           "Monthly API quota exceeded.", request,
                           retry_after=exc.retry_after_seconds)
        # ⚠️ THE header that prevents a retry storm. Never emit 429 without it.
        response.headers["Retry-After"] = str(exc.retry_after_seconds)
        response.headers["RateLimit-Reset"] = str(exc.retry_after_seconds)
        return response

    @app.exception_handler(TaxProviderUnavailable)
    async def _(request: Request, exc: TaxProviderUnavailable) -> JSONResponse:
        # 502: WE are fine; an upstream we depend on is not. 500 would tell the
        # client "your request broke us", which is both untrue and unactionable.
        response = problem(502, "Bad Gateway",
                           "Tax rate provider is unavailable; retry shortly.", request)
        response.headers["Retry-After"] = "5"
        return response
```

And the success side, where headers carry as much contract as the body:

```python
# ledgerly/routers/invoices.py (excerpt)
@router.post("", status_code=201, response_model=InvoiceOut)
async def create_invoice(body: InvoiceCreate, response: Response,
                         svc: Service, tenant: Tenant) -> InvoiceOut:
    invoice = await svc.create(tenant, body)
    response.headers["Location"] = f"/v1/invoices/{invoice.id}"   # 201 → the new resource
    response.headers["ETag"] = f'"{invoice.version}"'             # enables If-Match (01.4)
    return invoice
```

Seen from the wire:

```bash
$ curl -i -X POST https://api.ledgerly.com/v1/invoices -H 'Idempotency-Key: 7c1f…' -d @invoice.json
HTTP/1.1 201 Created
location: /v1/invoices/inv_9f2c41
etag: "1"
ratelimit-limit: 1000
ratelimit-remaining: 863
content-type: application/json

$ curl -i -X POST https://api.ledgerly.com/v1/invoices -d @invoice.json   # quota gone
HTTP/1.1 429 Too Many Requests
retry-after: 47
ratelimit-limit: 1000
ratelimit-remaining: 0
ratelimit-reset: 47
content-type: application/problem+json

{"type":"https://api.ledgerly.com/problems/too-many-requests","title":"Too Many Requests",
 "status":429,"detail":"Monthly API quota exceeded.","retry_after":47}
```

The second response tells a client library everything it needs to behave correctly **without a human
reading the docs**. That is the standard to aim for.

## Design Patterns / Tradeoffs

### Where the error status is decided

**A. Raise `HTTPException` in the handler**

- *How it works:* the router raises `HTTPException(status_code=409, detail=...)` directly.
- *Advantages:* immediate, obvious, no indirection; fine for tiny services.
- *Disadvantages:* HTTP concerns leak into business logic; the same domain error gets mapped
  differently in different routers; you cannot reuse the service layer from a worker or CLI (11.1)
  without dragging FastAPI along.
- *Failure mode:* the identical "already paid" condition returns `400` on one route and `409` on
  another; clients build per-route special cases.
- *Use when:* the check is genuinely an HTTP-layer concern (bad header, unsupported media type).
- *Do NOT use when:* the condition arises inside the service or repository layer.

**B. Domain exceptions + a central mapping** (shown above)

- *How it works:* services raise typed domain errors; one module maps them to statuses.
- *Advantages:* one table to review and test; services are reusable from workers; consistent
  taxonomy across the API; adding a status is a one-line change.
- *Disadvantages:* one more indirection; the mapping table must be maintained.
- *Failure mode:* an unmapped domain error falls through to a generic `500` — mitigate with a test
  that asserts every `LedgerlyError` subclass has a handler.
- *Use when:* anything beyond a handful of routes. This is the default for the rest of the curriculum.

**C. Result objects instead of exceptions**

- *How it works:* services return `Ok(value) | Err(code)`; routers translate.
- *Advantages:* errors are visible in signatures; no invisible control flow; type checkers help.
- *Disadvantages:* verbose in Python; every layer must propagate; unfamiliar to most teams.
- *Use when:* a small, hot, well-typed core where exception cost or invisibility genuinely matters.

### Fine-grained statuses vs a small stable set

- **Fine-grained** (`402`, `409`, `410`, `412`, `422`, `423`, `428`, `451`) tells clients precisely
  what happened and lets generic middleware behave well. Costs: clients must handle more branches,
  and some corporate proxies mangle uncommon codes.
- **Small set** (`400`, `401`, `403`, `404`, `409`, `429`, `500`, `503`) plus a machine-readable
  `type` field in the body (02.9) keeps client code simple while still being precise. Costs: clients
  must read the body to differentiate.
- **Recommendation:** a small status set for control flow + a stable `type` URI in the body for
  detail. Clients branch on status; humans and dashboards read `type`. Never encode meaning only in
  the human-readable `detail` string — it will be translated or reworded and break someone.

### The `200`-with-an-error-body anti-pattern

Some APIs return `200 OK` with `{"success": false, "error": "..."}`. It is worth naming why this is
not a style preference:

- Every generic retry, alerting, circuit-breaker (15.15) and dashboard in the world keys off status.
  With `200`, your error rate is permanently zero and your circuit breaker never opens.
- Load balancers cannot health-check meaningfully.
- Caches may store the failure as a success (01.4).
- *The only defensible use:* a batch endpoint where individual items fail (02.7) — then the outer
  status is `207 Multi-Status` or `200` with a per-item status array, and the semantics are
  documented.

## Production Scenario

**Ledgerly, Monday 02:10.** A `p99 latency` page fires for the whole API. Within four minutes the
error rate crosses 30% and the on-call escalates. Nothing was deployed for three days.

### Symptoms

- `http_requests_total` rate: **8,400/s**, against a normal overnight baseline of ~150/s.
- Almost all of it is `429`: `sum(rate(http_requests_total{status="429"}[1m])) = 7,900`.
- Successful requests are *also* degraded — p99 on `GET /v1/invoices` rose from 40 ms to 2.1 s,
  because the 429s still cost a TLS handshake, a rate-limit lookup in Redis, and an event-loop slot.
- `redis_commands_processed_total` up 50×; Redis CPU at 88%.
- All the traffic carries one API key, `key_live_7ac…`, belonging to a single mid-size customer, and
  one user agent: `python-requests/2.32.3`.
- No 5xx. No deploy. No infrastructure change.

### Diagnosis

1. **Alert** on latency SLO. The first useful question — *is this more work, or slower work?* — is
   answered by request rate: 56× normal. It is more work.
2. **Metrics.** Split by status: 94% are `429`. The rate limiter is doing its job; something is
   ignoring it. Split by API key: one key. Split by route: `POST /v1/invoices`.
3. **Logs.** Sampled request logs for that key show the same `Idempotency-Key` value repeating up to
   60 times within a second:

```json
{"ts":"2026-08-24T02:11:03.412Z","route":"/v1/invoices","status":429,"api_key":"key_live_7ac…",
 "idempotency_key":"batch-2026-08-24-0001","tenant":"t_44f1","retry_after_sent":null}
```

   The `retry_after_sent: null` field (added by the logging middleware precisely to catch this) is
   the smoking gun.
4. **Trace.** Traces show a tight loop: request → `429` in 4 ms → next request 6 ms later. There is
   no backoff at all.
5. **Dependency health.** Redis is hot but not the cause; it is a victim. Postgres is idle — almost
   nothing is reaching it.
6. **Root cause identified by reading the 429 response**, reproduced with `curl`.

### Root Cause

Two weeks earlier, the rate limiter had been refactored to return a Problem Details body. In the
rewrite, the `429` path stopped setting the `Retry-After` header — the header had been added by the
old middleware, which was deleted.

The customer's nightly batch job uses `requests` with a `urllib3.Retry(total=5,
status_forcelist=[429, 500, 502, 503])` and **no `backoff_factor`**. `urllib3` honours `Retry-After`
when present; with the header absent and `backoff_factor=0`, its wait is zero. Each of the
customer's 8 worker threads retried instantly, 5 times, in a loop that restarted per invoice — a
retry storm amplifying a normal 150-invoice batch into 8,000 requests per second.

The customer's client is badly configured (a bounded retry with no backoff is a defect — 15.14).
But **the server made it possible by omitting one header**, and a public API must assume its clients
are imperfect.

### Fix

*Mitigation (3 minutes):* block the offending API key at the edge, restoring service for everyone
else. Then, at minute 9, ship the header:

```python
response.headers["Retry-After"] = str(exc.retry_after_seconds)
```

Traffic from that key fell from 7,900/s to 12/s within one retry cycle, without the customer
changing anything.

*Permanent fix:*

1. `Retry-After` on **every** `429` and `503`, enforced by the contract test below.
2. `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset` on all responses, so clients can
   pace themselves *before* being refused (02.12).
3. **Edge-level shedding**: a client exceeding its limit by more than 10× has connections rejected at
   the proxy (01.10), so a storm cannot consume application CPU or Redis at all. Cheap refusals are
   the difference between degraded and down (15.17).
4. A note in the client SDK and docs: retries must use exponential backoff with jitter.

### Prevention

- **A contract test that fails the build** if any error response lacks its mandatory headers:

```python
# tests/contract/test_error_headers.py
import pytest
from httpx import AsyncClient

MANDATORY = {429: {"retry-after"}, 503: {"retry-after"}, 401: {"www-authenticate"},
             405: {"allow"}, 201: {"location"}}

@pytest.mark.parametrize("status,headers", sorted(MANDATORY.items()))
@pytest.mark.anyio
async def test_status_carries_required_headers(client: AsyncClient, status, headers, force):
    response = await force(client, status)          # fixture provokes each status
    missing = headers - {h.lower() for h in response.headers}
    assert not missing, f"{status} response missing {missing}"
```

- **An alert on retry amplification**: `rate(http_requests_total{status="429"}) /
  rate(http_requests_total)` above 0.2 for 2 minutes pages. A high 429 ratio is not "the limiter
  working" — it is a client burning your capacity to be told no.
- **Per-key request-rate alerting**, so one customer's runaway job is visible before it is an outage.
- Load-test the *refusal* path, not only the success path (13.14). Nobody had ever measured what a
  `429` costs, and it turned out to cost almost as much as a `201`.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the client retries on `4xx`? | It should not, except `408`/`425`/`429`. If your `4xx` is really transient, it is a `5xx` or `409` — fix the status, not the client. |
| ...you return `500` for a dependency failure? | Clients and dashboards blame your code; circuit breakers trip on the wrong service. Use `502`/`503` + `Retry-After`. |
| ...a `429` has no `Retry-After`? | Retry storm — the scenario above. |
| ...you return `403` instead of `404` cross-tenant? | You have confirmed the resource exists to someone who should not know (16.8). |
| ...you return `200` with an error body? | Your error rate metric, alerts and circuit breakers all go blind. |
| ...headers exceed the server limit? | uvicorn/nginx reject with `431`/`400` **before your app runs** (01.1) — invisible in app logs. Watch for fat JWTs and cookies (08.3). |
| ...you redirect a `POST` with `302`? | Many clients rewrite it to `GET` and drop the body. Use `307`/`308`. |
| ...traffic increases 10×? | Refusals must be cheap. Measure the cost of your `429` path, not just your `200` path. |

## Common Pitfalls

**`200` with `{"success": false}`.** Blinds every generic reliability mechanism you own. *Instead:*
real statuses, with a machine-readable `type` in the body for detail.

**`500` as the catch-all.** A bare `except Exception:` that returns `500` hides validation bugs,
dependency outages and genuine crashes behind one number, so no alert can be specific. *Instead:*
map known conditions explicitly; keep `500` for "we did not anticipate this" — and alert on it hard,
because every `500` is a missing branch in your mapping.

**`401` for permission failures.** Sends clients into a token-refresh loop that can never succeed
(08.4). *Instead:* `401` only when identity is missing or invalid; `403` when identity is fine.

**Leaking exception detail into the body.** `detail: "duplicate key value violates unique constraint
\"ix_invoices_tenant_number\""` tells an attacker your schema (16.2). *Instead:* a stable `type`, a
safe `detail`, and the stack trace in your logs keyed by the request ID (15.2).

**Inventing `X-` headers.** Deprecated by RFC 6648, and they collide across vendors. *Instead:*
unprefixed, namespaced names, and prefer standard ones where they exist (`traceparent` over
`X-Trace-Id`).

**Forgetting `Location` on `201`.** The client cannot find what it just made without guessing your
URL scheme. *Instead:* always set it; it is one line.

**Returning `204` with a body.** Some proxies drop it, some clients error. `204` means *no content*.
*Instead:* `200` if you have something to say.

## How to Test This

- The header contract test shown above — parametrised over `(status, required headers)`.
- A test per domain error asserting the mapped status: `test_voiding_paid_invoice_returns_409`.
- A test that every `LedgerlyError` subclass has a registered handler (walk `__subclasses__()`),
  so a new domain error cannot silently become a `500`.
- Cross-tenant tests asserting `404`, not `403` (13.3, and again in 16.8).

## Interview Questions

1. *Explain.* What does the difference between `4xx` and `5xx` mean to a client's retry logic? — Do
   not retry vs retry with backoff; this is the operational reason the split exists.
2. *Explain.* `401` or `403` for an expired token? For a user without permission? — `401` then `403`;
   getting it backwards causes refresh loops.
3. *Design.* A tenant requests an invoice belonging to another tenant. Which status, and why? —
   `404`, to avoid confirming existence.
4. *Debug this.* Request rate is 50× normal, 94% of responses are `429`, and nothing was deployed. —
   Retry storm; check for a missing `Retry-After` and the client's backoff configuration.
5. *Explain.* When is `409` right rather than `422`? — When the request could succeed against a
   different state.
6. *Design.* Your dependency (a tax-rate provider) is down. What status do you return and which
   headers? — `502`/`503` with `Retry-After`; never `500`; consider degraded mode (15.16).
7. *Debug this.* Some clients report `400` errors your application logs have no record of. — Rejected
   before ASGI: header size, malformed request line, TLS. Look at proxy and uvicorn logs (01.1).

## Key Takeaways

- Choose the status by asking **what the caller's retry logic should do**, not what reads well.
- `4xx` = do not retry (except `408`, `425`, `429`); `5xx` = retry with backoff. Miscategorising
  produces either storms or silent data loss.
- `429` and `503` without `Retry-After` are incomplete responses and actively cause outages.
- `404` beats `403` across tenant boundaries; `401` means "who are you", `403` means "not you".
- Never `200` an error. It disables every generic reliability mechanism you have.
- Decide statuses in **one** mapping module, driven by typed domain errors — not scattered
  `HTTPException`s.
- Refusals must be cheap. Measure the cost of your error path; under attack it is your hot path.
