# 01.1 Request/Response Lifecycle — Socket to ASGI to Handler

> **Prerequisites:** modern-python 11.2 (TCP client and server), 11.5 (HTTP from sockets to `requests`), 12.5 (asyncio)
> **What you'll learn:**
> - Trace a request from the client's `connect()` to the last byte of the response, naming who owns each step
> - Read an ASGI `scope` and explain what uvicorn has already decided before your handler runs
> - Identify which latency your application metrics *cannot* see, and where to measure instead
> - Choose between WSGI and ASGI, and between `uvicorn` and `gunicorn`-managed workers, on evidence
> **Level:** Beginner

## Concept

### Plain-English Explanation

When someone calls your API, a lot happens before your Python function runs — and a lot happens
after it returns. Your function is a small step in the middle of a long pipeline: find the server,
open a connection, agree on encryption, send some bytes, have those bytes parsed into something
structured, wait in a queue for a worker to be free, run the handler, turn the result back into
bytes, and send them home.

Most backend engineers know their handler. Far fewer can say what happens in the ten steps around
it — which is exactly why so many production incidents look like "the app is slow" when the
application's own timers say it is fast. The gap between *what the client experienced* and *what
your handler measured* lives in this pipeline.

### Technical Explanation

The path of a single HTTP request to a Python service:

1. **Name resolution.** The client resolves `api.ledgerly.com` to an IP. DNS answers are cached
   with a TTL; a stale or slow resolver is a real (and commonly missed) source of latency.
2. **TCP handshake.** SYN → SYN-ACK → ACK. One round trip before any application byte moves.
   On a 40 ms RTT link, that is 40 ms you pay before TLS even begins (see 01.7 for how keep-alive
   removes this cost from subsequent requests).
3. **TLS handshake.** One further round trip (TLS 1.3) or two (TLS 1.2). Covered in 01.8.
4. **Request framing.** The client writes a request line, headers, blank line, and optional body.
   This is just bytes on a stream — HTTP/1.1 has no length prefix, so the server must parse
   incrementally to know where the message ends (`Content-Length` or chunked encoding).
5. **Accept.** The kernel completed the handshake and put the connection on the listening socket's
   **accept queue**. It sits there until a server process calls `accept()`. ⚠️ A connection can wait
   in this queue for seconds while your application metrics record nothing at all.
6. **Protocol parsing.** uvicorn (via `httptools` or `h11`) parses the bytes into a method, path,
   headers and a body stream. Malformed requests die here with a `400` your code never sees.
7. **ASGI scope construction.** The parsed request becomes a `scope` dict plus two callables,
   `receive` and `send`. This is the boundary between "the web server" and "your application".
8. **Application.** Starlette (which FastAPI is built on) walks the middleware stack, matches a
   route, converts and validates parameters, and calls your handler.
9. **Response.** Your return value is serialised, a status and headers are chosen, and Starlette
   calls `send()` — once with `http.response.start`, then one or more `http.response.body` messages.
10. **Framing and write.** uvicorn turns those messages back into bytes and writes them to the
    socket. The connection is then either reused (keep-alive) or closed.

**ASGI** (Asynchronous Server Gateway Interface) is the contract at step 7. An ASGI application is
a coroutine with the signature `async def app(scope, receive, send)`. That is the entire interface.
FastAPI, Starlette, middleware, and your handlers are all layers wrapped around this one function
shape.

### Mental Model

> A request is a byte stream that gets progressively parsed into structure, and **every layer that
> parses can reject, delay, or transform it**. Your handler is the innermost layer. Anything you
> measure inside the handler is blind to the eight layers outside it.

## How It Works

```text
CLIENT                          KERNEL              UVICORN                 YOUR APP
  │
  ├─ DNS lookup ────────────────────────────────────────────────────▶ (not measured by you)
  ├─ TCP SYN ──────────────────▶ handshake
  │                              completes
  │                              ┌──────────────┐
  │                              │ accept queue │◀── connection waits here
  │                              └──────┬───────┘    ⚠️ INVISIBLE TO APP METRICS
  ├─ TLS ClientHello ──────────────────▶│
  ├─ POST /v1/invoices ────────────────▶│
  │  Content-Length: 412                └──▶ accept() + h11 parse
  │                                          │
  │                                          ├─▶ scope = {"type": "http",
  │                                          │            "method": "POST",
  │                                          │            "path": "/v1/invoices", ...}
  │                                          │
  │                                          └──▶ await app(scope, receive, send)
  │                                                    │
  │                                                    ├─ middleware stack (outermost first)
  │                                                    ├─ route match  → create_invoice()
  │                                                    ├─ body: await receive()
  │                                                    ├─ pydantic validation
  │                                                    ├─ ── your handler runs here ──
  │                                                    ├─ await send({"type":
  │                                                    │        "http.response.start", ...})
  │                                          ┌─────────┴─ await send({"type":
  │                                          │            "http.response.body", ...})
  │◀─ HTTP/1.1 201 Created ──────────────────┘
  │   (connection kept alive for the next request — 01.7)
```

Two details in that diagram matter more than the rest:

**The accept queue is where hidden latency lives.** Your handler's timer starts at step 8. If one
uvicorn worker is busy for 3 seconds, connections pile up in the kernel queue and every one of them
experiences 3 seconds of latency your `http_request_duration_seconds` histogram will report as
"5 ms". This is the single most common reason for the sentence "the dashboards are green but
customers say it's slow."

**`receive` is a stream, not a value.** The body is not in `scope`. Reading it is `await receive()`,
possibly several times for a large upload. This is why streaming uploads (03.11) are possible at all,
and why middleware that reads the body must be careful to make it readable again.

## Code Example

The clearest way to see the boundary is to write an ASGI application with no framework at all. This
is exactly what FastAPI is, minus twenty thousand lines.

```python
# ledgerly/raw_asgi.py — the entire ASGI contract, no framework.
import json
from typing import Any, Awaitable, Callable

Scope = dict[str, Any]
Receive = Callable[[], Awaitable[dict[str, Any]]]
Send = Callable[[dict[str, Any]], Awaitable[None]]


async def app(scope: Scope, receive: Receive, send: Send) -> None:
    assert scope["type"] == "http"          # also: "lifespan" (03.9), "websocket" (03.12)

    body = b""
    while True:                              # the body arrives in chunks
        message = await receive()
        body += message.get("body", b"")
        if not message.get("more_body", False):
            break

    payload = {"received_bytes": len(body), "path": scope["path"]}
    data = json.dumps(payload).encode()

    await send({
        "type": "http.response.start",
        "status": 201,
        "headers": [(b"content-type", b"application/json"),
                    (b"content-length", str(len(data)).encode())],
    })
    await send({"type": "http.response.body", "body": data})
```

Run it with `uvicorn ledgerly.raw_asgi:app --port 8000` and post an invoice draft:

```bash
curl -i -X POST localhost:8000/v1/invoices -d '{"customer_id":"cus_8f21","amount_cents":49900}'
```

```text
HTTP/1.1 201 Created
date: Tue, 24 Aug 2026 09:41:02 GMT
server: uvicorn
content-type: application/json
content-length: 51

{"received_bytes": 47, "path": "/v1/invoices"}
```

Note what you had to do by hand: read the body in a loop, encode it, compute `content-length`, pick a
status, and emit two separate `send` messages. Note also what uvicorn did for you: parsed the
request line and headers, built `scope`, and framed the response. Everything FastAPI adds — routing,
validation, dependency injection, OpenAPI — is **above** this line.

Now the version that matters in production: middleware that measures the request at the ASGI layer
rather than inside a handler, so it captures middleware and validation time too.

```python
# ledgerly/middleware/timing.py
import time
from typing import Any, Awaitable, Callable

class ServerTimingMiddleware:
    """Pure-ASGI timing. Sits outside routing, so it also measures validation and
    other middleware — unlike a @app.middleware('http') function, which does not."""

    def __init__(self, app: Callable[..., Awaitable[None]]) -> None:
        self.app = app

    async def __call__(self, scope: dict[str, Any], receive, send) -> None:
        if scope["type"] != "http":
            await self.app(scope, receive, send)
            return

        started = time.perf_counter()

        async def send_with_timing(message: dict[str, Any]) -> None:
            if message["type"] == "http.response.start":
                elapsed_ms = (time.perf_counter() - started) * 1000
                # bytes, not str — ASGI headers are raw
                message.setdefault("headers", []).append(
                    (b"server-timing", f"app;dur={elapsed_ms:.1f}".encode())
                )
            await send(message)

        await self.app(scope, receive, send_with_timing)
```

Wired into the invoicing API:

```python
# ledgerly/main.py
from fastapi import FastAPI
from ledgerly.middleware.timing import ServerTimingMiddleware

app = FastAPI(title="Ledgerly Invoicing API")
app.add_middleware(ServerTimingMiddleware)
```

The response now carries `server-timing: app;dur=6.4`. Compare that number against what the client
measures. **The difference is your queueing time**, and finding it is the whole point of the
production scenario below.

## Design Patterns / Tradeoffs

### WSGI vs ASGI

**WSGI** (`def app(environ, start_response)`) is synchronous: one request occupies one worker
thread or process for its entire duration, including time spent waiting on the database.

- *Advantages:* simple mental model, mature ecosystem (Django ≤2, Flask), no async foot-guns, a
  blocking library cannot break anything.
- *Disadvantages:* concurrency is bounded by threads/processes; 200 concurrent slow requests need
  200 workers, each with its own memory.
- *Failure mode:* worker starvation under slow downstreams — all workers blocked, new requests queue.
- *Use when:* the codebase is synchronous, concurrency is modest, and the team has no async experience.
- *Do NOT use when:* you have high-concurrency I/O-bound workloads, WebSockets, or SSE.

**ASGI** (`async def app(scope, receive, send)`) is asynchronous: one process handles thousands of
concurrent connections, provided nothing blocks the event loop.

- *Advantages:* high concurrency per process; native WebSocket and SSE support (03.12, 12.4);
  streaming request and response bodies.
- *Disadvantages:* a single blocking call stalls *every* concurrent request in that process (04.2);
  requires async-native libraries throughout.
- *Failure mode:* one synchronous `requests.get()` in a handler freezes the whole worker.
- *Use when:* I/O-bound work, many concurrent connections, real-time protocols.
- *Do NOT use when:* your work is CPU-bound (04.7) — async buys you nothing and costs you clarity.

### Process model: bare uvicorn vs gunicorn + uvicorn workers vs uvicorn `--workers`

| | Bare `uvicorn` (1 process) | `uvicorn --workers N` | `gunicorn -k uvicorn.workers.UvicornWorker` |
|---|---|---|---|
| How it works | One event loop, one core | uvicorn spawns and supervises N children | gunicorn is the master; each child runs a uvicorn event loop |
| Advantages | Simplest; ideal in a container where the orchestrator scales replicas | Uses all cores from one command | Mature process supervision, graceful timeouts, `--max-requests` worker recycling |
| Disadvantages | Uses one core; a stall halts everything | Fewer supervision knobs | Extra dependency and layer; signal handling subtleties |
| Failure mode | One slow endpoint queues all traffic | A leaking worker keeps leaking | Misconfigured `--timeout` SIGKILLs workers mid-request |
| Use when | Kubernetes/Swarm scales replicas for you (14.9) | A VM where you want all cores | You need worker recycling for a slow memory leak (17.7) |
| Avoid when | You have spare cores and no orchestrator | You need `max-requests` recycling | The orchestrator already supervises processes |

**Recommendation for this curriculum:** one uvicorn process per container, scaled by replicas
(14.9). It makes each container's CPU and memory attributable, which is what 15.3 metrics and
17.9 scaling depend on. Switch to gunicorn-managed workers when you need `--max-requests`
recycling for a leak you have not yet fixed.

### Where to do the work: proxy vs application

TLS termination, gzip, static files, request-size limits, and slow-client buffering can be done in
your app or in a reverse proxy (nginx, Traefik, Envoy — see 01.10).

- *In the proxy:* faster (C, not Python), protects the app from slow clients, keeps the event loop
  free. Costs an extra hop and another config surface.
- *In the app:* one place to reason about, works identically in local development. Costs Python CPU
  on every request and exposes your event loop to slowloris-style clients (16.9).
- *Rule of thumb:* anything that is pure byte manipulation and identical for all tenants belongs in
  the proxy. Anything that needs to know *who is calling* belongs in the app.

## Production Scenario

**Ledgerly, Tuesday 09:38.** The finance-team dashboard at a large customer runs a nightly-batch
catch-up every morning. Support escalates: "invoice creation is taking 4–8 seconds, it was instant
last week." The engineer on call opens Grafana and sees a flat green line.

### Symptoms

- Customer-reported latency on `POST /v1/invoices`: 4–8 s, occasionally a client-side timeout.
- Application histogram `http_server_request_duration_seconds{route="/v1/invoices"}` p99: **11 ms**.
  Unchanged for a week.
- The load balancer's own metric `haproxy_http_total_time_average_seconds` for the same backend:
  **5.2 s**. The two numbers disagree by three orders of magnitude.
- No errors. CPU on the container is 96% of a single core; the host has 8 cores mostly idle.
- `docker compose logs api` shows normal `201` access lines, all with tiny durations.

### Diagnosis

Following the ladder — **Alert → Metrics → Logs → Trace → Dependency health → Root cause**:

1. **Alert** fired on the *proxy's* latency SLO, not the app's. That mismatch is the first clue: the
   two measurement points bracket a gap.
2. **Metrics.** Handler duration is flat; proxy duration is huge. Therefore the time is spent
   *outside the handler* — before step 8 in the lifecycle above. Two candidates remain: the accept
   queue, or the event loop being blocked.
3. **Logs.** Access logs show a new endpoint in the mix: `GET /v1/invoices/{id}/pdf`, added in
   Friday's release, with durations of 900–1400 ms. Low volume — about 3 requests per second.
4. **Trace.** A trace of a slow `POST /v1/invoices` shows a single span of 11 ms with a
   4.9 s gap between the proxy's client span and the server span starting. **Nothing is slow; the
   request is waiting to begin.**
5. **Dependency health.** Postgres p99 is 3 ms, Redis 0.4 ms. Neither is implicated.
6. **The decisive check.** On the container:

```bash
$ ss -lnt 'sport = :8000'
State   Recv-Q  Send-Q   Local Address:Port
LISTEN  128     128            0.0.0.0:8000     # Recv-Q 128 = accept queue FULL
```

  and an event-loop lag probe (a task that sleeps 250 ms and measures its overshoot):

```text
event_loop_lag_seconds  1.83
```

### Root Cause

The new PDF endpoint calls a synchronous rendering library inside an `async def` handler. Every
render occupies the single event loop for ~1.2 s of pure CPU. At 3 requests per second, the loop is
blocked roughly 100% of the time. Invoice creation is genuinely fast — it just cannot get scheduled.
Connections accumulate in the kernel accept queue, which is invisible to any timer that starts when
the handler starts.

Two independent defects: a blocking call on the event loop (04.7 will treat this properly), and
**instrumentation that could not see the problem** — which is the lifecycle lesson.

### Fix

*Mitigation (deployed in 6 minutes):* scale the API from 1 to 6 replicas. This does not fix the
blocking render, but spreads it so that 5 of 6 loops remain schedulable. p99 drops to 700 ms.

*Permanent fix, part 1 — get the CPU work off the loop:*

```python
# ledgerly/routers/invoices.py
import anyio
from fastapi import APIRouter
from ledgerly.pdf import render_invoice_pdf   # synchronous, CPU-bound, third-party

router = APIRouter(prefix="/v1/invoices", tags=["invoices"])

@router.get("/{invoice_id}/pdf")
async def get_invoice_pdf(invoice_id: str) -> Response:
    invoice = await repo.get(invoice_id)
    # Runs in the threadpool; the event loop stays free to accept and schedule.
    pdf = await anyio.to_thread.run_sync(render_invoice_pdf, invoice)
    return Response(pdf, media_type="application/pdf")
```

⚠️ The threadpool is a bounded resource (40 threads by default) and this is CPU work fighting the
GIL — it is a *stopgap*, not the answer. The real answer is a worker (11.1) or a separate rendering
service; 03.10 draws that line precisely.

*Permanent fix, part 2 — measure where the truth is:* export an event-loop lag gauge and alert on
it, and record latency at the proxy as the SLI (15.10), not the app histogram.

```python
# ledgerly/observability/loop_lag.py
import asyncio, time
from prometheus_client import Gauge

LOOP_LAG = Gauge("event_loop_lag_seconds", "Scheduling delay of the asyncio event loop")

async def monitor_loop_lag(interval: float = 0.25) -> None:
    while True:
        start = time.perf_counter()
        await asyncio.sleep(interval)
        LOOP_LAG.set((time.perf_counter() - start) - interval)   # overshoot == lag
```

Started from the lifespan hook (03.9), this gauge would have been at 1.8 s from the moment the PDF
endpoint shipped.

### Prevention

- **Two-point latency measurement is mandatory.** The SLI is measured at the edge (proxy/LB); the
  app histogram is a *debugging* signal, never the SLO. Alert on the delta between them.
- `event_loop_lag_seconds > 0.1` is a paging alert on every Python async service.
- A code-review rule: any new dependency called from an `async def` handler must be shown to be
  non-blocking, or wrapped. 04.2 gives the detection technique (`asyncio` debug mode, `blockbuster`).
- Load-test new endpoints *alongside* existing traffic, not in isolation (13.13). Tested alone, the
  PDF endpoint looked fine.

## Failure-First Checklist

| What if... | What happens in the lifecycle |
|---|---|
| ...the handler is slow? | Connections queue in the kernel accept queue; app metrics stay green. Measure at the edge. |
| ...the client is slow to send the body? | `await receive()` suspends. With a reverse proxy buffering (01.10), the app never notices; without one, a slowloris client holds a connection open (16.9). |
| ...the client disconnects mid-request? | uvicorn sends `http.disconnect` on `receive`. Your handler is **not** cancelled unless you check for it (04.8). Work continues, wasting capacity. |
| ...the response body is huge? | Multiple `http.response.body` messages; memory stays bounded only if you stream (03.11). Returning a 500 MB list materialises 500 MB. |
| ...the request is malformed? | Rejected by the protocol parser with `400` before ASGI. Your logs and metrics see nothing — check the proxy/uvicorn logs. |
| ...traffic increases 10×? | Accept queue depth grows first, then `listen` backlog overflows and the kernel drops SYNs — clients see connection timeouts, not 503s. |
| ...the process is killed mid-request? | The socket closes; the client sees a connection reset, not a status code. Graceful shutdown (04.9) exists to avoid this. |

## Common Pitfalls

**Measuring latency only inside the handler.** The defect at the centre of the scenario above. Your
histogram starts after routing and ends before the body is written; it excludes queueing, TLS,
request parsing, and the client's download. *Instead:* record the SLI at the proxy and treat the app
number as a component.

**Assuming `scope` contains the body.** It contains method, path, headers, query string, client
address and server address — not the body. Middleware that "just reads the JSON" to log it must
re-inject what it consumed, or the handler receives an empty body. *Instead:* log identifiers from
headers and path; if you must inspect bodies, do it in the proxy or with an explicit, size-bounded
buffering middleware.

**Writing `@app.middleware("http")` and thinking it wraps everything.** Starlette's HTTP middleware
decorator runs *inside* the outer ASGI stack and misses some error paths; a `BaseHTTPMiddleware`
also breaks response streaming in subtle ways. *Instead:* write pure-ASGI middleware (as above) for
anything cross-cutting — timing, request IDs (15.2), tenancy resolution.

**Treating uvicorn's access log as your request log.** It has no tenant, no user, no correlation ID,
and no structured fields. *Instead:* disable it in production (`--no-access-log`) and emit one
structured log line per request from your own middleware (15.1).

**One uvicorn process on an 8-core box.** You are using 12.5% of what you pay for, and one blocking
call halts the entire service. *Instead:* replicas or workers, sized in 17.7.

## Interview Questions

1. *Explain.* Walk me through everything that happens between `curl https://api.example.com/v1/invoices`
   and the first response byte. — Expect DNS, TCP, TLS, framing, accept, parse, ASGI, routing, handler.
2. *Explain.* What is ASGI and how does it differ from WSGI? — The three-argument coroutine contract;
   `receive`/`send` as streams; concurrency model implications.
3. *Debug this.* Your app's p99 histogram says 8 ms; customers report 4 s. Where is the time? — Between
   accept and handler start: accept queue and/or blocked event loop. Name the two checks (`ss -lnt`,
   loop-lag gauge).
4. *Design.* Where would you terminate TLS, enforce a 10 MB body limit, and gzip responses — proxy or
   app? Justify each. — Byte-level and tenant-agnostic work goes to the proxy.
5. *Explain.* Why can middleware that reads the request body break your handler? — `receive` is a
   one-shot stream unless replayed.
6. *Debug this.* Clients report connection timeouts, but there are zero 5xx responses in your logs.
   — Requests never reached the app: listen backlog overflow, LB health-check failure, or DNS.
7. *Design.* You must add a request ID to every log line and response header. At which layer, and why?
   — Pure-ASGI middleware, outermost, using `contextvars` (04.4, 15.2).

## Key Takeaways

- Your handler is step 8 of 10. **Latency you cannot see is latency in steps 1–7**, and the accept
  queue is where it usually hides.
- ASGI is one coroutine signature: `async def app(scope, receive, send)`. Everything FastAPI does
  sits above that line; everything uvicorn does sits below it.
- The body is a stream reached through `receive`, not a value in `scope`. This is what makes
  streaming possible and what makes body-reading middleware dangerous.
- Measure latency at **two** points — the edge and the handler — and alert on the gap. One point is
  not instrumentation, it is a guess.
- `event_loop_lag_seconds` is a first-class production metric for any async Python service.
- Choose the process model deliberately: one loop per container plus replicas by default; gunicorn
  workers when you need recycling; never one process on a many-core host by accident.
