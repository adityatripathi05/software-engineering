# 01.6 Stateless vs Stateful Services

> **Prerequisites:** 01.1 (lifecycle), 01.5 (sessions — the most common piece of state)
> **What you'll learn:**
> - Say precisely what "stateless" means (it does not mean "has no data")
> - Identify process-local state in an existing service, including the kinds that hide
> - Predict exactly which bugs appear the day a service is scaled from one replica to many
> - Choose deliberately between externalising state, sticky sessions, and staying single-instance
> **Level:** Beginner

---

## Concept

### Plain-English Explanation

"Stateless" is one of the most over-used and least-defined words in backend engineering. It does not
mean your service has no data — your service has a database full of data. It means something much
narrower and much more useful:

> **Any replica can serve any request, and it does not matter which one.**

If request 1 goes to replica A and request 2 goes to replica D and the result is identical, the
service is stateless. If replica D gives a different answer — or an error — because replica A
remembered something in its own memory, the service is stateful, whatever the README says.

This matters because everything you will do in modules 14 and 17 — running multiple replicas,
rolling deploys, autoscaling, zero-downtime releases — assumes any instance is interchangeable with
any other. The day that assumption breaks, it breaks quietly and in production.

### Technical Explanation

**State is any information that must survive between requests.** The question is only *where it
lives*:

| Where it lives | Survives a restart? | Shared across replicas? | Verdict |
|---|---|---|---|
| PostgreSQL, Redis, S3 | ✅ | ✅ | Externalised — the service stays stateless |
| A module-level `dict` or `set` | ❌ | ❌ | **Process-local state** — the problem |
| `functools.lru_cache` on a function | ❌ | ❌ | Process-local; fine for pure functions, a bug for anything else |
| An in-memory rate-limit counter | ❌ | ❌ | Process-local; limits multiply by replica count |
| A WebSocket connection object | ❌ | ❌ | Genuinely local — cannot be externalised (12.7) |
| Local disk (`/tmp`, uploaded files) | Sometimes | ❌ | Process-local unless on shared storage (09.1) |
| An `asyncio.Lock` | ❌ | ❌ | Coordinates *within* one loop only (04.5); not a distributed lock (10.12) |

A **stateless service** keeps nothing in the top group's absence — every piece of cross-request
information is in an external store, and the process's memory holds only caches that are *correct if
empty and correct if stale*.

**Why it is the enabling property:**

- **Horizontal scaling** (17.9) — add replicas without changing behaviour.
- **Rolling deploys** (14.15) — kill a replica mid-flight; the next request goes elsewhere and works.
- **Failure isolation** (15.17) — one unhealthy instance is removed from the load balancer with no
  user-visible loss.
- **Autoscaling** — instances appear and vanish without coordination.

**The two honest exceptions.** Some state genuinely cannot be externalised: a WebSocket connection is
a live TCP socket owned by one process (12.7 solves fan-out with Redis Pub/Sub, not by moving the
socket), and an in-process cache of immutable reference data is legitimate — *provided* it is a pure
performance optimisation that a cold replica reproduces correctly.

That last clause is the test that separates a safe local cache from a latent outage:

> **Would this service still be correct if every replica's memory were wiped between every
> request?** If yes, the state is a cache. If no, it is state, and it is in the wrong place.

### Mental Model

> Treat each replica as **disposable and amnesiac**. It can be killed at any moment and replaced by
> a fresh one that remembers nothing. Any correctness that depends on a replica remembering
> something is a bug that will surface the first time you scale, deploy, or lose a container — and
> it will surface as wrong data, not as an error.

## How It Works

The same request pattern, under one replica and under six:

```text
ONE REPLICA (the state is invisible)          SIX REPLICAS (the state is a bug)

 client ──▶ [ replica A ]                      client ──▶ LB ──┬─▶ [A]  seen = {k1}
              seen = {k1, k2, k3}                              ├─▶ [B]  seen = {k2}
              ▲                                                ├─▶ [C]  seen = {}
              └─ every request lands here,                     ├─▶ [D]  seen = {k1}   ← k1 AGAIN
                 so the in-memory set is                       ├─▶ [E]  seen = {}
                 always complete                               └─▶ [F]  seen = {k3}

 ✅ dedupe works                                ❌ each replica knows ~1/6 of the truth;
                                                   a duplicate is caught only if the retry
                                                   happens to land on the same replica
                                                   ≈ 1 in 6
```

The failure is **probabilistic**, which is what makes it so unpleasant: it does not appear in
staging (one replica), it passes every test (one process), and in production it corrupts a fraction
of requests. Nothing errors. The service reports itself healthy throughout.

Restarts produce the same class of bug on a different axis: with `seen` in memory, a rolling deploy
(14.15) empties every set, and a client retrying across the deploy is deduplicated against nothing.

## Code Example

Two versions of Ledgerly's idempotency guard. The first is what shipped; the second is what should
have.

```python
# ❌ ledgerly/services/idempotency.py — process-local. Correct on one replica, wrong on many.
_seen: dict[str, str] = {}          # module-level mutable state: the tell

async def create_invoice(tenant: UUID, body: InvoiceCreate, key: str) -> Invoice:
    if key in _seen:
        return await repo.get(tenant, _seen[key])     # "already created" fast path
    invoice = await repo.insert(tenant, body)
    _seen[key] = invoice.id
    return invoice
```

Everything about that code looks reasonable in review. It has no obvious bug, it is fast, and it
works perfectly in every test. It is also unbounded (a memory leak — 17.7) and wrong the moment a
second replica exists.

```python
# ✅ ledgerly/services/idempotency.py — externalised, and correct under concurrency.
from datetime import timedelta
from redis.asyncio import Redis

IDEMPOTENCY_TTL = timedelta(hours=24)

async def create_invoice(
    tenant: UUID, body: InvoiceCreate, key: str, redis: Redis, repo: InvoiceRepository
) -> Invoice:
    cache_key = f"idem:{tenant}:{key}"

    if (existing_id := await redis.get(cache_key)) is not None:
        return await repo.get(tenant, existing_id.decode())

    # SET NX: atomic claim. Only one replica wins, even if six arrive in the same
    # millisecond — this is what an in-memory `if key in _seen` cannot do (04.5).
    claimed = await redis.set(cache_key, "in-flight", nx=True, ex=IDEMPOTENCY_TTL)
    if not claimed:
        raise IdempotentRequestInFlight(key)          # → 409, client retries (01.3)

    invoice = await repo.insert(tenant, body)
    await redis.set(cache_key, invoice.id, ex=IDEMPOTENCY_TTL)
    return invoice
```

⚠️ Redis is now on the critical path, so it is a new failure mode, not a free win — 10.6 covers
timeouts and what to do when it is down. And Redis alone is not sufficient: the durable guarantee
comes from a **unique constraint in PostgreSQL** on `(tenant_id, idempotency_key)` (05.3), with
Redis as the fast path. 02.8 builds the complete version. The point here is narrower: *the state
left the process.*

**Finding process-local state in an existing service.** The tell is a mutable module-level object.
A cheap check that runs in CI:

```python
# tests/architecture/test_no_process_local_state.py
"""Fails the build on module-level mutable state in the service layer.
Not a substitute for review, but it catches the accidental `_seen = {}`."""
import ast, pathlib, pytest

ALLOWED = {"ledgerly/constants.py", "ledgerly/http/error_mapping.py"}   # frozen data only
MUTABLE = (ast.Dict, ast.List, ast.Set)

@pytest.mark.parametrize("path", sorted(pathlib.Path("ledgerly").rglob("*.py")))
def test_no_module_level_mutable_state(path: pathlib.Path) -> None:
    if str(path).replace("\\", "/") in ALLOWED:
        pytest.skip("explicitly allow-listed as immutable configuration")
    tree = ast.parse(path.read_text(encoding="utf-8"))
    offenders = [
        node.targets[0].id
        for node in tree.body                                   # module level only
        if isinstance(node, ast.Assign)
        and isinstance(node.targets[0], ast.Name)
        and isinstance(node.value, MUTABLE)
        and node.value.keys if isinstance(node.value, ast.Dict) else True
    ]
    assert not offenders, f"{path}: module-level mutable state {offenders}"
```

## Design Patterns / Tradeoffs

### Where to put the state

**A. Externalise everything (stateless service)**

- *How it works:* sessions in Redis (10.14), files in object storage (09.4), counters in Redis,
  everything durable in PostgreSQL.
- *Advantages:* replicas are interchangeable; scaling, rolling deploys and autoscaling all just
  work; a lost container costs nothing.
- *Disadvantages:* a network round trip on paths that used to be a dict lookup; a new availability
  dependency; you must decide fail-open vs fail-closed for each store.
- *Failure mode:* the external store becomes a single point of failure — which is why 10.6 and 15.16
  exist.
- *Use when:* almost always. This is the default for HTTP services.
- *Do NOT use when:* the state genuinely cannot leave the process (a live socket).

**B. Sticky sessions (session affinity at the load balancer)**

- *How it works:* the LB hashes a cookie or client IP so a given client always reaches the same
  replica.
- *Advantages:* keeps in-memory state working with no code change; occasionally the pragmatic answer
  for a legacy app; reduces cache misses for per-user caches.
- *Disadvantages:* a replica restart loses those users' state (and deploys restart every replica);
  load distributes unevenly; autoscaling is much less effective; it hides the real problem so it
  compounds.
- *Failure mode:* deploy → every sticky user loses state simultaneously. The worst possible timing.
- *Use when:* a genuine transitional measure with an owner and a deadline, or for WebSocket
  connection affinity where it reduces (but does not remove) the need for cross-replica fan-out.
- *Do NOT use when:* it is being chosen instead of externalising state. That is a deferral, not a fix.

**C. Stay single-instance**

- *Advantages:* everything is simple and correct; no distributed anything.
- *Disadvantages:* no redundancy — a restart is downtime; vertical scaling only; no zero-downtime
  deploys.
- *Use when:* internal tools, low-traffic admin services, early prototypes. This is a legitimate
  choice, made explicitly.
- *Do NOT use when:* the service has an availability commitment.

**Recommendation:** A, always, for anything customer-facing. Choose C consciously for internal tools
and write down the availability consequence. Treat B as debt with a due date.

### What may legitimately stay in the process

| Legitimate | Why it is safe |
|---|---|
| A compiled regex, a parsed config, a loaded ML model | Immutable; identical on every replica |
| An `lru_cache` on a **pure** function | Cold replicas recompute the same answer |
| A connection pool (05.9, 06.8) | Per-process by design; sizing must account for replica count |
| A short-TTL local read cache for reference data | Correct if empty, correct if stale; **only** if staleness is acceptable |
| An open WebSocket (12.7) | Cannot be externalised; fan-out via Redis instead |

The connection pool row has a trap worth stating now: pool size is **per replica**. Six replicas
with `pool_size=20` open 120 connections to PostgreSQL, and `max_connections` defaults to 100. That
is 05.9's incident, and it is a direct consequence of forgetting that processes multiply.

## Production Scenario

**Ledgerly, Friday 10:15.** Three customers report duplicate invoices — the same invoice number
issued twice, both emailed. For a billing product this is a data-integrity incident with an
accounting consequence: their ledgers no longer reconcile.

### Symptoms

- 41 duplicate invoice pairs in 90 minutes, across 7 tenants, out of ~6,000 creations.
- Every duplicate pair shares an `Idempotency-Key` — the guard is being bypassed, not skipped.
- `http_requests_total{route="/v1/invoices",status="201"}` is up ~4% against a normal request rate.
- **Zero errors.** No `5xx`, no exceptions, no alerts. Latency normal.
- `duplicate_invoice_total` did not exist as a metric, so the signal came from support.

### Diagnosis

1. **Alert.** None. The service was healthy by every technical measure while producing wrong data —
   the recurring lesson of this module.
2. **Metrics.** A `201` rate 4% above the request-per-tenant baseline suggests creations that should
   have been deduplicated. The anchor for "when did this start" comes next.
3. **Logs.** Grouping creation logs by `idempotency_key` finds the pairs immediately, and the log
   line includes the hostname (added for exactly this reason):

```json
{"ts":"…T10:07:41Z","route":"/v1/invoices","status":201,"idempotency_key":"po-88213",
 "invoice_id":"inv_9f2c41","tenant":"t_44f1","hostname":"ledgerly-api-7c9d4-x2k1"}
{"ts":"…T10:07:43Z","route":"/v1/invoices","status":201,"idempotency_key":"po-88213",
 "invoice_id":"inv_9f2c58","tenant":"t_44f1","hostname":"ledgerly-api-7c9d4-b8m3"}
```

   **Same key, two invoices, two different hostnames, two seconds apart.** That single pair of log
   lines is the entire root cause.
4. **Trace.** The two requests are unrelated traces — the client's HTTP library retried after a
   1.5 s timeout, and the retry was load-balanced to a different replica.
5. **Dependency health.** PostgreSQL and Redis both healthy. Redis is not even involved — nothing in
   the creation path talks to it.
6. **Correlation with the change.** The duplicates begin at 08:40 Thursday, which matches an
   autoscaling policy change that raised the minimum replica count from 1 to 6 to handle month-end
   load. That deploy touched no application code at all.

### Root Cause

The idempotency guard was the `_seen` dict shown above: a module-level Python dictionary, local to
each process. With one replica it was complete and correct, and it had been correct for fourteen
months. With six replicas each holds roughly one sixth of the keys, so a client retry lands on a
replica that has never seen the key about five times out of six — and creates a second invoice.

The database had no unique constraint on `(tenant_id, idempotency_key)`, so nothing downstream
caught it either.

**A pure infrastructure change turned working code into a data-corruption bug**, because the code
had an unstated single-replica assumption.

### Fix

*Mitigation (12 minutes):* scale back to one replica. Duplicates stop instantly. This is the correct
call — the deduplication guarantee matters more than the throughput — and it buys time to fix
properly rather than under pressure.

*Permanent fix, in dependency order:*

1. **A unique constraint** — the durable guarantee, independent of any cache:

```sql
-- alembic/versions/2026_08_24_idempotency_uniqueness.py
ALTER TABLE invoices ADD COLUMN idempotency_key text;
CREATE UNIQUE INDEX CONCURRENTLY ix_invoices_tenant_idempotency
    ON invoices (tenant_id, idempotency_key) WHERE idempotency_key IS NOT NULL;
```

   `CONCURRENTLY` because this is a live table (06.13). A partial index because historical rows have
   no key. Now a duplicate insert raises `UniqueViolation` no matter how many replicas exist, and the
   service converts it into "return the existing invoice."

2. **Redis as the fast path** (the ✅ version above), so the common case does not reach a constraint
   violation.
3. **Scale back to six replicas**, verified with a load test that fires deliberate retries (13.14).
4. **Backfill:** the 41 duplicates were voided and the affected tenants' ledgers reconciled by hand.

### Prevention

- **A CI test that runs the API with two replicas** behind a load balancer and asserts that a
  repeated `Idempotency-Key` yields one invoice. Single-replica tests cannot express this class of
  bug at all, which is why it survived fourteen months of a green test suite (13.14).
- **The architecture test** shown earlier, failing the build on module-level mutable state.
- **`duplicate_invoice_total` as a business-invariant metric**, alerting above zero. Technical
  metrics were perfect throughout; only a business invariant could have caught it.
- **A review rule for infrastructure changes**: any change to replica count, autoscaling policy or
  process model requires an application-owner reviewer. This deploy was reviewed only by the platform
  team, who had no reason to know about `_seen`.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a replica restarts mid-request? | The client retries and lands elsewhere. Anything the old process remembered is gone — it must not have been needed. |
| ...you scale from 1 to N? | Every in-memory counter, cache and lock becomes 1/N correct. Rate limits multiply by N; dedupe fails ~(N−1)/N of the time. |
| ...a rolling deploy runs? | Every replica's memory is cleared, staggered over minutes. Sticky sessions make this *worse*, not better. |
| ...the external store is down? | You have traded process-local correctness for a dependency. Decide fail-open (available, unguarded) or fail-closed (unavailable, safe) per feature — 15.16. |
| ...one instance becomes unhealthy? | With stateless replicas, remove it from the LB and lose nothing. With process-local state, you lose whatever it held. |
| ...traffic increases 10×? | Stateless: add replicas, and re-check per-replica pool sizes against `max_connections` (05.9). Stateful: you cannot add replicas safely at all. |
| ...two replicas act on the same row concurrently? | `asyncio.Lock` does not help across processes (04.5). You need a DB constraint, `SELECT FOR UPDATE` (05.14), or a distributed lock (10.12). |

## Common Pitfalls

**A module-level `dict` used as a cache or guard.** Invisible in review, correct on one replica,
wrong on many. *Instead:* Redis with a TTL, or a database constraint for anything that must be
guaranteed.

**In-memory rate limiting.** With N replicas the effective limit is N× what you configured, and
unevenly distributed. *Instead:* a shared counter (10.13).

**`asyncio.Lock` for cross-request mutual exclusion.** It coordinates coroutines in one event loop
only (04.5). *Instead:* a database lock or an advisory lock; a distributed lock if you truly must
(10.12, including why it is harder than it looks).

**Writing uploads to local disk.** They vanish on restart and are invisible to other replicas.
*Instead:* object storage (09.4).

**Reaching for sticky sessions to make the bug go away.** It hides the failure until the next deploy,
when it returns for every user at once. *Instead:* externalise, and use affinity only where the state
is genuinely unmovable.

**Assuming the connection pool is global.** It is per process; multiply by replicas before setting
`pool_size` (05.9, 06.8).

**Testing only with one replica.** The entire class of bug in this notebook is invisible under a
single process. *Instead:* at least one CI job with two replicas behind a load balancer.

## How to Test This

- A two-replica integration test in CI (compose with `--scale api=2`) that asserts idempotency,
  rate limits and session behaviour hold. This is the test that matters.
- A restart test: send a request, restart the container, send a dependent request, assert success.
- The architecture test for module-level mutable state.
- Business-invariant assertions in load tests (13.13): "N clients each retrying produce exactly N
  invoices."

## Interview Questions

1. *Explain.* What does "stateless" mean precisely, and why is it a prerequisite for horizontal
   scaling? — Any replica can serve any request; interchangeability enables scaling and rolling deploys.
2. *Explain.* Which of these is safe in process memory: an LRU cache of a pure function, a rate-limit
   counter, an open WebSocket? Why? — Safe / unsafe / unavoidable.
3. *Debug this.* Duplicate records appear after an autoscale from 1 to 6 replicas, with no code change
   and no errors. — Process-local dedupe; look for module-level mutable state; check hostnames in logs.
4. *Design.* You must add rate limiting to a service running 8 replicas. Where does the counter live
   and what happens when that store is unavailable? — Shared store; state the fail-open/fail-closed choice.
5. *Explain.* Why are sticky sessions a poor substitute for externalising state? — Deploys and
   restarts lose state for all affected users simultaneously; uneven load; hides the defect.
6. *Design.* Your service holds 50,000 WebSocket connections across 10 replicas. How do you deliver a
   message to a specific user? — Fan-out via Redis Pub/Sub; the socket cannot move (12.7, 12.8).
7. *Explain.* You set `pool_size=20`. You now run 6 replicas. What have you actually configured? —
   120 connections; check `max_connections` (05.9).

## Key Takeaways

- Stateless means **any replica can serve any request**, not "has no data". The test: would the
  service still be correct if every process's memory were wiped between requests?
- Module-level mutable state is the canonical bug. It is correct on one replica and probabilistically
  wrong on many — no errors, just wrong data.
- Scaling from 1 to N replicas silently divides in-memory guards by N and multiplies in-memory limits
  by N. An infrastructure change can break application correctness.
- Externalise state to PostgreSQL or Redis, but back guarantees with a **database constraint** —
  a cache is an optimisation, never the guarantee.
- Sticky sessions defer the problem to your next deploy. Single-instance is a legitimate choice when
  made explicitly, with the availability cost written down.
- Test with more than one replica, and alert on **business invariants**, not only on errors.
