## Concept

### Plain-English Explanation

Opening a connection is expensive; using one is cheap. A new HTTPS connection costs two or three
network round trips before a single byte of your request moves — on a 40 ms link, that is 80–120 ms
of pure waiting, every time. Reusing an existing connection costs zero.

So every layer in the stack keeps connections open and reuses them: browsers, your reverse proxy,
your HTTP client library, your database driver. This works beautifully and invisibly right up until
two layers disagree about *when it is safe to close one*. Then you get a small, steady trickle of
errors that appear in no application log, correlate with nothing, and survive every attempt to
reproduce them.

That disagreement is the most common connection-related outage in production, and it is caused by
two configuration numbers being in the wrong order.

### Technical Explanation

**What a connection costs**, on a 40 ms RTT link:

```text
Cold connection, HTTP/1.1 over TLS 1.3        Reused connection
─────────────────────────────────────         ─────────────────
DNS (often cached)              0–40 ms       —
TCP handshake (SYN/SYN-ACK/ACK)    40 ms      —
TLS 1.3 handshake (1-RTT)          40 ms      —
Request + response                 40 ms      Request + response   40 ms
─────────────────────────────────────         ─────────────────
TOTAL                          120–160 ms     TOTAL                40 ms
```

TLS 1.2 costs a further round trip (2-RTT); TLS 1.3 session resumption can reach 0-RTT for repeat
connections. The headline: **a cold connection is 3–4× the latency of a warm one**, and no amount of
application optimisation recovers it.

**Keep-alive.** HTTP/1.1 defaults to persistent connections: after a response, the connection stays
open for the next request. Each participant has an *idle timeout* — how long it will hold an unused
connection before closing it. Servers also cap the number of requests per connection to bound memory
and force periodic rebalancing.

**Head-of-line (HOL) blocking** exists at two layers, and conflating them is the usual source of
confusion:

- **HTTP/1.1 HOL** — one connection carries one request at a time. A slow response blocks everything
  queued behind it on that connection. Clients work around it by opening 6+ parallel connections per
  host.
- **TCP HOL** — a lost packet stalls *everything* on that TCP connection until it is retransmitted,
  because TCP guarantees ordered delivery to the layer above.

```text
HTTP/1.1     conn 1: [ req A ═══════════▶ ][ req D ▶ ]     6 connections per host,
             conn 2: [ req B ▶ ]                            each strictly serial
             conn 3: [ req C ═════▶ ]                       → HTTP-level HOL per connection

HTTP/2       conn 1: [ A ▶ ][ B ▶ ][ C ▶ ][ D ▶ ]  interleaved streams, one TCP connection
                     └─ solves HTTP-level HOL
                     └─ ⚠️ INHERITS TCP HOL: one lost packet stalls ALL streams

HTTP/3       conn 1: [ A ▶ ][ B ▶ ][ C ▶ ][ D ▶ ]  streams over QUIC (UDP)
                     └─ independent streams: a loss on A does not stall B
                     └─ 0-RTT resumption; survives IP changes (connection migration)
```

That diagram contains the honest summary of the version history: **HTTP/2 fixed HTTP-level HOL and
made TCP-level HOL worse** (by putting everything on one connection), and **HTTP/3 fixed TCP-level
HOL** by replacing TCP with QUIC over UDP.

**Where each belongs in a Python backend:**

- **Browser ⇄ edge**: HTTP/2 or HTTP/3, terminated at the CDN or reverse proxy. Real, large wins for
  page loads with many small assets.
- **Proxy ⇄ your uvicorn app**: HTTP/1.1 with keep-alive, over a local network. Multiplexing buys
  almost nothing here — the proxy already maintains a warm pool, RTT is sub-millisecond, and h2
  costs CPU. ⚠️ uvicorn does not speak HTTP/2 at all; Hypercorn does. This is rarely a reason to
  switch.
- **Your app ⇄ internal services**: HTTP/2 helps when you make many concurrent calls to one host —
  gRPC uses it for exactly this (02.2).

### Mental Model

> A connection is a **warm resource with an expiry that every layer estimates independently**. It is
> reused until someone decides it is stale. The failure mode is never "reuse is bad" — it is **two
> layers disagreeing about the expiry**, where the closer's `FIN` and the reuser's next request cross
> in flight.

## How It Works

The race that produces phantom `502`s, in sequence:

```text
LOAD BALANCER (idle timeout 60 s)                UVICORN (keep-alive timeout 5 s)
        │                                                 │
   t=0  ├── response delivered ──────────────────────────┤ connection idle
        │   LB keeps connection in its pool                │
   t=5  │                                                 ├── 5 s elapsed → sends FIN
        │                                                 │   (server considers it closed)
   t=5.0001                                               │
        ├── new request arrives; LB picks that            │
        │   pooled connection — its FIN has not           │
        │   yet been processed ─────────────────▶ ✗       │
        │                                            RST / closed socket
        │◀── connection reset ────────────────────────────┤
        │                                                 │
        └── LB has a half-sent request it cannot safely   │
            retry (it may be a POST) → returns 502        │
                                                          │
   Application sees: NOTHING. The request never reached ASGI.
```

The window is small — microseconds per idle connection — but at thousands of requests per second
across hundreds of pooled connections, small windows produce a steady error rate.

**The invariant that prevents it:**

```text
client idle timeout  <  proxy/LB idle timeout  <  server keep-alive timeout
```

Whoever is *upstream* (closer to the origin) must hold connections **longer**, so the party that
reuses a connection is always the one that closes it first. Get the order backwards anywhere in the
chain and you get the race above at that hop.

Concrete defaults that fight each other out of the box:

| Component | Setting | Default |
|---|---|---|
| AWS ALB | idle timeout | **60 s** |
| nginx | `keepalive_timeout` (upstream) | 60 s |
| Traefik | `respondingTimeouts.idleTimeout` | 180 s |
| **uvicorn** | `--timeout-keep-alive` | **5 s** ⚠️ |
| gunicorn | `--keep-alive` | 2 s ⚠️ |
| `httpx` | `keepalive_expiry` | 5 s |

uvicorn behind an ALB with defaults is *already* misconfigured: 5 s server vs 60 s LB, exactly
backwards.

## Code Example

Little of this lives in application code — which is the point. The configuration *is* the
engineering, so it belongs in version control with the reasoning attached.

```dockerfile
# ledgerly/Dockerfile (excerpt — full treatment in 14.4)
# ⚠️ INVARIANT: timeout-keep-alive MUST exceed the load balancer's idle timeout (60 s).
# If the LB holds a connection longer than uvicorn does, uvicorn's FIN races the LB's
# next request and clients get 502s that never appear in application logs. See 01.7.
CMD ["uvicorn", "ledgerly.main:app", \
     "--host", "0.0.0.0", "--port", "8000", \
     "--timeout-keep-alive", "75", \
     "--timeout-graceful-shutdown", "30", \
     "--no-access-log", \
     "--proxy-headers", "--forwarded-allow-ips", "10.0.0.0/8"]
```

```nginx
# infra/nginx/ledgerly.conf (excerpt)
upstream ledgerly_api {
    server api:8000;
    keepalive 64;                 # pooled connections to the app — without this,
                                  # nginx opens a NEW connection per request
    keepalive_timeout 60s;        # < uvicorn's 75s  ✅ invariant holds
    keepalive_requests 1000;
}

server {
    location /v1/ {
        proxy_pass http://ledgerly_api;
        proxy_http_version 1.1;   # ⚠️ default is 1.0 — which disables keep-alive entirely
        proxy_set_header Connection "";   # ⚠️ must clear the inherited "close" header
    }
}
```

The two `⚠️` lines in the nginx block are the most commonly missed configuration in this entire
notebook: nginx proxies with **HTTP/1.0** by default and forwards `Connection: close`, so an
`upstream ... keepalive` block silently does nothing. The symptom is a service that is mysteriously
slower than it should be, with a connection count equal to the request count.

Verify from the outside — a warm connection is directly observable:

```bash
$ curl -w 'connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n' \
       -o /dev/null -s https://api.ledgerly.com/v1/invoices/inv_9f2
connect=0.041 tls=0.083 ttfb=0.128          # cold: 3 RTTs before the response

$ curl -w '…' -o /dev/null -s https://api.ledgerly.com/v1/invoices/inv_9f2 \
       https://api.ledgerly.com/v1/invoices/inv_9f3     # two URLs, one connection
connect=0.041 tls=0.083 ttfb=0.127
connect=0.000 tls=0.000 ttfb=0.043          # warm: handshakes are free
```

`128 ms → 43 ms` for identical work. That is the value of the whole notebook in two commands.

And on the **outbound** side, where Ledgerly calls the tax-rate provider, connection reuse is
something you must not accidentally throw away:

```python
# ledgerly/clients/tax.py
import httpx

# ✅ ONE client for the process lifetime, created in the lifespan hook (03.9).
# Creating an AsyncClient per request means a full TCP+TLS handshake per request —
# the single most common self-inflicted latency bug in FastAPI services (04.3).
def build_tax_client() -> httpx.AsyncClient:
    return httpx.AsyncClient(
        base_url="https://api.taxprovider.example",
        timeout=httpx.Timeout(connect=1.0, read=3.0, write=3.0, pool=1.0),
        limits=httpx.Limits(
            max_connections=100,
            max_keepalive_connections=20,
            keepalive_expiry=30.0,        # < the provider's idle timeout: we close first
        ),
        http2=False,   # enable only if the provider supports it AND you measure a win
    )
```

## Design Patterns / Tradeoffs

### HTTP/1.1 vs HTTP/2 vs HTTP/3, per hop

**HTTP/1.1 with keep-alive**

- *How it works:* persistent connections, one in-flight request each; clients open several.
- *Advantages:* universally supported; trivial to debug (`curl`, `tcpdump`, proxy logs are readable);
  no per-connection state to tune; uvicorn speaks it natively.
- *Disadvantages:* HTTP-level HOL; header bytes repeated on every request; many connections per client.
- *Failure mode:* the keep-alive timeout race above.
- *Use when:* proxy-to-app hops, internal service calls, anything you will have to debug at 3 a.m.
- *Do NOT use when:* a browser is loading hundreds of subresources over a high-latency link.

**HTTP/2**

- *How it works:* multiplexed streams over one TCP connection, binary framing, HPACK header compression.
- *Advantages:* removes HTTP-level HOL; large header savings for repetitive requests; server push
  (deprecated in practice); the transport gRPC requires.
- *Disadvantages:* inherits and worsens **TCP** HOL — one lost packet stalls every stream; harder to
  debug; **uvicorn does not support it** (Hypercorn does); one connection means one LB target, which
  can unbalance load.
- *Failure mode:* on a lossy mobile network, h2 can be *slower* than h1.1 with parallel connections.
- *Use when:* browser↔edge, and app↔internal services with many concurrent calls to one host (gRPC).
- *Do NOT use when:* proxy↔uvicorn on a local network — you would swap servers to gain nothing.

**HTTP/3 (QUIC over UDP)**

- *Advantages:* independent streams (no TCP HOL); 0-RTT resumption; connection migration across
  network changes — a genuine win for mobile.
- *Disadvantages:* UDP is blocked or rate-limited on some corporate networks; higher CPU (userspace
  congestion control); Python server support is immature; observability tooling is behind.
- *Use when:* the CDN or edge offers it as a checkbox — take it there, and nowhere else for now.
- *Do NOT use when:* you would have to run it yourself in Python.

**Recommendation for a Python backend in 2026:** HTTP/2 or HTTP/3 at the CDN/edge (someone else's
problem, real user-facing win); HTTP/1.1 with correctly ordered keep-alive timeouts from the proxy
inward. Reach for h2 internally only for gRPC or a measured fan-out problem.

### Connection reuse on the outbound side

| | One client per process (✅) | New client per request (❌) | No keep-alive (`Connection: close`) |
|---|---|---|---|
| Handshakes | Amortised to ~zero | Every request | Every request |
| Added p99 latency | 0 | +80–120 ms | +80–120 ms |
| Ephemeral ports | Bounded | Exhausted under load (`TIME_WAIT`) | Exhausted |
| Failure mode | Pool exhaustion under a slow dependency (04.3) | Port exhaustion; `Cannot assign requested address` | Same |
| Use when | Always | Never | Only for a one-shot CLI |

Pool exhaustion is a real cost of the correct choice, not an argument against it — 04.3 covers
sizing and `pool` timeouts.

## Production Scenario

**Ledgerly, ongoing for eleven days.** A low-grade, chronic problem rather than an outage: roughly
0.2% of API requests fail with `502 Bad Gateway`. Customers with retry logic barely notice; two
customers without it have opened tickets about "random failures".

### Symptoms

- `502`s at 0.15–0.3% of all requests, steady, all hours, all endpoints, all tenants.
- **Zero corresponding entries in the application logs.** Not an error, not a slow request — nothing.
  The `502` count from the LB does not match any application-side count.
- Not correlated with deploys, traffic level, CPU, memory, or any dependency.
- Reproducing it by hand is impossible; every manual `curl` succeeds.
- Load-balancer access logs are the only place the failures exist:

```text
elb_status_code=502  target_status_code=-  request_processing_time=0.000
target_processing_time=-1  response_processing_time=-1  "POST /v1/invoices HTTP/1.1"
```

### Diagnosis

1. **Alert.** The `5xx` SLO alert fires and clears repeatedly — 0.2% sits right at the threshold. It
   had been acknowledged and muted twice, which is its own finding (15.12, alert fatigue).
2. **Metrics.** The decisive comparison: the LB reports `502`s that the application's own
   `http_responses_total` has no record of. **When the edge counts errors the origin never saw, the
   request died between them** — same principle as 01.4's cache leak, different layer.
3. **Logs.** `target_status_code=-` and `target_processing_time=-1` in the ALB log mean the LB never
   received a response — it could not even complete the request to the target. This excludes
   application errors entirely.
4. **Trace.** Traces for failed requests do not exist at all (no server span). Confirms the request
   never reached ASGI (01.1).
5. **Dependency health.** PostgreSQL, Redis, tax provider all clean. Not implicated.
6. **The decisive experiment.** A `tcpdump` on one API container, filtered to the LB subnet, shows
   the pattern directly:

```text
10:41:22.104  api → lb   FIN, ACK        seq=8801        # uvicorn closing an idle connection
10:41:22.104  lb  → api  PSH, ACK  len=612               # LB sending a request on it
10:41:22.105  api → lb   RST                             # socket is gone
```

   A `FIN` and a request crossing in flight, 1 ms apart. Then the configuration comparison:

```bash
$ aws elbv2 describe-load-balancer-attributes --load-balancer-arn … \
      | jq -r '.Attributes[] | select(.Key=="idle_timeout.timeout_seconds")'
{"Key":"idle_timeout.timeout_seconds","Value":"60"}

$ docker inspect ledgerly-api | jq -r '.[0].Config.Cmd | join(" ")'
uvicorn ledgerly.main:app --host 0.0.0.0 --port 8000       # no --timeout-keep-alive → 5 s
```

### Root Cause

The ALB holds idle connections for 60 seconds. uvicorn holds them for 5 seconds (its default). The
invariant is inverted: **the party that reuses connections holds them 12× longer than the party that
closes them.**

Every idle connection older than 5 seconds is closed by uvicorn while the ALB still believes it is
usable. When the next request happens to select one of those connections in the microseconds before
the `FIN` is processed, the write fails. The ALB will not retry a `POST` (correctly — it is
non-idempotent, 01.2), so it returns `502`.

Nothing was broken in any single component. Two defaults, from two vendors, in the wrong order.

### Fix

*Mitigation and permanent fix are the same one-line change* — deployed within the hour:

```diff
- CMD ["uvicorn", "ledgerly.main:app", "--host", "0.0.0.0", "--port", "8000"]
+ # INVARIANT: must exceed the ALB idle timeout (60 s). See 01.7.
+ CMD ["uvicorn", "ledgerly.main:app", "--host", "0.0.0.0", "--port", "8000", \
+      "--timeout-keep-alive", "75"]
```

`502`s fell from 0.2% to 0.000% within one deployment cycle and did not return.

*Hardening applied alongside:*

- The same audit across every hop found a second inversion: the internal service mesh's client
  `keepalive_expiry` (30 s) exceeded a downstream service's server timeout (10 s), producing a
  smaller version of the same errors. Both were corrected.
- The timeout ordering was written into the deployment template as a comment *with the reason*,
  because a future engineer trimming "unnecessary" flags is exactly how this recurs.

### Prevention

- **A documented, tested invariant.** A CI check that reads the infrastructure and container
  configuration and asserts the ordering:

```python
# tests/infra/test_keepalive_ordering.py
"""client keepalive < LB idle timeout < server keep-alive. Inversions cause phantom 502s."""
from infra.config import load_alb_config, load_uvicorn_args, load_httpx_limits

def test_keepalive_timeout_ordering() -> None:
    client = load_httpx_limits().keepalive_expiry        # 30
    lb = load_alb_config()["idle_timeout.timeout_seconds"]  # 60
    server = int(load_uvicorn_args()["--timeout-keep-alive"])  # 75
    assert client < lb < server, (
        f"keep-alive inversion: client={client}s lb={lb}s server={server}s — "
        "the upstream must hold connections longer than the downstream reuses them"
    )
```

- **Alert on the edge-vs-origin error discrepancy**: `lb_5xx_total − app_5xx_total > 0` sustained. Any
  error the edge sees that the origin does not is, by construction, a connection-layer problem. This
  single alert generalises to a whole family of incidents.
- **Do not mute a flapping SLO alert.** 0.2% errors for eleven days was two acknowledged pages away
  from being fixed on day one (15.12).
- **Include connection-level configuration in deployment review**, with the invariant stated in the
  template.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the LB holds connections longer than the server? | Phantom `502`s with no application logs — the scenario above. |
| ...keep-alive is disabled somewhere in the chain? | Every request pays TCP + TLS (+80–120 ms) and burns ephemeral ports. Check `proxy_http_version 1.1` and `Connection ""` in nginx. |
| ...you create an HTTP client per request? | Same cost, plus `TIME_WAIT` port exhaustion under load (04.3). |
| ...a deploy drains a replica? | In-flight requests must complete before the socket closes — graceful shutdown (04.9), and `--timeout-graceful-shutdown` must exceed your slowest request. |
| ...one HTTP/2 connection carries all a client's traffic? | It pins to one LB target; load balances poorly, and one connection failure affects every in-flight stream. |
| ...packets are lost on a mobile network? | HTTP/2 stalls all streams (TCP HOL); HTTP/3 stalls only the affected one. |
| ...traffic increases 10×? | Connection *count* may not grow proportionally if reuse is healthy. If it does grow linearly, reuse is broken somewhere. |
| ...an idle connection sits behind a stateful firewall or NAT? | It may be silently dropped after ~5 minutes. TCP keep-alive probes or a shorter idle timeout are needed; symptoms look identical to this incident. |

## Common Pitfalls

**Leaving uvicorn's 5 s keep-alive behind a 60 s load balancer.** The default configuration is
already wrong. *Instead:* `--timeout-keep-alive` above the LB idle timeout, with the reason in a comment.

**nginx `upstream ... keepalive` without `proxy_http_version 1.1` and `proxy_set_header Connection ""`.**
The pool silently does nothing. *Instead:* all three lines together, always.

**Creating an `httpx.AsyncClient` inside a handler.** Full handshake per request. *Instead:* one
client per process, built in the lifespan hook (03.9).

**Assuming HTTP/2 is faster everywhere.** On lossy networks it can be slower, and it buys nothing on
a sub-millisecond internal hop. *Instead:* h2/h3 at the edge; measure before adopting it elsewhere.

**Treating a 0.2% error rate as background noise.** Chronic low-grade errors are almost always a
specific, findable, fixable defect. *Instead:* investigate the discrepancy between edge and origin
counts; the answer is usually one configuration line.

**Setting a graceful-shutdown timeout shorter than your slowest request.** Deploys then sever
in-flight requests, producing the same `502` signature from a different cause (04.9, 14.17).

## How to Test This

- The keep-alive ordering assertion above, run in CI against real configuration files.
- A connection-reuse test: issue 10 requests through one `httpx.AsyncClient` and assert the transport
  opened one connection (`len(client._transport._pool.connections) == 1`), catching a regression that
  disables reuse.
- A soak test (13.13) at low RPS for 10+ minutes with idle gaps — the failure only appears with idle
  connections, so a short burst test will never find it.
- Assert `curl` timings: warm `time_connect` is 0.

## Interview Questions

1. *Explain.* What does a new HTTPS connection cost, and why does keep-alive matter more on mobile? —
   2–3 RTTs; higher RTT multiplies the saving.
2. *Explain.* What problem does HTTP/2 solve, and what problem does it make worse? — HTTP-level HOL;
   TCP-level HOL.
3. *Debug this.* 0.2% of requests are `502` with no application logs and `target_status_code=-`. —
   Keep-alive timeout inversion; the request never reached the app.
4. *Design.* State the correct ordering of keep-alive timeouts across client, LB and server, and
   justify it. — Upstream holds longer; the reuser must not be the one surprised by a close.
5. *Explain.* Why might HTTP/2 be slower than HTTP/1.1 on a lossy connection? — All streams share one
   TCP connection; a loss stalls everything.
6. *Debug this.* Your service opens one outbound TCP connection per request under load and starts
   failing with "cannot assign requested address". — Client created per request, or keep-alive
   disabled; ephemeral port exhaustion.
7. *Design.* Would you enable HTTP/2 between nginx and uvicorn? — No: uvicorn does not support it, and
   the hop is sub-millisecond with a warm pool; the gain is nil.

## Key Takeaways

- A cold HTTPS connection costs 2–3 round trips; a warm one costs none. Connection reuse is usually
  the largest single latency win available, and it is configuration, not code.
- **The invariant: client idle < proxy idle < server keep-alive.** Inverting it anywhere produces
  `502`s that never appear in application logs.
- uvicorn's 5 s default is *below* every common load-balancer default. Set it explicitly, above the
  LB, with the reason written down.
- nginx needs `proxy_http_version 1.1` **and** `proxy_set_header Connection ""` for upstream
  keep-alive to work at all.
- HTTP/2 solves HTTP-level HOL and inherits TCP-level HOL; HTTP/3 solves TCP-level HOL. Use them at
  the edge; keep HTTP/1.1 from the proxy inward unless you have measured otherwise.
- One HTTP client per process, built at startup. Per-request clients silently add ~100 ms and exhaust
  ephemeral ports.
- When the edge counts errors the origin never saw, the problem is in the connection layer. Alert on
  that discrepancy.
