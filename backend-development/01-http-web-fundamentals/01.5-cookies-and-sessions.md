# 01.5 Cookies and Sessions

> **Prerequisites:** 01.1 (lifecycle), 01.3 (headers) · modern-python 18.2 (bearer tokens as a client)
> **What you'll learn:**
> - Explain what a cookie actually is at the protocol level, and what each `Set-Cookie` attribute controls
> - Choose `SameSite` correctly — and predict which flows break under each value
> - Separate the *session identifier* from the *session data*, and know where each belongs
> - Recognise why a browser dashboard and a machine API want different credential mechanisms
> **Level:** Beginner

---

## Concept

### Plain-English Explanation

HTTP has no memory. Two requests from the same person are, to the protocol, two unrelated events. A
cookie is the workaround: the server hands the browser a small piece of text and says "attach this to
every future request to me", and the browser — a piece of software the server does not control —
mostly complies.

Everything difficult about cookies comes from that last clause. The browser decides *which* requests
get the cookie, based on rules designed to stop malicious websites from using your credentials
(01.9, 16.5). Those rules changed significantly between 2020 and 2024, and every "it worked
yesterday, and only in Chrome" login bug traces back to them.

A **session** is the thing the cookie usually points at: server-side state — who this person is,
which tenant they are acting for, when they logged in — kept somewhere the browser cannot see.

### Technical Explanation

A cookie is two headers. The server sends:

```http
Set-Cookie: ledgerly_session=v2.9f3c…; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=1209600
```

and the browser thereafter sends:

```http
Cookie: ledgerly_session=v2.9f3c…
```

Note the asymmetry: `Set-Cookie` carries attributes, `Cookie` carries **only name–value pairs**. The
server never learns which cookie came from which domain or path, and cannot read `HttpOnly` or
`Secure` back. Attributes are instructions to the browser, not data you get returned.

**The attributes, and what each actually defends against:**

| Attribute | Effect | Omit it and... |
|---|---|---|
| `HttpOnly` | JavaScript cannot read `document.cookie` | An XSS bug becomes full session theft (16.4) |
| `Secure` | Sent only over HTTPS | The cookie can leak over a plaintext hop |
| `SameSite=Lax` (default) | Sent on same-site requests and **top-level `GET` navigations** from other sites | See below — the default breaks cross-site `POST` |
| `SameSite=Strict` | Never sent on any cross-site request | Following a link from an email lands the user logged out |
| `SameSite=None` | Sent on all cross-site requests; **requires `Secure`** | Needed for third-party contexts; reopens CSRF risk (16.5) |
| `Path=/` | Which paths receive it | Not a security boundary — sibling paths on the same origin can still read it via JS |
| `Domain=` | Widens to subdomains | ⚠️ Omitting it is *narrower* and safer. Setting `Domain=ledgerly.com` shares the cookie with every subdomain, including a compromised marketing site |
| `Max-Age` / `Expires` | Persistent lifetime | Cookie becomes a session cookie, dying with the browser process |
| `__Host-` name prefix | Browser enforces `Secure`, `Path=/`, no `Domain` | You lose browser-enforced hardening |
| `Partitioned` (CHIPS) | Separate jar per top-level site | Required for third-party cookies in embedded contexts |

The single most useful modern hardening is the **`__Host-` prefix**: naming the cookie
`__Host-ledgerly_session` makes the browser itself reject it unless it is `Secure`, has `Path=/`, and
has no `Domain` — so a misconfiguration cannot ship silently.

**Session identifier vs session data.** Two designs:

```text
A. Opaque ID + server-side store           B. Signed/encrypted data in the cookie
   Cookie: sid=9f3c…  (32 random bytes)       Cookie: sess=<base64 payload>.<HMAC>
   Redis: session:9f3c… → {user, tenant,      Server verifies signature; no lookup.
          roles, csrf_token, expires_at}
   ✓ Revocable instantly                      ✓ No store to run or scale
   ✓ Small cookie                             ✗ Cannot revoke before expiry
   ✗ A store to run (10.14)                   ✗ Size limits (~4 KB per cookie)
   ✗ A lookup on every request                ✗ Rotating the key logs everyone out
```

Ledgerly uses A for the browser dashboard (revocation matters for a finance product) and bearer
tokens for the machine API. Module 08 makes that choice properly, with the security analysis; here
the point is only that the *cookie carries a pointer, the server carries the truth*.

### Mental Model

> A cookie is **a string the server asks the browser to memorise, with rules about when to repeat
> it**. You control the string; the browser controls the rules and enforces them for you. Design
> your login flows around what the browser will actually send — not around what you told it to store.

## How It Works

`SameSite` is where sessions break in production, so it is worth seeing precisely. "Same site" means
the same registrable domain (`ledgerly.com`), not the same origin — `app.ledgerly.com` and
`api.ledgerly.com` are same-site, but `ledgerly.com` and `login.okta.com` are not.

```text
Cookie: __Host-ledgerly_session; SameSite=Lax   (the default when you omit SameSite)

user clicks a link in an email → GET https://app.ledgerly.com/invoices
   cross-site, but a TOP-LEVEL GET NAVIGATION            → ✅ cookie sent

app.ledgerly.com fetches api.ledgerly.com/v1/invoices
   same-site                                             → ✅ cookie sent

Okta POSTs a SAML assertion to app.ledgerly.com/sso/acs
   cross-site + POST                                     → ❌ COOKIE NOT SENT
                                                            ← this is the outage below

evil.example.com auto-submits a form POST to app.ledgerly.com/v1/invoices
   cross-site + POST                                     → ❌ not sent (this is the point:
                                                            Lax is CSRF defence — 16.5)
```

The last two rows are the same browser rule serving two purposes. `SameSite=Lax` blocks the attack in
row four and, unavoidably, the legitimate flow in row three.

## Code Example

Ledgerly's dashboard login, with an opaque session ID in Redis and hardened cookie attributes.

```python
# ledgerly/auth/session_cookie.py
import secrets
from datetime import timedelta
from fastapi import Response

SESSION_COOKIE = "__Host-ledgerly_session"      # prefix enforces Secure + Path=/ + no Domain
SESSION_TTL = timedelta(days=14)

def new_session_id() -> str:
    """32 bytes from the OS CSPRNG. Never uuid4() for a credential, never a
    counter, never anything derived from the user id."""
    return secrets.token_urlsafe(32)

def set_session_cookie(response: Response, session_id: str, *, secure: bool = True) -> None:
    response.set_cookie(
        key=SESSION_COOKIE,
        value=session_id,
        max_age=int(SESSION_TTL.total_seconds()),
        httponly=True,      # XSS cannot read it (16.4)
        secure=secure,      # HTTPS only — False only for local http:// development
        samesite="lax",     # blocks cross-site POST CSRF (16.5)
        path="/",           # required by the __Host- prefix
        # no `domain=` — deliberately narrow to this exact host
    )

def clear_session_cookie(response: Response) -> None:
    # Attributes must match the ones used to set it, or the browser ignores the deletion.
    response.delete_cookie(SESSION_COOKIE, path="/", httponly=True,
                           secure=True, samesite="lax")
```

```python
# ledgerly/routers/auth.py
@router.post("/login")
async def login(body: LoginIn, response: Response, sessions: SessionStore,
                users: UserService) -> dict[str, str]:
    user = await users.verify_password(body.email, body.password)   # 08.15

    # ⚠️ Session fixation defence: always mint a NEW id at privilege change.
    # Reusing a pre-login session id lets an attacker who planted one ride it in.
    session_id = new_session_id()
    await sessions.create(session_id, user_id=user.id, tenant_id=user.tenant_id,
                          ttl=SESSION_TTL)
    set_session_cookie(response, session_id)
    return {"status": "ok"}


@router.post("/logout")
async def logout(response: Response, sessions: SessionStore,
                 session_id: Annotated[str | None, Cookie(alias=SESSION_COOKIE)] = None):
    if session_id:
        await sessions.delete(session_id)   # server-side revocation — the reason for design A
    clear_session_cookie(response)          # client-side tidy-up; never the only step
    return {"status": "ok"}
```

The two comments mark the mistakes that matter: **regenerate the session ID on login** (otherwise
session fixation, 08.2), and **delete server-side on logout** (clearing the cookie alone leaves a
valid session anyone holding the string can use).

## Design Patterns / Tradeoffs

### Cookie session vs bearer token

| | Cookie + server session | `Authorization: Bearer` token |
|---|---|---|
| Sent by | The browser, automatically | The client, explicitly |
| CSRF exposure | Yes — automatic sending is the vulnerability (16.5) | No — an attacker's page cannot set the header |
| XSS exposure | Mitigated by `HttpOnly` | High if stored in `localStorage` |
| Revocation | Immediate (delete the store entry) | Hard (08.6) |
| Works for | Browsers on your own domain | Mobile, server-to-server, CLIs, third parties |
| Cost per request | A store lookup (~0.3 ms Redis) | Signature verification (~0.05 ms, no I/O) |
| Use when | First-party web UI | Machine clients, cross-origin SPAs, mobile |
| Avoid when | Non-browser clients, or cross-site by design | You need instant, reliable revocation |

**Recommendation:** cookies for the first-party dashboard, tokens for the public API — which is what
Ledgerly does. Do not force one mechanism onto both; the "single auth system" simplification usually
ends as `localStorage` tokens (XSS-exposed) or CSRF-vulnerable cookies. Full treatment in 08.1.

### `SameSite` value selection

- **`Lax`** — the default and the right answer for ~95% of session cookies. Blocks cross-site
  `POST`; permits the email-link navigation users expect. *Do NOT use when* a third party must
  `POST` back to you mid-flow (SSO POST bindings, some payment returns).
- **`Strict`** — highest CSRF protection. *Do NOT use for the main session cookie:* arriving from any
  external link, the user appears logged out, then logged in on the next click. A confusing UX bug
  that generates support load. Reasonable for a second "step-up" cookie guarding admin actions.
- **`None; Secure`** — required for genuine third-party contexts (embedded widgets, cross-site POST
  callbacks). *Reopens CSRF*, so it must be paired with token-based CSRF defence (16.5) and, in
  embedded contexts, `Partitioned`.

The mature pattern is **two cookies**: a `Lax` long-lived session, plus a short-lived `None; Secure`
cookie scoped to the one callback path that needs it — which is exactly the fix below.

## Production Scenario

**Ledgerly, Tuesday 08:05.** The largest enterprise customer files a P1: *"Nobody at our company can
log in. We get bounced back to the login page forever."* Ledgerly's own staff log in fine. Two other
SSO customers report the same within the hour; four do not.

### Symptoms

- Affected users: only those on **SAML SSO**, and only in Chrome and Edge. Firefox users are fine.
- The browser shows a redirect loop: `/sso/start` → identity provider → `/sso/acs` → `/login`.
- `http_requests_total{route="/sso/acs",status="302"}` is normal — the endpoint is *succeeding*.
- `login_success_total` for those tenants: **0** since 06:00 UTC. For password-login tenants:
  unchanged.
- No deploy in eight days. No configuration change on Ledgerly's side at all.

### Diagnosis

1. **Alert.** None. Ledgerly alerted on `5xx` and latency; a login that returns `302` and quietly
   fails is invisible to both. (Prevention item one.)
2. **Metrics.** Segmenting `login_success_total` by auth method isolates it instantly: SSO zero,
   password normal. The problem is in the SSO flow, not authentication generally.
3. **Logs.** `/sso/acs` logs show the SAML assertion validating correctly and a session being created
   — then the *next* request to `/invoices` arrives with **no session cookie at all**:

```json
{"route":"/sso/acs","saml_valid":true,"session_created":"9f3c…","set_cookie":true}
{"route":"/invoices","cookie_present":false,"outcome":"redirect_to_login"}
```

   The server is doing everything right. The browser is not sending back what it was given.

4. **Browser-side check.** Chrome DevTools → Application → Cookies shows the cookie **absent**, and
   the Issues panel carries the explanation verbatim: a cookie was not sent because of its
   `SameSite=Lax` attribute in a cross-site `POST` context.
5. **Dependency health.** The identity provider is fine; the assertion is valid. Not implicated.
6. **The differentiator** — why only some customers — is the SAML binding: the affected identity
   providers use the **HTTP-POST binding** (a cross-site `POST` to `/sso/acs`); the unaffected ones
   use the redirect binding (a top-level `GET`, which `Lax` permits).

### Root Cause

The session cookie is set during `/sso/acs`, which the identity provider reaches by **`POST`ing a
form from its own domain**. The cookie has `SameSite=Lax`. Chrome had been rolling out stricter
enforcement of the `Lax` default; on Tuesday it reached this customer's Chrome channel. From that
moment, the browser **rejected the cookie at `Set-Cookie` time** — a `Lax` cookie arriving in the
response to a cross-site `POST` never enters the jar — so there was no cookie to send on the
subsequent navigation, every request after login looked unauthenticated, and the app redirected to
`/login`.

Nothing changed at Ledgerly. A browser default changed underneath them, and their SSO flow depended
on the old behaviour. **This is the defining risk of cookies: the enforcement point is software you
do not deploy.**

### Fix

*Mitigation (25 minutes):* the SSO callback sets a **separate, short-lived, `SameSite=None; Secure`
handoff cookie** scoped to one path, then immediately exchanges it for the normal `Lax` session on a
same-site redirect:

```python
# ledgerly/routers/sso.py
HANDOFF_COOKIE = "ledgerly_sso_handoff"   # no __Host- prefix: needs a narrow Path

@router.post("/sso/acs")
async def sso_assertion_consumer(request: Request, sessions: SessionStore,
                                 saml: SamlService) -> RedirectResponse:
    """Cross-site POST from the IdP. A Lax cookie set here will not come back,
    so we set a single-use handoff cookie that IS allowed cross-site."""
    assertion = await saml.validate(await request.form())
    handoff = new_session_id()
    await sessions.create_handoff(handoff, user_id=assertion.user_id, ttl=timedelta(seconds=60))

    response = RedirectResponse("/sso/complete", status_code=303)
    response.set_cookie(
        HANDOFF_COOKIE, handoff, max_age=60, httponly=True, secure=True,
        samesite="none",              # ← permitted cross-site; MUST be Secure
        path="/sso/complete",         # ← one endpoint only; not the whole site
    )
    return response


@router.get("/sso/complete")
async def sso_complete(response: RedirectResponse, sessions: SessionStore,
                       handoff: Annotated[str | None, Cookie(alias=HANDOFF_COOKIE)] = None):
    """Same-site GET. Consume the single-use handoff, mint the real Lax session."""
    if handoff is None:
        return RedirectResponse("/login?error=sso_handoff_missing", status_code=303)
    claim = await sessions.consume_handoff(handoff)     # single use, deleted on read
    if claim is None:
        return RedirectResponse("/login?error=sso_handoff_expired", status_code=303)

    session_id = new_session_id()
    await sessions.create(session_id, user_id=claim.user_id, tenant_id=claim.tenant_id,
                          ttl=SESSION_TTL)
    redirect = RedirectResponse("/invoices", status_code=303)
    set_session_cookie(redirect, session_id)            # normal Lax session
    redirect.delete_cookie(HANDOFF_COOKIE, path="/sso/complete")
    return redirect
```

The handoff cookie is `None`-scoped but is single-use, 60-second, `HttpOnly`, `Secure`, and valid on
exactly one path — so the CSRF surface it reopens is negligible.

*Permanent fix:* the SSO flow is now explicitly documented and tested as a cross-site flow, and the
`SameSite` value of every cookie is asserted in tests rather than being an implicit default.

### Prevention

- **Alert on business outcomes, not just errors**: `rate(login_success_total)` by auth method, with
  an alert on a drop to zero. This failure produced no errors of any kind (15.11).
- **A cookie-attribute contract test**, so an attribute can never change by accident:

```python
# tests/contract/test_cookie_attributes.py
EXPECTED = {
    "__Host-ledgerly_session": {"httponly": True, "secure": True, "samesite": "lax", "path": "/"},
    "ledgerly_sso_handoff":    {"httponly": True, "secure": True, "samesite": "none",
                                "path": "/sso/complete", "max-age": "60"},
}

def test_cookie_attributes(login_response, sso_response):
    for response in (login_response, sso_response):
        for raw in response.headers.get_list("set-cookie"):
            name = raw.split("=", 1)[0]
            if name in EXPECTED:
                attrs = {k.strip().lower(): v for k, _, v in
                         (p.partition("=") for p in raw.split(";")[1:])}
                for key, want in EXPECTED[name].items():
                    got = attrs.get(key, True if key in attrs else None)
                    assert str(got).lower() == str(want).lower(), f"{name}.{key}={got!r}"
```

- **Track browser release notes for cookie behaviour** as a standing operational task. Chrome,
  Safari and Firefox have each shipped a change in the last five years that broke working login
  flows without any server change.
- **A synthetic SSO login canary per binding type**, running every five minutes against a test IdP.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...an XSS bug lands? | `HttpOnly` stops cookie theft, but not actions taken as the user. Both matter (16.4). |
| ...the browser changes its `SameSite` default? | It has, and it will again. Depend on explicit values and monitor login success rates. |
| ...the session store (Redis) is down? | With server-side sessions, **everyone is logged out**. Decide deliberately: fail closed, or a short-lived signed fallback. This is 10.6's availability question arriving early. |
| ...the cookie exceeds 4 KB? | Browsers silently drop it. Never put roles or claims in the cookie; store a pointer. |
| ...a user logs out on one device? | Only server-side sessions can revoke everywhere. Cookie-encoded state cannot (08.6). |
| ...the user's clock is wrong? | `Max-Age` is relative and safe; `Expires` is absolute and can misbehave. Prefer `Max-Age`. |
| ...you set `Domain=ledgerly.com`? | Every subdomain — including a third-party-hosted marketing site — receives the session cookie. Omit `Domain`. |

## Common Pitfalls

**Not regenerating the session ID on login.** Session fixation: an attacker plants a known ID before
login and inherits the authenticated session. *Instead:* mint a new ID at every privilege change,
including step-up authentication.

**Clearing the cookie as "logout".** The session string still works for anyone who captured it.
*Instead:* delete server-side first; clear the cookie second.

**Putting roles or tenant data in the cookie to "save a lookup".** It becomes stale the moment
permissions change, and it grows past the size limit. *Instead:* an opaque ID plus a fast store
lookup (10.14).

**`SameSite=Strict` on the main session.** Users following a link from an email land logged out.
*Instead:* `Lax`, with `Strict` reserved for a separate step-up cookie.

**Setting `Domain=` to share across subdomains.** Widens exposure to every subdomain you or a vendor
ever hosts. *Instead:* omit `Domain` and use the `__Host-` prefix.

**Deleting a cookie with different attributes than it was set with.** The browser ignores the
deletion, and the user stays logged in. *Instead:* keep set and clear in one module, as above.

## How to Test This

- The cookie-attribute contract test above.
- `test_login_rotates_session_id` — assert the post-login ID differs from any pre-login one.
- `test_logout_invalidates_server_side` — call logout, then reuse the old cookie, expect `401`.
- An end-to-end SSO test per SAML binding (POST and redirect), which is the only kind of test that
  would have caught the incident.

## Interview Questions

1. *Explain.* What does `HttpOnly` protect against, and what does it not? — Cookie exfiltration via
   XSS; not actions performed by injected script.
2. *Explain.* Difference between `SameSite=Lax` and `Strict`, with a flow each breaks. — Cross-site
   `POST` callbacks; inbound email links.
3. *Design.* Session data in the cookie or an opaque ID plus a store? Defend your choice for a
   finance product. — Revocation requirement points to a store.
4. *Debug this.* SSO users on Chrome are in a redirect loop; the server creates sessions
   successfully; Firefox is fine. — Cookie set in a cross-site `POST` context with `SameSite=Lax`.
5. *Explain.* Why is session-ID regeneration on login required? — Session fixation.
6. *Explain.* What does the `__Host-` prefix guarantee, and who enforces it? — `Secure`, `Path=/`, no
   `Domain`; enforced by the browser.
7. *Design.* Your Redis session store fails. What is the user-visible behaviour and what would you
   choose instead? — Mass logout vs a signed short-lived fallback; state the tradeoff.

## Key Takeaways

- A cookie is a string plus **browser-enforced rules**. The enforcement point is software you do not
  control and that changes under you — monitor login success as a first-class metric.
- `HttpOnly`, `Secure`, `SameSite=Lax`, no `Domain`, and the `__Host-` prefix are the default set.
  Deviations need a written reason.
- Keep the **identifier** in the cookie and the **data** on the server. Cookie-encoded state cannot
  be revoked and will outgrow 4 KB.
- Regenerate the session ID on login; revoke server-side on logout. Both are one line and both are
  routinely missing.
- Cross-site `POST` callbacks (SAML POST binding, some payment returns) need a narrow, single-use
  `SameSite=None; Secure` cookie — not a weakening of your main session cookie.
- Browsers for cookies, tokens for machines. One mechanism for both usually means one of them is
  insecure.
