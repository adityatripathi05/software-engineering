> - Make cross-tenant references **unrepresentable** with composite foreign keys — the write-side guarantee nothing else provides
> - Deploy row-level security as the read floor without stepping on its three real mines: the superuser bypass, the fail-open GUC, and pooled-connection bleed
> **Level:** Intermediate

> ⚡ **Tuesday 5 January, 11:20** — an agent at a small freight startup screenshots their ticket #212: four support comments they never wrote, including an internal note discussing another company's contract renewal. The cause: a merge tool that trusted an id.

## Concept

### Plain-English Explanation

Every table Deskhub owns carries a `tenant_id`, and every query is supposed to filter by it. That sentence contains the entire architecture *and* the entire risk: "supposed to" is a per-path promise, and 05.3 just spent a notebook establishing what per-path promises are worth. A missing `WHERE tenant_id = …` is the famous version of the failure — one tenant reading another's rows. The less famous version, and this notebook's incident, is a **write**: a row that ends up *belonging* to the wrong tenant, at which point every correctly-scoped query in the fleet faithfully shows tenant A's data to tenant B, forever, because the data itself now says so.

Multi-tenant modelling is therefore not "add a column". It is deciding, deliberately, **which layer refuses a cross-tenant operation** — application code, the schema's geometry, the database's row filter, or a physical boundary — knowing that each layer catches a different class of mistake and misses the others. Deskhub runs the pooled model (one schema, all tenants), which is the right default for a SaaS with thousands of small tenants; this notebook is about making that model earn the word *isolation*.

### Technical Explanation

**The three architectures**, named the way operators name them:

- **Pool** — shared schema, `tenant_id` on every scoped table. One set of tables, one migration, one connection pool; isolation is logical.
- **Bridge** — schema-per-tenant. One database, N schemas; isolation by namespace; every migration runs N times.
- **Silo** — database-per-tenant (or instance-per-tenant). Physical isolation; per-tenant everything, including cost.

The Tradeoffs section prices them; the headline is that the pool model wins on operations (one migration, one pool, cross-tenant analytics for free) and *loses by default* on isolation — which is recoverable, because PostgreSQL gives the pool model two mechanisms the application cannot match.

**Mechanism one: composite foreign keys make cross-tenant references unrepresentable.** A plain FK — `comments.ticket_id REFERENCES tickets(id)` — asks only *"is this a ticket?"* It is tenant-blind, so a comment pointing at another tenant's ticket is a perfectly valid row. The fix is geometric: put `tenant_id` on the child and make the FK **composite**:

```text
tickets:  UNIQUE (tenant_id, id)          ← the referenceable pair
comments: FOREIGN KEY (tenant_id, ticket_id) REFERENCES tickets (tenant_id, id)
```

Now the pair must exist together in `tickets`, so "Baltic-tenant comment on a Nordwind ticket" is not a bug that better code avoids — it is a row that **cannot be written**, by any path, ever. The `tenant_id` copy on the child is duplication of the safe kind (05.2's trichotomy): a copy of an *immutable* fact — Deskhub decides here, as canon, that tickets never change tenants (tenant mergers are export/import migrations, not row moves) — kept honest by the strongest writer that exists, the constraint itself.

**Mechanism two: row-level security is the read floor.** `CREATE POLICY … USING (tenant_id = <current tenant>)` makes the database append the tenant filter to every query against the table — including the query someone forgot to scope. The current tenant travels as a session **GUC** (`SET LOCAL app.tenant_id = …`), set by the application once per transaction from the authenticated principal (03.5's `get_tenant`, one layer down). Three properties decide whether RLS protects you or merely decorates the schema, and the lab captures all three: **superusers bypass policies unconditionally** (and table owners do too unless `FORCE ROW LEVEL SECURITY`) — so the app must connect as a dedicated non-privileged role; an **unset GUC must fail closed** (the policy's `NULLIF(current_setting(…, true), '')` guard turns "nobody said which tenant" into zero rows, not all rows); and the GUC is **per-connection state** — exactly the shape of 04.4's thread-local bleed, one layer down, with the same cure: scope it to the unit of work (`SET LOCAL`, dying with its transaction), never to the shared carrier.

**What no database mechanism replaces:** authorisation *within* the tenant — which agent may see internal notes, who may merge tickets — stays application logic (module 08), and per-object checks against the *caller's* tenant remain the service layer's job. RLS bounds the blast radius of those bugs; it does not make them correct.

### Mental Model

> `tenant_id` is not a column; it is a **dimension** — every key, every index, every constraint and every query plan acquires it. And isolation is a ladder, not a feature: conventions stop nothing by themselves, application checks stop the paths that run them, **composite FKs stop every cross-tenant write, RLS stops every unscoped read** — and each rung exists because the one below it has a failure class it cannot see. The pool model is safe exactly as high as you climb.

## How It Works

**The write the launch schema cannot refuse** — Deskhub's merge tool, handed a source ticket id from the wrong tenant (`_lab/lab_05_04_tenancy.py`):

```text
move Nordwind #212's comments onto Baltic #212 : UPDATE 2   <- no error
  Baltic's ticket #212 now shows: 'internal: Nordwind renewal - propose 8% uplift'  (INTERNAL NOTE)
author-vs-ticket tenant audit finds            : 2 contaminated comments
```

The plain FK held — both rows point at a real ticket. Nothing else was asked. Note also the *detector*: with tenant-blind comments, contamination is only visible through an independent signal — the comment's **author** belongs to Nordwind while the ticket belongs to Baltic. That join is the audit query, and it is the only tool that can even measure the blast radius.

**The same write, after the composite FK** — installed with 05.3's live-table discipline (backfill, `NOT VALID`, `VALIDATE`):

```text
repair (audit-guided move back)         : audit now finds 0
backfill + UNIQUE(tenant_id, id) + composite FK (NOT VALID -> VALIDATE): ok
the same hostile merge UPDATE -> ForeignKeyViolationError,
                                 constraint_name='fk_comments_tenant_ticket'
```

The application bug that caused the incident is *still there* at this point in the lab — and it no longer matters at the data layer: the schema refuses what the endpoint failed to. That is what "defence in depth" means when it is not a slogan: the layers fail independently.

**The read floor, and its three mines**, captured in sequence:

```text
policy + FORCE, queried as the compose user : count(*) = 15,000  <- SUPERUSER: policies
                                                                    never apply, FORCE or not
as deskhub_app, GUC never set               : count(*) = 0       <- fail CLOSED, not open
as deskhub_app, tenant set, no WHERE        : count(*) = 5,000
INSERT a row FOR ANOTHER TENANT             : new row violates row-level security policy
```

Read the first line twice: the policy existed, `FORCE` was on, and the query saw everything — because the lab's compose user is a superuser, and **no policy applies to superusers, ever**. RLS is a floor only for the role that stands on it, which is why the canon below adds `deskhub_app`: a plain login role with table grants and nothing else. The remaining lines are the floor working: an unset tenant yields *zero* rows (the `NULLIF` guard — a blank GUC that cast `''::uuid` would instead error on every query, and a policy comparing against NULL simply matches nothing), a set tenant scopes a completely unscoped `count(*)`, and `WITH CHECK` polices the write direction too.

**The bleed** — one server connection serving two logical requests, which is every transaction-pooling proxy's normal day (05.9):

```text
request 1 (nordwind, session SET): 5,000 rows
request 2 (NEVER set a tenant)   : 5,000 rows   <- sees NORDWIND
SET LOCAL inside txn             : 5,000 rows during, 0 after commit
asyncpg pool, release + reacquire: current_setting = ''   <- the pool's RESET ALL saved us
```

Session-level `SET` outlives the request that issued it — request 2 inherited Nordwind's scope without ever asking, which is 04.4's last-writer-wins bleed re-materialised as database state. asyncpg's own pool happens to rescue you (`RESET ALL` on release); PgBouncer in transaction mode will not, because session state and transaction-pooled connections are fundamentally incompatible. `SET LOCAL` inside the transaction is the only shape that composes with every pooler — the 04.4 rule (scope state to the flow, not the carrier) applied to connections.

**And the price of the floor**, which is where 02.5's index rule pays out:

```text
Index Scan using ix_tickets_tenant_activity on tickets (actual time=0.019..0.033 rows=50)
  Index Cond: (tenant_id = (NULLIF(current_setting('app.tenant_id', true), ''))::uuid)
Execution Time: 0.062 ms
```

The policy predicate is folded into the plan as an ordinary qualifier and lands in the **Index Cond**, because every Deskhub index leads with `tenant_id`. RLS on tables whose indexes do not lead with the tenant becomes a per-query sequential filter — the security floor priced as a performance incident.

## Code Example

The canon migration — geometry first, floor second, role third:

```sql
-- deskhub/schema.sql (05.4 additions)  — live-table discipline per 05.3 throughout
ALTER TABLE comments    ADD COLUMN tenant_id uuid;
ALTER TABLE attachments ADD COLUMN tenant_id uuid;
UPDATE comments    c SET tenant_id = t.tenant_id FROM tickets  t WHERE t.id = c.ticket_id;
UPDATE attachments a SET tenant_id = c.tenant_id FROM comments c WHERE c.id = a.comment_id;
ALTER TABLE comments    ALTER COLUMN tenant_id SET NOT NULL;
ALTER TABLE attachments ALTER COLUMN tenant_id SET NOT NULL;

-- The referenceable pairs, then the geometry: cross-tenant references become
-- unrepresentable for comments, attachments AND assignment.
ALTER TABLE tickets  ADD CONSTRAINT uq_tickets_tenant_id_id  UNIQUE (tenant_id, id);
ALTER TABLE comments ADD CONSTRAINT uq_comments_tenant_id_id UNIQUE (tenant_id, id);
ALTER TABLE agents   ADD CONSTRAINT uq_agents_tenant_id_id   UNIQUE (tenant_id, id);

ALTER TABLE comments ADD CONSTRAINT fk_comments_tenant_ticket
    FOREIGN KEY (tenant_id, ticket_id)  REFERENCES tickets (tenant_id, id) NOT VALID;
ALTER TABLE attachments ADD CONSTRAINT fk_attachments_tenant_comment
    FOREIGN KEY (tenant_id, comment_id) REFERENCES comments (tenant_id, id) NOT VALID;
ALTER TABLE tickets ADD CONSTRAINT fk_tickets_tenant_assignee
    FOREIGN KEY (tenant_id, assignee_id) REFERENCES agents (tenant_id, id) NOT VALID;
-- VALIDATE each after the audit runs clean (05.3's two-step).
```

The assignment FK deserves its sentence: it makes "ticket assigned to another tenant's agent" — a bug class no test suite thinks to write — unrepresentable in the same stroke. Then the floor and the role:

```sql
-- RLS on every tenant-scoped table; FORCE so even the owner obeys.
ALTER TABLE tickets ENABLE ROW LEVEL SECURITY;
ALTER TABLE tickets FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON tickets
    USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
-- (same pair on comments, attachments, agents, ticket_counters)

-- The runtime role: NOT the owner, NOT a superuser - policies only exist for it.
CREATE ROLE deskhub_app LOGIN PASSWORD :app_password;
GRANT USAGE ON SCHEMA public TO deskhub_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO deskhub_app;
```

Migrations keep running as the owning role; the *application* connects as `deskhub_app` — the split every production system needs anyway (14.x wires it; 16.10 owns the secrets). And the application's half of the contract, one helper the whole service layer goes through:

```python
# deskhub/db.py — the only way request code gets a connection
@asynccontextmanager
async def tenant_scope(pool: asyncpg.Pool, tenant_id: TenantId) -> AsyncIterator[Connection]:
    """One transaction, scoped to one tenant, on the app role.

    SET LOCAL, never SET: the GUC dies with the transaction, so a pooled or
    proxied connection can never carry this tenant into the next request
    (04.4's bleed, measured at this layer in the lab). set_config with a
    parameter also keeps the tenant id out of SQL strings."""
    async with pool.acquire() as conn, conn.transaction():
        await conn.execute(
            "SELECT set_config('app.tenant_id', $1::text, true)", str(tenant_id))
        yield conn
```

The queue query that started the module now reads almost bare — the floor supplies the tenant, the app supplies intent — though Deskhub's canon keeps explicit `WHERE tenant_id = $1` in repository queries *as well*: the redundancy costs one predicate and means a single failure (a route that forgot the scope helper, a policy dropped in a migration) is still not a leak. Belt, braces, and the audit query from How It Works as the nightly invariant over both.

> **Version note** — captured on PostgreSQL 18.6 via the module compose stack. RLS, `FORCE ROW LEVEL SECURITY` and `current_setting(name, missing_ok)` are stable since 9.5/9.6; asyncpg's pool reset behaviour (`RESET ALL` on release) is asyncpg's default and not something transaction-pooling proxies replicate. Reproduce with `_lab/lab_05_04_tenancy.py`.

## Design Patterns / Tradeoffs

### Pool vs bridge vs silo

| | Pool (shared schema) — Deskhub | Bridge (schema/tenant) | Silo (DB/tenant) |
|---|---|---|---|
| Isolation | Logical: constraints + RLS (this notebook) | Namespace | Physical |
| Migrations (06.12) | Once | × N schemas, partial-failure states | × N databases |
| Connections (05.9) | One pool | `search_path` per conn — poisons transaction pooling | Pool per tenant — explodes |
| Noisy neighbour | Shared everything; quotas at the edge (02.12) | Shared instance | Contained |
| Per-tenant restore (05.18) | Hard (row-level extract) | pg_dump a schema | Trivial |
| Cross-tenant analytics | One query | UNION over N | ETL |
| Scale shape | Millions of small tenants | Hundreds | Tens, or compliance |

**Recommendation:** pool by default — it is the only shape whose operational costs stay flat as tenant count grows — with the **hybrid escape hatch** designed in from day one: the largest or regulated tenant can graduate to a silo later *only if* nothing in the schema assumes single-database (no cross-tenant FKs — which the pool model shouldn't have anyway — and tenant-scoped natural keys, which 05.1 already made canon). Bridge is the tempting middle that combines both sets of problems; it earns its keep mainly where per-tenant restore is a contractual promise.

### The enforcement ladder, honestly

| Rung | Stops | Cannot stop |
|---|---|---|
| Convention ("always filter") | Nothing by itself | Everything |
| Repository helpers + review | Forgotten scopes on paths that use them | New paths, raw SQL, tooling |
| App-level authz (08) | Wrong *caller* access | Bugs in itself; unchecked ids (the incident) |
| **Composite FKs** | Every cross-tenant **write**, all paths, forever | Reads |
| **RLS + app role** | Every unscoped **read**; wrong-tenant writes at the row filter | Superuser sessions; logic bugs within a tenant |
| Silo | Nearly everything | Cost, ops multiplication |

RLS's real costs, stated: the `SET LOCAL` ceremony on every transaction (one round trip; batch it with `set_config` in the opening statement); policies apply only to non-privileged roles (the lab's 15,000-row lesson); testability demands the app role in CI, not the owner; and the planner treats the policy as a qual — leading-`tenant_id` indexes or the floor becomes a per-query scan. When a service is genuinely single-tenant-per-deployment, skip RLS; when it is a pool, the two schema mechanisms are the cheapest insurance in this module — the composite FKs in particular cost *nothing* at read time and closed the incident's entire class.

## Production Scenario

**Deskhub, Tuesday 5 January, 11:20.** An agent at Baltic Freight — a twelve-person startup tenant — screenshots ticket #212 to their account manager: four comments they never wrote, authored by names nobody recognises, one flagged as an internal note and discussing *"Nordwind renewal — propose 8% uplift"*. Nordwind Logistik is Deskhub's largest tenant. This is a cross-tenant confidentiality breach, visible to the wrong customer, with commercial terms in it. Legal is in the thread by 11:40.

### Symptoms

- Baltic's ticket #212 displays comments whose `author_agent_id` resolves to Nordwind agents. Every query involved is correctly tenant-scoped — the *data* crosses tenants, so scoped queries faithfully serve the leak.
- Nordwind's own ticket #212 has lost the same four comments; their agent had filed it as "comments disappeared, probably a glitch" an hour earlier.
- The audit trail (04.4's discipline) shows the comments' `ticket_id` changed at 10:52 by an agent using the **ticket-merge tool**, shipped in late November for de-duplicating email threads.
- No errors anywhere, at any layer, at any time.

### Diagnosis

1. **Alert → the row.** No alert could exist: rows are individually valid and every read is scoped. The screenshot is the detector. Fetching the four comments confirms the impossible-by-intent state: comment author's tenant ≠ ticket's tenant.
2. **The write path.** The audit trail names the merge tool. Its handler loads the *destination* ticket through the tenant-scoped service (correct), then passes the client-supplied *source* ticket id straight into the repository's `UPDATE comments SET ticket_id = :dst WHERE ticket_id = :src` — the unchecked-parent-id shape 02.1 flagged in URI design, now in a write path. The agent had pasted a ticket id from an email that happened to reference *Nordwind's* #212; ids travel (URLs, emails, screenshots), and nothing at any layer asked whose ticket it was. Unguessability is not authorisation.
3. **Blast radius.** The author-vs-ticket audit join, fleet-wide: **9 contaminated merges since the tool launched** (214 merges total), across 5 tenant pairs; 2 involve internal notes. Seven of the nine had produced "comments vanished" support tickets that were closed as unreproducible — 04.6's October pattern again: the losers' evidence was there all along, unjoined.
4. **Eliminated:** RLS-style read leaks (queries all scoped — confirmed by log sampling), the import pipeline (untouched since December), and malice (the agent's paste is on the audit trail, innocent).

### Root Cause

A cross-tenant reference was representable, so one unchecked identifier made it real: the merge endpoint verified the destination ticket's tenant but not the source's, and the tenant-blind `comments.ticket_id` FK accepted the move — after which every correctly-scoped query in the product served Nordwind's internal pricing note to Baltic Freight. Per-query discipline cannot stop a write whose *values* are cross-tenant; only the schema can.

### Fix

*Mitigation (12:05):* the audit query drives the repair — all 9 contaminated merges reversed by moving comments back to their authors' tenants' tickets; Baltic's cached ticket page purged; disclosure prepared for the five affected tenant pairs (what was visible, to whom, for how long — answerable *only* because authorship made contamination joinable).

*Permanent fix, in ladder order:* the merge endpoint verifies both tickets against the caller's tenant (the app rung — necessary, insufficient); then the schema rung from the Code Example, staged with 05.3's discipline — `tenant_id` backfilled onto comments and attachments in batches, composite FKs added `NOT VALID`, audit re-run clean, `VALIDATE`d over the weekend. The same hostile UPDATE now dies with `fk_comments_tenant_ticket` regardless of any future endpoint's bugs. RLS + `deskhub_app` rolls out the following sprint as the read floor — not because a read leak happened, but because the incident review asked "what is the *read* twin of this?" and nobody liked the answer.

### Prevention

- **The audit joins the nightly invariants** (05.2's family): author-tenant vs ticket-tenant mismatches must be zero — the only detector this class had, now standing watch with an alert instead of waiting for a screenshot.
- **The incident closes into a named CI test** — hostile by construction, on the app role:

```python
# tests/tenancy/test_cross_tenant_references_are_unrepresentable.py
async def test_merge_cannot_move_comments_across_tenants(app_db, two_tenants):
    """Nordwind's renewal note surfaced on Baltic's ticket via one unchecked id
    (5 Jan). The schema, not the endpoint, is the guarantee (05.4)."""
    nordwind_ticket, baltic_ticket = two_tenants.tickets
    with pytest.raises(asyncpg.ForeignKeyViolationError) as err:
        await app_db.execute(              # the repository's own UPDATE, hostile args
            "UPDATE comments SET ticket_id = $1 WHERE ticket_id = $2",
            baltic_ticket, nordwind_ticket)
    assert err.value.constraint_name == "fk_comments_tenant_ticket"

async def test_unscoped_read_returns_zero_rows_without_a_tenant(app_db):
    assert await app_db.fetchval("SELECT count(*) FROM tickets") == 0   # RLS floor
```

- **A schema lint**: every table with `tenant_id` must have (a) it leading every index, (b) an RLS policy pair, (c) composite FKs to every tenant-scoped parent — three greppable properties, failing CI on the next table someone adds without them.
- **CI runs as `deskhub_app`**, never as the owner: a test suite on a policy-exempt role certifies a floor nobody is standing on (the lab's 15,000-row capture, institutionalised).

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a query forgets its tenant filter? | RLS returns the current tenant's rows anyway — provided the session set a tenant and the role is not privileged. That is the floor's whole job. |
| ...a write carries another tenant's foreign key? | The composite FK refuses it, from every path (measured: the merge UPDATE dies by constraint name). App checks are the first rung, never the last. |
| ...the GUC is never set? | Zero rows (fail closed), because the policy NULL-guards the setting. A policy that errors or defaults open on a blank GUC is a leak with a delay. |
| ...the app connects as the owner or a superuser? | Policies silently do not apply (measured: 15,000 rows through FORCE). The runtime role is a plain login role; migrations keep the owner. |
| ...a connection is shared by a pooler? | Session `SET` bleeds tenant scope into the next request (measured). `SET LOCAL` per transaction is the only composable shape; driver-pool resets are a bonus, not a contract. |
| ...a tenant must move to its own database? | The pool model graduates a tenant cleanly only if no cross-tenant FKs exist and all natural keys are tenant-scoped — both canon since 05.1. Design the exit before you need it. |
| ...two tenants merge? | An export/import migration, by decision — never `UPDATE … SET tenant_id`, which would fight every composite FK and rewrite history (05.2's snapshot lesson at tenant scale). |
| ...an id leaks in a URL, email or screenshot? | It will. Unguessable ids are not access control (02.1); the question is what refuses the id when it comes back from the wrong tenant. |

## Common Pitfalls

**Trusting per-query discipline as the isolation story.** It is rung one, and the incident happened on a *write*, where reads-side discipline never looked. *Instead:* composite FKs for writes, RLS for reads, app checks for semantics.

**Tenant-blind child tables.** `comments.ticket_id REFERENCES tickets(id)` asks "is this a ticket?", never "whose?". *Instead:* `tenant_id` on every scoped table — including grandchildren — and composite FKs all the way down.

**RLS certified by the wrong role.** Tests (and psql sessions) as the owner or a superuser see everything and prove nothing. *Instead:* the app role in CI; `FORCE` for owners; superuser sessions treated as production access events.

**Session-level `SET` for the tenant.** Composes with nothing that shares connections; the bleed is 04.4's, measured here. *Instead:* `SET LOCAL` via `set_config(..., true)` inside the transaction, in one shared helper.

**A policy that fails open or fails loud on a blank GUC.** `current_setting('app.tenant_id')` without `missing_ok` errors every query; `''::uuid` errors too. *Instead:* the `NULLIF(current_setting(…, true), '')::uuid` shape — blank means zero rows.

**Indexes that don't lead with `tenant_id`.** The policy qual becomes a filter instead of an Index Cond, and the floor becomes a seq-scan tax (contrast the measured 0.062 ms). *Instead:* the 02.5/05.2 rule is now also a security-performance rule.

**Reaching for schema-per-tenant "for isolation".** You inherit N× migrations and a `search_path` fight with transaction pooling, while the isolation you wanted was two constraints away in the pool model. *Instead:* pool + this notebook's ladder; bridge only for contractual per-tenant restore.

## How to Test This

- The two hostile tests above — the FK refusal (by constraint name) and the zero-rows floor — run as `deskhub_app` against the assembled schema.
- The nightly author-vs-ticket audit as a standing invariant, alerting above zero (it found the blast radius; keep it found).
- The schema lint: `tenant_id` present, leading every index, policy pair present, composite FKs present — parametrised over every tenant-scoped table so the next table inherits the checks.
- A bleed test: two sequential logical requests on one pooled connection, second without a tenant — assert zero rows, pinning the `SET LOCAL` discipline against a future "optimisation".

2. *Explain.* What does a composite FK give you that application checks cannot? — All-paths, all-futures write refusal: the cross-tenant pair cannot exist in the child, so the bug class is unrepresentable rather than untested.
3. *Debug this.* One tenant's internal notes appear on another tenant's ticket; every read query is correctly scoped; no errors. — A cross-tenant *write*: find the writer via the audit trail, measure blast radius via an author-vs-owner join, fix the endpoint, then make the reference unrepresentable.
4. *Explain.* Three ways RLS silently protects nothing. — Privileged role (superuser always; owner without FORCE), fail-open handling of an unset GUC, and testing/certifying as an exempt role.
5. *Design.* Tenant scoping under PgBouncer transaction pooling. — `SET LOCAL` via `set_config` at transaction start from the authenticated principal; no session state ever; policies NULL-guarded; app role non-privileged.

7. *Design.* A regulated tenant demands physical isolation next year. What must be true of today's schema? — No cross-tenant references, tenant-scoped natural keys, tenant-keyed sequences/counters — i.e., the pool model kept graduation-ready (05.1/05.3 canon).

## Key Takeaways

- `tenant_id` is a **dimension**: on every scoped table (grandchildren included), leading every index, inside every unique constraint — canon since 05.1, now load-bearing for security.
- Isolation is a **ladder**; each rung stops a class the others miss. The two schema rungs are the ones application code can never match: **composite FKs make cross-tenant writes unrepresentable** (measured: the incident's UPDATE dies by constraint name), **RLS makes unscoped reads return the right rows anyway**.
- RLS has three mines, all measured: privileged roles bypass everything (run as a plain app role; FORCE for owners), a blank GUC must mean *zero* rows, and the GUC is connection state — `SET LOCAL` per transaction is the only shape that survives poolers.
- The read floor is cheap only because the indexes already lead with the tenant: the policy qual lands in the Index Cond (0.062 ms measured).
- Unguessable ids are not authorisation — they leak by design (URLs, emails, screenshots), and the schema must refuse them when they return from the wrong tenant.
- Contamination has no error signal; only an independent join (author-tenant vs owner-tenant) can see it. Ship the audit as a nightly invariant, not an incident tool.
- Keep the pool model **graduation-ready**: no cross-tenant references and tenant-scoped keys mean your biggest tenant can silo later without a rewrite.
