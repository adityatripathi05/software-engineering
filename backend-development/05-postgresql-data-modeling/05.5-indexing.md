## Concept

### Plain-English Explanation

The module has been writing IOUs against this notebook since 02.6 declared every sortable field "an index commitment". Time to define the commitment precisely. An index is **a sorted copy of some of your columns** — nothing more mystical than that — and 05.2's vocabulary applies to it exactly: it is *derived data*, with the strongest possible writer (the database maintains it inside every transaction) and the strongest possible auditor (it cannot drift). What 05.2 taught about copies still holds: the copy costs every write, forever, and is only worth keeping if reads by its shape repay that cost.

The read side of the bargain is a logarithm. A **B-tree** keeps its sorted entries in a shallow tree of 8 KiB pages — for Deskhub's 410k tickets, a root, one inner level, and leaves — so finding one key means reading three or four pages instead of thousands (measured below: `Buffers: shared hit=4`). Every index question in this notebook reduces to one form: *can the query's shape ride that sorted order all the way to its answer, or does it have to read broadly and throw rows away?* The throwing-away has a name in every plan — **`Rows Removed by Filter`** — and that counter, times the buffer count next to it, is the diagnosis of nearly every slow list query you will ever meet, including this notebook's incident.

### Technical Explanation

**How a composite index answers queries.** An index on `(tenant_id, assignee_id, last_activity_at DESC)` is a phone book sorted by last name, then first name, then date. Three consequences fall out of the sort order:

- **Equality on a prefix narrows to a contiguous run**: `tenant = X AND assignee = Y` lands the scan on exactly the block of entries for that pair — and because the third column is sorted within the pair, `ORDER BY last_activity_at DESC LIMIT 50` is satisfied by *reading the first fifty entries*, no sort node at all.
- **The column-order rule** follows: **equality predicates first, then the range or sort column, last**. Put the sort column before an equality column and the equalities degrade into filters over a wide scan — which is precisely the incident.
- **The leftmost-prefix rule**: without a predicate on the leading column, the contiguous-run property is gone. (PostgreSQL 18 softens this with a **skip scan** — measured below — which probes once per distinct leading value; a rescue at 3 tenants, a multiplication at 30,000.)

**Partial indexes** add a `WHERE` clause to the index itself: `… WHERE status IN ('open','pending')` indexes only the working set. For Deskhub — where ~80% of tickets are closed forever — that is a 7.5 MiB index instead of 19.8 MiB (measured), hotter in cache, cheaper on writes to closed tickets, and it *encodes the query's predicate*, so only queries carrying a matching condition can use it. A partial index is the database-side twin of 02.5's "cap the page in the contract": put the boundary where the data is, not in every caller's discipline.

**Index-only scans** serve a query entirely from the index when every referenced column is in it (key columns, or `INCLUDE`d payload columns). The trap is the word *only*: index entries carry no visibility information (who can see this row — 05.11's MVCC story), so the scan must consult the **visibility map**, and any page not marked all-visible forces a **heap fetch** anyway. Measured below: the same query does 3,526 heap fetches right after an update burst and 0 after `VACUUM`. Index-only performance is a vacuum promise, not an index property.

**What disqualifies an index silently.** Indexes match **expressions, not intentions**: `lower(email)` is a different expression than `email`, so the plain index degrades to prefix-scan-plus-filter (measured: 133k rows removed per worker). The fix is an expression index on `lower(email)` — or better, normalising at write time so the question never needs the function (05.3's conventions). The same blindness applies to `date_trunc(...)`, concatenations, and casts; 02.6 already covered the leading-wildcard `LIKE`.

**The write bill, mechanically.** Every index is one more sorted structure to update per affected row — and there is a cliff hidden in it: a **HOT update** (heap-only tuple) rewrites a row *without touching any index*, but it is only possible when the update changes **no indexed column** (and the page has room — hence `fillfactor` below 100 on update-heavy tables, now Deskhub canon). Index a column you update and every one of those updates starts writing index entries: measured, 20k `priority` updates went from 8,585 HOT / 2.2 s / 39 MiB WAL to **0 HOT / 5.0 s / 49 MiB** the moment `priority` gained an index nobody queries. 05.1 priced the key's geometry; this is the same lesson generalised: *indexes are where writes go to pay for reads*.

### Mental Model

> An index is **a bet, placed once and paid on every write**: that reads of this exact shape — these equality columns, this sort — will outnumber and outweigh the writes that maintain it. `Rows Removed by Filter` is the sound of a query paying retail because nobody placed its bet; `idx_scan = 0` is the sound of a bet nobody collects. Both numbers are on the table; read them.

## How It Works

**The incident's shape, side by side** (`_lab/lab_05_05_indexing.py`, Nordwind at 400k tickets). The inbox query — `WHERE tenant AND assignee AND status IN ('open','pending') ORDER BY last_activity_at DESC LIMIT 50` — with only the general activity index to ride:

```text
-- busy agent (thousands of open tickets):
Index Scan using ix_tickets_tenant_activity   (actual time=0.133..9.855 rows=50)
  Filter: status IN (...) AND assignee_id = ...
  Rows Removed by Filter: 2,925          Buffers: shared hit=3004
Execution Time: 9.994 ms

-- sparse agent (3 open tickets):
Index Scan using ix_tickets_tenant_activity   (actual time=790.6..793.2 rows=3)
  Rows Removed by Filter: 399,997        Buffers: shared hit=402986
Execution Time: 793.229 ms
```

Read the asymmetry carefully, because it is the whole incident. The planner walks the tenant's tickets newest-first and filters; it may stop at fifty matches. For a busy agent, fifty matches arrive within ~3,000 rows — 10 ms, fine in every test. For a sparse agent the matches *never arrive*: the scan walks all 400k index entries and 402,986 buffers to return three rows. **The cost of this plan is inversely proportional to how much matching data exists** — the emptier your queue, the more the database works to prove it — and no fixed-size test dataset surfaces it, because the villain is a *distribution*, not a volume.

**The purpose-built index**, applying both design rules at once:

```text
CREATE INDEX CONCURRENTLY ix_tickets_inbox
    ON tickets (tenant_id, assignee_id, last_activity_at DESC NULLS LAST)
    WHERE status IN ('open','pending');
-- built in 0.66s with no write lock; 7.5 MiB vs the full index's 19.8 MiB

-- sparse agent, after:
Index Scan using ix_tickets_inbox   (actual time=0.019..0.023 rows=3)
  Index Cond: (tenant_id = ... AND assignee_id = ...)
  Buffers: shared hit=5
Execution Time: 0.048 ms
```

793 ms to 0.048 ms — four orders of magnitude — and the deeper change is qualitative: every predicate moved from `Filter` (read, then discard) into `Index Cond` and the partial-`WHERE` (never read at all). The query stopped searching and started reading its answer.

**The leftmost rule, and its PostgreSQL 18 asterisk** — the same composite index, queried without its leading column:

```text
Index Scan using ix_tickets_inbox
  Index Cond: (assignee_id = ...)
  Index Searches: 5                      <- PG18 SKIP SCAN: one descent per
                                            distinct leading value (3 tenants)
```

Older releases would refuse this index outright; 18 probes it once per distinct `tenant_id`. With three tenants that is a rescue; with thirty thousand it is thirty thousand descents wearing an index scan's clothes. The design rule — lead with what you always filter by — survives its own exception, and `Index Searches` is the tell when skip scan is quietly saving (or drowning) you.

**The visibility-map dependency**, measured on an index-only scan straight after a 40k-row update burst, then after `VACUUM`:

```text
right after updates:  Heap Fetches: 3526    Execution Time: 25.768 ms
after VACUUM:         Heap Fetches: 0       Execution Time: 0.706 ms
```

## Code Example

The canon additions, and the discipline for shipping them:

```sql
-- deskhub/schema.sql (05.5 additions)

-- The agent-inbox index: equality columns first, sort column last, working set
-- only. This is THE query shape of the product; it gets a purpose-built index.
CREATE INDEX CONCURRENTLY ix_tickets_inbox
    ON tickets (tenant_id, assignee_id, last_activity_at DESC NULLS LAST)
    WHERE status IN ('open', 'pending');

-- Requester history ("all tickets from this email") - normalised at write time
-- (05.3), so the index matches the stored expression:
CREATE INDEX CONCURRENTLY ix_tickets_tenant_requester
    ON tickets (tenant_id, requester_email);

-- Update-heavy tables leave HOT headroom (measured in the lab: F):
ALTER TABLE tickets SET (fillfactor = 90);
```

⚠️ `CREATE INDEX CONCURRENTLY` is the only acceptable spelling on a live table, and it has two sharp edges worth knowing before 03:00: it cannot run inside a transaction (so it gets its own migration step — 06.12), and **a failed build leaves an `INVALID` index behind** — visible in `\d` and `pg_index.indisvalid`, still taxing writes, serving nothing. The runbook line is: on failure, `DROP INDEX CONCURRENTLY` the corpse and re-run. The plain `CREATE INDEX` takes a lock that blocks every write for the duration of the build — the incident's first responder measured that the hard way.

The governance that keeps the bet-book honest — 02.6's registry rule, now generalised into CI:

```python
# tests/schema/test_list_queries_ride_their_indexes.py
LIST_QUERY_SHAPES = [   # every list endpoint registers its shape here (02.6's registry)
    ("inbox", INBOX_SQL, {"max_filtered": 100}),
    ("requester_history", REQUESTER_SQL, {"max_filtered": 100}),
    ("queue_awaiting_reply", QUEUE_SQL, {"max_filtered": 100}),
]

@pytest.mark.parametrize("name,sql,budget", LIST_QUERY_SHAPES)
async def test_shape_has_a_bounded_plan(db_at_scale, name, sql, budget):
    """793ms and 402,986 buffers hid behind a query that averaged 10ms (18 Jan).
    Run each registered shape against the scale seed with a WORST-CASE parameter
    (sparse agent, rare requester) and assert the plan discards almost nothing."""
    plan = await explain_json(db_at_scale, sql, worst_case_params(name))
    assert rows_removed_by_filter(plan) <= budget["max_filtered"], (
        f"{name}: the plan filters instead of seeking - index and query no longer "
        f"agree (05.5)")
```

Two details carry it: the test runs against the **scale seed** (the lab's 400k-ticket shape, not a ten-row fixture), and it parameterises for the **worst case** — the sparse agent, not the busy one — because that is the case averages hide. `Rows Removed by Filter` as a CI budget turns "the index matches the query" from a review opinion into an assertion.

> **Version note** — captured on PostgreSQL 18.6 via the module compose stack. B-tree **skip scan** (`Index Searches` > 1 without a leading-column predicate) is new in 18; on 17 and earlier the no-leading-column query simply cannot use the index, which only strengthens the leading-column rule. `EXPLAIN`'s `Index Searches` line is also an 18 addition. Reproduce with `_lab/lab_05_05_indexing.py`.

## Design Patterns / Tradeoffs

### Purpose-built vs general indexes

- **A few general indexes** (`(tenant_id, last_activity_at)` serving everything): fewest objects, lowest write tax, and every query that isn't the general shape pays in `Filter` — tolerably for dense matches, catastrophically for sparse ones (measured: 10 ms vs 793 ms on the *same plan*). *Use for:* the default sort, genuinely shared shapes.
- **Purpose-built per query shape** (this notebook's inbox index): each hot list endpoint seeks its exact answer; the cost is one more write-taxed object per shape, and index-count creep. *Use for:* the product's few defining queries — the ones in the CI registry. The registry is also the cap: a shape not worth registering is not worth an index.
- **Partial over full** whenever the query always carries the predicate: smaller, hotter, cheaper on the excluded rows' writes (measured 7.5 vs 19.8 MiB). The cost is coupling — widen the status vocabulary (05.3) without widening the index's `WHERE`, and the index silently stops matching new rows' queries. The pairing rule: the partial predicate and the query predicate live next to each other in the registry.
- **Covering (`INCLUDE`) columns** buy index-only scans for the cost of a fatter index and more non-HOT updates — and only pay out under a healthy vacuum (measured: heap fetches 3,526 → 0). *Use when* a hot query reads exactly two or three columns; not as a reflex.

### Beyond B-tree, in one honest table

| Type | Answers | Deskhub use |
|---|---|---|
| **B-tree** | `=`, ranges, `ORDER BY`, uniqueness | Everything so far — the default, ~always right for scalars |
| **GIN** | "contains": arrays, JSONB, full-text, trigram | Tags, custom fields, search — 05.8 and 05.15 own it |
| **BRIN** | Ranges over physically-ordered huge tables | Append-only event/audit tables — 05.17's partitioned NMS alarms |
| **GiST** | Geometric/overlap; `EXCLUDE` constraints | The no-overlapping-shifts shape (05.3's EXCLUDE mention) |
| **Hash** | `=` only | Effectively never — B-tree does `=` and everything else |

**Recommendation:** B-tree until a predicate literally cannot be expressed as one ("contains", "overlaps", "near") — then the table above names the tool, and its own notebook prices it.

### When *not* to index

Small tables (the planner will rightly seq-scan a 3-page table whatever you build); low-selectivity columns alone (`status` by itself narrows 400k rows to 80k — that is a filter, not a seek; it earns a place *inside* composite or partial indexes, never solo); and write-hot columns whose queries are rare — the measured F trade: 2.3× slower updates and +25% WAL for an index with `idx_scan = 0`. That last shape is common enough to deserve its own audit, which is the hygiene section of the lab: `pg_stat_user_indexes`, monthly, dropping unscanned **non-unique** indexes with `DROP INDEX CONCURRENTLY` — and leaving unique ones alone until checked, because a unique index at zero scans may be doing constraint work (05.4's `uq_tickets_tenant_id_id` backs three composite FKs and will *never* show scans).

## Production Scenario

**Deskhub, Monday 18 January, 09:07.** European helpdesks share a rhythm: Monday morning is the week's traffic peak, agents triaging the weekend's backlog with inbox views auto-refreshing every 30 seconds. This Monday, the database CPU alert fires at 09:07 — 97% and pinned — and p95 across the product climbs from 60 ms to 2.8 s. Every tenant is affected: the database is a shared resource, and something is eating it (02.2's shape).

### Symptoms

- `pg_stat_statements` (05.7 owns the tool; the on-call knows the query) ranks one normalised statement first by total time: the agent-inbox query, ~90 calls/s (refresh storm), **mean 210 ms** — against a dashboard history of ~8 ms.
- The variance is the anomaly: p50 is 9 ms, p99 is **1.9 s**. The slow calls correlate not with load, not with tenant size, but with *which agent* — and the slowest agents are team leads and part-timers with nearly empty queues.
- Buffer reads per call for the slow cohort: ~400k (`# illustrative - not captured output`; the lab's 402,986 is the same mechanism at capture scale). The buffer cache is being churned by inbox refreshes, degrading every other query's hit ratio — the fleet-wide p95 is collateral, not cause.
- Nothing changed this weekend. Nordwind's history import finished in December; ticket volume crossed 400k quietly. **The distribution grew into the plan.**

### Diagnosis

1. **Alert → the statement.** CPU + `pg_stat_statements` gives the query in two minutes. `EXPLAIN (ANALYZE, BUFFERS)` with a *fast* agent's id shows a healthy-looking plan — 10 ms, 3k buffers. The trap: diagnosing with a convenient parameter. Re-run with a slow cohort agent: **`Rows Removed by Filter: 399,997`**, 402,986 buffers. The two plans are *identical*; only the data's distribution differs — the scan runs until it finds 50 matches, and for sparse agents there aren't 50 to find.
2. **Why now.** The plan was always O(scan-until-50-matches). At 40k tickets the worst case was 40k rows — 15 ms, invisible. At 400k it is 400k rows — 800 ms — and Monday's refresh storm multiplies it by ninety calls a second. No regression, no deploy: a linear cost curve crossed a visibility threshold (03.6's "nothing changed; the traffic did", data edition).
3. **The first fix makes it worse (09:31).** The on-call creates the obvious index — `CREATE INDEX ix_inbox ON tickets (tenant_id, assignee_id, last_activity_at DESC)` — *without* `CONCURRENTLY`. The build queues behind a long-running report transaction, and every ticket write in the fleet queues behind the build's lock: 40 seconds of frozen writes and a spike of 03.5-style timeouts before the statement is cancelled. The lesson is now muscle memory: **on a live table, index DDL is `CONCURRENTLY` or nothing.**
4. **Eliminated:** a bad plan flip (the plan is stable — it is simply the only plan available), stale statistics (`ANALYZE` changes nothing; estimates were never the problem), and vacuum debt (heap fetches are not the dominant term here).

### Root Cause

The inbox query's shape (two equalities, a status predicate, an activity sort) had no index of its own; it rode the general `(tenant_id, last_activity_at)` index and filtered. That plan's cost is inversely proportional to the density of matching rows, so it punished exactly the agents with the least work, grew linearly with the tenant's history, and detonated under Monday's refresh concurrency — pinning shared CPU and cache, and degrading every tenant. The failed emergency fix added a write freeze on top, by building the index with the blocking DDL form.

### Fix

*Mitigation (09:44):* the refresh interval on inbox views is bumped 30 s → 120 s via feature flag (14.16's machinery), shedding three quarters of the storm; CPU falls to 60%, the product breathes.

*Permanent fix (09:58):* `ix_tickets_inbox` from the Code Example — equality columns first, sort last, partial on the open/pending working set — built with `CONCURRENTLY` in 0.66 s (lab scale; ~4 min at production scale, `# illustrative - not captured output`), plus the `INVALID`-corpse cleanup from the aborted 09:31 attempt. The sparse-agent worst case drops from ~800 ms to sub-millisecond (the lab's 793 → 0.048 ms is the same fix at capture scale); the refresh interval goes back to 30 s the same afternoon.

### Prevention

- **The registered-shapes CI test** from the Code Example: every list endpoint's query shape runs against the scale seed with worst-case parameters, and `Rows Removed by Filter` is budgeted. The sparse agent becomes a permanent test fixture — the case averages hide, institutionalised.
- **A `mean_exec_time` *distribution* alert, not just a mean**: p99/p50 ratio above ~20 on a top statement pages, because parameter-dependent cliffs (this incident, 02.2's GraphQL, 03.11's slow clients) live in the ratio while the mean sleeps.
- **The index runbook**: `CONCURRENTLY` only; check for and drop `INVALID` leftovers; every new index PR pastes the before/after plan and names which registered shape it serves — an index that serves no registered shape is refused by default (the bet-book stays balanced).
- The monthly `pg_stat_user_indexes` audit from the lab, with the unique-constraint exemption written down.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...the query is fast in tests and slow for some users? | Parameter-dependent plans: re-EXPLAIN with the worst-case parameter. `Rows Removed by Filter` is the confession (measured: 2,925 vs 399,997 on identical plans). |
| ...you add the index without `CONCURRENTLY`? | Every write to the table queues behind the build — the incident's 40-second freeze. Live tables get concurrent DDL, always. |
| ...`CREATE INDEX CONCURRENTLY` fails midway? | An `INVALID` index remains: taxing writes, serving nothing. Drop it (concurrently) and re-run. |
| ...the partial index's WHERE and the query drift? | The index silently stops applying (new status value, changed predicate). Keep predicate and query adjacent in the registry; the CI shape test catches the drift. |
| ...an index-only scan is slow anyway? | `Heap Fetches` — the visibility map is stale. VACUUM is part of index-only performance (measured 3,526 → 0). |
| ...the query wraps the column in a function? | The index is invisible to it (measured: 133k filtered per worker). Index the expression, or normalise at write time. |
| ...you index a frequently-updated column? | HOT dies for every update of that column (measured 8,585 → 0), writes slow 2.3×, WAL +25%. Price it against real read traffic first. |
| ...an index shows `idx_scan = 0` for months? | Non-unique: pure write amplification — drop it concurrently. Unique: it may be constraint infrastructure (05.4's FK targets) — check before touching. |
| ...tenant count grows 100×? | Skip-scan rescues degrade linearly with distinct leading values; the leading-column rule and per-shape indexes are what actually scale. |

## Common Pitfalls

**Diagnosing with a friendly parameter.** The busy agent's 10 ms plan and the sparse agent's 793 ms plan are the *same plan*. *Instead:* EXPLAIN the worst case; budget `Rows Removed by Filter` in CI.

**One general index serving every shape.** It serves the dense case and bills the sparse one at full scan. *Instead:* purpose-built composites for registered shapes; equality → sort order.

**Sort column first.** `(last_activity_at, tenant_id)` turns every equality into a filter over the whole timeline. *Instead:* equality columns lead — including `tenant_id` always (05.4 made this a security-performance rule).

**Blocking DDL on live tables.** Plain `CREATE INDEX`/`DROP INDEX` take locks that freeze writes. *Instead:* `CONCURRENTLY` both ways, with the `INVALID`-corpse cleanup in the runbook.

**Indexing "just in case".** Every index taxes every write forever (measured: 2.3× and +25% WAL for a never-scanned index) and kills HOT on its column. *Instead:* indexes serve registered shapes; the monthly audit drops the rest.

**Expecting `INCLUDE` columns to guarantee index-only.** The visibility map decides; a write-hot table without vacuum headroom fetches heap anyway. *Instead:* measure `Heap Fetches`; treat vacuum health as part of the feature (05.11).

**Forgetting FK-column indexes.** Postgres does not create them (05.2's canon note); parent-side deletes and joins seq-scan the child per row. *Instead:* every FK column (or its composite prefix) gets an index the day the FK lands.

**Reading `idx_scan = 0` as "safe to drop" universally.** Unique indexes do constraint work at zero scans. *Instead:* the audit exempts `indisunique` until reviewed.

## How to Test This

- The registered-shapes plan test at the scale seed with worst-case parameters — the direct closure of the incident.
- A DDL-safety lint: index migrations must use `CONCURRENTLY` (grep-level, on the migrations directory) and each carries its before/after plan in the PR.
- The lab as the standing measurement harness: re-run F (the write bill) before indexing any column that appears in UPDATE statements; paste the HOT/WAL numbers.
- The monthly `pg_stat_user_indexes` report as a scheduled job, flagging unscanned non-unique indexes and drift between partial predicates and registry predicates.

## Interview Questions

1. *Explain.* Why can the same query plan be 10 ms for one parameter and 800 ms for another? — Scan-until-N-matches plans cost inversely to match density; `Rows Removed by Filter` exposes it. Diagnose with the sparse case, not the convenient one.
2. *Design.* Index the query `WHERE tenant=? AND assignee=? AND status IN (...) ORDER BY activity DESC LIMIT 50` on a 100M-row table. — Composite (tenant, assignee, activity DESC), equalities leading; status into a partial WHERE if the vocabulary is stable; built CONCURRENTLY; verified by Rows-Removed ≈ 0 at worst case.
3. *Explain.* What does a HOT update require, and what breaks it? — No indexed column changed plus same-page space (fillfactor); indexing an updated column converts every such update into index writes — measured 8,585 → 0 HOT, 2.3× slower.
4. *Explain.* Why was your index-only scan doing heap fetches? — Visibility map staleness: index entries carry no MVCC visibility, so un-vacuumed pages force heap checks. Vacuum is part of the feature.
5. *Debug this.* `WHERE lower(email) = ...` ignores the email index. — Indexes match expressions; index `lower(email)` or normalise at write. Same family: casts, `date_trunc`, concatenation.
6. *Explain.* What changed about the leftmost-prefix rule in PostgreSQL 18, and does the design rule survive? — Skip scan probes per distinct leading value; fine at low cardinality, multiplicative at high. Lead with what you filter by, still.
7. *Design.* An index-governance policy for a team of twenty. — A registry of query shapes each owning its index; plan budgets in CI at scale; CONCURRENTLY-only DDL; monthly idx_scan audit with the unique exemption; every index PR names the shape it serves.

## Key Takeaways

- An index is **sorted redundancy with a constraint-grade writer** — 05.2's copy rules apply: it must repay, on reads of its exact shape, what it taxes on every write.
- Composite design is mechanical: **equality columns first, sort column last, working-set predicates into a partial WHERE** — measured at 793 ms → 0.048 ms and 402,986 → 5 buffers for the incident's shape.
- **`Rows Removed by Filter` × `Buffers` is the diagnosis** of slow list queries — and it must be read at the *worst-case parameter*, because scan-until-N plans hide their cliff behind dense-case averages.
- Index-only is a vacuum promise (Heap Fetches 3,526 → 0); expression mismatch is silent (index the expression you query); the leftmost rule survives PG18's skip scan.
- The write bill is real and measured: one unused index cost 2.3× on updates, +25% WAL, and all 8,585 HOT updates. `fillfactor < 100` on update-heavy tables is canon.
- Live-table index DDL is **`CONCURRENTLY` or an outage**, and a failed concurrent build leaves an `INVALID` corpse to clean up.
- Govern indexes like the standing costs they are: registered query shapes with plan budgets in CI, and a scheduled `idx_scan` audit — dropping unscanned non-unique indexes, exempting constraint-bearing unique ones.
