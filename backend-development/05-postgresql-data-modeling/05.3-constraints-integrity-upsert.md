> ⚡ **Thursday 17 December, 15:40** — a Nordwind requester phones their account manager: they replied to a support ticket a day ago and no agent has ever seen it. The ticket exists. It is in no queue, no metric, no SLA timer. The cause: a word with a capital letter.

## Concept

### Plain-English Explanation

Deskhub's API validates ticket status values. The dashboard's TypeScript client validates them too. So did the code review. And on Wednesday night, 1,900 tickets acquired the status `'Solved'` — capital S — a value none of those validators would ever emit, and none of them saw arrive.

The uncomfortable truth about application-level validation is that it is **per-path**: it protects exactly the code that runs it. Every new path — a second endpoint, a bulk importer, an integration, tomorrow's migration script, a teammate's psql session — starts from zero. The database is different in kind, not degree: it is the *intersection* every path must cross, present and future. A **constraint** is validation attached to the data instead of to the code, which makes it the only validation whose coverage is "everyone, always" — 04.6 established this for races (the constraint as the only arbiter replicas share); this notebook widens it to *meaning*: vocabularies, ranges, relationships, and the integrity rules that make every queue, metric and SLA timer trustworthy.

The same one-statement thinking produces this notebook's second tool. **Upsert** — `INSERT … ON CONFLICT` — is what 04.5's check-then-act lesson looks like when the database applies it to itself: instead of asking "does this row exist?" and then acting on a stale answer, the insert *carries* the question, and the constraint answers it atomically.

### Technical Explanation

**The constraint taxonomy**, and what each one refuses:

| Constraint | Refuses | Deskhub examples |
|---|---|---|
| `NOT NULL` | Absent facts | Nearly every column (05.1) — nullability is a modelling decision, not a default |
| `CHECK` | Values outside a rule | `ck_tickets_status`; `byte_size > 0` on attachments |
| `UNIQUE` | Duplicate identities | `(tenant_id, number)`, `(tenant_id, email)` — 05.1's natural identities |
| `FOREIGN KEY` | Orphans and dangling references | Every child→parent edge, with an `ON DELETE` decision each |
| `EXCLUDE` | Overlaps (ranges, adjacency) | None yet — the tool for "no two on-call shifts overlap" shapes |

Two properties turn constraints from guardrails into *infrastructure*. First, **constraints are named, and the name is an API**: `violates check constraint "ck_tickets_status"` arrives in the driver's exception with `constraint_name` attached, which is exactly the stable key 03.8's repository mapping consumes. Deskhub names everything — `ck_`, `uq_`, `fk_` prefixes — because an autogenerated name is a mapping key nobody chose (03.13's operationId lesson, in DDL). Second, **constraints can be adopted without downtime**: `ADD CONSTRAINT … NOT VALID` installs the rule for *new* writes instantly and without scanning; `VALIDATE CONSTRAINT` later certifies the stock under a lock weak enough that writes continue. That two-step is what makes "we should have had a constraint" fixable on a live table — measured below.

**Upsert semantics.** `INSERT … ON CONFLICT (target) DO UPDATE SET …` needs three things understood precisely: the **conflict target** must identify a unique constraint or index (name one explicitly with `ON CONFLICT ON CONSTRAINT uq_…` when the table has several — a wrong implicit target is a wrong behaviour, silently); **`excluded`** is the row you *tried* to insert, available to the update; and the statement is atomic under concurrency — two simultaneous upserts of the same key produce one row and two successes, no retry loop. `DO NOTHING` is the idempotent-create variant, with a trap of its own below.

**Column conventions are constraints in spirit** — decisions made once so every table agrees. Deskhub's, now canon: **`timestamptz` always** (a `timestamp` without zone stores wall-clock digits whose meaning changes with the session's timezone — captured below, one row becoming two instants); **`numeric` or `bigint` minor units for money, never `float8`** (03.4's rule at the storage layer, where every path meets it); and **`text` over `varchar(n)`** — a length cap worth having is a `CHECK (char_length(…) <= n)` with a name your error mapping can speak, not an anonymous truncation-adjacent type modifier.

### Mental Model

> Constraints are **the schema's type system**. Application validation is a code path's opinion; a constraint is a property of the data — enforced at the only door every present and future writer must walk through. And an upsert is the door doing the checking: instead of *look, then leap* (a photograph, 04.6), you leap and let the door decide — one statement, one verdict, no window.

## How It Works

**Constraining a live table** — the sequence, exactly as the incident's fix ran it (`_lab/lab_05_03_constraints.py`, 200k rows, 997 of them garbage):

```text
plain ADD CONSTRAINT   -> FAILS: check constraint "ck_tickets_status" of relation
                          "tickets" is violated by some row
ADD ... NOT VALID      -> ok in   3.6 ms  (no scan; NEW writes constrained from this instant)
repair the stock       -> UPDATE 997
VALIDATE CONSTRAINT    -> ok in  0.03s   (scans, but under a weaker lock: writes continue)
```

The order is the point. Plain `ADD` must scan-and-certify while holding `ACCESS EXCLUSIVE` — and it fails outright if any stock violates, leaving you unprotected while you clean. `NOT VALID` inverts the race: the door is guarded *first* (3.6 ms, no scan), the garbage stops growing, the repair runs at leisure, and `VALIDATE` takes only `SHARE UPDATE EXCLUSIVE` — normal traffic continues through the certification scan. Protect the door, clean the room, then certify it. Once installed, the constraint speaks 03.8's language:

```text
INSERT status='Solved' -> CheckViolationError, constraint_name='ck_tickets_status'
```

**Upsert under real concurrency.** Twenty simultaneous ingestions of the same ERP order reference, first with the shape every handler naturally writes — SELECT, decide, INSERT:

```text
20 concurrent check-then-act, same ref : {'inserted': 1, 'unique_violation': 9, 'skipped': 10}
20 concurrent ON CONFLICT DO UPDATE    : all -> {'row 11'}, 1 row in the table
```

Read the first line the slow way: one winner; nine callers who checked before the winner landed and crashed into the constraint (their check was a photograph — 04.6); ten who happened to check after and skipped. Three different outcomes for identical requests, decided by scheduling luck — and *without* the UNIQUE constraint, those nine violations would have been nine duplicate rows. The upsert line is the whole argument: one row, and every caller walks away with its id.

**The gapless allocator** 05.1 owed. Sequences gap by design; Deskhub's per-tenant ticket numbers must not (a support desk that skips numbers files "where is ticket 1042?" tickets about its own tickets). The mechanism is a counter *row* per tenant, bumped inside the same transaction that inserts the ticket:

```text
naive max+1, 20 concurrent            : 20 rows but only 2 distinct numbers
counter-row allocator, 20 concurrent  : 20 rows, 20 distinct, numbers 1..20
allocate 21 then ROLLBACK -> next allocation gets 21   <- the bump dies with the txn
300 allocations, ONE tenant           :  2.52s   <- serialised on one counter row
300 allocations, TEN tenants          :  0.42s
```

Four captures, four facts. `max(number)+1` is check-then-act and collapses under concurrency (twenty "unique" numbers, two distinct values). The counter row issues 1..20 exactly, because the `UPDATE` takes a **row lock** that concurrent allocators queue behind. The rollback capture is what *gapless* actually means mechanically: the bump is transactional, so an aborted ticket returns its number — compare 05.1's sequence, which cannot rewind. And the last two lines are the invoice: that row lock is held until commit, so **ticket creation serialises per tenant** — six times slower when one tenant takes all the traffic. Gaplessness is not a free upgrade over sequences; it is a deliberate purchase of ordering at the price of concurrency, affordable precisely because a single tenant's humans do not create hundreds of tickets per second.

## Code Example

The canon DDL this notebook adds — everything named, every name a mapping key:

```sql
-- deskhub/schema.sql (05.3 additions)
ALTER TABLE tickets ADD CONSTRAINT ck_tickets_status
    CHECK (status IN ('open', 'pending', 'solved', 'closed'));
ALTER TABLE tickets ADD CONSTRAINT ck_tickets_priority
    CHECK (priority IN ('low', 'normal', 'high', 'urgent'));

-- The ERP integration's idempotency anchor (02.8's natural-key variant):
ALTER TABLE tickets ADD COLUMN external_ref text;
CREATE UNIQUE INDEX uq_tickets_tenant_external_ref
    ON tickets (tenant_id, external_ref) WHERE external_ref IS NOT NULL;

-- The gapless per-tenant number source (05.1's deferred debt):
CREATE TABLE ticket_counters (
    tenant_id   uuid PRIMARY KEY REFERENCES tenants(id),
    last_number bigint NOT NULL DEFAULT 0
);
```

Notes a reviewer should be able to give on sight: the partial unique index constrains only rows that *have* an external ref (dashboard-created tickets carry NULL, and NULLs never collide); its name matches the Ledgerly constraint from 03.8's incident on purpose — same pattern, same mapping discipline. FK deletion policy stays PostgreSQL's default (`NO ACTION`) everywhere: Deskhub hard-deletes nothing a support trail depends on — tickets, comments and attachments are history, agents get deactivated rather than dropped (08.x), and the erasure story that *does* delete is a designed feature (16.14), not a cascade surprise.

The allocator and the ERP sync, as the service layer runs them:

```python
# deskhub/repositories/tickets.py (excerpt)
ALLOCATE_NUMBER = """
    INSERT INTO ticket_counters AS c (tenant_id, last_number) VALUES ($1, 1)
    ON CONFLICT (tenant_id) DO UPDATE SET last_number = c.last_number + 1
    RETURNING last_number"""

async def create_ticket(conn, tenant_id, body) -> Ticket:
    async with conn.transaction():
        # Same transaction as the INSERT below: an abort rolls the bump back too,
        # which is the entire gapless guarantee (measured: rollback reuses 21).
        number = await conn.fetchval(ALLOCATE_NUMBER, tenant_id)
        return await conn.fetchrow(
            "INSERT INTO tickets (tenant_id, number, requester_email, subject) "
            "VALUES ($1, $2, $3, $4) RETURNING *",
            tenant_id, number, body.requester_email, body.subject)

UPSERT_FROM_ERP = """
    INSERT INTO tickets (tenant_id, number, external_ref, requester_email, subject)
    VALUES ($1, $2, $3, $4, $5)
    ON CONFLICT (tenant_id, external_ref) WHERE external_ref IS NOT NULL
    DO UPDATE SET subject = excluded.subject,      -- excluded = the row we TRIED to insert
                  updated_at = now()
    RETURNING id, number"""                        -- every caller gets the row, new or found
```

The allocator is itself an upsert — self-bootstrapping (a tenant's first ticket creates its counter row) and atomic (the `DO UPDATE` bump is one statement, no read-modify-write window). Note what the ERP upsert deliberately does **not** touch: `status`. A sync that blindly overwrote status would be 04.6's lost update through the front door — upsert makes *insertion* races safe, and does nothing for fields that carry a state machine; those still go through 04.6's CAS transitions.

Two traps, both captured, both shipped by real teams:

```text
DO NOTHING ... RETURNING on a conflict : returned None   <- no row, no error
next fresh insert's identity           : id=32  <- every conflicting attempt burned a number
```

⚠️ `ON CONFLICT DO NOTHING … RETURNING` returns rows only for inserts it actually performed — on conflict you get *nothing back*, and code that expected the existing row's id follows up with a confused NULL. If callers need the row either way, use `DO UPDATE` (even a no-op `SET external_ref = excluded.external_ref`) or a follow-up read. And every conflicting attempt still consumed the identity sequence — 05.1's gaps, actively farmed; harmless, but the team that monitors "gap rate" as a corruption signal will page itself. (Deskhub's uuid keys sidestep this one — the capture is from a `bigint` identity table, where most teams first meet it.)

> **Version note** — captured on PostgreSQL 18.6 via the module compose stack. `ALTER TYPE … DROP VALUE` remains unimplemented as of 18 (captured: *"dropping an enum value is not implemented"*); `NOT VALID`/`VALIDATE` semantics and locks are long-stable. Reproduce with `_lab/lab_05_03_constraints.py`.

## Design Patterns / Tradeoffs

### A closed vocabulary: CHECK vs ENUM type vs lookup table

The captures that decide it — adding `'on_hold'` to each mechanism:

```text
CHECK:  drop + re-add (NOT VALID) + validate -> 0.02s, plain DDL, reversible
ENUM:   ALTER TYPE ADD VALUE                 -> ok (cheap to add ...)
ENUM:   ALTER TYPE DROP VALUE                -> dropping an enum value is not implemented
LOOKUP: INSERT INTO statuses                 -> a data change, not DDL
```

- **`CHECK (status IN (…))`** — *advantages:* plain text column (no cast friction in drivers, logs, CSV); evolution is ordinary DDL in both directions; the constraint name feeds 03.8. *Disadvantages:* the vocabulary lives in DDL, so per-value metadata (labels, sort order) needs a separate home; nothing stops two tables defining drifting copies of the list. *Use when:* small closed sets whose transition logic lives in application state machines — **Deskhub's choice** for `status` and `priority`.
- **`ENUM` type** — *advantages:* one shared definition, 4-byte storage, type-checked everywhere it is used. *Disadvantages:* values are forever (captured above — removal means a column rewrite through a new type); adding mid-order is awkward; every driver and tool meets a custom OID. *Use when:* a genuinely permanent vocabulary shared by many tables.
- **Lookup table + FK** — *advantages:* the vocabulary is *data* — evolvable by INSERT, carries metadata columns, deletion policy expressible as `ON DELETE`; the FK is the constraint. *Disadvantages:* a join (cheap — 05.2) or a cache for display; "just insert a row" means vocabulary changes escape DDL review unless you gate them. *Use when:* values carry attributes or tenants can extend the set — which is where Deskhub's *tags* already are (05.2's `ticket_tags`), and where custom ticket fields will go (05.15).

One boundary rule from module 02 needs restating here because the incident turned on it: 02.3's "enums ship open" is an **output** posture — never break a reader on a value you add. **Input** vocabularies are the opposite: closed, exactly, at the edge (a `Literal` in the schema, 03.3) *and* at the database (the CHECK). Being liberal in what your API accepts is how `'Solved'` got in.

### Gapless allocator vs sequence

|  | Sequence / identity | Counter row (this notebook) |
|---|---|---|
| Gaps | By design (rollbacks, crashes, caching) | None — the bump is transactional (measured: rollback reuses) |
| Concurrency | Lock-free, effectively unbounded | Serialised per counter row (measured: 6× at 300 hot allocations) |
| Scope | Per database | Any scope you can key a row by — per tenant here |
| Use when | Internal ids, high-rate inserts | Human-facing numbering where "missing" numbers cost support trust, at human creation rates |

The honest framing: Deskhub buys gaplessness because ticket numbers are a customer-facing promise, and the price — per-tenant serialisation — is affordable at human rates. An event-ingestion table making that trade would be malpractice. When a future tenant automates ticket creation at machine rates, this row is where it will hurt, and 05.12 (locks) plus 05.14 (`SKIP LOCKED` patterns) are where the renegotiation happens.

## Production Scenario

**Deskhub, Thursday 17 December, 15:40.** Go-live week, day three. A Nordwind end-customer phones their account manager: they replied to ticket TKT-48112 yesterday morning and nobody has responded. The account manager finds the ticket by number — the page loads fine, the reply is right there, twenty-six hours old and unread. The ticket appears in **no** agent queue. Not "awaiting first reply", not "open", not the SLA breach list — which is the eeriest part, because a 26-hour-old unanswered reply should be *loudly* breaching.

### Symptoms

- Direct fetch by id or number: works. Every list, queue, count and SLA timer: the ticket does not exist. The two truths coexist because every list query filters `status IN (…something…)` and this row matches nothing anyone filters for.
- `SELECT DISTINCT status FROM tickets WHERE tenant_id = :nordwind` returns the four canon values — and `'Solved'`, `'In Progress'`, `'On-Hold'`. 1,912 rows across the three, all written since Wednesday 09:00.
- Every one of those rows was last touched by the API key of the **ERP status-sync integration** — built for go-live, pushing Nordwind's internal workflow states onto Deskhub tickets.
- No errors, anywhere, ever: the PATCH endpoint returned `200` for every one of those updates. The SLA engine, queues and dashboards are all *correctly* querying values that no longer describe the data.

### Diagnosis

1. **Alert → the row itself.** No alert fired; none could — every component is internally consistent. The account manager's phone call is the detector, and the first `SELECT DISTINCT` is the diagnosis: the status column's *vocabulary* has grown, which means some write path is not speaking Deskhub's language.
2. **Which path.** The audit trail (04.4's discipline carried forward) attributes every foreign value to the ERP sync's key. The integration maps Nordwind's ERP states onto ticket statuses — and for states with no mapping entry it passed the ERP's own string through. `'Solved'` is Nordwind's ERP spelling.
3. **Why nothing refused it.** The status-update endpoint declares `status: str` — a reviewer had applied 02.3's "enums ship open" to an *input* field, so Pydantic accepted anything. And the column, from the founding schema, is bare `text NOT NULL` — the CHECK constraint was a known 05.1 deferral that never got un-deferred. Two doors, both open; the dashboard's client-side validation guarded neither, because the integration is not the dashboard.
4. **Blast radius.** 1,912 tickets invisible to queues and SLA timers for up to 36 hours; 74 of them had requester replies pending. The SLA engine cannot even retroactively assess them — its timers key on status transitions that, per the data, never happened.

### Root Cause

The status vocabulary was enforced only in clients that chose to enforce it. A new write path — the ERP sync — wrote its own dialect, and 1,912 tickets slid out of every queue, metric and SLA timer simultaneously, with zero errors, because each query faithfully filtered a vocabulary the data no longer honoured. Validation was per-path; the paths multiplied; the one validator every path shares — the database — had never been given the rule.

### Fix

*Mitigation (16:10):* the repair, then the door — in that order because the door won't close over garbage:

```sql
UPDATE tickets SET status = CASE lower(trim(status))
        WHEN 'solved' THEN 'solved'  WHEN 'in progress' THEN 'open'
        WHEN 'on-hold' THEN 'pending' ELSE 'open' END,
       updated_at = now()
WHERE status NOT IN ('open','pending','solved','closed');     -- 1,912 rows
```

The 74 tickets with pending replies surface in queues within the minute; agents triage them that evening; Nordwind gets a list and an apology. Then the two-step from How It Works, exactly as measured: `ADD CONSTRAINT ck_tickets_status … NOT VALID` (instant — the sync can no longer add dialect), `VALIDATE` after the repair (0.03 s here; minutes on a big table, but under the write-friendly lock either way).

*Permanent fix:* the input edge closes too — the endpoint's schema becomes a `Literal["open","pending","solved","closed"]` returning a catalogue `422` (02.9), and `ck_tickets_status` joins the repository's constraint-name map (03.8) so even a future unvalidated path yields a clean catalogue error instead of a 500. The ERP integration gets an **explicit, exhaustive mapping table** — an unmapped ERP state is now a rejected sync event in a dead-letter list (02.11's discipline), not a passthrough.

### Prevention

- **The incident closes into a named CI test** — the vocabulary is enforced where every path meets it, and the test proves it by *bypassing* the application:

```python
# tests/schema/test_vocabularies_are_database_enforced.py
async def test_status_garbage_is_refused_at_the_lowest_layer(db):
    """1,912 tickets left every queue via an integration's dialect (17 Dec).
    App validation is per-path; the CHECK is all-paths - test it by writing
    the way the NEXT rogue path will: raw SQL (05.3)."""
    with pytest.raises(asyncpg.CheckViolationError) as err:
        await db.execute(
            "INSERT INTO tickets (tenant_id, number, requester_email, subject, status) "
            "VALUES ($1, 999999, 'x@example.com', 'probe', 'Solved')", TENANT)
    assert err.value.constraint_name == "ck_tickets_status"   # 03.8's mapping key
```

- **A schema lint in CI**: every column named `status`/`priority`/`kind`/`type` must carry a CHECK, an enum type or a FK — a vocabulary column with none is a failing build, so the *next* deferral cannot silently persist.
- **The input/output posture written into the API guide**: outputs evolve openly (02.3); inputs are closed sets, validated at the edge *and* constrained in the schema. One sentence, and it ends the `status: str` class of review approval.
- The integration runbook gains the dead-letter rule: an unmappable upstream value is a *parked event and a page*, never a passthrough — unknown input is a fact to surface, not data to store.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a new write path skips the service layer? | App validation never sees it; the constraint does. That asymmetry is the whole argument (measured: three garbage inserts refused by name). |
| ...the constraint must land on a table with existing violations? | Plain `ADD` fails and leaves you unguarded. `NOT VALID` first (instant, guards new writes), repair, then `VALIDATE` under the weaker lock. |
| ...two requests upsert the same key simultaneously? | One row, both succeed, both get it via `RETURNING` — the constraint is the arbiter (04.6) and the upsert is the act. Check-then-act instead: 1/9/10 outcome lottery, measured. |
| ...`DO NOTHING` meets a conflict and you expected the row back? | `RETURNING` yields nothing on skipped rows (captured: `None`). Use `DO UPDATE` or a follow-up read. |
| ...an upsert includes state-machine fields? | It becomes a lost-update machine (04.6) — sync facts, never transitions. Status changes go through CAS. |
| ...the allocator's transaction rolls back? | The number comes back with it (captured: 21 → 21). That is the gapless property — and why the bump must share the ticket's transaction. |
| ...one tenant creates tickets at machine rate? | The counter row serialises them (measured 6×). Gaplessness is the wrong trade there — renegotiate at 05.12/05.14. |
| ...a `timestamp` column meets a second timezone? | The same digits become a different instant (captured: `same instant? False`). `timestamptz` everywhere; the convention is a constraint in spirit. |
| ...an enum value must be removed? | It can't be (captured: "not implemented") — plan vocabularies with CHECK or lookup tables when removal is conceivable. |

## Common Pitfalls

**"The application validates it."** The application *path* validates it — and paths multiply: integrations, imports, scripts, next year's second service. *Instead:* the rule lives on the data; the app's copy is UX, not enforcement.

**Applying 02.3's open-enum posture to inputs.** Open vocabularies are reader tolerance; accepting any string is how dialects enter. *Instead:* inputs closed (`Literal` + CHECK), outputs tolerant.

**Plain `ADD CONSTRAINT` on a big live table.** An exclusive-lock scan at best; a failed scan over existing garbage at worst — while the garbage keeps arriving. *Instead:* `NOT VALID` → repair → `VALIDATE`, always, out of habit.

**Unnamed constraints.** `tickets_status_check` autogenerated today is a different name after tomorrow's recreate — and it is a public key the moment 03.8's mapping consumes it. *Instead:* `ck_`/`uq_`/`fk_` names, chosen, forever.

**Upsert as a blind overwrite.** `DO UPDATE SET status = excluded.status` is a photograph war (04.6) hiding in idempotency clothing. *Instead:* upsert identity-and-facts; transition state with guarded writes.

**`SELECT max(n) + 1`.** The measured lottery: 20 writers, 2 distinct numbers. *Instead:* the counter-row upsert in the insert's transaction — or a sequence, if gaps are acceptable (they usually are).

**Gapless numbering by reflex.** It serialises writers per counter (measured 6×) to buy a property most tables don't need. *Instead:* sequences by default; buy gaplessness only where humans audit the numbers.

**`varchar(40)` as validation.** An anonymous limit with an unmappable error, doing nothing about content. *Instead:* `text` plus a named `CHECK` for any limit that matters.

## How to Test This

- The raw-SQL garbage test above — per vocabulary column, asserting the constraint *name*, because the next rogue path will not use your service layer either.
- An allocator test: N concurrent creations for one tenant yield exactly 1..N (the lab's shape as a fixture); plus the rollback-reuse assertion.
- An upsert idempotency test: the same ERP event delivered twice yields one row, same id both times, and never touches `status`.
- The schema lint: vocabulary-shaped columns without CHECK/enum/FK fail CI; `timestamp` (without tz) and `float8` money columns fail the same sweep (03.4's rule, enforced at the schema).

## Key Takeaways

- **The database is the only validator every write path shares.** Vocabulary, range and relationship rules belong on the data, named, with the app's validation as UX in front — not instead.
- Constraint names are an API: `ck_`/`uq_`/`fk_`, chosen deliberately, consumed by 03.8's error mapping, tested by raw SQL that bypasses the service on purpose.
- The zero-downtime adoption path is a habit worth automating: **`NOT VALID` → repair → `VALIDATE`** — guard the door first, clean second, certify third (measured: 3.6 ms to guard).
- **Upsert is check-then-act collapsed into one verdict** — measured against 20 concurrent writers: one row versus a 1/9/10 outcome lottery. Sync facts with it; never state transitions (04.6 owns those).
- Know the traps: `DO NOTHING` returns nothing on conflict; conflicts burn identity numbers; the conflict target should be named when the table has multiple unique constraints.
- Gapless numbering = a counter row bumped in the same transaction — rollback-safe by construction, serialised per tenant by construction (measured 6×). Buy it only where humans audit numbers.
- Inputs are closed vocabularies; outputs are open ones. 02.3 and this notebook are two halves of one rule.
- `timestamptz` always; `numeric`/minor-unit money always — conventions are constraints that happen to have no name yet, and the schema lint gives them one.
