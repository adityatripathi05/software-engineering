## Concept

### Plain-English Explanation

Normalisation has a reputation as database theory — normal forms, Codd, exam questions. In production it is one working rule: **store every fact exactly once, and derive the rest**. The reason is not elegance. A fact stored in five places is an update that must land in five places, atomically, forever, through every code path anyone ever writes — and the first path that forgets leaves your database *disagreeing with itself*, with no error, no exception and no alert, because every individual row is perfectly valid. Module 02 taught that contract violations are invisible from the server; this notebook shows the storage-layer version: **consistency violations between copies are invisible to the database**, because the database was never told the copies were related.

Denormalisation — deliberately storing a fact or a derived value redundantly — is therefore not the opposite of good design; it is a *loan against it*. Sometimes the loan is worth taking: this notebook measures a Deskhub queue query that drops from 892 ms to 3.8 ms on the strength of one denormalised column. But a loan has payments: every copy needs a writer that cannot be bypassed and an auditor that notices when it lies. The incident below is what happens when a copy has neither.

### Technical Explanation

**The anomaly test.** A schema is under-normalised when ordinary operations produce one of three anomalies. An **update anomaly**: the same fact lives in many rows, so changing it means a multi-row update no mechanism enforces — miss any row and the data contradicts itself. An **insert anomaly**: you cannot record a fact without inventing an unrelated one (you cannot store a new agent's name until they have a ticket, if agent names live only on tickets). A **delete anomaly**: removing the last row that mentions a fact destroys the fact (delete the last ticket, lose the agent). All three are the same disease — a fact living in the wrong table — seen from three directions.

**The normal forms name specific versions of the disease**, and each has a concrete Deskhub example:

- **1NF** — one value per column, one fact per row. Violation: `tags text` holding `'billing,vip'`. The measured consequence (below): the only possible query is a substring match, and `LIKE '%vip%'` cheerfully matches `'not-vip'`. Fix: one row per fact — the `ticket_tags` association table, whose composite natural key is legitimately its primary key (05.1's exception, now in use).
- **2NF** — every non-key column depends on the *whole* key. Violation: `ticket_tags(ticket_id, tag_id, tag_label)` — the label depends on `tag_id` alone, so renaming a tag means updating every tagged ticket. Fix: the label moves to a `tags` table.
- **3NF** — and nothing but the key: no column that is really a fact about *another* column's referent. Violation: `tickets.assignee_name` — a fact about the agent, reachable through `assignee_id`, cached onto every ticket. This is the one that ships constantly, because it "saves a join".

The mnemonic that compresses all three is older than most databases and still the fastest review question: *every non-key column is a fact about the key, the whole key, and nothing but the key.*

**But not all duplication is the disease.** The decision that separates staff engineers from checklist-followers is telling three superficially identical patterns apart:

1. **A mutable current fact, copied** — `assignee_name` on tickets. An anomaly. Never.
2. **A point-in-time snapshot** — `requester_email` on tickets (05.1's schema, deliberately): the address the requester used *when they raised this ticket*, like the shipping address on an order or the unit price on an invoice line. It must **not** track later changes; "fixing" it to reference a mutable profile would rewrite history. This is correct modelling wearing duplication's clothes, and normalising it is a bug.
3. **A derived value** — `comment_count`, `last_activity_at`: computable from other rows, stored for speed. Legitimate *only* with a maintenance mechanism and a detector, and only when a measurement says the derivation is too expensive to run per query.

The test that separates 1 from 2: *if the source changes tomorrow, should this row change?* Yes → you have copied a live fact (anomaly). No → you have captured history (snapshot). And 3 is distinguished by construction: it has a formula.

### Mental Model

> A normalised schema is a system where **every fact has one home address**, and every question is answered by visiting addresses — visits are joins, and joins are cheap (measured below). A denormalised column is a **cache line inside your own database**: it has all of caching's problems — staleness, invalidation, drift — and none of caching's safety nets, because there is no TTL and no cache-miss path. If you would not deploy a cache without an invalidation story, do not add a derived column without a writer and an auditor.

## How It Works

**The update anomaly, executed.** Take 05.1's schema, add the launch-era shortcut `tickets.assignee_name`, and let Agent 7 get married. The rename lands on `agents`, and on the copies — through an UPDATE somebody scoped by hand, which missed half of them (`_lab/lab_05_02_normalisation.py`):

```text
assignee_name='Agent 7'             on 2,000 tickets
assignee_name='Anna Weber-Fuchs'    on 2,000 tickets
```

One agent, two names, zero errors. Every consumer of those rows — CSV exports, search, the audit trail — now disagrees with the agents table, and nothing in the system knows. This is 04.6's photograph problem made permanent: the copy was correct at exposure time and is a lie forever after.

**The join it "saved" was never expensive.** The reason `assignee_name` got copied was fear of joining. Measured — the 50-row agent inbox as a full 3-way join (tickets → agents → tenants) at 200k tickets:

```text
Limit  (cost=0.73..11.95 rows=50 width=102) (actual time=0.044..0.223 rows=50.00 loops=1)
Planning Time: 0.229 ms
Execution Time: 0.246 ms
```

A quarter of a millisecond, total, for the joined page. PostgreSQL walks the ticket index and probes two primary keys per row — the entire "joins are slow" folklore, at OLTP page sizes with indexed keys, is worth 0.2 ms. Denormalising to avoid *this* is taking the loan to dodge a bill of pocket change.

**Where the real bill lives: deriving under `ORDER BY`.** The agent queue sorts by *last activity* — a value that does not exist on any row; it is `max(comments.created_at)` per ticket. Displaying a derived value for 50 rows is cheap (50 indexed probes); **sorting or filtering by it means deriving it for every candidate row first**. Measured, same database:

```text
->  Sort ... rows=50   Sort Method: top-N heapsort
->  HashAggregate ... rows=200000    ← every open ticket aggregated...
->  Seq Scan on comments ... rows=799995   ← ...over the whole comments table
Execution Time: 622.877 ms

aggregate version:    892.4 ms   ← per queue page view
counter version  :      3.8 ms   ← tickets.last_activity_at + one index
```

**236× — and that is the honest shape of the denormalisation decision.** The aggregate version re-reads 800k comment rows to sort 50 tickets, on every refresh of every agent's queue; the derived column turns it into one indexed read. The rule this measurement generalises to: *display-only derived values rarely justify a copy; derived values you filter or sort by usually do.* You now owe the loan payments.

**The 1NF capture**, for completeness, because every team meets it:

```text
WHERE tags LIKE '%vip%' returns:
  Invoice question   tags='billing,vip'
  Password reset     tags='not-vip'   <- WRONG
  Printer on fire    tags='vip,hardware'
ticket_tags WHERE tag = 'vip' returns: ['Invoice question', 'Printer on fire']
```

A list in a column can only ever be interrogated as a substring; the association table makes the same question exact, indexable, and constrainable (a `UNIQUE` tag vocabulary, a FK to who may tag — none of which a text blob can hold).

## Code Example

The canon addition this notebook makes to Deskhub's schema — the two derived columns the queue measurement justified, with their writer welded on:

```sql
-- deskhub/schema.sql (05.2 additions)
ALTER TABLE tickets
    ADD COLUMN comment_count    int         NOT NULL DEFAULT 0,
    ADD COLUMN last_activity_at timestamptz;

CREATE INDEX ix_tickets_tenant_activity
    ON tickets (tenant_id, last_activity_at DESC NULLS LAST);   -- the queue's index

-- The ONLY writer. A trigger fires on every insert path there is - the service
-- layer, a bulk import, a psql session at 03:00 - which is exactly the property
-- application-side maintenance cannot offer (the incident below).
CREATE FUNCTION bump_ticket_activity() RETURNS trigger AS $$
BEGIN
    UPDATE tickets
    SET comment_count    = comment_count + 1,
        last_activity_at = greatest(coalesce(last_activity_at, NEW.created_at),
                                    NEW.created_at),
        updated_at       = now()
    WHERE id = NEW.ticket_id;
    RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_comment_activity
    AFTER INSERT ON comments
    FOR EACH ROW EXECUTE FUNCTION bump_ticket_activity();

COMMENT ON COLUMN tickets.comment_count IS
    'derived: count(comments). Writer: trg_comment_activity. Audited nightly.';
```

Three properties carry the design. The trigger runs **inside the inserting transaction** — if the comment rolls back, so does the bump; the lost-update window of two separate statements simply does not exist (04.6's lesson: bind the consequence to the fact). It is **path-proof**: Deskhub's bulk-import endpoint writes comments with batched INSERTs that skip the service layer, and the trigger neither knows nor cares. And the `COMMENT ON COLUMN` line is not decoration — it is the schema documenting the loan: *what formula, which writer, who audits*. (One honest caveat: `comment_count + 1` on the parent row takes a row lock, so a thousand simultaneous comments on one ticket serialise. For a helpdesk that is nothing; for likes-on-a-celebrity-post scale it is the reason batched counter designs exist — 10.x.)

The auditor is one query — the same one that diagnosed the incident:

```sql
-- nightly invariant: a derived column that cannot drift silently
SELECT count(*) FILTER (WHERE t.comment_count <> s.n)  AS drifted,
       coalesce(sum(abs(t.comment_count - s.n)), 0)    AS total_error
FROM tickets t
JOIN LATERAL (SELECT count(*) AS n
              FROM comments c WHERE c.ticket_id = t.id) s ON true;
-- alert: drifted > 0. The formula IS the test.
```

And the measured story of why the trigger, not app code, is the writer — the launch-era shape was an INSERT followed by a *separate* counter UPDATE from the service, which loses the bump when anything fails between the statements (03.10's at-most-once) and double-bumps when a webhook redelivery re-runs the handler (02.8's missing idempotency). Run 1,000 comments through that shape, then a 100-row bulk import that bypasses the app entirely, then the same traffic with the trigger as sole writer:

```text
naive app-side, 1,000 comments: 42 tickets drifted (total error 42)
+ a 100-row bulk import (bypasses the app): 135 drifted (total error 136)
trigger as the only writer, incl. another bulk import: 0 drifted (total error 0)
trigger cost: 20,000 inserts  without= 0.31s  with= 0.76s  (2.5x)
```

⚠️ The last line is the part advocacy usually omits: the trigger is an extra UPDATE per insert, and on bulk paths that measured **2.5×** on insert throughput. That is the loan payment, priced. Pay it knowingly — the 236× read win buys a lot of 2.5× write cost for a read-heavy queue — or choose a cheaper mechanism from the table below. And note the corollary hiding in the design: **exactly one writer**. Install the trigger and *delete* the app-side bump in the same change, or every API comment counts twice.

> **Version note** — captured on the module compose stack (PostgreSQL 18.6). Plan shapes and timings are machine-dependent; the *ratios* (join ≪ aggregate, trigger ≈ 2–3× on bulk inserts) are the stable content. Reproduce with `_lab/lab_05_02_normalisation.py`.

## Design Patterns / Tradeoffs

### Keeping a derived value honest: the mechanisms

| Mechanism | Freshness | Survives every write path? | Cost | Use when |
|---|---|---|---|---|
| **Compute on read** (no copy) | Perfect | — no copy exists | Paid per query | Default until a measurement says otherwise |
| **Same-transaction app code** | Perfect | ❌ only paths that remember | One UPDATE, in your code, visible in review | One write path, enforced by "all writes go through the service" — and an auditor anyway |
| **Trigger** (Deskhub's choice here) | Perfect | ✅ by construction | One UPDATE per row, ~2.5× measured on bulk inserts; hidden from application review | Multiple write paths exist (imports, ETL) or ever will |
| **Materialized view** | Stale until `REFRESH` | ✅ (rebuilt from source) | Full recompute per refresh; `CONCURRENTLY` needs a unique index | Dashboards and reports where minutes-old is fine |
| **Async rebuild** (queue/worker recomputes) | Eventually | ✅ if triggered reliably (11.15's outbox problem) | Complexity of module 11 | Cross-system derivations; counters too hot for row locks |

The recommendation is the table read top-down: **compute on read until measured pain; then the narrowest mechanism whose staleness you can afford.** Deskhub takes the trigger for `comment_count`/`last_activity_at` because the bulk-import path is now a permanent feature (December proved it), perfect freshness matters (SLA timers read these columns), and the write rate is comfortably inside the 2.5× budget. The moment either assumption breaks — a counter too hot to row-lock, a derivation spanning services — the answer moves down the table, and the *auditor stays regardless*, because every mechanism except compute-on-read can be wrong.

### How normalised is normalised enough?

Third normal form is the working target for OLTP schemas like Deskhub's, and it is worth saying why you stop there rather than chasing higher forms: beyond 3NF the anomalies being prevented get exotic (multi-valued and join dependencies) while the query cost of the extra tables is constant and real. The practical posture: **normalise to 3NF by default; document every deliberate exception as one of the three duplication kinds** — snapshot (no sync, by design), or derived (writer + auditor named). An exception that cannot say which kind it is, is an anomaly waiting for its December.

The reverse question — "should we denormalise this?" — gets the measured discipline from this notebook: the join myth means *reading through a relationship* almost never justifies a copy (0.25 ms for a 3-way joined page), while *sorting or filtering by a derivation* often does (892 → 3.8 ms). Demand the measurement in the PR, the way 05.1 demands the key-geometry table.

## Production Scenario

**Deskhub, Wednesday 16 December, 08:30.** Nordwind Logistik — the tenant whose 6M-ticket import 05.1's incident throttled and rescheduled — goes live this morning. At 08:30 their operations manager calls, unhappy: the **"awaiting first reply" queue shows 38,000 tickets**, their managers' inboxes are filling with SLA-breach escalations, and most of the "breaching" conversations were closed years ago in the old system. Deskhub's own SLA dashboard agrees with the queue: Nordwind's first-response compliance reads 4%.

### Symptoms

- The queue view — `WHERE tenant_id = … AND status = 'open' AND comment_count = 0` — returns ~38,000 rows for Nordwind. Their genuinely-unanswered backlog, per their old system, is about 1,200.
- Spot-checking any of the 38,000: the ticket *has* comments — years of them, visible right there on the ticket page (which lists the `comments` table directly). The row says `comment_count = 0` anyway.
- The SLA engine, which reads `last_activity_at` (also `NULL` on every imported ticket), has queued ~36,000 first-response-breach escalation emails; the notification worker is happily draining them into managers' inboxes.
- Nothing is erroring. Every query is fast. The database is consistent with itself row by row — and disagrees with itself table to table.

### Diagnosis

1. **Alert → the data.** No system alert fired and none could: every row is valid and every query cheap. The detector is a customer looking at a number they know to be wrong — 03.13's lesson, storage edition. The reconciliation query (the auditor that did not yet exist) is written *during* the incident: `comment_count` vs `count(*)` per ticket. For Nordwind: 38,112 mismatches — every one an imported ticket.
2. **Correlate with the write path.** Imported tickets and comments were loaded through the migration's bulk endpoint — added in November for throughput, batched INSERTs straight through the repository, skipping the service method that bumps counters. The columns were maintained *by convention in one code path*, and the migration built a second path.
3. **Widen the query.** Run the reconciliation across all tenants: another **0.9% of live, never-imported tickets** have drifted counters (`# illustrative - not captured output`; the lab's 42-in-1,000 is the same mechanism at capture scale). These are the older, slower leak: the service's two-statement shape — INSERT, then a separate UPDATE — losing bumps when a deploy or error landed between them (03.10's at-most-once) and double-bumping when webhook redeliveries re-ran the handler (02.8).
4. **Eliminated:** the import data itself (comments are all present and correct — the *source* facts are fine), the queue query (it faithfully reads the column it was told to), and the SLA engine (correctly escalating what the columns assert). Every component did its job; the copy lied to all of them.

### Root Cause

Two derived columns were maintained by application code in one code path, so the bulk-import path wrote the facts (comments) without the consequences (counters) — filling the go-live queue with 38,000 answered tickets — while the two-statement service shape had been silently drifting live tenants' counters at ~0.9% for months. A derived value had no bound writer and no auditor: the failure was not wrong data at rest but **an unowned copy**, and it stayed invisible precisely because no error can fire when every row is individually valid.

### Fix

*Mitigation (09:10):* the backfill — recompute both columns from source for Nordwind (one statement, the lab's repair query, ~seconds at their size); the queue collapses to 1,187 tickets; the ~36k queued escalation emails are purged from the notification queue before most send (the ones already delivered get an apology from the account team).

*Permanent fix:* the trigger from the Code Example becomes the columns' only writer; the service-layer bump is **deleted in the same deploy** (two writers double-count); a fleet-wide backfill repairs the historical 0.9%. The bulk-import endpoint needs no change at all — that is the point of the mechanism chosen.

### Prevention

- **The auditor ships as a nightly job**: the reconciliation query with `alert: drifted > 0`. For wrong-data failures this is the *only* detector class that exists — the recurring lesson (01.6, 03.3, 03.10, 04.4) now applied to every derived column as a standing rule, not an incident response.
- **The incident closes into a named CI test** — every write path, one invariant:

```python
# tests/schema/test_derived_columns_survive_every_write_path.py
async def test_counter_is_correct_after_service_and_bulk_paths(db, seeded_ticket):
    """38k imported tickets showed comment_count=0 with years of comments (16 Dec):
    derived columns must be write-path-proof, not convention-proof (05.2)."""
    await comment_service.add(seeded_ticket.id, body="via the service")
    await db.execute(          # the migration's path: batched INSERT, no service
        "INSERT INTO comments (ticket_id, body) VALUES ($1, 'via bulk import')",
        seeded_ticket.id)
    row = await db.fetchrow(
        "SELECT comment_count, (SELECT count(*) FROM comments WHERE ticket_id=$1) AS actual "
        "FROM tickets WHERE id=$1", seeded_ticket.id)
    assert row["comment_count"] == row["actual"] == 2
```

- **A schema rule with a home**: every derived column carries a `COMMENT ON COLUMN` naming its formula, its writer and its auditor — reviewable, greppable, and the first thing the next 03:00 investigator reads.
- The go-live runbook gains a line: after any bulk load, run the reconciliation for the affected tenant *before* the SLA engine sees the rows.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a fact is stored in two places and one write path forgets? | The tables disagree, silently and validly. Only a reconciliation query can see it — which is why every copy names an auditor. |
| ...a new write path is added (import, ETL, admin script)? | App-maintained copies drift immediately (measured: 135 tickets from one 100-row import). Triggers and rebuilds survive; conventions do not. |
| ...the maintenance UPDATE and the INSERT are separate statements? | Anything between them — error, deploy, kill — loses the bump (03.10); a retry doubles it (02.8). In-transaction maintenance makes both windows unrepresentable. |
| ...two writers maintain the same column? | Systematic double-counting. Installing a trigger means deleting the app-side bump in the same change. |
| ...the derived column is only ever displayed? | It probably shouldn't exist: 50 indexed probes are cheap. Copies earn their keep under ORDER BY and WHERE (measured 236×). |
| ...a "duplicate" is actually a snapshot (order address, requester_email)? | Normalising it rewrites history. Classify before you fix: *should this change when the source changes?* |
| ...one row's counter gets extremely hot? | The trigger's parent-row lock serialises writers (05.12). Batched or sharded counters, or async rebuild — a different row in the mechanisms table. |
| ...write traffic ×10? | The trigger's 2.5× rides along on every insert. Re-run the lab's cost probe before and after; the loan payment scales with the writes. |

## Common Pitfalls

**Denormalising out of join fear.** The folklore says joins are slow; the measurement says 0.25 ms for a 3-way joined page. *Instead:* demand the numbers — copies are for aggregate-shaped `ORDER BY`/`WHERE`, not for reading a name through a foreign key.

**Derived columns maintained "in the service".** Correct until the second write path exists, and the second path always arrives (an import, a backfill script, a teammate's psql session). *Instead:* a trigger, or close every other path and audit anyway.

**Fixing the drift without deleting the old writer.** Trigger plus surviving app-side bump = everything counts twice, and the auditor now pages nightly. *Instead:* one writer, enforced in the same deploy.

**Normalising a snapshot.** "requester_email duplicates requester data" — no: it records who asked *then*. Pointing it at a mutable profile rewrites every historical ticket. *Instead:* classify duplication before eliminating it; snapshots are correct.

**Lists in columns.** `'billing,vip'` can only be substring-searched (`'not-vip'` matches `'%vip%'`), never constrained, never counted. *Instead:* an association table — and when the shape is genuinely document-like, that is 05.15's JSONB discussion, not a text blob.

**Copies without auditors.** The mechanism can be right and still break next year (a disabled trigger, a logical-replication path, a bug). *Instead:* the formula is the test — one nightly query per derived column, alerting above zero.

**Counting on `count(*)` being cheap.** It reads every matching row, every time; that is *why* the counter column exists. *Instead:* measure both sides — the aggregate's cost justifies the copy, the copy's write cost bounds it.

## How to Test This

- The two-path CI test above: service path and bulk path both leave the counter equal to `count(*)`.
- The nightly reconciliation per derived column — the formula as a standing invariant, alerting on `drifted > 0`.
- A rollback test: insert a comment in a transaction that aborts; assert the counter did not move (the trigger's in-transaction property, pinned).
- The lab's cost probe re-run on schema changes that add triggers to hot tables: bulk-insert throughput with and without, recorded in the PR.

## Interview Questions

1. *Explain.* What actually goes wrong in an under-normalised schema — mechanically, not aesthetically? — Update/insert/delete anomalies: multi-row updates no mechanism enforces, facts you cannot record alone, facts destroyed by unrelated deletes. All are "a fact in the wrong table".
2. *Explain.* Three kinds of duplication and how you tell them apart. — Copied mutable fact (bug), point-in-time snapshot (correct — must *not* sync), derived value (cache — needs writer + auditor). Test: should it change when the source changes? Does it have a formula?
3. *Debug this.* A go-live queue shows 38k "unanswered" tickets that all visibly have replies; no errors anywhere. — A derived counter with a bypassed write path; reconcile counter vs `count(*)`, correlate mismatches with the bulk-import path, backfill, then bind the writer to the fact (trigger).
4. *Design.* The agent queue must sort by last activity across millions of comments. Walk the decision. — Measure compute-on-read (aggregate over comments per view: ~600 ms plan); justify the derived column (3.8 ms indexed); choose the mechanism by write paths and staleness (trigger here); ship the auditor with it.
5. *Explain.* Why is "INSERT, then UPDATE the counter" from application code structurally unsound? — Two statements = a window: failures between them lose the bump (at-most-once), redeliveries double it (no idempotency). In-transaction maintenance removes the window instead of shrinking it.
6. *Explain.* When is a trigger the right maintenance mechanism, and what does it cost? — When multiple write paths exist or will; measured ~2.5× on bulk inserts plus a parent-row lock that serialises hot rows; and it demands deleting every other writer.
7. *Design.* A per-tenant dashboard needs ticket counts by status, refreshed within a minute. — Not a per-row counter (too many cells) and not compute-on-read (too hot): a materialized view refreshed on a schedule, or 10.x's cache — chosen by staleness budget, with the reconciliation habit intact.

## Key Takeaways

- **Store every fact once; derive the rest.** The anomaly test (update/insert/delete) finds violations faster than reciting forms — and 3NF is where OLTP normalisation sensibly stops.
- Duplication has three kinds: **bug, snapshot, cache**. Classify before eliminating — normalising a snapshot rewrites history, and keeping a mutable copy invites December.
- The join myth is measurable: **0.25 ms** for a 3-way joined page. Copies are never justified by "avoiding a join"; they are justified by **sorting/filtering on a derivation** — measured here at 892 → 3.8 ms.
- A derived column is a cache with no TTL: it needs **exactly one writer** (bound to the fact — a trigger survives every write path; conventions survive one) and **an auditor** (the formula as a nightly invariant).
- Two-statement maintenance drifts by construction — lost bumps and doubled bumps are 03.10 and 02.8 wearing storage clothes. In-transaction maintenance makes both unrepresentable.
- Copies cost writes: the trigger measured **2.5×** on bulk inserts and serialises hot parent rows. Price the loan; re-price it when traffic grows.
- Consistency between copies is invisible to the database and to every dashboard. **The formula is the only detector** — ship it with the column, or a customer ships it for you.
