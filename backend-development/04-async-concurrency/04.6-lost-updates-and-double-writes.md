# 04.6 Lost Updates and Double Writes

> **Prerequisites:** 04.5 (check-then-act, the process boundary) · 03.8 (IntegrityError by constraint name) · 03.10 (the outbox rides the transaction) · 02.8 (idempotency keys) · 01.6 (replicas share nothing) · modern-python 10.2 (transactions, who commits — assumed)
> **What you'll learn:**
> - Recognise 04.5's two master bugs — read-modify-write and check-then-act — when the shared state is a database row and the interleaving is between replicas
> - Make the write carry the condition: atomic expressions, compare-and-swap transitions, and rowcount as the only truthful verdict
> - Use unique constraints as arbiters of "at most once", not as safety nets — and map their verdicts to business meaning (03.8)
> - Choose between optimistic (version/CAS) and pessimistic (row locks) concurrency, and surface conflicts to clients as 409/412 with ETags
> - Tie side effects to the winning transaction, so losing a race means *nothing happened*, not half of it
> **Level:** Advanced

> ⚡ **Thursday 12 November, 11:35** — a customer receives, by email, an invoice their accountant voided twenty minutes earlier; Ledgerly's own UI says "sent". No error was logged by either action. The cause: two requests that each read the word "draft".

## Concept

### Plain-English Explanation

04.5 ended at the process boundary: an `asyncio.Lock` coordinates one loop, and Ledgerly runs twelve. But the requests didn't stop being concurrent — they just meet in a different room now. The database is the *only* place where every replica's requests are genuinely present at once, and so it is where the same two bugs from 04.5 reappear with new bodies: **the lost update** (two requests read a row, each computes a new value from its copy, each writes — the second write silently erases the first) and **the double write** (two requests both check "not done yet", both find it true, both do it). Same anatomy, different physics: the hazard window is no longer an `await` in your code but the gap between *your transaction's read and its write*, and no primitive you hold in Python can close it — only the database can, because only the database sees both requests.

### Technical Explanation

**The lost update, measured** — two payments applied to one invoice by read-modify-write on two connections:

```text
req-1 read 0, wrote 40; req-2 read 0, wrote 60
final paid_amount: 60   (40 is GONE — last write wins)
atomic expression (SET paid = paid + ?): final = 100
```

The read is a **photograph**: correct at exposure time, historical by write time. Every fix in this notebook is the same move in different clothes — *stop acting on the photograph; make the write itself operate on, or verify, the current row*. The first clothing is the **atomic expression**: `SET paid_amount = paid_amount + :x` hands the arithmetic to the database, which applies it to whatever the row is *now*, under its own serialisation of writers. No lock in your code, nothing to retry, and the interleaving becomes harmless.

**The guarded write (compare-and-swap).** When the write depends on a condition — state-machine transitions above all — the condition rides *in* the write: `UPDATE invoices SET status='sent' WHERE id=:id AND status='draft'`. Two properties make this the workhorse. It is atomic: the check and the act are one statement, and the database evaluates the WHERE against the current row. And it *reports*: **`rowcount` is the verdict** — 1 means your transition won; 0 means the row moved under you, and you must not proceed. Captured, the incident's exact interleaving:

```text
naive : final status='sent', emails sent=['invoice email to customer']
        (the VOID was silently overwritten, and the email went out)
CAS   : void.rowcount=1, send.rowcount=0 -> status='void', emails sent=NONE
```

⚠️ The naive version's deepest sin is not the wrong final status — it is that **the loser never learned it lost**, so its side effect fired. A guarded write converts "silently overwrote someone" into "was told no", and *being told no* is what lets you suppress the email.

**The unique constraint as arbiter.** For double writes — "insert this at most once" — the check-then-act (`SELECT`… then `INSERT`) races exactly like 04.5's token check. The arbiter is the constraint: let both insert, and the database elects a winner:

```text
replica 1: INSERT ok — reminder sent
replica 2: IntegrityError: UNIQUE constraint failed: reminders.invoice_id, kind, period
```

This is 03.8's machinery finally shown from the *design* side: the constraint is not a safety net behind the check — it **is** the check, the only one that works across replicas, and the IntegrityError it throws is a named business verdict (03.8 maps it by constraint name) that the loser handles as "already done — fetch and continue" (02.8's replay semantics). 01.6's duplicate-invoice incident ends here, properly: the in-memory `_seen` dict's real replacement was never Redis-for-the-dict, it was a uniqueness the database enforces.

**Version columns and row locks** complete the kit. A **version column** generalises CAS to whole-row edits: read `(row, version)`, write `WHERE version = :read_version`, `rowcount 0` → reload-and-retry or surface upward — captured: both editors read version 1, first rowcount 1, second rowcount 0. Surfaced to clients it becomes HTTP's own optimistic concurrency: `ETag`/`If-Match` and `412 Precondition Failed` (01.4's validators, 02.x's contract). **Row locks** (`SELECT … FOR UPDATE`; PostgreSQL semantics in 05.x) are the pessimistic alternative: block rivals for the duration instead of detecting them after — a held loan with everything 03.11 taught about loans.

### Mental Model

> The database is the only room where every replica is actually present; everything your code "knows" about a row is a photograph from some moment ago. So never *act* on a photograph — **send the condition along with the act** (atomic expression, CAS, constraint) and read the verdict (`rowcount`, `IntegrityError`) as seriously as you'd read the row. A write that can't tell you it lost is a write that will someday lie for you.

## How It Works

The incident's interleaving — 04.5's diagram with transactions where tasks were:

```text
   invoices.status = 'draft'                     (two replicas, two humans)
   send-request (replica 3)              void-request (replica 7)
t1 SELECT status  -> 'draft' 📷
t2                                       SELECT status -> 'draft' 📷
t3                                       UPDATE ... SET status='void'   COMMIT
t4 photograph still says 'draft':
   UPDATE ... SET status='sent'  COMMIT      ← overwrites the void, no error
t5 outbox: enqueue send-email            ← the side effect of a stale check
       the accountant's void: nowhere. the email: on its way.

   with CAS, t4 becomes:
   UPDATE ... SET status='sent' WHERE status='draft'   → rowcount 0
   → transition REFUSED → no status write, no outbox row, 409 to the caller
```

The mapping from 04.5, made explicit — same bugs, escalating rooms:

```text
                     in one process (04.5)         across replicas (04.6)
read-modify-write    counter across an await       lost update on a row
check-then-act       token refresh stampede        double write / double send
the fix's home       the loop (Lock, task)         the WRITE ITSELF
                                                   (expression, CAS, constraint)
verdict for losers   lock acquired late /          rowcount == 0,
                     awaited the shared flight     IntegrityError by name
```

And the rule that makes losing *safe*: **side effects ride the winning transaction**. Ledgerly's email doesn't go out because a handler decided to send it; it goes out because 03.10's outbox row committed — and the outbox enqueue sits in the same transaction as the CAS transition. Rowcount 0 → transaction never commits → no outbox row → no email. The race's loser leaves no trace, which is the whole point: a lost race must cost *nothing*, not half of something.

## Code Example

Ledgerly's transition function after the incident — every status change in the codebase goes through it:

```python
# ledgerly/services/invoice_transitions.py
async def transition(session: AsyncSession, invoice_id: InvoiceId,
                     from_status: str, to_status: str) -> bool:
    """Compare-and-swap on the state machine. Returns whether WE won the
    transition; a False is a verdict to act on, never to ignore (04.6)."""
    result = await session.execute(
        update(Invoice)
        .where(Invoice.id == invoice_id, Invoice.status == from_status)
        .values(status=to_status, version=Invoice.version + 1)
    )
    return result.rowcount == 1


async def send_invoice(session, invoice_id: InvoiceId) -> None:
    if not await transition(session, invoice_id, "draft", "sent"):
        raise DomainError(problem=INVOICE_NOT_SENDABLE)        # 409 problem (02.9)
    await outbox.enqueue(session, SendInvoiceEmail(invoice_id))  # SAME txn (03.10)
    # commit happens at the request boundary (03.5): CAS win + email enqueue
    # are one atomic fact — lose the race, and neither exists
```

Two details carry the design. The return value is a `bool` the caller *must* branch on — the function's docstring says verdict, and the 409 problem type tells the client what happened in catalogue terms ("the invoice was no longer sendable"; their UI refreshes and shows the void). And the outbox enqueue shares the transaction: the guarded transition and its side effect commit or vanish together.

⚠️ The same bug wears ORM clothing so well that reviews wave it through:

```python
# ❌ the incident, written the way it actually looked (SQLAlchemy idiom)
invoice = await session.get(Invoice, invoice_id)     # the photograph
if invoice.status != "draft":
    raise DomainError(problem=INVOICE_NOT_SENDABLE)  # the check (stale in 1 line)
invoice.status = "sent"                              # mutate the copy
await outbox.enqueue(session, SendInvoiceEmail(invoice_id))
# flush writes: UPDATE ... SET status='sent' WHERE id=?   ← no status guard!
```

`session.get` → attribute assignment → flush emits an unconditional UPDATE: the ORM's convenience path *is* read-modify-write. Nothing here looks like a race; the fix is knowing that entity mutation compiles to an unguarded write, and reaching for `update().where(...)` — or the version column, which SQLAlchemy can check automatically (`__mapper_args__ = {"version_id_col": ...}` turns every flush into CAS and raises `StaleDataError` on rowcount 0).

> **Version note** — captured on SQLite (two connections, deterministic interleave; reproduce with `_lab/lab_04_06_lost_updates.py`). SQLite has no `SELECT … FOR UPDATE` — its pessimistic flavour is `BEGIN IMMEDIATE` — so the row-lock discussion here states PostgreSQL semantics without a local capture; 05.x captures them against real Postgres via the module compose file. The CAS, constraint and version-column behaviour shown is identical on both engines.

## Design Patterns / Tradeoffs

### Optimistic vs pessimistic vs "make it atomic"

- **Atomic expressions** (`SET x = x + :d`): no conflict *exists* — the database serialises writers anyway, so ride it. *Limits:* only for commutative, unconditioned changes (sums, counters). *Use first* whenever the update is arithmetic; the measured fix for every balance-shaped bug.
- **Optimistic — CAS / version column:** write cheap, detect conflict by `rowcount`, loser retries or surfaces 409/412. *Advantages:* no held locks, no waiting, honest failures; scales with low contention. *Disadvantages:* losers must have a retry-or-report path; under *high* contention, retry storms (a herd of losers is 04.5's stampede reborn — bound retries, add jitter). *Use when:* conflicts are exceptional — state machines, user edits, most of a CRUD API. **Ledgerly's default.**
- **Pessimistic — `SELECT … FOR UPDATE`:** block rivals up front; no losers, only waiters. *Advantages:* the only clean answer when the operation must read *several* rows consistently before deciding (apply-payment-across-allocations, 05.x's ledger work). *Disadvantages:* a lock is a loan (03.11) — held across an outbound call it becomes 04.3's incident with the DB as victim; deadlocks appear at two locks (order them); waiters queue invisibly like any pool. *Use when:* multi-row invariants, or contention so hot that optimistic retries thrash.
- **Unique constraints:** the only tool that makes *insertion* races safe, and the cheapest at-most-once there is. Not a fallback — the *design* (02.8's key row, 01.6's invoice numbers, the reminders table). Pair with 03.8's name-mapping so the verdict reaches the business layer intact.

**Recommendation:** atomic expression if the maths allows; CAS/version for transitions and edits, surfaced as 409/`If-Match` 412 at the API (the client is part of the concurrency story); `FOR UPDATE` for multi-row decisions; constraints under every "at most once" regardless of what else guards it. Escalate to 10.12's distributed locks only when the invariant outgrows one database.

## Production Scenario

**Ledgerly, Thursday 12 November, 11:35.** A customer's accounts-payable inbox receives invoice `inv_8c11d0` — €14,300, due in 14 days. Their accountant calls Ledgerly's customer directly: *we voided that this morning — the line items were wrong.* At 11:52 the customer opens a P2: the invoice shows **sent** in the dashboard, the void is simply gone, and their client is being dunned for a wrong amount.

### Symptoms

- The invoice row: `status='sent'`, and the email demonstrably delivered (outbox row, provider receipt). No trace of a void anywhere in the current state.
- The audit trail (04.4's, now trustworthy): `11:14:02.113 void by user u_at_customer` — followed at `11:14:02.291` by `sent by api key key_live_7ac`. Both actions **succeeded**; 180 ms apart; different replicas.
- No errors, no 5xx, no alerts — both requests returned 200-class responses to their callers. The only detector was a human who remembered voiding.
- Support sampling finds two prior occurrences in October — both written off at the time as "user error, probably didn't save".

### Diagnosis

1. **Alert → the audit trail.** Two successful, contradictory transitions 180 ms apart on different replicas is the entire story: this is not a bug in either handler but in what they *share*. 04.5's in-process suspects are eliminated by the replica split — only the row itself was common.
2. **Read the writer.** `send_invoice`: `session.get`, check `status == 'draft'` in Python, assign `status = 'sent'`, enqueue email, commit. The ORM idiom above — an unguarded UPDATE behind a stale photograph. The void's handler: same shape. Whichever committed second would erase the first; the customer's ERP fired the send (a scheduled batch) while the accountant clicked void.
3. **Why the email went out:** the send handler's check passed against its photograph, so the outbox enqueue ran — and its transaction committed *after* the void's, taking both the status overwrite and the email with it. The side effect wasn't an extra bug; it was the same bug's shadow.
4. **Confirm mechanically** with the lab's interleave: read-read-write-write reproduces `status='sent'` + email in four statements. The 180 ms window in production needs no load spike — just a human and a batch job touching one invoice in the same second, which month-end guarantees eventually.

### Root Cause

Both status transitions were check-then-act against a read copy — the ORM's get-mutate-flush emitting unconditional UPDATEs — so the second commit silently overwrote the first, and the send's side effect (already enqueued in its transaction, guarded only by the stale check) shipped a voided invoice; a lost update whose loser was never told, twice ignored in October because losing left no evidence.

### Fix

*Mitigation (same day):* the affected invoice corrected by hand (re-voided, customer's client emailed a cancellation note by the account team); a fleet-wide audit query — transitions within 5 s on one invoice from different actors — finds the two October cases for remediation.

*Permanent fix:* the `transition()` CAS function (Code Example) with the state machine's legal moves table; every handler branches on the verdict, mapping loss to the `invoice-not-sendable` / `invoice-not-voidable` problem types (409); the outbox enqueue stays inside the winning transaction so refused transitions ship nothing. The version column added and surfaced as `ETag` on invoice GETs; the dashboard sends `If-Match`, so a *human* editing a stale screen gets 412 and a refresh prompt instead of silently clobbering the ERP's action.

### Prevention

- **The incident closes into a named CI test** — the lab's interleave as a permanent gate, run against the real handlers:

```python
# tests/races/test_transitions_cannot_be_overwritten.py
async def test_send_and_void_interleaved_exactly_one_wins(two_sessions) -> None:
    """Read-check-act let 'sent' overwrite a committed void AND emailed a
    voided invoice (12 Nov). CAS: one winner, loser gets 409, no side
    effect from the loser (04.6)."""
    s_send, s_void = two_sessions                       # separate connections
    assert await transition(s_void, "inv_x", "draft", "void") is True
    assert await transition(s_send, "inv_x", "draft", "sent") is False
    assert await outbox_rows(invoice="inv_x") == []     # the loser shipped NOTHING
```

- **The contradictory-transition invariant** joins the nightly checks (03.13's family): any invoice with two committed transitions from the same source status is a bug *by definition* — the query that found October's cases now runs forever.
- Review rule beside 04.5's: `session.get(...)` followed by a status/amount assignment is a finding — conditioned writes go through `update().where()` or the version column, and **every guarded write's rowcount is read by someone**.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...two requests read-modify-write one row? | Last write wins; the other vanishes without error (measured: the 40 is gone). Atomic expression or CAS — the fix lives in the write. |
| ...two requests race a state transition? | Unguarded: contradictory successes, side effects from stale checks. CAS: rowcount elects one winner; loser gets a 409 problem and ships nothing. |
| ...both replicas insert "the first" row? | The unique constraint arbitrates; the loser's IntegrityError maps by name (03.8) to "already done — fetch and continue" (02.8). |
| ...the guarded UPDATE matches zero rows? | That IS the signal. Unread rowcount = the bug reinstalled with extra steps; every caller branches on it. |
| ...optimistic losers retry hot? | A retry herd is 04.5's stampede at the database. Bound retries, jitter them, and above some contention switch the row to pessimistic. |
| ...a row lock is held across an outbound call? | A loan held through 04.3's weather: waiters (and their pool slots, 03.11) queue behind a tax API's bad day. Locks span statements, never awaits to third parties. |
| ...the side effect isn't in the transaction? | Then losing the race still ships half an action — email without status, status without email. Outbox in the same transaction (03.10), always. |
| ...the invariant spans two databases or a queue? | Neither CAS nor constraints reach across systems — that is idempotent consumers (11.x) and sagas (19.x); don't fake it with hope. |

## Common Pitfalls

**Checking in Python, acting in SQL.** Get-mutate-flush is check-then-act with an ORM accent; the flush's UPDATE carries no guard. *Instead:* `update().where(condition)` or the mapper's version column; treat entity mutation of contested fields as a review finding.

**Ignoring rowcount.** An UPDATE matching zero rows "succeeds" in every language binding. *Instead:* rowcount is the verdict — return it, branch on it, test it.

**Constraints as safety nets.** "The SELECT check catches it; the constraint is just in case" — the SELECT catches nothing across replicas; the constraint is the *only* check. *Instead:* design the constraint first, map its name (03.8), let losers handle a clean verdict.

**Side effects outside the winning transaction.** The email fired on a stale check's say-so. *Instead:* effects ride the outbox in the CAS's transaction — losers leave no trace.

**Version checks without a client story.** A 500 on `StaleDataError` punishes the user for concurrency. *Instead:* 409/412 problem types, ETag/If-Match on the API, refresh-and-retry in the UI.

**Pessimistic locks as the default.** Every reader of the row becomes a waiter; deadlocks arrive with the second lock. *Instead:* optimistic by default; locks where multi-row consistency demands them, ordered and brief.

## How to Test This

- The interleaved-transition test above: two sessions, both orders, assert single winner + empty outbox for the loser.
- A concurrent-increment test: N tasks apply payments via the atomic expression; assert the exact sum (the lab's section A as a gate).
- A constraint-verdict test: double-insert the reminder row; assert the second maps to the *named* problem, not a 500 (03.8's contract).
- The nightly contradictory-transition invariant — the detector for whatever this notebook missed.

## Interview Questions

1. *Explain.* What is a lost update, and why does no error accompany it? — Read-modify-write across transactions: the second write applies arithmetic/state computed from a stale read, overwriting the first. Both UPDATEs are individually valid; the database was never told they were related.
2. *Debug this.* An invoice a user voided arrives at the customer by email; the row says "sent"; the audit log shows both actions succeeding 180 ms apart. — Unguarded state transitions (ORM get-mutate-flush): CAS with rowcount, side effects into the same transaction, 409 for the loser.
3. *Explain.* Why is `UPDATE ... WHERE status='draft'` + rowcount fundamentally different from `SELECT`-check-then-`UPDATE`? — The condition is evaluated atomically against the current row under write serialisation; the select's check is a photograph that expires before the update runs.
4. *Design.* At-most-once monthly reminders across N scheduler replicas. — Unique `(invoice, kind, period)`; all replicas insert; IntegrityError by name = already sent; the send side effect rides the inserting transaction via the outbox.
5. *Explain.* Optimistic vs pessimistic concurrency — decision criteria? — Contention frequency and invariant shape: exceptions → CAS/version (no locks, losers retry/409); multi-row consistent decisions or thrashing retries → FOR UPDATE, held briefly, ordered, never across external awaits.
6. *Design.* Surface row versioning to API clients end-to-end. — Version column → ETag on GET; mutations require If-Match; version mismatch → 412 problem; UI refreshes and replays. HTTP's CAS, closing the loop from 01.4's validators.
7. *Explain.* Why must the outbox enqueue share the CAS's transaction? — So the side effect exists iff the transition committed: losers ship nothing, winners ship exactly once (with 03.10's relay), and "half an action" becomes unrepresentable.

## Key Takeaways

- 04.5's bugs cross the process line intact: read-modify-write becomes the lost update, check-then-act becomes the double write — and the only room with everyone present is the database.
- A read is a photograph. Move the logic into the write: atomic expressions for arithmetic, CAS (`WHERE` + old state) for transitions, constraints for insertions — measured fixes, all of them.
- **rowcount is the verdict.** A guarded write that matched nothing is the race telling you that you lost; a codebase that doesn't read it has reinstalled the bug politely.
- Unique constraints are the design, not the net — the one at-most-once that works across replicas, delivering named verdicts through 03.8's mapping.
- Losers must lose *completely*: side effects ride the winning transaction's outbox, so a refused transition ships nothing and a silent overwrite becomes unrepresentable.
- Optimistic by default (409/412 + ETag makes clients part of the story), pessimistic for multi-row decisions — and a lock is a loan with every loan rule from 03.11 attached.
- Wrong-data races alert nobody twice: the audit trail plus a contradictory-state invariant are the detectors; October's two "user errors" were this incident, unwitnessed.
