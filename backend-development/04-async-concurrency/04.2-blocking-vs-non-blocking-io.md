## Concept

### Plain-English Explanation

04.1 taught the tax of many small slices. This notebook is the degenerate case: one call that does not come back. **Blocking** is not about a call being slow — awaiting a slow database parks the coroutine and the loop serves everyone else. Blocking means the call *holds the thread while it waits*: a sync socket read sits in the kernel with the loop's only thread hostage, and for that duration the process does nothing — no requests, no accepts, no timers, no health-check responses, no metrics. A 2-second blocking call is not a slow request; it is a 2-second total outage of the worker, repeated on every call.

The trap is that nothing in your code's *shape* warns you. The handler says `async def`; the call looks like any other; staging is fast so the freeze is 80 ms and invisible. Then the dependency has a bad day, and every one of its bad seconds is transplanted, whole, into your event loop.

### Technical Explanation

**What non-blocking actually means.** An awaited I/O call registers the socket with 04.1's selector and *suspends the coroutine* — the thread returns to the loop immediately; the OS signals readiness later. A blocking call never talks to the selector: it issues a synchronous `recv` and the thread stays inside it until the kernel returns. The event loop cannot preempt (04.1) and cannot even *know* — from its perspective, one slice is simply taking forever.

Three tiers exist in real codebases, and the lab measures all three — a bystander `/v1/ping` probed mid-call while a handler waits on a 2-second provider:

```text
idle baseline                     -> /v1/ping:       8 ms
/v1/rate-async-shared             -> during the call:       4 ms   ← truly parked
/v1/rate-async-per-request        -> during the call:     382 ms   ← "async" hiding sync
/v1/rate-sync-async-def           -> during the call:    2563 ms   ← the loop is gone
```

Tier one: the lifespan-held `AsyncClient` (03.9's rule), awaited — the loop never notices the provider's 2 seconds. Tier three: a **sync client inside `async def`** — the bystander pays the full remaining call. ⚠️ Tier two is the education: `httpx.AsyncClient()` constructed *per request* is async in name, but its constructor **builds an SSL context synchronously** — a cert-store load worth ~350 ms on this machine — executed as one 04.1 slice on the loop. "Async library" is not a property that distributes over every method; construction, first-use imports, and helper paths can all be sync. This is *why* 03.9 put the client in lifespan, stated at the mechanism level.

**The usual suspects.** Sync socket stacks (`requests`/`urllib3`, vendor SDKs built on them, `psycopg2`, `smtplib`, `boto3`), `time.sleep` in someone's retry helper, file I/O (fine on a local SSD until it's an NFS mount), logging handlers that do network I/O (`SMTPHandler`, syslog-over-TCP — which fire *during* incidents), and CPU-heavy calls (`bcrypt`, compression, big JSON — 04.7's subject, same symptom). One honest subtlety: `socket.getaddrinfo` (DNS) is sync, but asyncio routes it through the 03.6 executor for you — resolver trouble costs threadpool tokens, not the loop.

**Why your tests said this was fine.** The blocking call usually enters through a seam your tests fake: the suite replaced the tax client at the service boundary, so the vendor SDK's `requests` stack never executed under 04.1's `strict_event_loop` fixture. Mocks verify your logic; they *unplug the very code whose runtime behaviour is the bug*. Detection has to come from things that don't need the call to run in CI — the import guard — and from watching the real process — the sampler and the stack dump.

### Mental Model

> `async def` is a promise about the gaps between awaits — and nothing enforces it. Whether a call blocks is a property of its *implementation*, invisible at the call site, all the way down the stack. So don't trust shape; trust evidence: the loop-lag sampler says *whether* the loop freezes, and a stack dump taken mid-freeze says *where*. The stack is the one artefact that ends the argument.

## How It Works

Anatomy of one frozen call, with everything that stops:

```text
t=0      handler calls vendor_sdk.rate_for(addr)     ← sync socket write+read begins
         ┌────────────── loop thread inside recv() — 04.1's till is EMPTY ─────────────┐
t=0..2s  │ new connections: kernel backlog only (accept() never runs)                  │
         │ parked tasks whose I/O completed: stay parked (nobody polls the selector)   │
         │ timers, keepalive pings (03.12), lag sampler: none fire                     │
         │ /health, /ready: no response → probe timeouts begin (03.14)                 │
         └─────────────────────────────────────────────────────────────────────────────┘
t=2s     recv returns → loop resumes → the backlog BURSTS through at once
         → repeat per call: the fleet stalls in WAVES, one provider-latency wide
```

The signature table this module accumulates, extended:

```text
slow dependency (awaited)   degradation concentrated in its callers · lag flat
04.1 many small slices      uniform p99 climb · lag SMOOTH and elevated · CPU pegged
04.2 blocking call          stalls in waves · sampler shows GAPS then one giant sample
                            · probes flake → restarts · CPU mostly IDLE (thread asleep)
```

The sampler's view deserves its own capture, because it is counter-intuitive — the metric cannot report a freeze *during* the freeze (the sampler is a task on the frozen loop too):

```text
t= 0.3s  lag=    9.4 ms
t= 0.5s  lag=    3.3 ms
         (silence — no samples emitted for ~2.6s)
t= 3.4s  lag= 2618.1 ms ############################################################
t= 3.6s  lag=    8.8 ms
```

Gaps in the series *are* the signal, and the giant sample is the freeze measuring itself on the way out. Alerting must treat "no data" from this metric as seriously as a bad value — the 03.13 lesson (absence as evidence) at metric granularity.

## Code Example

Finding the call in a live process, with stdlib alone: `faulthandler.dump_traceback_later` arms a watchdog *thread* (immune to the frozen loop) that dumps every thread's stack if not cancelled in time. Captured mid-freeze:

```text
Timeout (0:00:01)!  ...  Thread 0x… (the frozen event loop):
File ".../httpcore/_backends/sync.py", line 128 in read          ← a SYNC socket read
File ".../httpcore/_sync/http11.py", line 217 in _receive_event
File ".../httpcore/_sync/http11.py", line 177 in _receive_response_headers
File ".../httpcore/_sync/http11.py", line 106 in handle_request
File ".../httpcore/_sync/connection.py", line 103 in handle_request
```

`_sync/` in the path of an async worker's main thread is the entire diagnosis — no hypothesis survives contact with this dump. In production Ledgerly arms it as a flight recorder, triggered only when the freeze is already underway:

```python
# ledgerly/observability/freeze_recorder.py — supervised per 03.9
async def freeze_recorder(threshold: float = 1.0) -> None:
    """Arms a watchdog before each sleep; a healthy loop cancels it in time.
    If the loop freezes past `threshold`, the WATCHDOG THREAD (unaffected by
    the freeze) dumps all stacks to the log — the incident records itself."""
    with open(settings.freeze_dump_path, "a") as sink:
        while True:
            faulthandler.dump_traceback_later(threshold, file=sink, exit=False)
            try:
                await asyncio.sleep(threshold / 2)     # cancel comfortably early
            except asyncio.CancelledError:
                faulthandler.cancel_dump_traceback_later()
                raise                                  # 03.9: never swallow shutdown
```

(`py-spy dump --pid <pid>` is the richer external answer — full native stacks, no pre-arming, attachable to any wedged process; the stdlib recorder's advantage is that it is *already there* at 03:00.) And the guard that works where mocks blind CI — imports don't lie:

```python
# tests/contract/test_no_sync_io_in_request_path.py — the incident's named closure
BANNED = {"requests", "urllib3", "boto3", "smtplib", "psycopg2", "time.sleep"}

@pytest.mark.parametrize("module", request_path_modules("ledgerly"))
def test_request_path_imports_no_sync_io(module: ast.Module) -> None:
    """The vendor SDK entered through a seam the test suite fakes, so no test
    ever RAN its blocking socket under the strict loop. Its imports were in
    plain sight the whole time (04.2)."""
    hits = imported_names(module) & BANNED
    assert not hits, f"{module.path}: sync I/O import(s) {sorted(hits)} — " \
                     "these block the event loop; use the lifespan httpx client " \
                     "or route through the executor (03.6) deliberately"
```

Captured against the incident's tree: `routers/invoices.py ok · services/tax.py ok · services/tax_vendor_sdk.py FAIL — ['requests', 'urllib3']`.

> **Version note** — captured on Python 3.14/Windows: `faulthandler` labels stack blocks `Thread 0x…` without names (the frozen loop is the last block), and the per-request `AsyncClient` cost (~350 ms) is dominated by the Windows cert-store load — Linux pays less, but pays it on the loop all the same. Reproduce everything with `_lab/lab_04_02_blocking.py`.

## Design Patterns / Tradeoffs

### Integrating a sync-only SDK (the incident's actual decision)

- **Reimplement the thin part on the shared `AsyncClient`.** The vendor SDK did token refresh plus one GET; ~40 lines on the lifespan client (03.9). *Advantages:* no thread cost, no hidden paths left, full 04.8 timeout/cancellation semantics. *Disadvantages:* you now own protocol drift when the vendor changes auth. *Use when:* the surface you use is small and stable — **Ledgerly's choice**.
- **Wrap every call in `run_in_executor`** with a *dedicated, bounded* executor and a timeout. *Advantages:* keeps the vendor's code exactly as shipped; mechanical. *Disadvantages:* spends threads per in-flight call (03.6 arithmetic — under provider slowness you now exhaust a pool instead of freezing a loop: a better failure, still a failure); cancellation cannot interrupt the sync call (04.8). *Use when:* the SDK is large, cryptographic, or churns too fast to reimplement. ⚠️ *Never* the shared default executor — that couples the vendor's bad day to every `def` route.
- **Go sync deliberately:** make the calling endpoints `def` so the whole call chain lives on the threadpool. *Advantages:* honest; no async pretence. *Disadvantages:* the 03.6 budget now prices this route; response-path still async. *Use when:* a route is wholly built on sync libraries anyway.
- **The vendor's async SDK**, when one exists: evaluate it as a *new dependency*, not as a fix — tier two above was an async library blocking the loop from inside.

**Recommendation:** smallest honest surface first (reimplement thin, wrap thick, `def` when the route is sync-native) — and whichever you pick, the import guard pins the decision so the next upgrade cannot quietly reintroduce tier three.

## Production Scenario

**Ledgerly, Wednesday 14 October, 15:05.** Three weeks earlier, a release replaced the hand-rolled tax-provider calls with the provider's official Python SDK — it handles their new OAuth token rotation, review said "less code we own". Today the provider's status page reads *elevated latency* (their p99: 300 ms → 2.5 s). At 15:05 Ledgerly's own pages start: readiness probe failures, then the orchestrator restarting api replicas — which kills their in-flight requests (03.14), which customers feel as resets.

### Symptoms

- Replicas stall **in waves**: 1–3 s windows where a replica answers nothing at all — not slowly, *nothing* — then a burst of completions. `/ready` misses land exactly in the windows; restarts follow; the restart itself hard-drops whatever the freeze hadn't already delayed.
- `event_loop_lag_ms`: **gaps** in the series with 2,000–3,000 ms samples at the gap edges — the 04.2 signature, nothing like 8 October's smooth 40–60 ms (04.1).
- CPU: near idle. Traces: requests that span a freeze show the time *inside* the tax span this time — but every *other* request on the replica shows it as unattributed gap.
- 5xx from the API: few. The damage is timeouts, resets from restarts, and the fleet's capacity sawtoothing as the orchestrator "heals" healthy-but-frozen processes.

### Diagnosis

1. **Alert → Metrics.** Wave-stalls + sampler gaps + idle CPU eliminate 04.1's queueing (smooth lag, pegged core) and any awaited-dependency theory (parked awaits don't stop `/ready`). Something is holding the loop's thread outright.
2. **Correlate the waves.** Stall windows match the provider's latency graph 1:1. But an *awaited* slow provider cannot freeze a loop — so the provider is the trigger, not the mechanism.
3. **Take the stack.** `py-spy dump` against a wedged replica (the freeze_recorder went in *after* this incident): main thread in `urllib3 … connectionpool.py … recv` under `vendor_tax_sdk/client.py:  rate_for` under an `async def` service method. The argument is over in one screenful: the SDK is `requests` underneath, and every call transplants the provider's latency into the loop, whole.
4. **Why nothing caught it earlier:** the provider was *fast* for three weeks — 100–300 ms freezes lost in normal jitter; CI faked the tax client at the service seam, so the SDK's sockets never ran under the strict loop; and the sampler had no alert on gaps. The bug shipped healthy and waited for someone else's incident.

### Root Cause

The vendor SDK is synchronous (`requests`/`urllib3`) and was called directly from async handlers, so each tax lookup held the event loop's thread for the provider's full round-trip; when the provider's p99 rose to seconds, every call became a seconds-long total stall of its worker — surfacing as wave-stalls, probe failures, and orchestrator restart churn rather than as errors.

### Fix

*Mitigation (15:24):* roll back to the previous release (the pre-SDK httpx path — old but correct); stalls stop with the deploy. The orchestrator's restart storm ends on its own once probes pass.

*Permanent fix:* token rotation reimplemented on the lifespan-held `AsyncClient` (~40 lines, the Tradeoffs decision); the SDK removed from the request path. While fixing, the audit the incident forced also found tier two — a **per-request `AsyncClient`** in the PDF-renderer service (the measured ~350 ms sync SSL build per call) — moved to the shared client the same day.

### Prevention

- **The import guard** (`test_no_sync_io_in_request_path`, above) in CI — it fails on the SDK's `requests` import in seconds, needs no network, and is immune to mocking.
- **The freeze recorder** armed in every worker: the next freeze writes its own stack before anyone is paged.
- **A gap alert on the sampler**: `absent(event_loop_lag_ms) for 2 sampling intervals` pages — treating metric silence as the signal it is.
- The strict-loop CI fixture (04.1) now runs the tax path against **transport-level fakes** (respx) instead of service-seam fakes, so the real httpx code executes under the 20 ms budget — mocks moved down a layer so they stop hiding the layer that matters.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...a dependency gets slow but is properly awaited? | Requests to its callers slow; everyone else unaffected; lag flat. Not this notebook — that's timeout territory (04.8). |
| ...a sync call sneaks into one handler? | Every invocation freezes the whole worker for the call's duration; damage scales with the *dependency's* latency, not yours. |
| ...the freeze outlasts the probe window? | 03.14's machinery "heals" the replica by killing it — in-flight requests die, capacity sawtooths. A watchdog restart is a symptom amplifier, not a fix. |
| ...DNS is slow? | `getaddrinfo` rides the executor, not the loop: cost lands as threadpool tokens (03.6). Different meter, different fix (caching resolver). |
| ...logging is the blocker? | `SMTPHandler`/socket handlers fire on ERROR — i.e., mid-incident, exactly when you log most. Queue handlers (15.x); never network-log synchronously on the loop. |
| ...the blocking call is CPU, not a socket? | Same freeze signature; different remedy (processes, 04.7). The stack dump distinguishes: `recv` vs your own frames. |
| ...the SDK upgrade re-adds a sync path? | The import guard fails the PR; the strict-loop fixture catches transport-level regressions the guard's blocklist misses. |
| ...you need the stack from a frozen prod replica right now? | `py-spy dump --pid` — no restart, no code change; or read the freeze recorder's file if armed. Never bounce the replica first: the stack dies with it. |

## Common Pitfalls

**Trusting `async def` as a property of the body.** The keyword promises nothing about callees. *Instead:* trust the sampler and the dump; audit seams where sync stacks enter (SDKs, helpers, logging).

**Faking dependencies at the service seam in tests.** The fake absorbs the blocking call and CI certifies the bug. *Instead:* transport-level fakes (respx) so real client code runs under the strict loop; the import guard for what tests can't execute.

**Constructing clients per request.** Tier two: async constructors doing sync work (SSL contexts) on the loop, measured at ~350 ms. *Instead:* lifespan-held clients (03.9) — construction is a startup cost, not a request slice.

**Wrapping the SDK in the *default* executor.** Now the vendor's latency exhausts the shared 40 threads and takes 03.6's routes with it. *Instead:* dedicated bounded executor, with a timeout, sized like any pool.

**Diagnosing by restarting.** The wedged replica is the evidence; a bounce destroys the stack and reschedules the freeze. *Instead:* dump first (py-spy/recorder), then recycle.

**Alerting only on lag *values*.** A frozen loop emits nothing; your graph shows a polite gap. *Instead:* alert on absence; read the giant edge-sample as the freeze's tombstone.

## Interview Questions

1. *Explain.* What exactly distinguishes a blocking call from an awaited slow call? — The awaited call suspends the coroutine and returns the thread to the loop (selector-driven resume); the blocking call holds the thread inside the syscall, so the worker serves nothing for the duration.
2. *Debug this.* Replicas freeze in waves, health probes flake, the orchestrator restart-loops them; CPU is idle and your lag metric has holes in it. — Blocking call on the loop, duration set by some dependency's latency; stack-dump a wedged replica (py-spy/faulthandler) and read the `_sync/` frames; check what shipped weeks ago, not today.
3. *Explain.* Why did a fully green test suite ship this? — The blocking code entered through a seam the tests faked; mocks unplug the code whose runtime behaviour is the bug. Guards that work: import blocklists, transport-level fakes, live canaries.
4. *Design.* Your team must use a large sync-only SDK. Integrate it safely. — Dedicated bounded executor + timeouts around every call; never the default pool; budget the threads like 03.6; or reimplement the thin slice you actually use on the lifespan client.

6. *Design.* Detection for this class across a fleet. — Strict loop in CI (transport fakes), import guard, always-on lag sampler with a *gap* alert, pre-armed faulthandler flight recorder, py-spy in the runbook. Each layer catches what the previous can't run.
7. *Explain.* Distinguish the telemetry of: awaited-slow dependency, 04.1 slice pressure, and a blocking call. — Concentrated slowdown + flat lag; uniform slowdown + smooth high lag + pegged core; wave-stalls + sampler gaps + idle CPU + probe failures.

## Key Takeaways

- Blocking = holding the thread, and on a one-thread loop that is a total stall of the worker: no accepts, no timers, no probes, no metrics — a per-call outage sized by the *dependency's* latency.
- Three tiers, measured: awaited on a shared client (4 ms bystander), "async" hiding sync construction (382 ms), sync-in-async (the full 2.5 s). `async def` is a promise nothing enforces.
- The signature: wave-stalls, sampler **gaps** with giant edge samples, idle CPU, probe-failure restarts — cleanly distinguishable from 04.1's smooth lag and from any awaited dependency.
- The stack dump is the argument-ender: `faulthandler.dump_traceback_later` as an always-armed flight recorder, `py-spy dump` for any wedged pid — dump before you bounce.
- Mocks at the service seam certify this bug; move fakes to the transport layer and add the import guard, which needs no execution at all.
- Sync SDKs: reimplement thin, executor-wrap thick (dedicated + bounded + timed), go `def` when the route is sync-native — and pin the choice in CI.
- Lifespan-held clients are loop protection, not tidiness: construction is sync somewhere, so pay it once at startup (03.9, now with the measurement).
