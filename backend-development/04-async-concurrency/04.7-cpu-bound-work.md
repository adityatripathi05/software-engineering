# 04.7 CPU-Bound Work and Event-Loop Blocking

> **Prerequisites:** 04.1 (the lag sampler, slices) · 04.2 (freezes, the stack dump) · 03.6 (the threadpool) · 03.9 (lifespan-owned infrastructure) · modern-python 11.x (GIL, processes — assumed)
> **What you'll learn:**
> - Place any CPU-heavy call in the four-row matrix — inline, thread+GIL-holding, thread+GIL-releasing, process — from measurements, not folklore
> - Explain why a GIL-holding thread makes the loop *limp* rather than freeze, and why that limp is still a fleet-wide tax
> - Know which common "CPU" calls release the GIL (KDFs, compression, hashing) and get threads for free via 03.6's pool
> - Run a process pool as lifespan infrastructure with honest economics: start-up, pickling, and what work is big enough to earn the trip
> - Ask the question that precedes all of the above: does this CPU work belong in the request path at all?
> **Level:** Intermediate

> ⚡ **Wednesday 18 November, 16:20** — four minutes after a security-hardening deploy, the loop-lag alert fires on every replica at once; p99 is climbing past two seconds. The cause: the fix was aimed at the wrong kind of secret.

## Concept

### Plain-English Explanation

04.2's freezes came from *waiting* wrongly — a thread parked in a sync socket. This notebook's freezes come from *working*: the stack dump shows no `recv`, no `_sync/` frames, just your own code, busy. CPU-bound work is the one load the event loop fundamentally cannot help with — the loop's whole trick is doing something else while I/O waits, and computation never waits. So the question is purely *where the burning happens*: on the loop thread (a freeze, 04.2's symptom with your name on the stack), on a worker thread (it depends — on the GIL), or in another process (clean, at a price). This notebook measures all four homes with 04.1's sampler and gives you the matrix to place any workload.

### Technical Explanation

**The matrix, measured** — one ~250 ms CPU task, four homes, the lag sampler watching the loop throughout:

```text
strategy                             wall   lag p50   lag max
inline in the handler               0.23s     5.9ms   228.9ms   ← frozen for the task
thread + GIL-HOLDING work           0.31s    21.4ms    29.7ms   ← the LIMP
thread + GIL-RELEASING work (kdf)   0.44s     5.8ms    12.6ms   ← clean
process pool (pure python)          0.28s     5.8ms    15.1ms   ← clean
```

(5.8 ms is this platform's timer floor — 04.1's Version note; read the rows against it.)

**Row one** is 04.2's freeze with a different fingerprint: max lag equals the task duration, because the loop *is* the thread doing the work. **Row two** is this notebook's own discovery: pushing pure-Python work to 03.6's threadpool does *not* free the loop — both threads want the same interpreter, and the **GIL** hands over only at the switch interval (`sys.getswitchinterval()` = 5 ms). The loop lives, but every slice of it queues behind up to 5 ms of someone else's bytecode: a standing ~20 ms tax on *every* request's *every* await, which is 04.1's lag law fed from a thread. ⚠️ It looks fixed — no freeze, no alert in light testing — and ships a fleet-wide latency floor.

**Row three** is the escape most engineers don't know they already have: C extensions doing real work **release the GIL** around their hot sections — `hashlib` (including `pbkdf2_hmac`/scrypt), `zlib`/compression, most crypto primitives, NumPy's kernels. For these, 03.6's ordinary threadpool is the correct home: the loop stays at the floor while OpenSSL burns a different core. Whether a call releases the GIL is a *fact about the library*, checkable exactly the way this lab checks it — run it in a thread and watch the sampler. **Row four**, the process pool, is the home for pure-Python (GIL-holding) burns — full isolation, real parallelism, and costs the next section prices.

**Process-pool economics, measured:**

```text
create pool + first trivial submit :   547.8 ms     ← spawn: lifespan pays this, once
warm trivial submit round-trip     :     1.5 ms     ← pickle + IPC, every call
warm submit of the real 250ms task :   250.7 ms     ← overhead vanishes into real work
```

Half a second to stand workers up means the pool is **lifespan infrastructure** (03.9) — created once, warmed, sized (workers × per-worker memory is a budget like every 03.6/04.3 budget), never built per request. The 1.5 ms round-trip prices admission: arguments and results cross by pickle, so work worth sending is *much* bigger than its serialised size, and the 250 ms task's overhead disappears while a 2 ms task's overhead is the task.

**The zeroth question.** Before choosing a row: should this burn be in a request at all? A CPU cost that scales with input size, sits on a hot path, or exceeds the 04.1 slice budget by an order of magnitude is usually 02.10/03.10's territory — an operation handled by a worker process, where the matrix still applies but the audience is a queue, not a waiting socket.

### Mental Model

> The loop is a scheduler, not an engine — it can only *arrange* work, never absorb it. CPU work is a fire: inline, it burns the scheduler's own desk; in a thread it shares the scheduler's oxygen (the GIL) unless the library brings its own (releases it); in a process it burns in another building, and you pay freight (pickle) both ways. Place fires by measurement — the sampler tells you in one run — and remember the cheapest fire is the one you moved out of the request entirely.

## How It Works

Why the thread limps — the GIL handover, on 04.1's timeline:

```text
loop thread:     [slice][wait GIL·····][slice][wait GIL·····][slice]
worker thread:   [·····bytecode 5ms···][·····bytecode 5ms···][····]
                        ▲ switch interval: the interpreter OFFERS a handover
                          every 5ms of bytecode — the loop runs in the gaps
result: no freeze, no 04.2 signature — just +15-25ms on every loop slice,
        which the lag law (04.1) multiplies into every request's p99

kdf/zlib in a thread:   [acquire GIL][release → OpenSSL burns another core][acquire]
                        the loop keeps the GIL almost the whole time: CLEAN
process pool:           other interpreter, other GIL, other core: CLEAN + freight
```

And the decision path, as the review question sequence:

```text
CPU cost in a request path?
 ├─ can it leave the request? (worker/operation, 02.10/03.10)   ── best row: none
 ├─ is it small & bounded? (< the 20ms slice budget, 04.1)      ── inline is FINE
 ├─ does the library release the GIL? (measure: sampler + thread)
 │    ├─ yes ── 03.6 threadpool, semaphore-capped (04.5)         ── row three
 │    └─ no ─── lifespan process pool, sized & warmed            ── row four
 └─ never: pure-Python burn inline or "fixed" into a thread untested — rows one & two
```

The cap matters on both worker rows: N concurrent KDF calls are N cores of demand — a semaphore (04.5's budget primitive) keeps CPU-heavy endpoints from bidding the machine away from the loop, exactly as 04.3 capped connections.

## Code Example

The legitimate version of the incident's workload — password verification (module 08's real need), homed correctly:

```python
# ledgerly/security/passwords.py (08.x consumes this)
_KDF_CAP = asyncio.Semaphore(2)     # at most 2 cores of KDF at once (04.5):
                                    # auth bursts must not starve the loop's core

async def verify_password(candidate: str, stored: StoredHash) -> bool:
    """pbkdf2_hmac releases the GIL (measured: loop stays at the floor), so
    03.6's ordinary threadpool is the right home — no process freight."""
    async with _KDF_CAP:
        derived = await anyio.to_thread.run_sync(
            hashlib.pbkdf2_hmac, "sha256",
            candidate.encode(), stored.salt, stored.iterations)
    return hmac.compare_digest(derived, stored.hash)
```

And the pool for genuinely pure-Python burns, owned like every other resource:

```python
# ledgerly/lifespan.py (extending 04.3's registry)
@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[dict]:
    cpu_pool = ProcessPoolExecutor(max_workers=settings.cpu_pool_workers)  # cores-1
    cpu_pool.submit(int, 1).result()          # warm at startup: spawn's ~550ms
    try:                                      # is a boot cost, never a request's
        yield {"clients": clients, "engine": engine, "cpu_pool": cpu_pool}
    finally:
        cpu_pool.shutdown(cancel_futures=True)
```

⚠️ What the incident actually shipped, for contrast — and the reason its rollback was also the *correct* end state:

```python
# ❌ the hardening PR: a password KDF applied to API keys, inline
async def resolve_api_key(key: str) -> Tenant:
    key_hash = hashlib.pbkdf2_hmac("sha256", key.encode(), SALT, 600_000)
    #          ~250ms of CPU on the loop thread, on EVERY request        ⚠️
    return await lookup_by_hash(key_hash)

# ✅ the revert IS the fix: api keys are 256-bit random values. A KDF's slow-
#    ness exists to punish guessing of LOW-entropy secrets (passwords); against
#    a 2^256 space it buys nothing. Fast hashing is the correct design:
async def resolve_api_key(key: str) -> Tenant:
    return await lookup_by_hash(hashlib.sha256(key.encode()).digest())  # ~2µs
```

> **Version note** — captured on a standard-GIL CPython 3.14 build (the pinned stack); the 5.8 ms lag floor is Windows' timer granularity (04.1). On the **free-threaded** 3.13+/3.14 builds the GIL-holding-thread row changes character (bytecode threads genuinely parallelise); the other three rows and all the economics are build-independent. `sys.getswitchinterval()` default 5 ms. Reproduce with `_lab/lab_04_07_cpu_bound.py`.

## Design Patterns / Tradeoffs

### The four homes (and the zeroth)

- **Out of the request entirely** (02.10 operation + worker): for burns that scale with input, exceed hundreds of ms, or serve patience-tolerant needs (exports, renders). *Cost:* asynchrony reaches the client (polling/webhooks). The best row is not being in the matrix.
- **Inline**: for bounded small work — validation, modest serialisation — under 04.1's 20 ms slice budget. *Failure mode:* "small" that grows with input (a list, a file) until it's row one; bound the input (02.5's caps) or move homes.
- **Threadpool (03.6)** — *only* for GIL-releasing calls: KDFs, compression, hashing, image codecs (measure!). *Advantages:* zero freight, shared pool already exists. *Failure modes:* assuming release (row two ships silently — the measured 21 ms limp); uncapped bursts bidding for every core; pool tokens spent (03.6's budget).
- **Process pool**: pure-Python burns that must stay request-attached. *Advantages:* true isolation and parallelism; a worker crash is a pool event, not a process death. *Failure modes:* per-request pool creation (measured 548 ms); shipping big arguments (pickle freight both ways); unbounded workers vs container CPU limits (03.14); forgetting `cancel_futures` at shutdown (04.8/04.9 pick this up).

**Recommendation:** escape the request if the work lets you; inline under the slice budget; threads for measured GIL-releasers behind a semaphore; a warmed, lifespan-owned, capped process pool for the pure-Python remainder. And re-measure on library upgrades — GIL release is an implementation detail that version bumps may change; the sampler test is one run.

## Production Scenario

**Ledgerly, Wednesday 18 November, 16:20.** A security-hardening PR ships: a pen-test prep review (16.x is on the calendar) flagged that API keys were stored as plain SHA-256 — "unsalted fast hash" pattern-matched to the password-storage anti-pattern, so the fix applied `pbkdf2_hmac` with 600k iterations to API-key lookup. Reviewed, approved, merged: defence in depth.

At **16:24**, `event_loop_lag_ms` pages for every replica simultaneously — p50 lag 300–600 ms and climbing with traffic. p99 latency crosses 2 s. This time, nobody spends twenty minutes theorising.

### Symptoms

- Loop lag elevated and *smooth* — 04.1's signature, not 04.2's gaps — but the onset is a deploy edge, not a traffic edge, and the lag's floor tracks request rate exactly: every request now carries one mandatory ~250 ms slice.
- CPU: the api container's core pegged (03.14's per-process view); host graph placid as ever.
- A staging stack-sample during the page (04.2's runbook, now muscle memory): the loop thread mid-`pbkdf2_hmac`, under `resolve_api_key`, under the auth dependency — **your own frames**, the 04.7 fingerprint. No `_sync/`, no `recv`.
- The 04.1 strict-loop CI fixture had *not* fired: the auth dependency is replaced by a fake in almost every test (04.2's seam lesson, incompletely applied — the fixture guards handlers, and auth was faked out from under it).

### Diagnosis

1. **Alert → deploy correlation.** Fleet-simultaneous lag onset at a deploy boundary: the 04.1 alert did its job and named the class (slices, not freezes, not pools) within four minutes. The remaining question was only *which* slice.
2. **The stack sample answers it** — one capture, `pbkdf2_hmac` on the loop thread. Diff the deploy: the hardening PR. Mechanism fully in hand by 16:29: 600k iterations × every authenticated request × inline on the loop = the lag law with a 250 ms coefficient.
3. **Rollback at 16:31**; lag at the floor by 16:33. Total customer exposure: nine minutes of elevated p99, no errors. The system built by 04.1/04.2 — sampler, alert, stack-dump runbook — turned this class from an afternoon into single digits of minutes.
4. **The design review that followed** asked the better question: where should the KDF *live*? And the answer surprised the room: nowhere. API keys are generated 256-bit random values (`key_live_7ac…`); a KDF's cost exists to make *guessing low-entropy secrets* expensive, and against 2^256 it purchases nothing but latency. The hardening was aimed at the wrong kind of secret — SHA-256 over a high-entropy key is the correct design, and the revert was the fix. The KDF budget belongs to module 08's *password* endpoints — where `verify_password` (Code Example) homes it in the threadpool it measurably deserves.

### Root Cause

A password-grade KDF was applied to high-entropy API keys and executed inline on the event loop, adding a mandatory ~250 ms CPU slice to every authenticated request; the loop-lag alert caught the resulting fleet-wide queueing four minutes after deploy, and the correct fix was recognising that key-derivation cost defends low-entropy secrets only — fast hashing was never the vulnerability.

### Fix

*Mitigation (16:31):* rollback; nine minutes end to end.

*Permanent fix:* SHA-256 lookup retained *by decision* this time, with the reasoning recorded in the security review doc (entropy of the secret, not dogma about fast hashes, decides the hash's speed); the KDF machinery landed where it belongs — password verification, threadpooled and semaphore-capped (Code Example) — ready for module 08.

### Prevention

- **The incident closes into a named CI test** — the matrix as a gate for the auth path specifically, with the seam un-faked:

```python
# tests/perf/test_auth_dependency_slice_budget.py
async def test_api_key_resolution_stays_under_slice_budget(real_auth) -> None:
    """The 18 Nov hardening put 250ms of KDF on the loop per request; auth was
    faked in every test the strict-loop fixture guarded. This test runs the
    REAL dependency under the 20ms budget (04.1) — hashing choices for the
    hot path answer to it (04.7)."""
    with strict_loop(slow_callback_duration=0.020):
        await resolve_api_key("key_live_7ac" + "x" * 32)
```

- The security-review checklist gains the entropy rule: *KDF cost scales with guessability — passwords yes, random tokens no* — so the next hardening PR argues entropy, not pattern-matching.
- The stack-sample runbook (04.2) annotated with this fingerprint: own-frames + smooth lag + deploy edge = CPU slice; the three-signature table now covers all of module 04's first act.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...CPU work runs inline in a handler? | The loop freezes for its duration (measured: max lag = task length); at any RPS the lag law multiplies it into everyone's p99. |
| ...you move it to a thread without checking the GIL? | Pure-Python work limps the whole loop (~20 ms tax measured) — no freeze, no alert in light testing, fleet-wide floor in production. Measure with the sampler. |
| ...the library releases the GIL? | Threads are the right home: loop at the floor while another core burns (measured). Cap concurrency with a semaphore; it still spends 03.6 tokens. |
| ...the process pool is created per request? | ~550 ms of spawn per call (measured) — worse than the work. Lifespan-owned, warmed, sized to cores minus the loop's. |
| ...arguments/results are large? | Pickle freight both ways prices the trip; ship references (paths, ids) not payloads, or the work wasn't process-pool-shaped. |
| ...N CPU requests arrive at once? | N cores of demand: uncapped, they starve the loop's own core and each other. Semaphore on the endpoint (04.5) or shed (02.12/04.3's shapes). |
| ...a pool worker crashes mid-task? | `BrokenProcessPool` to the awaiting request — a mapped problem (03.8), pool rebuilt by supervision; the process boundary contained it. |
| ...the burn scales with user input? | It will outgrow every row: bound the input in the contract (02.5) or leave the request path for an operation (02.10). |
| ...the deploy carries a new "small" CPU cost? | The lag alert is the tripwire (proven: 4 minutes) — but only for code the tests don't fake; keep real dependencies under the strict loop. |

## Common Pitfalls

**"Async handles it."** The loop schedules waiting, not working — CPU work has no await to interleave at. *Instead:* the matrix; the sampler run that places your workload takes one minute.

**Thread-and-done.** Row two ships quietly: pure-Python in the executor still shares the GIL, taxing every slice. *Instead:* verify release by measurement; process pool for holders.

**Folklore about the GIL instead of facts.** Which calls release it is per-library, per-version. *Instead:* the lab's harness is the test — thread it, sample it, read the floor.

**Per-request pools and cold pools.** Half a second of spawn attributed to some innocent request. *Instead:* lifespan-owned, warmed at boot, shut down with `cancel_futures`.

**Hardening by pattern-matching.** "Fast hash = bad" shipped 250 ms per request against a threat that didn't exist. *Instead:* the entropy rule — KDF cost defends guessable secrets; random tokens need speed and secrecy, not slowness.

**Faking the very code your budget fixture guards.** The strict-loop CI never saw the KDF because tests faked auth. *Instead:* at least one test path runs every hot-path dependency for real under the budget (04.2's transport-fake lesson, applied to internal seams).

## How to Test This

- The slice-budget test on real hot-path dependencies (above): strict loop, 20 ms budget, no fakes on the code being budgeted.
- The placement harness from the lab as a reusable fixture: assert a given callable, run in a thread, keeps sampler p50 at the floor — the "does it release the GIL" fact pinned per dependency version.
- A pool-lifecycle test: warm submit under 5 ms overhead, `BrokenProcessPool` maps to its problem type, shutdown cancels futures (03.9's teardown discipline).

## Interview Questions

1. *Explain.* Why can't the event loop help with CPU-bound work, and what are the four placements? — The loop interleaves waits; computation never waits. Inline (freeze), thread+GIL-holding (limp — shared interpreter), thread+GIL-releasing (clean), process pool (clean + freight).
2. *Debug this.* Fleet-wide smooth lag beginning exactly at a deploy, core pegged, stack sample shows your own frames in a hash function. — A CPU slice added to a hot path (here: KDF on API-key auth); roll back, then ask whether the work belongs at all before choosing a home.
3. *Explain.* Why does pure-Python work in a thread still hurt the loop, and by how much? — Both threads contend for the GIL, handed over each switch interval (5 ms); measured ~20 ms median lag — alive but taxed, multiplied by 04.1's law.
4. *Design.* Home password verification for a login endpoint (KDF ~250 ms). — pbkdf2/argon2 release the GIL: threadpool via `to_thread`, semaphore-capped to a core budget, constant-time compare; never inline, never a process pool's freight for a 32-byte result.
5. *Explain.* The economics that decide process-pool admission. — ~550 ms spawn (paid once, in lifespan), ~1.5 ms pickle/IPC per call: work must dwarf its round-trip and serialise small; otherwise threads (if releasing) or a worker service.
6. *Design.* An endpoint that renders large PDFs (2–8 s CPU). — Not a request: 02.10 operation + worker fleet (03.10); inside the worker the same matrix applies (process parallelism, bounded input); the API returns 202 + handle.
7. *Explain.* When is a *fast* hash the secure choice? — When the secret is high-entropy (random API keys/tokens): KDF slowness prices guessing, and 2^256 can't be guessed; slow hashing there is pure self-inflicted latency. Entropy decides, not pattern.

## Key Takeaways

- CPU work has no await: the loop can only be frozen by it (inline), taxed by it (GIL-holding thread, ~20 ms measured), or freed from it (GIL-releasing thread / process pool — both at the floor).
- The GIL question is empirical per library: one sampler run answers it, and KDFs/compression/hashing mostly release — 03.6's pool is better than folklore says.
- Process pools are lifespan infrastructure with measured economics: ~550 ms to build, ~1.5 ms per trip — warm once, cap workers, ship references not payloads.
- Cap CPU concurrency like any pool (semaphore): N simultaneous burns are N cores of demand against the loop's one.
- The zeroth question beats every row: bounded-small stays inline; everything that grows leaves the request (02.10/03.10).
- The 04.x observability stack paid out: lag alert in 4 minutes, stack fingerprint (own frames, smooth lag, deploy edge) in one sample, nine minutes end to end — but only for code the tests didn't fake.
- Security costs are engineering costs: KDF slowness is a *purchase* justified by secret guessability — high-entropy tokens buy nothing with it. Entropy, not dogma.
