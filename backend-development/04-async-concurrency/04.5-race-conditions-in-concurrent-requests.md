# 04.5 Race Conditions in Concurrent Requests — asyncio.Lock and Queue

> **Prerequisites:** 04.1 (no preemption between awaits) · 04.4 (what may live in-process: ambient/telemetry state) · 04.2/04.3 (the token refresh this notebook breaks) · 01.6 (per-process state and replicas) · modern-python 12.5 (TaskGroup, Queue — assumed)
> **What you'll learn:**
> - State the async atomicity rule precisely — code between awaits cannot race — and its corollary: every race lives at an await point
> - Recognise check-then-act across an await as the master pattern behind stampedes, double-initialisation and lost in-process updates
> - Fix it three ways — Lock with double-check, shared-task single-flight, queue-fed single writer — and choose between them on purpose
> - Use `asyncio.Semaphore` and bounded `Queue` as what they are: concurrency budgets and backpressure, not just synchronisation trivia
> - Draw the boundary where in-process coordination stops being the answer (one process) and the database/Redis takes over (04.6, 10.x)
> **Level:** Advanced

> ⚡ **Tuesday 3 November, 08:47** — tax lookups fail fleet-wide for ninety seconds, then heal; the same storm has been firing at 47 minutes past every hour for a week, small enough that nobody paged. The cause: three lines that check a token before refreshing it.

## Concept

### Plain-English Explanation

The comforting folklore about asyncio is "single-threaded, so no locks needed". It is exactly half true, and both halves matter. True: within one process there is no preemption (04.1) — a stretch of code with no `await` in it runs to completion, untouched, so the data races that plague threads (torn reads, interleaved byte-level writes) do not exist. False as a conclusion: the moment your read-modify-write, or check-then-act, spans an `await`, every other request in the process may run *inside* your operation — and unlike thread preemption, which strikes anywhere, async interleaving strikes at points you can list. That is the async trade: fewer races than threads, but each one sitting *exactly* where your code declares "I pause here", wearing an innocent keyword.

This notebook is about the state that legitimately lives in one process and gets touched by many requests — cached credentials, lazily built singletons, in-process queues, counters — and the small set of tools that make touching it safe.

### Technical Explanation

**The atomicity rule, measured.** One hundred concurrent tasks incrementing a shared counter:

```text
no await inside the operation : 100/100
one await inside the operation:   1/100
```

The first line is the true half of the folklore: no locks, perfect result, because `+= 1` never yields. The second is the rest of the story — read, `await`, write-back: ninety-nine of one hundred updates lost, because every task read the counter before any wrote it. ⚠️ Nothing about the code *looks* one hundred times worse; the entire difference is one await between the read and the write. The rule to carry: **an invariant is safe if every operation that maintains it completes without yielding; it is unprotected the moment any of them awaits.**

**Check-then-act is the master pattern.** Almost every in-process race in a web service is this shape: *check* some condition ("token expired?", "singleton missing?", "not yet sent?"), then *act* on it (refresh, build, send) — with the act containing an await. Every request that performs the check during the act's await sees the same stale condition and acts too. At concurrency N, one intended action becomes N actions: the **stampede**. Captured, against a fake provider whose newly issued token invalidates the previous one (the harshest real-world policy):

```text
30 concurrent tax calls hitting an expired token
naive         -> token issuances: 30   calls failing 401: 29/30
lock          -> token issuances:  1   calls failing 401:  0/30
single-flight -> token issuances:  1   calls failing 401:  0/30
```

The naive column deserves a slow read: thirty refreshes happened, *and twenty-nine calls still failed* — each herd member's fresh token was invalidated by the next member's refresh before it could be used. A stampede is not merely wasteful; against stateful endpoints it is mutually destructive.

**The toolkit** is four primitives, all loop-local, none thread-safe, each with one honest job. **`asyncio.Lock`**: mutual exclusion between tasks — with the mandatory *double-check* after acquiring, because the condition may have been fixed by whoever held the lock first. **The shared task** (single-flight): instead of excluding others, let them `await` the *same* refresh task — one action, N waiters, and the result distributes automatically. **`asyncio.Semaphore(n)`**: not exclusion but budget — at most n inside a region (captured: 20 tasks, cap 5, observed max in-flight exactly 5) — the formal name for 04.3's mitigation semaphore. **Bounded `asyncio.Queue`**: hand work to a single consumer task and let `maxsize` pace producers — captured: 12 puts into `maxsize=4`, five returned instantly and seven *blocked* until the consumer caught up. 03.12's `Queue(maxsize=256)` was this pattern; the bound is not a tuning detail but the backpressure itself.

**The boundary.** Everything above coordinates *one process*. The moment the invariant spans replicas — one invoice number sequence, one idempotency verdict, one at-most-once send — no asyncio primitive can hold it, because there are twelve loops (01.6's incident was exactly this confusion). In-process tools protect in-process resources: this process's token cache, this process's queue to its writer task. Cross-process invariants belong to the database's locks and constraints (04.6, 05.x) or Redis (10.x).

### Mental Model

> Between awaits you hold the only microphone in the room — say anything, uninterrupted. An `await` passes the microphone, and everyone waiting speaks before you get it back. A race is a sentence you assumed you'd finish in one turn. So read your critical operations the way the scheduler does: **every `await` is a seam where the world may change**, and the fix is either to finish the sentence in one turn (no await inside), to take the talking stick (`Lock`), or to have one designated speaker everyone listens to (single-flight task, queue consumer).

## How It Works

The stampede's anatomy — the incident's three lines, interleaved at concurrency three (the real one was thirty):

```text
       cache = {token: EXPIRED}
req-1  check: expired ✓ ──▶ await issue_token() ──────────┐  (in flight)
req-2  check: expired ✓ ──▶ await issue_token() ────────┐ │  (same stale check!)
req-3  check: expired ✓ ──▶ await issue_token() ──────┐ │ │
                                                      │ │ └▶ tok_001  (invalidated…)
                                                      │ └──▶ tok_002  (…by this)
                                                      └────▶ tok_003  (…and this)
req-1  uses tok_001 ──▶ 401        the herd's tokens kill each other;
req-2  uses tok_002 ──▶ 401        only the LAST issuance survives,
req-3  uses tok_003 ──▶ 200        and the provider just served 3× the load
```

The two repair shapes, side by side — exclusion versus designation:

```text
Lock + double-check                      single-flight (shared task)
────────────────────────                 ──────────────────────────────
fast path: token valid? return it        fast path: token valid? return it
async with lock:                         refresh_task exists and alive?
    token valid NOW? return it  ◀━ the       └─ no: create ONE task
    token = await issue()          double    await refresh_task   ◀━ N waiters,
    return token                   check                             one action
```

Both measured identical (1 issuance, 0 failures). Their difference is temperament: the lock *serialises* — latecomers queue even on the fast path if you scope it wrong, and a slow refresh holds the lock for its full duration; single-flight *broadcasts* — waiters attach to work already in progress and failures propagate to the whole cohort at once (which you must then handle: a failed shared task must be cleared so the next caller retries, not inherited forever). The queue-fed **single writer** is the third temperament — don't guard the state, *own* it: one supervised task (03.9) is the only code that ever touches the resource, requests submit intentions through a bounded queue, and the race is gone by construction because concurrency never reaches the state at all. 03.12's socket writer was this; module 12 builds on it.

## Code Example

The incident's fix as it shipped — Ledgerly's token cache, single-flight with the failure path handled:

```python
# ledgerly/clients/tax_auth.py (the 04.2 reimplementation, now race-safe)
class TokenCache:
    """One refresh in flight per process, however many requests need it.
    Provider tokens: 60min TTL; refreshed REFRESH_MARGIN early so the herd
    boundary never coincides with expiry itself."""

    def __init__(self, client: httpx.AsyncClient) -> None:
        self._client = client
        self._token: Token | None = None
        self._refresh: asyncio.Task[Token] | None = None

    async def get(self) -> Token:
        if self._token and not self._token.expires_within(REFRESH_MARGIN):
            return self._token                     # fast path: no coordination at all
        if self._refresh is None or self._refresh.done():
            self._refresh = asyncio.create_task(self._issue())   # ONE flight
        try:
            # shield: a cancelled WAITER (its request timed out) must not kill
            # the flight every other request is awaiting — measured in 04.8
            self._token = await asyncio.shield(self._refresh)
        except Exception:
            self._refresh = None                   # ⚠️ clear it: a failed flight must
            raise                                  # not poison every future caller
        return self._token

    async def _issue(self) -> Token:
        r = await self._client.post("/oauth/token", data=CLIENT_CREDENTIALS)
        r.raise_for_status()
        TOKEN_REFRESHES.inc()                      # the metric the incident lacked
        return Token.from_response(r.json())
```

Three lines carry the design. The fast path touches no primitive — coordination costs nothing when the token is healthy. The `done()` check plus `create_task` is the single-flight gate: whoever arrives during a live refresh awaits it rather than starting another. And the `except` clause is the part reviews miss: without clearing `_refresh`, one failed refresh becomes an immortal poisoned task that every future request awaits and re-raises — the stampede fix turned into a permanent outage.

For contrast, the same safety via `Lock` — right when the acted-on state is genuinely exclusive rather than shareable:

```python
# the exclusion shape: lazy per-process resources built exactly once
_init_lock = asyncio.Lock()

async def warm_rate_table(app_state) -> RateTable:
    if (table := app_state.get("rates")) is not None:
        return table
    async with _init_lock:
        if (table := app_state.get("rates")) is not None:
            return table                           # the double-check: the first
        app_state["rates"] = await load_rates()    # holder already did the work
        return app_state["rates"]
```

Skip the double-check and the lock still "works" — requests serialise politely through it and *each one reloads the table*, which is the original bug wearing a seatbelt.

## Design Patterns / Tradeoffs

### Choosing the primitive

- **Nothing** — restructure so the operation doesn't yield mid-invariant (compute-then-swap: build the new value locally, assign in one statement). *Advantages:* zero coordination, zero deadlock surface. *Use when:* the await can be hoisted out of the critical span. Always the first question, not the fallback.
- **`Lock` + double-check** — exclusive access when the act must happen at most once *and* callers arriving later should reuse the result via the state, not the flight. *Failure modes:* forgetting the double-check (serialised stampede); holding it across unrelated slow awaits (a 03.11-style loan: everyone queues behind one slow holder); mixing it with `threading.Lock` (loop-bound vs thread-bound — an asyncio.Lock does nothing for 03.6's threads, and holding a threading.Lock across an await blocks the loop, 04.2). *Use when:* protecting mutation of exclusive state — lazy init, cache rebuild.
- **Single-flight shared task** — deduplicate identical concurrent work; waiters share one result. *Failure modes:* the poisoned-task leak (clear on failure); cancellation — ⚠️ a naive `await shared_task` lets one cancelled waiter cancel the flight for everyone (measured in 04.8; waiters `shield` the await). *Use when:* the work is idempotent-to-share: token refresh, cache fill, config fetch. **Ledgerly's choice** for the incident.
- **`Semaphore(n)`** — a budget, not a guard: caps concurrency toward a resource (04.3's per-dependency cap, formalised). *Failure mode:* mistaking it for exclusion — n>1 protects no invariant. *Use when:* the problem is "too many at once", not "wrong interleaving".
- **Bounded `Queue` + single writer** — ownership: one supervised task is the only toucher; the bound is the backpressure (measured: producers block when the writer lags). *Failure modes:* unbounded queue (the imbalance hides as memory until it doesn't — 03.12); writer death (supervision, 03.9); and the at-most-once caveat — an in-process queue *is* BackgroundTasks-grade durability (03.10), so must-happen work still rides the outbox. *Use when:* ordering matters, the resource is serial by nature (a socket, a file, a sequence), or contention is constant rather than exceptional.

**Recommendation:** hoist the await if you can; single-flight for shareable work; lock+double-check for exclusive state; semaphore for budgets; queue-writer for owned serial resources. And none of them across processes — that line is where 04.6 begins.

## Production Scenario

**Ledgerly, Tuesday 3 November, 08:47.** Month-start invoicing is in full swing when tax-dependent routes fail at 40% for roughly ninety seconds, then recover on their own. On-call scrolls back: the same storm — smaller — fired at 07:47, 06:47, 05:47… a week of hourly blips just under the alert threshold, each self-healing before a human looked. Today's month-start concurrency pushed it over.

### Symptoms

- `POST /oauth/token` to the tax provider: a burst of ~350 calls in two seconds at :47, most answered **429** (their token endpoint allows 10/min per client id). Normal rate: 12 per hour, one per replica.
- Failing tax calls mapped through 03.8 as `upstream-auth` problems; traces show the failure inside the *refresh*, not the rate lookup.
- The periodicity is exact: 47 minutes past each hour — and the fleet's tokens all expire together because Monday's 16:47 deploy (03.14: rolling restart) had every replica fetch its first token within the same minute. Token TTL 60 min; the fleet re-synchronises itself hourly forever.
- Between storms: perfectly healthy. The 04.1/04.2/04.3 signatures all absent — no lag, no freezes, no pool starvation.

### Diagnosis

1. **Alert → Metrics.** The shape *is* the clue: strictly periodic, self-healing, amplitude tracking concurrency. Cron-shaped failure with no cron = a synchronised cache expiring. The :47 phase matching Monday's deploy time turns suspicion into arithmetic.
2. **Count the refreshes.** No metric existed for token issuance (the incident's first lesson) — but the provider's 429s are countable from error logs: ~350 refresh attempts per storm across 12 replicas ≈ 30 concurrent tax calls per replica each independently deciding to refresh. Thirty deciders, one decision needed.
3. **Read the writer.** The 04.2 reimplementation — praised at the time for being ~40 lines — contains `if token_expired(): token = await issue_token()`. Check, await, act: every request whose check ran during a neighbour's in-flight refresh joined the herd. The lab's measurement is the mechanism in miniature: at width 30, one intended refresh becomes thirty.
4. **Eliminated:** the provider (their 429s are *correct* — the contract is 10/min and the herd broke it); load itself (between :47s the same traffic is fine); and 04.3's pools (connections were plentiful — the starvation here is of a *credential*, not a connection).

### Root Cause

The per-process token cache refreshed via unguarded check-then-act across the refresh await, so at each synchronized expiry every concurrent tax call launched its own refresh; the fleet's deploy-aligned token TTLs concentrated ~350 simultaneous refreshes into a 10/min-limited endpoint, and the resulting 429s failed ninety seconds of tax-dependent traffic — hourly, on a timer set by Monday's deploy.

### Fix

*Mitigation (09:05):* config change, no code: `TOKEN_REFRESH_MARGIN` raised from 0 to 300 s with ±60 s jitter per replica — refreshes now happen *early and de-synchronised*, so the next boundary spreads 12 replicas across two minutes instead of stacking them at :47 with expired tokens. The 09:47 storm doesn't fire.

*Permanent fix:* the single-flight `TokenCache` (Code Example) — one refresh per process per expiry, with the failed-flight clearing and the issuance metric. Fleet-wide worst case drops from 350 calls to 12, inside the provider's limit with room to spare.

### Prevention

- **`token_refreshes_total` and a rate alert** — 30× the replica count in a minute is a stampede signature worth paging on regardless of customer impact; the metric that would have shown a week of warning shots.
- **The incident closes into a named CI test** — the lab's measurement as a regression gate:

```python
# tests/races/test_token_refresh_is_single_flight.py
async def test_thirty_concurrent_calls_one_refresh(fake_provider) -> None:
    """Check-then-act across the refresh await turns 1 refresh into N and,
    against single-active-token providers, into mutual 401s (3 Nov, 04.5)."""
    cache = TokenCache(fake_provider.client)
    async with asyncio.TaskGroup() as tg:
        for _ in range(30):
            tg.create_task(cache.get())
    assert fake_provider.issuances == 1
```

- Review rule, added beside 04.1's slice budget: **every `await` between a check and its act is a finding** — the pattern is grep-adjacent (`if not.*:\n.*await`) and the question ("what if thirty requests run this line together?") takes ten seconds to ask.
- Deploy-time cache alignment noted in the 03.14 runbook: anything cached with a TTL at startup synchronises fleet-wide on every rollout — jitter belongs in every TTL the process sets for itself.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...two requests increment a counter with no await between read and write? | Safe — atomic between awaits (measured 100/100). The folklore's true half. |
| ...the operation spans one await? | Every concurrent request may interleave there (measured: 99/100 lost). Hoist the await, or coordinate. |
| ...N requests hit an expired cache entry together? | Stampede: N refreshes, and against stateful endpoints, mutual destruction (29/30 measured). Single-flight or lock+double-check. |
| ...the single-flight task fails? | Cleared-on-failure: next caller starts a fresh flight. Forgotten: every future caller awaits a poisoned task forever. |
| ...the lock is held across a slow unrelated await? | Everyone queues behind one loan-holder — 03.11's arithmetic applied to a mutex. Scope locks to the mutation, not the neighbourhood. |
| ...a `threading.Lock` meets an await, or an `asyncio.Lock` meets a thread? | The first blocks the loop (04.2's freeze); the second protects nothing. Primitives match their concurrency model; `def`-endpoint state needs thread-side tools (03.6). |
| ...the queue is unbounded? | The producer/consumer imbalance accumulates as memory until the process dies far from the cause. Bound it; the measured put-blocking *is* the feature. |
| ...the invariant spans replicas? | No asyncio primitive applies — twelve loops share nothing (01.6). Database constraints and locks (04.6), or Redis (10.x). |
| ...the writer task dies? | The queue backs up silently against a corpse — supervision with restart counting (03.9), and the queue-depth metric alerts. |

## Common Pitfalls

**"Single-threaded means no races."** Half true, and the false half ships: any check-then-act across an await races at exactly that await. *Instead:* the review question — what if thirty requests run this together?

**Lock without the double-check.** The herd serialises and each member repeats the work — the bug with extra latency. *Instead:* re-verify the condition after acquiring, always.

**Single-flight without failure clearing.** One failed refresh poisons every future caller. *Instead:* clear the shared task in `except`, re-raise, let the next caller retry.

**Guarding the whole operation instead of the mutation.** A lock around "call provider + update cache" serialises all tax traffic to fix a cache race. *Instead:* fast path lock-free; critical section = the mutation alone.

**In-process coordination for cross-replica invariants.** An `asyncio.Lock` around invoice-number allocation "fixes" the race in every test and ships 01.6's incident. *Instead:* the process boundary is the tool boundary — DB/Redis beyond it (04.6).

**Unbounded queues as decoupling.** They decouple until memory couples everything. *Instead:* `maxsize` chosen like any pool limit (04.3), with put-timeout semantics decided on purpose.

**Deploy-synchronised TTLs.** Every replica caching at startup with equal TTLs builds an hourly fleet-wide thundering herd. *Instead:* jitter in every self-set TTL; margin so refresh precedes expiry.

## How to Test This

- The single-flight regression test above: 30 concurrent callers, assert exactly one issuance against the fake provider — fails against check-then-act in milliseconds.
- A poisoned-flight test: fail the first refresh, assert the *second* caller triggers a fresh one (the `except` clause verified).
- An interleave stress harness (the lab's shape): any suspected shared-state operation run 100-wide with `sleep(0)` injected at each await point — lost-update counting as assertion, not inspection.
- The queue-writer's supervision test: kill the writer, assert restart-counter increments and queue depth drains (03.9's pattern, retargeted).

## Interview Questions

1. *Explain.* Why does async code race less than threaded code, and where exactly does it still race? — No preemption between awaits makes await-free spans atomic; every race therefore sits at an await inside a read-modify-write or check-then-act. You can enumerate the hazard points from the code.
2. *Debug this.* A dependency fails for ~90 s at the same minute every hour, self-heals, and worsens with load; provider shows bursts of 429 on their auth endpoint. — Synchronised cache expiry (deploy-aligned TTL) plus a refresh stampede from unguarded check-then-act; fix with margin+jitter now, single-flight permanently.
3. *Design.* A token cache for one process serving 200 concurrent requests. — Fast path lock-free on a validity margin; single-flight refresh via a shared task; clear on failure; jittered margin; issuance metric; the 30-callers-one-refresh test.
4. *Explain.* Lock-with-double-check vs single-flight — when each? — Lock guards exclusive *state* (lazy init, rebuild): latecomers reuse via the state. Single-flight shares the *work*: waiters join a live flight — right for idempotent shareable fetches; needs failure-clearing and cancellation care.
5. *Explain.* What is a bounded queue actually for in a server? — Ownership (single writer serialises a resource) plus backpressure: a full queue makes producers wait, converting imbalance into pacing instead of memory growth. The bound is the contract.
6. *Debug this.* After "fixing a race with a lock", the endpoint is slow under load and the duplicate work still happens once per waiter. — Lock without double-check, scoped around the whole operation: serialised stampede. Re-check inside; shrink the critical section.
7. *Design.* Where does in-process coordination end? — At the process: any invariant spanning replicas (sequences, at-most-once, quotas) needs the shared store's primitives — DB locks/constraints (04.6), Redis (10.x). Asyncio primitives protect only this loop's state.

## Key Takeaways

- Between awaits, async code is atomic (measured 100/100); across one await, unprotected (measured 1/100). Every race has an address, and it is an `await`.
- Check-then-act across an await is the master bug: at concurrency N it becomes N acts — and against stateful endpoints, N mutually destructive ones (29/30 failed calls measured).
- Single-flight (shared task) for shareable work, Lock+double-check for exclusive state, Semaphore for budgets, bounded Queue+single writer for owned serial resources — and hoisting the await beats all of them.
- The two clauses reviews miss: the double-check after acquiring, and clearing a failed shared flight — each omission is its own incident.
- Bounded queues are backpressure by construction (measured: producers block); unbounded ones are memory leaks with better manners.
- Deploy-aligned TTLs synchronise the whole fleet into hourly herds — jitter every TTL your process sets for itself.
- In-process primitives stop at the process: cross-replica invariants belong to the database and Redis — which is the next notebook.
