## Concept

### Plain-English Explanation

Module 03 assembled the application; module 04 goes inside the machine that runs it. One uvicorn worker (one per container since 03.14) is, at its heart, a single thread running a loop: *look at which sockets and timers are ready, run every piece of work that readiness unblocked, repeat*. Every request your process is "concurrently" serving is a coroutine parked at an `await`, waiting its turn on that one thread. Concurrency here is an accounting trick — one worker interleaves many conversations — and the entire trick rests on each piece of work giving the thread back quickly.

That last clause is the part with production consequences. Between two `await`s, your code owns the thread outright — nothing else runs, no matter how urgent. Most of this module is about the ways that ownership goes wrong; this notebook builds the model of the machine itself and the one metric that watches it.

### Technical Explanation

**The loop's iteration** is three steps. Poll the **selector** — the OS facility (epoll on Linux, IOCP behind Windows' Proactor) that reports which sockets became readable or writable — with a timeout set by the nearest timer. Move the callbacks that readiness unblocked onto the **ready queue**. Then drain the queue: each entry runs *to completion* — for a task, that means to its next `await` on something not yet ready. There is no preemption; ⚠️ the scheduler cannot interrupt a slice that is overstaying, because the scheduler is the same thread, and it is not running while your code is.

**A request's life in those terms.** The listening socket goes ready → uvicorn's protocol callback parses the request and **creates a task per request** → the task runs your handler until its first genuine wait (the DB via 03.5's session, the tax provider over httpx) → parks; the loop serves others → the response arrives from the dependency, the socket goes ready, the task rejoins the ready queue → runs to its next await, and eventually to `send`. Captured — three requests on one thread, every boundary an `await`:

```text
t=0.00s [MainThread] req-1: handler entered
t=0.00s [MainThread] req-2: handler entered
t=0.00s [MainThread] req-3: handler entered      ← all three IN before any resumes
t=0.05s [MainThread] req-1: resumed after DB
t=0.06s [MainThread] req-2: resumed after DB
t=0.06s [MainThread] req-3: resumed after DB
t=0.12s [MainThread] req-1: response ready
```

**The lag law.** Because the queue is drained one slice at a time, a task that becomes ready must first wait for every slice ahead of it. Define **loop lag** as the gap between "scheduled to run" and "actually ran" — measurable as how late a short sleep fires. Then to first order **lag ≈ ready-queue depth × typical slice length**, and — this is the operational point — that lag is added to *every* request in the process, at *every one of its awaits*, regardless of whose slices caused it. Captured, workers each burning a 5 ms await-free slice:

```text
 0 tasks -> sampler's 10ms sleep fires    5.8 ms late     ← platform timer floor
 4 tasks -> sampler's 10ms sleep fires   50.7 ms late
 8 tasks -> sampler's 10ms sleep fires  111.1 ms late
16 tasks -> sampler's 10ms sleep fires  232.5 ms late
```

Linear, as predicted. Two readings of the same table: a handler that keeps its slices near zero buys the whole process headroom; and a process whose lag is 50 ms has silently added 50 ms to the p99 of its *fastest* endpoint. The 03.6 threadpool hangs off this same loop — `def` routes hand work to threads, but the *hand-off and the response path* still ride the queue.

**One core, and the metrics trap that follows.** The loop uses one core; with 03.14's one-worker-per-container layout, a loop at 100% is one core pegged — on an eight-core host graphed as ~12% CPU. Fleet CPU averages are structurally incapable of showing this saturation, which is why the lag metric, not CPU, is the loop's health signal.

### Mental Model

> A worker is a single cashier serving fifty customers by switching whenever one pauses to check their phone. Throughput looks concurrent; the till is strictly serial. **Loop lag is the length of the line at the till** — it is paid by everyone, caused by whoever lingers, and it appears on no per-customer receipt. If you graph one thing about an async server, graph the line.

## How It Works

One loop iteration, with the law annotated:

```text
        ┌────────────────────────── one iteration ──────────────────────────┐
        │ 1. selector.poll(timeout=next timer)                              │
        │      OS: "sockets 12, 41 readable; timer for Task-7 due"          │
        │ 2. ready queue ← callbacks/tasks those events unblocked           │
        │ 3. drain:  [slice][slice][slice][slice]  ← each runs to its next  │
        │            └──── lag for the LAST = sum of slices before it ────┘ │
        └───────────────────────────────────────────────────────────────────┘
   request task timeline:   parse ▸ run──await DB ▸ (parked) ▸ ready ▸ WAIT ▸ run──await tax ▸ …
                                                              ^^^^^^
                                    loop lag: paid HERE, at every await, by every request
```

And the failure geometry this notebook exists to teach — contrast it with 03.6's:

```text
03.6  one def endpoint, 3s calls   → 40 threads pinned → def routes stall TOGETHER,
                                     async routes keep running (the pool saturates)
04.1  many small sync slices       → ready queue deepens → EVERY route slows a little,
      (30–50ms each, no villain)     then a lot; nothing is "down", p99 just climbs
04.2  one long await-free stretch  → the loop is GONE for its duration: even accepts
      (next notebook)                queue; heartbeats miss (03.14's gunicorn kill)
```

The middle row is the sneaky one: it has no single guilty endpoint, no saturated dependency, and no error — only a fleet-wide latency drift that tracks load. Its telemetry signature is *uniformity*: every route's p99 rises by roughly the same absolute amount, because they all pay the same queue. The signature of a slow dependency is the opposite — concentrated in the routes that call it.

## Code Example

The detector asyncio ships with — debug mode names any slice that overstays a budget. Captured:

```text
loop.set_debug(True); loop.slow_callback_duration = 0.02      # 20ms budget
asyncio: Executing <Task finished name='Task-43' coro=<chunky() ...> took 0.051 seconds
```

That line is the review comment you didn't have to write: the exact task, the exact cost. It is too expensive to leave on in production, which is where the sampler comes in — 03.9's supervised background task, now with its purpose stated: what Ledgerly's sampler samples *is loop lag*, emitted as the process's headline health metric:

```python
# ledgerly/observability/loop_lag.py — the 03.9 sampler, formalised (15.x wires export)
async def loop_lag_sampler(interval: float = 0.5) -> None:
    """Measures how late a short sleep fires: the queue's length in milliseconds.
    Supervised per 03.9 — restarts counted, cancellation re-raised."""
    while True:
        t0 = time.monotonic()
        try:
            await asyncio.sleep(interval)
        except asyncio.CancelledError:
            raise                                    # 03.9: never swallow shutdown
        LOOP_LAG_MS.observe((time.monotonic() - t0 - interval) * 1000)
```

Finally the incident's mechanism, measured on a real server: an innocent `/v1/ping` while four clients loop on the invoice report endpoint. The report route is *fast* — it just serialises a big page in one slice:

```text
idle baseline                      ping p50=   4.7 ms  p95=  10.8 ms
4 x /reports?limit=5000 looping    ping p50=  35.6 ms  p95=  57.7 ms   ← bystander taxed
4 x /reports?limit=200  looping    ping p50=   9.7 ms  p95=  17.6 ms   ← page cap = slice cap
```

Nothing about `/v1/ping` changed between the rows. What changed is the queue it stands in: serialising 5,000 response models is one 30–50 ms await-free stretch (FastAPI validates and dumps the list in a single slice), and four of those in flight keep the queue deep. Cap the page and the slice shrinks with it — 02.5's "cap page size in the contract" rule, which arrived there as an API-design nicety, turns out to be **loop-slice budgeting**.

> **Version note** — captured on Windows' `ProactorEventLoop` (Python 3.14): the ~5.8 ms zero-load "lag" is the platform timer floor, and debug mode even flags the proactor's own `_loop_self_reading` handle — both Windows artifacts. On Linux, epoll timing is tighter, and uvicorn will use **uvloop** (`--loop uvloop`, Linux/macOS only) when installed; the law and the signatures are identical on all of them. Reproduce with `_lab/lab_04_01_event_loop.py`.

## Design Patterns / Tradeoffs

### Which loop, and how observed

- **stdlib asyncio** (uvicorn's default): everywhere, debuggable, boring — the right default. *Failure mode:* none of its own; it just faithfully runs your slices.
- **uvloop**: a libuv-based drop-in, typically 2–4× faster at the *loop machinery* (polling, callbacks, transports). *Disadvantages:* Linux/macOS only; marginally different edge behaviours under debugging. ⚠️ *The trap is the expectation:* uvloop speeds up the till, not your slices — a 50 ms serialisation stretch is 50 ms on any loop, so it moves the baseline, never the incident. *Use when:* Linux, high RPS, machinery overhead measurable. *Not:* as a fix for lag caused by your own code.
- **Debug mode** (`loop.set_debug(True)` + `slow_callback_duration`): the precise detector, at real overhead (every slice timed, creation stacks kept). *Use:* always in tests and staging — it is the slice budget's enforcement arm; never in production, where the **sampler** (cheap, statistical, always-on) owns the job. The pairing is the pattern: sampler tells you *that* the queue is deep in prod; debug mode in staging tells you *who*.

**Recommendation:** stdlib by default, uvloop on Linux once you measure a reason, sampler always-on with an alert, debug mode wired into CI (How to Test This). Revisit only when a profiler shows loop machinery itself on top — which for a CRUD-shaped API it essentially never is.

### Where big serialisation work should live

The incident's slices came from response building. Real alternatives: **cap the page** (the 02.5 contract cap — smallest change, bounds the slice at the source; right default); **precompute/cache the heavy representation** (10.x — right when the same big page is pulled repeatedly); **move the build off the loop** (`run_in_executor` into 03.6's threadpool — buys loop headroom at the price of pool tokens; right for rare, genuinely large one-offs); **make it a real export job** (02.10/03.10's operation + worker — right when "page" was a lie and the client wanted the dataset). *Not* an alternative: chunking the serialisation with `await asyncio.sleep(0)` sprinkled in — it converts one honest slice into many hidden ones and helps only the sampler's graph. Choose by access pattern; Ledgerly takes the cap now and the export path for the two tenants who actually wanted everything (Scenario).

## Production Scenario

**Ledgerly, Thursday 8 October, 09:12.** Quarter-end. Finance teams at a dozen tenants start their morning reconciliation pulls. The fleet-wide p99 alert fires: API p99 has gone from 180 ms to 610 ms. 5xx: zero. DB: healthy, pool waits zero (the 03.11 dashboards). Redis: healthy. RPS: up 40% — busy, not extraordinary.

### Symptoms

- **Every route is slower by roughly the same amount** — `/v1/ping`-class endpoints included, which touch no dependency at all. The degradation is uniform, not concentrated.
- Traces show the time in none of the spans: DB spans normal, outbound spans normal — the growth is in the *gaps between* spans, unattributed request-local time.
- Per-container CPU: the api process pinned near one full core; the host graph reads 13% and alerts on nothing.
- `event_loop_lag_ms` (the 03.9 sampler's metric, emitted since module 03 but never given an alert): p50 lag 40–60 ms on exactly the replicas serving report traffic, tracking the p99 delta almost 1:1.

### Diagnosis

1. **Alert → Metrics.** Uniform per-route degradation eliminates every dependency-shaped hypothesis at once: a slow DB or slow tax API would tax its callers, not `/v1/ping`. Something *process-local and shared* is adding a constant.
2. **Traces.** The added time is between spans — after the DB returned, before the response was sent. That interval is loop-queue time; nothing else lives there.
3. **The lag metric names the queue.** Lag 40–60 ms on report-serving replicas; near zero elsewhere. Correlate requests on those replicas: `/v1/reports/invoices?limit=500` (the contract's maximum), rows fat with line summaries — quarter-end's favourite call, at 4–6 concurrent per replica.
4. **Confirm the slice.** In staging, debug mode with a 20 ms budget: `Executing <Task ... report ...> took 0.048 seconds` per page — the serialisation of 500 heavy rows in one await-free stretch. Four concurrent ≈ a standing 50 ms queue: the lag law, with the measured numbers from the Code Example.

### Root Cause

Between awaits, response serialisation runs as one uninterruptible slice on the worker's only thread; quarter-end report pages at the contract's maximum size produced 40–50 ms slices at steady concurrency, and the resulting ready-queue depth added that lag to every request the process served — a uniform, dependency-free, error-free p99 collapse.

### Fix

*Mitigation (09:31):* scale api replicas ×2 (halves per-loop report concurrency — lag is per-process, so spreading reporters dilutes it), and an edge concurrency cap of 2 in-flight report pulls per tenant (02.12's machinery). p99 back under 250 ms by 09:44.

*Permanent fix:* the report page maximum drops from 500 to 200 in the *contract* (02.5's cap, now with its real justification — a page size is a slice budget), with `Deprecation` headers on larger requests per 02.13; the two tenants who genuinely wanted the full dataset get the 02.10 export operation instead, built in a worker (03.10) where slices tax nobody. And the **slice budget becomes policy**: no await-free stretch over 20 ms in request handlers, enforced below.

### Prevention

- **The lag alert that should have existed**: `event_loop_lag_ms p50 > 25ms for 5m` pages — it led the customer-visible p99 by minutes and named the replica set.
- **The incident closes into a named CI test** — the whole suite runs under a strict loop, so any handler growing a chunky slice fails the build with the task named:

```python
# tests/conftest.py (13.x wires the plumbing)
@pytest.fixture(autouse=True)
def strict_event_loop(event_loop, caplog):
    """Debug mode as CI enforcement: any await-free stretch over 20ms in any
    exercised handler fails the test that exercised it (04.1)."""
    event_loop.set_debug(True)
    event_loop.slow_callback_duration = 0.020
    yield
    slow = [r.message for r in caplog.records
            if "Executing" in r.message and "took" in r.message]
    assert not slow, f"slice budget exceeded: {slow}"
```

- Review rule, written where the 03.6 pool arithmetic lives: an endpoint returning N items owns a slice estimate; N is bounded in the contract, not in hope.

## Failure-First Checklist

| What if... | Answer |
|---|---|
| ...one handler blocks outright (no awaits for seconds)? | The loop is gone — accepts queue, heartbeats miss, everything stalls. That is 04.2's notebook (and 03.14's watchdog kill). |
| ...many handlers each burn small slices? | This notebook: lag ≈ depth × slice, paid fleet-uniformly. Watch the sampler; budget the slices. |
| ...traffic ×10? | Queue depth scales with in-flight slices: lag rises before CPU or any pool complains. The lag alert is the early one. |
| ...the DB slows down? | *Not* a loop problem: tasks park longer at awaits, the queue stays shallow. Signature: degradation concentrated in DB-calling routes; lag flat. The two signatures distinguish 04.1 from every dependency incident. |
| ...CPU shows 12% but users complain? | Per-host averages hide one pegged core (one worker = one core, 03.14). Graph per-process CPU and loop lag, not host CPU. |
| ...`def` routes are in the mix? | Their bodies run on 03.6's threads, but scheduling and response paths still ride this queue — pool exhaustion and loop lag are separate meters on the same engine. |
| ...the sampler task dies? | A dead sampler is a blind alert (03.9): supervised, restart-counted, cancellation re-raised. |
| ...lag is high only on some replicas? | Slices follow traffic mix — 03.14's contested accept means uneven work. Label the metric per replica; diagnose the mix, not the fleet average. |

## Common Pitfalls

**Reading host CPU as loop health.** One pegged core reads as ~12% on eight; the fleet graph stays green through the whole incident. *Instead:* per-process CPU and `event_loop_lag_ms`, alerted.

**Hunting for the slow endpoint when every endpoint is slow.** Uniform degradation means a shared queue, and there is exactly one: the loop's. *Instead:* check lag *first* on the fleet-wide-p99 page; it splits the diagnosis tree in one read.

**Adopting uvloop as a latency fix.** It accelerates loop machinery, not your slices; the incident reproduces identically on it. *Instead:* budget slices; take uvloop as a baseline bonus on Linux.

**`await asyncio.sleep(0)` sprinkled through heavy code.** Cosmetic yielding: total CPU unchanged, the one visible slice becomes many invisible ones, debug mode goes quiet. *Instead:* cap the work (page size), move it (executor/worker), or precompute it — the Tradeoffs table.

**Unbounded response sizes in the contract.** Every uncapped `limit` is an unbounded slice a client can schedule on your loop at will. *Instead:* contract-level caps (02.5), with the loop as the stated reason.

**Debug mode in production.** Every callback timed, creation stacks retained — you bought the detector at ambulance prices. *Instead:* sampler in prod, debug mode in staging and CI.

## Interview Questions

1. *Explain.* What does one uvicorn worker do with fifty concurrent requests? — One thread, one selector, one ready queue; a task per request runs slice-by-slice between awaits; concurrency is interleaving, never parallelism, and preemption does not exist.
2. *Explain.* Define loop lag and derive what it does to p99. — How late ready work runs: ≈ queue depth × slice length; it is added to every request at every await, so it is a process-wide latency floor that no per-endpoint view attributes.
3. *Debug this.* p99 tripled on every route including no-op health checks; DB, cache and downstreams are clean; host CPU is 13%. — Uniform degradation + unattributed trace gaps + one pegged core = loop queueing; find the chunky slices (here: max-size page serialisation), cap or relocate them.
4. *Explain.* Why does uvloop not fix this class of incident? — It speeds the scheduler's own machinery; your await-free stretches run at native speed already. The queue is your code.
5. *Design.* Loop observability for a 40-replica fleet. — Always-on lag sampler (supervised, 03.9) exported per replica; alert on p50 lag; debug mode with a 20 ms `slow_callback_duration` in staging/CI; per-process CPU; trace-gap dashboards as the correlating view.
6. *Explain.* How do the failure signatures of "slow dependency", "exhausted threadpool" and "deep ready queue" differ? — Dependency: concentrated in its callers, lag flat. Threadpool (03.6): `def` routes stall together, async routes fine. Ready queue: uniform absolute slowdown everywhere, lag climbing.
7. *Design.* A tenant needs the full 400k-row dataset your report endpoint pages. — Not through the loop: 02.10 operation + 03.10 worker builds the export; the request path keeps its slice budget; the contract page cap stays honest.

## Key Takeaways

- One worker = one thread running selector → ready queue → drain; a task per request; awaits are the only yield points and preemption does not exist.
- **Loop lag ≈ queue depth × slice length**, and it is charged to every request at every await — the process's invisible, shared latency floor.
- The signature is uniformity: every route slower by the same amount, time in the trace *gaps*, dependencies clean, one core pegged inside a green host graph.
- Graph the loop: the supervised lag sampler always-on in prod with an alert; debug mode's `slow_callback_duration` as the named-culprit detector in staging and CI.
- Slice budgets are contract design: an uncapped page size is an unbounded slice any client can schedule; 02.5's cap is loop protection wearing API clothes.
- uvloop moves the baseline, not the incident; cosmetic `sleep(0)` hides slices from the detector without shrinking them.
- Big builds belong off the loop — capped, cached, executor'd, or exported to a worker — chosen by access pattern, not reflex.
